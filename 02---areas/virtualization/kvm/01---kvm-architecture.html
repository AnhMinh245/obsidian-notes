1. KVM trong Linux Kernel

1.1. KVM không phải một hypervisor độc lập

KVM không phải một phần mềm chạy riêng biệt như ESXi. Thay vào đó, KVM là một kernel module biến Linux kernel thành hypervisor.

Phân loại: KVM thường được gọi là Type 1 (bare-metal) vì guest code chạy trực tiếp trên hardware qua VMX non-root mode. Tuy nhiên, KVM khác Type 1 truyền thống (ESXi) ở chỗ nó tái sử dụng Linux kernel thay vì viết kernel riêng. Một số tài liệu gọi đây là “hybrid Type 1”:

Trước khi load KVM module:
  Linux kernel = OS bình thường (scheduler, memory manager, drivers)

Sau khi load KVM module:
  Linux kernel = OS + Hypervisor
  ┌────────────────────────────────────────────────┐
  │ Linux kernel + kvm.ko                          │
  │   └── Mọi subsystem Linux (CFS scheduler,     │
  │       memory manager, network stack, drivers)  │
  │       đều PHỤC VỤ cho cả host processes        │
  │       VÀ VM workloads                          │
  └────────────────────────────────────────────────┘

Lợi thế kiến trúc này:

  • KVM tái sử dụng toàn bộ Linux subsystems thay vì viết lại từ đầu
  • Linux CFS scheduler → vCPU scheduling
  • Linux memory manager → guest memory management (EPT/KSM/hugepages)
  • Linux network stack → VM networking (bridge, OVS)
  • Linux device drivers → hardware support rộng nhất (hàng nghìn drivers)
  • Linux cgroups → resource limits per VM
  • Linux SELinux/sVirt → VM security isolation

Đây là lý do KVM "thắng" trong cloud

KVM leverage toàn bộ 30+ năm phát triển của Linux kernel. VMware phải tự viết VMkernel, Xen phải tự viết Dom0 drivers. KVM “miễn phí” nhận tất cả cải tiến kernel mỗi bản release.

1.2. Kernel Modules

KVM gồm 2 (hoặc 3) kernel modules:

ModuleVai trò
kvm.koFramework chung: tạo /dev/kvm, quản lý VM structures, memory regions
kvm-intel.koIntel-specific: VMXON/VMXOFF, VMCS management, EPT, APICv
kvm-amd.koAMD-specific: SVM enable, Nested Page Tables, AVIC

1.3. /dev/kvm — Cổng vào hypervisor

Khi KVM module được load, nó tạo character device /dev/kvm. Mọi tương tác với hypervisor đều qua ioctl() calls trên file descriptor này:

/dev/kvm
  │
  ├── ioctl(KVM_CREATE_VM)          → tạo VM mới, trả fd
  │     └── VM fd
  │         ├── ioctl(KVM_CREATE_VCPU)    → tạo vCPU, trả fd
  │         │     └── vCPU fd
  │         │         ├── ioctl(KVM_RUN)        → chạy vCPU
  │         │         ├── ioctl(KVM_GET_REGS)   → đọc registers
  │         │         └── ioctl(KVM_SET_REGS)   → set registers
  │         │
  │         ├── ioctl(KVM_SET_USER_MEMORY_REGION) → map RAM
  │         ├── ioctl(KVM_CREATE_IRQCHIP)         → tạo virtual APIC
  │         └── ioctl(KVM_SET_TSS_ADDR)           → set TSS
  │
  └── ioctl(KVM_GET_API_VERSION)    → version API
  └── ioctl(KVM_CHECK_EXTENSION)    → kiểm tra features

QEMU là "client" của /dev/kvm

QEMU process mở /dev/kvm, gọi các ioctl() để tạo VM, set memory, chạy vCPU. KVM kernel module xử lý tất cả hardware virtualization. Đây là phân công rõ ràng: kernel lo CPU/memory (performance-critical), QEMU lo device emulation (flexibility).

Sau khi hiểu KVM module chỉ lo CPU/memory virtualization, câu hỏi tiếp theo là: ai lo phần device emulation? → Đó là QEMU.

2.2. QEMU Process = 1 VM

Mỗi VM là một QEMU process trên host:

Thread model bên trong QEMU process:

ThreadVai tròSố lượng
Main threadEvent loop, device emulation, management1

2.3. VM Memory Model

QEMU allocate RAM cho VM bằng mmap(), sau đó đăng ký vùng nhớ này với KVM:

QEMU process address space:
┌────────────────────────────────────────────┐
│  QEMU code + data                         │
├────────────────────────────────────────────┤
│  Guest RAM (mmap'd region)                │
│  ┌──────────────────────────────────────┐  │
│  │  0x0000_0000 - 0x0FFF_FFFF          │  │ ← 256MB below VGA hole
│  │  0x1000_0000 - 0xBFFF_FFFF          │  │ ← rest of guest RAM
│  │  ...                                 │  │
│  └──────────────────────────────────────┘  │
│                                            │
│  MMIO regions (device registers)           │
│  ROM regions (BIOS, Option ROMs)           │
└────────────────────────────────────────────┘

KVM EPT maps: Guest Physical Address → Host Virtual Address → Host Physical Address
                                        (QEMU mmap region)

Host coi VM RAM như process memory

Vì VM RAM là mmap() trong QEMU process, Linux có thể:

  • KSM: scan và merge identical pages giữa các QEMU processes
  • Swap: swap VM pages ra disk nếu host thiếu RAM
  • NUMA: pin VM memory vào đúng NUMA node
  • Hugepages: dùng 2MB/1GB pages cho VM RAM
  • cgroups: limit memory per QEMU process

3. vCPU Execution Loop

3.1. KVM_RUN Loop

Đây là trung tâm hoạt động của KVM — mỗi vCPU thread chạy loop này liên tục:

vCPU Thread trong QEMU:
┌─────────────────────────────────────────┐
│                                         │
│  while (true) {                         │
│    // 1. Chuẩn bị (inject interrupts)   │
│    prepare_vcpu();                      │
│                                         │
│    // 2. Chạy guest code trên CPU thật  │
│    ioctl(vcpu_fd, KVM_RUN);  ◄──────── Blocking call
│    //   → KVM kernel:                   │
│    //     VMLAUNCH / VMRESUME           │
│    //     Guest code chạy native        │
│    //     ... cho đến khi VM Exit       │
│    //     Return về userspace           │
│                                         │
│    // 3. Xử lý lý do VM Exit           │
│    switch (run->exit_reason) {          │
│      case KVM_EXIT_IO:                  │
│        handle_io();      // I/O port    │
│      case KVM_EXIT_MMIO:                │
│        handle_mmio();    // MMIO access │
│      case KVM_EXIT_HLT:                 │
│        handle_halt();    // CPU idle    │
│      case KVM_EXIT_SHUTDOWN:            │
│        handle_shutdown();               │
│      case KVM_EXIT_INTERNAL_ERROR:      │
│        handle_error();                  │
│    }                                    │
│  }                                      │
└─────────────────────────────────────────┘

3.2. VM Exit Reasons (phổ biến)

Exit ReasonKhi nào xảy raXử lý bởi
KVM_EXIT_IOGuest truy cập I/O port (in/out)QEMU emulate device
KVM_EXIT_MMIOGuest truy cập MMIO regionQEMU emulate device
KVM_EXIT_HLTGuest CPU idle (HLT instruction)QEMU block thread (tiết kiệm host CPU)
KVM_EXIT_IRQ_WINDOW_OPENCơ hội inject interruptKVM inject pending interrupt
KVM_EXIT_SHUTDOWNGuest shutdown/resetQEMU cleanup
KVM_EXIT_FAIL_ENTRYVM entry failed (config lỗi)QEMU báo lỗi
(handled in kernel)EPT violation, APIC access, MSR accessKVM kernel xử lý, không về QEMU

Đa số VM Exit được xử lý TRONG kernel

EPT violations, APIC virtualization, interrupt injection — KVM xử lý trong kernel và VMRESUME ngay lập tức. Chỉ I/O emulation phức tạp mới return về QEMU userspace. Đây là lý do KVM nhanh.

4. Memory Architecture trong KVM

4.1. Memory Slots

KVM chia guest memory thành memory slots — mỗi slot map một vùng Guest Physical Address (GPA) sang Host Virtual Address (HVA):

Guest Physical Address Space:
  0x0000_0000 ┬─────── Slot 0: RAM below ~3.25GB (lowmem)
              │        HVA = QEMU mmap region A
  0x000A_0000 │        (VGA memory, 640KB-1MB — legacy hole)
  0xC000_0000 ┤
              │        PCI MMIO hole (~3GB-4GB, device MMIO/ROM)
              │        (Không map RAM ở đây)
  0xFFFF_FFFF ┤
  0x1_0000_0000 ┬───── Slot 1: RAM above 4GB (highmem)
                │      HVA = QEMU mmap region B
  0x2_0000_0000 ┘      (tuỳ tổng RAM size)

4.2. Address Translation Chain

Guest Virtual Address (GVA)
       │ Guest Page Table (guest OS quản lý)
       ↓
Guest Physical Address (GPA)
       │ EPT / NPT (KVM quản lý)
       ↓
Host Virtual Address (HVA)
       │ Host Page Table (Linux kernel quản lý)
       ↓
Host Physical Address (HPA)
       = Physical RAM

Chi tiết cơ chế EPT xem ../theory/04 - Memory Virtualization > 3. Hardware-Assisted: EPT / NPT.

Ngoài CPU và memory, VM cũng cần nhận interrupts (timer tick, disk I/O complete, network packet). KVM xử lý việc này bằng virtual interrupt controller.

5. Interrupt Delivery

5.1. Virtual Interrupt Controller

KVM emulate full interrupt controller stack trong kernel:

Guest perspective:
  Device → PIC/IOAPIC → LAPIC → CPU interrupt

KVM implementation:
  ┌──────────────────────────────────────┐
  │  KVM kernel module                   │
  │  ┌────────────────────────────────┐  │
  │  │  Virtual PIC (i8259)          │  │  ← legacy
  │  │  Virtual IOAPIC               │  │  ← modern
  │  │  Virtual LAPIC (per vCPU)     │  │
  │  └────────────┬─────────────────┘  │
  │               │                     │
  │  APICv/AVIC: hardware-accelerated   │
  │  interrupt delivery (nếu CPU hỗ trợ)│
  └──────────────────────────────────────┘

5.2. APICv (Intel) / AVIC (AMD)

Hardware-assisted APIC virtualization — giảm VM Exit cho interrupt operations:

Không APICvCó APICv
Guest đọc APIC register → VM ExitGuest đọc APIC register → virtual APIC page (no exit)
EOI (End of Interrupt) → VM ExitEOI → hardware handles (no exit)
IPI delivery → VM Exit + emulateIPI → Posted Interrupt (no exit)
~10,000 VM Exits/sec cho interrupt~100 VM Exits/sec cho interrupt

Với kiến trúc vCPU loop, memory isolation, và interrupt delivery đã rõ, phần cuối cùng quan trọng là: làm sao bảo đảm các VM không ảnh hưởng lẫn nhau?

6. KVM Security Model

6.1. sVirt (SELinux Virtualization)

Trên Fedora/RHEL, mỗi QEMU process chạy với SELinux context riêng biệt:

FeatureMô tả
Unique categoryMỗi VM nhận MCS category riêng (c123,c456)
File labelingVM disk files được label khớp với VM category
Cross-VM isolationVM A không thể đọc disk/memory của VM B (SELinux block)
Auto-labelinglibvirt tự gán label khi start VM

6.2. Các lớp isolation

┌───────────────────────────────────────────────────────┐
│  Layer 1: Hardware (VT-x VMX root/non-root)           │
│  → Guest code chạy trong VMX non-root, không escape   │
├───────────────────────────────────────────────────────┤
│  Layer 2: EPT (Extended Page Tables)                  │
│  → VM chỉ truy cập memory đã được map cho nó          │
├───────────────────────────────────────────────────────┤
│  Layer 3: QEMU process isolation (Linux DAC)          │
│  → QEMU chạy dưới user 'qemu', limited permissions    │
├───────────────────────────────────────────────────────┤
│  Layer 4: SELinux/sVirt (MAC)                         │
│  → Mỗi VM có SELinux category riêng                   │
├───────────────────────────────────────────────────────┤
│  Layer 5: cgroups                                     │
│  → Limit CPU, memory, I/O per VM                      │
├───────────────────────────────────────────────────────┤
│  Layer 6: seccomp (QEMU sandbox)                      │
│  → QEMU chỉ được gọi whitelist syscalls               │
└───────────────────────────────────────────────────────┘

KVM security mạnh hơn nhiều người nghĩ

So với container (chỉ có namespaces + cgroups + seccomp), KVM có thêm hardware isolation (VMX) + EPT + sVirt. Đây là lý do cloud providers dùng VM isolation giữa tenants thay vì container.

AspectKVMVMware ESXi

MemoryLinux mm + KSM + hugepagesVMkernel mm + TPS + compression
DriversLinux drivers (hàng nghìn)VMware HCL (hàng trăm)
