1. Ảo hoá là gì?

Virtualization là quá trình tạo ra một phiên bản ảo (virtual) của tài nguyên phần cứng hoặc phần mềm — CPU, RAM, disk, network, hoặc toàn bộ máy tính — sao cho nhiều hệ thống logic có thể cùng chia sẻ một hạ tầng vật lý.

┌─────────────────────────────────────────────┐
│         Phần cứng vật lý (Physical)         │
│   CPU cores · RAM · Disk · NIC · GPU       │
└──────────────────┬──────────────────────────┘
                   │
          ┌────────┴────────┐
          │   Hypervisor    │  ← Lớp trừu tượng hoá
          │  (VMM)          │
          └────┬───┬───┬────┘
               │   │   │
         ┌─────┴┐ ┌┴───┴┐ ┌──────┐
         │ VM 1 │ │VM 2 │ │ VM 3 │
         │ OS A │ │OS B │ │ OS C │
         └──────┘ └─────┘ └──────┘

Bản chất cốt lõi

Ảo hoá = trừu tượng hoá (abstraction) + cô lập (isolation) + chia sẻ (multiplexing).
Một phần cứng duy nhất phục vụ nhiều workloads độc lập, mỗi workload “tưởng” nó đang sở hữu toàn bộ phần cứng.

2. Tại sao cần ảo hoá?

2.1. Bài toán gốc: Lãng phí tài nguyên

Trước ảo hoá, mỗi ứng dụng chạy trên một máy chủ riêng (bare-metal):

Vấn đềMô tả
Utilization thấpServer trung bình chỉ dùng 10-15% CPU, phần còn lại idle
Chi phí caoMỗi app = 1 server vật lý = tiền phần cứng + điện + cooling
Triển khai chậmMua server mới mất hàng tuần đến hàng tháng
Xung đột môi trườngApp A cần lib version X, App B cần version Y trên cùng OS
Khó DR/HAFailover yêu cầu hardware dự phòng đắt đỏ

2.2. Ảo hoá giải quyết

Lợi íchCơ chế
Server consolidationNhiều VM trên 1 host → tận dụng CPU/RAM tối đa
IsolationMỗi VM có OS riêng, crash VM này không ảnh hưởng VM kia
PortabilityVM = file → copy, backup, migrate dễ dàng
Rapid provisioningTạo VM mới trong vài phút từ template
Resource elasticityTăng/giảm vCPU, RAM hot-plug (tuỳ platform)
Snapshot & rollbackChụp trạng thái → thử nghiệm → quay lại nếu lỗi

Điểm mấu chốt lịch sử

VT-x/AMD-V (2005-06) là bước ngoặt quan trọng nhất: trước đó, ảo hoá x86 phải dùng tricks phần mềm phức tạp (binary translation). Sau đó, CPU hỗ trợ native → hiệu năng gần bằng bare-metal.

4. Phân loại ảo hoá

4.1. Theo đối tượng ảo hoá

Virtualization
├── Server Virtualization      ← Trọng tâm của tài liệu này
│   └── Ảo hoá toàn bộ máy chủ (CPU + RAM + Disk + NIC)
├── Desktop Virtualization (VDI)
│   └── Ảo hoá desktop cho end-user (Citrix, VMware Horizon)
├── Network Virtualization
│   └── VLAN, VXLAN, SDN, NFV
├── Storage Virtualization
│   └── SAN, NAS, Software-defined Storage
├── Application Virtualization
│   └── App streaming, ThinApp, App-V
└── OS-level Virtualization (Containers)
    └── Docker, Podman, LXC — KHÔNG phải VM

4.2. Theo kỹ thuật ảo hoá server

Kỹ thuậtCơ chếVí dụ
Full VirtualizationGuest OS không cần sửa đổi, hypervisor mô phỏng hoàn toàn phần cứngVMware, KVM + QEMU
ParavirtualizationGuest OS được sửa đổi để gọi trực tiếp hypervisor qua hypercallsXen PV, virtio drivers
Hardware-assistedCPU có instruction set riêng cho ảo hoá (VT-x, AMD-V)KVM, VMware ESXi, Hyper-V
OS-level (Container)Dùng chung kernel, cô lập bằng namespaces + cgroupsDocker, Podman, LXC

Thực tế hiện nay

Hầu hết hypervisor hiện đại kết hợp hardware-assisted + paravirtualization:

  • CPU/Memory: dùng VT-x/AMD-V (hardware-assisted)
  • I/O (disk, network): dùng virtio drivers (paravirtualization)

→ Đạt hiệu năng cao nhất cho cả hai mặt.

Không phải "VM vs Container" — mà là "VM + Container"

Trong thực tế production:

  • Kubernetes nodes thường là VM (chạy trên vSphere, KVM, hoặc cloud instances)
  • Containers chạy bên trong VM đó
  • VM cung cấp isolation mạnh, container cung cấp density và tốc độ deploy

→ Hiểu VM là nền tảng để hiểu tại sao Kubernetes cluster thường không chạy trên bare-metal.

7. Các khái niệm nền tảng cần nắm

7.1. Privileged Instructions và Ring Model

CPU x86 có 4 privilege rings (0-3):

Ring 0 — Kernel mode  (cao nhất, truy cập hardware trực tiếp)
Ring 1 — (ít dùng)
Ring 2 — (ít dùng)
Ring 3 — User mode    (application, bị hạn chế)

Vấn đề với ảo hoá:

  • Guest OS cần chạy ở Ring 0 để quản lý kernel
  • Hypervisor cũng cần Ring 0 để kiểm soát hardware
  • Không thể có 2 thực thể cùng ở Ring 0

Giải pháp lịch sử:

Giải phápCách hoạt động
Ring deprivilegingGuest OS chạy ở Ring 1 hoặc Ring 3, hypervisor ở Ring 0
Binary translationVMware: dịch instruction Ring 0 của guest → instruction an toàn
ParavirtualizationXen: guest OS gọi hypercall thay vì instruction đặc quyền
VT-x/AMD-VTạo Ring -1 (root mode) cho hypervisor, guest OS chạy Ring 0 bình thường

VT-x giải quyết triệt để

Với hardware extensions, CPU có 2 mode:

  • VMX root mode (Ring -1): hypervisor chạy ở đây
  • VMX non-root mode: guest OS chạy Ring 0 thật sự ở đây

→ Guest không cần sửa đổi, không cần binary translation → hiệu năng native.

7.2. Trap-and-Emulate

Cơ chế cốt lõi nhất của mọi hypervisor:

Guest OS thực thi instruction đặc quyền
         │
         ↓
CPU phát hiện (trap/fault) → chuyển quyền điều khiển về hypervisor
         │
         ↓
Hypervisor xử lý (emulate) instruction đó
         │
         ↓
Trả quyền điều khiển về guest OS

Đây là nền tảng lý thuyết, sẽ được phân tích sâu ở 03 - CPU Virtualization.

7.3. Overcommitment

Overcommit = gán cho VM nhiều tài nguyên hơn vật lý có:

Tài nguyênOvercommit?Cơ chế
CPU✅ Phổ biếnvCPU scheduling — không phải tất cả VM cần CPU cùng lúc
Memory✅ Có nhưng rủi roBallooning, KSM, swap — có thể gây OOM
Storage✅ Rất phổ biếnThin provisioning — chỉ dùng disk khi thật sự write
Network⚠️ Hạn chếBandwidth shaping — giới hạn per-VM

Memory overcommit cẩn thận

Overcommit CPU ít rủi ro (chỉ chậm). Overcommit RAM nhiều quá → ballooning + swap → VM chậm nghiêm trọng → OOM killer.
Quy tắc: bắt đầu 1.2:1 ratio, monitor sát, tăng dần.
