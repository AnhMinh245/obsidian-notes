1. Bài toán cốt lõi

Trên bare-metal, OS quản lý một tầng address translation:

Virtual Address (VA) → [Page Table] → Physical Address (PA)

Với ảo hoá, có ba lớp địa chỉ:

Guest Virtual Address (GVA)
         │
         ↓  Guest page table (guest OS quản lý)
Guest Physical Address (GPA)
         │
         ↓  ??? (hypervisor phải xử lý)
Host Physical Address (HPA) = Machine Address

Câu hỏi cốt lõi: Làm sao để translate GPA → HPA hiệu quả?

  • Guest OS nghĩ GPA = physical memory thật
  • Thực tế, GPA chỉ là một “ảo giác” — hypervisor map GPA vào HPA
  • Mỗi VM cần bảng mapping riêng, cô lập hoàn toàn

2. Shadow Page Tables (SPT)

2.1. Cơ chế

Shadow Page Table là kỹ thuật phần mềm, hypervisor duy trì bảng page table “bóng” kết hợp GVA → HPA trực tiếp:

Guest OS tạo page table:  GVA → GPA  (guest quản lý)

Hypervisor tạo shadow:    GVA → HPA  (kết hợp 2 tầng)
                                       ↑
                                   Đây là bảng CPU thật sự dùng
                                   (nạp vào CR3)

2.2. Quy trình hoạt động

1. Guest OS tạo/sửa page table entry (GVA → GPA)
         │
         ↓
2. VM Exit (trap vì guest ghi CR3 hoặc sửa PTE)
         │
         ↓
3. Hypervisor:
   a. Đọc guest page table (GVA → GPA)
   b. Tra bảng GPA → HPA riêng
   c. Tạo shadow PTE: GVA → HPA
   d. Nạp shadow page table vào CR3 thật
         │
         ↓
4. VM Entry — guest tiếp tục chạy
   CPU dùng shadow PT để translate trực tiếp GVA → HPA

2.3. Đánh giá

Ưu điểmNhược điểm
TLB hit = fast (GVA → HPA trực tiếp)Rất nhiều VM Exit khi guest sửa page table
Không cần CPU extensionsHypervisor phải track mọi thay đổi PT của guest
RAM overhead: mỗi process trong guest cần 1 shadow PT
Code phức tạp, khó maintain

Shadow PT đã lỗi thời

Kỹ thuật này chủ yếu dùng trước EPT/NPT (2008). Hiện chỉ còn ý nghĩa lịch sử và dùng trong một số trường hợp đặc biệt (CPU không support EPT).

3. Hardware-Assisted: EPT / NPT

3.1. Extended Page Tables (Intel EPT) / Nested Page Tables (AMD NPT)

EPT/NPT = CPU tự động xử lý 2 tầng translation mà không cần VM Exit.

         Guest Page Table          EPT / NPT
GVA ──────────────────────► GPA ─────────────────► HPA
         (guest quản lý)          (hypervisor quản lý)
         (trong VM)               (trong VMCS)

CPU hardware tự động walk cả 2 bảng → KHÔNG cần VM Exit

3.2. Quy trình 2D Page Walk

Khi guest truy cập memory:

CPU cần translate GVA → HPA:

1. Đọc guest CR3 → Guest PML4 base (GPA)
2. Translate Guest PML4 base: GPA → HPA qua EPT (4 levels)
3. Đọc Guest PML4 entry → Guest PDPT base (GPA)
4. Translate Guest PDPT base: GPA → HPA qua EPT (4 levels)
5. ... (lặp cho PD và PT)

Worst case: 4 (guest levels) × 4 (EPT levels) + 4 = 24 memory accesses
           thay vì 4 trên bare-metal

                    EPT Walk cho mỗi level
                  ┌──────────────────────┐
GVA ──► Guest PT  │  GPA→HPA via EPT    │
        Level 4  ─┤  (4 memory reads)    │
        Level 3  ─┤  (4 memory reads)    │
        Level 2  ─┤  (4 memory reads)    │
        Level 1  ─┤  (4 memory reads)    │
                  └──────┬───────────────┘
                         ↓
              Final GPA → HPA via EPT
              (4 memory reads)
              
Total worst case: 5 × 4 = 20 reads + overhead

3.3. TLB và VPID

Vấn đề: VM switch → flush TLB → performance drop

VPID (Virtual Processor ID) giải quyết:

TLB entry format (without VPID):
  [GVA → HPA]  ← tất cả VM dùng chung, phải flush khi switch

TLB entry format (with VPID):
  [VPID=1, GVA → HPA]  ← VM1
  [VPID=2, GVA → HPA]  ← VM2
  → Không cần flush khi switch VM, mỗi VM có tag riêng
FeatureMục đích
EPT/NPTHardware 2D page walk, loại bỏ VM Exit cho PT access
VPIDTag TLB entries per-VM, tránh flush khi VM switch
Large Pages2MB/1GB pages trong EPT giảm walk depth

3.4. So sánh SPT vs EPT

Tiêu chíShadow Page TableEPT/NPT
VM Exit cho PTRất nhiều (mỗi lần guest sửa PT)Gần như không
TLB miss cost4 reads (fast, 1 tầng)20+ reads (2D walk)
TLB hitFastFast (tương đương)
Memory overheadCao (shadow PT per process)Thấp (1 EPT per VM)
ComplexityHypervisor code phức tạpHardware lo, hypervisor đơn giản

Hiện tạiLegacyChuẩn mặc định

EPT/NPT là chuẩn từ ~2008

Mọi hypervisor hiện đại (ESXi 4+, KVM, Hyper-V, Xen) đều dùng EPT/NPT. Shadow PT chỉ còn là fallback cho CPU cực cũ.

4. Memory Management Techniques

4.1. Memory Overcommit

Gán cho VM tổng RAM > RAM vật lý:

Physical RAM: 64 GB

VM1: 32 GB  ─┐
VM2: 24 GB   ├── Tổng = 80 GB > 64 GB → Overcommit
VM3: 24 GB  ─┘

4.2. Memory Ballooning

Balloon driver chạy bên trong guest OS, “phồng lên” để thu hồi RAM:

Trước khi balloon:
  VM1: 32 GB allocated
  VM2: 24 GB allocated  
  Free host RAM: 8 GB ← sắp hết!

Hypervisor ra lệnh balloon inflate cho VM1:
  1. Balloon driver trong VM1 "xin" 8 GB từ guest OS
  2. Guest OS thu hồi 8 GB (swap/reclaim pages)
  3. Balloon driver báo hypervisor: 8 GB này không cần nữa
  4. Hypervisor thu hồi 8 GB physical RAM

Sau balloon:
  VM1: 24 GB effective (8 GB bị balloon chiếm)
  VM2: 24 GB allocated
  Free host RAM: 16 GB ← đã giải phóng

┌──────────────────────────────────┐
│           VM1 (32 GB)            │
│                                  │
│  ┌──────────┐  ┌──────────────┐  │
│  │ App data │  │ 🎈 Balloon  │  │
│  │ 24 GB    │  │    8 GB     │  │
│  │          │  │ (inflated)  │  │
│  └──────────┘  └──────────────┘  │
└──────────────────────────────────┘
     ↑                    ↑
     Thật sự dùng     Hypervisor thu hồi
     physical RAM      physical RAM này
HypervisorBalloon driver
VMwarevmballoon (VMware Tools)
KVM/QEMUvirtio-balloon
Hyper-Vhv_balloon

Balloon vs swap

  • Balloon: guest OS tự chọn page nào ít dùng nhất để trả lại → thông minh hơn
  • Hypervisor swap: hypervisor swap page ra disk, không biết page nào quan trọng → chậm hơn

Thứ tự ưu tiên reclaim: Transparent Page Sharing → Ballooning → Compression → Swap

4.3. KSM — Kernel Same-page Merging

KSM (Linux/KVM) / TPS (VMware Transparent Page Sharing):

Trước KSM:                          Sau KSM:
VM1 RAM: [Page A] [Page B]          VM1 RAM: [Page A*] [Page B]
VM2 RAM: [Page A] [Page C]          VM2 RAM: [Page A*] [Page C]
VM3 RAM: [Page A] [Page D]          VM3 RAM: [Page A*] [Page D]
                                              ↑
Physical: 9 pages used               Page A chỉ lưu 1 copy
                                     (Copy-on-Write nếu VM sửa)
                                     Physical: 7 pages used

Cách hoạt động:

  1. Daemon quét memory pages của tất cả VM
  2. Hash nội dung page, tìm page giống nhau
  3. Merge thành 1 physical page, đánh dấu Copy-on-Write (CoW)
  4. Nếu VM sửa page → tạo private copy (page fault → allocate mới)

Hiệu quả cao khi: nhiều VM cùng OS (ví dụ: 10 VM Ubuntu → share kernel pages).

KSM security concern

KSM có thể bị exploit qua side-channel attack: attacker đo thời gian write để detect page merge → suy ra nội dung RAM VM khác. Một số cloud provider disable KSM vì lý do này.

4.4. Memory Compression

Trước khi swap ra disk, nén page trong RAM:

Thay vì:  Page → swap to disk (slow, ~ms)
Dùng:     Page → compress in RAM (fast, ~μs, ratio ~2:1)
  • VMware ESXi: memory compression cache (tự động)
  • KVM: zswap hoặc zram trong host kernel

4.5. Tổng kết thứ tự reclaim

Hypervisor xử lý memory pressure theo thứ tự:

Memory pressure tăng dần →

1. TPS / KSM (free)       ← Share identical pages, CoW
2. Ballooning (nhẹ)       ← Guest OS tự reclaim thông minh  
3. Compression (trung bình) ← Nén page trong RAM
4. Host swap (nặng)        ← Swap page ra disk, chậm nhất
5. OOM (critical)          ← Kill VM hoặc process

Golden rule: tránh để host swap

Nếu hypervisor phải swap → VM cực kỳ chậm (disk I/O thay vì RAM access). Monitor memory usage và điều chỉnh overcommit ratio.

5. Memory Hot-plug / Hot-remove

Một số platform cho phép thêm/bớt RAM khi VM đang chạy:

PlatformHot-addHot-remove
VMware ESXi✅✅ (cần VM version 7+)
KVM/QEMU✅ (virtio-mem)✅ (với virtio-mem)
Hyper-V✅ (Dynamic Memory)✅
Proxmox✅ (qua QEMU)⚠️ Hạn chế

Guest OS cũng phải support

Hot-add RAM vào VM chỉ là một phía. Guest OS phải có driver/kernel support để nhận ra và sử dụng RAM mới (Linux: memory_hotplug, Windows: Enterprise editions).

6. Huge Pages / Large Pages

Thay vì page 4KB mặc định, dùng page lớn hơn:

Page sizeMô tảBenefit
4 KBDefaultFlexible, nhưng nhiều TLB entries
2 MBHuge page (x86)512x ít TLB entries, giảm TLB miss
1 GBGigantic page (x86)Database, HPC workloads

Tại sao quan trọng cho VM:

  • VM 64GB RAM → với 4KB pages = 16,777,216 entries trong EPT
  • Với 2MB pages = 32,768 entries → EPT walk nhanh hơn nhiều lần
  • Database (Oracle, PostgreSQL) trong VM luôn nên dùng huge pages
