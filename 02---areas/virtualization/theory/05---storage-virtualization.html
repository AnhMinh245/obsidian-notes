05 · Storage Virtualization

← 🖥️ Virtualization MOC

1. Bài toán cốt lõi

Guest OS nghĩ nó có disk riêng (SCSI, SATA, NVMe). Thực tế, “disk” đó là một file trên host hoặc block device được chia sẻ. Hypervisor phải:

  1. Trình bày virtual disk cho guest (emulate disk controller)
  2. Map I/O requests từ guest → storage thật (file, LVM, SAN, NFS)
  3. Cô lập data giữa các VM
  4. Tối ưu throughput và latency
Guest OS
  │ write(sector 1000, data)
  ↓
Virtual Disk Controller (emulated hoặc virtio)
  │
  ↓
Hypervisor Storage Layer
  │ translate sector → offset trong virtual disk file
  ↓
Storage Backend
  ├── Local: file trên filesystem (qcow2, vmdk)
  ├── Local: LVM logical volume
  ├── Network: NFS share
  ├── Network: iSCSI target
  └── Distributed: Ceph RBD, GlusterFS

2.2. QCOW2 — Deep dive

QCOW2 (QEMU Copy-On-Write version 2) là format quan trọng nhất cho KVM ecosystem:

QCOW2 File Structure:
┌──────────────────────────────────────┐
│ Header (magic, version, size, ...)   │
├──────────────────────────────────────┤
│ L1 Table (index → L2 table offset)  │
├──────────────────────────────────────┤
│ L2 Table (index → data cluster)     │
├──────────────────────────────────────┤
│ Data Clusters (actual disk data)    │
├──────────────────────────────────────┤
│ Refcount Table (reference counting) │
├──────────────────────────────────────┤
│ Snapshot Table (internal snapshots)  │
└──────────────────────────────────────┘

Tính năng QCOW2:

Tính năngMô tả
Thin provisioningFile nhỏ ban đầu, grow khi guest write
Internal snapshotsLưu trạng thái disk tại thời điểm (COW)
Backing filesChain: base image → overlay → overlay2 (linked clones)
CompressionNén data clusters (zlib/zstd)
EncryptionLUKS encryption trong file
Preallocationoff, metadata, falloc, full

2.3. VMDK Sub-formats

VMware VMDK có nhiều loại, hiểu rõ để chọn đúng:

Sub-formatBehaviourUse case
ThinGrow on demand, file nhỏ ban đầuDev, test, tiết kiệm space
Thick Lazy ZeroedAllocate full space, nhưng zero-on-first-writeBalance performance/space
Thick Eager ZeroedAllocate + zero toàn bộ ngay lập tứcProduction, database, Fault Tolerance
SEsparseThin + space reclamation (SCSI UNMAP)vSphere 5.5+ linked clones

Eager Thick cho production

Database, mission-critical VM: luôn dùng Eager Zeroed Thick vì:

  • Không có latency từ zero-on-first-write
  • Disk space đã guaranteed (không bị hết space bất ngờ)
  • Bắt buộc cho VMware Fault Tolerance

3. Thin vs Thick Provisioning

3.1. So sánh

Thick Provisioning:
  VM xin 100 GB → hypervisor allocate 100 GB ngay trên storage
  ┌────────────────────────────────────────┐
  │████████████ 100 GB allocated ██████████│  (dù chỉ dùng 20 GB)
  └────────────────────────────────────────┘

Thin Provisioning:
  VM xin 100 GB → hypervisor allocate theo nhu cầu thực tế
  ┌──────────┬─────────────────────────────┐
  │██ 20 GB ██│ 80 GB available (chưa dùng) │
  │ (used)   │ (chưa allocate trên storage)│
  └──────────┴─────────────────────────────┘
Tiêu chíThickThin
Space efficiencyThấp — allocate hết ngayCao — chỉ dùng khi cần
PerformanceỔn định (no allocation delay)Có thể có latency khi grow
OvercommitKhông (1:1 mapping)Có (tổng virtual > physical)
Rủi roLãng phí spaceStorage full bất ngờ nếu overcommit quá mức
Production✅ Recommended⚠️ Cần monitor sát

Thin provisioning overcommit = bomb hẹn giờ

Nếu tổng virtual disk > physical storage capacity:

  • Mọi thứ chạy bình thường cho đến khi storage thật sự đầy
  • Khi đầy → VM pause hoặc crash → data loss
  • Monitor: set alert ở 80% capacity, 90% critical

3.2. Space Reclamation (TRIM/UNMAP)

Khi guest xoá file, thin disk không tự thu hồi. Cần TRIM/UNMAP:

Guest xoá file 10GB
    │
    ↓
Guest filesystem: đánh dấu blocks "free"
NHƯNG hypervisor không biết → thin disk vẫn chiếm 10GB trên host

Giải pháp: SCSI UNMAP / ATA TRIM
    │
    ↓
Guest gửi UNMAP command → hypervisor biết blocks đã free
    → Thin disk shrink (hoặc punch hole)

5. Snapshots

5.1. Cơ chế Snapshot

Snapshot = capture trạng thái disk (và tuỳ chọn: RAM + device state) tại một thời điểm.

Trước snapshot:
  disk.qcow2: [Block A] [Block B] [Block C]

Tạo snapshot:
  disk.qcow2: [Block A] [Block B] [Block C]  ← frozen, read-only
  overlay.qcow2: (empty) ← mọi write mới vào đây (COW)

Sau khi VM tiếp tục write:
  disk.qcow2: [Block A] [Block B] [Block C]  ← không thay đổi
  overlay.qcow2: [Block B'] [Block D]         ← chỉ blocks đã thay đổi

Read flow:
  Đọc Block A → không có trong overlay → đọc từ disk.qcow2
  Đọc Block B → có Block B' trong overlay → trả Block B' (mới nhất)

5.2. Snapshot chains

base.qcow2 ← snap1.qcow2 ← snap2.qcow2 ← current.qcow2 (active)
  │              │              │              │
  └── original   └── delta 1   └── delta 2   └── current writes

Snapshot chains dài = performance disaster

Mỗi read phải walk ngược chain để tìm block mới nhất. Chain > 3-4 levels → I/O latency tăng đáng kể.

Best practice:

  • Snapshot chỉ dùng tạm thời (trước update, test)
  • Commit (merge) hoặc delete snapshot sau khi xong
  • KHÔNG dùng snapshot như backup dài hạn

6. Disk I/O Performance

6.1. I/O Path so sánh

Performance (high → low):

1. Virtio-blk + RAW + direct I/O     ← nhanh nhất
2. Virtio-scsi + QCOW2 + writeback   ← balanced
3. IDE emulation + QCOW2             ← chậm nhất (legacy)

6.2. Cache Modes

Cache modeWrite pathCrash safetyPerformance
none (direct)Guest → host disk trực tiếp✅ An toàn nhấtTốt cho SSD/NVMe
writebackGuest → host page cache → disk⚠️ Mất data nếu host crashNhanh nhất
writethroughGuest → host disk + host cache✅ An toànChậm nhất
unsafeGuest → host cache, no flush❌ Mất dataNhanh nhất (chỉ cho test)

Production recommendation

  • SSD/NVMe storage: cache=none + io=native + discard=unmap
  • HDD / NFS: cache=writeback + io=threads (cẩn thận với crash)
  • Database VM: cache=none (database có write-ahead log riêng)

7. VM Cloning

7.1. Full Clone vs Linked Clone

Full Clone:
  base.qcow2 (50GB) → copy → clone.qcow2 (50GB)
  → 100% independent, tốn gấp đôi space

Linked Clone:
  base.qcow2 (50GB) ← read-only base
     ├── clone1.qcow2 (delta, ~MB) ← COW overlay
     ├── clone2.qcow2 (delta, ~MB)
     └── clone3.qcow2 (delta, ~MB)
  → Tiết kiệm space, NHƯNG phụ thuộc vào base
  → Xoá base = mất tất cả clones
Clone typeSpaceTốc độ tạoĐộc lập
FullGấp đôiChậm (copy toàn bộ)✅ Hoàn toàn
LinkedRất ít (delta only)Rất nhanh❌ Phụ thuộc base
