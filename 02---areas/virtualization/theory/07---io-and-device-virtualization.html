1. Bài toán cốt lõi

Guest OS cần truy cập devices: disk, network, USB, GPU, serial port… Nhưng devices vật lý chỉ có 1 bộ registers, 1 interrupt line. Làm sao chia sẻ cho nhiều VM?

Ba approach chính:

Performance ←──────────────────────────────────────────→ Flexibility

Emulation          Paravirtualization        Passthrough
(chậm nhất)        (balanced)                (nhanh nhất)
(linh hoạt nhất)   (cần driver đặc biệt)    (ít linh hoạt nhất)

2. Device Emulation (Full Emulation)

2.1. Cơ chế

Hypervisor giả lập hoàn toàn một thiết bị phần cứng trong phần mềm:

Guest OS (driver cho Intel e1000 NIC)
    │
    │ write(NIC register 0x10, data)
    ↓
VM Exit (trap vì truy cập MMIO range)
    │
    ↓
Hypervisor (QEMU):
  "Đây là write vào emulated e1000 register 0x10"
  → Xử lý logic (buffer packet, generate interrupt)
  → Gửi packet qua host network stack
    │
    ↓
VM Entry → guest tiếp tục

2.2. QEMU Device Emulation

QEMU là champion của device emulation — mô phỏng hàng trăm loại thiết bị:

CategoryEmulated Devices
DiskIDE (PIIX4), AHCI, SCSI (LSI, Megasas), NVMe, USB storage
NetworkIntel e1000/e1000e, Realtek RTL8139, Intel i82559
DisplayVGA, QXL (SPICE), bochs-display, virtio-gpu
USBUHCI, OHCI, EHCI, xHCI controllers
SoundIntel HDA, AC97, SB16
Serial16550A UART
InputPS/2 keyboard/mouse, USB tablet

2.3. Đánh giá

Ưu điểmNhược điểm
Guest không cần driver đặc biệtMỗi I/O operation = VM Exit (~1000 cycles)
Dùng driver sẵn có trong OSThroughput thấp, latency cao
Tối đa compatibilityCPU host bận xử lý emulation
An toàn cho live migration

Khi nào dùng emulation?

  • OS rất cũ (Windows XP, DOS) không có paravirt driver
  • Giai đoạn cài đặt OS (trước khi cài virtio driver)
  • Thiết bị không có paravirt alternative (USB, serial)

3. Paravirtualization (virtio)

3.1. Khái niệm

Thay vì giả lập device cũ, tạo giao thức I/O mới tối ưu cho ảo hoá:

Emulation:
  Guest → "Tôi viết vào thanh ghi NIC e1000" → VM Exit → QEMU xử lý

Paravirtualization:
  Guest → "Tôi đặt packet vào shared ring buffer, thông báo hypervisor"
       → Hypervisor batch process, ít VM Exit hơn

3.2. virtio Architecture

virtio là chuẩn paravirtualization cho KVM/QEMU, được OASIS standardize:

3.3. Virtqueue — cơ chế giao tiếp

Virtqueue = shared memory ring buffer giữa guest driver và hypervisor:

Guest (producer)                    Host (consumer)
     │                                    │
     │    ┌─────────────────────────┐     │
     ├───►│  Descriptor Table       │◄────┤
     │    │  [addr, len, flags, next]│     │
     │    │  [addr, len, flags, next]│     │
     │    │  ...                    │     │
     │    └─────────────────────────┘     │
     │                                    │
     │    ┌─────────────────────────┐     │
     ├───►│  Available Ring         │     │
     │    │  (guest → host: "data sẵn")│  │
     │    └─────────────────────────┘     │
     │                                    │
     │    ┌─────────────────────────┐     │
     │    │  Used Ring              │◄────┤
     │    │  (host → guest: "đã xong")│   │
     │    └─────────────────────────┘     │
     │                                    │
     │    Notification:                   │
     │    Guest kick → eventfd → Host     │
     │    Host → interrupt → Guest        │

Flow gửi network packet:

  1. Guest driver đặt packet data vào descriptor
  2. Thêm descriptor index vào Available Ring
  3. Kick hypervisor (write vào MMIO register hoặc eventfd)
  4. Hypervisor đọc descriptor, gửi packet ra host network
  5. Đánh dấu descriptor trong Used Ring
  6. Inject interrupt vào guest (tuỳ chọn, có thể batch)

3.5. vhost — Kernel-side virtio

vhost đưa virtio backend vào kernel thay vì QEMU userspace:

Without vhost (QEMU userspace):
  Guest → virtqueue → QEMU (userspace) → kernel → NIC
                       ↑ context switch overhead

With vhost-net (kernel):
  Guest → virtqueue → vhost-net (kernel module) → NIC
                       ↑ no context switch to QEMU

With vhost-user (userspace DPDK):
  Guest → virtqueue → DPDK app (userspace) → NIC
                       ↑ zero-copy, polling mode
BackendPerformanceUse case
QEMU backendBaselineMặc định, đơn giản
vhost-net~20-30% fasterProduction KVM/Proxmox
vhost-user (DPDK)~2-3x fasterNFV, telco, high-performance

4. Device Passthrough

4.1. PCI Passthrough

Gán nguyên device PCI cho VM — VM truy cập hardware trực tiếp:

Without passthrough:
  Guest → emulated/virtio device → hypervisor → physical device

With passthrough:
  Guest → physical device (trực tiếp, native performance)
  Hypervisor chỉ setup IOMMU mapping ban đầu

4.2. IOMMU — An toàn cho passthrough

IOMMU (I/O Memory Management Unit) = MMU cho DMA:

Without IOMMU:
  Device DMA → truy cập BẤT KỲ physical memory
  → VM có passthrough device có thể đọc RAM của host/VM khác!
  → SECURITY DISASTER

With IOMMU (Intel VT-d / AMD-Vi):
  Device DMA → IOMMU translate → chỉ truy cập RAM được phép
  → VM chỉ thấy RAM của chính nó
  → An toàn cho passthrough

            ┌───────────────────┐
            │    CPU / Memory   │
            │   ┌───────────┐   │
            │   │  VM1 RAM  │   │
            │   │  VM2 RAM  │   │
            │   │  Host RAM │   │
            │   └─────┬─────┘   │
            │         │         │
            │   ┌─────┴─────┐   │
            │   │   IOMMU   │   │  ← DMA remapping
            │   │  (VT-d)   │   │     chỉ cho phép
            │   └─────┬─────┘   │     device truy cập
            │         │         │     RAM của VM owner
            └─────────┼─────────┘
                      │
              ┌───────┴────────┐
              │  PCI Device    │
              │  (GPU, NIC...) │
              │  assigned to   │
              │  VM1           │
              └────────────────┘

4.3. GPU Passthrough

Use case phổ biến: gán GPU cho VM (gaming, AI/ML, CAD):

Host:
  CPU: AMD Ryzen 7
  GPU 1: AMD integrated → host display
  GPU 2: NVIDIA RTX → passthrough cho VM

VM (Windows):
  "Thấy" NVIDIA RTX như hardware thật
  Cài driver NVIDIA bình thường
  Chạy game/CUDA ở native performance

GPU passthrough phức tạp

  • IOMMU group phải chứa chỉ GPU (hoặc dùng ACS override)
  • NVIDIA có anti-VM detection (cần workaround cho consumer GPUs)
  • Reset bug trên một số GPU (AMD navi, NVIDIA pre-Turing)
  • Cần 2 GPU (hoặc headless host)

5. Interrupt Virtualization

5.1. Vấn đề

Devices giao tiếp với CPU qua interrupts. Trong VM, interrupt phải được ảo hoá:

Physical device interrupt:
  Device → APIC → CPU → Interrupt handler

Virtual interrupt:
  Emulated device "generates interrupt"
  → Hypervisor inject virtual interrupt vào guest
  → Guest CPU xử lý interrupt handler trong guest OS

5.2. Interrupt delivery path

Device → Physical APIC → Host CPU
    │
    ↓ (hypervisor intercepts if for VM)
    
Hypervisor:
  1. Check: interrupt thuộc VM nào?
  2. Inject virtual interrupt vào VMCS
  3. Guest resume → thấy pending interrupt
  4. Guest APIC → Guest interrupt handler

5.3. Hardware-assisted interrupt virtualization

FeatureMục đích
APICv (Intel)Virtual APIC page → giảm VM Exit cho APIC access
AVIC (AMD)Tương tự APICv cho AMD
Posted InterruptsDeliver interrupt trực tiếp vào VM mà không cần VM Exit
Without APICv:
  Guest read APIC register → VM Exit → hypervisor emulate → VM Entry
  = 2 VM Exits per interrupt operation

With APICv:
  Guest read APIC register → virtual APIC page → NO VM Exit
  Posted interrupt → delivered to guest → NO VM Exit for hypervisor
