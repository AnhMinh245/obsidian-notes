Schema và Functional Level - Nền tảng nâng cấp

Tóm tắt nhanh

  • Schema định nghĩa mọi object class và attribute trong AD — replicate đến toàn bộ DC trong forest
  • Schema là cumulative và additive: chỉ thêm, gần như không thể xoá — mỗi thay đổi là vĩnh viễn
  • Functional Level (FFL/DFL) là cơ chế unlock tính năng mới khi toàn bộ DC đạt OS tối thiểu
  • Nâng Functional Level là thao tác một chiều không thể rollback — phải kiểm tra kỹ trước khi thực hiện
  • Schema version và Functional Level là hai khái niệm khác nhau — có thể extend schema mà chưa nâng FL
  • Trước khi nâng cấp AD lên WS2025: phải chạy adprep để extend schema lên version 91

AD Schema Deep Dive

Schema là gì?

  • Schema là blueprint của toàn bộ AD database — tương tự database schema trong SQL
  • Mọi object trong AD (user, computer, group, OU, GPO…) đều được định nghĩa bởi Schema
  • Schema gồm 2 thành phần chính:
    • Object Classes (classSchema): định nghĩa loại object có thể tạo — ví dụ class user, class computer, class organizationalUnit
    • Attributes (attributeSchema): định nghĩa thuộc tính gắn với object — ví dụ sAMAccountName, mail, userPrincipalName, memberOf
  • Mỗi class quy định attribute nào là mandatory (bắt buộc) và optional (tuỳ chọn)

Tương tự thực tế

  • Schema giống như bản thiết kế kiến trúc của một toà nhà: quy định có bao nhiêu loại phòng (class), mỗi phòng có bao nhiêu cửa sổ, bao nhiêu ổ điện (attribute)
  • Một khi toà nhà đã xây (AD đã hoạt động), bạn có thể thêm phòng mới (add class), thêm ổ điện (add attribute), nhưng không thể xoá tầng đã xây (cannot delete class/attribute)
  • Bản thiết kế này áp dụng cho toàn khu đô thị (forest) — không phải riêng 1 toà nhà (domain)

Cấu trúc bên trong Schema

Object Class Hierarchy

  • AD Schema sử dụng inheritance (kế thừa) giống OOP:
    • Class top → class cha gốc của mọi class
    • Class person kế thừa từ top → có các attribute chung cho “person”
    • Class organizationalPerson kế thừa từ person → thêm attribute tổ chức
    • Class user kế thừa từ organizationalPerson → thêm attribute login, password
  • Khi extend schema, class mới có thể kế thừa class có sẵn → tự động có mandatory/optional attributes của class cha
  • 3 loại class:
    • Structural: có thể tạo instance (ví dụ: user, computer, group)
    • Auxiliary: bổ sung attribute cho class khác (ví dụ: mailRecipient)
    • Abstract: chỉ dùng làm cha để kế thừa (ví dụ: top, person)

Attribute Syntax và OID

  • Mỗi attribute có Object Identifier (OID) duy nhất — số dạng 1.2.840.113556.1.4.xxx
  • OID đã dùng không bao giờ được tái sử dụng — kể cả khi attribute bị deactivate
  • Mỗi attribute có syntax xác định kiểu dữ liệu:
    • 2.5.5.12 = Unicode String
    • 2.5.5.9 = Integer
    • 2.5.5.8 = Boolean
    • 2.5.5.11 = Generalized Time
    • 2.5.5.1 = Distinguished Name (DN reference)

Kiểm tra chi tiết hơn:

Deferred Index Creation

  • Khi schema extension thêm attribute mới với flag indexed → AD cần build index cho attribute đó trên mọi DC
  • Trong forest lớn (hàng triệu object), index building có thể tốn thời gian và resource đáng kể
  • Deferred Index Creation (từ WS2012+):
    • Index không được build ngay khi schema extend
    • Thay vào đó, index được build sau khi replication hoàn tất và DC khởi động lại
    • Giảm impact lên production trong quá trình schema extension
  • Attribute searchFlags value 8192 (bit 13) = fATTINDEX — flag yêu cầu index
  • Best practice: schedule schema extension ngoài giờ cao điểm, cho phép DC rebuild index dần

Chi tiết từng bước:

  1. adprep /forestprep:

    • Phải chạy trên DC giữ role Schema Master
    • Account chạy phải thuộc Schema Admins + Enterprise Admins
    • Modify Schema partition — thêm class và attribute cho OS mới
    • Chỉ chạy 1 lần cho toàn forest
    • Đợi replication hoàn tất trước khi tiếp (kiểm tra bằng repadmin /replsummary)
    • Thời gian: thường vài phút, có thể lâu hơn trong forest lớn

  2. adprep /domainprep:

    • Phải chạy trên DC giữ role Infrastructure Master của mỗi domain
    • Account chạy phải thuộc Domain Admins của domain đó
    • Update ACL, tạo container mới trong domain partition
    • Chạy 1 lần cho mỗi domain trong forest
    • Nhanh hơn forestprep — thường vài giây đến vài phút

  3. Automatic adprep (WS2012+):

    • Khi promote DC mới bằng Server Manager hoặc PowerShell
    • Nếu account có đủ quyền (Schema Admin + Enterprise Admin) → adprep tự chạy
    • Nếu không đủ quyền → phải chạy manual trước
    • Khuyến nghị: vẫn nên chạy manual trong production để kiểm soát timing

Schema Conflicts và Troubleshooting

Duplicate OID Conflicts

  • Xảy ra khi hai ứng dụng khác nhau cố dùng cùng OID cho attribute khác nhau
  • Nguyên nhân phổ biến:
    • Vendor không đăng ký OID riêng với IANA, dùng OID tự chọn
    • Developer copy schema extension từ nguồn khác mà không thay OID
  • Hậu quả: adprep hoặc schema extension fail với lỗi “OID already exists”
  • Xử lý:
    • Liên hệ vendor để lấy schema extension với OID đúng
    • Không tự sửa OID — có thể gây mất tương thích
    • Test trong lab trước khi apply production — luôn luôn

Attribute Name Conflicts

  • Hai extension dùng cùng ldapDisplayName cho attribute khác nhau
  • Ít phổ biến hơn OID conflict nhưng vẫn xảy ra
  • Schema extension sẽ fail nếu tên đã tồn tại với definition khác

Best Practices tránh Schema Conflicts

  • Luôn test schema extension trong isolated lab forest trước
  • Verify vendor đã đăng ký OID arc riêng (nên bắt đầu từ 1.2.840.113556.1.8.xxxx hoặc private arc)
  • Kiểm tra schema compatibility matrix giữa các ứng dụng cần extend
  • Backup System State trên Schema Master trước mọi extension
  • Sau extension: chạy repadmin /replsummary để verify replication healthy

Functional Level

Khái niệm

  • Functional Level là cơ chế gate-keeping: unlock tính năng mới chỉ khi toàn bộ DC đạt OS tối thiểu
  • Tương tự hiệp ước quốc tế: tính năng mới chỉ có hiệu lực khi tất cả thành viên (DC) đồng ý (chạy OS đủ mới)
    • Nếu 1 DC vẫn chạy OS cũ → không thể nâng FL vì DC đó không hiểu protocol/feature mới
  • Có 2 cấp:
    • Forest Functional Level (FFL): tính năng áp dụng toàn forest
    • Domain Functional Level (DFL): tính năng áp dụng trong phạm vi 1 domain
  • DFL có thể cao hơn FFL nhưng không được thấp hơn
  • Nâng FFL yêu cầu tất cả DFL trong forest đều >= FFL target

Tính năng chi tiết theo từng Functional Level

FFL 2003 — Linked-Value Replication (LVR)

  • Trước FFL 2003: group membership replicate toàn bộ attribute member mỗi khi có thay đổi
    • Group 5000 members, thêm 1 member → replicate lại cả 5000 entries → bandwidth lớn, conflict nhiều
  • Từ FFL 2003: Linked-Value Replication chỉ replicate giá trị thay đổi (delta)
    • Thêm 1 member → chỉ replicate 1 entry mới → efficient, ít conflict
  • LVR là yêu cầu bắt buộc cho group lớn (>5000 members) — trước đó group bị giới hạn ngầm khoảng 5000 members vì replication issue
  • Đây là 1 trong những lý do quan trọng nhất để nâng lên tối thiểu FFL 2003

FFL 2008 — DFS-R cho SYSVOL

  • SYSVOL chứa Group Policy objects và logon scripts — cần replicate giữa tất cả DC
  • FRS (File Replication Service): cơ chế cũ, không reliable, khó troubleshoot, không hỗ trợ differential replication
  • DFS-R (Distributed File System Replication): cơ chế mới, efficient, differential, self-healing
  • Khi nâng FFL lên 2008: không tự động migrate SYSVOL từ FRS sang DFS-R
    • Phải chạy migration thủ công theo 4 giai đoạn: Start → Prepared → Redirected → Eliminated
    • Kiểm tra trạng thái: dfsrmig /getglobalstate
  • Quan trọng: nếu FFL đã ở 2008+ mà SYSVOL vẫn dùng FRS → cần migrate ngay (FRS đã deprecated)

FFL 2008 R2 — AD Recycle Bin

  • Trước đây: xoá object trong AD → object thành tombstone → chỉ giữ lại vài attribute (SID, GUID) → sau tombstone lifetime (60-180 ngày) → xoá vĩnh viễn
  • AD Recycle Bin: object bị xoá → vào trạng thái deleted (giữ TẤT CẢ attributes) → sau deleted object lifetime → thành recycled → sau recycled lifetime → xoá vĩnh viễn
  • Khôi phục: có thể restore object với toàn bộ attribute (group membership, linked values…) thay vì chỉ SID/GUID
  • Lưu ý quan trọng: bật Recycle Bin là thao tác một chiều — bật rồi không tắt được
  • Default deleted object lifetime: 180 ngày (có thể tuỳ chỉnh)

FFL 2012 R2 — Authentication Policies và Protected Users

  • Protected Users security group: member của group này được bảo vệ đặc biệt
    • Không dùng NTLM auth (chỉ Kerberos)
    • Không delegation
    • Kerberos TGT lifetime giảm xuống 4 giờ (thay vì 10 giờ)
    • Không lưu plaintext credentials trong LSASS
  • Authentication Policies: cho phép restrict authentication scope cho privileged accounts
    • Ví dụ: Domain Admin chỉ được login từ DC, không từ workstation
    • Dựa trên Kerberos Armoring (FAST)
  • Authentication Silos: group các tài khoản và policy lại → enforce authentication boundary

FFL 2016 — Privileged Access Management (PAM)

  • PAM: cho phép tạo time-limited group membership (just-in-time access)
    • Admin không phải member thường trực của Domain Admins
    • Khi cần → request membership → được cấp cho 1-4 giờ → tự động remove
  • Yêu cầu MIM (Microsoft Identity Manager) hoặc custom solution để quản lý PAM
  • Shadow principal: user từ production forest được map vào bastion forest với time-limited membership
  • Giảm attack surface vì privileged group thường rỗng — attacker không thể lợi dụng persistent membership

FFL 2025 — Windows Server 2025 New Features

  • Database 32K pages:
    • NTDS.DIT trước đây dùng 8K page size (giống ESE engine)
    • WS2025 nâng lên 32K page size → hỗ trợ multi-valued attributes lớn hơn nhiều (>1600 values per attribute)
    • Giải quyết vấn đề group >1600 members gặp khó khăn trong single-valued attribute storage
    • Không tự động convert DB cũ → cần migration process
    • Chỉ có hiệu lực khi tất cả DC đều chạy WS2025 và FFL được nâng lên 2025
  • Improved Kerberos:
    • Kerberos Key Distribution (KKDCP) improvements
    • Khả năng authenticate mà không cần line-of-sight đến DC qua HTTPS proxy
    • Enhanced certificate-based authentication
  • LDAP improvements:
    • LDAP channel binding mặc định được enforce
    • LDAP signing required by default
    • Cải thiện security posture cho LDAP communication
  • Improved security defaults:
    • SMB over QUIC support
    • Enhanced credential protection
    • Default security hardening không cần manual configuration

CRITICAL: Tính không thể đảo ngược

  • Nâng FFL/DFL là thao tác MỘT CHIỀU — không có lệnh “lower functional level”
  • Cách duy nhất để “hạ” FFL: restore AD từ backup trước khi nâng → mất mọi thay đổi sau đó
  • Vì vậy:
    • Luôn backup System State trên tất cả DC trước khi nâng
    • Luôn test trên lab environment trước
    • Luôn verify tất cả ứng dụng compatible với target functional level
    • Đặc biệt: kiểm tra xem có ứng dụng nào phụ thuộc tính năng bị thay đổi khi nâng level
    • Ví dụ: ứng dụng dùng NTLM auth → nâng FFL + bật Protected Users → app bị break

Checklist trước khi nâng Functional Level

  • Tất cả DC chạy OS >= target level
  • RODC (nếu có) cũng chạy OS >= target level
  • repadmin /replsummary không có lỗi
  • dcdiag /v pass trên tất cả DC
  • Full System State backup hoàn tất
  • Lab test đã xong, không có issue
  • Các ứng dụng third-party (Exchange, SCCM…) compatible với target level
  • Thời gian thực hiện ngoài giờ cao điểm
  • Có kế hoạch rollback (restore backup) nếu cần
  • Stakeholders đã được thông báo
  • Schema version đã được extend phù hợp (adprep đã chạy)
  • DNS resolution hoạt động bình thường
  • SYSVOL replication healthy (DFS-R hoặc đã migrate từ FRS)

  • Schema version và Functional Level là hai thứ khác nhau:
    • Schema version: quyết định object class/attribute nào tồn tại trong database
    • Functional Level: quyết định tính năng nào được bật
  • Có thể extend Schema (chạy adprep) mà chưa nâng Functional Level
    • Điều này cho phép add WS2025 DC vào forest mà FFL vẫn ở 2016
    • Schema extension là prerequisite, nhưng FL raise là bước riêng biệt
  • Ngược lại, nâng Functional Level yêu cầu Schema đã được extend phù hợp
  • Quy trình đúng khi nâng cấp AD:
    1. Extend Schema (adprep /forestprep) → Schema version mới
    2. Update domain (adprep /domainprep)
    3. Nâng cấp/thay thế tất cả DC lên OS mới
    4. Nâng DFL → nâng FFL (thao tác cuối cùng — điểm không thể quay lại)

Câu hỏi thường gặp (FAQ)

Q: Schema extension có gây downtime không?

Không. AD vẫn hoạt động bình thường trong quá trình extend. Tuy nhiên, Schema replication là high-priority → có thể tăng replication traffic tạm thời. Trong forest lớn, nên schedule ngoài giờ cao điểm.

Q: Nâng FFL có rollback được không?

Không. Nâng FFL/DFL là thao tác MỘT CHIỀU. Cách duy nhất “rollback” là restore AD từ backup trước khi nâng → mất mọi thay đổi sau đó. Vì vậy LUÔN backup trước.

Q: WS2019 và WS2022 có Functional Level riêng không?

Không. Cả WS2019 và WS2022 đều sử dụng FFL/DFL 2016. Điều này nghĩa là nâng cấp từ WS2016 DC lên WS2022 DC không cần nâng FFL.

Q: Có thể có DFL khác nhau trong cùng forest không?

Có. Mỗi domain trong forest có thể có DFL khác nhau, miễn là tất cả DFL >= FFL. Ví dụ: FFL = 2016, DFL root = 2016, DFL child = 2025 → hợp lệ.

Q: Exchange schema extension lớn đến mức nào?

Rất lớn. Exchange thêm hàng trăm attribute vào schema. Replication có thể tốn bandwidth đáng kể trong forest lớn. Nên chạy ngoài giờ cao điểm và monitor replication sau đó.

Q: Gỡ Exchange có xoá schema extension không?

Không. Schema extension tồn tại vĩnh viễn ngay cả khi gỡ Exchange hoàn toàn. Schema là additive — không thể xoá attribute/class đã thêm.

Lưu ý quan trọng

  • Schema extension không gây downtime — AD vẫn hoạt động bình thường trong quá trình extend
  • Tuy nhiên, Schema replication là high-priority → có thể tăng replication traffic tạm thời
  • Không rollback được Schema extension — nếu sai, chỉ có thể deactivate attribute mới, không xoá được
  • Exchange schema extensions đặc biệt lớn — cần plan bandwidth cho replication
  • Khi nâng FFL lên 2008: SYSVOL chuyển từ FRS sang DFS-R — cần migrate thủ công nếu chưa làm
  • Khi nâng FFL lên 2008R2: có thể bật AD Recycle Bin — bật rồi không tắt được
  • Khi nâng FFL lên 2025: cần plan cho 32K database page migration — significant change
