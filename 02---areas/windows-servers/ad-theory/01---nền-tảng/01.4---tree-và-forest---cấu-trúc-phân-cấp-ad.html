Tree và Forest - Cấu trúc phân cấp AD

Tóm tắt nhanh

  • Tree là tập hợp domains có chung DNS namespace liên tục, tự động có parent-child trust
  • Forest là ranh giới cao nhất trong AD — chia sẻ chung 1 Schema và 1 Configuration partition
  • Forest Root Domain là domain đầu tiên được tạo, giữ vai trò đặc biệt không thể thay thế
  • Một forest có thể chứa nhiều trees với disjoint namespace (namespace khác nhau)
  • Schema là read-only trên mọi DC trừ Schema Master — thay đổi Schema ảnh hưởng toàn forest và không thể undo
  • Quyết định forest design là quan trọng nhất — thay đổi sau này cực kỳ khó khăn

Tree — Cây domain

Định nghĩa

  • Tree là tập hợp 1 hoặc nhiều domains chia sẻ contiguous DNS namespace (namespace liên tục)
  • Domain con kế thừa namespace của domain cha:
corp.example.com          ← Tree root
├── hr.corp.example.com   ← Child domain
├── it.corp.example.com   ← Child domain
└── sales.corp.example.com
    └── asia.sales.corp.example.com   ← Grandchild domain

Tương tự thực tế: Tree giống như tập đoàn kinh doanh với tên thương hiệu chung. Công ty mẹ corp.example.com có công ty con hr.corp.example.com, sales.corp.example.com — tất cả mang họ “example.com”.

Đặc điểm của Tree

Đặc điểmMô tảÝ nghĩa thực tế
NamespaceContiguous — domain con kế thừa DNS suffix của chaUser UPN: user@hr.corp.example.com
TrustAutomatic parent-child trust (two-way, transitive)User ở child domain tự động có thể xác thực ở parent domain
Quản trịMỗi domain có Domain Admins riêngIT team ở hr.corp.example.com tự quản lý domain của mình
ReplicationDomain partition riêng biệt cho từng domainDữ liệu HR không replicate sang IT domain → giảm WAN traffic

Tại sao tạo child domain?

  • Replication boundary: giảm replication traffic giữa các vùng địa lý có WAN chậm
  • Policy boundary: cần password policy hoặc security settings khác biệt hoàn toàn
  • Administrative autonomy: delegation ở level domain, không chỉ OU — IT team địa phương có toàn quyền
  • Regulatory requirement: data phải lưu tại quốc gia cụ thể, cần domain partition riêng

Lưu ý: Trend hiện đại là single domain, multiple OU — child domain chỉ tạo khi thật sự cần, vì tăng complexity đáng kể (thêm DC, DNS zone, trust management, admin overhead).

Forest — Rừng domain

Định nghĩa

  • Forest là container logic cao nhất trong Active Directory
  • Bao gồm 1 hoặc nhiều trees
  • True security boundary — cách ly hoàn toàn giữa 2 forests (trừ khi tạo Forest Trust)

Tương tự thực tế: Forest giống như quốc gia — có hiến pháp riêng (Schema), lãnh thổ riêng (Configuration), và chỉ hợp tác với quốc gia khác qua hiệp ước ngoại giao (Forest Trust). Mọi bang/tỉnh (domains) trong quốc gia đều phải tuân theo hiến pháp.

Các thành phần được chia sẻ trong Forest

Thành phầnPhạm viMô tảÝ nghĩa
SchemaToàn forestĐịnh nghĩa mọi object class và attributeThay đổi Schema = ảnh hưởng mọi DC
ConfigurationToàn forestSites, subnets, replication topology, servicesTopology mạng chung cho toàn forest
Global CatalogToàn forestPartial Attribute Set của mọi domainCross-domain search, UPN logon

  • User ở fabrikam.com có thể truy cập resources ở corp.example.com nhờ transitive trust
  • Lý do thêm tree mới: công ty mua lại công ty khác (M&A), muốn giữ DNS namespace riêng nhưng chia sẻ Schema/GC

Forest Root Domain

Vai trò đặc biệt

  • Domain đầu tiên được tạo khi thiết lập forest mới
  • Chứa 2 groups quan trọng nhất:
    • Enterprise Admins: quyền admin trên mọi domain trong forest — auto-added vào local Administrators group trên mọi DC
    • Schema Admins: quyền duy nhất để sửa Schema — nên để trống khi không cần
  • Giữ Forest-wide FSMO roles:
    • Schema Master (1 per forest)
    • Domain Naming Master (1 per forest)
  • Không thể xoá — xoá Forest Root Domain = xoá toàn bộ forest
  • Không thể demote DC cuối cùng của Forest Root Domain

Best practice cho Forest Root Domain

  • Nhiều tổ chức lớn dùng dedicated (empty) root domain: example.com chỉ chứa Enterprise Admins/Schema Admins, không chứa user/computer thường
    • Ưu điểm: isolate forest-level admin accounts, giảm attack surface, Enterprise Admins không bị ảnh hưởng nếu child domain bị compromise
    • Nhược điểm: thêm complexity, cần ít nhất 2 DC riêng cho root domain (tốn license)
  • Tổ chức nhỏ/vừa thường dùng single domain làm cả root domain và chứa users — hoàn toàn hợp lệ
  • Không bao giờ rename Forest Root Domain — ảnh hưởng toàn bộ forest trust path

Ví dụ thực tế cho từng mô hình

Single Domain: Công ty phần mềm 500 người, 3 văn phòng (HCM, HN, DN)

  • viettech.local — 1 domain, 3 sites, OUs theo phòng ban

Multi-Domain: Tập đoàn bán lẻ 5000 người, cần tách quản lý cho mỗi khu vực

  • retail.vn (Forest Root) → north.retail.vn → south.retail.vn

Multi-Tree: Tập đoàn mua lại công ty khác, giữ brand riêng

  • Tree 1: viettech.com (Forest Root), Tree 2: acquired-company.com

Multi-Forest: Ngân hàng + công ty chứng khoán cùng tập đoàn, quy định pháp lý yêu cầu tách biệt

  • Forest 1: bank.example.com, Forest 2: securities.example.com + Forest Trust

Schema

Schema là gì

  • Schema định nghĩa cấu trúc của mọi object có thể tồn tại trong AD:
    • Class: loại object (User, Computer, Group, OU, Contact…)
    • Attribute: thuộc tính của class (displayName, mail, memberOf, userAccountControl…)
  • 1 forest = 1 Schema duy nhất — replicate đến mọi DC trong forest

Tương tự thực tế: Schema giống như khuôn đúc trong nhà máy. Khuôn User quy định user object phải có: tên, email, password, department… Muốn thêm trường mới (ví dụ: mã nhân viên) → phải sửa khuôn. Nhưng khuôn đã sửa không thể undo — chỉ có thể ngừng dùng (deactivate).

Đặc điểm Schema

Đặc điểmMô tảHệ quả
ExtensibleCó thể thêm class/attribute mớiExchange, Lync, SCCM đều extend Schema khi cài
Không thể xoáAttribute/class đã thêm chỉ có thể deactivateCần test kỹ trong lab trước khi extend production
VersionedMỗi lần extend → Schema version tăngKiểm tra version: objectVersion attribute trên Schema container
Single MasterChỉ Schema Master FSMO role mới ghi đượcProtect Schema Master DC, giữ offline khi không cần
Forest-wide1 Schema cho toàn forestSchema conflict giữa ứng dụng → cần planning kỹ

Ví dụ thực tế: Schema Extension

Tình huống: Cài Exchange Server 2019 vào forest có sẵn AD

  1. Exchange setup chạy setup.exe /PrepareSchema — cần quyền Schema Admins
  2. Thêm ~1000+ attributes mới vào Schema (ví dụ: msExchMailboxGuid, msExchRecipientDisplayType)
  3. Extend class User — thêm attributes mới liên quan đến mailbox
  4. Schema replicate đến mọi DC trong forest — kể cả DC ở domain không dùng Exchange
  5. Không thể undo — nếu gỡ Exchange, các attributes vẫn nằm trong Schema mãi

Quy trình an toàn:

  • Test trong lab forest trước
  • Backup System State trên Schema Master
  • Thêm account vào Schema Admins → extend → remove khỏi Schema Admins
  • Monitor replication: repadmin /showrepl trên mọi DC

Schema Object ID (OID)

  • Mỗi class/attribute có OID (Object Identifier) duy nhất toàn cầu
  • Microsoft có dải OID: 1.2.840.113556.1.x.x
  • Custom attributes cần OID riêng — không dùng OID của vendor khác
  • Đăng ký OID doanh nghiệp tại IANA (hoặc generate từ Microsoft script oidgen.vbs)

Configuration Partition

Nội dung

  • Sites và Subnets: topology mạng vật lý
  • Site Links: kết nối giữa sites, schedule replication
  • Services: Exchange, DFSR, và các service đăng ký vào AD
  • Replication topology: được KCC tự động tạo
  • Partitions container: danh sách Application partitions

Câu hỏi thường gặp

Tôi có thể merge 2 forests thành 1 không?

  • Không có công cụ merge trực tiếp — đây là limitation lớn nhất của AD
  • Phải dùng Active Directory Migration Tool (ADMT) để migrate users, computers, groups từng bước
  • Quá trình phức tạp, tốn thời gian, ảnh hưởng users
  • Khuyến nghị: plan forest design kỹ từ đầu

Tại sao forest là true security boundary mà domain thì không?

  • Trong cùng forest, Enterprise Admins có quyền trên mọi domain
  • Domain Admins có thể khai thác SID History để leo thang quyền
  • Kerberos trust path trong forest là transitive — compromise 1 domain có thể ảnh hưởng forest
  • Chỉ forest boundary mới ngăn chặn hoàn toàn các attack path này

Số lượng domain tối đa trong 1 forest?

  • Không có giới hạn cứng — nhưng Microsoft khuyến nghị < 40 domains
  • Mỗi domain tăng thêm: replication traffic, DNS complexity, admin overhead
  • Best practice: ít domains nhất có thể

Lưu ý quan trọng

  • Forest design là quyết định quan trọng nhất — merge/split forest sau này cực kỳ khó khăn
  • Đừng tạo child domain chỉ vì có văn phòng ở thành phố khác — dùng Sites và OU. Child domain chỉ cần khi có yêu cầu isolation thật sự
  • Schema extension không thể undo — luôn test trong lab forest trước khi apply vào production
  • Enterprise Admins và Schema Admins nên để trống hoặc chỉ có members khi cần thực hiện forest-level operations, sau đó remove
  • Khi tạo Forest Trust giữa 2 forests, chúng vẫn giữ Schema riêng, Configuration riêng — chỉ chia sẻ authentication path
  • Functional Level của forest quyết định features có sẵn — chi tiết xem 03.2 - Schema và Functional Level
