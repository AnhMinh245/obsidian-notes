Domain Controller - Trái tim của AD

Tóm tắt nhanh

  • Domain Controller (DC) là máy chủ chạy AD DS role, lưu trữ bản sao đầy đủ của AD database và xử lý authentication/authorization
  • NTDS.DIT là file database chính (ESE engine), chứa 3 partition: Schema, Configuration, Domain — cùng Application Partitions
  • SYSVOL chứa GPO files và scripts, replicate giữa các DC bằng DFS-R
  • AD dùng mô hình multi-master replication — mọi DC đều read-write (trừ RODC)
  • Xác thực chủ yếu qua Kerberos v5 (ticket-based), truy vấn directory qua LDAP
  • DC là critical infrastructure — mỗi domain cần ít nhất 2 DC, placement ảnh hưởng trực tiếp đến user experience

DC là gì

Domain Controller là máy chủ Windows Server đã được promote (cài đặt AD DS role và chạy dcpromo hoặc Server Manager wizard) để trở thành thành viên quản lý của Active Directory domain.

Tương tự thực tế: DC giống như trụ sở UBND quận — nơi xác nhận danh tính (CCCD), cấp giấy phép (permissions), lưu trữ hồ sơ (database), và đồng bộ thông tin với các quận khác (replication). Mỗi quận cần ít nhất 1 trụ sở, nhưng có 2 trụ sở thì tốt hơn (high availability).

NTDS.DIT Database

Tổng quan

  • NTDS.DIT = NT Directory Services - Directory Information Tree
  • Đường dẫn mặc định: %SystemRoot%\NTDS\ntds.dit
  • Engine: ESE (Extensible Storage Engine) — cùng engine với Exchange Server database
  • Kèm theo transaction logs (edb*.log) để đảm bảo ACID compliance
  • Checkpoint file (edb.chk) theo dõi log nào đã commit vào database

Cấu trúc nội bộ NTDS.DIT (ESE Database)

NTDS.DIT sử dụng ESE (Extensible Storage Engine), hay còn gọi là JET Blue. Hiểu cấu trúc bên trong giúp troubleshoot và sizing:

Database sizing

  • Trước Server 2025: page size 8KB — giới hạn hiệu quả khoảng vài trăm triệu objects
  • Server 2025: page size 32KB — hỗ trợ 2+ tỷ objects, giảm IO overhead
  • Kích thước thực tế: khoảng 1 KB per user object (đơn giản) đến 5-10 KB (với nhiều attributes populated)
  • Ước tính: 10.000 users ≈ 50-100 MB NTDS.DIT (tuỳ complexity)
  • Defragmentation: ntdsutil có thể offline defrag — thu nhỏ file, cải thiện performance

Các Partition trong NTDS.DIT

PartitionPhạm vi replicateNội dungGhi được từ

  • Schema và Configuration giống nhau trên mọi DC trong forest
  • Domain partition chỉ có trên DC của domain đó — DC ở corp.example.com không chứa domain data của sales.example.com
  • Application partition linh hoạt: có thể replicate theo scope tuỳ chỉnh

Transaction Log và Recovery

  • ESE dùng Write-Ahead Logging (WAL): ghi vào log trước, commit vào database sau
  • Nếu DC crash giữa chừng → khi khởi động lại, ESE replay log để đưa database về trạng thái consistent
  • Circular logging mặc định TẮT cho NTDS.DIT — logs giữ lại cho recovery
  • Backup tạo snapshot consistent của NTDS.DIT + logs — cần dùng Windows Server Backup hoặc tool hỗ trợ VSS

SYSVOL

SYSVOL chứa gì

  • Group Policy Templates (GPT): mỗi GPO có 1 folder trong SYSVOL\domain\Policies\{GUID}\
    • Machine\Registry.pol — registry settings cho Computer Configuration
    • User\Registry.pol — registry settings cho User Configuration
    • Scripts (startup/shutdown, logon/logoff)
    • Admx/adml files (nếu Central Store được cấu hình)
  • Logon scripts: nếu user profile chỉ định logon script
  • NETLOGON share: alias trỏ vào SYSVOL\domain\Scripts\

Replication của SYSVOL

  • FRS (File Replication Service): cơ chế cũ (NT → Server 2003 R2), đã deprecated
    • Single-threaded, không reliable, không delta replication
  • DFS-R (Distributed File System Replication): cơ chế hiện đại (Server 2008+)
    • Delta replication: chỉ replicate phần thay đổi, tiết kiệm bandwidth
    • Remote Differential Compression (RDC) — compress changes hiệu quả
    • Multi-threaded, parallel replication
    • Migration từ FRS sang DFS-R là bắt buộc với functional level 2008+

SYSVOL Troubleshooting Concepts

Vấn đềTriệu chứngNguyên nhân phổ biến

SYSVOL share missingnet share không thấy SYSVOL/NETLOGONDFS-R service dừng, hoặc SYSVOL not ready

SYSVOL quá lớnDisk space warning trên DCScripts/files lớn đặt trong SYSVOL thay vì DFS share
  • Kiểm tra SYSVOL health: dcdiag /test:sysvolcheck, dfsrdiag pollad
  • DFS-R conflict: khi 2 admin sửa cùng GPO file trên 2 DC → DFS-R giữ 1 bản, move bản kia vào ConflictAndDeleted folder
  • Best practice: luôn edit GPO từ 1 DC duy nhất (thường là PDC Emulator) để tránh conflict

Multi-Master Replication

Nguyên lý

  • Mọi DC đều có thể nhận ghi (write) — không còn mô hình PDC/BDC như NT4
  • Thay đổi trên DC-A sẽ replicate sang DC-B, DC-C… tự động
  • Conflict resolution dựa trên:
    • Timestamp: thay đổi mới nhất thắng (last-writer-wins) — clock accuracy quan trọng
    • Version number: mỗi attribute có version, tăng mỗi lần sửa — version cao hơn thắng
    • USN (Update Sequence Number): số tuần tự trên mỗi DC để track changes — local per DC

Ngoại lệ: FSMO Roles

  • Dù là multi-master, một số operations chỉ nên thực hiện trên 1 DC để tránh conflict:
    • Schema Master: quản lý thay đổi Schema (1 per forest)
    • Domain Naming Master: thêm/xoá domain (1 per forest)
    • PDC Emulator: password changes ưu tiên, time sync, GPO editor, account lockout (1 per domain)
    • RID Master: cấp phát RID pools cho SID generation (1 per domain)
    • Infrastructure Master: cập nhật cross-domain references (1 per domain)
  • Chi tiết xem 03.1 - FSMO Roles - 5 vai trò chủ chốt

RODC — Read-Only Domain Controller

  • DC đặc biệt chỉ chứa bản sao read-only của AD database
  • Dùng cho branch office có bảo mật vật lý yếu
  • Không cache passwords mặc định — phải cấu hình Password Replication Policy
  • Chi tiết xem 03.3 - RODC - Read-Only Domain Controller

Các khái niệm Kerberos quan trọng

  • TGT (Ticket Granting Ticket): “vé vào cổng” — chứng minh user đã xác thực thành công, dùng để xin Service Ticket mà không cần nhập lại password
    • Lifetime mặc định: 10 giờ, renewable 7 ngày
    • Chứa: user identity, group memberships, session key, timestamps
    • Encrypted bằng KRBTGT account key — chỉ KDC mới decrypt được
  • Service Ticket: “vé vào phòng” — cho phép truy cập 1 service cụ thể
    • Lifetime = TGT lifetime hoặc service setting, tuỳ cái nào ngắn hơn
    • Encrypted bằng key của service account — chỉ service đó mới decrypt được
  • KDC (Key Distribution Center): chạy trên mỗi DC, gồm AS và TGS
    • Mỗi DC trong domain đều là KDC — client dùng DC gần nhất (cùng site)
  • KRBTGT account: service account đặc biệt, key của nó dùng để mã hoá TGT
    • Compromise account này = compromise toàn domain (Golden Ticket attack)
    • Password reset cần thực hiện 2 lần, cách nhau ít nhất 10 giờ (> TGT lifetime)
  • SPN (Service Principal Name): định danh duy nhất cho service
    • Format: service/hostname:port
    • Ví dụ: cifs/fileserver.corp.example.com, MSSQLSvc/sqlserver.corp.example.com:1433
    • Duplicate SPN → Kerberos authentication fail cho service đó

Kerberos Ticket Lifetime và Renewal

SettingMặc địnhVị trí cấu hìnhÝ nghĩa
TGT Lifetime10 giờDefault Domain PolicySau 10 giờ, TGT hết hạn, cần renew hoặc xin TGT mới
TGT Renewal7 ngàyDefault Domain PolicyTGT có thể renew trong 7 ngày, sau đó phải xác thực lại
Service Ticket Lifetime10 giờDefault Domain PolicyService Ticket có thể dùng 10 giờ
Clock Skew Tolerance5 phútDefault Domain PolicyNếu clock lệch > 5 phút → Kerberos fail

Kerberos Delegation Overview

  • Unconstrained Delegation: service có thể impersonate user đến bất kỳ service nào — nguy hiểm, tránh dùng
  • Constrained Delegation: service chỉ impersonate user đến danh sách services chỉ định — an toàn hơn
  • Resource-Based Constrained Delegation (RBCD): resource server tự quyết ai được impersonate đến mình — an toàn nhất, khuyến nghị từ Server 2012+
  • Delegation cần thiết cho multi-tier applications (ví dụ: Web Server → SQL Server, dùng identity của user)

Fallback: NTLM

  • Khi Kerberos không khả dụng (truy cập bằng IP thay vì hostname, hệ thống legacy), AD fallback về NTLM
  • NTLM yếu hơn Kerberos: không mutual authentication, dễ bị relay attack, không hỗ trợ delegation mạnh
  • NTLM v1: rất yếu, không nên dùng. NTLM v2: tốt hơn nhưng vẫn kém Kerberos
  • Best practice: disable NTLM nếu có thể, hoặc audit NTLM usage trước khi disable
    • Dùng GPO: Network security: Restrict NTLM: Audit NTLM authentication in this domain
    • Sau khi audit clean → enforce restrict

LDAP Interface

Tổng quan LDAP

  • LDAP (Lightweight Directory Access Protocol): giao thức tiêu chuẩn để truy vấn và chỉnh sửa directory
  • Ports:
    • 389: LDAP (plaintext hoặc STARTTLS)
    • 636: LDAPS (LDAP over SSL/TLS)
    • 3268: Global Catalog LDAP
    • 3269: Global Catalog LDAPS

LDAP Operations cơ bản

OperationMô tảVí dụ
BindXác thực với directory (simple bind hoặc SASL)App kết nối AD để query
SearchTìm kiếm objects theo filter — phổ biến nhấtTìm users trong OU: IT
AddTạo object mớiTạo user account
ModifySửa attributes của objectĐổi email, phone number
DeleteXoá objectXoá computer account
ModifyDNĐổi tên hoặc move objectMove user sang OU khác

LDAP Search cơ bản

  • Base DN: điểm bắt đầu tìm kiếm, ví dụ DC=corp,DC=example,DC=com
  • Scope: Base (chỉ base object), OneLevel (con trực tiếp), Subtree (tất cả bên dưới)
  • Filter: biểu thức lọc, ví dụ (&(objectClass=user)(department=IT))
  • LDAP signing: bắt buộc từ Server 2025 mặc định — encrypt LDAP traffic để chống man-in-the-middle

Câu hỏi thường gặp

DC có thể chạy thêm role khác không?

  • Không khuyến nghị — DC là critical infrastructure, nên isolate
  • Ngoại trừ: DNS Server (gần như bắt buộc trên DC) và DHCP (chấp nhận được cho tổ chức nhỏ)
  • Tuyệt đối không: File Server, SQL Server, IIS, Exchange trên DC

Nếu DC chết, chuyện gì xảy ra?

  • Nếu còn DC khác trong domain → clients tự chuyển sang DC khác (via DNS SRV records)
  • Nếu DC chết giữ FSMO role → cần seize role trên DC còn lại
  • Nếu tất cả DC chết → domain mất hoàn toàn (chỉ recover từ backup)

Dùng Windows Server Core hay Desktop Experience cho DC?

  • Server Core: khuyến nghị — ít attack surface, ít patches, ít reboot
  • Desktop Experience: dễ quản lý hơn cho admin mới — nhưng tốn resources và có nhiều vectors attack hơn
  • Trend: dùng Core + quản lý remote bằng RSAT/Windows Admin Center

Lưu ý quan trọng

  • Mỗi domain nên có ít nhất 2 DC — để đảm bảo high availability. Nếu chỉ có 1 DC và nó chết = mất toàn bộ authentication
  • DC không nên chạy workload khác (application server, database) — DC là critical infrastructure, cần isolate
  • KRBTGT password cần được reset định kỳ (2 lần, cách nhau ít nhất 10 giờ) để giảm rủi ro Golden Ticket
  • NTDS.DIT chứa password hashes — nếu ai lấy được file này + SYSTEM hive = có thể crack mọi password trong domain
  • LDAP signing và channel binding nên bật bắt buộc để chống LDAP relay attacks — Server 2025 bật mặc định
  • Luôn đặt NTDS.DIT và transaction logs trên volumes riêng — tách khỏi OS volume cho performance và recovery
