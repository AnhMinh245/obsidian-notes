DNS trong Active Directory

Tóm tắt nhanh

  • Active Directory phụ thuộc hoàn toàn vào DNS — không có DNS = AD không hoạt động
  • Domain name trong AD chính là DNS domain name; DC locator dựa trên DNS SRV records
  • AD-integrated DNS zones lưu trong AD database (không phải zone file), replicate theo AD replication
  • Client tìm DC thông qua DNS SRV records trong subdomain _msdcs — đây là cơ chế cốt lõi cho domain join và logon
  • Scavenging (dọn dẹp records cũ) cần được bật thủ công — mặc định tắt, dễ gây tích tụ stale records
  • Secure Dynamic Updates đảm bảo chỉ authenticated machines mới cập nhật được DNS records

Vì sao AD phụ thuộc DNS

DNS là nền tảng của AD

Quy tắc vàng: Nếu DNS hỏng, AD hỏng. Troubleshoot AD luôn bắt đầu bằng kiểm tra DNS. Đây là rule #1 trong AD troubleshooting.

DNS vs WINS (lịch sử)

Tiêu chíWINS (NT4)DNS (AD)
Resolution typeNetBIOS name (flat)FQDN (hierarchical)
DiscoveryBroadcast + WINS serverSRV records (standards-based)
ScalabilityHạn chếRất tốt
StandardsProprietaryRFC-based
Còn dùng?Chỉ legacy appsBắt buộc cho AD
  • NT4 dùng WINS (Windows Internet Name Service) — NetBIOS name resolution, broadcast-based
  • AD (từ Windows 2000) chuyển hoàn toàn sang DNS — hierarchical, standards-based, scalable
  • WINS vẫn có thể tồn tại cho backward compatibility nhưng không liên quan đến AD operations

Secure Dynamic Updates

Cơ chế hoạt động

sequenceDiagram
    participant Client as "Domain-joined PC"
    participant DNS as "AD-Integrated DNS Server"
    participant KDC as "KDC (DC)"

    Client->>DNS: Dynamic Update request<br/>"Create/update A record for pc-01"
    DNS->>Client: "Zone requires Secure Update.<br/>Authenticate first!"
    
    Client->>KDC: Kerberos AS-REQ<br/>"Authenticate for DNS update"
    KDC->>Client: TGT
    Client->>KDC: TGS-REQ for DNS service
    KDC->>Client: Service Ticket for DNS

    Client->>DNS: GSS-TSIG signed update<br/>+ Service Ticket
    DNS->>DNS: Verify Kerberos ticket<br/>Check ACL on record
    DNS->>Client: Update accepted
  • Khi zone là AD-integrated, có thể bật Secure Dynamic Updates Only
  • Chỉ authenticated computers (joined domain) mới được tạo/cập nhật DNS records
  • Record owner = computer account tạo record → chỉ owner mới update được
  • Ngăn chặn rogue devices đăng ký DNS records giả

Vấn đề “stale ownership”

  • Nếu computer bị rebuild (reinstall OS) → new computer account → không phải owner cũ → không update được DNS record cũ
  • Fix: admin xoá record cũ thủ công, hoặc dùng DnsUpdateProxy group
  • DnsUpdateProxy group: members tạo records không được set làm owner → mọi authenticated user đều update được
    • Thường dùng cho DHCP server — DHCP register DNS thay cho clients
    • Cẩn thận: records không có owner → bất kỳ ai cũng sửa được (less secure)

Key SRV Records

SRV RecordMục đíchAi đăng ký
_ldap._tcp.corp.example.comTìm DC cung cấp LDAP serviceMọi DC
_kerberos._tcp.corp.example.comTìm KDC cho Kerberos authenticationMọi DC
_ldap._tcp.<SiteName>._sites.corp.example.comTìm DC trong site cụ thểDC trong site đó
_gc._tcp.corp.example.comTìm Global Catalog serverChỉ GC server
_ldap._tcp.pdc._msdcs.corp.example.comTìm PDC EmulatorChỉ 1 DC giữ PDC Emulator role
_kerberos._tcp.dc._msdcs.corp.example.comTìm DC qua GUID-based DNS nameReplication partner discovery

SRV Record Format

_ldap._tcp.corp.example.com  SRV  0  100  389  dc-01.corp.example.com
  • Priority (0): ưu tiên (thấp hơn = ưu tiên hơn)
  • Weight (100): load balancing giữa các records cùng priority
  • Port (389): LDAP port
  • Target: FQDN của DC

_msdcs Subdomain

  • _msdcs.corp.example.com là subdomain đặc biệt chứa DC locator records
  • Forest Root Domain sở hữu zone _msdcs.<ForestRootDomain> — replicate toàn forest (ForestDnsZones)
  • Đây là zone quan trọng nhất — xoá hoặc corrupt zone này = AD ngừng hoạt động
  • Chứa GUID-based CNAME records cho mỗi DC — dùng cho replication partner discovery

Khi client không tìm được DC trong site

  1. Client query _ldap._tcp.<SiteName>._sites.corp.example.com → không có kết quả
  2. Fallback: query _ldap._tcp.corp.example.com → nhận bất kỳ DC nào trong domain
  3. DC trả về site name đúng cho client (dựa trên IP subnet mapping)
  4. Client cache site info và lần sau query đúng site
  5. Nếu subnet chưa được mapping vào site → client luôn dùng random DC → performance kém, WAN traffic không cần thiết

Lưu ý: Đây là lý do phải map mọi subnet vào site trong AD Sites and Services. Subnet chưa mapped = client “đi lạc”.

Dynamic DNS Update

Quy trình Dynamic Update

  • Khi computer join domain hoặc renew DHCP lease hoặc khởi động:
    1. Computer gửi SOA query để tìm DNS server authoritative cho zone
    2. Computer gửi Dynamic Update request (RFC 2136) đến DNS server
    3. Nếu Secure Dynamic Updates: DNS server yêu cầu Kerberos authentication trước khi chấp nhận update
    4. DNS server tạo/cập nhật A record (và PTR record nếu configured)
  • DHCP server cũng có thể đăng ký DNS records thay cho client (cho clients không hỗ trợ dynamic update)
    • DHCP đăng ký cả A và PTR records cho non-Windows clients
    • Windows clients tự đăng ký A record, DHCP đăng ký PTR record

DC Registration

  • Mỗi DC chạy service Netlogon để đăng ký SRV records vào DNS
  • Netlogon đăng ký records mỗi 1 giờ (re-registration interval)
  • Nếu DC không đăng ký được SRV records → clients không tìm được DC → logon fail
  • Troubleshoot: kiểm tra file %SystemRoot%\System32\config\Netlogon.dns — chứa danh sách records DC cần đăng ký
    • Nếu file này đúng nhưng DNS không có records → Netlogon service hoặc DNS service có vấn đề
    • Event ID 5774, 5775 trong System log = Netlogon registration issues

Scavenging — Dọn dẹp Records cũ

Vấn đề

  • Khi computer bị decommission nhưng không cleanup DNS → stale records tồn tại mãi
  • Stale records gây: DNS query trả về IP cũ, LDAP/Kerberos timeout, logon chậm, application errors

Aging và Scavenging — Cơ chế chi tiết

graph LR
    subgraph timeline["DNS Record Lifecycle"]
        create["Record created<br/>Timestamp = T0"]
        noRefresh["No-Refresh Interval<br/>(7 days default)<br/>Record CANNOT be<br/>refreshed during this period"]
        refresh["Refresh Interval<br/>(7 days default)<br/>Record CAN be<br/>refreshed by client"]
        scavenge["Scavenging eligible<br/>If not refreshed<br/>during Refresh Interval<br/>= Record DELETED"]
    end

    create --> noRefresh
    noRefresh --> refresh
    refresh --> scavenge
  • Aging: mỗi DNS record có timestamp ghi lần cập nhật cuối
  • No-Refresh Interval (mặc định 7 ngày): khoảng thời gian record không được refresh — giảm replication traffic không cần thiết (client cố refresh nhưng bị từ chối)
  • Refresh Interval (mặc định 7 ngày): sau No-Refresh, record có thể được refresh bởi client
  • Scavenging: sau No-Refresh + Refresh interval (14 ngày mặc định), records không được refresh sẽ bị xoá tự động

Cấu hình Scavenging — Phải bật 2 nơi

Nơi bậtCách bậtÝ nghĩa
DNS Server levelDNS Manager → Server Properties → Advanced → Enable automatic scavengingCho phép server chạy scavenging process
Zone levelDNS Manager → Zone Properties → General → AgingCho phép zone đó bị scavenge

Cả 2 đều phải bật mới hoạt động. Chỉ bật 1 trong 2 = scavenging không chạy.

Scavenging Configuration Best Practices

SettingGiá trị khuyến nghịGiải thích

Scavenging Period7 ngàyServer chạy cleanup mỗi 7 ngày

Lưu ý về Scavenging

  • Mặc định TẮT — admin phải bật thủ công trên cả DNS server và từng zone
  • Nếu không bật → stale records tích tụ vĩnh viễn → DNS ngày càng “bẩn”
  • Nếu bật quá aggressive (interval quá ngắn) → có thể xoá records hợp lệ của máy tạm offline
  • Static A records (tạo thủ công, timestamp = 0) không bị scavenging xoá — cần cleanup thủ công
  • Best practice: bật scavenging, giữ interval 7+7 ngày mặc định, monitor trước khi áp production
    • Chạy dnscmd /ageallrecords trên zone test trước → xem records nào sẽ bị ảnh hưởng

Split-Brain DNS

Vấn đề

  • Khi domain AD dùng cùng DNS namespace với domain public (ví dụ: AD domain = viettech.com, website cũng = viettech.com)
  • Internal clients query viettech.com → nhận AD DNS records (internal)
  • External clients query viettech.com → nhận public DNS records (external)
  • Đây gọi là split-brain DNS (hay split-horizon DNS)

DNSSEC trong AD

DNSSEC là gì

  • DNS Security Extensions: thêm chữ ký số (digital signatures) vào DNS responses
  • Ngăn chặn: DNS spoofing, cache poisoning, man-in-the-middle attacks trên DNS
  • AD DNS hỗ trợ DNSSEC từ Server 2012

DNSSEC trong AD — Thực tế

Khía cạnhChi tiết
Có cần cho internal AD?Tuỳ — nếu mạng internal tin tưởng (trusted), DNSSEC thêm complexity mà ít lợi ích
Key managementDNSSEC keys lưu trong AD → replicate tự động → dễ quản lý hơn standalone
Trust anchorsPhân phối qua Group Policy (auto) hoặc manual
Performance impactResponses lớn hơn (thêm RRSIG records), CPU overhead cho signing
RecommendationKhông bắt buộc cho internal AD DNS. Cân nhắc cho zones public hoặc khi có compliance requirement

Khi nào nên dùng DNSSEC trong AD

  • ✅ Regulatory compliance yêu cầu DNS integrity
  • ✅ High-security environments (quân sự, tài chính)
  • ✅ Public-facing AD zones (nếu có)
  • ❌ AD internal DNS thông thường — overhead không đáng, LDAP signing + Kerberos đã bảo vệ tốt
  • ❌ Nếu chưa có PKI — DNSSEC cần key management tốt

Conditional Forwarders, Stub Zones, Delegation

So sánh 3 cơ chế

Cơ chếCách hoạt độngKhi nào dùngTự động cập nhật
Conditional ForwarderForward queries cho domain cụ thể đến DNS server chỉ địnhForest Trust, partner DNSKhông — phải update IP thủ công
Stub ZoneChứa SOA, NS, glue A records — tự query NS records mớiAwareness về zone khác, linh hoạt hơn CFCó — tự update NS records
DelegationNS record trong parent zone trỏ đến child DNSChild domains trong treeTự động khi tạo child domain

Conditional Forwarders

  • DNS server forward queries cho domain cụ thể đến DNS server chỉ định
  • Dùng khi: cần resolve DNS name của forest/domain khác (ví dụ khi thiết lập Forest Trust)
  • Ví dụ: DNS server của corp.example.com forward queries cho partner.com đến 10.5.5.1
  • Phải tạo ở cả 2 phía khi thiết lập Forest Trust — thiếu 1 phía = trust verification fail
  • Có thể lưu trong AD (replicate đến mọi DC) hoặc lưu local trên server

Stub Zones

  • Chứa SOA, NS, và glue A records của zone khác (không chứa full zone data)
  • Tự động cập nhật khi NS records thay đổi ở zone gốc
  • Nhẹ hơn secondary zone, linh hoạt hơn conditional forwarder
  • Dùng khi cần maintain awareness về DNS servers của zone khác mà không cần full zone copy
  • Ưu điểm so với Conditional Forwarder: nếu partner đổi DNS server IP → stub zone tự biết

Delegation

  • Tạo NS record trong parent zone trỏ đến DNS server quản lý child zone
  • Ví dụ: zone corp.example.com delegate hr.corp.example.com đến DNS server riêng
  • AD tự động tạo delegation khi tạo child domain (nếu DNS server của parent domain reachable)
  • Nếu delegation hỏng → child domain DNS không resolve được từ parent

Câu hỏi thường gặp

DNS server nên chạy trên DC hay server riêng?

  • Trên DC — đây là Microsoft Best Practice
  • AD-integrated DNS chỉ hoạt động trên DC
  • Lợi ích: multi-master updates, secure dynamic updates, replicate tự động
  • Chạy DNS trên non-DC → phải dùng Standard Primary → single point of failure

Nếu DNS server chết, client có logon được không?

  • Không — client cần DNS để tìm DC
  • Mỗi client nên cấu hình ít nhất 2 DNS servers (primary + alternate)
  • DNS servers nên đặt ở sites khác nhau nếu có thể
  • Client cache DNS responses → nếu DNS chết nhưng client đã cache DC address → có thể logon tạm

Tôi có nên forward internal DNS ra Internet không?

  • Có — internal DNS server cần resolve Internet names cho clients
  • Cấu hình root hints hoặc forwarder đến DNS provider (ví dụ: 8.8.8.8, ISP DNS)
  • Không forward Internet traffic ngược lại — external DNS không nên resolve internal names

Records DC quan trọng nhất mà tôi phải kiểm tra là gì?

  1. _ldap._tcp.dc._msdcs.<DomainDNSName> — SRV records cho DCs
  2. _kerberos._tcp.dc._msdcs.<DomainDNSName> — KDC records
  3. A records cho mỗi DC
  4. _msdcs.<ForestRootDomain> zone tồn tại và có records

Lưu ý quan trọng

  • Luôn cài DNS role trên DC — AD-integrated DNS là best practice. Tránh dùng DNS server standalone cho AD zone
  • Conditional forwarders phải được tạo ở cả 2 phía khi thiết lập Forest Trust — thiếu 1 phía = trust verification fail
  • Đừng xoá zone _msdcs — đây là zone quan trọng nhất cho DC locator
  • Static A records (tạo thủ công, không có timestamp) không bị scavenging xoá — cần cleanup thủ công
  • DNS debug logging rất hữu ích cho troubleshoot nhưng tạo file log rất lớn — chỉ bật tạm thời
  • Mỗi client nên cấu hình 2 DNS servers — nếu chỉ có 1 DNS = single point of failure
  • Scavenging phải bật ở cả server level VÀ zone level mới hoạt động
  • DNS client settings trên DC: preferred DNS = chính nó (127.0.0.1 hoặc IP riêng), alternate = DC khác
