AD DS - Active Directory Domain Services

Tóm tắt nhanh

  • AD DS là role trung tâm khi cài đặt Domain Controller — nó đóng gói toàn bộ directory database, authentication engine, policy framework và replication engine vào một unit duy nhất
  • Bên trong AD DS chạy 6 thành phần cốt lõi: NTDS (database), Kerberos KDC, LDAP server, DNS (thường co-host), Netlogon và DFS-R (SYSVOL replication)
  • Group Policy xử lý theo thứ tự LSDOU (Local → Site → Domain → OU) với nhiều cơ chế lọc: inheritance blocking, enforcement, WMI filter, security filtering, loopback processing
  • Kerberos v5 là giao thức authentication chính, NTLM chỉ còn dùng cho legacy fallback
  • AD DS cung cấp thêm các cơ chế bảo mật nâng cao: Protected Users, Fine-Grained Password Policies, Managed Service Accounts, AD Recycle Bin

Kiến trúc tổng quan

AD DS không phải là một service đơn lẻ — khi bạn promote một Windows Server thành 01.3 - Domain Controller - Trái tim của AD, hệ điều hành kích hoạt cả một hệ sinh thái các thành phần phối hợp với nhau. Giống như một thành phố cần đồng thời hệ thống điện, nước, giao thông, hành chính — AD DS chạy database, authentication, directory, DNS, replication đồng thời và phụ thuộc lẫn nhau.

Các thành phần chi tiết

NTDS - NT Directory Service

  • Database engine: sử dụng ESE (Extensible Storage Engine) — cùng engine mà Exchange Server dùng
    • ESE là transactional database engine, hỗ trợ ACID (Atomicity, Consistency, Isolation, Durability)
    • Write-ahead logging: mọi thay đổi ghi vào transaction log trước khi commit vào database file
  • File database chính: %SystemRoot%\NTDS\NTDS.dit
  • Các file đi kèm:
    • edb.log — transaction log hiện tại (10 MB mặc định)
    • edb*.log — transaction log xoay vòng (circular logging mặc định)
    • edbres00001.jrs, edbres00002.jrs — reserved log (dự phòng khi ổ đĩa đầy, mỗi file 10 MB)
    • edbtmp.log — temporary transaction log đang được ghi
  • NTDS.dit chứa tất cả AD objects: users, computers, groups, OUs, GPO links, schema, configuration
  • Database được chia thành partitions (naming contexts):
    • Domain NC — object riêng của domain hiện tại (users, computers, groups)
    • Configuration NC — topology replication, sites, services (replicate toàn forest)
    • Schema NC — class và attribute definitions (replicate toàn forest)
    • Application partitions — DNS zones, custom partitions (replicate theo config)
  • Defragmentation:
    • Online: tự động mỗi 12 giờ, giải phóng space bên trong file nhưng file size không giảm
    • Offline: dùng ntdsutil trong DSRM, tạo file mới nhỏ hơn — hiếm khi cần trên server hiện đại với disk dung lượng lớn

Kerberos KDC - Key Distribution Center

  • Chạy trên mỗi Domain Controller — không phải chỉ trên 1 DC duy nhất
    • Mọi DC đều có khả năng authenticate users, giảm single point of failure
  • Gồm 2 sub-service:
    • AS (Authentication Service) — xác minh identity ban đầu, cấp TGT (Ticket-Granting Ticket)
    • TGS (Ticket-Granting Service) — dùng TGT để cấp Service Ticket cho từng resource cụ thể
  • Dùng shared secret (password hash của user/computer) để mã hoá ticket
  • Ticket có lifetime mặc định:
    • TGT: 10 giờ (renewable lên 7 ngày)
    • Service Ticket: 10 giờ
    • Có thể điều chỉnh qua Default Domain Policy nhưng cần cân nhắc security vs usability
  • KDC sử dụng krbtgt account — account đặc biệt trong AD, password hash của nó dùng để ký TGT
    • Compromise krbtgt = Golden Ticket attack — attacker có thể forge TGT cho bất kỳ user nào
    • Best practice: reset krbtgt password 2 lần (AD giữ current + previous password), cách nhau ít nhất 10 giờ

LDAP Server

  • LDAP (Lightweight Directory Access Protocol) — giao thức truy vấn và sửa đổi directory
    • Dựa trên X.500 DAP nhưng đơn giản hoá — “Lightweight” so với DAP gốc
  • Ports:
    • 389 — LDAP (cleartext hoặc STARTTLS)
    • 636 — LDAPS (LDAP over SSL/TLS) — yêu cầu certificate trên DC
    • 3268 — Global Catalog (GC) — search toàn forest
    • 3269 — Global Catalog over SSL
  • Mỗi object có một Distinguished Name (DN) duy nhất: CN=John,OU=Users,DC=corp,DC=local
    • DN hoạt động như “địa chỉ đầy đủ” trong directory tree
  • LDAP operations chính: Bind (authenticate), Search, Add, Modify, Delete, Compare
  • LDAP Referral — khi DC không giữ partition được query, nó trả referral đến DC phù hợp
  • Global Catalog port (3268) cho phép search tất cả object trong forest nhưng chỉ trả partial attribute set (PAS)
    • Khoảng 200 attributes trong PAS mặc định — đủ cho Universal Group membership resolution

DNS Server (co-hosted)

  • DNS không bắt buộc cài trên DC, nhưng hầu như luôn luôn co-host vì mối quan hệ phụ thuộc chặt chẽ
  • AD-Integrated DNS zones lưu trong AD database → replication tự động qua AD replication
    • Ưu điểm: không cần cấu hình zone transfer riêng, secure dynamic update tích hợp sẵn
  • Vai trò thiết yếu của DNS trong AD:
    • SRV records — để client tìm DC (_ldap._tcp.dc._msdcs.<domain>)
    • DC Locator — Netlogon dùng DNS để tìm DC gần nhất (site-aware)
    • Kerberos cần DNS để resolve KDC hostname
  • Chi tiết xem 01.7 - DNS trong Active Directory

Netlogon Service

  • Secure Channel — kênh giao tiếp được mã hoá giữa domain member và DC
    • Dùng machine account password (tự rotate mỗi 30 ngày mặc định)
    • Password rotation có thể điều chỉnh qua GPO: Domain member: Maximum machine account password age
    • Nếu secure channel bị hỏng → máy không thể authenticate → phải rejoin domain hoặc reset machine account bằng Test-ComputerSecureChannel -Repair
  • DC Locator — quy trình tìm DC phù hợp:
    1. Client gửi DNS query tìm SRV records _ldap._tcp.<sitename>._sites.dc._msdcs.<domain>
    2. DNS trả danh sách DC trong site
    3. Client gửi LDAP UDP ping đến các DC
    4. DC đầu tiên respond → client cache lại (DsGetDcName cache)
    5. Cache timeout mặc định: 15 phút — sau đó client re-discover
  • Netlogon cũng xử lý pass-through authentication cho NTLM — khi member server nhận NTLM auth request, nó chuyển tiếp qua secure channel đến DC để verify

DFS Replication (SYSVOL)

  • Từ Windows Server 2008+, DFS-R thay thế FRS (File Replication Service) cũ
    • FRS không còn được support từ Windows Server 2016 — migration lên DFS-R là bắt buộc
  • Replicate nội dung SYSVOL share giữa tất cả DC trong domain
  • SYSVOL chứa:
    • Group Policy Templates (GPT) — thư mục {GUID} cho mỗi GPO
    • Login/logoff scripts
    • Các file khác được admin đặt vào (cẩn thận: mọi file đều replicate đến tất cả DC)
  • DFS-R dùng RDC (Remote Differential Compression) — chỉ replicate phần thay đổi, tiết kiệm bandwidth
    • Cross-file RDC: có thể tìm block tương tự giữa các file khác nhau
  • Replication topology được KCC (Knowledge Consistency Checker) tính toán tự động

Group Policy - Cơ chế quản lý tập trung

Cấu trúc GPO

Mỗi Group Policy Object (GPO) thực chất gồm 2 phần tách biệt:

Thành phầnLưu trữNội dung
GPC (Group Policy Container)AD database (NTDS.dit)Metadata: GUID, version, link info, WMI filter link, status
GPT (Group Policy Template)SYSVOL (\\<domain>\Policies\{GUID})Settings thực tế: Registry.pol, Scripts, Security, ADMX
  • GPC và GPT liên kết bởi GUID — nếu 1 trong 2 bị thiếu/lỗi → GPO không áp dụng được
  • Version number trong GPC phải khớp với GPT — nếu mismatch, client sẽ re-download GPT
  • GPT structure bên trong thư mục GUID:
    • Machine\ — Computer Configuration settings
    • User\ — User Configuration settings
    • Machine\Registry.pol — registry-based policy cho computer
    • User\Registry.pol — registry-based policy cho user
    • Machine\Scripts\ — startup/shutdown scripts
    • User\Scripts\ — logon/logoff scripts

Quy tắc xử lý:

  • Later wins — GPO áp dụng sau sẽ ghi đè GPO trước nếu cùng setting
  • OU gần object nhất có priority cao nhất (trừ khi bị Enforced từ trên)
  • Nhiều GPO link vào cùng 1 container → xử lý theo Link Order (số nhỏ = priority cao)
  • Ví dụ thực tế: GPO “Password Policy” link ở Domain level (Link Order 1), GPO “Desktop Lockdown” link ở OU “Kiosk” — user trong OU Kiosk nhận cả 2, nhưng nếu conflict thì Desktop Lockdown wins vì gần hơn

Inheritance, Blocking và Enforcement

  • Inheritance — mặc định, GPO từ parent container sẽ áp xuống tất cả child containers
    • Cơ chế giống thác nước: settings “chảy” từ domain → parent OU → child OU
  • Block Inheritance — đặt tại OU/domain, ngăn GPO từ parent áp xuống
    • Chỉ chặn được GPO không enforced
    • Icon trong GPMC: dấu chấm than (!) trên OU
    • Use case: OU đặc biệt (vd: OU chứa service accounts) cần cách ly khỏi GPO chung
  • Enforced (trước đây gọi No Override) — đặt tại GPO link, đảm bảo GPO này luôn áp dụng bất kể Block Inheritance
    • Enforced + LSDOU cuối cùng = highest priority
    • Nhiều GPO enforced → GPO link cao nhất trong hierarchy wins (ngược với non-enforced)
    • Icon trong GPMC: biểu tượng khoá trên GPO link

WMI Filters

  • WMI (Windows Management Instrumentation) filter — dùng WQL query để quyết định GPO có áp dụng hay không
  • Ví dụ: chỉ áp dụng GPO cho máy có RAM > 8GB, hoặc chỉ cho Windows 11:
    • SELECT * FROM Win32_OperatingSystem WHERE Version LIKE "10.0.2%" AND ProductType = "1"
  • 1 GPO chỉ link được 1 WMI filter, nhưng 1 WMI filter có thể dùng cho nhiều GPO
  • WMI filter evaluate trên client — nếu query trả true → GPO áp dụng; false → bỏ qua toàn bộ GPO
  • Performance: WMI query chạy mỗi GP refresh cycle → filter phức tạp có thể gây chậm logon/startup

Security Filtering

  • Mặc định GPO áp dụng cho group Authenticated Users — tức tất cả user/computer đã authenticate
  • Có thể thay đổi để chỉ áp dụng cho security group cụ thể
  • Yêu cầu permission: Read + Apply Group Policy trên GPO
  • Từ MS14-025 patch: cần thêm Domain Computers có quyền Read nếu dùng Computer Configuration
    • Thiếu permission này = GPO computer settings không áp dụng → lỗi rất phổ biến sau patching

Loopback Processing

  • Bình thường: User settings áp dụng theo OU chứa user object
  • Loopback Processing: User settings áp dụng theo OU chứa computer object mà user đang logon vào
  • 2 mode:
    • Replace — chỉ dùng User GPO của computer OU, bỏ qua User GPO gốc hoàn toàn
    • Merge — kết hợp cả hai, computer OU GPO wins khi conflict
  • Use case: kiosk machines, RDS session hosts, lab computers — nơi cần cố định user experience bất kể ai logon
  • Ví dụ: nhân viên IT logon vào máy kiosk → vẫn bị apply wallpaper cố định, Start menu giới hạn vì loopback Replace mode

Client-Side Extensions (CSE)

  • GP Engine trên client không tự xử lý tất cả settings — nó gọi các CSE DLL tương ứng
  • Mỗi CSE xử lý 1 loại setting:
    • Registry CSE → Registry-based settings (ADMX)
    • Security CSE → Security settings (password policy, audit policy)
    • Scripts CSE → Startup/shutdown, logon/logoff scripts
    • Software Installation CSE → MSI deployment
    • Folder Redirection CSE → redirect Desktop, Documents, etc.
    • IE Maintenance CSE (deprecated từ IE11)
  • CSE được identify bằng GUID trong registry
  • Mỗi CSE có thể có behavior riêng: có CSE chỉ process khi có thay đổi, có CSE luôn process mỗi cycle

Lỗi phổ biến:

  • GPO link Disabled — admin vô tình disable link thay vì chỉ edit
  • User Configuration Disabled trên GPO chỉ có User settings (hoặc ngược lại)
  • Security filtering bỏ Authenticated Users nhưng quên thêm group cụ thể
  • SYSVOL replication chưa hoàn tất — GPO edit trên DC-A nhưng client dùng DC-B

Ví dụ thực tế - GPO Scenarios

Scenario 1: Password Policy cho VIP Users

  • Default Domain Policy set password min 8 ký tự, max age 90 ngày
  • Yêu cầu: Domain Admins phải dùng password 16 ký tự, max age 30 ngày
  • Giải pháp: Fine-Grained Password Policy (FGPP) — không dùng GPO vì password policy chỉ áp dụng ở domain level

Scenario 2: Kiosk Lockdown

  • OU “Kiosk Computers” chứa máy kiosk
  • GPO “Kiosk Policy” link vào OU này, enable Loopback Processing (Replace mode)
  • User settings trong GPO: disable Control Panel, lock Start Menu, auto-logoff sau 15 phút idle
  • Bất kỳ user nào logon vào máy trong OU này đều bị apply settings trên

Scenario 3: Software Deployment có điều kiện

  • GPO “Deploy Office 365” link ở domain level
  • WMI Filter: SELECT * FROM Win32_ComputerSystem WHERE TotalPhysicalMemory >= 8589934592 (>= 8 GB RAM)
  • Security Filter: group “Office Users”
  • Kết quả: chỉ máy có đủ RAM VÀ user trong group mới nhận Office deployment

Authentication Protocols

Kerberos v5 - Giao thức chính

Kerberos dựa trên nguyên tắc trusted third party (KDC) — client không bao giờ gửi password trực tiếp đến resource server. Tương tự như hệ thống vé: bạn mua vé tại quầy (KDC), rồi dùng vé đó để vào các khu vực khác nhau mà không cần xác minh lại danh tính.

sequenceDiagram
    participant Client
    participant AS as "KDC: AS<br/>Authentication Service"
    participant TGS as "KDC: TGS<br/>Ticket-Granting Service"
    participant Server as "Resource Server"

    Note over Client: User enters password<br/>Client computes hash

    Client->>AS: 1. AS-REQ<br/>Username + Timestamp encrypted with password hash
    AS->>AS: Verify identity<br/>Lookup password hash in AD
    AS-->>Client: 2. AS-REP<br/>TGT encrypted with krbtgt hash<br/>+ Session Key encrypted with user hash

    Note over Client: Client has TGT<br/>Cached in memory

    Client->>TGS: 3. TGS-REQ<br/>TGT + SPN target + Authenticator
    TGS->>TGS: Decrypt TGT with krbtgt hash<br/>Verify Authenticator
    TGS-->>Client: 4. TGS-REP<br/>Service Ticket encrypted with service account hash<br/>+ Service Session Key

    Client->>Server: 5. AP-REQ<br/>Service Ticket + Authenticator
    Server->>Server: Decrypt Service Ticket<br/>Verify Authenticator
    Server-->>Client: 6. AP-REP<br/>Mutual Authentication confirm

    Note over Client,Server: Session established<br/>Access granted per ACL

Các khái niệm quan trọng:

  • TGT (Ticket-Granting Ticket) — “vé tổng” chứng minh identity, dùng để xin Service Ticket mà không cần nhập lại password
    • Cached trong LSASS memory — đây là lý do LSASS process là target hàng đầu cho credential theft
  • Service Ticket — vé cho 1 resource cụ thể, chứa thông tin authorization (PAC)
  • SPN (Service Principal Name) — định danh duy nhất cho mỗi service instance: HTTP/webserver.corp.local
    • Format: <serviceclass>/<host>:<port>/<servicename>
    • Duplicate SPN → Kerberos fail → fallback NTLM
  • PAC (Privilege Attribute Certificate) — embedded trong ticket, chứa SID của user + group membership → server dùng PAC để quyết định authorization
    • PAC được ký bởi KDC — server có thể (optionally) verify chữ ký với KDC
  • Pre-authentication — bước 1 yêu cầu client chứng minh biết password bằng cách encrypt timestamp → chống replay attack và offline brute-force
    • Disable pre-auth → AS-REP Roasting attack — attacker request TGT mà không cần biết password
  • Delegation:
    • Unconstrained — service có thể impersonate user đến bất kỳ resource nào (rất nguy hiểm, avoid)
    • Constrained — service chỉ impersonate đến các SPN được chỉ định (S4U2Proxy)
    • Resource-Based Constrained Delegation (RBCD) — quyền delegate được set tại resource, không phải tại service → linh hoạt hơn cho cross-domain

NTLM - Giao thức legacy

  • Challenge-Response protocol — không dùng third party, DC verify trực tiếp
  • Quy trình:
    1. Client gửi username đến server (NEGOTIATE message)
    2. Server gửi challenge (16-byte random nonce) — CHALLENGE message
    3. Client dùng password hash để encrypt challenge → gửi response — AUTHENTICATE message
    4. Server chuyển tiếp (username + challenge + response) đến DC qua Netlogon secure channel
    5. DC lookup password hash, tự tính response, so sánh → accept/reject

Tại sao NTLM vẫn tồn tại

Dù Microsoft khuyến nghị disable NTLM, nó vẫn cần trong nhiều tình huống:

Tình huốngLý do cần NTLMGiải pháp thay thế
Workgroup machinesKhông có Kerberos KDCJoin domain nếu có thể
IP address accessKerberos cần hostname → SPNDùng hostname thay vì IP
Legacy applicationsApp không hỗ trợ KerberosUpgrade hoặc wrap trong proxy
Kerberos failDC unreachable, SPN lỗi, time skewFix root cause
Cross-forest (no trust)Kerberos cần trust pathThiết lập forest trust
Local account logonKerberos chỉ dùng domain accountsDùng domain accounts

NTLM Risks và Mitigation

  • Pass-the-Hash — attacker có NTLM hash không cần biết password gốc, dùng hash trực tiếp để authenticate
    • Mitigation: Credential Guard (virtualization-based security), Protected Users group
  • NTLM Relay — attacker đứng giữa, chuyển tiếp authentication response đến target khác
    • Mitigation: SMB Signing, Extended Protection for Authentication (EPA), LDAP channel binding
  • Không có mutual authentication — client không verify server identity → MitM risk
    • Kerberos có mutual auth (AP-REP), NTLM thì không
  • Không hỗ trợ MFA natively — NTLM chỉ dựa vào password hash
  • Brute-force offline — NTLMv1 hash dễ crack, NTLMv2 tốt hơn nhưng vẫn vulnerable

Chiến lược giảm dần NTLM:

  1. Audit: bật NTLM auditing qua GPO (Network security: Restrict NTLM)
  2. Identify: xem Event Log 8001-8004 để biết app/service nào dùng NTLM
  3. Fix: sửa SPN, upgrade app, chuyển sang Kerberos
  4. Restrict: bật NTLM restriction dần dần theo OU/domain
  5. Block: cuối cùng block NTLM hoàn toàn (hiếm khi đạt được 100%)

Claims-based Authentication

  • Bổ sung từ Windows Server 2012+
  • Claims — assertions về identity: “user thuộc department Finance”, “device có BitLocker enabled”
    • Claims giống như “nhãn dán” bổ sung trên identity, ngoài group membership
  • Dynamic Access Control (DAC) — dùng claims để define access rules thay vì chỉ dựa vào group membership
    • Ví dụ: “Chỉ user có claim Department=Finance AND clearance=Confidential mới đọc được folder Finance Reports”
  • Claims được embed vào Kerberos ticket (trong PAC) → không phải giao thức riêng
  • Use case: conditional access policies, resource classification, central access policies

Authorization Model

Access Token

Khi user logon thành công, hệ thống tạo Access Token chứa:

  • User SID — Security Identifier duy nhất của user
  • Group SIDs — tất cả group mà user là member (kể cả nested, cả universal groups)
  • Privileges — quyền hệ thống (SeBackupPrivilege, SeDebugPrivilege…)
  • Claims — nếu DAC được bật
  • Integrity Level — Low, Medium, High, System (UAC related)
  • Token không tự update khi group membership thay đổi — user phải logoff/logon lại để nhận token mới
    • Ngoại lệ: klist purge chỉ xoá Kerberos ticket, không ảnh hưởng group SIDs trong token

ACL - Access Control List

  • DACL (Discretionary ACL) — danh sách ACE (Access Control Entry) quy định ai được phép/bị cấm truy cập
    • Deny ACE luôn được evaluate trước Allow ACE — đây là lý do “Deny always wins”
    • Nếu không có DACL → everyone có full access (null DACL)
    • Nếu DACL rỗng → nobody có access (empty DACL)
  • SACL (System ACL) — quy định auditing: log khi ai truy cập thành công/thất bại
    • Cần privilege SeSecurityPrivilege để đọc/sửa SACL
    • Kết hợp với Advanced Audit Policy cho compliance (SOX, HIPAA, PCI-DSS)
  • Inheritance — ACE từ parent container tự động áp xuống child objects
    • Có thể disable inheritance tại child, chọn copy hoặc remove inherited ACEs
    • Copy: giữ lại ACEs hiện tại nhưng chuyển từ inherited → explicit
  • Effective Permissions — kết quả tổng hợp từ tất cả ACE áp dụng cho user (tính cả group membership)
    • Dùng tab “Effective Access” trong Advanced Security settings để kiểm tra

SID Structure

  • Format: S-1-5-21-<DomainID>-<RID>
    • S-1 = SID revision 1
    • 5 = NT Authority
    • 21 = domain subauthority
  • Well-known SIDs:
    • S-1-5-21-...-500 — Administrator (built-in, không thể xoá)
    • S-1-5-21-...-512 — Domain Admins
    • S-1-5-21-...-519 — Enterprise Admins (chỉ forest root domain)
    • S-1-1-0 — Everyone
    • S-1-5-11 — Authenticated Users
    • S-1-5-18 — Local System
  • SID không thay đổi khi rename user/group — đây là lý do rename không ảnh hưởng permissions
  • SID History — attribute lưu SID cũ khi migrate user giữa domains → giữ access đến resources ở domain cũ
    • Rủi ro bảo mật: SID History có thể bị lạm dụng cho privilege escalation → nên cleanup sau migration

Từ Windows Server 2008+, FGPP cho phép đặt password policy khác nhau cho các nhóm user khác nhau trong cùng domain — khắc phục giới hạn của GPO (password policy chỉ áp dụng ở domain level).

Security group đặc biệt cung cấp hardened authentication cho các tài khoản nhạy cảm:

Ai nên ở trong Protected Users:

  • Domain Admins, Enterprise Admins
  • Service accounts không dùng NTLM hoặc delegation
  • VIP accounts có quyền hạn cao

Ai KHÔNG nên ở trong Protected Users:

  • Service accounts cần delegation (SQL Server, IIS)
  • Accounts cần NTLM cho legacy apps
  • Computer accounts (sẽ break Kerberos ticket refresh)

Authentication Policies và Silos (2012 R2+)

  • Authentication Policies — kiểm soát TGT lifetime và access conditions cho tài khoản cụ thể
    • Có thể set khác nhau cho User, Computer, Service accounts
    • Dùng access control expressions: “Chỉ cấp TGT nếu logon từ máy trong group Protected-Workstations”
  • Authentication Policy Silos — nhóm accounts + policies thành một “vùng bảo mật”
    • Ví dụ: Silo “Tier 0” chứa Domain Admins + DCs → chỉ cho phép Domain Admins logon lên DCs
    • Implement tiered admin model (Tier 0 / Tier 1 / Tier 2)
  • Yêu cầu: Domain Functional Level 2012 R2+, Kerberos armoring (FAST)

Managed Service Accounts

Vấn đề với Service Accounts truyền thống

  • Service accounts (tài khoản chạy Windows services) thường dùng regular domain user accounts
  • Vấn đề:
    • Password phải managed thủ công — admin phải nhớ rotate
    • Password thường không bao giờ đổi (security risk)
    • Nhiều services dùng chung 1 account → change password = restart tất cả services
    • SPN phải đăng ký thủ công

Standalone Managed Service Account (sMSA)

  • Giới thiệu từ Windows Server 2008 R2
  • AD tự động quản lý password (rotate mỗi 30 ngày)
  • Tự động đăng ký SPN
  • Giới hạn: chỉ dùng cho 1 server duy nhất — không thể dùng cho clustered services hoặc NLB

Group Managed Service Account (gMSA)

  • Giới thiệu từ Windows Server 2012
  • Mở rộng sMSA: có thể dùng cho nhiều servers cùng lúc (NLB, clustering, farm)
  • KDS (Key Distribution Service) trên DC sinh password tự động
    • Tất cả servers trong cùng group đều retrieve được cùng password từ KDS
  • Yêu cầu: Schema phải ≥ Windows Server 2012, KDS root key phải tồn tại

AD Recycle Bin

Vấn đề trước AD Recycle Bin

  • Xoá object trong AD → object di chuyển vào Deleted Objects container (tombstone)
  • Tombstone chỉ giữ một số ít attributes — hầu hết attributes bị strip
  • Muốn restore tombstone → object mất attributes → phải manually repopulate
    • Group membership, OU placement, custom attributes — tất cả mất
  • Nếu tombstone lifetime hết (mặc định 180 ngày) → object bị xoá vĩnh viễn khỏi database
  • Phương án duy nhất: restore authoritative từ backup → ảnh hưởng toàn bộ AD, complex, risky

AD Recycle Bin (2008 R2+)

  • Enable AD Recycle Bin → deleted objects giữ tất cả attributes trong giai đoạn “Deleted” (mặc định 180 ngày)
  • Restore object = restore hoàn chỉnh, kể cả group membership, linked attributes
  • Bất khả đảo ngược: một khi enable, không thể disable AD Recycle Bin
  • Yêu cầu: Forest Functional Level ≥ 2008 R2

Câu hỏi thường gặp

Q: AD DS và AD có giống nhau không?
A: AD là tên chung cho bộ directory services của Microsoft. AD DS là role cụ thể (Domain Services). Còn có AD LDS, AD CS, AD FS, AD RMS — mỗi cái là role riêng biệt.

Q: Có phải mọi DC đều chạy AD DS?
A: Đúng — promote server thành DC = cài AD DS role. Không có DC nào không chạy AD DS.

Q: Password policy chỉ áp dụng ở Domain level, không ở OU level — tại sao?
A: Design decision của Microsoft. GPO password policy chỉ effective khi link ở domain root. Muốn per-group password policy → dùng FGPP (PSO). Đây là misconception phổ biến khi admin mới link password GPO ở OU rồi thắc mắc tại sao không hoạt động.

Q: AD Recycle Bin có ảnh hưởng performance không?
A: Rất ít. Deleted objects giữ attributes nhưng không tham gia vào normal queries. Database size tăng chút nhưng trên server hiện đại không đáng kể. Benefit >>> cost.

Q: Khi nào nên dùng gMSA thay vì regular service account?
A: Luôn ưu tiên gMSA khi service hỗ trợ (IIS, SQL Server, Task Scheduler, và hầu hết Windows services). Regular account chỉ dùng khi service/app yêu cầu interactive logon hoặc chạy trên non-Windows.

Lưu ý quan trọng

CAUTION

NTDS.dit là crown jewel — chứa tất cả password hash. Bảo vệ backup NTDS.dit như bảo vệ DC. Bất kỳ ai có access vào file backup này đều có thể extract toàn bộ password hashes offline.

  • krbtgt account — reset password krbtgt phải thực hiện 2 lần (vì AD giữ 2 password gần nhất), cách nhau ít nhất 10 giờ (TGT max lifetime). Reset lần 1 invalidate TGT cũ nhất, reset lần 2 invalidate tất cả TGT hiện tại.
  • GPO troubleshooting — dùng gpresult /r hoặc rsop.msc để xem Resultant Set of Policy; gpupdate /force để force refresh. Kiểm tra Event Log Group Policy Operational channel cho chi tiết.
  • Group Policy refresh interval — mặc định 90 phút ± random offset 0-30 phút cho workstation/member server; 5 phút cho DC. Random offset tránh tất cả machines query DC cùng lúc.
  • Kerberos time sync — client và DC phải lệch tối đa 5 phút (mặc định), nếu lệch nhiều hơn → authentication fail. PDC Emulator là authoritative time source cho domain.
  • SYSVOL replication lag — GPO vừa edit trên DC này có thể chưa replicate sang DC khác → user connect DC khác sẽ nhận GPO cũ. Kiểm tra repadmin /replsummary khi troubleshoot.
  • AD Recycle Bin — enable ngay khi forest functional level cho phép. Không có lý do gì để không enable. Cost gần bằng 0, benefit rất lớn.
