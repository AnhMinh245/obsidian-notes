DHCP - Kiến trúc và nguyên lý

Tóm tắt nhanh

  • DHCP tự động cấp phát IP address và network configuration cho clients, loại bỏ quản lý IP thủ công ở quy mô lớn
  • Quy trình cấp phát cơ bản: DORA (Discover → Offer → Request → Acknowledge) — 4 bước broadcast-based
  • DHCP Failover hỗ trợ 2 mode: Hot Standby (primary/secondary) và Load Balance (chia tải 50/50)
  • Trong môi trường AD, DHCP server phải được authorized — cơ chế chống rogue server cấp sai IP
  • DHCPv6 hoạt động khác fundamental so với DHCPv4, tương tác với SLAAC/RA
  • DHCP security (starvation, rogue server, snooping) là mối quan tâm quan trọng trong enterprise

Tại sao cần DHCP

Tưởng tượng bạn quản lý tòa nhà 500 phòng — nếu phải đánh số phòng thủ công, ghi sổ ai ở phòng nào, đổi số phòng khi ai chuyển đi → chaos. DHCP tự động hoá toàn bộ quy trình này cho IP addresses.

  • Gán IP thủ công gây ra:
    • Xung đột IP (2 máy cùng IP) — lỗi phổ biến nhất, cực khó debug khi mạng lớn
    • Khó scale: 500 máy = 500 lần cấu hình, mỗi lần risk nhập sai
    • Khó thay đổi: đổi DNS server = sửa trên từng máy một
    • Khó track: ai đang dùng IP nào? → spreadsheet quản lý IP = nightmare
    • Human error: gõ sai subnet mask = máy mất kết nối mà không rõ nguyên nhân
  • DHCP giải quyết tất cả vấn đề trên bằng cấp phát tập trung, tự động, có thời hạn (lease)
    • Thêm 100 máy mới? DHCP tự cấp IP — zero manual work
    • Đổi DNS server? Sửa 1 chỗ trên DHCP → tất cả clients nhận config mới khi renew lease

Nguyên lý hoạt động - DORA

sequenceDiagram
    participant Client
    participant DHCPServer as "DHCP Server"

    Client->>DHCPServer: 1. DHCPDISCOVER<br/>Broadcast 255.255.255.255<br/>Src: 0.0.0.0, MAC address

    DHCPServer->>DHCPServer: Find available IP<br/>in scope

    DHCPServer-->>Client: 2. DHCPOFFER<br/>Proposed IP + Subnet + Options<br/>Broadcast or Unicast

    Note over Client: Client may receive<br/>multiple Offers from multiple servers

    Client->>DHCPServer: 3. DHCPREQUEST<br/>Broadcast: selects specific Offer<br/>Includes Server Identifier

    Note over DHCPServer: Other servers see<br/>Request not selecting them<br/>withdraw their Offer

    DHCPServer-->>Client: 4. DHCPACK<br/>Confirms IP assignment<br/>Full configuration

    Note over Client: Client configures IP<br/>Starts Lease Timer

Chi tiết từng bước:

  1. DISCOVER — Client broadcast (destination 255.255.255.255, source 0.0.0.0)
    • Chứa: Client MAC address, hostname, requested lease time, previous IP (nếu có)
    • XID (Transaction ID) — random number để match request với response
    • Client gửi trên port 68 (DHCP client), server listen trên port 67 (DHCP server)
  2. OFFER — Server đề xuất IP address
    • IP chưa bị commit — server chỉ tạm “reserve” trong vài giây chờ client chọn
    • Nếu nhiều server cùng offer → client thường chọn offer đến trước
    • Server kiểm tra IP availability: có thể ping trước khi offer (nếu Conflict Detection bật)
  3. REQUEST — Client chọn offer, broadcast để tất cả server biết
    • Chứa Server Identifier option (IP của server được chọn) — option 54
    • Các server không được chọn → release offered IP về pool
    • REQUEST là broadcast vì client vẫn chưa có IP hợp lệ
  4. ACK — Server xác nhận, commit lease vào database
    • Chứa đầy đủ: IP, subnet mask, default gateway, DNS servers, lease duration, tất cả options
    • Client nhận ACK → bind IP address → bắt đầu lease timer

  • Client cũng gửi DHCPREQUEST khi reboot — xin lại IP cũ (nếu lease chưa hết)
    • Server kiểm tra: IP vẫn available cho MAC này? Nếu có → ACK, nếu không → NAK
  • DHCPRELEASE — client chủ động trả IP trước khi hết hạn
    • Ít xảy ra tự động, thường do admin chạy ipconfig /release
    • Lưu ý: DHCPRELEASE là unicast — chỉ gửi đến server, không broadcast
  • DHCPDECLINE — client phát hiện IP bị trùng (ARP check sau khi nhận ACK) → từ chối, server đánh dấu IP là BAD_ADDRESS
  • DHCPNAK — server từ chối request (client xin IP không thuộc scope hiện tại, vd sau khi move sang subnet khác)

DHCP Server Architecture

Scope

  • Scope = 1 dải IP cho 1 subnet — đơn vị cấp phát cơ bản nhất
  • Định nghĩa: IP range, subnet mask, lease duration, exclusion ranges, options
  • 1 scope = 1 subnet — không thể 1 scope phục vụ 2 subnet khác nhau
  • Scope phải được Activate mới bắt đầu cấp phát
  • Mỗi scope có riêng: statistics (used/available), exclusions, reservations, options

Superscope

  • Nhóm nhiều scope lại thành 1 đơn vị quản lý
  • Use case chính: multinetting — 1 physical segment có nhiều logical subnet
    • Ví dụ: VLAN 10 chạy cả 10.1.1.0/24 và 10.1.2.0/24 — khi scope 1 hết IP, cấp từ scope 2
  • Superscope giúp DHCP server cấp IP từ scope nào còn trống
  • Không phổ biến — multinetting thường là dấu hiệu cần re-design network

Exclusion Ranges

  • Dải IP loại trừ khỏi pool — server sẽ không cấp các IP này
  • Dùng cho: default gateway, switches, printers, servers có IP tĩnh nằm trong subnet range
  • Ví dụ: scope 10.1.1.0/24, exclusion 10.1.1.1 - 10.1.1.20 → chỉ cấp từ .21 trở đi
  • Best practice: exclusion ở đầu hoặc cuối range, tránh rải rác → dễ quản lý

Reservations

  • MAC → IP binding — đảm bảo device cụ thể luôn nhận IP cố định qua DHCP
  • Kết hợp ưu điểm: IP cố định (như static) + quản lý tập trung (như DHCP options)
  • Use case: printers, IP phones, servers cần IP ổn định nhưng vẫn muốn quản lý DHCP centrally
  • Reservation vẫn đi qua quy trình DORA — client vẫn phải request, server đối chiếu MAC → trả reserved IP
  • Reservation có thể có options riêng — override scope options cho device cụ thể

Option Hierarchy

  • Options có thể set ở nhiều level — level cụ thể hơn ghi đè level chung hơn:

  |-- Scope Options (override server options cho scope nay)

Option Classes

Vendor Class

  • Options theo hãng thiết bị — server nhận diện vendor từ option 60 trong DISCOVER
  • Ví dụ thực tế:
    • Microsoft Options — vendor class mặc định cho Windows clients
    • Cisco IP Phone — send TFTP server, VLAN info cho IP phones
    • Tạo custom class: netsh dhcp server add class "CustomDevice" "My devices" "" 1

User Class

  • Options theo nhóm tuỳ chỉnh do admin define
  • Client tự declare thuộc class nào: ipconfig /setclassid "Ethernet" "VoIP"
  • Use case:
    • Class “Laptop” → lease ngắn 4 giờ (di chuyển nhiều)
    • Class “Desktop” → lease dài 8 ngày (cố định)
    • Class “VoIP” → DNS server khác, gateway khác cho voice VLAN

Hot Standby Mode

  • Primary xử lý 100% DHCP requests trong điều kiện bình thường
  • Secondary nhận bản sao lease database qua replication — passive cho đến khi cần
  • Khi Primary down → Secondary chờ hết MCLT rồi bắt đầu cấp lease
  • Configurable: bao nhiêu % address pool dự trữ cho standby (mặc định 5%)
    • 5% = secondary có thể cấp 5% pool ngay lập tức, không cần chờ MCLT cho 5% này
  • Use case: central site + branch site — branch server làm standby cho central DHCP

Load Balance Mode

  • Cả 2 server đều active, chia tải theo tỉ lệ (mặc định 50/50, configurable 60/40, 70/30…)
  • Phân chia dựa trên MAC address hash — đảm bảo cùng client luôn đến cùng server
    • Hash deterministic: client A luôn đến server 1, client B luôn đến server 2
  • Nếu 1 server down → server còn lại tự nhận 100% sau khi hết MCLT
  • Use case: 2 DHCP server cùng site, cần HA + load distribution

MCLT - Maximum Client Lead Time

  • Khoảng thời gian chờ trước khi partner server nhận quyền cấp lease cho IP thuộc server kia
  • Mặc định: 1 giờ
  • Mục đích: tránh 2 server cùng cấp 1 IP trong thời gian transition (split-brain prevention)
  • Trong Load Balance: khi 1 server down, server còn lại chỉ cấp lease với duration = MCLT cho đến khi admin set Partner Down state
  • Auto State Switchover Interval — thời gian chờ trước khi tự động chuyển sang Partner Down (mặc định: disabled — cần admin can thiệp)

DHCP Relay Agent

Vấn đề

  • DHCPDISCOVER là broadcast — broadcast không đi qua router (giới hạn trong Layer 2 segment)
  • Subnet không có DHCP server → client không thể tìm server
  • Không thể đặt DHCP server trên mỗi subnet — tốn tiền, phức tạp

Giải pháp: Relay Agent (ip helper-address)

sequenceDiagram
    participant Client as "Client<br/>Subnet 10.1.1.0/24"
    participant Router as "Router / Relay Agent<br/>ip helper-address 10.0.0.5"
    participant DHCP as "DHCP Server<br/>10.0.0.5"

    Client->>Router: 1. DHCPDISCOVER<br/>Broadcast on local subnet

    Router->>Router: 2. Receives broadcast<br/>Sets GIADDR = 10.1.1.1<br/>Converts to unicast

    Router->>DHCP: 3. Forward DHCPDISCOVER<br/>Unicast to 10.0.0.5<br/>GIADDR = 10.1.1.1

    DHCP->>DHCP: 4. Based on GIADDR<br/>selects scope 10.1.1.0/24<br/>Allocates IP from that scope

    DHCP-->>Router: 5. DHCPOFFER<br/>Unicast to Relay Agent

    Router-->>Client: 6. DHCPOFFER<br/>Broadcast on client subnet

    Note over Client,DHCP: REQUEST and ACK<br/>follow same path via Relay

Trường GIADDR (Gateway IP Address):

  • Relay Agent điền IP address của interface nhận broadcast vào GIADDR
  • DHCP server đọc GIADDR → biết client thuộc subnet nào → chọn scope phù hợp
  • Nếu không có scope match GIADDR → server không thể cấp IP, ignore request
  • GIADDR là cơ chế quan trọng nhất trong multi-subnet DHCP — hiểu sai GIADDR = cấu hình sai toàn bộ

DHCPv6

DHCPv4 vs DHCPv6 — Khác biệt fundamental

IPv6 có cơ chế cấp phát địa chỉ riêng (SLAAC) không cần DHCP. DHCPv6 bổ sung, không thay thế.

Router Advertisement flags:

  • M flag (Managed Address Configuration) — bật = client dùng DHCPv6 để nhận IPv6 address
  • O flag (Other Configuration) — bật = client dùng DHCPv6 cho DNS, domain, NTP (nhưng tự tạo address qua SLAAC)
  • A flag (trên prefix) — bật = SLAAC allowed cho prefix này

DHCPv6 Stateful (M=1):

  • DHCPv6 server cấp IPv6 address, tương tự DHCPv4
  • Dùng IA_NA (Identity Association for Non-temporary Addresses)
  • Server track leases, support reservations

DHCPv6 Stateless (M=0, O=1):

  • Client tự tạo IPv6 address qua SLAAC
  • DHCPv6 chỉ cung cấp: DNS servers, domain search list, NTP, SIP servers
  • Server không track leases — chỉ cung cấp options
  • Đơn giản hơn, phổ biến trong nhiều deployments

IMPORTANT

DHCPv6 không cung cấp default gateway — gateway luôn từ Router Advertisement. Đây là khác biệt lớn nhất so với DHCPv4 mà admin IPv4 hay quên.

DHCP Policy-based Assignment

Giới thiệu (Windows Server 2012+)

  • DHCP Policies cho phép cấp khác nhau (IP range, options) dựa trên điều kiện của client
  • Điều kiện có thể dựa trên:
    • MAC address prefix — 3 bytes đầu = vendor OUI (vd: Cisco, HP, Dell)
    • Client Identifier — option 61
    • Vendor Class — option 60
    • User Class — option 77
    • FQDN — option 81
    • Relay Agent Information — option 82 (circuit ID, remote ID)

Use cases thực tế

PolicyĐiều kiệnAction
IP Phone policyVendor Class = “Cisco IP Phone”Cấp IP từ range .200-.250, option 150 = TFTP server
Laptop policyMAC prefix = Dell (00:14:22)Lease time = 4 giờ, DNS suffix = mobile.corp.local
Guest policyRelay Agent info = Guest VLANDNS = public DNS (8.8.8.8), no WINS
  • Policies evaluate theo priority order (Processing Order trong DHCP console)
  • First match wins — client match policy đầu tiên, bỏ qua phần còn lại
  • Client không match policy nào → nhận default scope settings

DHCP trong Active Directory

Authorization

  • Trong domain environment, DHCP server phải được authorized trong AD mới được phép cấp IP
    • Cơ chế bảo vệ: ngăn admin cài DHCP server tự ý gây conflict IP
  • Danh sách authorized servers lưu trong: CN=NetServices,CN=Services,CN=Configuration,DC=...
  • Khi DHCP service khởi động:
    1. Query AD để kiểm tra mình có trong danh sách authorized
    2. Nếu có → bắt đầu cấp lease bình thường
    3. Nếu không → service tự dừng cấp lease (vẫn chạy nhưng không respond DHCP requests)
  • Quyền authorize: Enterprise Admins (vì configuration partition replicate toàn forest)
    • Delegate: có thể delegate quyền authorize cho group cụ thể

Rogue Server Detection

  • DHCP server standalone (không join domain) kiểm tra khác:
    • Gửi DHCPINFORM lên mạng
    • Nếu nhận được response từ authorized server → tự disable (biết mình là rogue)
    • Nếu không có authorized server trên segment → tiếp tục hoạt động (lab/workgroup)
  • Cơ chế này không hoàn hảo — thiết bị non-Windows (Linux dhcpd, rogue devices) không tuân thủ
    • Giải pháp bổ sung: DHCP snooping trên switch (xem phần Security)

DHCP Database Maintenance

Database Engine

  • Windows DHCP dùng ESE (Extensible Storage Engine) — cùng engine như AD DS
  • Database file: %SystemRoot%\System32\dhcp\dhcp.mdb
  • Transaction logs: j50.log, j50*.log

Backup và Restore

  • Automatic backup: mặc định mỗi 60 phút, lưu vào %SystemRoot%\System32\dhcp\backup\
    • Backup đồng bộ: scope config, reservations, leases, options, policies
    • Interval configurable qua registry: BackupInterval (phút)
  • Manual backup: DHCP console → Right-click server → Backup → chọn folder
  • Restore: DHCP console → Right-click server → Restore → chọn backup folder
    • Restore sẽ overwrite database hiện tại → cẩn thận
  • Export/Import (PowerShell):
    • Export-DhcpServer -File C:\dhcp-export.xml — export toàn bộ config
    • Import-DhcpServer -File C:\dhcp-export.xml — import vào server mới

Database Compaction

  • Online compaction: tự động trong quá trình hoạt động — giải phóng space bên trong file
  • Offline compaction: dùng jetpack.exe khi database quá lớn
    • Stop DHCP service → jetpack dhcp.mdb temp.mdb → Start DHCP service
    • Hiếm khi cần trên server hiện đại — chỉ khi database > vài trăm MB

Database Integrity

  • dhcploc.exe — tool kiểm tra rogue DHCP servers trên mạng
  • Event Log: Microsoft-Windows-DHCP-Server/Operational — theo dõi leases, errors, authorization events
  • Audit logging: mặc định BẬT — ghi log vào %SystemRoot%\System32\dhcp\DhcpSrvLog-<Day>.log
    • Chứa: lease grants, releases, renewals, NAKs — crucial cho troubleshooting và audit

Tích hợp DNS Dynamic Update

Cơ chế

  • DHCP server có thể tự động cập nhật DNS thay mặt client
  • 2 loại records:
    • A record (forward lookup) — hostname → IP
    • PTR record (reverse lookup) — IP → hostname
  • Tuỳ chọn trên DHCP server:
    • Luôn update cả A và PTR
    • Chỉ update khi client yêu cầu (mặc định — option 81 FQDN)
    • Update cho clients không hỗ trợ DDNS (Windows 9x, non-Windows devices)

Secure Dynamic Update

  • DNS zone cấu hình Secure only → chỉ authenticated accounts mới được update
  • DHCP server dùng computer account của mình hoặc dedicated service account để update DNS
  • Vấn đề: nếu DHCP server tạo record → DHCP server là owner → DHCP server khác (failover partner) không có quyền update record đó
    • Đây là nguyên nhân “stale DNS records” phổ biến sau failover

DnsUpdateProxy Group

  • Giải pháp cho vấn đề ownership: thêm DHCP servers vào group DnsUpdateProxy
  • Records tạo bởi members của group này không có owner (no security) → bất kỳ authenticated user nào cũng update được
  • Rủi ro bảo mật: records không có ACL protection
  • Best practice hiện đại: cấu hình DHCP credential (dedicated service account) cho DNS update — an toàn hơn DnsUpdateProxy
    • Service account có quyền update DNS zone → cả 2 DHCP servers dùng chung account → ownership nhất quán

DHCP Starvation Attack

  • Attacker gửi hàng loạt DHCPDISCOVER với MAC address giả → chiếm hết IP pool
  • Kết quả: legitimate clients không nhận được IP → denial of service
  • Mitigation:
    • Port Security trên switch — limit số MAC address per port (vd: max 2)
    • DHCP snooping rate limiting — giới hạn DHCP packets per second per port

Rogue DHCP Server

  • Unauthorized DHCP server cấp IP/gateway sai → redirect traffic qua attacker (MitM)
  • Attacker cấp gateway = IP attacker → sniff/modify tất cả traffic
  • Mitigation:
    • DHCP Snooping trên switch — chỉ allow DHCP response từ trusted ports (uplink ports)
    • AD Authorization — Windows DHCP servers phải authorized
    • 802.1X — authenticate devices trước khi join network

DHCP Snooping (switch level)

  • Feature trên managed switches (Cisco, HP, Dell, etc.)
  • Trusted ports: uplink ports đến DHCP server — được phép gửi DHCPOFFER/DHCPACK
  • Untrusted ports: access ports — chỉ được gửi DHCPDISCOVER/DHCPREQUEST
  • Snooping xây dựng DHCP snooping binding table: MAC + IP + VLAN + Port
    • Table này dùng cho Dynamic ARP Inspection (DAI) và IP Source Guard

IPAM Integration

IPAM - IP Address Management

  • Windows Server role (từ 2012) cung cấp central management cho DHCP và DNS
  • IPAM giải quyết: “tôi có 50 scopes trên 5 DHCP servers — IP nào đã dùng, IP nào còn trống?”

Kiến trúc

  • IPAM server discover DHCP/DNS servers trong forest qua AD
  • Collect data qua WMI/WinRM (scheduled tasks, không agent-based)
  • Lưu data trong SQL Server (WID cho small, SQL Server cho production)
  • Integrate với DHCP: có thể tạo/sửa/xoá scope, reservation, policy từ IPAM console

Design decisions:

  • WiFi scope lease ngắn (4 giờ) — devices connect/disconnect thường xuyên, cần reclaim IP nhanh
  • Branch dùng relay agent — không cần DHCP server riêng tại branch, giảm quản trị
  • Voice VLAN scope riêng — option 150 (TFTP) cho IP Phone provisioning
  • HQ dùng Load Balance failover — 2 servers cùng active, chia tải 50/50
  • Branch-B dùng Hot Standby — HQ primary, DC-HQ-02 standby cho branch

Câu hỏi thường gặp

Q: Lease duration nên đặt bao lâu?
A: Phụ thuộc tính chất mạng. Office desktop = 8 ngày (ổn định). WiFi/Guest = 4-8 giờ (nhiều devices tạm thời). VPN = 1-2 giờ (disconnect thường xuyên). Rule of thumb: lease ≥ 2x thời gian typical connection.

Q: DHCP failover có thể 3 servers không?
A: Không — Windows DHCP failover chỉ hỗ trợ 2 servers per scope. Muốn N+1 → dùng DHCP clustering (Windows Failover Cluster) nhưng chỉ active-passive.

Q: Client xin IP cũ khi reboot — server có cấp lại không?
A: Nếu lease chưa hết VÀ IP chưa bị cấp cho device khác → server cấp lại cùng IP (DHCPACK). Nếu IP đã thuộc device khác → DHCPNAK → client bắt đầu DORA mới.

Q: Split scope 80/20 có còn dùng không?
A: Từ Windows Server 2012, DHCP Failover thay thế hoàn toàn split scope. Split scope không replicate leases → client có thể nhận duplicate IP trong edge case. Failover replicate leases → an toàn hơn.

Q: Reservation có tốn lease từ pool không?
A: IP trong reservation vẫn tính trong pool — nhưng nó reserved cho MAC cụ thể. Nếu device không online, IP đó idle chứ không cấp cho device khác.

Lưu ý quan trọng

CAUTION

Scope exhaustion — khi hết IP trong scope → client không nhận được lease → mất kết nối mạng. Monitor DHCP scope utilization, alert khi >80%. Dùng IPAM hoặc SCOM monitoring.

  • Lease duration tuning:
    • Mạng ổn định (office): lease dài (8 ngày) giảm DHCP traffic
    • Mạng nhiều thiết bị tạm thời (Wi-Fi guest): lease ngắn (4-8 giờ) reclaim IP nhanh
    • VPN: lease rất ngắn (1-2 giờ) tránh giữ IP khi disconnect
  • Failover ≠ clustering — DHCP failover chỉ hoạt động giữa 2 server (không phải N+1)
  • Split scope (legacy HA trước Windows 2012) — chia 80/20 giữa 2 server, không replicate lease. Failover mode thay thế hoàn toàn approach này
  • PXE boot — DHCP options 066/067 hoặc option 060 (PXEClient) cần cấu hình đúng để WDS/SCCM/MDT deployment hoạt động
  • Conflict detection — DHCP server có thể ping IP trước khi cấp (mặc định tắt, bật = thêm latency nhưng an toàn hơn). Client Windows cũng tự ARP check sau khi nhận lease
  • Backup regularly — test restore process ít nhất 1 lần/năm. DHCP database corrupt = toàn bộ network outage
