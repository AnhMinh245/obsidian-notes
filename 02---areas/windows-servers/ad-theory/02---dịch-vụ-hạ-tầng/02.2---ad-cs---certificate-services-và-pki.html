AD CS - Certificate Services và PKI

Tóm tắt nhanh

  • PKI (Public Key Infrastructure) là hệ thống quản lý digital certificates — nền tảng cho mã hoá, xác thực, và chữ ký số trong môi trường enterprise
  • AD CS là implementation của PKI trong Windows Server — tích hợp sâu với Active Directory qua Enterprise CA, hỗ trợ auto-enrollment và certificate templates
  • Kiến trúc PKI khuyến nghị: 2-tier — Root CA offline (bảo vệ private key) + Issuing CA online (phục vụ enrollment)
  • Revocation checking qua CRL (danh sách thu hồi) hoặc OCSP (kiểm tra realtime) đảm bảo certificate bị revoke không còn được tin tưởng
  • AD CS attack surface là mối quan tâm bảo mật lớn — ESC1-ESC8 vulnerabilities cần được awareness và mitigation

Digital Certificate - X.509

Certificate là một tài liệu số ràng buộc public key với identity, được ký bởi CA đáng tin cậy. Giống như CMND/CCCD — cơ quan nhà nước (CA) xác nhận danh tính bạn (public key + identity) bằng con dấu (digital signature).

    • Mỗi cert trong chain được verify bằng public key của cert ở tầng trên
    • Tương tự: bạn tin công ty A vì công ty A được uỷ quyền bởi bộ B, mà bộ B được chính phủ cấp phép (Root)

  • Enterprise CA tự động publish Root CA cert vào AD → tất cả domain members tự tin tưởng
    • Non-domain machines phải cài Root CA cert thủ công hoặc qua GPO preferences

CA Hierarchy

Single-tier (không khuyến nghị cho production)

  • 1 CA vừa là Root vừa là Issuing
  • Root CA luôn online → private key của Root CA luôn bị expose trên server đang chạy
  • Nếu Root CA bị compromise → toàn bộ PKI phải xây lại từ đầu — tất cả certificates đã issue trở thành untrusted
  • Chỉ phù hợp: lab, test, hoặc tổ chức rất nhỏ (<50 users) không có yêu cầu compliance

  • Root CA: Standalone CA, cài trên máy không join domain, tắt máy sau khi ký Issuing CA cert
    • Chỉ bật lên khi: ký cert cho Issuing CA mới, renew Issuing CA cert, publish CRL mới
    • CRL validity dài (6-12 tháng) vì Root CA offline — phải bật máy publish CRL trước khi CRL hiện tại hết hạn
    • Private key nên lưu trên HSM (Hardware Security Module) nếu có budget
    • Lưu offline trên USB encrypted hoặc smart card nếu không có HSM
  • Issuing CA: Enterprise CA, join domain, phục vụ enrollment hàng ngày
    • AD-integrated: tự publish cert vào AD, hỗ trợ auto-enrollment
    • CRL validity ngắn hơn (1-7 ngày) + Delta CRL (vài giờ)
    • Có thể có nhiều Issuing CA cho các mục đích khác nhau (1 cho internal, 1 cho DMZ)

Three-tier

  • Thêm Policy CA giữa Root và Issuing
  • Policy CA định nghĩa certificate policies, cross-certification giữa các PKI hierarchy
  • Dùng trong tổ chức lớn hoặc khi cần cross-trust giữa nhiều PKI (vd: sáp nhập công ty)
  • Hiếm gặp trong thực tế — 2-tier đủ cho hầu hết enterprise

Enterprise CA chi tiết

  • Tích hợp AD:
    • Publish certificates và CRL vào AD (LDAP paths)
    • Đọc certificate templates từ AD Configuration partition
    • Hỗ trợ auto-enrollment qua Group Policy
    • Kerberos authentication cho enrollment — single sign-on
  • Dùng certificate templates để kiểm soát loại cert được issue
  • Tự động populate Subject dựa trên AD attributes (sAMAccountName, UPN, dNSHostName)
  • CA certificate publish vào: CN=Certification Authorities,CN=Public Key Services,CN=Services,CN=Configuration,DC=...

Permissions trên Template (Security)

Template permissions quyết định ai được phép request certificate — đây là điểm quan trọng cho cả operations và security:

PermissionMô tảAi nên có
ReadThấy template trong enrollment UIAuthenticated Users (mặc định)

WARNING

Autoenroll + Enroll permission phải cùng grant cho 1 subject thì auto-enrollment mới hoạt động. Chỉ có Autoenroll mà thiếu Enroll → auto-enrollment fail âm thầm.

Key Usage và EKU

  • Key Usage — mục đích cryptographic cơ bản:
    • Digital Signature — ký data (authentication, code signing)
    • Key Encipherment — mã hoá symmetric key (RSA key exchange trong TLS)
    • Key Agreement — thoả thuận key (Diffie-Hellman, ECDH)
    • Non-Repudiation — chữ ký pháp lý, không thể chối bỏ
  • Enhanced Key Usage (EKU) — application-specific:
    • Server Authentication (1.3.6.1.5.5.7.3.1) — HTTPS, RDP, LDAPS
    • Client Authentication (1.3.6.1.5.5.7.3.2) — smart card logon, 802.1X, VPN
    • Code Signing (1.3.6.1.5.5.7.3.3) — ký software, scripts, drivers
    • Smart Card Logon (1.3.6.1.4.1.311.20.2.2) — Windows smart card authentication
    • KDC Authentication (1.3.6.1.5.2.3.5) — Domain Controller Kerberos
    • OCSP Signing (1.3.6.1.5.5.7.3.9) — OCSP responder
    • Email Protection (1.3.6.1.5.5.7.3.4) — S/MIME email encryption/signing

Certificate-based Authentication

Smart Card Logon

  • User insert smart card (chứa private key + certificate) thay vì nhập password
  • Quy trình: Smart card provider → Kerberos PKINIT → KDC verify certificate + issue TGT
  • Yêu cầu:
    • DC certificate với KDC Authentication EKU (template: Domain Controller Authentication)
    • User certificate với Smart Card Logon EKU
    • Root CA trusted bởi cả client và DC
    • CRL accessible tại thời điểm logon — nếu CRL check fail → logon fail
  • Use case: high-security environments, government, financial — thay thế password hoàn toàn

EAP-TLS (802.1X)

  • Certificate-based authentication cho network access control
  • Client present certificate → RADIUS server (NPS) verify → grant/deny network access
  • Dùng cho: wired 802.1X, wireless WPA2/WPA3-Enterprise, VPN
  • Yêu cầu:
    • Computer certificate trên client (auto-enrolled)
    • Server certificate trên NPS/RADIUS server
    • Trusted Root CA trên cả 2 phía

Code Signing

  • Ký digital signature lên executables, scripts, drivers, packages
  • Windows verify signature → xác nhận: (1) code chưa bị tamper, (2) biết ai ký
  • Use case:
    • PowerShell execution policy: AllSigned yêu cầu tất cả scripts phải được ký
    • Device driver signing: Windows 10/11 yêu cầu driver signed
    • Application deployment: SCCM/Intune verify signature trước khi install
  • Code Signing certificate nên có hardware-protected private key (HSM, smart card)

Enrollment Methods

Auto-enrollment qua GPO

  • GPO setting: Computer/User Configuration → Policies → Windows Settings → Security Settings → Public Key Policies → Certificate Services Client - Auto-Enrollment
  • Trigger: Group Policy refresh cycle (mỗi ~90 phút) hoặc user logon / computer startup
  • Client kiểm tra: template nào mình có quyền Autoenroll + cert hiện tại còn hạn không + cert đã bị supersede chưa
  • Renewal: auto-enrollment cũng tự renew cert khi còn lại 10% validity period (mặc định, configurable trên template)
    • Ví dụ: cert 2 năm → auto-renew khi còn ~73 ngày
  • Supersede: template mới thay thế template cũ → client tự request cert từ template mới, retire cert cũ

Manual Enrollment

  • MMC — certlm.msc (Local Machine) hoặc certmgr.msc (Current User) → Request New Certificate
  • Web Enrollment — https://<CA>/certsrv — CES/CEP web interface (legacy nhưng vẫn dùng cho non-domain devices)
  • certreq.exe — command-line tool, dùng INF file để define request
    • Workflow: certreq -new request.inf request.req → submit → certreq -accept cert.cer
  • PowerShell: Get-Certificate -Template <TemplateName> -CertStoreLocation Cert:\LocalMachine\My

NDES - Network Device Enrollment Service

  • Implementation của SCEP (Simple Certificate Enrollment Protocol) trên Windows
  • Dùng cho thiết bị không join domain: network switches, routers, firewalls, mobile devices (MDM)
  • NDES đứng giữa device và CA — nhận SCEP request, chuyển thành standard CA enrollment
  • Dùng one-time password (challenge password) để authenticate device — mỗi password dùng 1 lần
  • Mỗi NDES server có 2 RA (Registration Authority) certificates: Encryption + Signing
  • Tích hợp phổ biến: Microsoft Intune dùng NDES/SCEP để deploy certificates đến mobile devices

CEP/CES - Certificate Enrollment Policy/Service

  • CEP (Certificate Enrollment Policy Web Service) — cung cấp template information qua HTTPS
  • CES (Certificate Enrollment Web Service) — xử lý enrollment requests qua HTTPS
  • Dùng cho: enrollment qua internet, cross-forest enrollment, devices không direct LDAP access đến AD
  • Thay thế dần web enrollment (certsrv) cũ

Revocation

CRL - Certificate Revocation List

  • Base CRL — danh sách đầy đủ serial numbers của tất cả cert đã bị revoke
    • Publish định kỳ (thường 1 tuần cho Root CA, 1 ngày cho Issuing CA)
    • File size tăng dần theo thời gian — sau vài năm có thể nhiều MB
    • Client cache CRL cho đến khi hết validity (Next Update field)
  • Delta CRL — chỉ chứa cert bị revoke kể từ Base CRL gần nhất
    • Publish thường xuyên hơn (vài giờ)
    • File size nhỏ → download nhanh hơn
    • Client kết hợp Base CRL + Delta CRL mới nhất
    • Chỉ hỗ trợ từ CRL version 2 (V2)

OCSP - Online Certificate Status Protocol

  • Realtime verification — client hỏi OCSP responder: “cert serial X còn valid không?”
  • OCSP responder trả lời: Good, Revoked, hoặc Unknown
  • Windows Server có role Online Responder — cài riêng hoặc cùng CA server

OCSP Stapling:

  • Server tự query OCSP responder, cache response, gửi kèm trong TLS handshake
  • Client không cần contact OCSP responder riêng → nhanh hơn, privacy tốt hơn
  • Hỗ trợ trong IIS, Nginx, Apache

CDP và AIA

  • CDP (CRL Distribution Points) — URL trong certificate chỉ client nơi tải CRL
    • Thường có nhiều URL theo thứ tự ưu tiên: ldap:/// (AD), http:// (web), file:// (share)
    • Client thử từng URL cho đến khi tải được — thứ tự quan trọng cho performance
    • Best practice: http:// URL đầu tiên (nhanh nhất, accessible from everywhere), ldap:// sau
  • AIA (Authority Information Access) — URL để:
    • Tải CA certificate (cho chain building): http://pki.corp.local/AIA/IssuingCA.crt
    • Truy cập OCSP responder: http://ocsp.corp.local/ocsp
  • CDP/AIA phải accessible từ tất cả client — kể cả client ngoài domain (DMZ, internet)
    • Best practice: luôn có ít nhất 1 HTTP URL public
    • Không dùng ldap:// cho external clients (firewall chặn LDAP)

Key Archival và Recovery

Mục đích

  • Khi user mất private key (máy hỏng, profile corrupt) → không đọc được data đã encrypt
    • Email đã encrypt bằng S/MIME
    • File encrypt bằng EFS (Encrypting File System)
  • Key archival cho phép CA lưu bản sao private key → admin có thể recover khi cần

  • KRA (Key Recovery Agent) — certificate đặc biệt cho phép decrypt archived keys
    • KRA certificate template: Key Recovery Agent
    • Chỉ cấp cho admin được uỷ quyền (thường 2-3 người, require approval)
  • CA encrypt user private key bằng KRA public key trước khi lưu vào database
  • Recovery: dùng certutil -recoverkey hoặc CA MMC → retrieve archived key

Best Practices

  • CHỈ archive encryption keys (EFS, S/MIME) — KHÔNG archive signing keys
    • Signing key bị compromise → attacker ký giả mạo → không thể chứng minh non-repudiation
  • Yêu cầu ít nhất 2 KRA cho redundancy
  • Test recovery process định kỳ — đừng đợi emergency mới test
  • KRA private keys nên lưu trên HSM hoặc smart card

KSP vs CSP

CSP - Cryptographic Service Provider (Legacy)

  • Kiến trúc crypto cũ của Windows (từ Windows NT)
  • Dùng CryptoAPI (CAPI) — API crypto đầu tiên của Microsoft
  • Provider phổ biến: Microsoft RSA SChannel Cryptographic Provider, Microsoft Enhanced Cryptographic Provider
  • Giới hạn: chỉ hỗ trợ RSA, không hỗ trợ ECC, Suite B, hoặc CNG algorithms

KSP - Key Storage Provider (Modern)

  • Kiến trúc crypto mới, dùng CNG (Cryptography Next Generation) — từ Windows Vista/2008
  • Hỗ trợ: RSA, ECC (P-256, P-384, P-521), Suite B algorithms
  • Provider phổ biến:
    • Microsoft Software Key Storage Provider — software-based, mặc định
    • Microsoft Platform Crypto Provider — dùng TPM chip trên hardware
    • Microsoft Smart Card Key Storage Provider — smart card
  • Luôn ưu tiên KSP cho certificate templates mới (V3, V4)

  • Internal PKI: internal servers, DC certificates, smart card, 802.1X, internal web apps, EFS, S/MIME internal

  • Kết hợp: dùng cả hai — internal PKI cho nội bộ, public CA cho đối ngoại

AD CS Attack Surface Awareness

Tổng quan ESC1-ESC8

AD CS misconfigurations là vector tấn công phổ biến. Các lỗ hổng được phân loại ESC1 đến ESC8 (và expanding):

ESCTênMô tả tóm tắtSeverity

ESC2Misconfigured Templates - Any PurposeTemplate có Any Purpose hoặc SubCA EKU → dùng cho bất kỳ mục đíchHigh
ESC3Enrollment Agent TemplatesTemplate cho phép enroll on behalf of othersHigh
ESC4Vulnerable Template ACLTemplate permissions cho phép low-privilege user sửa templateHigh

Mitigation cơ bản

IMPORTANT

Không phải tất cả misconfigurations đều là vulnerability — chúng trở thành vulnerability khi combined với attacker access. Defense-in-depth là key.

  • ESC1: Review tất cả templates — disable ENROLLEE_SUPPLIES_SUBJECT flag trên templates có Client Auth EKU. Chỉ enable cho templates thực sự cần (vd: Web Server)
  • ESC6: Disable EDITF_ATTRIBUTESUBJECTALTNAME2 trên CA: certutil -config "CA\Name" -setreg policy\EditFlags -EDITF_ATTRIBUTESUBJECTALTNAME2
  • ESC8: Enforce HTTPS cho enrollment endpoints, enable Extended Protection for Authentication
  • General: Audit template permissions định kỳ, limit Enroll permission chỉ cho groups cần thiết

Công cụ audit:

  • Certify (GhostPack) — scan AD CS misconfigurations
  • Certipy (Python) — alternative tool cho AD CS auditing
  • PSPKIAudit (PowerShell) — Microsoft-friendly option

Câu hỏi thường gặp

Q: Có cần AD CS nếu đã dùng public CA (Let’s Encrypt, DigiCert)?
A: Có, nếu cần auto-enrollment cho domain computers, smart card logon, 802.1X, EFS, hoặc bất kỳ certificate nào yêu cầu AD integration. Public CA không thể auto-enroll qua GPO hay tạo custom templates.

Q: Root CA nên để online hay offline?
A: Offline luôn trong production. Root CA chỉ cần bật để ký Issuing CA cert và publish CRL. Online Root CA = single point of catastrophic failure cho toàn bộ PKI.

Q: CRL hết hạn thì sao?
A: Client không validate được certificate → connection fail → outage. Nếu Root CA CRL hết hạn → LDAPS, smart card logon, RD Gateway — tất cả fail. Đây là outage phổ biến thứ 2 (sau cert expiry) trong PKI operations.

Q: Certificate template V1 có cần upgrade lên V4 không?
A: Không bắt buộc nhưng khuyến nghị cho templates mới. V1 không hỗ trợ auto-enrollment, V2+ thì có. Nếu cần ECC/CNG → phải V3+. Không modify V1 trực tiếp — duplicate rồi sửa bản copy.

Q: NDES có an toàn không?
A: NDES dùng one-time passwords nhưng password management có thể weak nếu không cấu hình đúng. Luôn dùng HTTPS, limit challenge password lifetime, monitor enrollment logs.

Lưu ý quan trọng

CAUTION

Root CA private key là tài sản quan trọng nhất trong PKI — nếu bị compromise, toàn bộ PKI mất tin cậy và phải rebuild từ đầu. Giữ Root CA offline và lưu private key trên HSM nếu có thể.

  • CRL expiry — nếu CRL hết hạn và client không tải được CRL mới → certificate validation fail → service outage. Monitor CRL validity, set calendar reminder trước khi CRL expiry
  • Certificate template permissions — cấu hình sai template permissions là vector tấn công phổ biến (ESC1-ESC8)
    • Đặc biệt nguy hiểm: template cho phép user specify Subject Alternative Name + có EKU Client Authentication → impersonation attack
    • Review template permissions quarterly
  • Key archival — enable cho encryption certificates (Email, EFS) để recover khi user mất private key. Không archive signing key — violate non-repudiation principle
  • CA backup — backup CA database + private key định kỳ. Mất CA database = mất khả năng revoke cert đã issue
    • certutil -backup <BackupFolder> hoặc Backup-CARoleService PowerShell
  • Cert chaining errors — lỗi phổ biến: client không có Issuing CA cert trong Intermediate CA store → chain không build được. Enterprise CA tự publish vào AD, nhưng non-domain machines cần cài thủ công
  • CA certificate renewal — plan trước! Issuing CA cert expiry = CA ngừng issue cert. Renew ít nhất 6 tháng trước expiry
