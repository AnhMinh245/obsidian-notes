AD 2025 - Kiểm thử toàn diện

Tóm tắt nhanh

  • Kiểm thử chia 4 phase tương ứng 4 giai đoạn migration — mỗi phase có go/no-go gate trước khi tiếp tục
  • Mỗi test item có Expected Result cụ thể — pass/fail rõ ràng, không “có vẻ ổn”
  • Rollback criteria định nghĩa trước: severity level quyết định rollback hay fix-forward
  • Triết lý: “Validate everything before decommissioning anything” — không tắt DC cũ cho đến khi 100% confident
  • Tổng cộng 80+ test items cover mọi thành phần: AD DS, DNS, FSMO, CA, DHCP, RDS

Automated Testing Concepts

Tại sao cần tự động hoá test

  • 80+ test items → test thủ công mất nhiều thời gian và dễ sai
  • Cần chạy lại nhiều lần: sau mỗi phase, sau mỗi fix, sau rollback
  • Consistency: script cho cùng kết quả mỗi lần chạy, không phụ thuộc người test

Logic cho test script (không phải script thật — chỉ là concept)

flowchart TD
    START["Test Runner<br/>Input: Phase number"] --> LOAD["Load test cases<br/>for Phase N"]
    LOAD --> LOOP{"More test cases?"}
    LOOP -->|Yes| RUN["Run test case"]
    RUN --> CHECK{"Pass?"}
    CHECK -->|Pass| LOG_PASS["Log: PASS<br/>+ timestamp + output"]
    CHECK -->|Fail| LOG_FAIL["Log: FAIL<br/>+ timestamp + error"]
    LOG_PASS --> LOOP
    LOG_FAIL --> SEV{"Severity?"}
    SEV -->|Critical| STOP["STOP: Critical failure<br/>Alert admin immediately"]
    SEV -->|Major/Minor| LOOP
    LOOP -->|Done| REPORT["Generate Report<br/>Summary: Pass/Fail count<br/>Recommendation: Go/No-Go"]

User Acceptance Testing (UAT) Process

Tại sao cần UAT

  • IT team test ≠ user experience — IT test từ server side, user test từ workstation thực tế
  • User phát hiện issue mà IT không lường trước: app behavior, performance, workflow
  • UAT tạo user confidence — user biết hệ thống mới đã được test và hoạt động

Định nghĩa mức độ nghiêm trọng

SeverityĐịnh nghĩaVí dụHành động
CriticalService-down, ảnh hưởng toàn bộ hoặc đa số userReplication failure toàn bộ, CA không issue cert, DHCP không cấp IP, tất cả user không logonRollback ngay lập tức
MajorẢnh hưởng một phần user hoặc function1 site không auth được, 1 app bị lỗi delegation, DNS resolve chậmRollback nếu không fix trong 4h

CosmeticKhông ảnh hưởng operationWarning trong event log (non-critical), naming convention issueLog, fix khi rảnh

  • Là fallback cuối cùng nếu có issue bất ngờ
  • Chỉ decommission khi tất cả DC khác đã decommission thành công

Quy trình kiểm thử tổng thể

Trước mỗi test phase

  1. Backup trạng thái hiện tại (System State backup trên DC)
  2. Document baseline: ghi lại trạng thái “trước test” để so sánh — performance, event log
  3. Notify stakeholder: thông báo đang test, có thể ảnh hưởng service
  4. Prepare rollback: xác nhận rollback plan khả thi — DC cũ online, FSMO transferable
  5. Schedule: thực hiện test ngoài giờ cao điểm nếu có thể

Trong khi test

  1. Thực hiện từng test item theo thứ tự (dependency chain)
  2. Ghi kết quả Pass/Fail + Notes chi tiết + timestamp
  3. Nếu fail Critical: STOP — đánh giá severity, quyết định fix (1h window) hay rollback
  4. Nếu fail Major: document, attempt fix, continue testing các item khác
  5. Không skip test item — mọi item đều có lý do tồn tại

Sau mỗi test phase

  1. Tổng hợp kết quả: Pass count, Fail count, severity breakdown
  2. Generate report theo template (xem Test Report Template ở trên)
  3. Go/No-Go decision: IT management review kết quả, quyết định proceed hay rollback
  4. Sign-off: document approval bằng email/document trước khi sang phase tiếp
  5. Bảo lưu kết quả test, report, sign-off → lưu vào project documentation

Lưu ý quan trọng

  • Test từ perspective user thật — không chỉ test từ DC/server. Logon từ workstation ở mỗi site, dùng app thực tế
  • Test ngoài giờ cao điểm — giảm thiểu ảnh hưởng nếu phát hiện issue
  • Giữ DC cũ online trong suốt quá trình test — rollback cần DC cũ healthy
  • Event Log là nguồn thông tin quý — check Application, System, Directory Service, DNS Server, DFS Replication log trên mỗi DC
  • Không decommission DC cũ ngay sau khi pass — giữ thêm ít nhất 2 tuần (4 tuần càng tốt) để phát hiện issue phát sinh chậm (CRL cycle, weekly batch job, monthly report)
  • Automate test càng nhiều càng tốt — script test replication, DNS, DHCP chạy lại nhanh hơn, consistent hơn
  • FFL raise là bước cuối cùng — chỉ raise sau khi tất cả DC cũ đã decommission VÀ monitoring period pass
