AD 2025 - Chuyển đổi ứng dụng và DNS

Tóm tắt nhanh

  • Application migration yêu cầu audit dependency kỹ lưỡng — xác định ứng dụng nào kết nối AD qua LDAP, Kerberos, hay NTLM
  • SPN và Kerberos Delegation theo service account, không theo DC — migration DC thường không ảnh hưởng nếu app dùng domain FQDN
  • DNS cutover ưu tiên qua DHCP option 006 cho DHCP client, GPO cho static client
  • Nguyên tắc vàng: ứng dụng nên dùng domain FQDN (ldap://domain.local) thay vì hardcode tên DC cụ thể
  • LDAP signing và channel binding mặc định stricter trên Server 2025 — audit app compatibility là critical

Application Migration — Chuyển đổi ứng dụng

Tại sao Application Audit là bước quan trọng nhất

Analogie: DC migration giống như đổi tổng đài điện thoại — nếu mọi người gọi bằng số nội bộ (domain FQDN) → tổng đài mới tự chuyển đúng. Nhưng nếu ai đó ghi số đường dây trực tiếp (hardcode DC name) vào sổ → khi đổi tổng đài, cuộc gọi sẽ fail.

Audit trước migration để tìm “số đường dây trực tiếp” đó và sửa trước.

Các loại kết nối AD chi tiết

LDAP Bind

  • Domain FQDN (best practice): LDAP://domain.local → DNS SRV record tự trỏ về DC khả dụng. Khi DC cũ offline, DNS tự loại bỏ SRV record → client tự tìm DC mới
  • Hardcoded DC name: LDAP://DC-OLD-01.domain.local:389 → phải đổi sang domain FQDN hoặc DC mới. Đây là pattern phổ biến nhất gây issue khi migration
  • IP address: LDAP://10.1.1.5:389 → phải đổi — tệ nhất, không fallback, không load balance
  • LDAP over SSL (LDAPS port 636): kiểm tra certificate trên DC mới đã có — DC mới cần certificate để serve LDAPS
  • Serverless bind: app dùng ADSI/System.DirectoryServices mà không chỉ định server → AD SDK tự locate DC qua DNS → an toàn

LDAP Referral: khi DC nhận query mà object nằm ở domain khác, DC trả về referral → client tự theo referral. Trong single-domain forest, referral ít xảy ra.

LDAP Query Compatibility giữa 2012R2 và 2025

Server 2025 có thay đổi LDAP behavior cần lưu ý:

Thay đổi2012R2 Default2025 DefaultImpact
LDAP SigningNot requiredRequiredApp dùng simple bind không sign → bị reject
LDAP Channel BindingNot requiredRequiredApp không support channel binding → fail
LDAP authenticationAllow unsignedRequire signingLegacy app có thể bị ảnh hưởng
MaxPageSize10001000Không thay đổi
MaxValRange15001500Không thay đổi

Cách audit LDAP compatibility trước migration:

  1. Enable LDAP signing audit trên DC 2012R2: GPO → Network security: LDAP client signing requirements = Require signing (trong audit mode trước)
  2. Monitor Event Log: Event ID 2889 trong Directory Service log → liệt kê client nào dùng unsigned LDAP bind
  3. Fix: cập nhật app để dùng LDAP signing, hoặc upgrade LDAP client library
  4. Nếu không fix được: có thể tạm disable LDAP signing requirement trên DC 2025 qua GPO — nhưng đây là security risk

Kerberos Authentication

  • Kerberos dùng SPN (Service Principal Name) để identify service — client request TGS ticket cho SPN từ KDC (DC)
  • Khi DC thay đổi, Kerberos không bị ảnh hưởng nếu:
    • App dùng domain FQDN (KDC lookup qua DNS SRV record)
    • Service account không đổi (SPN register trên service account)
    • SPN vẫn registered đúng (không duplicate, không missing)

Kerberos Armoring (FAST)

Flexible Authentication Secure Tunneling (FAST) — hay gọi là Kerberos Armoring:

  • Chức năng: bảo vệ Kerberos pre-authentication exchange khỏi offline dictionary attack
  • Server 2025: có thể enforce FAST mặc định hoặc qua policy
  • Impact khi migration: nếu DC 2025 enforce FAST mà client/app chưa support → authentication fail
  • Mitigation: test FAST support trên client và app trước khi enable; deploy FAST từ từ qua GPO

Claims-Based Authentication

Server 2012+ giới thiệu Dynamic Access Control với claims-based authorization:

  • Claims = attribute từ AD user/device được nhúng vào Kerberos ticket
  • Impact khi migration: nếu đang dùng claims → verify claims policy replicate đúng sang DC 2025
  • Compound authentication: kết hợp user claim + device claim → verify device join đúng domain

Trong dự án này: nếu chưa dùng claims → không cần lo. Nếu đang dùng → test kỹ trên DC 2025 trước khi decommission DC cũ.

NTLM Fallback

  • NTLM là fallback khi Kerberos fail (thường do SPN issue, network, hoặc app không support Kerberos)
  • NTLM xác thực qua Netlogon secure channel đến DC — với DC mới, Netlogon channel tự thiết lập → NTLM vẫn hoạt động
  • Lưu ý quan trọng: Server 2025 có NTLM restriction policies mạnh hơn:
    • Có thể audit/block NTLM authentication
    • Legacy app dùng NTLM exclusively có thể bị ảnh hưởng
    • Audit trước: enable NTLM auditing GPO → monitor Event ID 4624 với LogonType NTLM → xác định app nào dùng NTLM

SPN (Service Principal Name) Considerations

SPN là “địa chỉ” của service trong Kerberos. Ví dụ:

SPN PatternÝ nghĩaRegistered trên
HTTP/webserver.domain.localWeb service trên webserverService account hoặc computer account
MSSQLSvc/sqlserver.domain.local:1433SQL Server instanceSQL service account
HOST/dc01.domain.localDC computer account servicesDC computer account (auto)
ldap/dc01.domain.localLDAP service trên DCDC computer account (auto)
DNS/dc01.domain.localDNS service trên DCDC computer account (auto)

Khi migration DC:

  • SPN trên DC computer account (HOST/, ldap/, DNS/, GC/) → DC mới tự register khi promote — không cần action thủ công
  • SPN trên service account (SQL, Exchange, custom app) → không đổi vì SPN theo account, không theo DC
  • Duplicate SPN là lỗi phổ biến nhất: setspn -X để detect duplicate trước VÀ sau migration

Kerberos Delegation chi tiết

Delegation cho phép service impersonate user để truy cập service khác (multi-tier application). Ví dụ: Web App → impersonate user → query SQL Server.

So sánh 3 loại Delegation:

LoạiCách cấu hìnhScopeRủi roRecommendation
UnconstrainedCheckbox “Trust this computer for delegation to any service”Delegate đến bất kỳ serviceCao — service có TGT, có thể impersonate đến mọi nơiTránh dùng — legacy
Constrained (KCD)msDS-AllowedToDelegateTo attributeDelegate đến danh sách SPN cụ thểTrung bìnhPhổ biến, acceptable
Resource-Based (RBCD)msDS-AllowedToActOnBehalfOfOtherIdentity trên resourceResource tự quyết định ai được delegateThấpKhuyến nghị — Server 2012+

Tác động đến migration:

  • Unconstrained Delegation: cấu hình trên computer/service account → nếu account không đổi → không cần thay đổi
  • KCD: msDS-AllowedToDelegateTo chứa SPN list → chỉ cần update nếu SPN đích chứa tên DC cũ (ví dụ ldap/DC-OLD-01.domain.local)
  • RBCD: cấu hình trên resource (target), theo account identity → không cần thay đổi khi DC migration

SQL Server Always On AG với AD Dependency

Nếu có SQL Server Always On Availability Group:

  • Listener SPN: AG Listener có SPN riêng → verify SPN registered đúng sau migration
  • Kerberos Authentication: AG Listener dùng Kerberos → SPN phải trên đúng service account
  • AD dependency: AG rely on AD cho authentication → DC mới phải healthy trước khi test AG failover
  • Computer account: AG VNN (Virtual Network Name) có computer account trong AD → verify account intact

DNS Migration

AD-Integrated DNS Zone Replication

Khi DC 2025 được promote với DNS role, DNS data tự replicate:

  • Forward Lookup Zone tự replicate qua AD replication — mọi record (A, CNAME, MX, TXT, SRV)
  • Reverse Lookup Zone tự replicate (nếu AD-integrated, không phải file-based legacy zone)
  • Replication partition:
    • DomainDnsZones — replicate đến tất cả DC có DNS role trong domain
    • ForestDnsZones — replicate đến tất cả DC có DNS role trong forest

→ Không cần “migrate” DNS data thủ công — AD replication lo phần này. Chỉ cần verify data đồng bộ đúng.

Split-Brain DNS Handling

Split-brain DNS = cùng zone name nhưng resolve khác nhau tùy client location (internal vs external).

ScenarioInternal DNS (AD-integrated)External DNS (public)Impact khi migration
domain.comResolve về internal server IPResolve về public IPAD DNS migration chỉ ảnh hưởng internal — verify external DNS không bị động
AutodiscoverInternal CA certPublic CA certVerify cả 2 path sau migration

Khi migration: chỉ thay đổi internal AD-integrated DNS — external DNS không bị ảnh hưởng. Nhưng cần verify rằng changes không leak ra external.

DNS Scavenging

  • Scavenging tự động xoá DNS record quá hạn (stale) — quan trọng để giữ DNS sạch sau migration
  • Cần cấu hình trên DC 2025 mới:
    • Server-level: enable scavenging trên DC
    • Zone-level: enable aging trên zone
    • Timing: No-refresh interval (7 ngày) + Refresh interval (7 ngày) = record stale sau 14 ngày
  • Chỉ enable scavenging trên 1-2 DC — tránh race condition xoá record (nhiều DC scavenge cùng lúc có thể xoá record valid)
  • Sau migration: scavenging sẽ tự cleanup record của DC cũ sau 14 ngày (nếu DC cũ đã offline)

Câu hỏi thường gặp

Q: App hardcode DC name nhưng không có source code (vendor app) — làm thế nào?

A: Nhiều options:

  1. Config file: tìm connection string trong config file (web.config, app.config, .ini, .properties) → đổi
  2. DNS CNAME workaround: tạo CNAME record trỏ tên DC cũ về DC mới → app vẫn resolve được. Tạm thời nhưng effective
  3. Liên hệ vendor: hỏi vendor cách cập nhật DC connection — vendor app thường có admin guide
  4. Registry: một số app lưu DC name trong registry → tìm bằng reg query hoặc Process Monitor

Q: LDAP signing requirement trên 2025 có bắt buộc không? Có thể tắt không?

A: Server 2025 mặc định require LDAP signing. Có thể tạm disable qua GPO (Network security: LDAP client signing requirements = None), nhưng:

  • Đây là security risk — unsigned LDAP cho phép man-in-the-middle attack
  • Microsoft khuyến nghị fix app thay vì disable requirement
  • Plan: enable audit mode → identify non-compliant apps → fix → enforce

Q: DNS cutover có gây downtime không?

A: Không, nếu làm đúng:

  • DNS zone data đã replicate sẵn trên DC 2025 (AD-integrated) → DC 2025 có đầy đủ DNS records
  • Client chuyển DNS server (qua DHCP renew) → query DNS mới → resolve đúng ngay
  • Parallel run: DNS cũ vẫn hoạt động trong khi client chuyển dần → zero downtime

Lưu ý quan trọng

  • Audit ứng dụng TRƯỚC khi chuyển đổi — đừng decommission DC cũ rồi mới phát hiện app hardcode tên DC → fix reactive rất costly
  • LDAP signing và channel binding có thể strict hơn trên Server 2025 — bắt buộc audit trước, enable audit mode trên DC hiện tại
  • DNS cutover nên rollout theo site — ROOT trước, sau đó MB, MN, TW. Không đổi tất cả cùng lúc
  • Giữ DNS trên DC cũ hoạt động trong parallel run — client chưa cập nhật vẫn resolve được
  • SPN duplicate là nguồn lỗi Kerberos phổ biến — chạy setspn -X để detect duplicate trước VÀ sau migration
  • NTLM restriction: Server 2025 mặc định có thể restrict NTLM mạnh hơn 2012R2 — audit app nào còn dùng NTLM (Event ID 4624)
  • Kerberos FAST: nếu DC 2025 enforce FAST → legacy client/app có thể fail auth. Test trước khi enable
