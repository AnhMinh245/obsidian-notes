AD 2025 Upgrade - Tổng quan dự án

Tóm tắt nhanh

  • Nâng cấp toàn bộ hạ tầng Active Directory từ Windows Server 2012R2 lên Windows Server 2025 — bao gồm AD DS, DNS, DHCP, Certificate Server và RDS
  • Kiến trúc đích: 8 Domain Controller 2025 phân bổ đều 4 site (ROOT, MB, MN, TW), loại bỏ RODC, nâng Forest Functional Level lên 2025
  • Dự án chia 3 phase: Preparation → Migration → DHCP/RDS, mỗi phase có gate kiểm thử trước khi sang phase tiếp
  • Mọi thay đổi đều có rollback plan — nguyên tắc “không decommission cũ cho đến khi mới đã verified”

Bối cảnh: Lịch sử Windows Server và AD

Tại sao phải nâng cấp?

Windows Server 2012R2 đã end of extended support từ tháng 10/2023. Điều này có nghĩa:

  • Không còn security patch → hạ tầng AD trở thành mục tiêu dễ dàng cho attacker
  • Không support từ Microsoft → nếu gặp bug nghiêm trọng, Microsoft không hỗ trợ fix
  • Compliance risk → các chuẩn bảo mật (ISO 27001, PCI-DSS) yêu cầu OS phải được support
  • Feature gap → thiếu các tính năng bảo mật hiện đại (Credential Guard, gMSA improvements, LDAP channel binding enforcement)

Tại sao chọn 2025 thay vì 2022?

  • Server 2025 là phiên bản mới nhất, đảm bảo lifecycle dài nhất (~10 năm support)
  • Tính năng bảo mật vượt trội: LDAP encryption mặc định, loại bỏ DES, cải thiện Kerberos
  • Nếu nâng lên 2022 rồi 2025 → tốn 2 lần migration effort. Nhảy thẳng 2012R2 → 2025 hiệu quả hơn
  • AD schema hỗ trợ upgrade trực tiếp từ 2012R2 lên 2025 (không cần bước trung gian)

Analogie: nâng cấp AD giống như nâng cấp nền tảng tòa nhà

  • AD Domain = nền móng tòa nhà — mọi dịch vụ (DHCP, CA, RDS, DNS) đều “dựng” trên nền này
  • Domain Controller = cột trụ — nếu 1 cột hỏng, tòa nhà vẫn đứng (redundancy). Nhưng nếu tất cả cột cũ mục nát (hết support) → phải thay thế
  • Migration = thay cột mới từng cái một (không phải đập hết rồi xây lại) — parallel run là chìa khóa

Cấu trúc AD hiện tại

  • Single Forest, Single Domain — kiến trúc đơn giản, phù hợp tổ chức vừa
  • 4 AD Sites đã cấu hình:
    • ROOT — site trung tâm chính, chứa DC giữ mọi FSMO role và chạy tất cả dịch vụ quan trọng
    • MB (Miền Bắc) — chi nhánh phía Bắc, phục vụ authentication cho user tại đây
    • MN (Miền Nam) — chi nhánh phía Nam, có thêm RODC (sẽ bị loại bỏ)
    • TW (Trung ương) — site hành chính trung ương
  • Forest Functional Level và Domain Functional Level: 2012R2
  • Replication topology hiện tại: hub-and-spoke với ROOT là hub

Kế hoạch 3 Phase

Phase 1: Preparation và AD Upgrade

Mục tiêu: chuẩn bị hạ tầng, loại bỏ RODC, mở rộng schema, triển khai DC 2025

Backup bắt buộc trước Phase 1:

  • System State backup trên mọi DC hiện tại (đặc biệt DC-OLD-01 giữ FSMO + CA)
  • Backup AD CS database + private key riêng
  • Export DHCP configuration
  • Document toàn bộ GPO, DNS zone, site topology hiện tại
  • Snapshot VM (nếu DC chạy trên VM) — nhưng không dùng snapshot để rollback DC (gây USN rollback)

Các bước thực hiện:

  • RODC Removal

    • Chuyển mọi workload khỏi RODC — xác nhận không client nào còn authenticate qua RODC
    • Demote RODC (dcpromo hoặc Server Manager) — graceful demotion tạo metadata cleanup tự động
    • Nếu demote thất bại → dọn metadata thủ công trong AD Sites and Services và ADSI Edit (CN=RODC-01,OU=Domain Controllers,DC=...)
    • Xác nhận replication health sau khi xoá: repadmin /replsummary phải không có error
    • Xoá computer object nếu vẫn còn tồn tại sau demote

  • Schema Extension

    • Chạy adprep /forestprep để mở rộng AD Schema cho Server 2025 — thêm các class và attribute mới
    • Chạy adprep /domainprep để cập nhật domain-level permissions và objects
    • Xác minh schema version sau khi chạy: kiểm tra objectVersion của CN=Schema,CN=Configuration,...
    • Yêu cầu: tài khoản Schema Admins + Enterprise Admins, chạy trên DC giữ Schema Master role
    • Schema extension không thể rollback — đây là one-way operation. Nhưng vô hại nếu không promote DC 2025

  • DC 2025 Deployment → Chi tiết tại 04.1 - Triển khai Additional Domain Controllers

    • Triển khai 8 DC mới (2 per site), bắt đầu từ ROOT site
    • Promote thành Additional Domain Controller trong existing domain
    • Cấu hình AD DS + DNS + Global Catalog trên mỗi DC
    • Xác nhận replication hoạt động đúng giữa mọi DC

  • CA Parallel Setup

    • Cài đặt AD CS role trên server 2025 (chưa migrate — chỉ chuẩn bị role)
    • Backup CA database + private key từ CA cũ (DC-OLD-01) — 3 bản backup, lưu ở 3 vị trí khác nhau
    • Test restore trong lab environment trước khi thực hiện production

Rollback Phase 1: nếu DC 2025 có vấn đề nghiêm trọng → demote DC 2025, DC cũ vẫn hoạt động bình thường. Schema extension không ảnh hưởng DC cũ.

Phase 2: Migration

Mục tiêu: chuyển đổi FSMO roles, CA, ứng dụng, DNS sang hạ tầng mới

Backup bắt buộc trước Phase 2:

  • System State backup trên DC 2025 đã promote (baseline sau Phase 1)
  • Backup CA database lần nữa (fresh backup)
  • Snapshot cấu hình DNS hiện tại
  • Document application connection strings, SPN list

Các bước thực hiện:

  • FSMO Transfer → Chi tiết tại 04.2 - Chuyển đổi FSMO và Certificate Server

    • Transfer lần lượt 5 FSMO roles sang DC 2025 tại ROOT site
    • Thứ tự: Schema Master → Domain Naming → RID → Infrastructure → PDC Emulator (từ ít disruptive đến nhiều nhất)
    • Xác nhận sau mỗi role transfer: netdom query fsmo, test chức năng tương ứng
    • Chờ 1-2 ngày sau FSMO transfer ổn định trước khi migrate CA

  • CA Migration → Chi tiết tại 04.2 - Chuyển đổi FSMO và Certificate Server

    • Restore CA database + private key lên CA mới (server 2025)
    • Cập nhật AIA (Authority Information Access) và CDP (CRL Distribution Point) trỏ về server mới
    • Publish CRL mới từ CA 2025
    • Xác nhận certificate chain: CA root cert → Issuing CA cert → Client cert

  • Application Migration → Chi tiết tại 04.3 - Chuyển đổi ứng dụng và DNS

    • Audit dependency: ứng dụng nào kết nối AD, qua giao thức nào (LDAP, Kerberos, NTLM)
    • Cập nhật LDAP connection string nếu hardcode tên DC cũ → chuyển sang domain FQDN
    • Kiểm tra SPN và Kerberos delegation — đảm bảo không có SPN duplicate

  • DNS Cutover → Chi tiết tại 04.3 - Chuyển đổi ứng dụng và DNS

    • DNS zone AD-integrated tự replicate sang DC 2025 — không cần migrate thủ công
    • Cập nhật DHCP option 006 trỏ DNS mới cho DHCP client
    • Cập nhật conditional forwarder nếu trỏ về DC cũ
    • Cleanup DNS record cũ (SRV, A, PTR) sau khi DC cũ demoted

Rollback Phase 2: transfer FSMO ngược về DC cũ (DC cũ vẫn online), revert CA service, revert DNS pointers. Thời gian ước tính: 2-4 giờ.

Phase 3: DHCP và RDS

Mục tiêu: triển khai DHCP và RDS trên hạ tầng mới, hoàn tất migration

Backup bắt buộc trước Phase 3:

  • Export DHCP configuration từ server cũ (fresh export)
  • Document RDS session collection, RemoteApp list, user profile location
  • Backup GPO liên quan đến DHCP và RDS

Các bước thực hiện:

  • DHCP Migration → Chi tiết tại 04.4 - DHCP và RDS Migration

    • Export cấu hình DHCP từ server cũ → Import vào DHCP server mới
    • Cấu hình DHCP Failover pair (Load Balance mode)
    • Chạy song song: deactivate scope cũ → activate scope mới → monitor 3-5 ngày
    • Cutover: deauthorize DHCP cũ sau khi xác nhận stable

  • RDS Deployment → Chi tiết tại 04.4 - DHCP và RDS Migration

    • Triển khai RDS trên hạ tầng 2025: Connection Broker, Session Host, Gateway, Web Access
    • Migrate session collection, RemoteApp programs, user profile
    • Cấp certificate từ CA mới cho RDS Gateway và Web Access

  • Final Validation → Chi tiết tại 04.5 - Kiểm thử toàn diện

    • Kiểm thử toàn diện mọi thành phần: AD DS, DNS, DHCP, CA, RDS
    • Xác nhận rollback plan vẫn khả thi
    • Sign-off từ stakeholders, documentation handover

  • Decommission DC cũ (sau khi pass validation + 2 tuần monitoring)

    • Demote từng DC 2012R2 một cách graceful
    • Cleanup DNS records, AD metadata
    • Nâng Forest Functional Level lên 2025 (chỉ sau khi không còn DC nào chạy OS thấp hơn 2025)

Rollback Phase 3: reauthorize DHCP cũ, redirect RDS về cũ. Thời gian ước tính: 1-2 giờ.

Phase Dependency - Chuỗi phụ thuộc

Mỗi phase có go/no-go gate — không được tiến sang phase tiếp nếu chưa qua validation. Đây là nguyên tắc “validate before proceed” để đảm bảo có thể rollback an toàn tại bất kỳ thời điểm nào.

  • CA 2025 issue certificate thành công, certificate chain valid

Change Window Best Practices

  • Phase 1 (DC Deployment): có thể thực hiện trong giờ hành chính — promote DC mới không ảnh hưởng DC cũ
  • Phase 2 (FSMO + CA + DNS): thực hiện ngoài giờ cao điểm (tối/cuối tuần) — PDC Emulator transfer có thể ảnh hưởng password change
  • Phase 3 (DHCP + RDS): DHCP cutover nên vào cuối tuần khi ít user; RDS cutover vào tối khi ít session

Documentation Requirements

Mỗi phase phải có documentation đầy đủ:

  • Before: baseline measurements, current state snapshot, rollback plan review
  • During: change log (ai làm gì, lúc nào), issues encountered, decisions made
  • After: test results, sign-off, lessons learned

Nguyên tắc chung của dự án

  • No Big Bang: không chuyển đổi tất cả cùng lúc — từng thành phần, từng phase, validate sau mỗi bước
  • Parallel Run: luôn chạy song song cũ-mới trước khi cutover — client phải có fallback
  • Rollback Ready: mỗi bước đều có kế hoạch quay lại trạng thái trước, đã test trước khi cần dùng
  • Validate Before Proceed: không tiến phase mới khi chưa pass kiểm thử — go/no-go gate bắt buộc
  • Document Everything: ghi lại mọi thay đổi để audit trail và knowledge transfer
  • Communicate Proactively: thông báo stakeholders trước mỗi phase, không để “bất ngờ”
  • Backup Before Change: full backup trước mỗi phase — đây là lưới an toàn cuối cùng

Câu hỏi thường gặp

Q: Có thể nâng cấp in-place (upgrade OS trên DC hiện tại) thay vì deploy DC mới?

A: Microsoft hỗ trợ in-place upgrade cho DC, nhưng không khuyến nghị vì:

  • Rủi ro cao: nếu upgrade fail, mất DC
  • Không có parallel run: không thể chạy song song cũ-mới
  • Không thể rollback dễ dàng: rollback = restore từ backup
  • Best practice: deploy DC mới → migrate → decommission cũ (swing migration)

Q: Tại sao loại bỏ RODC? RODC có lợi ích gì?

A: RODC thiết kế cho branch site thiếu bảo mật vật lý (server đặt ở nơi không an toàn). Trong kiến trúc đích:

  • Mọi site đều có 2 full DC → không cần RODC
  • RODC tạo complexity (password replication policy, one-way replication)
  • RODC không thể giữ FSMO role, không thể là CA

Q: Có thể bỏ qua 2 tuần monitoring và decommission DC cũ ngay?

A: Không. 2 tuần monitoring là thời gian phát hiện issue “chậm” — ví dụ:

  • Certificate CRL expire cycle (7-14 ngày)
  • DHCP lease renewal cycle
  • Application batch job chạy weekly
  • User chưa logon (nghỉ phép) quay lại gặp vấn đề

Lưu ý quan trọng

  • Forest Functional Level raise là một chiều — không thể hạ xuống sau khi nâng. Chỉ raise khi chắc chắn không còn DC chạy OS thấp hơn 2025 và đã monitor ổn định
  • RODC removal phải clean: nếu demote thất bại, cần cleanup metadata thủ công trong AD Sites and Services và ADSI Edit — leftover metadata gây replication error
  • CA migration là bước rủi ro cao nhất — nếu private key bị mất, toàn bộ PKI infrastructure phải xây lại từ đầu. Backup, backup, backup
  • Giữ DC cũ online ít nhất 2 tuần sau khi migrate xong mọi thứ — phòng trường hợp phát hiện vấn đề muộn
  • LDAP channel binding và signing mặc định stricter trên Server 2025 — audit application compatibility trước
