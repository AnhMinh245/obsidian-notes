Chương 04: Three Pillars Deep Dive — Traces

"Distributed tracing cho bạn thấy hành trình chi tiết của một request xuyên suốt hệ thống — như camera giám sát từng bước đi của một kiện hàng qua hệ thống logistics."

Mục tiêu chương này: Hiểu trace/span là gì, tại sao cần context propagation, sampling strategies, và quan trọng nhất — cách kết hợp 3 pillars để debug hiệu quả.

ShopVN evolution: Thêm tracing vào ShopVN (v4) — giờ mỗi request có thể “quan sát” từng bước.

1. Tại sao Distributed Tracing ra đời?

1.1 Monolith vs Microservices — Sự chuyển đổi tạo ra vấn đề mới

Thời monolith (1 ứng dụng duy nhất): Mọi code chạy trong 1 process. Khi request chậm → bật profiler → thấy function nào mất nhiều thời gian nhất. Đơn giản.

Thời microservices (nhiều services): Một request đi qua 5-10 services, mỗi service là process riêng, chạy trên server riêng. Khi request chậm → chậm ở service nào?

User bấm "Đặt hàng" trên ShopVN. Request đi qua:

Browser → API Gateway → Order Service → Product Service (check stock)
                                      → Payment Service → Bank API (charge)
                                      → Database (save order)
                                      → Notification Service (send email)

Tổng latency = 3 giây. Nhưng...

- Product check mất bao lâu? 
- Payment mất bao lâu? 
- Database mất bao lâu?
- Cái nào là BOTTLENECK?

Logs: mỗi service có logs riêng → phải lục 5 bộ logs khác nhau
Metrics: biết "p99 = 3s" nhưng KHÔNG BIẾT 3s đó phân bổ thế nào

→ CẦN MỘT CÁCH ĐỂ "NỐI" MỌI THỨ LẠI

Distributed Tracing ra đời để giải quyết chính xác vấn đề này: theo dõi một request duy nhất xuyên suốt mọi services, đo thời gian từng bước, và hiển thị dưới dạng trực quan.

2. Core Concepts — Trace, Span, và Parent-Child

2.1 Trace — “Toàn bộ hành trình”

Một Trace đại diện cho toàn bộ hành trình của một request từ lúc vào hệ thống đến lúc hoàn thành. Mọi thứ liên quan đến request đó — dù xảy ra ở bao nhiêu services — đều thuộc cùng một Trace.

Mỗi trace có Trace ID duy nhất — chuỗi ký tự dùng để liên kết mọi thứ lại.

Trace ID: abc-123-def-456

Trace này chứa MỌI THỨ xảy ra khi user U001 bấm "Đặt hàng"
— dù xảy ra ở Order Service, Product Service, Payment Service, hay Database.

2.2 Span — “Một bước trong hành trình”

Mỗi Span đại diện cho một đơn vị công việc (operation) trong trace. Khi Order Service gọi Product Service, đó là một span. Khi Product Service query database, đó là một span khác.

2.3 Parent-Child — Cây phả hệ của request

Spans tạo thành cấu trúc cây — span cha gọi span con:

Order Service      Product Service        Payment Service
     │                    │                      │
     ├── validate_input   │                      │
     │                    │                      │
     ├── check_inventory ─┤                      │
     │                    ├── query_product_db    │
     │                    │                      │
     ├── process_payment ─┼──────────────────────┤
     │                    │                      ├── call_bank_api
     │                    │                      │
     ├── save_to_db       │                      │
     │                    │                      │
     └── send_notification│                      │

Và khi visualize dưới dạng waterfall/timeline (đây là view bạn sẽ thấy trong Dynatrace/Datadog):

Timeline:   0ms         200ms        500ms        800ms   950ms
            │            │            │            │       │
Gateway     ████████████████████████████████████████████████ 950ms
  Order     ·███████████████████████████████████████████████ 900ms
    Product ·████████····                                    100ms
    Payment ·········█████████████████████████████           500ms
      Bank  ··········███████████████████████████            450ms  ← BOTTLENECK!
    DB      ···································████           50ms
    Notify  ·····································██          30ms

Power of Tracing

Nhìn vào waterfall trên, bạn thấy NGAY LẬP TỨC:

  • Payment mất 500ms, chiếm hơn nửa tổng thời gian
  • Trong 500ms đó, Bank API chiếm 450ms → đây là root cause
  • Product check nhanh (100ms), DB nhanh (50ms) → không phải vấn đề

Không cần đoán. Không cần lục logs. Nhìn 1 cái là biết.

3. Context Propagation — “Chuyền cờ” qua các services

3.1 Vấn đề

Mỗi service chạy trên process/container riêng. Khi Order Service gọi Payment Service, Payment Service nhận được một HTTP request bình thường — nó không tự biết mình đang xử lý request thuộc trace nào.

Vậy làm sao tất cả spans biết chúng thuộc cùng một trace?

3.2 Giải pháp: Truyền trace context qua HTTP headers

Khi Service A gọi Service B, nó gắn thêm trace information vào HTTP headers. Service B đọc headers → biết trace_id → tạo span thuộc cùng trace.

Phân tích traceparent header (W3C Trace Context standard):

traceparent: 00-abc123def456-span789-01
              │  │             │       │
              │  │             │       └─ Flags: 01 = sampled (đang được trace)
              │  │             └──────── Parent Span ID: span cha (Order Service)
              │  └────────────────────── Trace ID: ID chung cho toàn bộ request
              └───────────────────────── Version: 00 (current)

4. Sampling — Trace mọi thứ hay chọn lọc?

4.1 Vấn đề: Chi phí

ShopVN xử lý 10,000 requests/giây. Mỗi request tạo ~8 spans. → 80,000 spans/giây = rất nhiều data. Lưu trữ tất cả rất tốn kém.

4.2 Head-based Sampling — Quyết định ngay từ đầu

Request đến API Gateway → Tung đồng xu (10% probability)
  - Mặt ngửa (10%) → Trace request này, đánh dấu sampled=01 ✅
  - Mặt sấp (90%) → KHÔNG trace, đánh dấu sampled=00 ❌
  
Mọi service downstream đọc flag → tuân theo quyết định ban đầu.
(Nếu Gateway nói "không trace" → Product, Payment cũng không trace)

Ưu: Đơn giản, chi phí dự đoán được (trace 10% = 10% data).
Nhược: Bạn có thể bỏ lỡ request lỗi nếu nó rơi vào 90% không sample. Request lỗi hiếm (0.1%) → có thể không bao giờ bắt được trong 10% sample!

4.3 Tail-based Sampling — Quyết định sau khi request hoàn thành

Mọi request đều được trace (collect hết).
Sau khi request hoàn thành → Collector xem xét:
  ✅ Có error? → Giữ
  ✅ Duration > 2s? → Giữ (slow request — đáng xem)
  ✅ Random 5% requests bình thường → Giữ (baseline)
  ❌ Request bình thường, nhanh, không lỗi → BỎ

Ưu: Không bao giờ bỏ lỡ errors — mọi request lỗi đều được giữ.
Nhược: Phải buffer toàn bộ spans trước khi quyết định → tốn RAM. Phức tạp hơn.

Tiêu chíHead-basedTail-based
Quyết định khi nàoĐầu requestCuối request
Miss errors?Có thểKhông
Resource usageThấpCao (cần buffer)
ComplexityĐơn giảnPhức tạp
Best forHigh-traffic, budget limitedError-sensitive systems

5. Kết nối Three Pillars — Sức mạnh tổng hợp

Đây là phần quan trọng nhất: 3 pillars không đứng riêng lẻ mà kết hợp thành workflow debug cực mạnh.

┌──────────────────────────────────────────────────┐
│                  MỘT REQUEST                     │
│                                                   │
│  TRACE (trace_id = abc-123)                       │
│  ├── Span: API Gateway       — 950ms             │
│  │   ├── Span: Order Service — 900ms             │
│  │   │   ├── Span: Product   — 100ms             │
│  │   │   ├── Span: Payment   — 500ms 🔴          │
│  │   │   ├── Span: Database  — 50ms              │
│  │   │   └── Span: Notify    — 30ms              │
│  │   │                                            │
│  │   │   METRICS (per span):                      │
│  │   │   duration, status_code, db.rows_affected  │
│  │   │                                            │
│  │   │   LOGS (kèm trace_id):                     │
│  │   │   "Creating order...", "Payment failed..." │
│  │                                                │
└──────────────────────────────────────────────────┘

Workflow debug thực tế: “Order Service lỗi!”

🔔 BƯỚC 1 — METRICS phát hiện vấn đề
   Dashboard: "Order Service error rate tăng từ 0.3% lên 8%!"
   → Xác nhận: CÓ VẤN ĐỀ. Nhưng vấn đề gì?

🔍 BƯỚC 2 — TRACES xác định vị trí
   Mở traces lỗi của Order Service:
   → Waterfall view: Payment span hiện đỏ, duration = 5000ms (timeout)
   → Cụ thể hơn: Bank API span = "connection refused"
   → Biết rồi: BANK API BỊ CHẾT. Nhưng lỗi chính xác là gì?

📋 BƯỚC 3 — LOGS cung cấp chi tiết
   Search: trace_id = "abc-123" AND service = "payment-service"
   → Log: "Bank API returned HTTP 503: Service Temporarily Unavailable"
   → Log kèm message từ bank: "Scheduled maintenance until 15:00"
   → ROOT CAUSE: Bank API đang bảo trì theo lịch!

✅ GIẢI PHÁP: Enable circuit breaker, switch sang backup payment provider.

Sức mạnh kết hợp

  • Metrics alone: “Có lỗi” (biết symptom)
  • Traces alone: “Lỗi ở Payment → Bank API” (biết location)
  • Logs alone: “Bank API trả 503: maintenance” (biết detail)
  • Cả 3 kết hợp: Symptom → Location → Root Cause → Fix. Trong vài phút.

6. Tổng Kết

ConceptKey Takeaway
TraceToàn bộ hành trình 1 request, xuyên mọi services
Span1 operation trong trace, có duration + status + attributes
Parent-ChildSpans tạo thành cây — span cha gọi span con
Context PropagationTruyền trace_id qua HTTP headers (traceparent)
Head SamplingQuyết định đầu, đơn giản, có thể miss errors
Tail SamplingQuyết định cuối, giữ mọi errors, tốn resource hơn
3 Pillars CombinedMetrics (detect) → Traces (locate) → Logs (detail)

ShopVN sau Chương 04

ShopVN đã có đủ 3 pillars: Logs + Metrics + Traces. Nhưng code đang implement thủ công — phải tự tạo trace_id, tự truyền headers, tự đo duration. Rất nhiều boilerplate code, dễ sót, khó maintain.

Mapping lý thuyết → code:

  • Span (phần 2.2) → class Span trong code: trace_id, span_id, parent_id, duration, status, attributes
  • Parent-Child (phần 2.3) → trace.start_span("check_inventory", parent_span): span con thuộc span cha
  • Waterfall View (phần 2.3) → method print_waterfall(): vẽ timeline trực quan
  • Context Propagation (phần 3) → Trace object được truyền qua các hàm service (trong thực tế qua HTTP headers)

Thử nghiệm

Chạy 10-20 requests, quan sát: requests nào có Payment chậm? Product chậm? DB lỗi? Waterfall cho bạn thấy ngay lập tức mà không cần lục logs.
