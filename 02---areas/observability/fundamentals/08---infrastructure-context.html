Chương 08: Infrastructure Context

"Ứng dụng không chạy trong chân không — nó chạy trên infrastructure. Hiểu infrastructure = hiểu context của mọi vấn đề."

Mục tiêu chương này: Hiểu tại sao infrastructure context là mảnh ghép thiết yếu cho Observability, cách correlate application performance với infrastructure state, và biết cần observe gì ở K8s, load balancers, cloud, và service mesh.

ShopVN evolution: ShopVN deploy trên Kubernetes. Khi app metrics cho thấy latency tăng, bạn cần dữ liệu infrastructure để phân biệt: “Do app code chậm? Hay do node quá tải? Hay do network issue?” Không có infra context = debug với một mắt bị bịt.

Liên kết: Infrastructure metrics dùng framework USE từ 03 - Three Pillars Deep Dive - Metrics. Infra events correlate với alerts từ 07 - Alerting & Incident Management. Topology mapping hỗ trợ root cause analysis từ 09 - AIOps & Advanced Patterns.

Chương này tập trung vào góc nhìn Observability của infrastructure — không dạy cách setup K8s hay Cloud từ đầu.

1. Tại sao Infrastructure Context quan trọng?

1.1 Ví dụ: Không có infra context vs có infra context

Tình huống: "ShopVN Order Service latency p99 = 3 giây" (bình thường 200ms)

━━━━━━ KHÔNG CÓ infra context ━━━━━━
   Engineer nhìn app metrics:
   → Error rate bình thường
   → DB query time bình thường  
   → No recent deployments
   → Code không thay đổi
   → "Tại sao chậm???" 😤
   → 30 phút debug, vẫn không tìm ra 💀

━━━━━━ CÓ infra context ━━━━━━
   Engineer nhìn app metrics + infra metrics:
   → Order Service pod đang chạy trên Node worker-3
   → Node worker-3: CPU 98%, Memory 95%  ← ĐÂY RỒI!
   → Vì sao? Pod của batch-job-ML đang chạy cùng node, chiếm hết resource
   → Giải pháp: Evict batch job, hoặc move order-service sang node khác
   → ROOT CAUSE: Resource contention (noisy neighbor)
   → Không liên quan gì đến app code!
   → 3 phút tìm ra ✅

1.2 Bốn tầng observability data

┌─────────────────────────────────────┐
│  Business Logic (SLIs/SLOs)         │  ← Ch06: "Chất lượng dịch vụ thế nào?"
├─────────────────────────────────────┤
│  Application (Logs/Metrics/Traces)  │  ← Ch02-05: "App đang làm gì?"
├─────────────────────────────────────┤
│  Infrastructure (K8s/VM/Network)    │  ← Ch08 (bạn đang ở đây): "Infra có ổn không?"
├─────────────────────────────────────┤
│  Hardware (CPU/Memory/Disk/Network) │  ← Physical/virtual resources
└─────────────────────────────────────┘

Khi debug: đi từ TRÊN XUỐNG
  "SLO vi phạm" → "App error ở đâu?" → "Infra có vấn đề gì?"

Mỗi tầng bổ sung context cho tầng trên

Application metrics vô nghĩa nếu thiếu infrastructure context. “App chậm” có thể do code, do DB, hoặc do node hết memory. Chỉ nhìn app metrics thì không phân biệt được.

2. Containers & Kubernetes — Góc nhìn Observability

2.1 Tại sao containers phức tạp hóa Observability?

TRƯỚC containers (traditional):
  1 server = 1 ứng dụng = "App chậm = server chậm" → Dễ debug
  Monitor: SSH vào server, top, htop, xem CPU/memory → xong

SAU containers:
  1 server (node) = 20-50 containers → "Container NÀO chậm?"
  Containers tạo/xóa liên tục (scale up/down, rolling update)
  → IP thay đổi, hostname thay đổi, pod name thay đổi
  → "Ephemeral" — monitoring truyền thống (SSH, check process) không hoạt động
  → CẦN monitoring tự động, dynamic, label-based

2.2 Kubernetes Concepts — Chỉ những gì cần cho Observability

Bạn không cần hiểu toàn bộ K8s để làm Observability. Chỉ cần nắm các concepts sau và tại sao chúng quan trọng cho monitoring:

K8s ConceptLà gìTại sao Observability cần biết
PodĐơn vị nhỏ nhất, chứa 1+ containersObserve per-pod metrics: CPU, memory, restart count
NodeMáy vật lý/ảo chạy podsNode unhealthy → MỌI pod trên nó bị ảnh hưởng
NamespaceNhóm logic (prod, staging, dev)Filter metrics/logs theo namespace
ServiceNetwork endpoint trỏ đến podsObserve traffic qua service (load balanced)
DeploymentQuản lý replicas và rolloutObserve rollout events: bao nhiêu replicas ready, có lỗi không
DaemonSetĐảm bảo 1 pod per nodePattern phổ biến để deploy monitoring agents
HPAHorizontal Pod AutoscalerObserve scaling events: khi nào scale, lý do gì

2.4 K8s Metrics — Những gì PHẢI monitor

Cluster level — “Cluster có đủ resource không?”

Pod level — “Pod của tôi có healthy không?”

Deployment level — “Deployment rollout có OK không?”

OOMKilled — Nguyên nhân crash phổ biến nhất trên K8s

OOMKilled (Out of Memory Killed): K8s tự động giết pod khi nó dùng memory vượt quá limit.

Sequence:
1. Pod dùng dần memory (memory leak hoặc payload lớn)
2. Memory usage chạm limit (ví dụ 512MB)
3. K8s gửi SIGKILL → pod chết NGAY LẬP TỨC (không cleanup)
4. K8s restart pod → restart counter +1
5. Nếu crash lại → CrashLoopBackOff (restart interval tăng dần)

Monitor: Alert khi container_memory_usage_bytes > 85% of limit → fix TRƯỚC khi OOMKilled.

3. Cloud Infrastructure — Load Balancers & Auto-scaling

3.1 Load Balancer Observability

Load balancer (ALB, NLB trên AWS; Cloud Load Balancing trên GCP) là cánh cửa đầu tiên của mọi traffic. Metrics từ LB cho bạn biết toàn bộ traffic picture:

┌──────────────────────────────────────────────────────┐
│                 Load Balancer Dashboard               │
│                                                        │
│  Active connections:        1,250                      │
│  Requests/second:           850                        │
│  Response time (avg):       45ms                       │
│                                                        │
│  Healthy backends:          4/5  ⚠️ (1 unhealthy!)   │
│  5xx from LB itself:        0                          │
│  5xx from backends:         23                         │
│  Spillover (rejected):      0                          │
└──────────────────────────────────────────────────────┘
LB MetricĐiều nó cho bạn biếtAlert khi
Healthy backendsBao nhiêu server đang nhận traffic< desired count
5xx from backendsBackend nào đang trả lỗiTăng đột biến
5xx from LBLB không thể forward request (cực nghiêm trọng)> 0
Spillover countRequests bị reject vì quá tải> 0 (capacity issue!)
Target response timeBackend đang phản hồi chậmp99 > threshold
Active connectionsTraffic hiện tạiBất thường (quá cao hoặc quá thấp)

Request count từ LB = nguồn chính xác nhất cho throughput

LB thấy 100% traffic (trước khi nó được distribute đến backends). Đây là nơi tốt nhất để đo tổng throughput và error rate cho toàn bộ service.

3.2 Auto-scaling — “Tự co giãn” và cần observe gì

Horizontal Pod Autoscaler (HPA) watches metrics:
  CPU > 70% for 5 min → Scale UP: thêm pods (3 → 5 pods)
  CPU < 30% for 10 min → Scale DOWN: bớt pods (5 → 3 pods)

Observability cần track:
  1. SCALING EVENTS
     → Khi nào scale? Scale lên/xuống bao nhiêu? Trigger metric là gì?
     
  2. TIME TO SCALE
     → Từ lúc CPU > 70% đến lúc pod mới ready = bao lâu?
     → Nếu > 5 phút = có thể quá chậm, users đã bị ảnh hưởng
     
  3. SCALING FAILURES
     → Không thể scale vì hết resource trên cluster?
     → Không thể scale vì quota limits trên cloud?
     
  4. OSCILLATION
     → Scale up rồi scale down rồi scale up liên tục?
     → = threshold quá nhạy, cần tune

4. Service Mesh — Observability “gần như miễn phí”

4.1 Service Mesh là gì (từ góc nhìn Observability)?

Service Mesh (Istio, Linkerd) gắn một sidecar proxy (thường là Envoy) vào mỗi pod. Proxy này ngồi giữa app và network, xử lý mọi traffic vào/ra:

┌──── Pod: Order Service ─────────────────────┐
│                                               │
│  ┌──────────────┐     ┌────────────────────┐ │
│  │  Order App   │◄───►│  Envoy Proxy       │◄───► Network
│  │  (your code) │     │  (sidecar)         │ │
│  │              │     │                    │ │
│  │  Chỉ biết:   │     │  TỰ ĐỘNG thu thập: │ │
│  │  business    │     │  ✅ RED metrics    │ │
│  │  logic       │     │  ✅ Traces          │ │
│  │              │     │  ✅ mTLS encryption │ │
│  └──────────────┘     └────────────────────┘ │
└───────────────────────────────────────────────┘

4.2 Tại sao “gần như miễn phí”?

Vì proxy tự động thu thập RED metrics (Rate, Errors, Duration) và distributed traces cho MỌI HTTP/gRPC calls — không cần sửa một dòng code app nào. Chỉ cần deploy Istio lên cluster → tự có metrics + traces cho tất cả services.

4.3 Giới hạn — vẫn cần manual instrumentation

Service mesh cho bạn (free):
  ✅ HTTP request rate, error rate, latency (RED)
  ✅ Connection-level traces (service A gọi service B)
  ✅ Traffic visualization (service map)
  ✅ mTLS (encrypted traffic between services)

Service mesh KHÔNG cho bạn:
  ❌ Business context (order_id, user_id, product_category)
  ❌ Application-level spans (validate_input, check_inventory)
  ❌ Custom business metrics (orders_created, revenue)
  ❌ Log content

→ Best practice: Service mesh cho network-level observability + manual OTel cho business-level observability = complete picture.

5. Topology & Dependency Mapping

5.1 Tại sao cần “bản đồ” hệ thống?

Khi hệ thống có 50+ services, không ai nhớ hết “service nào gọi service nào”. Topology map trả lời:

  • Service X chết → ảnh hưởng bao nhiêu service downstream?
  • Chain dài nhất là gì? (càng dài → càng fragile)
  • Có circular dependency không? (A → B → C → A?)

Impact Analysis — “Nếu X chết, hậu quả là gì?”

Component chếtImpactSeverity

Blast radius analysis

Topology map cho bạn thấy blast radius (phạm vi ảnh hưởng) khi một component fail. Component có blast radius lớn (Bank API, User DB) cần SLO cao hơn, redundancy nhiều hơn, circuit breaker sẵn sàng.

6. Infrastructure Changes & Correlation

6.1 Change Events — Correlate infra change với performance change

Khi bạn thay đổi infrastructure, hậu quả có thể không hiện ngay:

Timeline:
  14:00 — Terraform apply: scale Order Service từ 4 pods → 2 pods
  14:01 — Mọi thứ OK (2 pods đủ handle traffic hiện tại)
  14:15 — Traffic afternoon peak bắt đầu
  14:20 — Latency tăng 300% (2 pods không đủ handle peak traffic)
  14:25 — Alert fires: "p99 > 2s"

Nếu KHÔNG correlate:
  → Engineer debug code → code bình thường → confused
  
Nếu CÓ correlate (change events overlay trên dashboard):
  → Engineer thấy: "Ồ, 14:00 có scale down event" → ROOT CAUSE ngay

6.2 Gửi change events vào Observability platform

Khi event này xuất hiện trên timeline, mọi correlation trở nên tức thì — nhìn 1 cái là thấy “có change → có problem”.

Luôn gửi change events

Cả Dynatrace (Events API) và Datadog (Events) đều hỗ trợ. Overlay deployment/config change events trên metrics dashboard → correlation tức thì.

Smartscape vs Service Map

  • Dynatrace Smartscape: Full-stack topology (từ process → host → datacenter). Agent-based, tự discover mọi thứ kể cả non-instrumented.
  • Datadog Service Map: Trace-based (chỉ thấy services đã instrumented). Nhẹ hơn nhưng blind spots cho uninstrumented dependencies.
