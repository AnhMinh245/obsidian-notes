🧪 ShopVN Demo — Hands-on Lab Guide

Bộ demo đi kèm Observability Fundamentals.
Mỗi chương có 1 version chạy được — quan sát trực tiếp lý thuyết đã học.

🚀 Setup (1 lần duy nhất)

Virtual environment

Thư mục .env/ chứa Python 3 virtual environment đã cài sẵn. Nếu bạn thấy (.env) ở đầu dấu nhắc lệnh, venv đã được activate thành công.

📋 Cách chạy (mỗi chương)

Mở 2 terminals cạnh nhau:

┌────────────────────────────┐  ┌────────────────────────────┐
│ Terminal 1: SERVER          │  │ Terminal 2: CLIENT          │
│                             │  │                             │
│ python v1_basic_app.py      │  │ python simulate_traffic.py  │
│                             │  │                             │
│ (quan sát output ở đây)     │  │ (gửi traffic ở đây)         │
└────────────────────────────┘  └────────────────────────────┘

Dừng server: Ctrl+C → Chạy version tiếp theo.

📖 Hành trình từng chương

Chương 01: v1 — Basic Application (Không có Observability)

Xem lý thuyết: Phần 10 (Concurrency), Bảng tổng kết chương 01

Quan sát:

  • Terminal 1 (server): Flask chỉ hiện 127.0.0.1 - - [date] "POST /api/v1/orders HTTP/1.1" 201 -
  • Bạn thấy status code (201, 400, 500) nhưng KHÔNG BIẾT:
    • User nào đặt hàng?
    • Sản phẩm gì?
    • Tại sao lỗi?
    • Mất bao lâu?

💡 Bài học: Không có observability = “bay trong sương mù”.

Chương 02: v2 — Structured Logging

Xem lý thuyết: Phần 2 (Structured Logging), Phần 5 (Correlation)

Quan sát ở Terminal 1 (server):

So sánh v1 vs v2:

  • Giờ bạn biết: AI (user_id), MUA GÌ (product_id), GIÁ (total), MẤT BAO LÂU (duration_ms)
  • Khi lỗi: biết lỗi gì (error_type), ở đâu (message)
  • request_id cho phép correlation — tìm tất cả logs của cùng 1 request

💡 Bài học: Structured logging biến “không biết gì” → “biết mọi thứ về từng sự kiện”.

Chương 03: v3 — Prometheus Metrics

Xem lý thuyết: Phần 2 (Metric Types), Phần 5 (RED/USE/Golden Signals)

Quan sát:

  1. Mở browser: http://localhost:5000/dashboard

    • Thấy RED metrics: Total requests, Error rate, Status breakdown
    • Trang tự refresh mỗi 5 giây
    • Gửi thêm traffic → metrics thay đổi realtime

  2. Mở: http://localhost:5000/metrics

    • Thấy Prometheus raw format:
    shopvn_http_requests_total{method="POST",endpoint="/api/v1/orders",status_code="201"} 42.0
shopvn_http_requests_total{method="POST",endpoint="/api/v1/orders",status_code="500"} 3.0
shopvn_http_request_duration_seconds_bucket{le="0.1",...} 38.0

So sánh v2 vs v3:

  • v2: biết chi tiết từng request (logs)
  • v3: biết xu hướng tổng thể — error rate bao nhiêu %, p99 latency bao nhiêu

💡 Bài học: Logs cho chi tiết. Metrics cho bức tranh lớn. Cần CẢ HAI.

Chương 04: v4 — Distributed Tracing

Xem lý thuyết: Phần 2 (Trace/Span), Phần 5 (3 Pillars Combined)

Quan sát ở Terminal 1 — WATERFALL VIEW:

  🔍 TRACE: a1b2c3d4e5f6...  (Total: 185ms)
  ─────────────────────────────────────────────
  ✅ order-service: POST /api/v1/orders   |████████████████████████████████████████| 185ms
  ✅   product-service: check_inventory   |███████·································|  35ms
  ✅   payment-service: process_payment   |·······████████████████████████████·····| 120ms
  ✅   database: db_insert_order          |····································███·|  15ms
  ─────────────────────────────────────────────

Khi có lỗi:

  🔍 TRACE: x9y8z7w6v5u4...  (Total: 3150ms)
  ─────────────────────────────────────────────
  🔴 order-service: POST /api/v1/orders   |████████████████████████████████████████| 3150ms
  ✅   product-service: check_inventory   |█·······································|   45ms
  🔴   payment-service: process_payment   |·███████████████████████████████████████| 3100ms
       ↳ ERROR: Payment gateway timeout after 3000ms
  ─────────────────────────────────────────────

So sánh v3 vs v4:

  • v3: biết “p99 = 3 giây” nhưng KHÔNG BIẾT chậm ở đâu
  • v4: thấy ngay Payment Service chiếm 3100ms = BOTTLENECK

💡 Bài học: Metrics phát hiện vấn đề. Traces xác định VỊ TRÍ vấn đề.

Chương 05: v5 — OpenTelemetry

Xem lý thuyết: Phần 4 (v4 vs v5 so sánh), Phần 3 (Kiến trúc OTel)

Quan sát ở Terminal 1 — OTel Span Export:

So sánh v4 vs v5:

  • v4: ~100 dòng manual tracing code (Span class, Trace class, print_waterfall)
  • v5: FlaskInstrumentor().instrument_app(app) — 1 dòng = tự trace mọi routes
  • v5: Context propagation TỰ ĐỘNG (OTel SDK làm)
  • v5: Đổi ConsoleSpanExporter → OTLPSpanExporter = gửi đến Jaeger/Dynatrace

💡 Bài học: Manual tracing giúp hiểu bản chất. OTel giúp làm thật — ít code, vendor-neutral.

🔄 Tóm tắt: Code thay đổi gì qua mỗi version?

v1 (Ch01): Flask app thuần         │ 0 observability
                                    │
v2 (Ch02): + JSONFormatter          │ + Biết CHI TIẾT từng sự kiện
           + log() helper           │
           + request_id             │
                                    │
v3 (Ch03): + prometheus_client      │ + Biết XU HƯỚNG (RED metrics)
           + Counter, Histogram     │ + /dashboard endpoint
           + /metrics endpoint      │
                                    │
v4 (Ch04): + Span, Trace classes    │ + Biết VỊ TRÍ bottleneck
           + Waterfall print        │ + Thấy từng bước mất bao lâu
           + Context propagation    │
                                    │
v5 (Ch05): - Bỏ manual tracing     │ + Tự động, vendor-neutral
           + OTel SDK               │ + 1 dòng auto-instrument
           + FlaskInstrumentor      │ + Sẵn sàng cho Jaeger/Dynatrace

📚 Concepts Tương ứng cho Chương 06-09

Chương 06-09 không có demo code riêng, nhưng data từ v2-v5 minh họa trực tiếp các concepts:

ChươngConceptÁp dụng vào data từ demo
06 - SLI, SLO & Error BudgetsSLI: error rate, latency p99Mả http_requests_total{status=5xx} v3 = Error Rate SLI
06 - SLI, SLO & Error BudgetsError BudgetNếu SLO = 99%: budget = 1%. V3 dashboard hiện error rate thực tế
07 - Alerting & Incident ManagementAlert ConditionAlert khi error_rate > 5% trong 5 phút — dùng metrics từ v3
08 - Infrastructure ContextResource saturationMô phỏng connection pool exhaustion trong db_save_order() (v1-v5)
09 - AIOps & Advanced PatternsAnomaly detectionPattern: payment timeout 5% random — cạ bặp của AI phân tích
