Chương 01: Application Logic Fundamentals

"Bạn không thể observe thứ bạn không hiểu."

Trước khi học cách giám sát một ứng dụng, bạn phải hiểu ứng dụng đó hoạt động như thế nào. Chương này xây dựng nền tảng đó — và mọi thứ ở các chương sau đều dựa trên những gì bạn học ở đây.

1. Client-Server Architecture — Nền tảng của mọi thứ

1.1 Mô hình cơ bản

Hãy tưởng tượng bạn vào một nhà hàng. Bạn (khách hàng) gọi món, phục vụ mang order xuống bếp, bếp nấu xong rồi phục vụ mang món ra cho bạn. Đây chính xác là cách một ứng dụng web hoạt động:

┌──────────┐     Request      ┌──────────┐
│  Client  │ ───────────────► │  Server  │
│ (Browser)│ ◄─────────────── │  (App)   │
└──────────┘     Response     └──────────┘
  • Client (người gọi món): Trình duyệt web, mobile app, hoặc một service khác — bất kỳ thứ gì gửi yêu cầu.
  • Server (nhà bếp): Nhận yêu cầu, xử lý logic, truy xuất dữ liệu, rồi trả về kết quả.

Mô hình này đơn giản, nhưng chứa đựng một ý tưởng quan trọng: client không cần biết server xử lý như thế nào bên trong — nó chỉ cần gửi request đúng format và nhận response. Điều này cho phép client và server phát triển độc lập.

1.2 Tại sao mô hình này quan trọng cho Observability?

Khi bạn mở Dynatrace hay Datadog, mọi thứ bạn thấy đều xoay quanh mô hình request-response:

  • Response time = thời gian từ lúc server nhận request đến lúc gửi response
  • Throughput = bao nhiêu request/giây server đang xử lý
  • Error rate = bao nhiêu phần trăm requests nhận được response lỗi

Nếu không hiểu request-response, những con số này vô nghĩa.

1.3 Kiến trúc nhiều tầng (Multi-tier Architecture)

Trong thực tế, “server” không phải là một cỗ máy duy nhất. Nó được chia thành nhiều tầng, mỗi tầng có chuyên môn riêng — giống như trong nhà hàng lớn có người tiếp tân (Web Server), đầu bếp chính (Application Server), và kho hàng (Database):

┌──────────┐    ┌───────────┐    ┌──────────────┐    ┌──────────┐
│  Client  │───►│ Web Server│───►│ App Server   │───►│ Database │
│ (Browser)│◄───│ (Nginx)   │◄───│ (Python/Java)│◄───│(Postgres)│
└──────────┘    └───────────┘    └──────────────┘    └──────────┘

Tầng 1 — Web Server (Nginx, Apache): Người tiếp tân. Nhận request từ internet, serve các file tĩnh (ảnh, CSS, JS), và chuyển tiếp các dynamic requests đến tầng sau. Nó cũng đóng vai trò reverse proxy — che giấu cấu trúc bên trong khỏi thế giới bên ngoài.

Tầng 2 — Application Server (Python/Flask, Java/Spring): Đầu bếp chính. Xử lý toàn bộ business logic — xác thực user, validate dữ liệu, tính toán giá, gọi các service khác. Đây là nơi phần lớn code ứng dụng chạy.

Tầng 3 — Database (PostgreSQL, MySQL, MongoDB): Kho hàng. Lưu trữ dữ liệu lâu dài — thông tin user, sản phẩm, đơn hàng. Application server hỏi database mỗi khi cần đọc hoặc ghi dữ liệu.

Tại sao chia tầng?

Mỗi tầng có thể scale độc lập. Database chậm? Tăng RAM cho database mà không cần động đến app server. App server quá tải? Thêm app server mà database giữ nguyên. Khi làm Observability, bạn sẽ monitor từng tầng riêng vì chúng có performance characteristics hoàn toàn khác nhau.

2. HTTP Protocol — Ngôn ngữ giao tiếp của Web

2.1 HTTP là gì và tại sao bạn phải hiểu nó?

HTTP (HyperText Transfer Protocol) là “ngôn ngữ” mà client và server dùng để nói chuyện với nhau. Khi bạn mở Dynatrace và thấy “HTTP 502 Bad Gateway”, bạn cần biết ngay đó nghĩa là gì — không phải mở Google tra.

HTTP có một đặc điểm quan trọng: nó là stateless (không trạng thái). Mỗi request là hoàn toàn độc lập — server không “nhớ” request trước đó. Giống như mỗi lần bạn gọi phục vụ là một người phục vụ khác, không biết bạn đã gọi gì trước đó.

Vậy làm sao server biết bạn đã đăng nhập?

Qua Cookies hoặc JWT tokens gửi kèm trong mỗi request. Client phải tự nhắc server “tôi là ai” trong MỌI request. Server không tự nhớ.

2.2 Cấu trúc một HTTP Request

Mỗi request gửi đi bao gồm 4 phần. Hãy tưởng tượng nó như một bức thư:

Bây giờ hãy nhìn từ góc nhìn Observability — mỗi thành phần cho bạn thông tin gì:

Thành phầnThông tin cho Observability
Method (POST)Đây là request tạo mới dữ liệu, không phải đọc
Path (/api/v1/orders)Request đến Order Service, tính năng tạo đơn hàng
AuthorizationBiết user nào đang gọi — cần thiết khi debug “user X bị lỗi gì?”
X-Request-IDCực kỳ quan trọng — ID duy nhất để tìm lại request trong hàng triệu logs
Body sizeBody lớn = latency cao hơn (serialize/deserialize mất thời gian)

2.3 HTTP Methods — Mỗi method nói lên điều gì?

HTTP có nhiều methods, mỗi method biểu thị một ý định khác nhau:

MethodÝ nghĩaẨn dụ nhà hàngCó thay đổi dữ liệu?
GETLấy/đọc dữ liệu”Cho xem menu”Không
POSTTạo dữ liệu mới”Gọi món mới”Có
PUTCập nhật toàn bộ”Đổi toàn bộ order”Có
PATCHCập nhật một phần”Đổi số lượng 1 món”Có
DELETEXóa dữ liệu”Hủy món”Có

Tại sao điều này quan trọng cho Observability? Vì khi phân tích traffic, bạn cần biết ý nghĩa của pattern bạn thấy:

  • GET chiếm 80% traffic = bình thường, người dùng đang duyệt web
  • POST tăng đột biến vào lúc 12:00 = có thể là flash sale hoặc bot tấn công
  • DELETE requests bất thường lúc 3 giờ sáng = 🔴 có thể ai đó đang xóa dữ liệu trái phép

2.4 HTTP Status Codes — “Bảng đèn sức khỏe” của ứng dụng

Đây là thứ bạn nhìn hàng ngày khi làm Observability. Server trả về một mã số (status code) để nói cho client biết kết quả xử lý. Các status codes được chia thành 5 nhóm:

🟢 2xx — Thành công

Khi bạn thấy 2xx, nghĩa là mọi thứ hoạt động đúng.

CodeTênKhi nào trả vềVí dụ ShopVN
200OKRequest xử lý thành côngGET /products → trả danh sách sản phẩm
201CreatedTạo mới thành côngPOST /orders → đơn hàng đã tạo
204No ContentThành công nhưng không cần trả bodyDELETE /orders/123 → đã xóa

🟡 3xx — Chuyển hướng

Client được yêu cầu đi đến một URL khác.

CodeTênÝ nghĩa thực tế
301Moved Permanently”Trang này đã chuyển vĩnh viễn sang URL mới”
302Found”Tạm thời chuyển hướng” (phổ biến sau khi login)
304Not Modified”Dữ liệu chưa đổi, dùng bản cached” (tiết kiệm bandwidth)

🟠 4xx — Lỗi phía Client

Client gửi sai — server hiểu request nhưng từ chối xử lý.

CodeTênNghĩa đời thựcKhi nào xảy ra ở ShopVN
400Bad Request”Tôi không hiểu bạn gửi gì”JSON sai format, thiếu field bắt buộc
401Unauthorized”Bạn chưa đăng nhập”Token hết hạn hoặc không có token
403Forbidden”Bạn đăng nhập rồi nhưng không có quyền”User thường truy cập trang admin
404Not Found”Không tìm thấy”URL sai hoặc sản phẩm đã bị xóa
429Too Many Requests”Bạn gửi quá nhiều, chậm lại đi”Rate limiting khi bị spam

🔴 5xx — Lỗi phía Server

Server bị lỗi — đây là nơi bạn cần chú ý nhất khi làm Observability.

CodeTênNghĩa đời thựcNguyên nhân thường gặp
500Internal Server Error”Server bị crash/bug”Exception không xử lý, bug trong code
502Bad Gateway”Server trung gian nhận response lỗi”Upstream service trả lỗi hoặc không response
503Service Unavailable”Server quá tải”Quá nhiều requests, server đang maintenance
504Gateway Timeout”Không nhận response kịp thời”Upstream service quá chậm, timeout

Rule quan trọng nhất cho Observability

  • 4xx tăng = có vấn đề UX hoặc API docs sai, khách hàng đang khó chịu
  • 5xx tăng = HỆ THỐNG BỊ LỖI — cần investigation ngay lập tức
  • Error rate (tỷ lệ 5xx / tổng requests) là một trong những SLI (Service Level Indicator) quan trọng nhất mà bạn sẽ học ở 06 - SLI, SLO & Error Budgets

Phân biệt 502 vs 503 vs 504

Cả ba đều liên quan đến “server downstream có vấn đề”, nhưng chi tiết khác nhau:

  • 502: Gateway nhận được response từ upstream, nhưng response đó không hợp lệ (ví dụ: upstream trả HTML thay vì JSON)
  • 503: Server tự biết nó đang quá tải hoặc đang maintenance, chủ động từ chối
  • 504: Gateway không nhận được response nào trong thời gian cho phép (timeout)

Khi debug, sự phân biệt này giúp bạn biết nên nhìn vào đâu — upstream service (502/504) hay chính service đó (503).

3. Request Lifecycle — Hành trình chi tiết của một Request

Bây giờ hãy theo dõi từng bước khi một request thực sự đi qua hệ thống. Hiểu được điều này, bạn sẽ biết cần observe ở đâu và cái gì.

3.1 Ví dụ: “Khi bạn bấm ‘Đặt hàng’ trên ShopVN”

Bước 1: DNS Resolution (1-50ms)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Browser hỏi DNS: "shopvn.com ở đâu?"
DNS trả lời:     "IP: 203.0.113.50"
→ Giống tra danh bạ để tìm số điện thoại từ tên người

Bước 2: TCP + TLS Handshake (50-150ms)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Browser mở kết nối TCP đến IP:Port
Sau đó TLS handshake để mã hóa kết nối (HTTPS)
→ Giống bắt tay + trao đổi mật khẩu bí mật trước khi nói chuyện

Bước 3: HTTP Request (< 1ms)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
POST /api/v1/orders
Body: { "product_id": "SP001", "quantity": 2 }
→ Gửi yêu cầu thực sự

Bước 4: Load Balancer (1-5ms)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LB nhận request, chọn 1 trong N app servers (ít tải nhất)
→ Giống lễ tân chọn bàn còn trống

Bước 5: App Server xử lý (50-500ms)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  5a. Parse JWT token → xác thực user
  5b. Validate input data
  5c. Gọi Product Service → kiểm tra tồn kho (50-100ms)
  5d. Gọi Payment Service → xử lý thanh toán (100-500ms)
  5e. Ghi database → INSERT order (5-50ms)
  5f. Gọi Notification Service → gửi email (fire-and-forget)

Bước 6: Response
━━━━━━━━━━━━━━━━
HTTP 201 Created
{ "order_id": "ORD-2026-001", "status": "confirmed" }

Bước 7: Browser render
━━━━━━━━━━━━━━━━━━━━━
"Đặt hàng thành công! 🎉"

3.2 Tại sao phải hiểu điều này?

Nhìn vào request lifecycle, bạn thấy ngay một sự thật: kiểm soát mỗi bước là điều kiện tiên quyết để observe. Nếu request tổng cộng mất 3 giây, bạn cần biết 3 giây đó chia như thế nào giữa các bước:

BướcThời gian điển hìnhAi chịu trách nhiệm?
DNS1-50msInfra / DNS provider
TCP + TLS50-150msInfra / Network
App Processing50-500msDevelopment team
Database5-100msDBA / Development
External API calls50-2000msKhông kiểm soát được — rủi ro lớn nhất

External dependencies là rủi ro lớn nhất

Trong ví dụ trên, Payment Service gọi đến Bank API (bên thứ 3). Bạn không kiểm soát được Bank API — nếu nó chậm hoặc chết, ShopVN cũng bị ảnh hưởng. Đây là lý do cần circuit breaker và timeout (phần 10).

4. Giới thiệu ShopVN — Ví dụ xuyên suốt

Xuyên suốt bộ tài liệu này, chúng ta sẽ dùng ShopVN — một nền tảng e-commerce Việt Nam giả lập — để minh họa mọi khái niệm. ShopVN được thiết kế với kiến trúc microservices, giống như các ứng dụng thực tế bạn sẽ gặp trong công việc.

Tại sao kiến trúc này?

Mỗi service có trách nhiệm riêng biệt (Single Responsibility). Điều này nghĩa là:

  • Product Service chỉ quản lý sản phẩm, tồn kho
  • Order Service chỉ xử lý đặt hàng
  • Payment Service chỉ xử lý thanh toán
  • Mỗi service có database riêng — không chia sẻ database (Database per Service pattern)

Lợi ích: Mỗi team phát triển độc lập, deploy độc lập. Nhược điểm: Debugging trở nên khó hơn nhiều — request đi qua nhiều services, lỗi có thể ở bất kỳ đâu. Đây chính xác là lý do Observability trở nên thiết yếu với microservices.

4.2 ShopVN Order Service — Code cơ bản

Đây là code Python cơ bản của Order Service. Bạn không cần nhớ mọi dòng — hãy tập trung vào flow: request đến → validate → gọi services khác → ghi DB → trả response.

Bạn thấy vấn đề gì không?

Code trên hoạt động nhưng hoàn toàn mù khi có lỗi:

  • Không có log nào → không biết request nào đã chạy, lỗi ở đâu
  • Không có metrics → không biết bao nhiêu orders/phút, latency trung bình bao nhiêu
  • Không có tracing → không biết request chậm ở bước nào (Product? Payment? DB?)

Các chương tiếp theo sẽ lần lượt thêm từng lớp observability vào chính đoạn code này.

5. Sync vs Async — Hai cách services “nói chuyện”

Trong kiến trúc microservices, services cần giao tiếp với nhau. Có hai cách chính, và mỗi cách ảnh hưởng đến cách bạn observe hệ thống.

5.1 Synchronous (Đồng bộ) — “Gọi điện thoại”

Client gửi request rồi đứng chờ cho đến khi nhận response. Giống gọi điện — bạn phải đợi người kia trả lời mới nói tiếp được.

Ưu điểm: Đơn giản, kết quả ngay lập tức, dễ debug.
Nhược điểm: Cascade effect — nếu Product Service chậm → Order Service chậm → Client chờ → User bực mình.

5.2 Asynchronous (Bất đồng bộ) — “Gửi tin nhắn”

Client gửi message vào message queue rồi tiếp tục làm việc khác ngay. Giống gửi tin nhắn — bạn gửi xong là đi làm việc khác, không cần chờ reply.

Ưu điểm: Không bị block, xử lý được traffic burst, retry tự động.
Nhược điểm: Khó debug hơn, kết quả không ngay, trace bị đứt qua queue.

5.3 ShopVN dùng cả hai

Giao tiếpKiểuLý do
Order → ProductSyncPhải biết ngay còn hàng không — không thể tạo đơn mà không biết
Order → PaymentSyncPhải biết ngay thanh toán thành công không — tạo đơn mà chưa trả tiền thì loạn
Order → NotificationAsyncEmail xác nhận gửi muộn 5-10 giây cũng OK — không urgent

Tác động đến Observability

  • Sync: Distributed tracing hoạt động tự nhiên — request A gọi service B, trace_id truyền qua HTTP header. Dễ theo dõi.
  • Async: Trace bị đứt tại message queue. Message vào queue rồi, consumer lấy ra sau — làm sao liên kết? Cần kỹ thuật đặc biệt gọi là context propagation qua message (sẽ học ở 04 - Three Pillars Deep Dive - Traces).

6. Database — Nơi 50-80% Performance Issues bắt nguồn

Trong kinh nghiệm thực tế, hơn nửa số performance issues đều liên quan đến database. Hiểu database ở mức cần thiết cho Observability là bắt buộc.

6.1 Connection Pooling — Tại sao không mở connection mới mỗi lần?

Mở một database connection rất tốn kém — cần TCP handshake, authentication, allocate memory. Mất khoảng 20-50ms mỗi lần. Nếu mỗi request mở connection mới rồi đóng, 1000 requests/giây = 1000 lần mở/đóng = rất lãng phí.

Connection Pool giải quyết vấn đề này: tạo sẵn một “bể” connections, tái sử dụng chúng.

Connection Pool Exhaustion — một nguyên nhân outage phổ biến

Nếu maxconn=20 nhưng có 50 requests đồng thời, 30 requests phải chờ connection. Kết quả: latency tăng vọt, rồi timeout → 504 Gateway Timeout.

Trong Observability, bạn cần monitor:

  • pool.active_connections — bao nhiêu đang được dùng
  • pool.idle_connections — bao nhiêu đang “rảnh”
  • pool.waiting_requests — bao nhiêu đang chờ → nếu > 0 = cảnh báo

6.2 N+1 Query Problem — Kẻ giết performance âm thầm

Đây là lỗi mà developer rất hay mắc phải mà không biết:

Phát hiện N+1 bằng Observability

Trong Distributed Tracing (Chương 04), N+1 hiện ra rõ ràng: bạn thấy hàng trăm spans database query (mỗi span = 1 query) bên trong 1 request. Pattern này cực dễ nhận ra. Cả Dynatrace lẫn Datadog đều có khả năng tự động phát hiện N+1.

6.3 Database Indexing — “Mục lục” cho database

Khi bảng có 10 triệu rows, tìm kiếm không có index = quét toàn bộ 10 triệu rows. Có index = nhảy thẳng đến kết quả.

Ẩn dụ: Index giống mục lục cuối sách. Muốn tìm chủ đề “TCP handshake”? Thay vì lật từng trang (full table scan), bạn mở mục lục → thấy “TCP handshake: trang 45” → nhảy thẳng đến trang 45.

Slow queries trong Observability

Mọi tool Observability đều có slow query detection. Dynatrace hiển thị top slow queries kèm execution plan. Khi bạn thấy query chậm, bước đầu tiên luôn là kiểm tra: có index chưa?

7. Caching — Tại sao lại cần “bộ nhớ tạm”?

7.1 Vấn đề

Nếu 1000 người cùng xem sản phẩm SP001 trong 1 phút, không lẽ query database 1000 lần cho cùng 1 kết quả? Database vốn đã là bottleneck — đừng làm nó nặng thêm.

7.2 Giải pháp: Cache

Cache = lưu kết quả đã tính xong vào bộ nhớ nhanh (RAM), phục vụ từ cache thay vì tính lại.

7.3 Cache Metrics — Monitor cache CÓ ĐANG HIỆU QUẢ KHÔNG?

MetricCông thứcÝ nghĩa
Hit Ratehits ÷ (hits + misses) × 100%Trên 90% = tốt. Dưới 50% = cache gần như vô dụng, cần review strategy
Eviction RateSố items bị xóa khỏi cache / phútCao = cache bị đầy, cần tăng memory
TTL EffectivenessTỷ lệ expired vs evictedGiúp tune TTL cho phù hợp

Cache Invalidation

Khi dữ liệu database thay đổi (ví dụ: giá sản phẩm đổi), cache vẫn giữ giá cũ cho đến khi TTL hết. Đây là trade-off: tốc độ vs freshness. Trong Observability, cần alert khi cache có stale data quá lâu.

8. Error Handling & Resilience Patterns

Trong microservices, lỗi là chuyện bình thường. Service nào cũng có thể chết bất cứ lúc nào. Câu hỏi là: khi một service chết, phần còn lại có chết theo không?

8.1 Circuit Breaker — “Cầu dao tự động”

Vấn đề: Payment Service bị chậm (mất 30 giây mỗi request). Nếu Order Service cứ tiếp tục gọi → 100 requests đều bị block 30 giây → thread pool cạn kiệt → Order Service cũng chết → cascade failure.

Giải pháp: Circuit Breaker — tự động ngắt gọi khi phát hiện service downstream đang lỗi.

Trạng thái CLOSED (bình thường):
  Mọi request đi qua bình thường
  Đếm số lần fail liên tiếp

  → Fail > 5 lần liên tiếp?
  
Chuyển sang OPEN (ngắt mạch):
  CHẶN MỌI REQUEST → trả lỗi ngay lập tức (không đợi timeout)
  Tiết kiệm resource, không làm tình hình tệ hơn
  
  → Sau 30 giây...
  
Chuyển sang HALF-OPEN (thử lại):
  Cho 1 request thử đi qua
  - Thành công? → Quay lại CLOSED ✅
  - Vẫn fail? → Quay lại OPEN ⏳

Circuit Breaker trong Observability

Circuit state (CLOSED/OPEN/HALF-OPEN) là một metric quan trọng cần monitor. Nếu circuit OPEN → bạn biết ngay service downstream đang có vấn đề nghiêm trọng — mà không cần chờ alert từ service đó.

8.2 Retry với Exponential Backoff

Khi request fail, thử lại là ý tưởng tốt. Nhưng thử lại ngay lập tức thì không — nếu service đang quá tải, bạn retry ngay chỉ khiến nó quá tải HƠN.

Exponential Backoff: Chờ lâu hơn giữa mỗi lần retry — 1 giây, 2 giây, 4 giây…

Tại sao phải thêm random (jitter)?

Tưởng tượng 1000 clients đều fail cùng lúc. Nếu tất cả retry sau đúng 1 giây → thundering herd — 1000 requests đập vào server cùng lúc → lại fail. Thêm random để phân tán retry ra → giảm tải cho server.

8.3 Timeout — Đừng chờ mãi

Timeout phải GIẢM DẦN theo chiều sâu:

Client (30s) → API Gateway (15s) → Order Service (10s) → Payment (5s) → Bank API (3s)
   ▲                                                                          ▲
   │                                                                          │
 Outer timeout > Inner timeout         Payment không nên chờ Bank quá 3 giây

Tại sao? Nếu innermost timeout = 30 giây (bằng client timeout), khi Bank API chậm → Payment chờ 30 giây → Order chờ 30 giây → Client cũng chờ 30 giây → user đã bỏ đi từ lâu.

9. Authentication & Load Balancing — Ngắn gọn

9.1 Authentication (AuthN) vs Authorization (AuthZ)

  • AuthN = “Bạn là ai?” → Xác minh danh tính qua JWT Token
  • AuthZ = “Bạn được phép làm gì?” → Kiểm tra quyền (role: admin, user, guest)

Observability signals: 401 tăng đột biến = token hết hạn hàng loạt hoặc auth service down. 403 tăng = có thể unauthorized access attempt.
