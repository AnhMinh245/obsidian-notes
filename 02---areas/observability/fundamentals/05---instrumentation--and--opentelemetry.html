Chương 05: Instrumentation & OpenTelemetry

"OpenTelemetry là tiêu chuẩn mở cho telemetry — instrument một lần, gửi data đến bất kỳ backend nào."

Mục tiêu chương này: Hiểu instrumentation là gì, tại sao OpenTelemetry ra đời, kiến trúc OTel, và cách ShopVN chuyển từ manual instrumentation sang OTel trong vài dòng code.

ShopVN evolution: Refactor từ v4 (manual tracing/logging/metrics) sang v5 (OpenTelemetry tự động).

1. Instrumentation là gì?

Instrumentation = quá trình thêm code/config để ứng dụng phát ra (emit) telemetry data — logs, metrics, traces.

Ẩn dụ: Nhà máy sản xuất

Nhà máy không có camera, đồng hồ, sensor = sản xuất “mù” — không biết đang chạy tốt hay dở, bao nhiêu sản phẩm/giờ, máy nào hỏng.

Gắn sensor (instrumentation) vào nhà máy: camera ở mỗi khâu, sensor đo nhiệt độ, đếm sản phẩm → biết mọi thứ đang xảy ra.

Instrumentation cho ứng dụng cũng vậy — “gắn sensor” để emit logs, metrics, traces.

Hai loại Instrumentation

LoạiCách hoạt độngƯu điểmNhược điểmVí dụ
AutoAgent/library tự động thu thập mà không sửa codeSetup nhanh, không cần developerThiếu business context (không biết order_id, user_id)Dynatrace OneAgent, OTel auto-instrumentation
ManualDeveloper thêm code SDK vào ứng dụngCustom, chi tiết, có business contextMất time, cần developerOTel SDK .start_span(), custom metrics

Best practice: Dùng cả hai. Auto cho baseline (HTTP requests, DB queries, framework operations). Manual cho business logic (order created, payment processed, user registered).

2. Tại sao OpenTelemetry ra đời?

2.1 Vấn đề: Vendor Lock-in

Trước OTel, mỗi vendor có SDK riêng:

Dùng Dynatrace? → Dynatrace OneAgent SDK → Code gắn chặt vào Dynatrace
Dùng Datadog?   → Datadog APM SDK        → Code gắn chặt vào Datadog
Dùng Jaeger?    → Jaeger SDK              → Code gắn chặt vào Jaeger

Đổi vendor? → Phải SỬA TOÀN BỘ instrumentation code 💀
   50 services × hàng trăm dòng instrumentation code → tuần/tháng công sức

2.2 Giải pháp: OpenTelemetry — Một chuẩn cho tất cả

OpenTelemetry (OTel) là tiêu chuẩn mở, vendor-neutral, do CNCF quản lý. Ý tưởng đơn giản: tách biệt việc thu thập data khỏi việc phân tích data.

                                            ┌── Dynatrace
App ──→ OTel SDK ──→ OTel Collector ──→     ├── Datadog
        (thu thập)    (xử lý/chuyển tiếp)   ├── Jaeger
                                            ├── Grafana
                                            └── Elasticsearch

Đổi vendor? → Chỉ đổi EXPORTER config
             → KHÔNG SỬA app code! 🎉

3. Kiến trúc OpenTelemetry

3.1 Tổng quan components

┌─────────────────────────── YOUR APP ──────────────────────────┐
│                                                                │
│  ┌──────┐    ┌──────┐    ┌──────────┐                         │
│  │ API  │───►│ SDK  │───►│ Exporter │──── gửi data ra ngoài  │
│  └──────┘    └──────┘    └──────────┘                         │
│                                                                │
│  API = Interface (bạn gọi vào)                                │
│  SDK = Implementation (xử lý bên trong)                       │
│  Exporter = Gửi data đến Collector hoặc trực tiếp backend    │
└───────────────────────────────┬────────────────────────────────┘
                                │
                                ▼
                    ┌───────────────────────┐
                    │    OTel Collector      │
                    │                        │
                    │  ┌──────────────────┐ │
                    │  │   Receivers      │ │ ← Nhận data từ apps (OTLP)
                    │  ├──────────────────┤ │
                    │  │   Processors     │ │ ← Filter, batch, enrich, sample
                    │  ├──────────────────┤ │
                    │  │   Exporters      │ │ ← Gửi đến 1 hoặc NHIỀU backends
                    │  └──────────────────┘ │
                    └───────────────────────┘
                         │        │        │
                         ▼        ▼        ▼
                     Dynatrace  Jaeger   Prometheus

Giải thích từng component:

ComponentVai tròẨn dụ
APIInterface chuẩn, không đổi giữa các versionỔ cắm điện — tiêu chuẩn, mọi thiết bị đều dùng được
SDKImplementation thực tế — tạo spans, collect metricsDây điện bên trong tường
ExporterGửi data ra ngoài appPhích cắm kết nối đến thiết bị cụ thể
CollectorTrạm trung chuyển — nhận, xử lý, gửi tiếpTrạm biến áp điện — nhận từ nhiều nguồn, phân phối đến nhiều nơi

3.2 Tại sao cần Collector (không gửi thẳng từ App đến Backend)?

  1. Offload processing — App chỉ emit data, không phải lo batch/filter/retry
  2. Multi-backend — Gửi data đến Dynatrace VÀ Jaeger cùng lúc
  3. Centralized config — Đổi routing, filter ở 1 chỗ thay vì sửa 50 services
  4. Buffer & retry — Nếu backend down tạm, Collector buffer data và retry

7. Proprietary vs OpenTelemetry

Tiêu chíProprietary (Dynatrace/Datadog Agent)OpenTelemetry
SetupCực dễ — install agent, doneCần config SDK + Collector
Auto-instrumentation depthRất sâu (code-level, AI-powered)Tốt nhưng không deep bằng
Vendor lock-inCó — đổi vendor = đổi agentKhông — đổi exporter config
AI featuresDavis AI, Watchdog (built-in)Không có (cần backend cung cấp)
CostLicense feeFree (open source)
Best forEnterprise nhanh chóngMulti-vendor, flexibility

Thực tế phổ biến: Dùng OTel SDK + export đến Dynatrace/Datadog → Được cả hai: không lock-in + powerful analysis backend.

ArchitectureApp (API→SDK→Exporter) → Collector (Receive→Process→Export) → Backends
CollectorTrạm trung chuyển: filter, batch, multi-backend export

OneAgent vs OTel — Khi nào dùng gì?

  • OneAgent: Mạnh hơn OTel về auto-discovery (Smartscape, Davis AI) — recommended nếu full Dynatrace.
  • OTel SDK: Vendor-neutral — dùng khi muốn gửi data tới nhiều backends, hoặc khi không muốn install agent.
  • Kết hợp: OneAgent + OTel custom spans — lấy best of both worlds.

Quan sát ở terminal server: OTel tự động export spans dưới dạng JSON — bao gồm cả spans bạn KHÔNG VIẾT CODE cho (Flask auto-instrumentation tạo root span cho mỗi route).

Mapping lý thuyết → code:

  • Auto-instrumentation (phần 1) → FlaskInstrumentor().instrument_app(app): 1 dòng, tự trace mọi routes
  • OTel SDK (phần 3.1) → TracerProvider, BatchSpanProcessor, ConsoleSpanExporter setup
  • Custom spans (phần 4.2) → tracer.start_as_current_span("check_inventory"): business logic spans
  • Semantic Conventions (phần 6) → "http.method", "db.system", "db.operation" — tên chuẩn OTel
  • Resource (phần 3.1) → Resource.create({"service.name": "order-service", ...})

So sánh code v4 vs v5:

  • v4: ~100 dòng cho class Span, class Trace, print_waterfall()
  • v5: Bỏ hết → thay bằng FlaskInstrumentor() + tracer.start_as_current_span()
  • v5: Context propagation tự động — không cần truyền trace object qua parameters

Thử nghiệm nâng cao

Đổi ConsoleSpanExporter → OTLPSpanExporter(endpoint="http://localhost:4317") rồi chạy Jaeger bằng Docker → thấy traces trên Jaeger UI. Đây chính là benefit của OTel: đổi exporter, không sửa business code.
