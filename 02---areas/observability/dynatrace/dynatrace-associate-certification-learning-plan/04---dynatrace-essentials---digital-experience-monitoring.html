﻿# Digital Experience Monitoring (DEM)

Bài học trước đã giới thiệu Application trong Dynatrace — front-end mà users tương tác. Bài này đi sâu vào cách Dynatrace monitor trải nghiệm người dùng thực tế: từ browser đến mobile, từ real users đến simulated users.

Mục Tiêu Bài Học

  1. Mô tả mục đích và các thành phần của Digital Experience Monitoring (DEM)
  2. Giải thích cách DEM cải thiện user experience qua việc xác định performance bottlenecks, downtime, và usability issues
  3. Cấu hình DEM features: Real User Monitoring, Synthetic Monitoring

Phần 1: Real User Monitoring (RUM) ⭐

RUM là gì?

RUM (Real User Monitoring) = đo lường performance của front-end application từ góc nhìn người dùng thực (real users). Dynatrace capture mọi tương tác thực tế: page loads, clicks, errors, load times — tất cả từ browser/mobile của người dùng.

TIP

Ví von cửa hàng kính thiên văn:
RUM giống như bạn đứng quan sát khách hàng trong cửa hàng:

  • Khách mất bao lâu để được phục vụ?
  • Khách có tìm được sản phẩm cần không?
  • Quá trình checkout có mượt không hay bị stuck?
  • Khách hài lòng hay rời đi với sự thất vọng?

RUM đo lường gì?

MetricMô tảVí dụ
Visually Complete TimeThời điểm mà mọi thứ nhìn thấy trên màn hình đã load xongYouTube: video + title + sidebar load xong → “visually complete”, dù comments vẫn đang load
Error RateTỉ lệ lỗi xảy raBroken images, 404 Not Found, 500 Server Error
Apdex ScoreĐiểm đánh giá user experience (0 → 1)0.92 = excellent, 0.65 = needs improvement

Apdex — Application Performance Index ⭐

Apdex là hệ thống chuẩn quốc tế (không riêng Dynatrace) để đo mức độ hài lòng của users dựa trên response time:

Response TimePhân loạiÝ nghĩa
0 – 3 giây🟢 SatisfiedUser hài lòng
3 – 15 giây🟡 ToleratingChấp nhận được nhưng không lý tưởng
> 15 giây hoặc error🔴 FrustratedUser thất vọng

Điểm quan trọng:

  • Apdex score tối đa = 1.0 (100% satisfied). Càng gần 1 → UX càng tốt
  • Error cũng = Frustrated: trang load trong 0.5 giây nhưng hiện 404 → vẫn bị tính là Frustrated
  • Thresholds có thể tùy chỉnh: VD login page cần load < 2 giây thay vì 3 giây mặc định

IMPORTANT

Để tùy chỉnh Apdex cho từng user action cụ thể, action đó phải được đánh dấu là Key User Action trước. Sẽ nói ở phần sau.

Cách RUM Hoạt Động — Auto Injection ⭐

BƯỚC 1: User nhập URL → Browser gửi request đến Web Server

BƯỚC 2: Web Server nhận request → xây dựng HTML page
         ↓
         OneAgent CAN THIỆP tại đây:
         "Chèn thêm JavaScript Snippet vào HTML trước khi trả về!"
         ↓
BƯỚC 3: Web Server trả về HTML + JavaScript Snippet cho Browser

BƯỚC 4: Browser load page + JavaScript Snippet tự động chạy
         → Thu thập: page load time, user clicks, errors, XHR calls
         → Gửi data về Dynatrace platform

→ Toàn bộ quá trình này gọi là "AUTO INJECTION"

TIP

Ví von nhà hàng:

  • Bình thường: bạn gọi món, nhân viên mang ra → xong
  • Có RUM: khi mang món ra, nhân viên kèm theo phiếu khảo sát (JavaScript Snippet)
  • Phiếu tự động thu thập: thời gian chờ, đồ ăn có đúng không, mức hài lòng
  • Khách “điền” phiếu (browser gửi data) → quản lý xem kết quả trên Dynatrace

OneAgent cần ở Full-stack mode trên web server để Auto Injection hoạt động.

Data trong Dynatrace Web Applications

Sau khi RUM thu thập data, mọi thứ được tổ chức vào Application entity trong Dynatrace. Traffic được route đến đúng application bằng Detection Rules (dựa trên URL/domain).

Data bổ sung Dynatrace capture

DataMục đích
IP AddressXác định location (có thể mask cho privacy)
Browser TypeChrome, Edge, Safari, Firefox…
User TypeReal user, Synthetic, Bot
OS & DeviceWindows/Mac/Linux, Desktop/Mobile
Screen ResolutionKích thước màn hình

Ứng dụng thực tế: Nếu lỗi chỉ xảy ra với users dùng Internet Explorer 7 → filter browser trong Dynatrace → xác định ngay lỗi chỉ ảnh hưởng browser cũ → quyết định có cần support browser đó nữa không.

Phần 2: Agentless RUM

Khi nào dùng?

Khi KHÔNG thể cài OneAgent trên web server:

  • Không có quyền truy cập server
  • Công nghệ server không hỗ trợ auto-injection
  • Chính sách bảo mật cấm cài phần mềm trên server

Cách hoạt động

Thay vì OneAgent tự inject → bạn thủ công chèn JavaScript Snippet (do Dynatrace cung cấp) vào từng page cần monitor.

Auto Injection (có OneAgent):
  OneAgent tự inject JS snippet vào MỌI page → tự động

Agentless RUM (không có OneAgent):
  Dev/Ops thủ công chèn JS snippet vào TỪNG page → manual
  Page nào KHÔNG có snippet → KHÔNG được monitor

NOTE

Data thu thập KHÔNG khác biệt giữa Auto Injection và Agentless RUM. Cùng page load times, user actions, Apdex score, errors. Chỉ khác cách chèn code, không khác data output.

Phần 3: User Actions ⭐

Các loại User Actions

User actions = tương tác giữa user và web app mà trigger request đến server. Dynatrace track 3 loại:

LoạiMô tảVí dụCách capture
Load ActionsFull page loadMở homepage, login page, search resultsTự động
XHR ActionsPhần page cập nhật KHÔNG refresh toàn bộ (Ajax)Apply filter, click “Next” trong gallery, live searchTự động
Custom ActionsActions custom track thủ côngPDF download, business-specific eventThủ công qua JS API

Custom Actions & OpenKit

  • Custom Actions: Dùng Dynatrace JavaScript API để define actions mà Dynatrace không tự capture
  • OpenKit: Package cho thick clients (desktop apps) không chạy trong browser — dùng Java/.NET/C để capture sessions
  • Setup thường do development team phối hợp với application team

Key User Actions ⭐

Đánh dấu actions quan trọng thành Key User Actions để:

Lợi íchChi tiết
Custom ApdexTùy chỉnh Apdex thresholds riêng (VD: login page phải < 2s)
DashboardThêm vào dashboards để monitor liên tục
Long-term storageLưu data lâu hơn actions thường

WARNING

Key User Action KHÔNG retroactive: Chỉ actions sau khi đánh dấu mới được enhanced tracking. Actions trước đó không bị ảnh hưởng.

Tools phân tích sâu

ToolMô tả
Waterfall AnalysisSequence loading của page elements (scripts, images, CSS). Dựa trên W3C timing standards. Chỉ ra chính xác element nào chậm
Error AnalysisPhân tích JavaScript errors và request errors gắn với user actions cụ thể

Phần 4: User Sessions ⭐

User Session là gì?

User Session = chuỗi tương tác mà một user thực hiện trong suốt một lần visit ứng dụng.

Một session capture:

  • Page Loads, Payments, Errors, Navigation
  • Metadata: browser, OS, device, screen resolution, location
  • User Tags (username, email) — nếu được cấu hình

User Tagging

Dynatrace có thể tag session với identifier (username, email). VD: trang hiển thị “Welcome Ryan” → cấu hình Dynatrace nhận diện “Ryan” là user → liên kết behavior với performance issues.

Setup thường do người quen thuộc với application code thực hiện.

Phân Tích User Behavior

Phân tíchCâu hỏi trả lời
Entry/Exit pointsUsers vào từ đâu? Rời ở trang nào? (VD: rời ở failed search → UX issue)
Bounce RateBao nhiêu % users chỉ xem 1 page rồi rời đi? (thường do load chậm hoặc UX kém)
User PathsUsers có follow expected flow không? (browse → cart → checkout → payment)

Conversion Goals

Dynatrace cho phép define conversion goals — sự kiện biểu thị session thành công:

Loại goalVí dụ
Visit specific pageUser đến trang “Payment Complete”
Number of actionsUser thực hiện ≥ 5 actions
Time on siteUser ở lại ≥ 3 phút
Specific user actionUser click “Purchase” (phổ biến nhất)

NOTE

  • Conversion goal mất khoảng 30 phút để hiển thị kết quả
  • Session phải completed mới tính cho conversion goal

Khi Nào Session Kết Thúc? ⭐

Điều kiệnChi tiết
35 phút không hoạt độngUser rời browser mà không đóng (idle timeout)
Đóng cửa sổ browserĐóng window (đóng tab KHÔNG kết thúc session)
8 giờ liên tụcGiới hạn tối đa dù user vẫn đang active

JavaScript API calldtrum.endSession() — kết thúc session bằng code (VD: khi user logout)

Licensing & Privacy

Licensing:

  • Mỗi user session thường tiêu 1 license unit
  • Bounce sessions (user chỉ load 1 page rồi rời) → thường KHÔNG tính license
  • Chi tiết licensing tùy theo hợp đồng

Privacy & Data Masking:

  • Dynatrace có thể mask: email, IP address, physical location
  • “Masked” trong session = data bị ẩn theo policy hoặc bạn không có permission

Phần 5: Synthetic Monitoring ⭐

Synthetics là gì?

Synthetic Monitoring = mô phỏng user truy cập website để monitor availability và performance — kể cả khi không có real users online.

TIP

Ví dụ: Website trường học không có traffic lúc 2 giờ sáng. Nếu site sập lúc đó → sáng mới biết. Với Synthetics → “user giả” vẫn test site 24/7 → alert ngay khi có vấn đề.

So Sánh RUM vs Synthetics

RUMSynthetics
UsersReal usersSimulated (giả lập)
Khi nào chạyChỉ khi có real traffic24/7 theo schedule
Cần OneAgent?✅ Có (Full-stack trên web server)❌ Không — chạy từ Dynatrace cloud
Phát hiệnIssues ảnh hưởng real usersIssues proactively (trước khi users bị ảnh hưởng)
Dùng choHiểu real UXTest availability, performance baselines

3 Loại Synthetic Monitors ⭐

LoạiMô tảUse caseVí dụ
Browser MonitorLoad 1 page đơn lẻBasic uptime & performance checkCheck homepage load OK
Browser ClickpathMô phỏng full user journey (nhiều steps)Test workflow end-to-endLogin → Search → Add to cart → Checkout
HTTP MonitorCheck API endpoint/URL (không load visual page)API health checkGửi GET request đến /api/health

NOTE

Browser Clickpath cần cài Dynatrace Synthetic Recording extension cho Chrome để record các bước.

Cấu hình Synthetics

  1. Chọn loại monitor (browser, clickpath, HTTP)
  2. Nhập URL cần monitor
  3. Record actions (cho clickpath)
  4. Chọn test locations (US, Europe, Asia…)
  5. Set tần suất (every 5 min, 15 min, hourly…)
  6. Xác nhận và lưu

Sau khi setup, cần 15–30 phút để synthetic monitor active (đặc biệt clickpaths phức tạp).

Phần 6: Session Replay

Session Replay là gì?

Session Replay = tái tạo trực quan hành trình user trong ứng dụng — KHÔNG ghi video. Đây là reconstruction (dựng lại) dựa trên collected data.

Session Replay KHÔNG phải:
  ❌ Screen recording / video capture
  ❌ Lưu trữ hình ảnh/video từ màn hình user

Session Replay LÀ:
  ✅ Reconstruction dựa trên DOM changes + user interactions
  ✅ Hiển thị layout page, clicks, scrolls, form interactions
  ✅ Security-first: không lưu sensitive data

Privacy & Data Masking

Mặc định, Session Replay mask sensitive data:

  • Text fields, form content, images, dropdown values → ẩn đi
  • Layout page vẫn hiển thị nhưng content bị masked
  • Passwords LUÔN masked, không thể unmask

Có thể unmask một số elements cụ thể (VD: product images, tên sản phẩm) — nhưng cần cấu hình rõ ràng.

Tại sao dùng Session Replay?

Lý doChi tiết
Troubleshoot frontend issuesXem chính xác user đã làm gì trước khi error xảy ra
Reproduce hard-to-find bugs”User click Buy nhưng không xảy ra gì” → replay để thấy
Improve support responseHiểu vấn đề nhanh hơn mà không cần hỏi user mô tả lại
Maintain privacyFull visibility mà vẫn protect sensitive data

Knowledge Check

Q1: What does Dynatrace Real User Monitoring (RUM) primarily help you understand?

  • A. How many users visit your app per month.
  • B. The experience and performance from the perspective of real users.
  • C. The financial cost of server uptime.
  • D. How much storage is available on your servers.

Đáp án: B — The experience and performance from the perspective of real users (Trải nghiệm và hiệu suất từ góc nhìn của người dùng thực).

Tại sao B đúng?

RUM (Real User Monitoring) là về việc đo lường trải nghiệm thực tế của users khi họ tương tác với ứng dụng. Cụ thể, RUM capture:

  • Page load times: trang load mất bao lâu từ góc nhìn user
  • User actions: clicks, scrolls, form submissions — mỗi action có response time
  • Errors: JavaScript errors, HTTP errors (404, 500) ảnh hưởng trải nghiệm
  • Apdex score: tổng hợp thành điểm hài lòng (Satisfied/Tolerating/Frustrated)

Keyword quan trọng: “perspective of real users” — RUM thu thập data từ browser thực của user (không phải từ server logs hay simulated tests).

Giải thích các lựa chọn sai:

  • A. How many users visit per month: Đây là traffic analytics (Google Analytics), không phải mục đích chính của RUM. RUM có thể cho thấy số sessions, nhưng mục đích chính là đo lường trải nghiệm, không phải đếm users.
  • C. Financial cost of server uptime: Chi phí vận hành server thuộc về billing/finance, hoàn toàn ngoài phạm vi RUM. RUM không tính tiền cho bạn.
  • D. Storage available on servers: Dung lượng lưu trữ thuộc về infrastructure monitoring (Host metrics), không phải user experience monitoring.

💡 Lời khuyên thi: RUM = Real User + Experience/Performance. Bất kỳ đáp án nào nói về server metrics, financial costs, hay storage → sai. RUM chỉ quan tâm đến user-facing experience.

Q2: When would you use Agentless RUM instead of the default OneAgent setup?

  • A. When you want to track mobile app usage.
  • B. When your application uses API endpoints.
  • C. When you cannot install OneAgent on the web server.
  • D. When your application doesn’t use JavaScript.

Đáp án: C — When you cannot install OneAgent on the web server (Khi không thể cài OneAgent trên web server).

Tại sao C đúng?

Agentless RUM tồn tại cho một tình huống cụ thể: khi bạn không thể hoặc không được phép cài OneAgent trên web server. Các lý do phổ biến:

  1. Không có quyền truy cập server (VD: dùng third-party hosting service)
  2. Chính sách bảo mật cấm cài phần mềm trên server (regulated industries: banking, healthcare)
  3. Công nghệ server không hỗ trợ OneAgent auto-injection (VD: một số static site generators, CDN-only hosting)

Khi đó, thay vì OneAgent tự inject JavaScript → bạn thủ công chèn JavaScript Snippet của Dynatrace vào HTML pages. Data thu thập được hoàn toàn giống nhau — chỉ khác cách inject.

Giải thích các lựa chọn sai:

  • A. Track mobile app usage: Mobile monitoring dùng Mobile RUM SDK (cài trong app code), không phải Agentless RUM. Agentless RUM chỉ dành cho web applications.
  • B. Application uses API endpoints: API endpoints được monitor bằng Service-level monitoring hoặc HTTP Synthetic Monitors, không phải Agentless RUM. RUM (cả auto và agentless) monitor user-facing web pages, không phải APIs.
  • D. App doesn’t use JavaScript: Mâu thuẫn — Agentless RUM dùng JavaScript Snippet để thu thập data! Nếu app không hỗ trợ JavaScript → Agentless RUM cũng không hoạt động.

💡 Lời khuyên thi: Agentless RUM = backup plan khi không cài được OneAgent. Từ khóa: “cannot install”, “no access”, “restrictions”. Output data hoàn toàn giống Auto Injection.

Q3: Which of the following is an example of a user action in Dynatrace?

  • A. Updating firewall rules.
  • B. Installing the OneAgent.
  • C. Clicking a “Buy Now” button.
  • D. Adjusting the screen brightness.

Đáp án: C — Clicking a “Buy Now” button (Click nút “Buy Now”).

Tại sao C đúng?

User action trong Dynatrace là tương tác giữa user và web application mà trigger một request đến web server. Clicking “Buy Now” là ví dụ hoàn hảo:

  1. User click nút “Buy Now” trên browser
  2. Browser gửi request đến web server (HTTP POST /api/orders)
  3. Server xử lý request (tạo order, charge payment)
  4. Dynatrace capture toàn bộ: response time, success/failure, code-level trace

Đây là một Load Action hoặc XHR Action tùy thuộc vào việc page có reload hay không.

Giải thích các lựa chọn sai:

  • A. Updating firewall rules: Đây là hành động admin/operator trên infrastructure — không phải tương tác user với web app. Firewall changes không trigger request đến application server.
  • B. Installing OneAgent: Đây là hành động setup/deployment — diễn ra trên server, không phải trong browser. OneAgent installation không phải user action.
  • D. Adjusting screen brightness: Đây là hành động local trên device — không trigger bất kỳ request nào đến web server. Dynatrace không capture local device settings.

💡 Lời khuyên thi: User action = user tương tác với WEB APP → trigger request đến server. Bất kỳ thứ gì xảy ra ngoài browser (infra config, local device settings, server-side actions) → KHÔNG phải user action.

Q4: What does a user session in Dynatrace represent?

  • A. A single HTTP request to the server.
  • B. A list of all users active on the app at once.
  • C. A series of user interactions during one visit to the app.
  • D. A backup of the user’s browser data.

Đáp án: C — A series of user interactions during one visit to the app (Chuỗi tương tác của user trong một lần visit ứng dụng).

Tại sao C đúng?

User session = toàn bộ hành trình của MỘT user trong MỘT lần visit ứng dụng. Ví dụ một session điển hình:

Session bắt đầu: User mở telescope-store.com
  → Load homepage (Load Action)
  → Click "Telescopes" (XHR Action)
  → Search "beginner telescope" (XHR Action)
  → Click product "Smart Telescope S50" (Load Action)
  → Click "Add to Cart" (XHR Action)
  → Click "Checkout" (Load Action)
  → Enter payment info (Custom Action tracked)
  → Click "Pay Now" (Load Action) → 404 Error!
Session kết thúc: User đóng browser window

Dynatrace capture TẤT CẢ actions trên thành 1 session, kèm metadata: browser, OS, device, location, user tag (nếu có). Session kết thúc khi: 35 phút idle, đóng window, 8 giờ max, > 200 actions, hoặc dtrum.endSession().

Giải thích các lựa chọn sai:

  • A. Single HTTP request: Một HTTP request chỉ là một phần nhỏ trong session. Một session thường có hàng chục hoặc hàng trăm requests. Request đơn lẻ chỉ là user action, không phải session.
  • B. List of all users active at once: Đây mô tả concurrent users hoặc active sessions overview — không phải definition của “a user session”. Một session chỉ thuộc về MỘT user, không phải danh sách nhiều users.
  • D. Backup of browser data: Dynatrace KHÔNG backup browser data. Session chỉ chứa monitoring data (performance, actions, errors), không phải bookmarks, history, hay local storage.

💡 Lời khuyên thi: Session = MỘT user + MỘT visit + CHUỖI interactions. Keyword: “series of interactions during one visit”. Session ≠ single request, ≠ multiple users, ≠ data backup.

Q5: What is the main purpose of Dynatrace Synthetic Monitoring?

  • A. To track storage capacity.
  • B. To simulate user behavior and test availability/performance.
  • C. To upgrade server hardware.
  • D. To export business analytics.

Đáp án: B — To simulate user behavior and test availability/performance (Mô phỏng hành vi user và test availability/performance).

Tại sao B đúng?

Synthetic Monitoring chạy “user giả lập” (bots) từ các locations trên toàn thế giới để:

  1. Test availability (uptime): Site có đang up không? Có accessible từ US, EU, Asia không?
  2. Test performance: Homepage load trong bao lâu? Login flow mất mấy giây?
  3. Proactive detection: Phát hiện vấn đề TRƯỚC KHI real users bị ảnh hưởng

Synthetics chạy 24/7 theo schedule — kể cả 2 giờ sáng khi không có real traffic. Nó bổ trợ cho RUM: RUM cho biết real users đang trải nghiệm gì, Synthetics đảm bảo app luôn available và performant.

Quan trọng: Synthetics KHÔNG cần OneAgent — mọi thứ chạy từ Dynatrace public/private locations.

Giải thích các lựa chọn sai:

  • A. Track storage capacity: Storage tracking thuộc infrastructure monitoring (Host metrics: disk usage, I/O). Synthetics không liên quan đến storage.
  • C. Upgrade server hardware: Upgrade hardware là hành động physical/manual do ops team thực hiện. Không có monitoring tool nào “upgrade hardware” — chúng chỉ observe và alert.
  • D. Export business analytics: Business analytics thuộc về business intelligence tools hoặc Dynatrace Business Events + DQL queries. Synthetics test technical performance, không export business data.

💡 Lời khuyên thi: Synthetics = Simulate + Test + Proactive. Phân biệt với RUM: RUM = real users (reactive), Synthetics = simulated users (proactive). Cả hai cùng tạo thành DEM (Digital Experience Monitoring).

Q6: What does Session Replay allow you to do in Dynatrace?

  • A. Watch recorded videos of users’ screens.
  • B. See a timeline of server performance.
  • C. Reconstruct a user’s experience based on their interactions.
  • D. Track financial transactions on the site.

Đáp án: C — Reconstruct a user’s experience based on their interactions (Tái tạo lại trải nghiệm user dựa trên interactions của họ).

Tại sao C đúng?

Session Replay tái tạo (reconstruct) hành trình user — KHÔNG ghi video. Cơ chế:

  1. Dynatrace capture DOM changes + user interactions (clicks, scrolls, form inputs) trong session
  2. Khi bạn “replay” → Dynatrace dựng lại (reconstruct) page layout + user actions từ data đã thu thập
  3. Bạn thấy: page layout, nút nào user click, form nào được điền, element nào failed to load

Ưu điểm so với video recording:

  • Privacy: Không lưu hình ảnh/video thực → sensitive data được protect
  • Storage: Nhẹ hơn nhiều so với video files
  • Security: Passwords LUÔN masked. Text fields, form content masked by default

Giải thích các lựa chọn sai:

  • A. Watch recorded videos: SAI và dễ nhầm! Session Replay KHÔNG phải video recording. Nó là reconstruction từ data, không phải screen capture. Không có video file nào được lưu trên server.
  • B. Timeline of server performance: Server performance timeline thuộc Service-level monitoring hoặc Host-level monitoring. Session Replay focus vào user-side experience trong browser, không phải server metrics.
  • D. Track financial transactions: Financial transaction tracking thuộc business analytics hoặc payment service monitoring. Session Replay hiển thị hành vi user (clicks, navigation), không track financial data.

💡 Lời khuyên thi: Session Replay = RECONSTRUCT (tái tạo), KHÔNG phải RECORD (ghi hình). Đây là điểm hay gài bẫy! Keyword: “reconstruct based on interactions”. Nhớ: sensitive data luôn masked, passwords NEVER visible.
