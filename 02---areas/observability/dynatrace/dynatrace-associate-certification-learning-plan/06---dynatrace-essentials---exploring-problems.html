﻿# Exploring Problems — Phát Hiện & Phân Tích Sự Cố

Vấn đề không phải lúc nào cũng bắt đầu bằng crash — chúng thường bắt đầu từ những dấu hiệu nhỏ mà con người khó nhận ra. Dynatrace phát hiện anomalies (bất thường), tự động tạo problems, nhóm các anomalies liên quan, và chỉ ra root cause — tất cả nhờ Dynatrace Intelligence (Davis AI).

Mục Tiêu Bài Học

  1. Xác định cách problems được trigger: anomaly detection, dynamic baselines, threshold breaches
  2. Giải thích vai trò của Dynatrace Intelligence trong root cause analysis
  3. Thực hành troubleshooting cơ bản trong Dynatrace

Phần 1: Anomaly Detection — Phát Hiện Bất Thường ⭐

Anomaly là gì?

Anomaly = khi một metric vượt qua threshold (ngưỡng) đã định — nghĩa là hệ thống không còn hoạt động bình thường.

Khi anomaly được phát hiện, Dynatrace sẽ:

  • Tạo problem mới, HOẶC
  • Gắn anomaly vào problem đã tồn tại (nếu liên quan)

Dynatrace sử dụng 2 loại thresholds để phát hiện anomalies:

1. Static Thresholds — Ngưỡng Cố Định

Giá trị cố định — nếu metric vượt qua → anomaly.

Ví dụ: Static threshold CPU = 90%

  Thời gian →
  CPU: 55% → 65% → 85% → 88% → 95%
                                    ↑
                              VƯỢT NGƯỠNG 90%!

  Nhưng Dynatrace KHÔNG trigger problem ngay lập tức!
  → Chờ xác nhận: cần 3 lần breach trong 5 phút
  → Nếu condition VẪN tiếp diễn → tạo Problem
  → Tránh false alarms do spike ngắn

Đặc điểm Static Thresholds:

Đặc điểmChi tiết
Giá trịCố định, do admin set (VD: CPU > 90%, disk > 95%)
Áp dụng mặc định choInfrastructure metrics: CPU%, memory, garbage collection, disk
Ưu điểmĐơn giản, dễ hiểu, rõ ràng
Nhược điểmKhông linh hoạt — cùng 1 ngưỡng cho mọi service/host

2. Auto-Adaptive Thresholds (Baselines) — Ngưỡng Tự Động ⭐⭐

Dynatrace HỌC hành vi bình thường của mỗi service theo thời gian → tự tạo baseline riêng cho từng service/app.

TIP

Ví von nhà hàng:

  • Fast-food: chờ 20 phút → BẤT THƯỜNG (bình thường chỉ 5 phút)
  • Nhà hàng sang: chờ 20 phút → BÌNH THƯỜNG (expected)

Cùng 20 phút, nhưng baseline khác nhau → kết luận khác nhau!

Dynatrace cũng vậy — mỗi service có baseline riêng, không áp dụng 1 ngưỡng cho tất cả.

Cách Baselines hoạt động

Service "LoginService" có baseline response time = 1 giây

  Response time bình thường: dao động nhẹ 0.8s - 1.2s (OK)
  
  Đột nhiên tăng: 1s → 2s → 3s → giữ ở 3s
                         ↑
                   VƯỢT 50% trên baseline (1s + 50% = 1.5s)
                   
  Dynatrace: "Response time đã vượt baseline 50% và VẪN duy trì"
            → Tạo Problem!

Quy tắc 50% ⭐

IMPORTANT

Mặc định, Dynatrace coi anomaly là đáng kể khi metric lệch ÍT NHẤT 50% so với baseline.

  • Baseline = 1s → anomaly khi > 1.5s
  • Baseline = 2% failure rate → anomaly khi > 3%

Ngưỡng 50% này có thể tùy chỉnh trong Anomaly Detection Settings.

Baselines được tính như thế nào?

Giai đoạnMô tả
2 giờ đầuBaseline ban đầu được thiết lập
Hàng ngàyBaseline được refine (tinh chỉnh)
~1 tuầnBaseline “trưởng thành” — phản ánh đúng hành vi bình thường

So Sánh 2 Loại Thresholds ⭐

Static ThresholdsAuto-Adaptive Baselines
Giá trịCố định (VD: CPU > 90%)Tự học, tự điều chỉnh
Áp dụng choInfrastructure metrics (CPU, RAM, disk, GC)Response time, failure rate, traffic cho services & apps
Linh hoạtKhông — cùng ngưỡng cho mọi entityCó — mỗi entity có baseline riêng
False positivesNhiều hơn (spike ngắn có thể trigger)Ít hơn (hiểu seasonal patterns)
Cần cấu hìnhAdmin set thủ côngDynatrace tự learn (out of the box)

Phần 2: Problems — Sự Cố ⭐

Problem là gì?

Khi anomaly được detect → Dynatrace tạo Problem event. Problems được phân loại theo severity:

SeverityIcon ý nghĩaMô tảVí dụ
🔴 AvailabilityNghiêm trọng nhấtHost/service/synthetic KHÔNG availableHost down, synthetic check fail
🟠 ErrorLỗi tăngError rate tăng bất thườngHTTP 500 errors tăng từ 1% → 15%
🟡 SlowdownHiệu suất giảmPerformance degradationPage load tăng từ 2s → 8s
🔵 ResourceTài nguyênInfrastructure resource issuesCPU saturation, memory exhaustion
⚪ CustomTùy chỉnhUser-defined problemsBusiness rule violations, custom metric thresholds

NOTE

Ngoài problem events, Dynatrace còn có các event types khác không phải problems nhưng cung cấp thêm context:

  • Info events: Thông tin bổ sung
  • Monitoring unavailable: OneAgent mất kết nối
  • Process restart: Process khởi động lại
  • Deployment change: Phát hiện deployment mới

Các events này có thể xuất hiện BÊN TRONG problems như context bổ sung, nhưng không phải problem types.

Phần 3: Root Cause Analysis ⭐⭐

Nhóm Anomalies → Một Problem

Dynatrace KHÔNG chỉ phát hiện từng anomaly riêng lẻ — nó nhóm các anomalies liên quan vào MỘT problem duy nhất bằng cách sử dụng topology mapping (Smartscape).

VẤN ĐỀ THỰC TẾ:

  Database server: CPU 98% (Resource anomaly)
       ↓ ảnh hưởng
  App servers: Response time tăng 300% (Slowdown anomaly)
       ↓ ảnh hưởng
  Web servers: Page load chậm (Slowdown anomaly)
       ↓ ảnh hưởng
  Users: Apdex score giảm từ 0.9 → 0.4 (Slowdown anomaly)

MONITORING TRUYỀN THỐNG:
  → 4 alerts riêng biệt → 4 teams nhận alert → "ALERT STORM"
  → Mỗi team điều tra riêng → mất thời gian, trùng lặp effort

DYNATRACE:
  → 1 Problem duy nhất
  → Root cause: Database CPU saturation
  → Impact: App servers → Web servers → Users
  → Tất cả trong 1 màn hình, có cả root cause + impact analysis

TIP

Ví von dây điện đứt:
Sau bão lớn, cả khu phố mất điện. Bạn biết CÓ mất điện (hiển nhiên), nhưng tìm đúng chỗ dây bị đứt mới là khó. Dynatrace giống đội kỹ thuật điện: nhanh chóng trace theo topology → chỉ ra chính xác điểm gây sự cố.

Problem Analysis — Dynatrace cho biết gì?

Khi mở một problem, Dynatrace hiển thị:

Thông tinMô tả
WHO is impactedBao nhiêu users bị ảnh hưởng, applications nào
WHAT is impactedEntities nào bị ảnh hưởng: hosts, services, processes
WHY it happenedRoot cause được đề xuất (suggested root cause)
TimelineKhi nào vấn đề bắt đầu, diễn biến theo thời gian
Related eventsDeployment changes, process restarts, config changes trùng thời điểm

WARNING

Dynatrace đề xuất root cause — nhưng bạn vẫn cần verify bằng investigation. Root cause suggestion là starting point, KHÔNG phải kết luận cuối cùng.

Tools Phân Tích Problems

ToolKhi nào dùngMô tả
Failure Rate AnalysisError rate tăngPinpoint spikes trong application errors, phân tích error patterns
Response Time HotspotsSlowdownsHighlight services/methods gây chậm — drill down đến method level
Distributed TracesKhông biết delay ở đâuBreakdown request end-to-end → thấy service nào, method nào tốn thời gian
Business Impact AnalysisĐánh giá ảnh hưởngUsers nào bị ảnh hưởng, bao nhiêu sessions, impact đến conversion

Quy Trình Troubleshoot

1. FOLLOW THE RED LINES
   → Dynatrace vẽ đường đỏ chỉ về phía root cause
   → Bắt đầu từ đây

2. START BROAD
   → Xem tổng quan: entities nào bị ảnh hưởng?
   → Đừng đào sâu code ngay — nhìn bức tranh lớn trước

3. NARROW DOWN
   → Slowdown? → dùng Response Time Hotspots
   → Error tăng? → dùng Failure Rate Analysis
   → Không rõ? → dùng Distributed Traces

4. VERIFY ROOT CAUSE
   → Check suggested root cause entity
   → Kiểm tra timeline: deployment change? Config change?
   → Confirm và fix

Phần 4: Dynatrace Intelligence (Davis AI) ⭐⭐

Davis AI là gì?

Dynatrace Intelligence (thường gọi là Davis AI) là AI engine bên trong Dynatrace, hoạt động liên tục behind the scenes. Nó có 3 capabilities chính:

1. Causal Correlation Analysis (Phân tích nhân quả)

Khả năngChi tiết
Detect anomaliesPhát hiện bất thường từ metrics
Determine root causesXác định nguyên nhân gốc bằng topology traversal
Group related problemsGom anomalies liên quan vào 1 problem
Understand topologyHiểu dependency: service A gọi service B gọi DB C

2. Seasonal Baselines (Baselines theo mùa)

Khả năngChi tiết
Auto-adaptive thresholdsTự tạo và cập nhật baselines
Seasonal patternsHọc patterns theo giờ/ngày/tuần (VD: traffic cao lúc 9 AM, thấp lúc 3 AM)
Per-entity baselinesMỗi service/app có baseline riêng

3. Forecast Analysis (Dự đoán)

Khả năngChi tiết
Predict future valuesDự đoán giá trị metric trong tương lai
Dùng trongDashboards và Notebooks
Use caseCapacity planning, trend analysis

IMPORTANT

Không có Davis AI, Dynatrace chỉ là tool monitoring thông thường. Davis AI là thứ biến Dynatrace từ “hiển thị data” thành “hiểu data + tìm root cause + dự đoán trends”. Đây là key differentiator của Dynatrace.

Knowledge Check

Q1: True or False — Dynatrace creates a new problem every time an anomaly is detected, even if one already exists.

  • ❌ False

Đáp án: False — Dynatrace KHÔNG tạo problem mới mỗi khi phát hiện anomaly nếu đã có problem liên quan.

Tại sao False?

Đây là một trong những sức mạnh cốt lõi của Dynatrace: intelligent problem grouping. Cơ chế:

  1. Anomaly #1 được phát hiện → Dynatrace tạo Problem A
  2. Anomaly #2 được phát hiện → Dynatrace kiểm tra: “Anomaly này có liên quan đến Problem A không?”
    • Nếu CÓ (cùng dependency chain trong topology) → gắn Anomaly #2 vào Problem A
    • Nếu KHÔNG → tạo Problem B mới
  3. Kết quả: Nhiều anomalies liên quan → 1 Problem duy nhất thay vì “alert storm”

Ví dụ: Database CPU spike → gây slowdown ở 5 app services → gây 3 web applications chậm. Đó là 9 anomalies nhưng chỉ 1 Problem — vì tất cả đều liên quan qua topology.

Nếu Dynatrace tạo 9 problems riêng → mỗi team nhận alerts → tất cả điều tra riêng biệt → lãng phí effort. Grouping thành 1 problem → 1 root cause → giải quyết nhanh hơn.

💡 Lời khuyên thi: Nhớ: Anomalies ≠ Problems. Nhiều anomalies có thể thuộc 1 problem. Dynatrace nhóm anomalies liên quan bằng topology analysis.

Q2: Which of the following are common types of problems detected in Dynatrace? (Select all that apply)

  • ✅ Availability
  • ❌ Memory Saturation
  • ❌ Slow Loggings
  • ✅ Error Rate increase
  • ❌ CPU overheating

Đáp án: Availability, Error Rate increase

Tại sao Availability và Error Rate increase đúng?

Dynatrace có 5 problem severity types chính thức:

SeverityTrong danh sách?
🔴 Availability✅ Có
🟠 Error (bao gồm Error Rate increase)✅ Có
🟡 SlowdownKhông có trong danh sách
🔵 ResourceKhông có trong danh sách
⚪ CustomKhông có trong danh sách

Tại sao các lựa chọn khác sai?

  • Memory Saturation: Memory issues thuộc loại Resource problem, KHÔNG phải problem type riêng gọi là “Memory Saturation”. Dynatrace phát hiện memory issues nhưng classify dưới Resource severity.
  • Slow Loggings: Không tồn tại problem type này trong Dynatrace. Nếu login chậm → classify là Slowdown problem (performance degradation). “Slow Loggings” không phải thuật ngữ Dynatrace.
  • CPU overheating: “Overheating” là vấn đề hardware vật lý — Dynatrace monitor software metrics (CPU usage %), không monitor nhiệt độ vật lý. CPU usage cao → classify là Resource problem.

💡 Lời khuyên thi: Nhớ 5 problem types: A-E-S-R-C (Availability, Error, Slowdown, Resource, Custom). Bất kỳ thứ gì không match chính xác → sai. “Memory Saturation”, “CPU overheating” nghe hợp lý nhưng KHÔNG phải official problem types.

Q3: What is the key difference between static and auto-adaptive thresholds?

  • A. Static thresholds apply only to databases.
  • B. Auto-adaptive thresholds require manual configuration.
  • C. Auto-adaptive thresholds adjust based on normal behavior.
  • D. Static thresholds change daily.

Đáp án: C — Auto-adaptive thresholds adjust based on normal behavior (Ngưỡng tự thích ứng điều chỉnh dựa trên hành vi bình thường).

Tại sao C đúng?

Đây là sự khác biệt fundamenta giữa 2 loại:

  • Static: Giá trị CỐ ĐỊNH → CPU > 90% = anomaly, bất kể context. Admin phải tự set giá trị. Không thay đổi theo thời gian.
  • Auto-adaptive (Baselines): Dynatrace HỌC hành vi bình thường → tự tạo baseline → tự điều chỉnh. VD: Service A bình thường respond 1s → baseline = 1s. Service B bình thường respond 5s → baseline = 5s. Mỗi entity có baseline riêng.

Baselines còn hiểu seasonal patterns: traffic cao lúc 9 AM → baseline cao hơn. Traffic thấp lúc 3 AM → baseline thấp hơn. Cùng response time 3s có thể OK lúc peak hours nhưng anomalous lúc off-hours.

Giải thích các lựa chọn sai:

  • A. Static thresholds apply only to databases: Sai — Static thresholds áp dụng cho mọi infrastructure metrics (CPU, RAM, disk, GC), không chỉ databases. Services và applications cũng có thể dùng static thresholds (custom alerts).
  • B. Auto-adaptive require manual configuration: Ngược lại! Auto-adaptive baselines tự động (out of the box) — Dynatrace tự learn, tự tạo baselines. Static thresholds mới cần manual configuration (admin set giá trị).
  • D. Static thresholds change daily: “Static” có nghĩa là KHÔNG thay đổi (cố định). Nếu thay đổi hàng ngày → đó là auto-adaptive, không phải static.

💡 Lời khuyên thi: Static = FIXED, Auto-adaptive = LEARNS + ADJUSTS. Nhớ phân biệt: Static cho infrastructure, Baselines cho response time + failure rate + traffic.

Q4: By default, a metric must exceed the baseline by how much for Dynatrace to detect an anomaly?

  • A. 10%
  • B. 25%
  • C. 50%
  • D. 100%

Đáp án: C — 50%

Tại sao 50%?

Mặc định, Dynatrace coi anomaly là đáng kể khi metric lệch ít nhất 50% so với baseline đã thiết lập:

BaselineAnomaly threshold (50%)Nghĩa là
Response time: 1s> 1.5sAnomaly nếu response > 1.5 giây
Failure rate: 2%> 3%Anomaly nếu failure rate > 3%
Traffic: 1000 req/min< 500 hoặc > 1500 req/minAnomaly nếu traffic biến động > 50%

Tại sao 50% mà không phải con số khác?

  • 10% (A) → quá nhạy, sẽ tạo rất nhiều false positives vì mọi dao động nhỏ đều trigger
  • 25% (B) → vẫn khá nhạy, nhiều noise
  • 50% (C) → cân bằng giữa sensitivity và accuracy — đủ lớn để loại noise, đủ nhỏ để bắt real issues
  • 100% (D) → quá vô cảm, metric phải gấp đôi baseline mới trigger → bỏ lỡ nhiều issues thực

NOTE

Con số 50% có thể tùy chỉnh trong Anomaly Detection Settings — tăng lên cho systems ít critical (giảm noise), giảm xuống cho systems rất critical (tăng sensitivity).

💡 Lời khuyên thi: Con số 50% hay ra thi. Nhớ: default anomaly detection = metric vượt 50% so với baseline.

Q5: Which of the following best describes how Dynatrace groups and analyzes issues in your environment?

  • A. Each anomaly is treated separately and must be investigated manually.
  • B. Anomalies are grouped into problems, which Dynatrace Intelligence analyzes to identify potential root causes.
  • C. Dynatrace only uses static thresholds to detect anomalies.
  • D. Problems are detected only when users manually flag unusual behavior.

Đáp án: B — Anomalies are grouped into problems, which Dynatrace Intelligence analyzes to identify potential root causes.

Tại sao B đúng?

Đây mô tả chính xác workflow end-to-end của Dynatrace problem detection:

  1. Detect: Metrics breach thresholds (static hoặc baseline) → anomaly detected
  2. Group: Davis AI dùng topology analysis (Smartscape) để xác định anomalies nào liên quan → nhóm vào 1 problem
  3. Analyze: Davis AI traverse dependency chain → xác định root cause entity (entity gốc gây ra cascade)
  4. Present: Hiển thị problem với WHO/WHAT/WHY + suggested root cause

Toàn bộ quá trình diễn ra TỰ ĐỘNG nhờ Dynatrace Intelligence (Davis AI) — không cần human intervention để detect, group, hay suggest root cause.

Giải thích các lựa chọn sai:

  • A. Treated separately, investigated manually: Hoàn toàn ngược — Dynatrace nhóm anomalies liên quan (không tách riêng) và tự động phân tích (không cần manual). Approach manual investigation từng anomaly là cách monitoring truyền thống — chính vấn đề mà Dynatrace giải quyết.
  • C. Only uses static thresholds: Sai — Dynatrace dùng CẢ static thresholds VÀ auto-adaptive baselines. Baselines thậm chí là phần mạnh hơn của anomaly detection (keyword: “biggest strength”).
  • D. Only when users manually flag: Ngược lại — Dynatrace phát hiện problems TỰ ĐỘNG. Users không cần “flag” gì. Tự động detection 24/7 là core value proposition — nếu cần manual flagging thì không khác gì monitoring truyền thống.

💡 Lời khuyên thi: Workflow: Anomaly → Group → Problem → Root Cause — all automatic by Davis AI. Keywords: grouped, Dynatrace Intelligence, root causes, automatic.
