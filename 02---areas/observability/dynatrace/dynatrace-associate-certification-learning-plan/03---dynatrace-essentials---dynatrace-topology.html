﻿# Dynatrace Topology — Smartscape

Smartscape topology cho ta một bản đồ real-time tự động của toàn bộ môi trường — từ infrastructure đến services và mọi thứ ở giữa. Hiểu topology giúp ta thấy bức tranh tổng thể: mọi thứ được kết nối như thế nào → khi có sự cố thì biết ngay ở đâu và ảnh hưởng gì.

Mục Tiêu Bài Học

  1. Giải thích cách Dynatrace topology map và visualize các thành phần IT, relationships, và data flows
  2. Điều hướng Smartscape interface, khám phá các layers và cách nó visualize dependencies

Phần 1: Topology Là Gì?

Khái niệm

Topology trong computing = cách các devices/nodes (servers, services, databases…) được sắp xếp và kết nối với nhau. Nó là bản đồ hoặc biểu diễn trực quan về cách các thành phần giao tiếp.

TIP

Ví von máy in văn phòng:

  • Laptop, desktop, tablet đều kết nối đến 1 máy in chung → tạo thành một mạng đơn giản
  • Mỗi thiết bị gửi print jobs đến 1 điểm chung: máy in
  • Tương tự: web server, app server, database đều trao đổi data → tạo thành IT topology

Tại Sao Topology Quan Trọng?

Hiểu topology = biết mối quan hệ giữa các thành phần → troubleshoot nhanh hơn.

Ví dụ: máy in văn phòng hỏng

Không biết topology:
  → Kiểm tra từng máy tính một → mất thời gian
  → Không biết chúng có liên quan không

Biết topology:
  → Biết TẤT CẢ máy tính đều kết nối đến cùng 1 máy in
  → Máy in là COMMON POINT → kiểm tra máy in trước
  → Tìm ra vấn đề NHANH HƠN (kẹt giấy, cần restart...)

Áp dụng vào IT: Khi website chậm, topology cho biết:

  • Web server kết nối tới app server nào?
  • App server gọi database nào?
  • Database chạy trên host nào?
    → Biết dependency chain → tìm root cause nhanh hơn.

Phần 2: Dynatrace Smartscape ⭐

Smartscape Là Gì?

Smartscape = tính năng của Dynatrace tự động build bản đồ real-time, tương tác của toàn bộ môi trường. Nó:

  • Tự động discover tất cả components (không cần cấu hình thủ công)
  • Visualize cách services, processes, hosts kết nối với nhau
  • Cập nhật real-time khi môi trường thay đổi (deploy mới, scale up/down)
  • Full-stack visibility: từ user clicks → infrastructure, across hybrid/multi-cloud

5 Layers của Smartscape ⭐

        ┌─────────────────────────────┐
Layer 5 │      APPLICATIONS           │  ← Browser/Mobile (user-facing)
        │  (what users interact with)  │
        ├─────────────────────────────┤
Layer 4 │        SERVICES             │  ← Code-level: xử lý requests
        │  (handle requests via code) │     (login, payment, API calls)
        ├─────────────────────────────┤
Layer 3 │       PROCESSES             │  ← Programs đang chạy
        │  (running programs on hosts)│     (Java, nginx, node...)
        ├─────────────────────────────┤
Layer 2 │         HOSTS               │  ← Servers (physical/virtual/cloud)
        │  (servers with OneAgent)    │     có OneAgent cài đặt
        ├─────────────────────────────┤
Layer 1 │      DATA CENTERS           │  ← Vị trí vật lý/cloud region
        │  (physical/cloud locations) │     (AWS us-east-1, on-prem DC)
        └─────────────────────────────┘

Cùng đi sâu vào từng layer, từ dưới lên trên.

Layer 3: Processes & Process Groups ⭐

Process là gì?

Process = một chương trình đang chạy trên host. Nó là instance cụ thể của một chương trình đã được thực thi.

LoạiVí dụ
Foreground (trực tiếp)Chrome browser, desktop app
Background (nền)Web server (nginx, Apache), runtime (JVM, Node.js), container

Ví von: Process giống như nhân viên bán hàng trong cửa hàng kính thiên văn — mỗi người có trách nhiệm cụ thể (phục vụ khách, quản lý kho, thu ngân). Tương tự, mỗi process có nhiệm vụ riêng (deliver web page, xử lý login request…).

Process Group là gì? ⭐ HAY NHẦM

Process Group = nhóm logic các processes cùng loại, thường chạy trên nhiều hosts khác nhau, thực hiện cùng chức năng.

Ví dụ: Website có 3 web servers

Host A: nginx process (PID 1001) ─┐
Host B: nginx process (PID 2002) ─┼─→ Process Group "nginx"
Host C: nginx process (PID 3003) ─┘

Tất cả serve cùng web pages, nhưng chạy trên hosts khác nhau.
Dynatrace gom chúng thành 1 Process Group.

Ví von: Nếu 1 process là 1 nhân viên bán hàng, thì process group là cả team nhân viên bán hàng. Họ đều làm cùng công việc, nhưng cần nhiều người để xử lý khi cửa hàng đông. Nếu 1 người nghỉ? → Những người còn lại vẫn cover được.

NOTE

Phân biệt (hay ra thi):

ProcessProcess Group
Là gì1 chương trình đang chạyNhóm logic các processes cùng loại
Số lượng1 instance cụ thểNhiều instances trên nhiều hosts
Entity IDPROCESS_GROUP_INSTANCE-xxxPROCESS_GROUP-xxx
MetricsPer-instanceAggregated across instances

Layer 4: Services ⭐⭐ RẤT QUAN TRỌNG

Service là gì?

Service = code phía server được thực thi bên trong process group khi nó nhận và xử lý request.

Nói đơn giản hơn: Khi process nhận request → phần code xử lý request đó → Dynatrace nhóm lại thành Service.

Ví dụ cụ thể

User click "Login"
    │
    ▼
Process (Java Tomcat trên host-web-01)
    │
    └─→ SERVICE "AuthenticationService"
         │
         ├── Nhận request: POST /api/login
         ├── Kiểm tra credentials (code-level)
         ├── Query database (SELECT * FROM users WHERE...)
         ├── Trả về response: 200 OK + JWT token
         │
         Dynatrace capture:
         • Response time: 350ms
         • Status: Success
         • Database query: 120ms
         • Method hotspot: validatePassword() 80ms

Service = Hành động cụ thể của nhân viên

Process = Nhân viên bán hàng (sẵn sàng phục vụ)
Service = Hành động cụ thể khi có khách (tìm kính thiên văn, thanh toán...)

1. Khách vào cửa hàng → request
2. Nhân viên CHƯA làm gì cho đến khi có yêu cầu → process chờ requests
3. Khách yêu cầu "tìm Smart Telescope S50" → request đến
4. Nhân viên tìm và đưa sản phẩm → service xử lý request

Các loại Services phổ biến

ServiceMô tảVí dụ
Web requestXử lý HTTP requestsPage loads, REST API
DatabaseXử lý DB queriesSQL queries, MongoDB operations
MessagingXử lý messagesKafka consumer, RabbitMQ
RPCRemote procedure callsgRPC, SOAP

Service chỉ xuất hiện khi có requests

WARNING

Trong Dynatrace, service chỉ hiện data khi có requests trong timeframe được chọn. Nếu không có requests → không có data cho service đó — giống nhân viên bán hàng chỉ làm việc khi có khách.

Dynatrace cho thấy gì ở Service layer?

  1. Requests nào được thực hiện (page loads, logins, API calls)
  2. Bao lâu để hoàn thành (response time)
  3. Process nào xử lý request
  4. Code-level detail: methods nào tốn nhiều thời gian nhất (method hotspots)
  5. Errors & exceptions nếu có

Database trong Smartscape

Database KHÔNG phải layer riêng

Database trong Dynatrace không hiển thị như layer riêng trong Smartscape, mà được monitor như một loại service đặc biệt.

Nguyên lý quan trọng: Monitor từ phía caller ⭐

Dynatrace monitor database queries từ phía app server gọi đến database, KHÔNG phải từ database server.

                    ┌─ OneAgent capture queries TẠI ĐÂY
                    ▼
App Server ──SQL query──→ Database Server
(Full-stack)              (Infrastructure only)

OneAgent trên app server thấy:
  ✅ Query gì được gửi (SELECT, INSERT...)
  ✅ Response time (bao lâu)
  ✅ Errors (nếu có)
  ✅ Code-level: method nào gọi query

OneAgent trên database server chỉ thấy:
  ✅ Host metrics (CPU, RAM, disk)
  ✅ Process metrics (DB process running)
  ❌ KHÔNG thấy chi tiết queries

So sánh 3 kịch bản monitoring

Cài OneAgent ở đâu?Thấy gì?Không thấy gì?
Chỉ app serverRequest gửi đến DB, query content, response timeDB internal performance
Chỉ database serverDB đang hoạt động (CPU, RAM)Query nào, từ đâu, bao lâu
CẢ HAI ✅Full picture: query + DB performance—

IMPORTANT

Khuyến nghị cho thi:

  • Cài OneAgent Full-stack trên app server → capture database queries
  • Cài OneAgent Infrastructure only trên database server → infrastructure metrics + tiết kiệm license
  • Câu hỏi hay gặp: “Để monitor database queries, cài OneAgent ở đâu?” → App server

Ví von cửa hàng

Database = Kho hàng phía sau cửa hàng
App server = Nhân viên bán hàng

Khách hỏi "Smart Telescope S50":
  1. Nhân viên vào kho tìm (= app server gửi SQL query)
  2. Kho trả về sản phẩm (= database trả kết quả)

Từ góc nhìn khách hàng (= Dynatrace monitor từ app server):
  ✅ Biết sản phẩm nào được yêu cầu (query gì)
  ✅ Biết nhân viên mất bao lâu (response time)
  ✅ Biết có lỗi không (sai sản phẩm?)
  ❌ KHÔNG biết chuyện gì xảy ra BÊN TRONG kho (DB internals)

Layer 5: Applications ⭐

Application trong Dynatrace là gì?

Application trong Dynatrace = front-end mà users tương tác qua browser hoặc mobile app. KHÔNG phải bất kỳ phần mềm nào.

WARNING

Dễ nhầm lẫn:

Nghĩa IT chungNghĩa trong Dynatrace
ApplicationBất kỳ phần mềm nào (DB, backend, internal tool…)Chỉ user-facing interface (web/mobile)

Backend services, databases, internal tools KHÔNG phải “Application” trong Dynatrace.

Cần gì để capture Application data?

OneAgent phải cài Full-stack mode trên web server phục vụ trang web → OneAgent tự inject JavaScript vào HTML → capture user experience data.

Application Detection Rules

Mặc định, Dynatrace gom tất cả web traffic vào “My Web Application”. Để tách ra, cần tạo detection rules (thường dựa trên domain hoặc URL pattern).

Mặc định:
  telescope-store.com   → "My Web Application"
  admin.telescope.com    → "My Web Application"
  api.telescope.com      → "My Web Application"

Sau khi tạo rules:
  telescope-store.com   → "Telescope Store" (web app)
  admin.telescope.com    → "Admin Portal" (web app)
  api.telescope.com      → không phải app (backend API)

NOTE

  • Traffic mới → phân loại đúng theo rules
  • Traffic cũ → vẫn nằm trong “My Web Application” (không retroactive)

Knowledge Check

Q1: What does topology refer to in computing?

  • A. The layout of a website
  • B. A tool for software installation
  • C. The arrangement and connections of devices and components
  • D. A design pattern used in programming

Đáp án: C — The arrangement and connections of devices and components (Cách sắp xếp và kết nối giữa các thiết bị và thành phần).

Tại sao C đúng?

Trong computing, topology chỉ cách các thiết bị (servers, databases, services, processes) được sắp xếp và kết nối với nhau — tạo thành một bản đồ mối quan hệ. Topology trả lời câu hỏi:

  • Thiết bị nào nói chuyện với thiết bị nào?
  • Nếu component A bị lỗi, component nào bị ảnh hưởng?
  • Đường đi của data từ user đến database là gì?

Trong Dynatrace, tính năng Smartscape tự động build topology map real-time — mapping 5 layers: Data Centers → Hosts → Processes → Services → Applications. Smartscape giúp Davis AI tìm root cause bằng cách traverse qua topology để xác định dependency chain.

Giải thích các lựa chọn sai:

  • A. Layout of a website: Layout website là về cách trình bày giao diện (HTML/CSS layout, UI/UX design) — hoàn toàn khác với topology. Topology nói về mối quan hệ backend giữa infrastructure components, không phải frontend design.
  • B. Tool for software installation: Topology là khái niệm (concept), không phải tool. Nó mô tả cấu trúc hệ thống, không liên quan đến việc cài đặt phần mềm.
  • D. Design pattern in programming: Design patterns (như Singleton, Factory, Observer) là giải pháp thiết kế phần mềm ở mức code. Topology là khái niệm ở mức infrastructure/architecture, không liên quan design patterns.

💡 Lời khuyên thi: Topology = Map/Bản đồ mối quan hệ. Trong Dynatrace, Smartscape = auto-discovered topology. Bất kỳ câu hỏi nào hỏi “topology là gì” → tìm keyword arrangement, connections, relationships.

Q2: Which of the following are layers in Dynatrace Smartscape? (Select THREE)

  • ✅ Services
  • ✅ Applications
  • ❌ Firewalls
  • ✅ Hosts
  • ❌ Logs

Đáp án: Services, Applications, Hosts

Tại sao 3 đáp án trên đúng?

Smartscape có chính xác 5 layers, từ dưới lên:

LayerMô tảVí dụ
1. Data CentersVị trí vật lý/cloudAWS us-east-1, on-prem DC
2. Hosts ✅Servers có OneAgentEC2, VM, physical server
3. ProcessesChương trình đang chạyJava, nginx, Node.js
4. Services ✅Code xử lý requestsLogin service, Payment API
5. Applications ✅User-facing frontendWebsite, mobile app

Câu hỏi chỉ liệt kê 3 trong 5 layers đúng (Services, Applications, Hosts). Processes và Data Centers cũng là layers nhưng không có trong danh sách lựa chọn.

Tại sao Firewalls sai?

Firewall là network security component — nó kiểm soát traffic vào/ra mạng. Dynatrace KHÔNG model firewall như một entity trong Smartscape. Smartscape chỉ model các thành phần application stack: từ server infrastructure lên đến user-facing apps. Network components như firewalls, load balancers, switches không phải Smartscape layers.

Tại sao Logs sai?

Logs là một loại data (kiểu dữ liệu) — giống metrics, traces, events. Logs được thu thập và lưu trong Grail, nhưng logs không phải layer topology. Layer topology chỉ bao gồm thực thể (entities) tham gia vào application stack, không phải loại dữ liệu.

💡 Lời khuyên thi: Ghi nhớ 5 layers bằng chữ viết tắt D-H-P-S-A (Data Centers – Hosts – Processes – Services – Applications). Bất kỳ thứ gì không phải entity (như Logs, Metrics, Firewalls, Networks) → KHÔNG phải Smartscape layer.

Q3: True or False — A service occurs when a process or group of processes manages a request, indicating that a particular task needs to be completed, and a process takes action to fulfill it.

  • ✅ True

Đáp án: True — Đúng, service xuất hiện khi process hoặc group of processes xử lý request.

Tại sao True?

Trong Dynatrace, mối quan hệ Process → Service hoạt động như sau:

  1. Process chạy sẵn trên host (VD: Java Tomcat đang running) — nhưng chưa làm gì
  2. Request đến (VD: HTTP POST /api/login) — input được gửi tới process
  3. Process xử lý request — code bên trong process thực thi logic (validate, query DB, return response)
  4. Dynatrace ghi nhận hoạt động này thành một Service — với response time, success/failure, method details

Ví von: Process = nhân viên bán hàng đứng trong cửa hàng chờ. Service = hành động phục vụ khách khi khách yêu cầu. Nhân viên không tự dưng lấy hàng — chỉ khi có khách hỏi (request).

Hệ quả quan trọng:

  • Không có request → không có service data trong timeframe đó
  • Service chỉ xuất hiện khi bạn chọn timeframe có requests
  • Nếu service “biến mất” trong UI → kiểm tra timeframe, có thể không có traffic trong khoảng thời gian đó

💡 Lời khuyên thi: Nhớ: Service = Process + Request. Thiếu 1 trong 2 → không có service. Đây là khái niệm cốt lõi để hiểu tại sao Smartscape service layer đôi khi trông “trống”.

Q4: To monitor database queries, where should the OneAgent be installed?

  • A. Only on the database server
  • B. Only on the network router
  • C. On the user’s browser
  • D. On the application server making the queries

Đáp án: D — On the application server making the queries (Trên app server đang gửi queries đến database).

Tại sao D đúng?

Đây là điểm RẤT quan trọng và thường xuyên ra thi!

Dynatrace monitor database queries bằng cách theo dõi phía gọi (caller), không phải phía nhận (database). Cơ chế:

  1. OneAgent cài Full-stack trên app server
  2. Khi app code gọi SELECT * FROM products WHERE id=123, OneAgent intercept call này tại code-level
  3. OneAgent ghi lại: query gì, từ method nào, mất bao lâu, có lỗi không
  4. Tất cả thông tin này hiển thị trong Service layer → Database statements

Tại sao cài trên database server không đủ? Vì OneAgent trên DB server chỉ thấy infrastructure metrics (CPU 85%, RAM 12GB used, disk I/O 50MB/s). Nó KHÔNG thấy nội dung queries — không biết query nào chạy, từ app nào gửi, mất bao lâu.

Best practice trong production:

  • App server: OneAgent Full-stack → capture queries + code-level detail
  • Database server: OneAgent Infrastructure Only → capture host metrics + tiết kiệm license

Giải thích các lựa chọn sai:

  • A. Only database server: Như giải thích trên — OneAgent trên DB server chỉ thấy metrics, KHÔNG thấy queries. Giống như đứng trong kho nhìn thấy hàng hóa nhưng không biết ai đặt hàng gì.
  • B. Network router: Router xử lý network traffic routing — OneAgent KHÔNG cài được trên router. Router không phải server chạy OS thông thường.
  • C. User’s browser: Browser chạy JavaScript phía client — cách xa database queries. Database queries diễn ra ở server-side (app server → database), không liên quan đến browser.

💡 Lời khuyên thi: Nhớ nguyên tắc: Database visibility = Monitor từ CALLER (app server), không phải từ DB server. Keyword: “application server making the queries”.

Q5: What is a common reason a user might switch a host to a different monitoring mode?

  • A. To reset all settings
  • B. To enable push notifications for alerts
  • C. To reduce licensing costs while monitoring essential metrics
  • D. To delete all historical performance data

Đáp án: C — To reduce licensing costs while monitoring essential metrics (Để giảm chi phí license trong khi vẫn giám sát được các metrics thiết yếu).

Tại sao C đúng?

Trong Dynatrace, chi phí license (Host Units) gắn liền trực tiếp với monitoring mode. Mỗi mode tốn lượng Host Units khác nhau:

1. Full-Stack Mode (Đắt nhất)

  • Thu thập: Host metrics + Process metrics + Service tracing + Code profiling + PurePath
  • Chi phí: Tốn nhiều Host Units nhất
  • Dùng cho: Business-critical apps (Production web servers, API servers)

2. Infrastructure Only Mode (Tiết kiệm hơn)

  • Thu thập: Host metrics + Process metrics + Logs (optional)
  • Không có: Service tracing, code profiling, PurePath
  • Chi phí: Rẻ hơn đáng kể so với Full-stack
  • Dùng cho: Database servers, Jenkins, Active Directory, build servers — nơi chỉ cần biết server “còn sống” và resource usage

3. Discovery Mode (Rẻ nhất)

  • Thu thập: Host metrics cơ bản + topology
  • Chi phí: Thấp nhất
  • Dùng cho: Kiosks, POS systems, endpoints chỉ cần xác nhận availability

Không phải mọi server đều cần Full-stack. Ví dụ: Database server chạy PostgreSQL — bạn không cần soi code-level bên trong PostgreSQL, chỉ cần biết CPU/RAM/disk có ổn không. Vậy chuyển sang Infrastructure Only → giám sát đủ dùng mà tiết kiệm license đáng kể.

Giải thích các lựa chọn sai:

  • A. To reset all settings: Đổi monitoring mode KHÔNG xóa các cấu hình đã set (tags, host group, metadata). Nó chỉ thay đổi loại data được thu thập từ thời điểm đó về sau. Settings và configurations vẫn giữ nguyên.
  • B. To enable push notifications: Thông báo/alerting được cấu hình trong phần Settings → Alerting Profiles — hoàn toàn độc lập với monitoring mode. Dù bạn dùng mode nào, miễn có data anomaly thì Davis AI vẫn tạo alert.
  • D. To delete historical data: Dữ liệu lịch sử được quản lý bởi Retention Policies (trong Grail Buckets), không phải monitoring mode. Đổi mode chỉ ảnh hưởng đến data thu thập từ thời điểm đó trở đi — data cũ vẫn còn cho đến khi hết retention period.

💡 Lời khuyên thi: Câu hỏi này thường xuyên xuất hiện. Nhớ keyword: Mode = Cost Optimization (Tối ưu chi phí). Đổi mode = cân bằng giữa visibility (cần thấy gì) và cost (tốn bao nhiêu license).
