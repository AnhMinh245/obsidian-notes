1. CI/CD cho Monaco — Tổng quan Workflow

Tại sao cần CI/CD cho monitoring config?

Hãy hình dung scenario này: một SRE nhận ticket “giảm SLO threshold của checkout service từ 99.5% xuống 99.0% vì team cần thời gian refactor”. Trong thế giới không có CI/CD, SRE phải:

  1. Đăng nhập Dynatrace UI dev → tìm SLO → sửa threshold → save
  2. Lặp lại cho staging
  3. Lặp lại cho prod
  4. Không ai review thay đổi. Không ai biết ngoại trừ SRE đó
  5. 3 tháng sau, không ai nhớ tại sao threshold là 99.0% thay vì 99.5%

Bây giờ hình dung với CI/CD pipeline:

  1. Developer sửa slo/config.yaml trong Git — thay threshold: 99.5 thành threshold: 99.0
  2. Tạo Merge Request. CI pipeline tự động chạy --dry-run validate — catch lỗi syntax, missing references
  3. Reviewer thấy diff, hỏi “tại sao giảm?” — developer giải thích trong MR comment
  4. Reviewer approve. Merge vào main
  5. Pipeline tự động deploy vào dev — test trước
  6. Pipeline deploy vào staging — xác nhận lần cuối
  7. Pipeline deploy vào prod — chờ manual approval. Lead SRE click approve → prod updated
  8. Toàn bộ không cần SSH vào server, không cần mở Dynatrace UI

Đó là sức mạnh của CI/CD cho configuration-as-code. Git history = audit trail. MR comments = rationale. Pipeline = automated safeguard.

Giá trị lớn nhất của CI/CD cho Monaco không phải tốc độ — mà là traceability. 6 tháng sau, ai đó hỏi "tại sao SLO threshold là 99.0%?", bạn search Git blame → thấy MR → đọc discussion → hiểu context. Đây là thứ mà click-ops trên UI KHÔNG BAO GIỜ cho bạn.

Tại sao mỗi stage cần tồn tại?

Mỗi stage trong pipeline không phải decorative — nó giải quyết một rủi ro cụ thể:

StageRủi ro nó giải quyếtKhi nào chạyTại sao
validateSyntax error, missing references, invalid schemaMerge RequestCatch lỗi trước khi code vào main. Giống compiler check — fail fast, fix cheap
deploy_devConfig logic error, unexpected behaviorAuto sau mergeDev là playground — nếu config sai, chỉ dev environment bị ảnh hưởng. Zero risk
deploy_stagingIntegration issues, performance impactAuto hoặc manualStaging mirror production — last chance test trước khi đụng prod
deploy_prodHuman error, unauthorized changeManual gateProduction là sacred — mọi thay đổi cần human acknowledge. Không bao giờ auto-deploy prod

Tại sao dev auto nhưng prod manual?

Dev environment là nơi team thử nghiệm — worst case scenario là dashboard bị lỗi vài phút, không ai bị ảnh hưởng. Nhưng prod chứa alerting profiles cho on-call, SLOs cho SLA reports, dashboards cho C-level. Một config sai ở prod = false alert → team bị gọi lúc 3 AM → trust breakdown. Manual gate là “seatbelt” cuối cùng trước khi config chạm prod.

Nguyên tắc vàng

  • MR/PR = validate only (--dry-run) — không deploy thật, chỉ kiểm tra
  • Merge to main = trigger deployment pipeline — main branch là source of truth
  • Progressive delivery: dev → staging → prod, mỗi bước có gate
  • Rollback: git revert commit → re-run pipeline = config rollback. Đơn giản hơn terraform destroy nhiều
  • Idempotent: chạy pipeline 5 lần → kết quả giống nhau. Giống kubectl apply — Monaco kiểm tra state hiện tại trước khi quyết định có cần update hay không

2. GitLab CI Pipeline — Focus chính

Tại sao GitLab CI?

GitLab CI là CI/CD platform phổ biến nhất trong enterprise DevOps ecosystem. Native integration với GitLab repository (MR events, protected branches, environment tracking), UI đơn giản cho manual approval, và pipeline visualization tốt. Nếu team bạn dùng GitHub, xem §3 — concept giống nhau, chỉ khác syntax.

.gitlab-ci.yml đầy đủ — Production-ready

Đây là pipeline template đã qua battle-test. Mỗi section đều có comment giải thích — nhưng đọc tiếp phần sau để hiểu tại sao từng field được chọn:

Giải thích sâu — Tại sao từng quyết định

Docker Image: Tại sao pin version?

Pin version cụ thể (v2.27.0) thay vì latest là bài học đắt giá từ DevOps. Hãy tưởng tượng: pipeline chạy ngon lành suốt 3 tháng. Một ngày, Monaco release v2.28.0 với breaking change trong YAML schema. Pipeline dùng latest tự động pull v2.28.0 → tất cả jobs fail → team mất 2 giờ debug → phát hiện không phải do code mà do Monaco upgrade. Giống như npm install không có lockfile — reproducibility biến mất.

Pin version cho bạn:

  • Reproducibility: pipeline hôm nay chạy giống hệt pipeline 3 tháng trước
  • Controlled upgrade: test version mới trên dev branch trước, merge khi sẵn sàng
  • Audit trail: Git history ghi rõ khi nào upgrade Monaco version

KHÔNG bao giờ dùng latest tag cho Docker image trong production pipeline.

Một ngày Monaco update breaking change → pipeline fail không rõ nguyên nhân. latest là alias thay đổi liên tục — hôm nay trỏ v2.27.0, mai trỏ v2.28.0. Pin version LUÔN. Khi cần upgrade: tạo MR đổi version → test → merge. Giống Terraform version constraint required_version = "~> 1.5.0".

rules: changes: — Tiết kiệm CI minutes

Không phải mọi commit đều cần trigger Monaco pipeline. Nếu ai đó chỉ sửa README.md hoặc .gitignore, chạy validate là phí CI minutes. rules: changes: nói với GitLab: “chỉ chạy job này khi files trong paths specified bị thay đổi”. Giống Terraform trigger: paths trong Azure DevOps hay paths: filter trong GitHub Actions.

Dùng rules: changes: để chỉ trigger pipeline khi Monaco files thay đổi.

Nếu team commit cả application code VÀ Monaco configs trong cùng repo (monorepo), filter này tránh chạy Monaco pipeline khi developer chỉ sửa Java code. Tiết kiệm CI minutes = tiết kiệm tiền (GitLab CI minutes tính phí trên SaaS plans).

when: manual + allow_failure: false — Production gate

Đây là combo quan trọng nhất trong pipeline. Hiểu sai 1 trong 2 field này là nguy hiểm:

CombinationBehaviorNguy hiểm?
when: manual + allow_failure: true (default!)Pipeline tiếp tục chạy stages sau mà không chờ manual click⚠️ CỰC KỲ NGUY HIỂM nếu có stage sau
when: manual + allow_failure: falsePipeline BLOCK — đứng im cho đến khi ai đó click approve✅ Đây là behavior bạn muốn

Trap phổ biến: nhiều người quên rằng when: manual mặc định có allow_failure: true. Nghĩa là nếu bạn viết:

GitLab sẽ coi stage này là “optional” — pipeline vẫn hiện ✅ passed mà không cần ai click approve. Nếu có stage sau (ví dụ notification), nó sẽ chạy ngay. Luôn thêm allow_failure: false cho manual gates.

when: manual mặc định allow_failure: true trong GitLab CI.

Nếu quên thêm allow_failure: false, pipeline sẽ hiện “passed” mà không cần ai approve. Đây là trap phổ biến nhất khi setup manual gates. Production deploy PHẢI có allow_failure: false — pipeline BLOCK cho đến khi human click approve. Giống terraform apply phải có “yes” confirmation.

needs: — Chain dependencies

needs: tạo explicit dependency giữa jobs. Staging chỉ chạy sau khi dev thành công. Prod chỉ chạy sau staging. Nếu dev fail → staging/prod không bao giờ chạy. Đây là “blast radius control” — lỗi bị catch ở level thấp nhất.

artifacts: false vì Monaco không cần artifacts từ stage trước — mỗi stage deploy independent từ Git source.

--verbose cho Production

Production deploy luôn cần --verbose vì:

  • Job log trở thành audit trail — ai deploy gì, lúc nào, thay đổi gì
  • Khi có incident, bạn grep log để tìm “config X đã thay đổi lúc nào?”
  • Compliance requirement: nhiều tổ chức yêu cầu full log cho prod changes

GitLab CI Variables Setup

Secret variables (API tokens, OAuth credentials) KHÔNG nằm trong .gitlab-ci.yml — chúng được cấu hình trong GitLab UI và inject vào pipeline runtime:

Settings → CI/CD → Variables:

Variable Key              | Value                  | Protected | Masked | Scope
──────────────────────────────────────────────────────────────────────────────
DT_DEV_TOKEN              | dt0c01.xxx...          | ✓         | ✓      | All
DT_DEV_URL                | https://abc.dt.com     | ✓         | ✗      | All
DT_DEV_CLIENT_ID          | dt0s02.xxx...          | ✓         | ✓      | All
DT_DEV_CLIENT_SECRET      | dt0s02.xxx.secret      | ✓         | ✓      | All
DT_STAGING_TOKEN          | dt0c01.yyy...          | ✓         | ✓      | All
DT_PROD_TOKEN             | dt0c01.zzz...          | ✓         | ✓      | All

Giải thích 2 flags quan trọng:

  • Protected: biến chỉ available trên protected branches (thường là main). Feature branches KHÔNG thấy biến này → developer trên branch riêng không thể đọc prod token. Giống AWS IAM policy restrict access theo branch.
  • Masked: giá trị bị [MASKED] trong job logs. Nếu script vô tình echo $DT_PROD_TOKEN, log chỉ hiện [MASKED]. BẮT BUỘC cho mọi secret.

Luôn bật cả Protected VÀ Masked cho token variables.

Protected = chỉ main branch access. Masked = không hiện trong logs. Thiếu 1 trong 2 là rủi ro: thiếu Protected → developer trên feature branch có thể đọc prod token. Thiếu Masked → token lộ trong job log (GitLab log có thể shared, exported, hoặc cached).

4. Secret Management — Bảo vệ Crown Jewels

Tại sao secret management là critical?

Hãy nghĩ về quyền lực mà một API token nắm giữ:

  • API Token với WriteConfig scope có thể xoá TOÀN BỘ alerting profiles → team on-call không nhận alert → incident kéo dài hàng giờ không ai biết
  • API Token với settings.write scope có thể thay đổi management zones → người dùng thấy data của tenant khác (multi-tenant violation)
  • OAuth client secret có thể tạo automation workflow malicious → exfiltrate monitoring data
  • Token bị leak trên public Git repo → attacker có full control monitoring stack trong vài phút

Đây là crown jewels của monitoring stack. Bảo vệ chúng không phải optional — nó là requirement ngang hàng với bảo vệ database credentials hoặc cloud IAM keys.

API Token leak = monitoring stack compromise.

Năm 2024, GitHub report rằng hơn 12 triệu secrets bị leak trên public repos. API tokens là target #1. Nếu Dynatrace token bị leak: attacker có thể disable alerting → deploy malware → xoá dấu vết monitoring → bạn không hề biết cho đến khi customer gọi. Bảo vệ token nghiêm túc như bảo vệ production database password.

Ba lựa chọn — Từ simple đến enterprise

Option A: Native K8s Secrets — Simple nhưng Risky

Tại sao xem xét: Đơn giản nhất, zero dependencies, setup trong 30 giây. Phù hợp cho lab, PoC, hoặc dev environment isolated.

Giải thích:

  • stringData vs data: stringData nhận plaintext, K8s tự encode base64. data nhận base64 sẵn. Dùng stringData để tránh encode sai
  • type: Opaque: generic secret type — K8s không validate nội dung

Ưu điểm:

  • Setup nhanh — kubectl apply -f secret.yaml xong
  • Không cần infrastructure thêm
  • Mọi Kubernetes cluster đều support

Nhược điểm — và đây là vấn đề lớn:

  • Base64 encoded — KHÔNG phải encrypted. echo "dt0c01.XXX" | base64 → ai cũng decode được. Giống để key dưới thảm chân — che mắt nhưng bất kỳ ai biết chỗ đặt đều lấy được
  • Ai có kubectl get secret -o yaml access → đọc được token ngay
  • File YAML chứa secret → KHÔNG commit vào Git. Nhưng không commit = mất traceability = không GitOps-safe
  • Không auto-rotate — token nằm đó cho đến khi ai đó nhớ thay
  • Không audit trail — không biết ai đọc secret khi nào

base64 KHÔNG phải encryption.

Nhiều người lầm tưởng K8s Secret “encrypted” vì nhìn thấy chuỗi base64 dài. Thực tế: echo "ZHQwYzAxLnh4eA==" | base64 -d → ra plaintext ngay. Base64 là encoding (biến đổi format), không phải encryption (bảo vệ bằng key). Giống viết ngược chữ — trẻ con cũng đọc được nếu biết trick.

Option B: Sealed Secrets — GitOps-safe, Single-cluster

Tại sao xem xét: Sealed Secrets (by Bitnami) giải quyết vấn đề lớn nhất của K8s Secrets — bạn CÓ THỂ commit encrypted secret vào Git mà không sợ leak. Phù hợp cho team nhỏ-trung, single cluster, chưa có Vault infrastructure.

Concept: Client-side encryption. Bạn dùng kubeseal CLI encrypt secret trên laptop → output là SealedSecret CR (encrypted) → commit vào Git → Sealed Secrets controller trên cluster decrypt → tạo K8s Secret. Chỉ controller trên cluster đó có private key → chỉ cluster đó decrypt được.

flowchart LR
    DEV["Developer<br/>(laptop)"] -->|"kubeseal encrypt"| SEALED["SealedSecret<br/>(encrypted YAML)"]
    SEALED -->|"git push"| GIT["Git Repo<br/>(safe to commit)"]
    GIT -->|"ArgoCD sync"| CTRL["Sealed Secrets<br/>Controller"]
    CTRL -->|"decrypt"| SECRET["K8s Secret<br/>(plaintext, in-cluster only)"]
    SECRET -->|"env var inject"| MONACO["Monaco Job"]

Tạo SealedSecret:

Ưu điểm:

  • GitOps-safe — commit encrypted secret vào Git. ArgoCD sync → controller decrypt → secret ready
  • Setup đơn giản hơn Vault — chỉ cần install Sealed Secrets controller (helm install)
  • Cluster-specific encryption — mỗi cluster có key pair riêng → secret encrypt cho cluster A không decrypt được trên cluster B

Nhược điểm:

  • Single cluster — mỗi cluster cần encrypt riêng. Multi-cluster = re-encrypt cho từng cluster
  • Key rotation phức tạp — khi rotate cluster key, phải re-seal toàn bộ secrets
  • Không auto-rotate secret value — token vẫn cùng giá trị cho đến khi ai đó re-seal
  • Key backup — nếu mất controller private key, tất cả SealedSecrets không decrypt được

Option C: External Secrets Operator + HashiCorp Vault (RECOMMENDED cho Production)

Tại sao đây là best practice: External Secrets Operator (ESO) kết hợp Vault giải quyết MỌI vấn đề của Option A và B: centralized secret management, auto-rotation, audit trail, multi-cluster support. Trade-off là complexity — nhưng cho production, complexity này xứng đáng.

Architecture: ESO là K8s operator. Nó watch ExternalSecret CRs → fetch secret values từ external store (Vault, AWS Secrets Manager, Azure Key Vault…) → tạo/update K8s Secret. Giống middleware — K8s workload vẫn đọc K8s Secret bình thường, nhưng secret value đến từ Vault.

SecretStore — Nói cho ESO biết connect tới Vault ở đâu, authenticate bằng cách nào:

Giải thích từng field quan trọng:

FieldGiá trịÝ nghĩa

ExternalSecret — Nói cho ESO biết fetch secret nào, đặt vào K8s Secret nào:

Giải thích flow:

  1. ArgoCD sync ExternalSecret manifest từ Git → K8s
  2. ESO thấy ExternalSecret → đọc secretStoreRef → connect tới Vault
  3. ESO fetch secret/data/dynatrace/dev từ Vault → lấy api-token, client-id, client-secret
  4. ESO tạo K8s Secret dynatrace-monaco-token với 3 keys
  5. Mỗi 1 giờ (refreshInterval), ESO re-fetch → nếu Vault value thay đổi → K8s Secret auto-update
  6. Monaco Job mount K8s Secret như env vars → deploy config

Ưu điểm:

  • Centralized: 1 Vault cho tất cả clusters, teams, environments
  • Auto-rotation: refreshInterval: 1h → Vault rotate token → ESO auto-sync → zero downtime
  • Audit trail: Vault log ai access secret nào, khi nào. Compliance-ready
  • Multi-cluster: ESO trên cluster A, B, C đều fetch từ cùng Vault → consistent
  • GitOps-safe: ExternalSecret manifest commit vào Git (không chứa secret value)
  • Secret versioning: Vault KV v2 giữ history — rollback secret value nếu cần

Nhược điểm:

  • Complexity: cần operate Vault cluster (HA, backup, unsealing)
  • Infrastructure overhead: Vault cần storage backend (Consul/Raft), TLS certs, auth config
  • Learning curve: Vault policies, auth methods, secret engines — đủ cho 1 course riêng
  • Cost: Vault Enterprise tính phí (Community edition free nhưng thiếu features)

5. Token Scopes — Principle of Least Privilege

Tại sao Least Privilege quan trọng cho monitoring?

Principle of Least Privilege (PoLP) nói: “mỗi identity chỉ có quyền TỐI THIỂU cần thiết để hoàn thành nhiệm vụ”. Cho Dynatrace tokens, điều này có nghĩa:

  • Token cho dev KHÔNG có quyền gì trên prod → nếu dev token bị leak, attacker chỉ đụng được dev environment
  • Token cho deploy SLO KHÔNG có quyền xoá dashboards → hạn chế blast radius
  • Token cho read KHÔNG có quyền write → download job không thể vô tình modify config

Real-world scenario: Developer commit Monaco config vào public repo (accidents happen). Repo chứa env variable reference $DT_API_TOKEN. Attacker clone repo, nhưng không có token value — safe. Nhưng nếu developer VÔ TÌNH hardcode token trong config file → token bị leak. Nếu token có WriteConfig + settings.write + ExternalSyntheticIntegration (quá nhiều scopes) → attacker có thể xoá toàn bộ alerting, tạo synthetic monitors malicious, disable detection rules. Nếu token chỉ có settings.write (scoped cho SLO only) → attacker chỉ sửa được SLO, không đụng được alerting hay synthetics. Blast radius nhỏ hơn 10x.

Resource TypeAuth MethodRequired ScopesTại sao cần scope đó
Settings 2.0 (alerting, MZ, tags)API Tokensettings.read, settings.writeSettings 2.0 API dùng chung 2 scopes cho mọi schema
Dashboards (classic)API TokenReadConfig, WriteConfigClassic Config API — legacy scopes
Dashboards (documents)OAuthdocument:documents:read, document:documents:writeDocument API là Platform API — chỉ OAuth
SLOsAPI Tokensettings.read, settings.write, slo.read, slo.writeSLO dùng cả Settings API (config) và SLO API (data)

API Token vs OAuth Client — khi nào dùng gì?

Quy tắc đơn giản: Classic API + Settings API → API Token. Platform API (Automation, Documents, OpenPipeline) → OAuth Client. Nếu Monaco project có cả Settings 2.0 VÀ Automation configs → manifest.yaml cần CẢ auth.token VÀ auth.oAuth. Xem 00 - Monaco v2 Overview & Architecture §Auth.

Token Strategy — 1 Token Per Environment

Token Architecture:
  ├── dt-token-dev          → DEV tenant scopes (rộng hơn cho testing)
  │     ├── settings.read
  │     ├── settings.write
  │     ├── ReadConfig
  │     ├── WriteConfig
  │     ├── slo.read
  │     ├── slo.write
  │     └── ExternalSyntheticIntegration
  │
  ├── dt-token-staging      → STAGING tenant scopes (giống prod)
  │     ├── settings.read
  │     ├── settings.write
  │     └── slo.read / slo.write
  │
  └── dt-token-prod         → PROD tenant scopes (MINIMAL!)
        ├── settings.read
        ├── settings.write
        └── slo.read / slo.write
        # Không có ExternalSyntheticIntegration
        # Không có WriteConfig (nếu không deploy classic dashboards)

Nguyên tắc:

  • 1 token per environment — KHÔNG share token cross-env. Dev token bị leak → prod safe
  • Prod token = tối thiểu scopes — chỉ scopes THẬT SỰ cần cho configs đang deploy
  • Dev token rộng hơn — dev dùng để test config types mới, cần scopes extra
  • Dedicated OAuth client per env — tương tự logic, nhưng cho Platform API

6. Kustomize Overlays — Multi-env K8s Manifests

Tại sao cần Kustomize ở đây?

Nếu bạn dùng ArgoCD deploy Monaco Jobs (xem 06 - Monaco + ArgoCD GitOps Integration), bạn cần K8s manifests khác nhau per environment: env vars khác, secrets khác, resource limits khác. Bạn KHÔNG muốn copy-paste 3 file Job giống hệt nhau chỉ khác TARGET_ENV.

Kustomize giải quyết bài toán này giống environmentOverrides của Monaco nhưng cho K8s layer. Monaco có overlays cho Dynatrace config (env-specific thresholds). Kustomize có overlays cho K8s manifests (env-specific env vars, resource limits, secrets).

2 layers, cùng concept:

LayerToolOverlays cho gìVí dụ
Dynatrace configMonaco environmentOverridesSLO threshold, alerting severitythreshold: 99.5 (prod) vs 99.0 (dev)
K8s manifestsKustomize overlaysEnv vars, secrets, resource limitsTARGET_ENV: prod vs TARGET_ENV: dev

Giống Helm values files nhưng không cần template engine — Kustomize dùng strategic merge patches. Simpler, no Go templating headaches.

Directory Structure

k8s/
├── base/                           # Template — shared across all envs
│   ├── kustomization.yaml          # Kustomize entry point
│   └── monaco-job.yaml             # Job template (generic)
├── overlays/
│   ├── dev/                        # Dev-specific overrides
│   │   ├── kustomization.yaml
│   │   └── resource-patch.yaml     # Optional: resource limits patch
│   ├── staging/
│   │   └── kustomization.yaml
│   └── prod/
│       ├── kustomization.yaml
│       └── resource-patch.yaml

Deploy với Kustomize

kubectl diff -k = terraform plan cho Kustomize.

Luôn chạy kubectl diff -k overlays/prod/ trước khi apply vào prod. Nó show diff giữa desired state (từ Git) và actual state (trên cluster). Nếu diff trống → không có gì thay đổi. Nếu có diff → review trước khi apply. Giống monaco deploy --dry-run nhưng cho K8s layer.

So sánh Kustomize vs Helm cho use case này

AspectKustomizeHelm
SyntaxPatch-based (JSON Patch/Strategic Merge)Template-based (Go templates)
Learning curveThấp — YAML patchesCao — Go template syntax
Built into kubectl✅ kubectl apply -k❌ Cần install Helm CLI
ArgoCD support✅ Native✅ Native
Best forSimple overrides (env vars, labels)Complex templating (conditionals, loops)
Monaco use case✅ Đủ dùng — chỉ patch env varsOverkill

Cho Monaco K8s manifests, Kustomize là đủ. Job template đơn giản — chỉ cần patch env vars và resource limits per env. Helm overkill cho use case này.
