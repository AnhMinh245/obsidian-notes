1. Tại sao cần GitOps cho Dynatrace Configuration

Scenario — Câu chuyện bạn sẽ gặp (hoặc đã gặp)

Hãy tưởng tượng team bạn quản lý 3 Dynatrace environments: dev, staging, prod. Mọi thứ đang chạy ổn — alerting profiles chuẩn, dashboards đồng bộ, SLOs consistent giữa các env.

Rồi tuần trước, một engineer nhận incident ticket lúc 2h sáng. Response time của payment-service tăng đột biến, Dynatrace báo problem. Trong quá trình debug, engineer mở Dynatrace UI trên production và sửa alerting threshold từ 2000ms lên 5000ms để tạm tắt alert gây noise trong lúc fix. Incident resolved lúc 4h sáng. Engineer đi ngủ. Quên revert threshold.

2 tuần sau, staging environment có bug tương tự — payment-service response time tăng lên 3500ms. Nhưng lần này không ai nhận alert. Tại sao? Vì alerting profile trên prod đã bị sửa lên 5000ms, và ai đó (hoặc script) đã copy config từ prod sang staging tuần trước để “đồng bộ”. Kết quả: staging alert threshold cũng là 5000ms → 3500ms không trigger → bug âm thầm ảnh hưởng testing 3 ngày trước khi QA phát hiện bằng mắt thường.

Đây là configuration drift — và nó xảy ra ở mọi team không dùng Configuration as Code.

Pain points chi tiết — Tại sao UI-based config là bom nổ chậm

1. Không có audit trail đáng tin cậy

Dynatrace UI có Settings changelog, nhưng nó chỉ ghi “who changed what” — không ghi “tại sao thay đổi”. Không có PR description, không có reviewer approval, không có rollback button. Khi incident xảy ra vì config sai, bạn biết ai sửa nhưng không biết context. So sánh với Git history: mỗi commit có message, có diff, có linked Jira ticket, có reviewer comments.

2. Không reproducible across environments

Setup 1 Dynatrace environment từ zero qua UI mất hàng giờ: tạo management zones, alerting profiles, notification channels, dashboards, SLOs, auto-tagging rules… Giờ setup env thứ 2? Làm lại từ đầu. Env thứ 3? Lại từ đầu. Mỗi lần setup là cơ hội tạo ra sai lệch. Monaco + Git giải quyết: monaco deploy manifest.yaml --environment staging — xong trong 30 giây, consistent 100%.

3. Configuration drift giữa environments

Dev có 15 alerting profiles, staging có 14 (ai đó quên tạo 1 cái), prod có 16 (ai đó tạo thêm 2 cái adhoc). Không tool nào phát hiện sự khác biệt này cho đến khi incident xảy ra. Với GitOps: Git repo là single source of truth — mọi env PHẢI match với repo, nếu drift → ArgoCD tự heal.

4. Không thể code review monitoring changes

Một junior engineer sửa SLO target từ 99.9% xuống 99% trên prod. Không ai review. Không ai biết. Với GitOps: thay đổi này phải qua PR → reviewer thấy diff 99.9 → 99.0 → hỏi “tại sao hạ target?” → ngăn chặn trước khi deploy.

5. Rollback gần như không thể

Nếu config mới gây vấn đề, bạn phải nhớ config cũ là gì rồi sửa lại bằng tay. Với Git: git revert <commit> + ArgoCD auto-sync → rollback trong 60 giây.

GitOps principles áp dụng cho monitoring configuration

GitOps không chỉ dành cho application deployment. 4 principles của GitOps áp dụng hoàn hảo cho monitoring config:

PrincipleApplication DeploymentMonitoring Config (Monaco)
DeclarativeK8s manifests mô tả desired stateMonaco YAML mô tả desired Dynatrace config
VersionedGit history cho app codeGit history cho alerting/dashboard/SLO configs
AutomatedArgoCD auto-sync khi Git thay đổiArgoCD trigger Monaco Job khi config thay đổi
Continuously ReconciledArgoCD detect drift, self-healArgoCD + Monaco detect config drift, re-apply

💡 “Tại sao không chỉ dùng Monaco CLI trong CI/CD pipeline?”

Câu hỏi rất hay, và đây là phân biệt quan trọng:

Monaco CLI trong CI/CD (vd: GitLab CI chạy monaco deploy khi merge MR):

  • ✅ Automated deployment
  • ✅ Version-controlled
  • ❌ Push-based — chỉ deploy khi có commit mới, không biết config bị sửa tay trên UI
  • ❌ Không có continuous reconciliation — nếu ai đó sửa config trên Dynatrace UI sau khi deploy, CI/CD không biết
  • ❌ Không có dashboard hiển thị sync status
  • ❌ Không có RBAC granular (ai được deploy env nào)

ArgoCD + Monaco:

  • ✅ Tất cả ưu điểm trên
  • ✅ Pull-based — ArgoCD liên tục poll Git repo, phát hiện thay đổi
  • ✅ Continuous reconciliation — ArgoCD so sánh desired state (Git) vs actual state (cluster) mỗi 3 phút (configurable)
  • ✅ Self-heal — nếu ai xoá Monaco Job, ArgoCD tạo lại
  • ✅ Visibility — ArgoCD UI hiển thị sync status, health, history cho mọi Application
  • ✅ Multi-cluster — 1 ArgoCD quản lý nhiều clusters/environments
  • ✅ RBAC — project-based permissions

Analogie

Dùng Monaco CLI trong CI/CD = push-based GitOps — giống kubectl apply chạy trong pipeline, chỉ apply khi có commit mới.
Thêm ArgoCD = pull-based GitOps — giống có người canh gác 24/7, liên tục so sánh “Git nói gì” vs “cluster đang có gì” và tự sửa khi lệch.
Tương tự sự khác biệt giữa chạy terraform apply thủ công vs dùng Terraform Cloud/Atlantis tự detect drift.

2. Kiến trúc tổng quan — 2 layers bổ sung nhau

Hiểu đúng: ArgoCD và Monaco KHÔNG overlap

Điều quan trọng nhất cần hiểu trước khi đi sâu: ArgoCD và Monaco hoạt động ở 2 LAYERS HOÀN TOÀN KHÁC NHAU. Chúng không cạnh tranh — chúng bổ sung cho nhau.

  • ArgoCD quản lý Kubernetes resources: Deployments, Services, ConfigMaps, Jobs, CronJobs. ArgoCD nói chuyện với Kubernetes API.
  • Monaco quản lý Dynatrace resources: Dashboards, SLOs, Alerting Profiles, Auto-tagging rules, Notification channels. Monaco nói chuyện với Dynatrace API.

ArgoCD không biết gì về Dynatrace API. Monaco không biết gì về Kubernetes. Cầu nối giữa chúng là K8s Job — ArgoCD trigger Job, Job chạy container có Monaco CLI, Monaco gọi Dynatrace API. Đơn giản nhưng cực kỳ powerful.

ASCII flow — Step by step cho người thích đọc tuần tự

STEP 2: ArgoCD detects change (poll mỗi 3 phút hoặc webhook)

STEP 3: ArgoCD Sync bắt đầu
         ↓

           Wave -2: Namespaces, CRDs
           Wave -1: Dynatrace Operator

         ↓

STEP 5: PostSync Hook triggered
         ↓
         ArgoCD tạo K8s Job chứa Monaco container
         Job chạy: monaco deploy manifest.yaml --environment prod

STEP 6: Monaco gọi Dynatrace API
         ↓
         Create/Update dashboards, SLOs, alerting profiles...
         Job complete → ArgoCD cleanup → Sync = Healthy ✅

Community Pattern — Không phải Official Integration

Đây là community best practice, KHÔNG phải official integration. Dynatrace không ship ArgoCD plugin, và ArgoCD không có native Dynatrace resource kind. Pattern này dùng K8s Job như cầu nối — ArgoCD trigger Job, Job chạy Monaco. Nhưng pattern này được dùng rộng rãi trong enterprise Dynatrace deployments, được đề cập trong Dynatrace community forums, và hoạt động production-ready. Tương tự cách Terraform không có native ArgoCD provider nhưng mọi người vẫn dùng kubernetes_manifest resource để quản lý ArgoCD Applications.

3. Pattern A: ArgoCD PostSync Hook — “Deploy xong app, cập nhật monitoring”

Scenario — Khi nào bạn cần Pattern này

Bạn merge PR cho app payment-service v2.1.0. ArgoCD sync → deploy new pods → health check pass → app healthy. Giờ bạn muốn TỰ ĐỘNG:

  • Update dashboard title thành “Payment Service v2.1.0”
  • Thêm SLO mới cho endpoint /api/v2/refunds (feature mới trong v2.1.0)
  • Adjust alerting threshold cho feature flag express-checkout (cần latency cao hơn vì gọi 3rd party)
  • Update management zone để include new service tags

PostSync Hook làm chính xác điều này: chạy Monaco SAU KHI app đã deploy thành công.

Flow chi tiết — 6 bước PostSync

┌─────────────────────────────────────────────────────────┐
│ STEP 1: ArgoCD Sync Start                               │
│   ArgoCD detect Git change → begin sync                 │
├─────────────────────────────────────────────────────────┤
│ STEP 2: Deploy K8s Resources (Wave 0)                   │
│   → Create/Update Deployments, Services, ConfigMaps     │
│   → payment-service pods rolling update to v2.1.0       │
├─────────────────────────────────────────────────────────┤
│ STEP 3: Health Assessment                               │
│   → ArgoCD waits: "Are all new pods Running?"           │
│   → "Do services have healthy endpoints?"               │
│   → "Is rollout complete (no old ReplicaSets)?"         │
│   → ✅ All healthy → proceed to hooks                  │
├─────────────────────────────────────────────────────────┤
│ STEP 4: PostSync Hook Triggered (Wave 5)                │
│   → ArgoCD creates K8s Job: monaco-postsync-<hash>      │
│   → Job starts init container: git clone configs repo   │
├─────────────────────────────────────────────────────────┤
│ STEP 5: Monaco Container Runs                           │
│   → monaco deploy manifest.yaml --environment prod      │
│   → REST API calls to Dynatrace:                        │
│     PUT /api/v2/settings/objects (SLOs, alerting)        │
│     PUT /api/config/v1/dashboards/<id> (dashboard)       │
│   → Exit code 0 = success                               │
├─────────────────────────────────────────────────────────┤
│ STEP 6: Cleanup                                         │
│   → HookSucceeded policy → ArgoCD deletes Job           │
│   → ArgoCD sync status = Healthy ✅                     │
│   → If Job failed → sync status = Degraded ⚠️           │
└─────────────────────────────────────────────────────────┘

K8s Job Manifest — Giải thích từng field quan trọng

Giải thích từng annotation quan trọng

argocd.argoproj.io/hook: PostSync

Chạy SAU KHI tất cả resources ở sync wave hiện tại đã healthy. Đây là điểm mấu chốt: nếu app deploy fail (pod crash, image pull error) → PostSync hook KHÔNG chạy → Monaco không deploy config cho app không tồn tại → đúng behavior mong muốn. ArgoCD hỗ trợ các hook types khác:

Hook TypeKhi nào chạyUse case
PreSyncTrước khi sync bắt đầuDB migration, schema validation
SyncCùng lúc với syncSidecar config, supplementary resources
PostSyncSau khi sync thành côngMonaco deploy, smoke tests, notifications
SyncFailKhi sync thất bạiAlert, cleanup, rollback trigger
PostDeleteSau khi resource bị xoáCleanup external resources

argocd.argoproj.io/hook-delete-policy: HookSucceeded

Cleanup Job sau khi succeed. Không để completed Jobs chất đống trong cluster (mỗi sync tạo 1 Job → 100 syncs = 100 completed Jobs nếu không cleanup). Có 3 policy options:

PolicyBehaviorKhi nào dùng
HookSucceededXoá Job khi exit code 0Default choice — giữ cluster sạch
HookFailedXoá Job khi exit code != 0Khi muốn giữ failed Jobs để kubectl logs debug
BeforeHookCreationXoá Job cũ trước khi tạo mớiTránh “Job already exists” khi re-sync

argocd.argoproj.io/sync-wave: "5"

Wave number quyết định thứ tự deploy. ArgoCD deploy resources theo wave tăng dần: wave -2 trước, rồi -1, rồi 0… Tại sao Monaco ở wave 5?

  • Wave 0 = app chính (Deployments, Services) — đây là default wave
  • Wave 5 = chạy SAU app đã deploy xong ở wave 0
  • Nếu đặt Monaco ở wave 0 → Monaco chạy SONG SONG với app → có thể fail vì Dynatrace entity cho service chưa tồn tại (OneAgent chưa kịp discover)
  • Giống Helm hook-weight: số nhỏ chạy trước, số lớn chạy sau

Dùng generateName thay name khi re-sync nhiều lần

Nếu dùng name: monaco-postsync và ArgoCD re-sync (manual hoặc auto), K8s sẽ báo “Job already exists” vì Job cũ có thể chưa được cleanup. Dùng generateName: monaco-postsync- → K8s tự append random suffix mỗi lần (monaco-postsync-x7k2q) → không bao giờ conflict. Kết hợp với hook-delete-policy: BeforeHookCreation để chắc chắn.

Job PHẢI có restartPolicy: Never

Nếu dùng restartPolicy: Always hoặc OnFailure, K8s sẽ restart container vô hạn khi Monaco exit (kể cả exit code 0, vì container “exited” = cần restart theo policy). Kết quả: Job không bao giờ complete → ArgoCD sync đứng vĩnh viễn ở PostSync phase → cần manual intervention. Never = container exit → Job complete (success hoặc fail) → ArgoCD tiếp tục lifecycle.

Tại sao dùng init container pattern cho git-clone?

Bạn có thể hỏi: “Tại sao không bake Monaco configs vào Docker image luôn?” — Init container pattern có 3 lợi ích:

  1. Luôn lấy config mới nhất — git clone --depth=1 --branch=main đảm bảo lấy HEAD mới nhất, không phụ thuộc vào thời điểm build image
  2. Tách biệt concerns — Monaco image chỉ chứa binary, không chứa config. Config thay đổi thường xuyên hơn Monaco version → tách ra = build ít image hơn
  3. Reusable — cùng 1 Job template dùng cho mọi environment, chỉ đổi biến TARGET_ENV và GIT_REPO_URL

So sánh: init container pattern giống initContainers trong Istio sidecar injection — setup environment trước khi main container chạy. Hoặc giống terraform init trước terraform apply.

Khi nào dùng Pattern A — và khi nào KHÔNG dùng

Dùng khi:

  • App code và Monaco configs cùng repo (hoặc cùng sync cycle)
  • Team nhỏ-trung (1-3 teams), không cần RBAC phức tạp
  • Muốn atomic deployment: app + monitoring config deploy cùng lúc
  • Prototype/PoC nhanh — setup đơn giản nhất

KHÔNG dùng khi:

  • Monaco configs thay đổi độc lập với app deployment (vd: SRE team update SLO mỗi sprint nhưng app không deploy)
  • Cần multi-environment deploy từ 1 template (→ dùng Pattern B)
  • Hệ thống phức tạp với >5 components cần lifecycle riêng (→ dùng Pattern C)

4. Pattern B: ApplicationSet Multi-Environment

Scenario — DRY principle cho multi-env

Bạn có 3 environments: dev, staging, prod. Mỗi env cần 1 ArgoCD Application riêng cho Monaco configs. Nếu viết 3 Application YAML riêng biệt:

# Bạn sẽ phải maintain 3 files gần giống nhau:
monaco-dev.yaml      → path: overlays/dev, cluster: dev-cluster
monaco-staging.yaml  → path: overlays/staging, cluster: staging-cluster
monaco-prod.yaml     → path: overlays/prod, cluster: prod-cluster

3 files thì OK. Nhưng khi có 10 environments? 20 tenants? Copy-paste 20 files → sửa 1 field → phải sửa 20 files → chắc chắn quên 1-2 files → drift.

ApplicationSet giải quyết: 1 template + 1 generator = N Applications tự động. Giống Terraform for_each — 1 resource definition, N instances. Hoặc giống Helm range loop.

ApplicationSet Manifest — giải thích chi tiết

Khi apply ApplicationSet này, ArgoCD sẽ tự động tạo 3 Applications: monaco-dev, monaco-staging, monaco-prod. Thêm 1 element vào generator → tự có Application thứ 4. Xoá element → Application bị xoá (nếu prune: true trong ApplicationSet policy).

Generator Types — Chọn đúng generator cho đúng use case

GeneratorMô tảUse caseVí dụ cụ thể

Git DirectoryScan directories trong Git repoMỗi team/tenant có folder riêng, tự phát hiện team mớiteams/team-a/, teams/team-b/ → auto-create Applications

Git Directory generator — Self-service cho teams

Đây là generator mạnh nhất cho enterprise. Khi dùng Git Directory generator, team mới chỉ cần tạo folder teams/team-xyz/ với Kustomize overlay → ApplicationSet TỰ ĐỘNG tạo Application cho team đó → không cần platform team intervention. Đây là true self-service GitOps — platform team cung cấp infrastructure (ApplicationSet template), product teams tự quản config (folder trong repo).

5. Pattern C: App of Apps — Enterprise architecture

Concept — Microservices cho GitOps

Khi hệ thống phức tạp (>5 services, >3 teams, cần RBAC per-component), Pattern A và B bắt đầu chạm giới hạn. App of Apps giải quyết bằng cách tạo hierarchy:

  • 1 Root Application = “parent” — quản lý lifecycle của tất cả child Applications
  • N Child Applications = “children” — mỗi child quản lý 1 component (frontend, backend, operator, monaco)
  • ArgoCD sync Root → tạo/update tất cả Children → Children sync resources riêng

So sánh: App of Apps giống microservices architecture cho GitOps — mỗi component có lifecycle riêng, team riêng, RBAC riêng, sync policy riêng. Root Application giống API Gateway — entry point duy nhất, route đến đúng service.

6. Sync Wave Ordering — Thứ tự quan trọng hơn bạn nghĩ

Tại sao sai thứ tự = cascading failures

Hãy xem scenario thực tế: team deploy full stack mới, tất cả resources cùng sync wave 0 (default). Chuyện gì xảy ra?

  1. ArgoCD sync → deploy tất cả cùng lúc: Namespace, DT Operator, App Deployments, Ingress, Monaco Job
  2. Monaco Job bắt đầu chạy → gọi monaco deploy → cố tạo SLO cho payment-service
  3. Nhưng payment-service Deployment chưa Ready (đang pull image) → OneAgent chưa discover service → Dynatrace entity chưa tồn tại
  4. Monaco SLO config reference type(SERVICE),entityName("payment-service") → entity not found → deploy fail
  5. ArgoCD báo sync failed → team panic → debug 30 phút → phát hiện chỉ vì thứ tự sai

Sync waves ngăn chặn scenario này bằng cách đảm bảo thứ tự: resources ở wave thấp deploy trước, wave cao deploy sau. ArgoCD wait cho mọi resource ở wave N healthy trước khi bắt đầu wave N+1.

Recommended Sync Waves — Giải thích từng wave

WaveComponentTại sao ở wave này
-2Namespaces, CRDsPhải tồn tại trước MỌI THỨ. CRDs định nghĩa custom resource types — nếu chưa có CRD, K8s không hiểu DynaKube CR. Namespace phải có trước khi tạo resource trong đó. Tương tự terraform phải tạo VPC trước khi tạo subnets.
-1Dynatrace Operator + DynaKube CROperator cần thời gian init: download OneAgent, inject vào node, start CSI driver. Nếu ở wave 0 cùng app → app pods có thể start trước OneAgent inject → miss initial transactions. Wave -1 cho Operator thời gian setup.
0Application Deployments, ServicesWorkload chính. Đây là default wave — resources không có annotation sync-wave tự động ở wave 0. App cần chạy trước Monaco vì Monaco config reference app entities.
1Ingress, NetworkPoliciesRouting cần app healthy trước. Ingress controller check backend health → nếu app chưa ready → Ingress báo 503. NetworkPolicies cần namespaces và pods tồn tại.
5Monaco PostSync JobChạy CUỐI CÙNG sau khi mọi thứ healthy. Gap lớn (0→5 thay vì 0→2) là intentional — để room cho future resources ở wave 2, 3, 4 mà không cần re-number. Tương tự Helm hook weight convention: dùng 5, 10, 20 thay vì 1, 2, 3.

Code examples — Annotations trên resources

Sync wave vs Hook — Hai concept khác nhau nhưng bổ sung

Sync wave quyết định thứ tự deploy TRONG cùng 1 sync phase. Hook quyết định resource chạy ở PHASE nào (PreSync, Sync, PostSync). Monaco Job thường dùng CẢ HAI: hook: PostSync (chạy ở phase PostSync) + sync-wave: "5" (nếu có nhiều PostSync hooks, chạy theo thứ tự wave). Giống ArgoCD Sync Phase giống Terraform lifecycle (create_before_destroy), Sync Wave giống Terraform depends_on — nhưng dùng số thay vì explicit reference.

Khi nào dùng mono-repo:

  • Team size < 20 người
  • 1 team (hoặc vài team làm việc chung) own tất cả configs
  • Release cycle đồng nhất (mọi thứ deploy cùng lúc)
  • Đơn giản hoá CI/CD — 1 pipeline cho tất cả

Option B: Multi-repo — Cho enterprise với team ownership rõ ràng

Repo 1: dynatrace-configs-platform     # Platform/SRE team owns
  └── management-zones, auto-tags, base alerting profiles

Repo 2: dynatrace-configs-frontend     # Frontend team owns
  └── dashboards, SLOs, synthetic monitors cho frontend

Repo 3: dynatrace-configs-backend      # Backend team owns
  └── dashboards, SLOs cho backend APIs

Repo 4: dynatrace-configs-sre          # SRE team owns
  └── alerting profiles, notification channels, global SLOs

Repo 5: gitops-root                    # Platform team owns
  └── Root Application + Child Application definitions

Khi nào dùng multi-repo:

  • Team ownership rõ ràng — CODEOWNERS per repo, không ai sửa nhầm config team khác
  • Các team có release cycle khác nhau — frontend deploy hàng ngày, platform deploy hàng tháng
  • Cần RBAC granular — backend devs không có access vào SRE alerting repo
  • Compliance yêu cầu audit trail per-team

Best Practices — Bất kể mono hay multi-repo

1. Tách Monaco configs khỏi application code

Đừng đặt Monaco YAML trong cùng repo với source code (src/, go.mod, package.json). Monaco configs thay đổi theo monitoring needs, app code thay đổi theo feature needs — lifecycle khác nhau. Nếu cùng repo: mỗi lần update dashboard title = 1 commit trong app repo = trigger CI build cho app → waste resources.

2. Version-control delete.yaml — biết chính xác cái gì bị xoá

Khi xoá Dynatrace config, Monaco cần delete.yaml explicit. File này PHẢI ở trong Git — không ai được xoá config bằng cách chạy Monaco local với adhoc delete file. Git history cho delete file = audit trail: ai quyết định xoá SLO cũ, khi nào, tại sao.

3. Environment-specific values qua Monaco environment YAML, KHÔNG hardcode

Sai: url: https://abc12345.live.dynatrace.com trong config template
Đúng: url: {{ .Env.DT_ENV_URL }} hoặc dùng Monaco environment file với token references

4. README.md với setup guide đầy đủ

Phải trả lời: (a) Cách setup local development (clone, install Monaco, cần tokens gì), (b) Cách contribute (branch strategy, PR template), (c) Cách rollback, (d) Cách thêm environment mới.

5. Branch protection + required reviewers

main branch phải có: required PR review (ít nhất 1 reviewer), CI checks pass (dry-run), no force push. Production-impacting changes (alerting, SLOs) nên require 2 reviewers.

6. Semantic commit messages

chore(alerting): update critical threshold for payment-service
feat(dashboard): add SRE golden signals dashboard
fix(slo): correct latency SLO target from 99 to 99.9

Giúp Git history readable, auto-generate changelog, dễ debug “change nào gây issue”.

8. ArgoCD Notifications → Dynatrace Events API

Tại sao Dynatrace cần biết khi nào deployment xảy ra

Đây là phần thường bị bỏ qua nhưng cực kỳ có giá trị. Davis AI — engine phát hiện và phân tích problems của Dynatrace — sử dụng deployment events để correlate problems với changes.

Hãy xem 2 scenarios:

Scenario A — KHÔNG có deployment event:

  1. Team deploy payment-service v2.1.0 lúc 14:00
  2. Response time tăng 200% lúc 14:05
  3. Davis phát hiện problem: “Response time degradation on payment-service”
  4. Root cause analysis: “Increased traffic?” “Database slow?” “Network issue?” — Davis đoán nhưng không chắc
  5. Team mất 30 phút debug → phát hiện v2.1.0 có N+1 query bug

Scenario B — CÓ deployment event:

  1. ArgoCD deploy payment-service v2.1.0 lúc 14:00 → gửi deployment event đến Dynatrace
  2. Response time tăng 200% lúc 14:05
  3. Davis phát hiện problem: “Response time degradation on payment-service — likely caused by deployment: payment-service v2.1.0 (deployed 5 minutes ago)”
  4. Team ngay lập tức biết nguyên nhân → rollback v2.1.0 → response time bình thường
  5. Debug time: 5 phút thay vì 30 phút

Deployment marker = correlation gold. Mỗi deployment event là data point giúp Davis AI loại trừ nguyên nhân và tập trung vào root cause thật.

ArgoCD Notifications Webhook Configuration

ArgoCD có built-in Notifications controller — gửi webhook khi sync events xảy ra. Cấu hình qua ConfigMap:

SDLC Event Types — Dynatrace hiểu event nào

Dynatrace hỗ trợ Software Development Lifecycle (SDLC) events — đây là schema chuẩn cho deployment tracking:

Event TypeMục đíchDavis AI sử dụng
CUSTOM_DEPLOYMENTĐánh dấu deployment xảy raCorrelation: link problem → deployment gần nhất
CUSTOM_INFOThông tin bổ sung (sync failed, config changed)Context cho investigation
CUSTOM_ANNOTATIONAnnotation trên timelineVisual marker trên dashboard charts

Properties quan trọng mà Davis AI sử dụng:

PropertyMục đích
dt.event.deployment.nameTên deployment — hiển thị trong problem card
dt.event.deployment.versionVersion — Git commit SHA hoặc app version tag
dt.event.deployment.projectGrouping — nhóm deployments theo project
dt.event.deployment.remediation_action_typeGợi ý action khi problem detected (vd: rollback)

Deployment marker = tự động Root Cause Analysis

Khi Davis phát hiện anomaly SAU deployment event (trong window 30 phút mặc định), nó tự động tag problem là “likely caused by deployment” và hiển thị deployment info trong problem card. Điều này giúp team skip bước “gì vừa thay đổi?” — Davis đã trả lời sẵn. Trong production với hàng chục deployments/ngày, đây là tiết kiệm hàng giờ debug mỗi tuần.

Annotation trên ArgoCD Application để subscribe notifications

Mỗi Application cần annotation này để “opt-in” vào notification. Không có annotation = không gửi event. Thiết kế này cho phép selective notification — không phải mọi Application đều cần gửi event đến Dynatrace (vd: ArgoCD system apps không cần).

Starting Recommendation

Nếu bạn mới bắt đầu: dùng Pattern A cho PoC. Setup 30 phút, prove value nhanh. Deploy 1 alerting profile + 1 dashboard qua PostSync Hook → thấy nó hoạt động → team buy-in.

Khi scale lên production: chuyển sang Pattern B khi có >2 environments. ApplicationSet giúp DRY — 1 template, N envs. Đây là sweet spot cho đa số teams.

Khi enterprise cần: dùng Pattern C khi có nhiều teams, nhiều components, cần RBAC per-component. Setup phức tạp hơn nhưng scale tốt nhất.

Các pattern KHÔNG exclusive — có thể kết hợp

Trong thực tế, enterprise thường dùng Pattern C (App of Apps) + Pattern B (ApplicationSet cho Monaco child) — Root Application chứa child Application cho Monaco, child Application đó dùng ApplicationSet để generate per-environment configs. Đây là combination phổ biến nhất trong production.
