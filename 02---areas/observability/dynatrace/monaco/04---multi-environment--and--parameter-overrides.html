1. Tại Sao Cần Multi-Environment — Vấn Đề Thực Tế

Trước khi viết bất kỳ dòng YAML nào, hãy hiểu tại sao multi-environment là vấn đề cốt lõi mà mọi team Observability phải giải quyết.

Scenario thực tế

Hãy tưởng tượng bạn quản lý 3 environments: dev, staging, prod. Cả 3 đều cần:

  • SLO cho response time — nhưng target khác nhau:

    • dev: 95% (code đang phát triển, chấp nhận fail nhiều)
    • staging: 98% (gần prod, nhưng vẫn có buffer)
    • prod: 99.5% (phản ánh SLA thật với khách hàng)

  • Alerting profile — nhưng behavior khác nhau:

    • dev: gửi Slack chỉ trong giờ làm việc (9AM-6PM), delay 30 phút trước khi alert (tránh noise khi test)
    • staging: gửi Slack 24/7, delay 10 phút
    • prod: gửi PagerDuty lúc 3AM nếu cần, delay 0 (immediate), escalate sau 5 phút

  • Dashboard — hiển thị cùng layout nhưng:

    • dev: filter Management Zone Dev Apps
    • staging: filter Staging Apps
    • prod: filter Production Apps

Nhìn vào 3 ví dụ trên, bạn thấy pattern rõ ràng: cùng config structure, khác GIÁ TRỊ. Copy-paste 3 bản config riêng biệt cho 3 env? Chắc chắn sẽ drift — khi bạn thêm 1 metric mới vào dashboard prod, bạn quên thêm vào dev. Khi bạn sửa alerting condition ở staging, bạn quên cập nhật prod.

Monaco giải quyết bài toán này bằng environmentOverrides — 1 template duy nhất, giá trị khác nhau per environment. Và đây không chỉ là syntax sugar — nó là architectural decision buộc bạn phải suy nghĩ: “cái gì THẬT SỰ khác giữa các env, cái gì chỉ là implementation detail?”

So sánh với tools quen thuộc

Nếu bạn đã dùng các IaC tools khác, concept này rất quen:

ToolCơ chế multi-envTương đương Monaco
Terraformterraform.tfvars per workspace, hoặc -var-file=prod.tfvarsenvironmentOverrides trong config.yaml
Helmvalues-dev.yaml, values-prod.yaml → helm install -f values-prod.yamlenvironmentGroups + overrides
Kustomizeoverlays/dev/, overlays/prod/ mỗi overlay patch basegroupOverrides (patch theo nhóm)
Ansiblegroup_vars/, host_vars/ override group_varsenvironmentOverrides > groupOverrides > base

Bản chất giống nhau: tách biệt “template/structure” khỏi “values/parameters”. Monaco manifest tương tự Terraform backend config — nó nói cho tool biết nơi deploy, nhưng không chứa config thật. Config nằm trong project directories, values nằm trong overrides.

Tư duy quan trọng

Khi thiết kế multi-env configs, bắt đầu bằng câu hỏi: “Cái gì giống nhau giữa dev và prod?” — đó là base config. “Cái gì khác?” — đó là overrides. Nếu 80% config giống nhau, bạn đang đi đúng hướng. Nếu chỉ 30% giống nhau, có lẽ bạn cần 2 projects riêng biệt thay vì overrides.

2. manifest.yaml Multi-Environment — Blueprint Của Toàn Bộ Deployment

manifest.yaml là entry point — nơi Monaco biết nó sẽ deploy ĐẾN ĐÂU, deploy CÁI GÌ, và authenticate BẰNG GÌ. Trong setup multi-environment, đây là file quan trọng nhất cần thiết kế kỹ.

Full manifest với 2 environmentGroups

Giải thích từng field — và TẠI SAO nó được thiết kế như vậy

Không chỉ “field X làm gì”, mà tại sao Dynatrace team thiết kế nó theo cách này:

environmentGroups — Tại sao group thay vì flat list?

Nếu bạn có 5 environments (dev, qa, staging, perf-test, prod), liệu bạn muốn viết overrides cho TỪNG cái? Không. Thông thường, dev/qa/staging/perf-test đều có chung đặc tính “non-prod” — threshold relaxed, alerting gửi Slack, retention thấp. Chỉ prod mới strict. Group cho phép bạn apply groupOverrides — tất cả non-prod environments tự động có threshold relaxed, production strict — mà không cần repeat.

Tương tự Ansible group_vars/non-prod/ vs host_vars/dev/ — group-level defaults, host-level overrides.

url.type: environment — Tại sao không nhập URL trực tiếp?

Value DT_DEV_URL là TÊN environment variable, KHÔNG phải URL. Đây là design decision cực kỳ quan trọng: manifest.yaml commit vào Git — nếu chứa URL trực tiếp, bạn lộ internal infrastructure information (Dynatrace tenant ID, region). Với type: environment, manifest chỉ chứa tên biến, giá trị thật nằm trong CI/CD secrets hoặc .env file (đã gitignore).

Tương tự cách Terraform backend config dùng partial configuration — bạn define backend type trong code, nhưng inject credentials lúc terraform init -backend-config=....

auth.token.name — Cùng lý do security: chỉ chứa tên biến, không chứa secret.

Sai lầm phổ biến nhất

Nhiều người mới viết value: "https://abc12345.live.dynatrace.com" trực tiếp trong manifest. Monaco vẫn chạy (nếu dùng type: value), nhưng bạn vừa commit URL tenant vào Git. Với type: environment, bạn an toàn — manifest chỉ là “map tên biến”, giá trị inject lúc runtime.

Set environment variables cho lab

Lab hack: 1 trial account, nhiều environments

Với 1 trial account, bạn vẫn test được multi-env flow: define 2 environments (dev và staging) trỏ cùng URL nhưng khác tên. Monaco deploy 2 lần với parameters khác nhau — cùng Dynatrace tenant sẽ có 2 sets configs (ví dụ: “Response Time SLO - dev” và “Response Time SLO - staging”). Đủ để verify logic override hoạt động mà không cần 3 trial accounts.

Trong CI/CD thật, mỗi env sẽ trỏ URL khác nhau — nhưng nguyên lý override vẫn giống hệt.

3. Environment Overrides — Cùng Template, Khác Giá Trị

Đây là trái tim của multi-environment trong Monaco. environmentOverrides cho phép bạn define base parameters cho tất cả environments, rồi override từng giá trị cụ thể cho environment đó.

Cơ chế hoạt động — Mental model

Monaco đọc config theo thứ tự:

flowchart TD
    A["Base Parameters<br/>(trong config.yaml)"] --> B{"Environment<br/>có override?"}
    B -->|Có| C["Merge: override<br/>THAY THẾ base value"]
    B -->|Không| D["Dùng base value<br/>nguyên bản"]
    C --> E["Config cuối cùng<br/>cho env đó"]
    D --> E

Quan trọng: override THAY THẾ (replace) base value — không append, không merge deep. Nếu base có target: 99.5 và override có target: 95.0, kết quả là 95.0, không phải [99.5, 95.0].

Giống CSS specificity: environment-specific > group-specific > base. Cụ thể nhất thắng.

Ví dụ 1: SLO với threshold khác nhau per env

Template — projects/shared-infra/slo/slo-response-time.json:

Template này là skeleton — nó define structure, nhưng giá trị target và warning đến từ parameters. Giống Helm template dùng {{ .Values.target }}.

Config — projects/shared-infra/slo/config.yaml:

Kết quả deploy — mỗi environment nhận giá trị khác nhau:

EnvironmentSLO TargetWarningÝ nghĩa thực tế
dev95.0%97.0%Thoải mái — code đang dev, services restart liên tục, test data không ổn định
staging98.0%99.0%Gần prod — integration tests chạy ở đây, muốn biết sớm nếu có performance regression
prod99.5%99.9%Strict nhất — SLA cam kết với khách hàng, warning cực sát target để catch vấn đề TRƯỚC khi breach

Tại sao base parameters nên là production-safe?

Nhìn vào config trên, base target: 99.5 và warning: 99.0 đều là giá trị prod. Đây là best practice: default phải là giá trị an toàn nhất (production). Non-prod overrides relaxed (giảm xuống). Lý do: nếu bạn quên viết override cho 1 env mới, nó sẽ nhận base value — tức production-safe. Ngược lại, nếu base là dev-relaxed (target: 95.0) và bạn quên override prod → prod chỉ monitor ở 95% → SLA breach mà không biết.

Tương tự nguyên tắc “fail-safe” trong engineering: mặc định phải là trạng thái AN TOÀN NHẤT.

Ví dụ 2: Alerting profile — dev relaxed, prod strict

Chú ý: prod không có override — nó dùng base values. Đây là pattern lý tưởng khi base đã là production-safe.

Ví dụ 3: Dashboard với Management Zone khác nhau

{{ .Env.name }} — built-in variable

Monaco tự inject tên environment hiện tại vào {{ .Env.name }}. Bạn không cần define parameter cho nó. Rất tiện để tạo tên config unique per env (ví dụ “Response Time SLO - dev”, “Response Time SLO - prod”) mà không cần override trường name.

Tương tự Terraform terraform.workspace — một biến context tự có sẵn.

4. Group Overrides vs Environment Overrides — Khi Nào Dùng Gì?

Đây là câu hỏi mà nhiều người mới dùng Monaco bối rối. Cả hai đều “override base parameters”, nhưng ở phạm vi khác nhau.

Override Hierarchy — Thứ tự ưu tiên

flowchart TD
    BASE["🔵 Base Parameters<br/>(config.yaml)"] --> GROUP["🟡 Group Overrides<br/>(groupOverrides)"]
    GROUP --> ENV["🔴 Environment Overrides<br/>(environmentOverrides)"]
    ENV --> FINAL["✅ Final Config<br/>cho environment cụ thể"]

    style BASE fill:#e3f2fd
    style GROUP fill:#fff9c4
    style ENV fill:#ffcdd2
    style FINAL fill:#c8e6c9

Thứ tự ưu tiên: environmentOverrides > groupOverrides > base parameters

Giống CSS: inline style (environmentOverrides) > class style (groupOverrides) > default style (base). Cụ thể nhất luôn thắng.

Khi nào dùng groupOverrides?

Dùng khi tất cả environments trong 1 group có chung config. Ví dụ: tất cả non-prod (dev, qa, staging, perf-test) đều dùng:

  • SLO target 95%
  • Alert delay 30 phút
  • Notification qua Slack

Thay vì viết 4 environmentOverrides giống hệt nhau cho dev/qa/staging/perf-test, viết 1 groupOverrides cho group non-prod.

Khi nào dùng environmentOverrides?

Dùng khi cần giá trị khác nhau giữa các environments TRONG CÙNG group. Ví dụ: dev cần SLO 95%, staging cần 98% — cả hai đều trong group non-prod, nhưng cần giá trị khác nhau.

Full code example: Kết hợp cả hai

Kết quả cuối cùng cho mỗi environment:

Environmenttargetwarningevaluation_windowNguồn quyết định
dev95.097.0-1dgroup non-prod
qa95.097.0-1dgroup non-prod
staging98.099.0-1denv override > group
perf-test95.097.0-1dgroup non-prod
prod99.599.9-1Mgroup production override evaluation_window, base cho target/warning

Staging nhận target: 98.0 từ environmentOverrides (thắng group default 95.0), nhưng giữ evaluation_window: "-1d" từ group (vì env override không đề cập field này).

Edge case: override partial parameters

Override chỉ thay thế parameters được liệt kê. Nếu group override có target: 95.0 và warning: 97.0, nhưng env override chỉ có target: 98.0 — kết quả sẽ là target: 98.0 (từ env) + warning: 97.0 (từ group, vì env không override field này). Monaco KHÔNG discard toàn bộ group override khi có env override — nó merge thông minh.

Tuy nhiên, nếu env override có cùng field với group → env thắng. Chỉ các field KHÔNG CÓ trong env override mới fallback về group.

5. Selective Deployment — Deploy Đúng Thứ, Đúng Nơi

Trong thực tế, bạn hiếm khi deploy TẤT CẢ configs vào TẤT CẢ environments cùng lúc. Monaco cho phép pinpoint deployment bằng các flags -e (environment) và -p (project).

Deploy chỉ 1 environment

Use case: Bạn đang hotfix alerting profile cho dev environment. Team dev phàn nàn alert noise quá nhiều, bạn tăng delay từ 10 phút lên 30 phút. Bạn muốn deploy ngay vào dev mà không đụng staging hay prod (đang ổn định cho release Friday).

Pattern này giống helm upgrade -n dev-namespace — bạn chọn chính xác target.

Deploy chỉ 1 project

Use case: Team Platform vừa thêm 3 auto-tagging rules mới vào project shared-infra. Họ muốn deploy rules này mà không deploy project app-monitoring (đang có PR pending review). Flag -p cho phép team-level autonomy — mỗi team chỉ deploy configs của mình.

Kết hợp: pinpoint deployment

Đây là mức granularity cao nhất — bạn biết chính xác cái gì sẽ deploy, vào đâu. Trong CI/CD production pipeline, đây là cách deploy khuyến nghị.

Dry-run trước khi deploy thật

Dry-run validate configs mà không gửi API call tới Dynatrace. Tương tự terraform plan nhưng không show diff (vì Monaco không có state file) — nó chỉ validate syntax, schema, dependencies.

Không dùng -e = deploy TOÀN BỘ environments

Khi bạn chạy monaco deploy manifest.yaml không có flag -e, Monaco deploy vào MỌI environment trong manifest. Trong lab thì vô hại — nhưng trong CI/CD pipeline, đây là bom hẹn giờ. Ai đó thêm environment prod-eu vào manifest, pipeline cũ không có -e → tự động deploy vào prod-eu chưa qua review.

Rule cứng cho CI/CD: LUÔN specify -e trong pipeline. Không bao giờ deploy “tất cả” trong automation.

Use cases tổng hợp

ScenarioCommandLý do
Test config mới ở dev-e devKhông muốn ảnh hưởng staging/prod
Hotfix alerting ở prod-e prod -p shared-infraPinpoint, không đụng app configs

6. Grouping Projects — Tổ Chức Configs Cho Team Lớn

Khi team scale lên (5+ người, 50+ configs), flat list projects trong manifest trở nên khó quản lý. Monaco hỗ trợ grouping projects — tạo hierarchy giúp tổ chức theo team, domain, hoặc service.

Deploy commands với grouping

Team ownership pattern

Grouping projects cho phép mỗi team sở hữu folder riêng trong cùng 1 repo. Combine với CODEOWNERS file:

# .github/CODEOWNERS
projects/app-configs/frontend/  @team-frontend
projects/app-configs/backend/   @team-backend
projects/app-configs/mobile/    @team-mobile
projects/shared-infra/          @team-platform

Khi team frontend tạo PR sửa projects/app-configs/frontend/, chỉ @team-frontend cần review. Platform team review shared-infra. Tương tự monorepo pattern trong microservices.

7. Template Reuse Best Practices

Một trong những lỗi phổ biến nhất khi dùng Monaco là copy-paste templates. Bạn tạo SLO template cho frontend, rồi copy sang backend, sửa 2 dòng. 6 tháng sau, khi Dynatrace update SLO schema, bạn phải sửa 10 copies. Template reuse giải quyết vấn đề này.

Nguyên tắc DRY: 1 template, nhiều config entries

3 SLOs, 1 template. Khi Dynatrace thay đổi SLO schema, bạn sửa 1 file slo-template.json → tất cả 3 configs cập nhật. Giống Helm template được dùng cho nhiều releases.

Shared templates strategy — Cross-project reuse

Khi nhiều projects cần cùng template (ví dụ cả frontend và backend đều tạo SLOs), đặt templates vào folder shared:

projects/
├── _shared-templates/                 # Convention: prefix _ để sort lên đầu
│   ├── slo-template.json
│   ├── alerting-template.json
│   └── dashboard-template.json
├── app-configs/
│   ├── frontend/
│   │   └── slo/
│   │       └── config.yaml           # template: ../../../_shared-templates/slo-template.json
│   └── backend/
│       └── slo/
│           └── config.yaml           # template: ../../../_shared-templates/slo-template.json
└── shared-infra/
    └── slo/
        └── config.yaml               # template: ../../_shared-templates/slo-template.json

Config.yaml reference template bằng relative path từ folder chứa config.yaml:

Relative path dễ sai

Khi dùng shared templates, đếm số ../ cẩn thận. Relative path tính từ folder chứa config.yaml, không phải project root hay manifest. Sai 1 cấp ../ = template not found error.

Mẹo: luôn dùng monaco deploy --dry-run sau khi refactor path. Dry-run validate template resolution trước khi deploy thật.

Naming conventions

Đối tượngConventionVí dụLý do

Config IDkebab-case, descriptiveresponse-time-slo, cpu-alert-prodMonaco dùng ID để track — phải unique và stable

Config ID là identity — đổi ID = tạo config mới

Monaco dùng id trong config.yaml để generate externalId — giá trị được lưu trên Dynatrace để track “config này đã deploy chưa, cần update hay tạo mới?”. Nếu bạn đổi id: slo-frontend thành id: frontend-slo, Monaco coi đó là config MỚI → tạo config mới, config cũ thành orphan (vẫn tồn tại trên Dynatrace nhưng Monaco không quản lý nữa).

Tương tự metadata.name trong Kubernetes — đổi name = tạo resource mới, resource cũ vẫn tồn tại.
