Cài Đặt Monaco CLI & First Deploy

⏱️ Thời gian: ~45 phút
📋 Prerequisites: Dynatrace SaaS trial account, terminal (bash/PowerShell), kết nối internet
🔗 Source: Monaco GitHub · Official Docs

Thuộc MOC - Dynatrace · Prev ← 00 - Monaco v2 Overview & Architecture · Next → 02 - Settings 2.0 & Classic API Configs

🎯 Mục Tiêu

Sau khi hoàn thành lab này, bạn sẽ:

  • Cài đặt Monaco CLI trên máy local — hiểu sự khác biệt giữa các phương thức cài đặt
  • Tạo API Token với đúng scopes — hiểu tại sao mỗi scope cần thiết
  • Xây dựng project structure đầu tiên (manifest → project → config → template)
  • Deploy 1 auto-tagging rule vào Dynatrace trial — hiểu behind-the-scenes flow
  • Chứng minh idempotent property qua 3 tests thực tế
  • Chạy dry-run validation — hiểu ứng dụng trong CI/CD pipeline
  • Download config ngược từ Dynatrace về local — hiểu use case bootstrap & drift detection

📚 Kiến Thức Nền

Trước khi bắt tay vào lab, bạn cần nắm vững một số concepts từ 00 - Monaco v2 Overview & Architecture:

  • Monaco là gì: CLI tool chính thức của Dynatrace để quản lý configuration dưới dạng code — viết bằng Go, chạy standalone, không cần runtime
  • 3-layer structure: manifest.yaml (nơi deploy) → project directory (nhóm configs) → config.yaml + template (từng config cụ thể)
  • Settings 2.0 vs Classic API: Settings 2.0 là hướng mới, dùng builtin:* schema. Lab này dùng Settings 2.0 (builtin:tags.auto-tagging)
  • externalId tracking: Monaco generate unique ID cho mỗi config → cho phép update/delete chính xác, không tạo duplicate

Nếu chưa đọc note 00, hãy dừng lại và đọc trước. Lab này assume bạn đã hiểu “tại sao cần Monaco” — ở đây ta sẽ tập trung vào “làm thế nào”.

1. Cài Đặt Monaco CLI

Monaco là single binary viết bằng Go — giống kubectl hay terraform, bạn chỉ cần download 1 file executable. Không dependency, không runtime, không pip install, không npm. Đây là lợi thế lớn của Go: compile thành static binary chạy được ngay trên mọi OS mà không cần cài thêm gì.

Bạn có 3 cách để cài Monaco. Mỗi cách phù hợp với một scenario khác nhau:

Phương thứcKhi nào chọnƯu điểmNhược điểm
Binary downloadLocal development, lab, learningĐơn giản nhất, full control versionPhải tự update
DockerCI/CD pipeline, team shared envVersion consistency, isolated, reproducibleCần Docker runtime
HomebrewmacOS/Linux dev dùng Homebrew sẵnAuto-update, 1 commandChỉ macOS/Linux, version có thể lag

1.1 Option A — Download binary trực tiếp (Recommended cho lab)

Đây là cách nhanh nhất và kiểm soát nhất. Giống cách bạn cài kubectl — download binary, move vào PATH, xong.

macOS (Apple Silicon / Intel):

Cả Linux và macOS đều follow cùng pattern: download → chmod → move. Nếu bạn quen cài kubectl, helm, hay terraform thì flow này hoàn toàn giống — đây là convention chung của CLI tools viết bằng Go.

1.2 Option B — Docker (Recommended cho CI/CD)

Khi nào dùng Docker? Khi bạn cần đảm bảo version consistency giữa các lần chạy. Trong CI/CD pipeline, nếu mỗi runner tự install binary thì có thể bị version mismatch. Docker image pin chính xác version, chạy ở đâu cũng như nhau.

1.3 Option C — Homebrew (macOS / Linux)

Homebrew tiện cho dev dùng macOS hàng ngày — brew upgrade update tất cả tools cùng lúc. Nhược điểm: version trên Homebrew có thể chậm hơn GitHub Releases vài ngày.

1.4 Verify cài đặt

Bất kể cài bằng cách nào, chạy lệnh này để xác nhận Monaco đã sẵn sàng:

Output mong đợi:

Nếu bạn thấy version number thay vì error → Monaco đã cài thành công. Nếu gặp command not found → binary chưa nằm trong PATH, quay lại bước move binary.

Docker là lựa chọn tốt nhất cho CI/CD pipeline

Docker image đảm bảo version consistency — mọi pipeline run đều dùng đúng cùng 1 version, không bị “works on my machine”. Binary download lại tốt nhất cho local development vì nhanh, không cần Docker daemon. Trong thực tế, nhiều team dùng cả 2: binary cho local dev, Docker cho CI/CD.

So sánh cài đặt Monaco vs các CLI tools khác

Cài Monaco giống hệt cài kubectl — download binary, move vào PATH, done. Không pip install (Python dependency hell), không npm install -g (Node.js version conflicts). Go binary là self-contained — tất cả dependencies đã compile sẵn bên trong. Đây là lý do tại sao hầu hết DevOps CLI tools hiện đại (Terraform, Helm, kubectl, k9s) đều viết bằng Go.

2. Tạo API Token — Cánh Cổng Vào Dynatrace API

Tại sao cần API Token?

API Token là cách Monaco authenticate với Dynatrace — chứng minh “tôi có quyền đọc/ghi configurations trong environment này”. Mỗi token có scopes giới hạn chính xác những gì nó được phép làm — giống IAM policy trong AWS hay RBAC ClusterRole trong Kubernetes.

Nếu không có token, hoặc token thiếu scope, Monaco sẽ bị Dynatrace API từ chối với lỗi 401 Unauthorized hoặc 403 Forbidden. Đây là lỗi phổ biến nhất khi mới bắt đầu — và thường do thiếu scope chứ không phải sai token.

sequenceDiagram
    participant Dev as Developer
    participant CLI as Monaco CLI
    participant API as Dynatrace API
    
    Dev->>CLI: monaco deploy manifest.yaml
    CLI->>CLI: Đọc manifest → tìm token env var
    CLI->>API: PUT /api/v2/settings/objects<br/>Header: Authorization: Api-Token dt0c01.xxx
    
    alt Token valid + đủ scopes
        API-->>CLI: 200 OK — config created/updated
        CLI-->>Dev: ✅ Deployed 1 config with 0 errors
    else Token thiếu scope
        API-->>CLI: 403 Forbidden — missing scope settings.write
        CLI-->>Dev: ❌ Error: insufficient permissions
    else Token invalid/expired
        API-->>CLI: 401 Unauthorized
        CLI-->>Dev: ❌ Error: authentication failed
    end

Bước tạo token trên Dynatrace UI

  1. Mở Dynatrace UI → thanh search trên cùng → gõ “Access tokens” → chọn kết quả (hoặc navigate: Manage → Access tokens)
  2. Click Generate new token
  3. Đặt tên: monaco-lab-token (tên gợi nhớ mục đích, dễ identify khi audit)
  4. Trong phần Search scopes, tìm và bật từng scope:
ScopeTên trong UITại sao cần?
ReadConfigRead configurationMonaco cần đọc existing configs để compare trước khi deploy — nếu config đã tồn tại và giống hệt, Monaco skip thay vì tạo duplicate
WriteConfigWrite configurationDeploy Classic API configs (dashboard, alerting-profile…). Dù lab này dùng Settings 2.0, nên cấp sẵn để không bị block khi mở rộng
settings.readRead settingsĐọc Settings 2.0 schemas và objects — Monaco cần verify schema tồn tại trước khi deploy
settings.writeWrite settingsGhi Settings 2.0 objects — đây là scope chính cho lab này vì builtin:tags.auto-tagging là Settings 2.0
  1. Click Generate token
  2. Copy token ngay lập tức — bạn sẽ thấy chuỗi dạng dt0c01.XXXXXXXX.YYYYYYYY...

Token chỉ hiển thị MỘT LẦN duy nhất

Sau khi đóng dialog, bạn không thể xem lại token. Nếu quên copy hoặc mất, phải tạo token mới và revoke token cũ. Đây là security by design — tương tự AWS Access Key hay GitHub Personal Access Token. Lưu tạm vào password manager hoặc biến môi trường ngay.

Set environment variables

Monaco đọc credentials từ environment variables — không hardcode trong file config. Đây là pattern chuẩn mà mọi DevOps tool đều dùng (Terraform dùng TF_VAR_*, kubectl dùng KUBECONFIG, AWS CLI dùng AWS_ACCESS_KEY_ID).

Linux / macOS (bash/zsh):

Windows PowerShell:

Principle of Least Privilege — đừng tạo "god token"

Cho labs, tạo 1 token “all-in-one” với 4 scopes là OK. Nhưng production phải tách:

  • 1 token read-only (ReadConfig + settings.read) — dùng cho monaco download và CI/CD validation
  • 1 token write (WriteConfig + settings.write) — chỉ dùng trong deploy pipeline, restricted access

Lý do: nếu read-only token bị leak, attacker chỉ xem được config (đã thấy trên UI rồi). Nếu write token bị leak → có thể phá toàn bộ monitoring config. Tách token = giảm blast radius.

💡 Tại sao dùng environment variable thay vì hardcode trong manifest?

Đây là câu hỏi mà nhiều người mới bắt đầu thắc mắc: “Sao không viết thẳng URL và token vào manifest.yaml cho tiện?” Ba lý do:

  1. Security: manifest.yaml nằm trong Git repo. Nếu hardcode token → commit secret lên GitHub → bất kỳ ai có access repo đều thấy token. Environment variable không bao giờ nằm trong Git.

  2. Portability: Cùng 1 manifest, dev set DT_ENV_URL=dev-env, staging set DT_ENV_URL=staging-env, production set DT_ENV_URL=prod-env. Manifest không đổi, chỉ env var thay đổi → 1 codebase cho tất cả environments. Giống cách 12-factor app dùng env var cho config.

  3. Rotation: Khi cần rotate token (expired, compromised), bạn chỉ đổi giá trị env var — không cần sửa code, không cần commit, không cần PR review. Trong CI/CD, đổi secret trong GitHub Actions / GitLab CI settings là xong.

Scenario

Bạn muốn tạo 1 auto-tagging rule trong Dynatrace: tự động gắn tag lab-managed cho tất cả Services. Thay vì click trên UI (mất 2 phút, nhưng không reproducible), bạn sẽ define rule này bằng code và deploy bằng Monaco.

3.1 Tạo thư mục

Giải thích cấu trúc:

monaco-first-project/          ← Root folder, nơi chứa manifest
└── projects/                  ← Convention: tất cả projects nằm trong folder này
    └── first-project/         ← Tên project — có thể có nhiều project
        └── auto-tagging/      ← Config type folder — mỗi folder = 1 loại config

Tại sao tách thành folder auto-tagging? Vì khi project lớn lên, bạn sẽ có nhiều config types:

projects/first-project/
├── auto-tagging/          ← Tag rules
├── alerting-profile/      ← Alerting configs
├── management-zone/       ← Management zones
├── dashboard/             ← Dashboards
└── synthetic-monitor/     ← Synthetic tests

Mỗi folder chứa 1 config.yaml + template files riêng. Cấu trúc rõ ràng, dễ navigate — giống cách Helm chart tổ chức templates theo resource type.

3.2 Tạo manifest.yaml — Entry point của project

Đây là file entry point — tương tự main.tf trong Terraform hay Chart.yaml trong Helm. Monaco đọc file này đầu tiên để biết:

  1. Có bao nhiêu project, ở đâu?
  2. Deploy lên environment nào?
  3. Authenticate bằng gì?

Giải thích TỪNG field quan trọng:

manifestVersion: "1.0"
Version của manifest format. Hiện tại chỉ có "1.0" — luôn dùng giá trị này. Khi Dynatrace release format mới, version sẽ tăng và Monaco sẽ backward-compatible.

projects
Danh sách project directories. Mỗi entry có:

  • name: tên logical, dùng trong logs và reference — phải unique trong manifest
  • path: đường dẫn tương đối so với manifest file — không dùng absolute path

environmentGroups
Nhóm environments. Tại sao có concept “group”? Vì trong thực tế, bạn có thể muốn deploy cùng configs lên dev + staging (group “non-prod”) nhưng config khác cho production (group “prod”). Group cho phép batch deploy theo nhóm.

environments[].url.type: environment

Đây là điểm HAY NHẤT và cũng dễ nhầm nhất

Value DT_ENV_URL ở đây KHÔNG PHẢI URL trực tiếp. Nó là TÊN của environment variable chứa URL. Khi Monaco đọc manifest, nó sẽ:

  1. Thấy type: environment → hiểu “đây là tên biến, không phải giá trị”
  2. Đọc env var DT_ENV_URL từ shell
  3. Lấy giá trị https://abc12345.live.dynatrace.com

Thiết kế này đảm bảo manifest KHÔNG chứa secrets và KHÔNG chứa environment-specific values → safe để commit vào Git. Mọi thứ nhạy cảm nằm trong env var, được inject lúc runtime.

auth.token.name: DT_API_TOKEN
Tương tự url.value — đây là tên env var chứa API token, không phải token trực tiếp. Monaco đọc biến DT_API_TOKEN từ shell khi chạy.

Có thể dùng type: value thay vì type: environment

Nếu bạn muốn hardcode URL trực tiếp (chỉ cho test, KHÔNG cho production):

Nhưng KHÔNG BAO GIỜ làm vậy với token — token phải luôn qua env var. URL thì acceptable trong một số trường hợp vì URL không phải secret (ai cũng thấy trên browser).

3.3 Tạo config.yaml cho auto-tagging

Config file này nói cho Monaco biết: “Tôi muốn tạo 1 Settings 2.0 object thuộc schema builtin:tags.auto-tagging, áp dụng cho toàn bộ environment, với payload từ file auto-tag-env.json.”

Giải thích TỪNG field:

id: tag-environment
Unique identifier trong project. Monaco dùng id + project name + schema để tạo externalId — mã định danh duy nhất cho config này trong Dynatrace. ExternalId là cách Monaco biết “config này đã tồn tại, chỉ cần update” thay vì “tạo mới” → đây là nền tảng của idempotent deploy.

Nếu bạn đổi id, Monaco coi đó là config MỚI → tạo thêm 1 tag nữa thay vì update tag cũ. Đây là lỗi phổ biến khi refactor.

config.name: "Environment Tag"
Tên hiển thị, dùng để:

  • Log output khi deploy (Deploying config "Environment Tag"...)
  • Trong một số API, name cũng là identifier trên UI (ví dụ: Classic API dashboard dùng name làm dashboard title)
  • Cho Settings 2.0, name chủ yếu là mô tả — UI lấy tên từ JSON payload

config.template: auto-tag-env.json
File chứa JSON payload gửi tới Dynatrace API. Path tương đối so với folder chứa config.yaml (trong trường hợp này: projects/first-project/auto-tagging/auto-tag-env.json). Đây chính là “nội dung thật” của config — tương tự values.yaml trong Helm.

config.skip: false
Cờ on/off:

  • false = deploy bình thường (default, có thể bỏ qua field này)
  • true = Monaco bỏ qua config này — hữu ích khi muốn tạm disable 1 config mà không xoá code

Khi nào dùng skip: true? Khi bạn đang debug và muốn deploy mọi thứ trừ 1 config cụ thể. Hoặc khi config chưa sẵn sàng nhưng bạn muốn commit code structure trước.

type.settings.schema: builtin:tags.auto-tagging
Schema ID của Settings 2.0. Mỗi loại config trong Dynatrace có 1 schema unique:

  • builtin:tags.auto-tagging → auto-tagging rules
  • builtin:alerting.profile → alerting profiles
  • builtin:anomaly-detection.metric-events → metric events

Bạn có thể list tất cả schemas bằng:

type.settings.scope: environment
Phạm vi áp dụng của config:

  • environment → toàn bộ Dynatrace environment (global)
  • host-<HOST_ID> → chỉ 1 host cụ thể
  • service-<SERVICE_ID> → chỉ 1 service cụ thể
  • Management zone, process group, etc.

Cho auto-tagging rule, environment là scope phổ biến nhất vì tags thường áp dụng global.

💡 Điều gì thực sự xảy ra behind the scenes?

Khi bạn chạy monaco deploy, đây là chính xác những gì xảy ra:

sequenceDiagram
    participant CLI as Monaco CLI
    participant FS as File System
    participant API as Dynatrace API
    
    CLI->>FS: 1. Đọc manifest.yaml
    CLI->>FS: 2. Resolve env vars (DT_ENV_URL, DT_API_TOKEN)
    CLI->>FS: 3. Scan project dirs → tìm config.yaml files
    CLI->>FS: 4. Parse config.yaml → load auto-tag-env.json
    CLI->>CLI: 5. Build dependency graph (DAG)
    CLI->>CLI: 6. Generate externalId từ (project + id + schema)
    
    CLI->>API: 7. PUT /api/v2/settings/objects
    Note right of API: Headers:<br/>Authorization: Api-Token dt0c01.xxx<br/>Content-Type: application/json
    Note right of API: Body: [{<br/>  "schemaId": "builtin:tags.auto-tagging",<br/>  "scope": "environment",<br/>  "externalId": "first-project:tag-environment",<br/>  "value": { ...JSON từ template... }<br/>}]
    
    API-->>CLI: 8. 200 OK + objectId
    CLI->>CLI: 9. Log success

Điểm quan trọng nhất: externalId. Monaco tạo externalId từ project name + config id + schema → đây là “fingerprint” unique cho mỗi config. Khi deploy lần 2, Monaco gửi cùng externalId → Dynatrace biết “config này đã tồn tại, UPDATE thay vì CREATE”.

Lần deploy đầu tiên = CREATE. Từ lần thứ 2 trở đi = UPDATE

Đây là nguyên lý upsert (update or insert) — giống kubectl apply trong Kubernetes. Nếu resource chưa tồn tại → create. Nếu đã tồn tại → update. Nhờ externalId, Monaco không bao giờ tạo duplicate configs, dù bạn chạy deploy bao nhiêu lần.

5. Idempotent Test — Chứng Minh Deploy An Toàn

Tại sao phải test idempotent?

Idempotent nghĩa là: chạy cùng 1 operation bao nhiêu lần cũng ra cùng kết quả. Đây là property QUAN TRỌNG NHẤT của Configuration as Code — nó đảm bảo bạn có thể re-deploy bất kỳ lúc nào mà không sợ side effects:

  • Không tạo duplicate configs
  • Không break existing configs
  • Không gây unexpected state changes

So sánh: idempotent giống kubectl apply — apply manifest 100 lần, Kubernetes chỉ tạo resource 1 lần và update nếu có thay đổi. Hay terraform apply — apply 10 lần liên tiếp, lần 2 trở đi Terraform báo “No changes. Your infrastructure matches the configuration.”

Monaco cũng hoạt động tương tự. Hãy chứng minh qua 3 tests:

Ý nghĩa: Đây chính là idempotent — deploy 100 lần cũng ra cùng kết quả. Bạn có thể set CronJob re-deploy mỗi 6 giờ mà hoàn toàn yên tâm.

💡 Tại sao idempotent quan trọng cho production?

Trong production environment, idempotent không chỉ là “nice to have” — nó là requirement:

  1. GitOps reconciliation: Bạn có thể setup CronJob chạy monaco deploy mỗi 6 giờ (hoặc ArgoCD-style continuous reconciliation). Nếu ai đó sửa config thủ công trên UI → lần re-deploy tiếp theo sẽ override manual changes → Git luôn là single source of truth.

  2. Disaster recovery: Environment bị corrupt? Tạo environment mới → set env vars → chạy monaco deploy → toàn bộ config restored từ Git. Không cần nhớ đã config gì, ở đâu.

  3. Multi-environment consistency: Deploy cùng configs lên dev/staging/prod — chỉ khác env var. Config drift giữa environments = zero.

  4. Safe CI/CD: Pipeline tự deploy khi merge PR. Nếu deploy fail giữa chừng → fix và re-run. Nhờ idempotent, configs đã deploy thành công không bị duplicate, chỉ configs fail sẽ retry.

6. Dry-run Validation — “Nếu Deploy Thì Sao?”

Concept

Dry-run = validate mà không apply thật. Monaco đọc tất cả configs, check syntax, verify schemas, resolve dependencies — nhưng KHÔNG gửi request tới Dynatrace API. Giống terraform plan — bạn thấy “sẽ tạo/sửa/xoá gì” trước khi thực sự thay đổi.

Tại sao cần? Vì trong CI/CD, bạn muốn chặn merge nếu config invalid — trước khi nó vào main branch và deploy lên production.

Command

Output khi configs VALID

7. Download Config — Reverse Engineering Environment

2 use cases chính

Use case 1 — Bootstrap project từ existing environment:
Bạn có Dynatrace environment đã running, configs đã tạo thủ công trên UI. Muốn chuyển sang Monaco mà không tạo lại từ đầu? monaco download tải toàn bộ configs về, tạo sẵn project structure → bạn import vào Git → bắt đầu iterate.

Use case 2 — Drift detection:
Team deploy configs bằng Monaco, nhưng ai đó vẫn sửa trên UI (vì “nhanh hơn”). monaco download + diff với source code → phát hiện configuration drift — sự khác biệt giữa Git (source of truth) và thực tế (Dynatrace environment).

Command

Flag -e my-trial chỉ định environment name (phải match tên trong manifest). Nếu không chỉ định, Monaco download từ tất cả environments.

Output structure

Monaco tạo folder mới với timestamp:

download_2026-06-18_100000/
├── manifest.yaml                    ← Manifest mới, generated bởi Monaco
└── project/
    └── auto-tagging/
        ├── config.yaml              ← Config definitions — mỗi config trên DT = 1 entry
        └── auto-tag-env.json        ← Downloaded template payload

So sánh downloaded vs source — drift detection

Nếu có ai sửa config trên UI → diff hiển thị sự khác biệt. Ví dụ:

Ai đó đã sửa tag value trên UI thành lab-managed-manual-edit. Re-deploy source configs → override manual changes, đưa environment về đúng trạng thái trong Git.

Bootstrap workflow khi bắt đầu Monaco cho environment hiện có

Đây là workflow recommended khi adopt Monaco cho environment đã có configs:

  1. monaco download → tải toàn bộ existing configs
  2. Review downloaded configs → clean up, organize thành projects
  3. Commit vào Git → bạn có starting point
  4. Từ giờ, mọi thay đổi qua Git + Monaco → UI chỉ để view, không để edit

Quan trọng: download lần đầu sẽ có RẤT NHIỀU configs (hàng trăm). Bạn không cần import tất cả — chọn configs quan trọng (alerting, tagging, management zones) trước, phần còn lại import dần.

Downloaded configs có thể khác format so với source

Monaco download tạo configs theo format chuẩn của nó — có thể khác cách bạn viết tay (thứ tự fields, formatting JSON). Khi compare, focus vào semantic diff (giá trị thực sự khác) chứ không phải formatting diff (spaces, field order).

Debug strategy khi gặp lỗi không rõ ràng

  1. Luôn chạy với --verbose flag để xem full request/response
  2. Thử --dry-run trước — nếu dry-run pass nhưng deploy fail → vấn đề nằm ở API permissions, không phải config syntax
  3. Test với curl trực tiếp:

Nếu curl trả về data → token OK, network OK. Nếu curl fail → vấn đề nằm ở token/network, không phải Monaco.
