1. Settings 2.0 vs Classic API — Hai thế hệ cấu hình

Bối cảnh lịch sử

Dynatrace ban đầu chỉ có Classic Config API (v1). Đây là bộ REST endpoints thuần tuý — mỗi loại config (alerting profile, dashboard, notification…) có 1 endpoint riêng, bạn POST JSON payload lên và Dynatrace lưu nó. Đơn giản, trực tiếp, hoạt động tốt khi platform còn nhỏ.

Nhưng khi Dynatrace phát triển — hàng trăm loại config, hàng nghìn customers với multi-tenant environments — Classic API bộc lộ hạn chế nghiêm trọng:

  • Không có schema validation phía server: Bạn có thể POST bất kỳ JSON nào. Server chỉ reject khi field thiếu hoặc sai type, nhưng không validate semantic logic. Kết quả: config deploy “thành công” nhưng behaviour sai, debug mất hàng giờ.
  • Scope control thô: Classic API apply global cho toàn environment. Muốn config khác nhau cho host group A vs host group B? Phải tạo 2 configs riêng, naming convention thủ công.
  • Naming conflicts: Classic API dùng name làm identifier trong nhiều trường hợp. Hai team tạo alerting profile cùng tên → conflict. Monaco v2 giải quyết bằng externalId, nhưng bản thân API vẫn không có concept này.
  • Không version-aware: Khi Dynatrace thêm field mới vào config, Classic API không enforce — bạn có thể deploy config thiếu field mới, behaviour undefined.
  • Fragmented endpoints: Mỗi config type 1 endpoint, 1 payload format. Không có consistency. Developer phải đọc docs riêng cho từng endpoint.

Settings 2.0 ra đời để giải quyết toàn bộ vấn đề trên. Đây không phải “API mới” — đây là kiến trúc cấu hình hoàn toàn mới:

  • Schema-based: Mọi config type có 1 JSON Schema chính thức. Server validate payload against schema TRƯỚC khi accept. Giống TypeScript vs JavaScript — type safety at compile time thay vì runtime surprises.
  • Scope-aware: Config có thể apply ở nhiều scope: environment (toàn env), host (1 host cụ thể), host-group (nhóm host), process-group, service… Scope này là first-class concept, không phải workaround.
  • Version-controlled schemas: Khi Dynatrace thêm field mới, schema version tăng. Backward compatible nhưng bạn biết rõ schema nào đang dùng.
  • Unified API: 1 endpoint duy nhất (/api/v2/settings/objects) cho TẤT CẢ config types. Payload format consistent. Khác biệt nằm ở schemaId.

Quy tắc ngón tay cái để nhận biết

Nếu config có prefix builtin: → Settings 2.0, dùng type: settings trong config.yaml.
Nếu config dùng tên endpoint trực tiếp (như alerting-profile, dashboard) → Classic API, dùng type: api.
Khi không chắc: chạy monaco generate schema để list tất cả Settings 2.0 schemas. Nếu schema tồn tại → Settings 2.0. Nếu không → Classic API (hoặc chưa migrate).

Migration path thực tế

Dynatrace đang migrate dần Classic API → Settings 2.0. Lộ trình này diễn ra qua nhiều năm:

  1. Đã migrate: Management Zones, Auto-tagging, Maintenance Windows, Anomaly Detection (metric events), SLO
  2. Đang dùng Classic: Dashboard, Notification, Alerting Profile, Request Attributes
  3. Chỉ có Settings 2.0: Các feature mới (Application Security settings, Ownership, v.v.)

Trong thực tế, bạn sẽ dùng cả hai trong cùng 1 project. Monaco handle điều này transparent — bạn chỉ cần khai báo đúng type trong config.yaml, Monaco sẽ gọi đúng API.

So sánh với thế giới Terraform

Classic API giống Terraform providers thời đầu — mỗi resource 1 cách configure riêng, docs phân tán.
Settings 2.0 giống Terraform khi đã trưởng thành — consistent resource schema, validation trước khi apply, state tracking rõ ràng.
Monaco type: reference tương đương terraform output + data source — cách để 1 config reference kết quả của config khác.

2. Deploy Management Zone (Settings 2.0)

Management Zone là gì và tại sao cần nó

Trước khi viết config, hãy hiểu Management Zone (MZ) giải quyết vấn đề gì.

Hình dung bạn có 1 Dynatrace environment cho cả công ty — 500 hosts, 2000 services, 15 teams. Nếu mọi người thấy TẤT CẢ data, sẽ xảy ra:

  • Information overload: Dashboard hiển thị 2000 services, engineer tìm service của mình như tìm kim trong đống rơm
  • Accidental changes: Team A vô tình sửa alerting config của Team B
  • Compliance violations: Team không được phép thấy data của team khác (PCI-DSS, HIPAA)
  • Noisy alerts: On-call engineer nhận alert cho services không thuộc team mình

Management Zone giải quyết bằng cách phân chia environment thành logical segments. Mỗi MZ define 1 tập rules — rules này match entities (hosts, services, process groups) dựa trên tags, host groups, hoặc entity properties. Khi user được assign MZ, họ chỉ thấy entities thuộc MZ đó.

Nếu bạn quen Kubernetes: MZ giống namespace — logical boundary cho phân quyền và isolation, nhưng không phải physical separation. 1 entity có thể thuộc nhiều MZ (khác K8s namespace — 1 resource chỉ thuộc 1 namespace).

Tại sao Management Zone quan trọng cho multi-team setup

MZ không chỉ là “filter” — nó là foundation cho RBAC, data scoping, và operational isolation:

Ứng dụngGiải thích
RBAC (Role-Based Access Control)Assign user/group vào MZ → họ chỉ thấy data trong MZ đó. Team Platform thấy infra, Team Checkout thấy checkout services
Dashboard scopingDashboard filter by MZ → mỗi team có dashboard riêng tự động. Không cần build 15 dashboard thủ công
Alerting isolationAlerting Profile + Notification bind to MZ → Team A chỉ nhận alert cho services của Team A
SLO per teamSLO scoped by MZ → mỗi team có SLO riêng cho services của mình
Cost allocationMonitor resource consumption per MZ → biết team nào consume bao nhiêu DDU (Davis Data Units)
ComplianceAudit: “Team X chỉ có quyền xem data trong MZ Y” → pass compliance review

config.yaml — Khai báo Management Zone

Bước đầu tiên: tạo folder structure cho MZ config:

projects/
└── management-zones/
    ├── config.yaml
    └── mz-production.json

File config.yaml định nghĩa metadata và deployment instructions cho MZ:

Hãy đi qua từng field — mỗi field có ý nghĩa cụ thể:

FieldGiá trịGiải thích
idmz-productionUnique identifier trong project. Monaco dùng ID này để track config qua externalId. Nếu bạn đổi id, Monaco sẽ tạo config MỚI thay vì update config cũ — giống việc đổi metadata.name trong K8s resource
config.name"Production Apps"Tên hiển thị trên Dynatrace UI. Đây là giá trị con người đọc, không ảnh hưởng logic. Bạn CÓ THỂ đổi name mà không tạo config mới — Monaco track bằng id, không phải name
config.templatemz-production.jsonĐường dẫn tương đối tới template JSON. Monaco đọc file này, inject parameters (nếu có), rồi gửi payload tới Dynatrace API. Tương tự Helm chart template → rendered manifest

Naming convention cho id

Dùng format <type>-<environment/team>, ví dụ: mz-production, mz-team-checkout, mz-staging. ID nên stable (không đổi sau khi deploy), vì externalId derived từ nó. Giống metadata.name trong K8s — đổi name = tạo resource mới.

mz-production.json — Template định nghĩa MZ rules

Template JSON chứa payload thực tế gửi tới Dynatrace. Đây là “thịt” của config — mọi logic nằm ở đây:

Giải thích từng phần của template:

  • {{ .name }}: Go template syntax. Monaco inject giá trị config.name từ config.yaml vào đây. Kết quả: "Production Apps". Cú pháp này giống Helm {{ .Values.name }} — đều dùng Go text/template engine.

  • rules[]: Array các rule quyết định entity nào thuộc MZ này. Mỗi rule match 1 pattern. Entity match BẤT KỲ rule nào → thuộc MZ.

  • type: "ME": ME = Monitored Entity. Đây là rule type phổ biến nhất — match dựa trên entity type và properties. (Type khác: DIMENSION cho metric dimensions, nhưng hiếm khi dùng trực tiếp.)

  • enabled: true: Rule đang active. Set false để tạm tắt rule mà không xoá.

  • entitySelector: Đây là Entity Selector syntax của Dynatrace — ngôn ngữ query mạnh mẽ cho phép select entities dựa trên type, tags, properties, relationships. Cú pháp: type(ENTITY_TYPE),tag("key:value"). Ở đây: “chọn tất cả HOST có tag environment:production”.

  • conditions: []: Array rỗng vì chúng ta dùng entitySelector (cách mới, linh hoạt hơn). conditions là cách cũ — vẫn hoạt động nhưng Dynatrace khuyến khích dùng entitySelector.

entitySelector vs conditions — chọn cái nào?

Dynatrace đang transition từ conditions (cũ) sang entitySelector (mới). entitySelector mạnh hơn nhiều — hỗ trợ relationship queries (isConnectedTo), negation (not), complex boolean logic. Luôn dùng entitySelector cho config mới. conditions chỉ giữ lại cho backward compatibility.

Nếu bạn download config từ UI (bằng monaco download), Dynatrace có thể trả về format conditions. Khi refactor, convert sang entitySelector.

3. Deploy Alerting Profile (Classic API)

Alerting Profile giải quyết vấn đề gì

Hình dung lúc 3 giờ sáng, điện thoại on-call reo. Engineer mở mắt, check alert: “Response time slowdown on internal-health-check service”. Một service health check nội bộ bị slow 200ms. Không ảnh hưởng user nào. Engineer thở dài, acknowledge alert, quay lại ngủ.

Đây là vấn đề kinh điển: không phải mọi problem đều cần đánh thức engineer. Alerting Profile giải quyết bằng cách hoạt động như bộ lọc thông minh — nó quyết định:

  • Severity nào được forward tới notification channel (AVAILABILITY? ERROR? SLOWDOWN? RESOURCE?)
  • Delay bao lâu trước khi forward (có nên chờ 5 phút xem problem tự heal không?)
  • Tag filter nào — chỉ forward alerts cho entities match tag cụ thể
  • Event type filter — chỉ forward loại event cụ thể

Nếu bạn quen Prometheus/Alertmanager: Alerting Profile tương đương route trong Alertmanager config — nó define matching rules và routing logic. Khác biệt: Alerting Profile là Dynatrace-native, tích hợp sẵn với Davis AI problem detection.

config.yaml cho Classic API — Sự khác biệt với Settings 2.0

So sánh ngay với MZ config.yaml ở section trước — sự khác biệt nằm ở block type:

Với Classic API:

  • Không có schema — thay bằng tên API endpoint trực tiếp (alerting-profile)
  • Không có scope — Classic API luôn apply global (environment-wide)
  • Ít structured hơn — bạn phải biết chính xác endpoint name, không có auto-complete từ schema

Làm sao tìm tên Classic API endpoint?

  1. Mở Dynatrace API docs → tìm config type bạn cần
  2. URL endpoint sẽ có dạng /api/config/v1/alertingProfiles → tên API trong Monaco là alerting-profile (kebab-case)
  3. Hoặc: chạy monaco download → xem folder names trong output → đó chính là API names
  4. Danh sách đầy đủ: Monaco API Types Reference

alerting-prod-critical.json — Template với severity rules

Giải thích logic đằng sau từng severity rule — đây là production-grade alerting strategy:

SeverityDelayRationale
AVAILABILITY0 phútService/host DOWN = impact ngay lập tức. Không chờ, alert ngay. Đây là P1 — wake up engineer.
ERROR5 phútError rate tăng. Chờ 5 phút vì: (1) có thể spike tạm thời do deploy, (2) Davis AI cần thời gian correlate root cause. Nếu vẫn error sau 5 phút → thật sự có vấn đề.
SLOWDOWN15 phútResponse time tăng. Chờ lâu hơn vì: (1) slowdown thường tự recover (GC pause, temporary load), (2) nếu persist 15 phút → systematic issue, cần investigate.
RESOURCE_CONTENTION30 phútCPU/memory/disk pressure. Chờ 30 phút vì: (1) resource spikes rất phổ biến (batch jobs, scheduled tasks), (2) autoscaling có thể resolve, (3) chỉ alert khi sustained contention.

Giải thích các field quan trọng trong template:

  • displayName: "{{ .name }}": Khác Settings 2.0 dùng name, Classic API dùng displayName. Mỗi API có naming convention riêng — đây là 1 trong những inconsistency mà Settings 2.0 giải quyết.

  • tagFilter.includeMode: "INCLUDE_ANY": Rule match entity có BẤT KỲ tag nào trong list. Ngoài ra có INCLUDE_ALL (phải match TẤT CẢ tags) và NONE (không filter — match mọi entity).

  • tagFilter.context: "CONTEXTLESS": Tag context. CONTEXTLESS = tag được tạo manual hoặc qua auto-tagging (không có context cụ thể). Các context khác: AWS, CLOUD_FOUNDRY, GOOGLE_CLOUD, KUBERNETES — tags tự động từ cloud integrations.

  • eventTypeFilters: []: Không filter event type — nhận tất cả event types (problem open, problem merge, problem close). Nếu muốn chỉ nhận “problem open”: thêm [{"predefinedEventFilter": {"eventType": "OPEN"}}].

Deploy & Verify

Verify trên UI:

  1. Settings → Alerting → Alerting profiles
  2. Tìm “Production Critical Alerts”
  3. Click vào → verify 4 severity rules với delay đúng
  4. Chú ý: profile chưa gắn với Notification nào — đó là bước tiếp theo (Lab 03)

Alerting Profile chỉ là bộ lọc, không phải kênh gửi

Nhiều người nhầm: “Tôi đã tạo Alerting Profile → alert sẽ gửi qua Slack”. Sai. Alerting Profile chỉ FILTER. Để gửi alert, bạn cần tạo Notification Integration (Slack, Email, PagerDuty…) và reference Alerting Profile trong đó. Xem 03 - Automation Workflows & Advanced Types > 3. Deploy Notification Integration.

Flow: Problem → Alerting Profile (filter) → Notification (gửi đi)

4. Deploy Dashboard (Classic API)

Dashboard as Code — Tại sao không tạo dashboard thủ công

Bạn đã bao giờ gặp tình huống này chưa?

  • Team mới join → “Anh ơi, share cho em dashboard production overview được không?” → copy dashboard thủ công → quên update 1 tile → data hiển thị sai
  • 3 environments (dev/staging/prod), mỗi env cần dashboard giống nhau nhưng khác Management Zone → tạo thủ công 3 lần → 1 tháng sau có thay đổi → sửa 3 lần
  • Engineer tạo dashboard đẹp → nghỉ việc → không ai biết dashboard config thế nào → không reproduce được

Dashboard as Code giải quyết bằng cách: dashboard là 1 JSON template, version controlled trong Git, deploy bằng Monaco. Team mới onboard → deploy → có dashboard. Environment mới → deploy cùng template, khác parameter → done.

config.yaml với Parameter Injection

Phần mới ở đây là block parameters. Hãy phân tích:

  • parameters: Block chứa các biến sẽ inject vào template. Mỗi parameter có type và giá trị tương ứng.
  • managementZoneName: Tên MZ sẽ inject vào dashboard template. Dùng type: value vì đây là giá trị cố định.
  • dashboardOwner: Owner identifier. Dùng để track ai “sở hữu” dashboard.

3 loại parameters trong Monaco

TypeKhi nào dùngVí dụ
valueGiá trị cố định, biết trướcmanagementZoneName: "Production Apps"
environmentGiá trị từ env var, khác nhau per environmentslackUrl: $SLACK_WEBHOOK_URL
referenceID/giá trị từ config khác đã deploymzId: ref → mz-production.id

Rule of thumb: value cho constants, environment cho secrets/env-specific, reference cho cross-config linking.

dashboard-prod-overview.json — Template Dashboard

Dashboard template phức tạp hơn config thông thường vì nó chứa layout information (vị trí tiles, kích thước, styling):

Giải thích các thành phần chính:

  • dashboardMetadata.shared: true: Dashboard visible cho tất cả users (trong cùng MZ). false = private, chỉ owner thấy.
  • dashboardMetadata.tags: Tags giúp filter/search dashboard. Tag managed-by-monaco là convention tốt — biết ngay dashboard nào managed by code.
  • dashboardMetadata.preset: false: true = dashboard xuất hiện trong preset gallery. false = dashboard thường.
  • tiles[]: Array các “ô” trên dashboard. Mỗi tile có tileType, bounds (vị trí + kích thước), và config riêng.
  • bounds: Vị trí pixel trên dashboard grid. top/left = toạ độ góc trên trái, width/height = kích thước. Hệ toạ độ gốc (0,0) ở góc trên trái.
  • {{ .managementZoneName }}: Parameter injection — cùng MZ name dùng xuyên suốt dashboard. Đổi 1 chỗ trong config.yaml → tất cả tiles update.
  • filterConfig.filtersPerEntityType: Filter tile by Management Zone. Tile chỉ hiển thị data cho entities thuộc MZ specified.

Deploy & Verify

Verify trên Dynatrace UI:

  1. Observe → Dashboards (hoặc search “Dashboards”)
  2. Tìm “Production Overview”
  3. Kiểm tra: Markdown header hiển thị đúng MZ name, Host/Service tiles filter by MZ, CPU/Response Time/Error Rate charts có data

Tại sao Dashboard as Code tuyệt vời

  • Consistency: 10 environments → deploy cùng template, mỗi env chỉ đổi managementZoneName parameter → 10 dashboard giống hệt nhau về structure, khác data
  • Version controlled: Dashboard thay đổi → Git diff cho thấy chính xác tile nào đổi, metric nào thêm. Rollback = git revert + monaco deploy
  • Onboarding tức thì: Team mới → tạo MZ cho team → deploy dashboard template → team có full observability dashboard trong 30 giây
  • Audit trail: “Ai thêm tile Error Rate vào dashboard?” → check Git blame → biết ai, khi nào, tại sao
  • Reproducible: Dashboard bị xoá accidentally? monaco deploy → khôi phục nguyên trạng

Gotcha: Dashboard JSON rất dài

Dashboard template thường 200-500 dòng JSON. Đừng viết tay — export từ UI (tạo dashboard trên UI → export JSON → clean up → dùng làm template). Hoặc dùng monaco download để lấy dashboard hiện có.

Khi export, nhớ replace hardcoded values bằng {{ .parameterName }} để template reusable.

5. Deploy SLO (Settings 2.0)

SLO concept — Mục tiêu chất lượng dịch vụ

Trước khi deploy, hãy hiểu SLO (Service Level Objective) là gì trong context Dynatrace.

SLO là cam kết chất lượng cho service: “Service checkout phải available 99.9% thời gian trong 1 tuần”. Nếu vi phạm → error budget cạn → team phải dừng feature development, focus reliability.

Các thành phần SLO:

ComponentGiải thíchVí dụ
TargetMức tối thiểu phải đạt99.9% (ba chín)
WarningMức cảnh báo sớm (cao hơn target)99.95% — khi xuống dưới mức này, team bắt đầu chú ý
Evaluation typeCách tính SLOAGGREGATE (tính trung bình), STATUS_BY_REQUEST (theo từng request)
TimeframeKhoảng thời gian đánh giá-1w (1 tuần rolling), -1M (1 tháng)
Metric expressionCông thức tính SLOsuccessCount / totalCount * 100
FilterScope SLO cho entities nàotype(SERVICE),mzId(...)

SLO vs SLA vs SLI

  • SLI (Service Level Indicator): metric thô — “availability hiện tại là 99.92%”
  • SLO (Service Level Objective): mục tiêu nội bộ — “chúng ta cam kết 99.9%”
  • SLA (Service Level Agreement): hợp đồng với khách hàng — “nếu dưới 99.9%, chúng tôi bồi thường”

Dynatrace SLO = SLI + target threshold. Nó tính SLI tự động từ metric expression, rồi so sánh với target bạn define.

config.yaml với Reference Parameter

Đây là phần quan trọng nhất của lab — reference parameter tạo implicit dependency:

Phân tích block managementZoneId — đây là reference parameter:

FieldGiá trịGiải thích
type: reference-Parameter sẽ resolve từ config khác đã deploy. Monaco tự inject giá trị runtime.
configTypebuiltin:management-zonesSchema/API type của config target. Monaco biết tìm config ở đâu.
configIdmz-productionID của config target (từ config.yaml của MZ). Monaco match bằng id field.
propertyidProperty nào từ deployed config cần lấy. id = Dynatrace internal ID (UUID sau khi deploy).

Điều kỳ diệu ở đây: Khi bạn khai báo reference, Monaco tự động:

  1. Detect dependency: SLO phụ thuộc vào MZ
  2. Order deployment: Deploy MZ trước, SLO sau
  3. Inject runtime value: Sau khi deploy MZ, Dynatrace trả về internal ID (dạng UUID). Monaco lấy ID này → inject vào SLO template thay cho {{ .managementZoneId }}

Bạn không cần khai báo ordering — Monaco resolve tự động từ dependency graph. Giống depends_on implicit trong Terraform khi bạn reference aws_vpc.main.id trong aws_subnet — Terraform tự biết tạo VPC trước.

Reference parameter là cơ chế dependency chính của Monaco

Không có depends_on keyword trong Monaco. Dependency hoàn toàn qua reference parameters. Nếu config A reference config B → B deploy trước A. Đơn giản, elegant, giống cách human nghĩ: “SLO cần MZ ID → MZ phải tồn tại trước”.

slo-service-availability.json — Template SLO

Giải thích từng field:

  • evaluationType: "AGGREGATE": Tính SLO trên aggregate data (trung bình toàn bộ timeframe). Option khác: "STATUS_BY_REQUEST" — đánh giá từng request, phù hợp cho SLO chi tiết hơn nhưng tốn resource hơn.

  • filter: "type(SERVICE),mzId({{ .managementZoneId }})": Entity selector — SLO chỉ áp dụng cho services trong MZ đã chỉ định. mzId() nhận Management Zone ID (UUID) — đây chính là giá trị Monaco inject từ reference parameter.

  • target: {{ .targetPercentage }}: Target SLO. Chú ý KHÔNG có dấu ngoặc kép — đây là numeric value, không phải string. Go template inject 99.9 trực tiếp.

  • warning: {{ .warningPercentage }}: Warning threshold. Phải >= target. Khi SLO nằm giữa warning và target → status WARNING (vàng). Dưới target → VIOLATION (đỏ).

  • timeframe: "-1w": Rolling window 1 tuần. Mỗi moment, Dynatrace tính SLO cho 7 ngày gần nhất. Options khác: -1d, -2w, -1M, -1y.

  • metricExpression: Đây là trái tim của SLO — công thức tính. Format gần giống DQL nhưng không hoàn toàn DQL. Phân tích:

    • builtin:service.errors.server.successCount:splitBy() = tổng số requests thành công
    • :splitBy() = không split, aggregate toàn bộ
    • / = chia cho
    • builtin:service.requestCount.server:splitBy() = tổng số requests
    • *100 = convert sang phần trăm
    • Kết quả: (successCount / totalCount) * 100 = availability percentage

Deploy & Verify

Nếu MZ chưa deploy → Monaco deploy MZ trước (nhờ dependency resolution), rồi mới deploy SLO.

Verify trên Dynatrace UI:

  1. Navigate Service Level Objectives (search “SLO”)
  2. Tìm “Production Service Availability”
  3. Kiểm tra: Target = 99.9%, Warning = 99.95%, Timeframe = 1 tuần
  4. Kiểm tra: SLO filter = Management Zone “Production Apps”
  5. Nếu có services trong MZ → SLO hiển thị percentage hiện tại

SLO cần data để hiển thị

Nếu không có services nào trong MZ, hoặc services không có traffic → SLO hiển thị “No data”. Đây là normal — SLO tính từ real metrics, không fake data.

6. Dependencies & Ordering — Monaco’s Dependency Graph

Tại sao dependency management quan trọng

Trong lab này, configs có quan hệ phụ thuộc rõ ràng:

  • SLO cần MZ ID → MZ phải deploy trước SLO
  • Dashboard hiển thị MZ name → Dashboard nên deploy sau MZ (dù không có hard dependency — dashboard dùng MZ name string, không phải ID)
  • Alerting Profile không phụ thuộc config nào → deploy bất kỳ lúc nào

Nếu deploy sai thứ tự: SLO deploy trước MZ → MZ ID chưa tồn tại → deploy fail.

Monaco giải quyết bằng dependency graph — automatically resolve ordering.

Topological sort — Thuật toán đằng sau

Monaco dùng topological sort để determine deploy order. Nếu bạn học Computer Science, đây là thuật toán quen thuộc trên DAG (Directed Acyclic Graph):

  1. Build graph: Monaco scan tất cả config files, tìm type: reference parameters → build dependency edges
  2. Detect cycles: Nếu A → B → C → A (cycle) → error ngay lập tức với message rõ ràng. Bạn phải break cycle trước khi deploy
  3. Sort: Topological sort trên DAG → output là thứ tự deploy valid
  4. Deploy: Deploy từng config theo thứ tự sorted. Sau mỗi deploy → capture returned IDs → inject vào configs phụ thuộc

Trong lab này, topological sort cho ra:

1. Management Zone (mz-production)     → no dependencies, deploy first
2. Alerting Profile (alerting-prod)    → no dependencies, can deploy parallel
3. SLO (slo-service-availability)      → depends on MZ, deploy after MZ
4. Dashboard (dashboard-prod-overview) → no hard dependencies, deploy anytime

Nếu dependency cycle xảy ra (A ref B, B ref A)

Monaco sẽ báo lỗi rõ ràng: circular dependency detected: configA → configB → configA. Break cycle bằng cách restructure: extract shared value thành parameter type: value hoặc type: environment thay vì type: reference.

Ví dụ: thay vì A reference B và B reference A, hãy tạo shared config C mà cả A và B reference. DAG trở thành: C → A, C → B. Không cycle.

So sánh dependency resolution cross-tool

ToolDependency mechanismExplicit/Implicit
Monacotype: reference parameterImplicit — chỉ cần reference, không cần khai báo ordering
Terraformdepends_on + implicit referencesCả hai — implicit qua interpolation, explicit qua depends_on block
Ansiblehandlers + task orderingExplicit — dùng notify và playbook sequence
HelmHook weights + subchart dependenciesExplicit — weight annotation trên hooks
ArgoCDSync waves + phasesExplicit — argocd.argoproj.io/sync-wave annotation

Monaco chọn approach implicit-only — elegant nhưng đòi hỏi bạn hiểu reference mechanism. Không có escape hatch depends_on khi cần force ordering mà không có data dependency.

Cross-project references

Dependency không giới hạn trong 1 project. Config trong project slos có thể reference config trong project management-zones:

Field project chỉ định project chứa config target. Monaco resolve cross-project dependency giống intra-project — build global dependency graph, topological sort, deploy theo thứ tự.

Cross-project reference cần manifest khai báo cả 2 projects

Nếu project slos reference project management-zones, thì manifest.yaml PHẢI list cả 2 projects. Nếu chỉ list slos → Monaco không biết management-zones tồn tại → reference fail.

Debug tips

Khi config deploy "thành công" nhưng UI hiển thị sai

Đây thường là vấn đề template — Dynatrace accept payload nhưng interpret khác. Cách debug:

  1. monaco download → lấy config từ Dynatrace
  2. So sánh downloaded JSON vs source template
  3. Tìm field bị override/ignore bởi Dynatrace
  4. Fix template → re-deploy
