1. Real-World Patterns — Monaco ngoài đời thực

Monaco trong lab là YAML files + monaco deploy. Monaco trong production là workflow, process, culture change. Phần này trình bày 4 patterns đã được battle-test ở các tổ chức lớn — mỗi pattern giải quyết 1 pain point cụ thể mà team observability gặp phải khi scale.

Pattern 1: Self-Service Monitoring Onboarding

Pain point: Team platform/SRE nhận 10+ tickets/tuần kiểu “xin tạo dashboard cho service X”, “cần alerting profile cho team Y”, “thêm SLO cho microservice Z”. Mỗi ticket mất 30-60 phút manual work trên Dynatrace UI. SRE team trở thành bottleneck — development teams chờ đợi, frustrated.

Solution: Chuyển từ “SRE tạo thủ công” sang “Development team tự submit, SRE review”.

Implementation:

flowchart LR
    DEV["Dev Team<br/>Submit MR"] -->|"Thêm configs<br/>vào projects/"| MR["Merge Request"]
    MR -->|"Auto validate"| CI["CI Pipeline<br/>(dry-run)"]
    CI -->|"Pass"| REVIEW["SRE Review<br/>(4-eyes)"]
    REVIEW -->|"Approve + Merge"| DEPLOY["Auto Deploy<br/>(dev → staging → prod)"]

    style DEV fill:#4ecdc4,color:#fff
    style REVIEW fill:#ff6b6b,color:#fff

Workflow cụ thể:

  1. Dev team clone Monaco Git repo
  2. Thêm config files vào projects/<team-name>/ — ví dụ: dashboard, alerting profile, SLO cho service mới
  3. Tạo Merge Request. CI pipeline chạy --dry-run tự động → catch syntax errors
  4. SRE/Platform team review MR:
    • Config có follow naming conventions?
    • Alerting threshold hợp lý? (không set quá sensitive → alert fatigue)
    • SLO target realistic? (99.99% cho service internal là overkill)
  5. Approve → merge → pipeline auto-deploy → monitoring ready trong phút

Kết quả thực tế: Team platform ở một enterprise fintech report rằng pattern này giảm 80% ticket “xin tạo dashboard/alert cho team tôi”. SRE chuyển từ “nhấn nút cho người khác” sang “review và coaching” — giá trị cao hơn nhiều.

Cấu trúc repo theo team ownership, không theo config type.

Thay vì projects/dashboards/, projects/alerting/ (organized by type), dùng projects/team-checkout/, projects/team-payments/ (organized by team). Lý do: team checkout chỉ cần MR access vào folder của họ. CODEOWNERS file define ai review folder nào. Giống microservices architecture — bounded context cho monitoring config.

Pattern 2: Environment Scaling — Bootstrap mới trong 5 phút

Pain point: Customer onboarding. Mỗi customer mới = 1 Dynatrace tenant mới. Setup monitoring đầy đủ (dashboards, alerting, SLOs, auto-tagging rules) bằng tay mất 2 ngày. Team platform có 3 người, onboard 5 customers/tháng → không scale được.

Solution: Tạo “golden template” — bộ Monaco configs chuẩn. Customer mới → tạo tenant → thêm environment entry trong manifest.yaml → monaco deploy → đầy đủ monitoring trong 5 phút.

Implementation:

Kết quả thực tế: Managed Service Provider (MSP) triển khai pattern này cho 50+ customers. Onboarding time giảm từ 2 ngày xuống 5 phút. Consistency đảm bảo — mọi customer có cùng baseline monitoring. Customization per customer qua environmentOverrides.

Pattern này là "cattle, not pets" cho monitoring config.

Thay vì mỗi customer là “pet” được configure thủ công (unique, fragile), mỗi customer là “cattle” deploy từ template (standardized, replaceable, scalable). Giống Terraform modules — write once, deploy many.

Pattern 3: Compliance Enforcement — Prevent Drift, Prove Compliance

Pain point: Auditor hỏi: “Có chắc alerting profile giống nhau cross-environment không? Prod có bị ai sửa tay không?” Team answer: “Ừ… chắc vậy?” → audit finding → remediation → 2 tuần làm lại.

Solution: Monaco CronJob chạy monaco deploy mỗi 6 giờ. Git state luôn được enforce. Ai sửa tay qua UI → lần deploy tiếp ghi đè lại.

Implementation (chi tiết xem §2 Drift Reconciliation CronJob):

CronJob schedule: 0 */6 * * *   (mỗi 6 giờ)
         ↓
git clone Monaco repo
         ↓
monaco deploy --environment prod --continue-on-error
         ↓
Kết quả:
  - Config đúng → không thay đổi gì (idempotent)
  - Config bị drift → GHI ĐÈ về Git state
  - Slack alert: "Drift detected and reconciled"

Compliance evidence khi auditor hỏi:

  1. Show Git history → mọi config change đều qua MR, có reviewer, có timestamp
  2. Show CronJob schedule → reconciliation chạy 4 lần/ngày, 365 ngày/năm
  3. Show CronJob logs → “No changes needed” = config đã đúng = compliance verified
  4. Show Slack alert history → nếu drift xảy ra, nó bị catch và fix trong ≤6 giờ

Auditor thấy evidence này → confident. So sánh với “chắc vậy” → night and day.

Drift reconciliation CronJob là compliance evidence machine.

Khi auditor hỏi “how do you ensure configuration consistency?”, câu trả lời không phải “we try to be careful” mà là “we have automated reconciliation running every 6 hours with full audit trail in Git and Slack notifications”. Đây là language auditors understand — evidence-based, automated, traceable.

Pattern 4: Disaster Recovery — Restore từ Git

Pain point: Worst case scenario — Dynatrace environment bị corrupt (misconfiguration, accidental mass delete) hoặc cần recreate (migration SaaS → managed, hoặc ngược lại). Tất cả dashboards, alerting profiles, SLOs, management zones… biến mất. Recreate thủ công? Tuần đến tháng.

Solution: Toàn bộ DT config trong Git. Recreate environment → monaco deploy từ Git → toàn bộ config restore trong phút.

Recovery playbook:

So sánh RTO (Recovery Time Objective):

Git-based DR chỉ hoạt động nếu TẤT CẢ configs đều trong Git.

Nếu team vẫn tạo config qua UI mà không commit vào Monaco repo → config đó “vô hình” với DR. Khi restore, config đó bị mất. Golden rule: “If it’s not in Git, it doesn’t exist.” Enforcement: CronJob reconciliation sẽ GHI ĐÈ UI changes → force team dùng Git workflow.

2. Drift Reconciliation CronJob

Concept — Tại sao cần liên tục enforce?

Monaco deploy là idempotent — nếu config đã đúng, nó không thay đổi gì. Giống kubectl apply — chạy bao nhiêu lần cũng ra cùng kết quả. Đặc tính này cho phép chạy deploy liên tục mà không lo side effects.

Tại sao cần chạy liên tục? Vì con người là unpredictable. Dù team đã adopt GitOps workflow, sẽ luôn có:

  • Senior engineer sửa alerting threshold “tạm thời” trên UI lúc 2 AM incident → quên revert
  • Consultant vào tenant customer demo → tạo dashboard test → quên xoá
  • Junior DevOps thử config mới trên prod UI “để test nhanh” → quên commit

CronJob reconciliation là safety net — nó catch và fix những lỗi human này tự động.

CronJob Manifest — Production-ready

Giải thích từng field quan trọng

FieldValueTại sao chọn giá trị này
schedule0 */6 * * *4 lần/ngày — balance giữa “catch drift sớm” và “không tốn resources”. Mỗi 30 phút quá aggressive, mỗi 24h quá chậm
concurrencyPolicyForbidCỰC KỲ quan trọng — không cho 2 reconciliation chạy song song. 2 Monaco processes cùng update 1 config = race condition = unpredictable results
backoffLimit3Retry 3 lần — handle transient errors (network blip, rate limit). Nếu fail 4 lần → có vấn đề thật → cần human investigate
ttlSecondsAfterFinished3600Giữ pod 1 giờ cho log inspection. Sau đó auto-cleanup → tránh hàng trăm completed pods tích tụ
--continue-on-errorFlag1 config fail (ví dụ: schema deprecated) → tiếp tục deploy configs khác. Không block toàn bộ reconciliation vì 1 lỗi
--verboseFlagFull audit trail trong pod logs. CronJob logs = compliance evidence
startingDeadlineSeconds300Nếu controller restart và miss schedule → cho start muộn 5 phút. Quá lâu → skip (sẽ chạy lần tiếp)
restartPolicy: Never—Job pod crash → K8s KHÔNG restart cùng pod → tạo pod MỚI (để backoffLimit count). OnFailure = restart cùng pod → backoff count bị reset

concurrencyPolicy: Forbid là field quan trọng nhất.

Nếu bạn chỉ nhớ 1 điều từ section này: LUÔN set concurrencyPolicy: Forbid cho Monaco CronJobs. Hai Monaco processes cùng update config sẽ race condition — config A update bởi process 1, bị overwrite bởi process 2 với stale data. Giống 2 người cùng edit 1 Google Doc mà không có real-time sync.

3. Drift Detection Script — Detect trước, Enforce sau

Concept — Tại sao detect thay vì enforce ngay?

Drift reconciliation (§2) là “auto-heal” — tốt cho team đã mature với GitOps. Nhưng khi team mới adopt Monaco, auto-enforce có rủi ro:

  • Senior engineer sửa config trên UI vì lý do chính đáng (hotfix) → CronJob ghi đè lại → hotfix mất → incident quay lại
  • Config trong Git outdated → CronJob deploy config cũ → regression

Drift detection là “training wheels” — detect và alert, KHÔNG enforce. Team review alert → quyết định: commit vào Git (adopt change) hoặc re-deploy (reject change). Khi team quen → chuyển sang auto-reconcile.

CronJob Manifest + Script

Reconcile vs Detect — Khi nào dùng

ApproachBehaviorBest forRisk
Reconcile (§2)Tự sửa drift → enforce Git stateTeam đã mature với GitOps, prod stableHotfix trên UI bị ghi đè

Cả haiDetect + alert → Reconcile sau N giờBest practice — biết drift + tự healComplexity quản lý 2 CronJobs

Migration path recommended: Detect → Reconcile.

Tháng 1-3: chạy Detect only → team quen seeing drift alerts, learn workflow. Tháng 4+: enable Reconcile → auto-heal. Giống lái xe: học lái với camera lùi (detect) → sau đó bật auto-park (reconcile). Đừng auto-park từ ngày đầu khi chưa quen xe.

4. Monaco Docker Image — Official vs Custom

Official Image — Khi nào đủ dùng?

Dynatrace publish official Docker image chứa Monaco binary + Alpine base:

Registry:  docker.io/dynatrace/dynatrace-configuration-as-code
Tags:
  latest        → rolling, KHÔNG dùng cho production
  v2.27.0       → pinned version, RECOMMENDED
  2.27.0        → same as v2.27.0 (without 'v' prefix)

Official image đủ dùng khi:

  • Pipeline chỉ chạy monaco deploy / monaco download
  • Không cần tools bổ sung (git, jq, curl, custom scripts)
  • CI/CD platform cung cấp git checkout riêng (GitLab CI, GitHub Actions tự checkout)

Official image KHÔNG đủ khi:

  • CronJob cần git clone (K8s Job không có native checkout)
  • Cần post-processing: jq parse output, curl send alerts
  • Cần custom scripts: validate, notify, cleanup

Custom Dockerfile — Thêm tools cho production use

Khi official image thiếu tools, build custom image. Luôn base FROM official image — đảm bảo Monaco binary đúng version + tận dụng Dynatrace security patches:

Build & Push

Image Strategy

ScenarioImageLý do
CI/CD pipeline (GitLab/GitHub)Official v2.27.0CI platform có native checkout, không cần git trong image
K8s CronJob (reconcile/detect)Custom v2.27.0-r3Cần git clone, curl alert, jq parse
Local developmentOfficial v2.27.0 hoặc binaryDev laptop có git sẵn

Tagging convention: <monaco-version>-r<revision> — ví dụ v2.27.0-r3 (Monaco v2.27.0, custom image revision 3). Khi update custom scripts mà không update Monaco → increment revision only.

LUÔN pin version. latest tag trong production = Russian roulette.

latest tag thay đổi mỗi khi có release mới. Hôm nay nó là v2.27.0, tuần sau là v2.28.0 với breaking changes. Pipeline/CronJob pull latest → behavior thay đổi không dự đoán được → debug nightmare. Pin version LUÔN. Upgrade = conscious decision, tested on dev first.

5. ArgoCD Notifications → Dynatrace Events

Tại sao Deployment Markers cực kỳ quan trọng?

Dynatrace Davis AI là AI engine phân tích root cause. Khi problem xảy ra (response time spike, error rate increase), Davis tìm root cause bằng cách correlate problem với events gần đó. Nếu không có deployment events → Davis chỉ nói “response time increased” — không hữu ích lắm.

Với deployment events, Davis nói: “Response time increased. Root cause: deployment ‘checkout-v2.3.1’ 3 minutes ago. Remediation: rollback deployment.” — hữu ích hơn 10 lần.

Deployment marker biến Davis AI từ “something broke” thành “deployment X broke service Y 3 minutes ago, here’s the rollback link”. Đây là khác biệt giữa MTTR 2 giờ (manual investigation) và MTTR 15 phút (Davis AI pinpoint).

6. Error Handling & Troubleshooting

Monaco CLI Flags — Khi nào dùng gì

FlagMục đíchKhi nào dùngKhi nào KHÔNG dùng
--dry-runValidate mà không deployCI validate stage, pre-checkProduction deploy (cần deploy thật)
--continue-on-error1 config fail → tiếp tục configs khácCronJob reconciliation (best-effort)Production deploy qua CI (fail fast!)
--verboseFull debug outputTroubleshoot, production auditDev deploy routine (quá nhiều noise)
--environment <env>Deploy cho 1 environment cụ thểLuôn — explicit tốt hơn implicit—
--project <name>Deploy 1 project cụ thểTest config mới, troubleshoot 1 projectFull deploy (cần tất cả projects)

--continue-on-error cho CronJob: YES. Cho CI production deploy: NO.

CronJob reconciliation dùng --continue-on-error vì: 1 config deprecated không nên block toàn bộ reconciliation cho 50 configs khác. Nhưng CI production deploy KHÔNG dùng — nếu 1 config fail, bạn MUỐN pipeline fail → human investigate → fix → re-deploy. “Fail fast” trong CI, “best effort” trong reconciliation.

Rate Limiting — Monaco tự handle

Dynatrace API có rate limits. Khi deploy nhiều configs, bạn có thể gặp HTTP 429 (Too Many Requests). Monaco tự động handle:

  1. Nhận 429 response
  2. Đọc Retry-After header (thường 5-30 giây)
  3. Wait
  4. Retry request
  5. Repeat nếu cần

Bạn không cần implement retry logic. Monaco built-in exponential backoff. Chỉ cần đảm bảo:

  • K8s Job backoffLimit: 3 — retry toàn Job nếu Monaco crash
  • CI/CD timeout đủ lâu (10-15 phút) — account cho rate limit delays
  • Không chạy nhiều Monaco instances song song vào cùng environment (→ rate limit nặng hơn)

7. Monaco vs Terraform — Deep Comparison

Tại sao so sánh này quan trọng?

Câu hỏi phổ biến nhất khi giới thiệu Monaco: “Chúng tôi đã có Terraform, tại sao cần thêm tool?” Câu trả lời: separation of concerns. Terraform quản lý infrastructure, Monaco quản lý monitoring configuration. Giống Docker vs Kubernetes — 2 layers khác nhau, bổ sung nhau.

Nhưng Terraform cũng có Dynatrace provider — có thể quản lý DT configs. Vậy khi nào dùng gì? Bảng dưới đây giúp quyết định.

Separation of concerns:

  • Terraform team (infra/platform engineers): provision infrastructure, create DT tenants, install operators. Changes infrequent, impact high → Terraform state management justified
  • Monaco team (SRE/observability engineers + dev teams): manage day-to-day monitoring configs. Changes frequent, impact medium → Stateless, fast deploy justified

Hai teams, hai tools, hai repos, hai pipelines. Mỗi bên own layer của mình. Giống microservices architecture — bounded contexts cho infrastructure.

Terraform state management là overhead không cần thiết cho monitoring configs.

Terraform plan rất powerful — show diff trước apply. Nhưng state file cần lock, backup, versioning. Cho monitoring configs thay đổi 10 lần/ngày bởi 5 teams khác nhau, state management trở thành bottleneck. Monaco stateless = parallel deploys, no lock contention. Trade-off hợp lý cho use case này.

8. Checklist: Monaco Production Readiness

Tại sao cần checklist?

Checklist không phải cho junior engineers — nó cho experienced engineers dưới áp lực. Atul Gawande viết trong The Checklist Manifesto: pilots dùng checklist không phải vì không biết bay, mà vì 200+ steps dưới stress → quên 1 step = accident. Production deployment tương tự.

Pre-Production Readiness

  • manifest.yaml tested across ALL environments (dev, staging, prod) — không chỉ dev. --dry-run pass cho cả 3 envs

    • Tại sao: Config valid cho dev có thể fail ở prod (env-specific variables thiếu, different API endpoints)

  • API tokens scoped with least privilege — review scopes quarterly

    • Tại sao: Over-privileged token bị leak = catastrophic. Xem §5 Token Scopes

  • Secrets managed via ESO/Vault hoặc Sealed Secrets — NOT plaintext in Git

    • Tại sao: Plaintext secrets trong Git = ticking time bomb. Git history giữ mãi mãi — git filter-branch không đủ

  • CI/CD pipeline: --dry-run on MR, deploy on merge to main

    • Tại sao: Validate trước khi code vào main = catch errors cheap. Deploy sau merge = automated, traceable

  • Manual gate cho production deploy — when: manual + allow_failure: false

    • Tại sao: Production là sacred. Auto-deploy prod = one bad commit away from outage

  • Docker image pinned to specific version (eg v2.27.0, KHÔNG latest)

    • Tại sao: Reproducibility. latest thay đổi bất cứ lúc nào → breaking changes without warning

  • delete.yaml reviewed carefully — delete trong Dynatrace là IRREVERSIBLE cho một số config types

    • Tại sao: monaco delete xoá config thật. Không có undo. Review delete.yaml như review DROP TABLE

Ongoing Operations

  • CronJob reconciliation enabled — recommend 6h interval

    • Tại sao: Prevent drift. UI manual changes bị ghi đè. Git = source of truth luôn

  • Drift detection alerts configured (Slack/email/PagerDuty)

    • Tại sao: Biết khi drift xảy ra → investigate tại sao → improve process

  • Token rotation scheduled — recommend 90 ngày

    • Tại sao: Long-lived tokens = higher risk if leaked. Rotation limits exposure window

  • Monaco version upgrade plan — test trên dev → staging → prod

    • Tại sao: Monaco releases có thể include breaking changes. Controlled upgrade = safe upgrade

Backup & Recovery

  • monaco download scheduled weekly — backup current DT state

    • Tại sao: Git chứa desired state. Download backup chứa actual state. So sánh 2 cái = full picture

  • Restore procedure documented AND tested — không chỉ documented, phải TEST

    • Tại sao: Untested DR procedure = no DR procedure. Chạy restore drill mỗi quarter

  • Git repo backup — mirror hoặc secondary remote

    • Tại sao: Git repo là single source of truth. Repo down = no deployment. Mirror = failover

Team & Process

  • Team trained on Monaco workflow — không chỉ tool, mà cả process (MR → review → merge → deploy)

    • Tại sao: Tool không thay đổi culture. Training + practice mới thay đổi. Invest time vào onboarding

  • CODEOWNERS file configured — define ai review folder nào

    • Tại sao: Không phải ai cũng qualified review mọi config. SRE review alerting, dev team review dashboards

  • Runbook documented — common operations: add config, rollback, troubleshoot, emergency token rotation

    • Tại sao: 3 AM incident, on-call engineer cần step-by-step guide. Không phải lúc để “figure it out”

Integration

  • Deployment markers configured — ArgoCD/CI → Dynatrace Events

    • Tại sao: Davis AI correlation. Deployment events = root cause analysis quality 10x better

  • Rollback procedure documented — git revert + re-deploy pipeline

    • Tại sao: Khi config mới gây incident → rollback phải nhanh hơn fix forward. git revert = seconds

  • Monitoring cho Monaco Jobs — alert khi CronJob fail 3+ lần liên tục

    • Tại sao: CronJob fail silently = drift accumulates = false sense of security. Alert = awareness
