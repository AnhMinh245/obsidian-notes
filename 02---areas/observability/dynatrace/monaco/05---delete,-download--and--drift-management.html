1. Delete — Xóa Configs Có Kiểm Soát

Tại sao cần delete workflow?

Trước khi nói HOW, hãy hiểu WHY. Hãy tưởng tượng scenario sau:

Team Alpha đã dùng Monaco deploy 50 configs vào Dynatrace: 10 dashboards, 15 SLOs, 10 alerting profiles, 15 auto-tagging rules. Sau 6 tháng, Team Alpha rời project — dự án của họ chuyển sang vendor khác. Giờ bạn cần cleanup TẤT CẢ 50 configs mà Team Alpha đã tạo, nhưng không đụng bất kỳ config nào của Team Beta, Team Gamma đang hoạt động bình thường.

Xoá thủ công trên UI? Với 50 configs nằm rải rác trong 4 config types khác nhau, bạn sẽ mất hàng giờ click và rất dễ xoá nhầm config của team khác. Sai 1 click → break alerting cho production.

monaco delete giải quyết bằng cách: bạn declare chính xác configs nào cần xoá trong file delete.yaml, review kỹ, dry-run, rồi execute. Declarative, auditable, reversible (vì config source vẫn còn trong Git).

Bước 1: Generate delete file

Monaco có command tự động generate delete.yaml từ configs hiện có trong project:

Output là file delete.yaml chứa danh sách configs sẽ bị xoá. Monaco scan project directories, tìm tất cả config entries, và liệt kê chúng.

generate deletefile không xoá gì cả

Command này chỉ tạo file — nó không gửi bất kỳ API call nào tới Dynatrace. File được tạo ra là input cho command monaco delete ở bước sau. Tương tự terraform plan -destroy -out=destroy.plan — tạo plan, chưa execute.

Bước 2: Anatomy của delete.yaml — hiểu từng dòng

Giải thích format:

Thành phầnÝ nghĩaVí dụ
Phần trước /Config type (API endpoint hoặc Settings 2.0 schema)slo, auto-tag, dashboard, builtin:tags.auto-tagging
Phần sau /Config ID (trùng id trong config.yaml)response-time-slo, env-tag
Toàn bộ entryUnique identifier cho 1 config trên Dynatraceslo/response-time-slo

Bạn có thể (và NÊN) edit thủ công file này trước khi execute:

  • Xoá entry → giữ lại config đó (không bị xoá)
  • Thêm entry → xoá config thêm (nhưng cẩn thận — chỉ thêm config bạn chắc chắn muốn xoá)
  • Comment bằng # → Monaco bỏ qua dòng đó

Review delete.yaml như review PR

Hãy coi delete.yaml là một Pull Request: mỗi dòng là 1 thay đổi destructive. Review từng dòng, hỏi: “Config này đúng là của Team Alpha? Có team khác dùng chung không? Xoá có break dependency nào không?” Cách tiếp cận cẩn thận này cứu bạn khỏi xoá nhầm production alerting.

Bước 3: Dry-run trước khi execute

Dry-run output cho bạn thấy:

  • Tổng số configs sẽ bị xoá
  • Config nào trên environment nào
  • Errors nếu config không tồn tại (đã bị xoá trước đó)

Tương tự kubectl delete --dry-run=client — validate mà không thực hiện.

Bước 4: Execute delete

Sau khi execute, configs bị xoá vĩnh viễn khỏi Dynatrace. Không có recycle bin, không có soft-delete, không có “undo” button.

monaco delete là DESTRUCTIVE — không có undo

Đây là point of no return. Configs bị xoá không thể recover từ Dynatrace — bạn phải re-deploy từ Git source. Workflow an toàn:

  1. Dry-run: monaco delete manifest.yaml --dry-run → review output
  2. Review delete.yaml: đọc từng entry, confirm không xoá nhầm
  3. Git commit delete.yaml TRƯỚC khi execute: git add delete.yaml && git commit -m "chore: cleanup team-alpha configs"
  4. Execute: monaco delete manifest.yaml
  5. Verify trên UI: check Dynatrace UI confirm configs đã biến mất

Tại sao commit TRƯỚC khi execute? Vì nếu bạn commit SAU và quên push, bạn mất record. Commit TRƯỚC = Git history ghi nhận “delete.yaml này tồn tại tại thời điểm X” → bạn biết chính xác cái gì đã bị xoá, bởi ai (commit author), khi nào (commit timestamp).

Version control delete.yaml — Audit trail không thể thiếu

Tại sao commit delete.yaml vào Git lại quan trọng?

Nghĩ về tình huống 3 tháng sau: manager hỏi “ai xoá dashboard X?”. Nếu delete.yaml nằm trong Git:

Bạn có: commit hash, author, timestamp, context (commit message). Đây là audit trail miễn phí mà Git cung cấp.

Nếu delete.yaml KHÔNG trong Git? Bạn chỉ biết “ai đó chạy monaco delete” — không biết xoá gì, không biết ai, không biết khi nào. Trong regulated environments (finance, healthcare), đây là compliance violation.

Full workflow mẫu: Cleanup Team Alpha

monaco delete xoá configs ở tất cả environments trong manifest (trừ khi dùng -e). Nếu manifest có dev + staging + prod, delete xoá ở cả 3. Dùng -e dev để chỉ xoá ở dev:

Cực kỳ hữu ích khi bạn muốn cleanup dev nhưng giữ nguyên prod.

2. Download — Reverse Engineering Dynatrace Environment

monaco download là chiều ngược lại của deploy: thay vì push configs từ code lên Dynatrace, nó pull configs từ Dynatrace về local files. Đây là tool cực mạnh cho 2 use cases quan trọng.

Use case 1: Bootstrap — Adopt Monaco cho environment hiện có

Scenario: Team đã dùng Dynatrace 2 năm, tạo 100+ configs bằng UI (dashboards, alerting profiles, SLOs, auto-tags…). Giờ bạn muốn adopt Configuration as Code. Viết lại 100 configs bằng tay? Không. Download tất cả → import vào Git → refactor dần.

Tưởng tượng monaco download như terraform import — nó không thay đổi gì trên Dynatrace, chỉ đọc state hiện tại và ghi vào files. Dynatrace environment không biết bạn vừa download — không có side effects.

Output structure — Monaco tạo project structure chuẩn, sẵn sàng dùng:

bootstrap/
├── manifest.yaml                    # manifest generated, trỏ về env vừa download
└── project/
    ├── auto-tag/                    # Auto-tagging rules
    │   ├── config.yaml              # Config definitions cho TẤT CẢ auto-tags
    │   └── auto-tag-env.json        # Template cho từng rule
    ├── dashboard/                   # Dashboards
    │   ├── config.yaml
    │   ├── overview-dashboard.json
    │   └── team-dashboard.json
    ├── slo/                         # SLOs
    │   ├── config.yaml
    │   └── slo-response-time.json
    ├── alerting-profile/            # Alerting profiles
    │   ├── config.yaml
    │   └── default-profile.json
    ├── management-zone/             # Management Zones
    │   ├── config.yaml
    │   └── prod-apps-mz.json
    └── builtin-tags-auto-tagging/   # Settings 2.0 configs
        ├── config.yaml
        └── setting-001.json

Workflow bootstrap hoàn chỉnh:

Downloaded configs cần refactoring

Configs download từ Dynatrace thường verbose — chứa nhiều default values mà Dynatrace tự thêm, IDs cụ thể mà bạn không cần hardcode, và structure flat (không tối ưu cho multi-env). Xem chúng như draft cần refactor, không phải production-ready code.

Tương tự terraform import — imported resource có tất cả attributes, nhưng bạn cần clean up thành chỉ giữ attributes quan trọng.

Use case 2: Audit — Ai sửa gì trên UI tuần rồi?

Scenario: Sáng thứ Hai, bạn nhận alert production SLO breach. Nhìn vào Git — không ai commit thay đổi SLO config tuần rồi. Ai đó đã sửa trực tiếp trên UI mà không qua code review. Làm sao biết chính xác họ sửa gì?

Output diff cho bạn thấy chính xác field nào khác — ví dụ ai đó giảm SLO target từ 99.5% xuống 95% trên UI. Bạn biết chính xác drift ở đâu.

Download không thay đổi Dynatrace

monaco download là read-only operation — 100% safe. Nó gọi Dynatrace API với GET requests, không PUT/POST/DELETE. Bạn có thể download bao nhiêu lần tuỳ ý mà không ảnh hưởng environment.

Tương tự terraform state pull hoặc kubectl get -o yaml — chỉ đọc, không sửa.

3. Drift Detection — Vấn Đề Không Ai Muốn Nói Tới

Configuration Drift là gì — và tại sao nó là nightmare?

Configuration Drift = trạng thái thực tế (config trên Dynatrace) khác với trạng thái mong muốn (config trong Git). Nói cách khác: Dynatrace environment KHÔNG reflect những gì code define. Đây là violation nghiêm trọng nhất của Configuration as Code principle — Git không còn là source of truth nữa.

Nguyên nhân drift phổ biến nhất:

  1. Engineer sửa trên UI để debug, quên revert: Lúc 2AM, on-call engineer tắt 1 alerting rule để stop false-positive alerts đang wakeup team. Sáng hôm sau quên bật lại. Alerting rule trên Dynatrace = disabled, nhưng Git vẫn nói enabled. Kết quả: production incident tiếp theo không ai biết vì alerting bị tắt.

  2. Tool khác cũng sửa cùng config: Dynatrace API mở cho mọi tool. Nếu team dùng cả Monaco LẪN custom Python script để manage configs, chúng có thể overwrite lẫn nhau. Tool cuối cùng chạy “thắng” — nhưng Git chỉ reflect 1 tool.

  3. Dynatrace tự update khi upgrade: Khi Dynatrace release version mới, một số schema thay đổi — default values được thêm, deprecated fields bị xoá, format thay đổi. Config bạn deploy 3 tháng trước có thể khác config hiện tại trên Dynatrace (dù bạn không sửa gì).

Drift tích luỹ: càng lâu không phát hiện, càng khó sửa

Drift nhỏ (1-2 fields) dễ fix — re-deploy là xong. Drift lớn (tích luỹ qua hàng tuần manual changes) thì nguy hiểm: re-deploy Monaco configs có thể overwrite manual changes mà team đã dựa vào. Ví dụ: engineer đã fine-tune alerting threshold qua nhiều lần trial-and-error trên UI — re-deploy Monaco sẽ reset về giá trị cũ trong Git, có thể gây alert noise hoặc miss alerts.

Đây là lý do drift detection phải chạy thường xuyên — catch sớm, fix nhỏ.

Monaco KHÔNG có native drift detection — tại sao?

Đây là câu hỏi mà nhiều người hỏi: tại sao Monaco không có monaco plan tương tự terraform plan?

Câu trả lời nằm ở architecture:

AspectTerraformMonaco
State fileCó terraform.tfstate — ghi nhận “lần deploy gần nhất tạo resource nào”KHÔNG CÓ state file
Drift detectionterraform plan so sánh state file vs actual → hiển exact diffKhông có tương đương
ReconciliationBiết chính xác resource nào cần create/update/deleteChỉ biết “deploy tất cả config trong project”
TrackingState file chứa resource IDsexternalId lưu trên Dynatrace (không lưu local)

Terraform lưu state file — nó biết “lần deploy trước tạo SLO X với target 99.5%”. Khi chạy terraform plan, nó:

  1. Đọc state file → “SLO X target 99.5%”
  2. Đọc actual trên cloud → “SLO X target 95.0%”
  3. Show diff: target: 99.5% → 95.0% (DRIFT!)

Monaco không có state file — nó chỉ biết “project này define config A, B, C” nhưng không biết lần deploy trước kết quả thế nào. Khi bạn chạy monaco deploy, nó:

  1. Đọc config files
  2. Gửi API call tới Dynatrace (upsert)
  3. Done — không so sánh, không diff

Design choice này có ưu điểm: không cần quản lý state file (state file corruption, locking, remote backend — toàn bộ complexity này biến mất). Nhưng nhược điểm rõ ràng: bạn không biết có drift hay không cho đến khi tự check.

Monaco team aware vấn đề này

Dynatrace team đã nhận feedback về drift detection. Trong tương lai có thể có monaco diff hoặc monaco plan command. Hiện tại (2026), bạn phải DIY. Đây cũng là lý do một số team chọn Terraform Dynatrace Provider — native drift detection là killer feature.

DIY Drift Check Script

Vì Monaco không có native drift detection, chúng ta tự build. Logic đơn giản: download current state → diff với Git source → alert nếu khác.

Cách chạy:

Mermaid Flow: Drift Detection Lifecycle

flowchart TD
    A["Git Source<br/>(desired state)"] -->|"monaco deploy"| B["Dynatrace Env<br/>(actual state)"]
    B --> C{"Manual change<br/>on UI?"}
    C -->|"Yes"| D["⚠️ Config Drift!<br/>actual ≠ desired"]
    C -->|"No"| E["✅ In sync"]

    D --> F["monaco download<br/>(read actual state)"]
    F --> G["diff với Git source"]

    H -->|"No"| E

    I --> J{"Action?"}

    J -->|"Adopt changes<br/>(update Git)"| L["Update config files<br/>+ commit to Git"]

    K --> E
    L --> E

Khi phát hiện drift, bạn có 2 lựa chọn

  1. Re-deploy từ Git (restore desired state): chạy monaco deploy → overwrite manual changes. Dùng khi manual change là sai/unauthorized.
  2. Adopt manual changes vào Git (update desired state): copy giá trị mới từ downloaded config → update source files → commit. Dùng khi manual change là đúng (emergency fix hợp lý).

Đừng tự động re-deploy mà không review — engineer có thể đã sửa UI vì lý do chính đáng (emergency fix lúc 2AM).

4. Drift Prevention — 3 Strategies Từ Đơn Giản Đến Enterprise

Phát hiện drift là bước 1. Bước 2 là ngăn nó xảy ra hoặc tự động fix. Ba strategies sau đây từ đơn giản → phức tạp, phù hợp cho các mức maturity khác nhau.

Strategy A: Periodic Reconciliation — “Tự heal mỗi 6 giờ”

Ý tưởng: chạy monaco deploy định kỳ (mỗi 6 giờ). Vì Monaco là idempotent, nếu không có drift → deploy không thay đổi gì (safe). Nếu có drift → deploy overwrite manual changes, restore desired state. Automatic healing.

Tương tự Kubernetes controller reconciliation loop — controller liên tục so sánh desired state vs actual state và fix discrepancies. ArgoCD auto-sync cũng cùng concept: mỗi 3 phút check Git vs cluster, nếu khác → sync.

Ưu điểm:

  • Đơn giản — chỉ cần CronJob + existing deploy command
  • Tự heal — drift tự fix trong tối đa 6 giờ
  • Không cần infrastructure phức tạp

Nhược điểm:

  • Không biết ai gây drift (no audit trail)
  • Drift tồn tại tối đa 6 giờ (window of vulnerability)
  • Nếu manual change là intentional → bị overwrite mất

Idempotent = an toàn khi chạy lại

Nhiều người lo “chạy deploy mỗi 6 giờ có gây vấn đề không?” — Không. Monaco idempotent giống kubectl apply: nếu config trên Dynatrace đã đúng → API call vẫn được gửi nhưng result là no-op. Không tạo duplicate, không overwrite với giá trị khác.

Tuy nhiên, mỗi lần deploy vẫn gọi Dynatrace API → có API rate limit impact nếu bạn có hàng nghìn configs. Với scale nhỏ (< 500 configs), 4 lần/ngày là hoàn toàn OK.

Strategy B: Detect and Alert — “Phát hiện và báo, người quyết định”

Ý tưởng: chạy drift check script định kỳ (mỗi ngày). Nếu phát hiện drift → gửi alert (Slack, email, PagerDuty). Người review và quyết định action (re-deploy hoặc adopt changes).

Ưu điểm:

  • Visibility — team biết ngay khi có drift
  • Accountability — report cho thấy config nào drift, có thể trace ai sửa UI
  • Human decision — không tự động overwrite, người quyết định

Nhược điểm:

  • Không tự fix — cần người xử lý
  • Phức tạp hơn Strategy A (cần scripting, CI integration)
  • Daily check → drift tồn tại tối đa 24 giờ

Strategy C: Lock UI — Restrict Manual Changes

Ý tưởng: ngăn drift từ gốc — dùng Dynatrace IAM policies để restrict ai được sửa config trên UI. Chỉ service account (Monaco) có write permission. Human users chỉ có read-only access.

Dynatrace IAM Policy:
├── Service Account "monaco-deployer"
│   ├── Read settings  ✅
│   ├── Write settings ✅
│   ├── Read config    ✅
│   └── Write config   ✅
│
├── Group "Developers"
│   ├── Read settings  ✅
│   ├── Write settings ❌   ← Không được sửa
│   ├── Read config    ✅
│   └── Write config   ❌   ← Không được sửa
│
└── Group "Emergency-Access" (break-glass)
    ├── All permissions ✅   ← Chỉ dùng khi emergency
    └── Requires approval + audit log

Ưu điểm:

  • Prevent drift at source — không ai sửa UI → không có drift
  • Compliance — regulated environments yêu cầu “all changes through code review”
  • Clean Git history — mọi thay đổi đều qua PR

Nhược điểm:

  • Debug khó hơn — engineer không thể quickly toggle alerting rule khi investigating incident
  • Emergency fix chậm — phải tạo PR, wait review, merge, deploy pipeline. Incident có thể kéo dài
  • Break-glass procedure phức tạp — cần process cho emergency access
  • Team pushback — developers thường ghét mất flexibility

Recommendation: phối hợp strategies theo maturity

Giai đoạn 1 (mới adopt Monaco): Bắt đầu với Strategy A (reconciliation CronJob). Đơn giản, tự heal, team vẫn có flexibility sửa UI.

Giai đoạn 2 (team quen Monaco): Thêm Strategy B (daily drift check + Slack alert). Giữ visibility, bắt đầu build culture “mọi thay đổi qua code”.

Giai đoạn 3 (enterprise mature): Thêm Strategy C (lock UI cho non-emergency). Chỉ áp dụng cho production. Dev/staging vẫn mở để developers experiment.

Không nên nhảy thẳng vào Strategy C — team sẽ phản đối và tìm cách bypass (tạo token riêng, sửa bằng API trực tiếp…).

Community/ecosystemDynatrace-specificHashiCorp ecosystem (modules, registry, Sentinel)

Khi nào CHỌN Monaco?

Dùng Monaco khi:

  • ✅ Team chủ yếu quản lý Dynatrace configs — không dùng Terraform cho infra khác
  • ✅ Muốn learning curve thấp — YAML/JSON dễ hơn HCL cho team non-DevOps (SRE, Observability engineers)
  • ✅ Cần hỗ trợ tất cả Dynatrace config types ngay khi release — Monaco luôn được update trước Terraform provider
  • ✅ GitOps workflow thuần: Git → CI pipeline → monaco deploy — đơn giản, không cần quản lý state
  • ✅ Stateless operation quan trọng — không muốn lo state file corruption, locking, remote backend
  • ✅ Team nhỏ (1-5 người), project mới, muốn adopt nhanh

Khi nào CHỌN Terraform Dynatrace Provider?

Dùng Terraform khi:

  • ✅ Team đã dùng Terraform cho infrastructure (AWS, GCP, K8s) — thêm DT provider vào existing workflow
  • ✅ Native drift detection là requirement — terraform plan show exact diff
  • ✅ Muốn quản lý Dynatrace cùng lifecycle với infra khác — 1 terraform apply provision EC2 + configure DT monitoring
  • ✅ State management quan trọng — audit trail, state locking, import
  • ✅ Team có Terraform expertise — HCL không phải barrier
  • ✅ Enterprise với Sentinel policies — governance rules cho mọi Terraform changes

Hybrid Approach — Best of Both Worlds

Trong thực tế, nhiều team mature dùng cả hai, chia concern rõ ràng:

Terraform xử lý “infrastructure concerns”:

  • Provision Dynatrace environment (nếu Managed)
  • Deploy OneAgent via Kubernetes operator
  • Setup ActiveGate
  • Tạo API tokens (output token → pass to Monaco)
  • Network configuration

Monaco xử lý “observability configs bên trong environment”:

  • Dashboards, SLOs, Alerting profiles
  • Auto-tagging rules, Management Zones
  • Automation Workflows
  • Synthetic monitors
  • OpenPipeline configs

Hybrid là approach phổ biến nhất ở enterprise

Trong thực tế, ít team chọn “100% Monaco” hoặc “100% Terraform”. Hybrid cho phép mỗi tool làm điều nó giỏi nhất: Terraform quản lý infrastructure lifecycle (create/destroy environments), Monaco quản lý observability configs (nhanh hơn, flexible hơn, learning curve thấp hơn cho Observability team).

Ranh giới: nếu config tạo/xoá cùng infrastructure lifecycle → Terraform. Nếu config thay đổi độc lập với infrastructure → Monaco.
