Monaco v2 Overview & Architecture

Thuộc MOC - Dynatrace · Next → 01 - Cài Đặt Monaco CLI & First Deploy

1. Monaco là gì — và tại sao bạn cần nó

1.1 Bối cảnh thực tế

Hình dung bạn đang quản lý 5 Dynatrace environments cho dev / staging / prod của 3 team product khác nhau. Mỗi environment cần hàng trăm cấu hình: alerting profiles, management zones, auto-tagging rules, dashboards, SLOs, synthetic monitors, request attributes… Tất cả đang được setup thủ công qua UI.

Hôm nay team Platform yêu cầu: “Thêm tag cost-center cho tất cả services trên cả 5 environments, áp dụng cùng logic.” Bạn mở Dynatrace UI, click vào env đầu tiên, tạo auto-tag rule, test xong… rồi lặp lại cho 4 env còn lại. Mất 2 tiếng. Tuần sau, team muốn sửa regex pattern — lại 2 tiếng nữa.

Đây chính là vấn đề mà Monaco (viết tắt của Monitoring as Code) ra đời để giải quyết.

1.2 Pain points khi config thủ công qua UI

Trước khi nói Monaco giải quyết gì, hãy liệt kê cụ thể những gì đang gây đau đầu:

  1. Không version control — Khi ai đó sửa alerting profile trên UI, không có Git history ghi lại ai sửa gì, lúc nào, vì lý do gì. Dynatrace có audit log, nhưng nó chỉ ghi “user X changed config Y” — không có diff chi tiết giống git diff để biết chính xác field nào đổi giá trị gì.

  2. Không reproducible — Setup 1 environment mới từ đầu mất hàng giờ click-and-configure. Khi cần tạo env thứ 2 giống hệt, bạn phải mở env cũ bên cạnh và copy-paste từng config. Quên 1 cái = environment bị lệch mà không biết.

  3. Configuration drift giữa environments — Dev, staging, prod ban đầu giống nhau. Sau 6 tháng, chúng “drift” — ai đó sửa threshold alerting trên prod nhưng quên staging, ai đó thêm management zone trên dev để test rồi quên xoá. Kết quả: staging không reflect prod, testing trở nên vô nghĩa.

  4. Human error không có safety net — 1 click sai có thể disable alerting cho toàn bộ production. Không có --dry-run, không có PR review, không có rollback ngoài việc nhớ config cũ là gì và sửa lại bằng tay.

  5. Không scale được theo tổ chức — 3 team cùng dùng 1 Dynatrace tenant. Team A sửa management zone, vô tình ảnh hưởng dashboard của team B. Không có cơ chế “ownership” hay “code review” cho config changes.

  6. Không CI/CD friendly — Config monitoring nằm ngoài deployment pipeline. Application deploy qua ArgoCD/Jenkins/GitHub Actions, nhưng monitoring config vẫn phải setup manual sau khi deploy xong. Khoảng cách này tạo ra gap: app mới chạy production nhưng chưa có alerting → incident bị miss.

  7. Audit và compliance khó — Trong regulated environments (tài chính, y tế), bạn cần chứng minh “monitoring config đã được review và approved trước khi deploy lên production.” Với UI manual, không có approval workflow nào ngoài việc tin tưởng người click.

  8. Disaster recovery chậm — Nếu Dynatrace environment bị corrupt hoặc cần recreate (hiếm nhưng xảy ra với Managed), bạn phải setup lại từ đầu. Không có “backup” nào ngoài screenshots và documentation viết tay.

1.3 Tại sao đây không chỉ là nice-to-have

Trong thực tế enterprise, manual configuration là nguyên nhân #1 gây incident liên quan monitoring. Kịch bản kinh điển:

Một kỹ sư sửa alerting profile trên production để giảm noise — tăng threshold từ 5% lên 15% error rate. Hoàn toàn hợp lý. Nhưng quên sửa staging. Hai tháng sau, staging bắt đầu có 10% error rate do bug mới. Staging không báo alert vì threshold vẫn là 5% (alert đã fire nhưng nobody checks staging alerts anyway). Bug lên production, alerting profile mới cần 15% mới fire. Khi cuối cùng alert fire ở 15% — impact đã lan rộng, khách hàng đã bị ảnh hưởng.

Nếu alerting profile nằm trong Git, change phải qua PR review, deploy qua pipeline đến cả staging và prod — kịch bản trên không xảy ra.

1.4 Monaco giải quyết như thế nào

Monaco là CLI tool chính thức của Dynatrace, viết bằng Go, chạy standalone (single binary, không cần runtime). Tên đầy đủ trên GitHub: dynatrace-configuration-as-code.

Cách Monaco giải quyết từng pain point:

Pain pointGiải pháp Monaco
Không version controlConfig = YAML/JSON files trong Git repo
Không reproduciblemonaco deploy — 1 command setup cả environment
Configuration driftCùng config deploy cho mọi env, chỉ khác parameters
Human error--dry-run + PR review trước khi deploy
Không scaleChia project theo team, merge qua Git workflow
Không CI/CDMonaco chạy trong pipeline như bất kỳ CLI tool nào

Disaster recoveryGit repo = backup, monaco deploy = restore

1.5 Monaco trong ecosystem — so sánh để hiểu rõ hơn

Nếu bạn đã quen Terraform, cách nghĩ đơn giản nhất:

Terraform quản lý infrastructure as code → Monaco quản lý monitoring configuration as code.

Mối quan hệ tương tự ở nhiều khía cạnh:

Khía cạnhTerraformMonaco
Triết lýDeclarative, idempotentDeclarative, idempotent

Monaco không cần state file

Đây là điểm khác biệt quan trọng nhất so với Terraform. Monaco dùng externalId — một hash unique được tính từ project + config type + config id — để track mỗi config trên Dynatrace. State được “lưu” ngay trên Dynatrace environment, không phải trong file riêng. Điều này loại bỏ hoàn toàn các vấn đề state lock, state corruption, state drift mà Terraform users rất quen thuộc.

Nếu bạn quen Kubernetes, một analogy khác:

Monaco deploy giống kubectl apply — chạy lại bao nhiêu lần cũng ra cùng kết quả (idempotent). Config đã tồn tại → update. Chưa có → tạo mới. Không bao giờ tạo duplicate.

2. Monaco v1 vs v2 — Migration context

2.1 Tại sao Dynatrace phải viết lại v2

Monaco v1 ra đời khi Dynatrace chỉ có Classic Config API. Khi Dynatrace phát triển Settings 2.0, Automation (Workflows), Grail (Buckets, Documents, OpenPipeline), v1 không theo kịp vì:

  • Name-based tracking: v1 dùng tên hiển thị (display name) để identify config. Nếu 2 configs cùng tên → conflict, Monaco không biết update cái nào. Trong enterprise với hàng trăm configs, name collision xảy ra thường xuyên hơn bạn nghĩ.

  • Chỉ hỗ trợ Classic API: v1 không có kiến trúc extensible để thêm config types mới. Mỗi lần Dynatrace ra API mới, phải hack thêm vào codebase cũ.

  • Không có delete: v1 chỉ có thể tạo và update — không xoá được config đã deploy. Muốn cleanup phải vào UI xoá tay.

  • Flat environment file: environments.yaml của v1 không support grouping, không có OAuth, không có environment variables cho secrets.

v2 được viết lại từ đầu (không phải refactor v1) để giải quyết tất cả vấn đề trên.

2.3 externalId — Bí mật của v2 tracking

externalId là hash unique cho mỗi config, được tính từ:

externalId = hash(projectName + configType + configId)

Nhờ đó Monaco biết chính xác config nào cần update, config nào cần tạo mới, không phụ thuộc vào tên hiển thị. Nếu bạn đổi display name từ “Production Alerts” thành “Prod Alert Profile”, Monaco vẫn biết đó là cùng 1 config và update thay vì tạo mới.

Cơ chế này tương tự Terraform state tracking nhưng không cần state file:

  • Terraform lưu mapping resource address → cloud resource ID trong .tfstate
  • Monaco lưu externalId dưới dạng tag/metadata trên chính Dynatrace environment

v1 đã deprecated — không còn nhận updates

Monaco v1 chính thức deprecated từ v2.0.0 release (2022). Mọi project mới bắt buộc dùng v2. Nếu bạn đang có v1 project, chạy monaco convert --environment environments.yaml --output-folder v2-project/ để migrate. Command này tự động chuyển đổi cấu trúc file, nhưng bạn vẫn cần review kết quả — đặc biệt là dependency references.

3.2 Flow chi tiết — 8 bước từ YAML đến Dynatrace

Mỗi lần bạn chạy monaco deploy manifest.yaml, đây là những gì xảy ra bên trong:

Bước 1 — Đọc manifest.yaml → phân tích environments, projects

Monaco bắt đầu bằng việc đọc manifest.yaml — file entry point duy nhất. Từ đây nó biết:

  • Có bao nhiêu environments (dev, staging, prod) và credentials từng env
  • Có bao nhiêu projects (shared, team-a, team-b) và path trên filesystem
  • Environment groups — cho phép deploy theo nhóm (vd: deploy tất cả non-prod)

Nếu bạn truyền flag -e dev, Monaco chỉ pick environment dev và bỏ qua phần còn lại.

Bước 2 — Scan project directories → tìm config.yaml files

Monaco đi qua từng project directory được khai báo, tìm tất cả file config.yaml trong mọi subfolder. Mỗi subfolder thường đại diện cho 1 config type (vd: auto-tagging/, alerting-profile/, dashboard/). Cấu trúc folder không bắt buộc — Monaco không quan tâm tên folder, nó đọc type field trong config.yaml để biết config thuộc loại nào.

Bước 3 — Parse config.yaml → validate schema references

Mỗi config.yaml được parse để extract:

  • Config id (unique identifier trong scope project)
  • Config type (settings schema, classic API endpoint, automation…)
  • Template file path (JSON payload)
  • Parameters (value, environment, reference, compound)
  • skip flag (cho phép disable config mà không xoá file)

Nếu type là Settings 2.0, Monaco validate schema ID tồn tại trên target environment. Nếu schema không exist (vd: environment cũ chưa có feature mới), deploy sẽ fail với error message rõ ràng.

Bước 4 — Load template files → resolve Go template syntax

Template files (.json) chứa payload thật sự gửi đến Dynatrace API. Chúng dùng Go template syntax để inject parameters:

Monaco resolve {{ .name }} bằng giá trị từ parameters section trong config.yaml. Nếu parameter type là environment → đọc từ OS environment variable. Nếu type là reference → resolve sau khi dependency deploy xong (bước 7).

Bước 5 — Build dependency graph (DAG) → topological sort

Đây là bước thông minh nhất. Monaco scan tất cả reference parameters để xây dựng Directed Acyclic Graph (DAG). Ví dụ:

SLO config → references → Management Zone
Dashboard config → references → SLO config
Dashboard config → references → Auto-tag config

DAG sau topological sort sẽ cho ra thứ tự deploy:

  1. Management Zone + Auto-tag (không phụ thuộc gì)
  2. SLO (phụ thuộc Management Zone)
  3. Dashboard (phụ thuộc SLO + Auto-tag)

Nếu phát hiện circular dependency (A → B → A), Monaco báo lỗi ngay tại bước này mà không deploy gì.

Bước 6 — Rate limit calculation → tránh 429 errors

Dynatrace API có rate limits (thường 50 requests/minute cho Settings 2.0). Monaco không ngu ngốc fire hàng trăm requests cùng lúc — nó tính toán batch size và thêm delays giữa các batches. Với feature flag MONACO_FEAT_GRAPH_DEPLOY_PARALLEL=true, các configs ở cùng level trong DAG (không phụ thuộc nhau) được deploy song song trong cùng batch.

Bước 7 — Deploy batch → idempotent PUT/POST via Dynatrace API

Mỗi config được deploy với logic:

  • Settings 2.0: PUT request với externalId → Dynatrace tự biết create hay update
  • Classic API: Monaco check config đã tồn tại chưa (via externalId tag) → PUT update hoặc POST create
  • Automation: POST/PUT via Automation API endpoint

Idempotent nghĩa là: chạy monaco deploy 5 lần liên tiếp với cùng config → kết quả trên Dynatrace giống hệt nhau, không tạo duplicate, không có side effects.

Bước 8 — Track externalId → cho phép update/delete chính xác

Sau khi deploy thành công, Monaco confirm externalId đã được gắn lên config trên Dynatrace. Lần deploy tiếp theo, nó dùng externalId để:

  • Tìm lại config đã deploy trước đó
  • Update nếu content thay đổi
  • Skip nếu content giống hệt (no-op)
  • Delete nếu config xuất hiện trong delete.yaml

3.3 Tại sao dependency graph quan trọng?

Hãy tưởng tượng bạn có 1 SLO config reference Management Zone “Production Services”:

Nếu Monaco deploy SLO trước Management Zone → API sẽ reject vì Management Zone ID chưa tồn tại. Monaco giải quyết bằng cách tự động detect reference này, thêm edge vào DAG, và deploy Management Zone trước.

So sánh với Terraform

Dependency resolution trong Monaco tương tự depends_on trong Terraform, nhưng ở Monaco nó IMPLICIT qua reference parameters — bạn không cần khai báo dependency explicitly. Terraform cũng có implicit dependencies qua resource references (aws_subnet.main.id), nhưng đôi khi vẫn cần explicit depends_on. Monaco không bao giờ cần explicit dependency declaration.

So sánh với ArgoCD sync waves

Nếu bạn quen ArgoCD, dependency ordering trong Monaco tương tự sync waves / Helm hook weights. Nhưng thay vì bạn phải annotate argocd.argoproj.io/sync-wave: "1" bằng tay, Monaco tự tính wave từ dependency graph. Ít manual work hơn, ít lỗi hơn.

4.2 Chi tiết từng type

Settings 2.0 — Đây là type bạn sẽ dùng nhiều nhất. Mỗi Settings 2.0 config được define bởi 1 schema (vd: builtin:tags.auto-tagging). Schema quy định fields nào có thể set, validation rules, và scope (environment, host, process group…). Ưu điểm lớn nhất: Dynatrace validate payload theo schema trước khi apply, nên bạn biết lỗi ngay lập tức thay vì deploy xong mới phát hiện config sai.

Classic API — Các endpoint REST API truyền thống như dashboard, alerting-profile, synthetic-monitor. Payload là free-form JSON — không có schema validation phía server. Bạn có thể gửi JSON sai format và API vẫn accept, nhưng config sẽ behave unexpected. Classic API đang dần deprecated — khi 1 config type available ở cả Classic API và Settings 2.0, luôn ưu tiên Settings 2.0.

Automation — Workflows là tính năng mạnh nhất của Dynatrace platform: auto-remediation, notification routing, data processing… Automation configs yêu cầu OAuth vì chúng chạy ở platform level, không phải environment level. Có từ Monaco v2.6.0+.

Bucket — Grail data buckets cho phép bạn tạo custom storage cho logs, metrics, business events. Mỗi bucket có retention policy riêng. Dùng khi bạn cần tách biệt data giữa các teams hoặc compliance domains.

Document — Dynatrace đang migrate dashboards từ Classic (JSON-based) sang new-generation (Document-based). Nếu bạn đang dùng Dynatrace Apps / new UI, dashboards mới thuộc loại Document. Notebooks cũng là Document type.

OpenPipeline — Pipelines xử lý data trước khi vào Grail: masking PII, enrichment, routing, filtering. Đặc biệt quan trọng cho compliance (GDPR/HIPAA) — bạn cần ensure pipeline config consistent across environments.

Account Management — Users, groups, policies ở level account (không phải environment). Deploy qua subcommand riêng: monaco account deploy. Cần OAuth credentials với account-level scopes.

4.3 Settings 2.0 vs Classic API — Migration path

Dynatrace đang dần migrate Classic API sang Settings 2.0. Lộ trình:

Classic API (legacy) ──────────────────▶ Settings 2.0 (modern)
                                          ▲
  auto-tag          ───────▶  builtin:tags.auto-tagging        ✅ Done
  alerting-profile  ───────▶  builtin:alerting.profile         ✅ Done
  dashboard         ───────▶  Documents (new-gen)              🔄 In progress
  synthetic-monitor ───────▶  (vẫn Classic, chưa migrate)      ⏳ Planned
  request-attributes───────▶  builtin:request-attributes       ✅ Done

Khi bạn thấy 1 config type available ở cả 2, ưu tiên Settings 2.0 vì:

  • Schema validation tốt hơn — bắt lỗi sớm
  • Scope control granular hơn — có thể apply ở host/process group level thay vì chỉ environment
  • Dynatrace roadmap focus vào Settings 2.0 — Classic API sẽ deprecated dần
  • externalId tracking native — không cần workaround

Kiểm tra config thuộc loại nào

Chạy monaco generate schema để list tất cả available Settings 2.0 schemas trên environment của bạn. Nếu config bạn cần không có trong list → dùng Classic API (tạm thời). Khi Dynatrace migrate xong schema đó, bạn sẽ thấy nó xuất hiện trong list và nên chuyển sang.

Hoặc trong Dynatrace UI: Settings → tìm config → nếu URL chứa /ui/settings/builtin: → đó là Settings 2.0.

5. Authentication — Security model

5.1 Hai phương thức authentication

Monaco hỗ trợ 2 phương thức auth, mỗi cái phục vụ scope khác nhau:

API Token — Authentication truyền thống cho environment-level resources. Token được tạo trong Dynatrace UI, scope vào 1 environment cụ thể. Đơn giản, trực tiếp, đủ cho hầu hết use cases.

OAuth Client Credentials — Authentication cho platform-level resources. OAuth client được tạo trong Account Management, scope vào account/platform — cross-environment. Cần cho Automation, Documents, Buckets, OpenPipeline vì chúng là platform features, không tied vào 1 environment.

5.2 API Token — chi tiết

Tạo token:

  1. Dynatrace UI → Settings → Access tokens (hoặc search “Access tokens”)
  2. Generate new token → đặt tên descriptive: monaco-cicd-token
  3. Chọn scopes cần thiết (xem bảng bên dưới)
  4. Generate → copy token (dt0c01.XXXX.YYYY) — chỉ hiển thị 1 lần

Scopes cần thiết theo use case:

# === MINIMUM cho deploy Settings 2.0 + Classic API ===
settings.read               # Đọc Settings 2.0 configs
settings.write              # Ghi Settings 2.0 configs
ReadConfig                  # Đọc Classic API configs
WriteConfig                 # Ghi Classic API configs

# === Thêm cho download ===
DataExport                  # Download dashboard data
entities.read               # Đọc entity information

# === Thêm cho specific config types ===
ExternalSyntheticIntegration    # Synthetic monitors (3rd party)
credentialVault.read            # Read credential vault entries
credentialVault.write           # Write credential vault entries
extensionEnvironment.read       # Extension 2.0 configs
extensionEnvironment.write      # Extension 2.0 configs

Best practices cho API Token:

  • Tạo dedicated token cho Monaco — không share với Terraform, scripts, hay tools khác. Khi token bị compromise, bạn revoke 1 token mà không ảnh hưởng tools khác.
  • Đặt expiry date — token vĩnh viễn là security risk. Set expiry 90 ngày, có process rotate trước khi hết hạn.
  • Lưu trong secret manager (HashiCorp Vault, AWS Secrets Manager, GitHub Secrets) — không bao giờ hardcode trong file.
  • Trong CI/CD: inject qua environment variable DT_API_TOKEN.

5.3 OAuth Client Credentials — chi tiết

Khi nào cần OAuth:

OAuth cần cho mọi platform-level resources: Automation (Workflows), Documents (Dashboards new-gen, Notebooks), Buckets, OpenPipeline. Lý do: platform resources không tied vào 1 environment — chúng chạy ở platform layer, nên cần auth ở platform layer.

Tạo OAuth client:

  1. Dynatrace Account Management → Identity & Access Management → OAuth clients
  2. Create client → chọn scopes:
    • automation:workflows:write — cho Workflows
    • document:documents:write — cho Documents
    • storage:buckets:write — cho Buckets
    • openpipeline:configurations:write — cho OpenPipeline
  3. Nhận clientId, clientSecret → lưu an toàn
  4. Token endpoint: https://sso.dynatrace.com/sso/oauth2/token (SaaS)

5.4 Bảng tổng hợp: Resource type → Auth method → Required scopes

Resource TypeAuth MethodRequired Scopes
Settings 2.0API Tokensettings.read, settings.write
Classic APIAPI TokenReadConfig, WriteConfig
Classic API (download)API Token+ DataExport (cho dashboards)
Synthetic monitorsAPI Token+ ExternalSyntheticIntegration
Automation (Workflows)OAuthautomation:workflows:read, automation:workflows:write
DocumentsOAuthdocument:documents:read, document:documents:write
BucketsOAuthstorage:buckets:read, storage:buckets:write
OpenPipelineOAuthopenpipeline:configurations:read, openpipeline:configurations:write
Account (Users/Groups)OAuth (Account)account-idm-write, account-env-write

Tại sao OAuth cho Automation?

Platform resources (Workflows, Documents) yêu cầu OAuth vì chúng chạy ở platform level, không phải environment level. API Token chỉ scope vào 1 environment, trong khi OAuth scope vào platform/account — có thể truy cập cross-environment resources.

Analogy: API Token giống SSH key cho 1 server cụ thể. OAuth giống IAM role trong AWS — scope vào account, có thể access multiple resources across regions.

KHÔNG BAO GIỜ commit token vào Git

Token bị leak trên Git (kể cả repo private) → attacker có thể:

  • Xoá toàn bộ Dynatrace config (alerting, dashboards, management zones)
  • Inject malicious alerting rules (suppress real alerts, tạo fake alerts)
  • Exfiltrate monitoring data (business metrics, user sessions, PII)
  • Modify synthetic monitors để point đến malicious endpoints

Dùng environment variables + secret manager. Luôn luôn. Thêm *.env vào .gitignore. Chạy git-secrets hoặc gitleaks trong CI pipeline.

6.2 manifest.yaml — Anatomy chi tiết

Giải thích từng field quan trọng:

  • manifestVersion: "1.0" — Version của manifest schema. Hiện tại luôn là "1.0". Dynatrace có thể release version mới trong tương lai với breaking changes.

  • projects[].name — Tên logical của project. Dùng khi reference configs cross-project (vd: team-frontend dashboard reference shared management zone). Cũng dùng trong CLI flag -p shared để deploy 1 project cụ thể.

  • projects[].path — Path relative tới manifest.yaml. Monaco resolve path từ vị trí manifest file, không phải current working directory.

  • url.type: environment — Đây là điểm dễ nhầm nhất. value: DT_DEV_URL KHÔNG PHẢI URL — nó là tên environment variable mà Monaco sẽ đọc lúc runtime. Thiết kế này đảm bảo URL và credentials không bao giờ nằm trong file YAML (có thể commit vào Git).

  • auth.token.name — Tương tự, đây là tên env var chứa API token, không phải token string.

  • oAuth — Block OAuth chỉ cần khi project có Automation/Document/Bucket/OpenPipeline configs. Nếu bạn chỉ dùng Settings 2.0 và Classic API, block này không cần.

manifest.yaml tương tự Terraform backend config

Nó nói cho tool biết nơi deploy (environments) và gì deploy (projects), nhưng không chứa config thật. Config thật nằm trong các config.yaml files bên trong project directories. Giống cách Terraform backend config chỉ define state storage location, không chứa resource definitions.

6.3 config.yaml — Settings 2.0

Giải thích fields:

  • id — Unique identifier cho config này trong scope project. Kết hợp với project name và config type, tạo thành externalId unique toàn cục. ID này KHÔNG PHẢI display name — bạn có thể đổi name mà không ảnh hưởng tracking.

  • template — Path relative tới config.yaml chứa JSON payload. Monaco đọc file này, resolve Go templates, rồi gửi kết quả tới API.

  • skip: false — Flag cực kỳ hữu ích. Set true để temporarily disable 1 config mà không cần xoá file. Dùng khi debug hoặc khi config gây issue trên 1 environment.

  • schema — Settings 2.0 schema ID. Tìm full list tại Dynatrace UI → Settings, hoặc monaco generate schema.

  • scope — Nơi config được apply. environment = toàn bộ environment. Có thể set scope granular hơn bằng entity selector hoặc reference tới host group/process group.

6.4 config.yaml — Classic API

Sự khác biệt với Settings 2.0: field type chỉ là api: <endpoint-name> — không có schema, schemaVersion, hay scope. Classic API scope luôn là environment-wide.

6.5 Template file (.json) — Go template syntax

Go template syntax trong Monaco:

  • {{ .name }} → resolve từ parameters section hoặc config name field
  • {{ .paramName }} → resolve từ parameter có key paramName
  • Chỉ simple variable substitution — không hỗ trợ if/else/range trong template (khác với Helm templates)

Naming convention cho folders

Đặt tên folder match config type giúp navigate dễ hơn khi project lớn:

  • auto-tagging/ cho builtin:tags.auto-tagging
  • alerting-profile/ cho builtin:alerting.profile hoặc Classic alerting-profile
  • management-zone/ cho builtin:management-zones

Monaco không enforce naming — bạn có thể đặt tên gì cũng được. Nhưng convention giúp team mới onboard nhanh hơn, và grep tìm config dễ hơn.

8. Parameter Types — Hệ thống templating

Monaco có 4 loại parameter, mỗi loại phục vụ mục đích khác nhau. Hiểu rõ chúng là chìa khoá để viết config linh hoạt.

8.1 Value parameter — giá trị tĩnh

Giá trị hard-coded trực tiếp trong config file. Dùng cho:

  • Giá trị không thay đổi giữa environments (team name, tag key names)
  • Default values không nhạy cảm
  • Giá trị cần version control rõ ràng

Trong template: {{ .owner }} → resolve thành team-platform.

Analogy: Giống default value trong Terraform variable — giá trị tĩnh, commit được vào Git.

8.2 Environment parameter — đọc từ env var

Đọc giá trị từ OS environment variable lúc runtime. Dùng cho:

  • Secrets (API keys, webhook URLs, email addresses)
  • Giá trị khác nhau giữa environments mà không muốn hardcode
  • Giá trị inject từ CI/CD pipeline (GitHub Secrets, Vault)

Trong template: {{ .alertEmail }} → resolve thành giá trị của $ALERT_EMAIL.

Environment type là cách Monaco inject secrets without hardcoding

Giống Helm values nhưng đọc từ env vars thay vì -f values.yaml. Ưu điểm: secrets không bao giờ xuất hiện trong bất kỳ file nào trên disk — chúng chỉ tồn tại trong memory lúc Monaco chạy.

8.3 Compound parameter — nối nhiều tham số

Nối nhiều parameters thành 1 giá trị mới. Dùng khi:

  • Cần tạo composite values từ nhiều sources
  • Naming convention cần consistent (vd: <team>-<env>-<service>)
  • Giá trị cuối cùng phụ thuộc vào nhiều inputs

Trong template: {{ .fullTag }} → resolve thành platform-prod.

8.4 Reference parameter — tham chiếu config khác (quan trọng nhất)

Reference parameter là cơ chế mạnh nhất — nó tạo implicit dependency giữa configs. Khi Monaco thấy reference, nó:

  1. Thêm edge vào dependency graph: SLO → depends on → Management Zone
  2. Deploy Management Zone trước (theo topological sort)
  3. Lấy id của MZ đã deploy → inject vào SLO template
  4. Deploy SLO với MZ ID đã resolved

Trong template: {{ .managementZoneId }} → resolve thành ID thật của Management Zone trên Dynatrace (vd: vu9U3hXa3q0AAAABABlidWlsdGluOm1hbmFnZW1lbnQtem9uZXMABnRlbmFudAAGdGVuYW50AClNaWNyb3NlcnZpY2VzIERlbW8gLSBLdWJlcm5ldGVzvu9U3hXa3q0).

Reference vs Terraform depends_on

Reference parameter kết hợp 2 chức năng mà trong Terraform tách rời:

  • Dependency declaration (depends_on)
  • Output reference (module.vpc.id)

Trong Monaco, khi bạn viết type: reference + property: id, bạn vừa khai báo dependency, vừa lấy output value — tất cả trong 1 block. Gọn hơn, nhưng cũng implicit hơn — bạn cần đọc kỹ reference params để hiểu dependency graph.

9. Feature Flags

Monaco có một số feature flags bật qua environment variable. Chúng kiểm soát behavior nâng cao, thường dùng cho large-scale deployments.

Feature FlagMô tảDefault
MONACO_FEAT_GRAPH_DEPLOYDeploy theo dependency graph (DAG) thay vì sequential. Đảm bảo thứ tự deploy đúng theo dependencies.Enabled (v2.15+)
MONACO_FEAT_FAST_DEPENDENCY_RESOLVERDùng resolver nhanh hơn cho dependency graph. Giảm thời gian build DAG ở large projects.Disabled
MONACO_FEAT_GRAPH_DEPLOY_PARALLELCho phép deploy song song các configs ở cùng level trong DAG (không phụ thuộc nhau). Giảm thời gian deploy tổng thể.Disabled

Khi nào nên bật:

  • GRAPH_DEPLOY_PARALLEL: Khi project có 100+ configs và deploy time quá lâu. Parallel deploy có thể giảm 50-70% thời gian. Tuy nhiên, cần lưu ý rate limits — parallel requests tăng risk 429 errors. Monaco có built-in rate limiter nhưng với rất nhiều concurrent configs, vẫn nên monitor.

  • FAST_DEPENDENCY_RESOLVER: Khi DAG build mất quá lâu (>10 giây). Thường chỉ xảy ra với 500+ configs với nhiều cross-references.

Feature flags có thể thay đổi giữa versions

Dynatrace có thể promote feature flag thành default behavior (như GRAPH_DEPLOY đã enabled by default từ v2.15), hoặc remove flag khi feature stable. Luôn check release notes khi upgrade Monaco version.
