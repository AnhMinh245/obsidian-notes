1. OAuth — Tại sao cần authentication khác?

Bối cảnh: Environment API vs Platform API

Cho đến giờ, bạn dùng API Token để deploy mọi thứ — Management Zone, Alerting Profile, Dashboard, SLO. API Token hoạt động tốt vì tất cả configs đó thuộc về Environment API — chúng sống trong 1 Dynatrace environment cụ thể (ví dụ: abc12345.live.dynatrace.com).

Nhưng khi bước vào Automation (Workflows, Business Calendars, Scheduling Rules), bạn gặp 1 thay đổi kiến trúc quan trọng: Automation resources chạy ở Platform level, không phải Environment level.

Tại sao? Vì Workflow có thể:

  • Cross-environment: 1 workflow có thể query data từ environment A, trigger action trên environment B
  • Cross-tenant: Trong Dynatrace Platform (SaaS), 1 account có thể có nhiều environments. Workflow orchestrate giữa chúng
  • Access platform services: AutomationEngine, AppEngine, Grail (data lakehouse) — đây là platform services, không thuộc 1 environment nào cụ thể

API Token scope vào 1 environment — nó được tạo trong environment settings, chỉ có quyền trong environment đó. Bạn không thể dùng API Token của environment A để access Automation APIs.

OAuth scope vào platform/account — nó được tạo trong Account Management (cấp cao hơn environment), có thể access Platform APIs bao gồm Automation.

OAuth credentials có expiry — khác hoàn toàn API Token

API Token bạn có thể set “never expire” (dù không nên). OAuth Client Secret luôn expires — default 1 năm, có thể config ngắn hơn. Trong production, bạn CẦN:

  1. Lưu credentials trong vault (HashiCorp Vault, AWS Secrets Manager)
  2. Automate rotation trước expiry
  3. CI/CD pipeline pull credentials từ vault, không hardcode

Nếu quên rotate → deploy fail lúc 3AM → P1 incident. Đừng để điều đó xảy ra.

2. Deploy Workflow — Auto-Remediation

Scenario thực tế

Hình dung: 3 giờ sáng, CPU spike trên production cluster. Truyền thống, điều gì xảy ra?

  1. Davis AI detect CPU anomaly → tạo Problem
  2. Problem trigger Alerting Profile → gửi notification tới on-call
  3. On-call engineer thức dậy, mở laptop, SSH vào server
  4. Chạy diagnostic commands, tìm root cause
  5. Execute remediation (restart service, scale pods)
  6. Verify recovery
  7. Post-mortem

Toàn bộ quá trình: 30 phút - 1 giờ. Trong thời gian đó, users bị ảnh hưởng.

Với Dynatrace Workflow, bạn automate steps 2-6:

  1. Davis AI detect CPU anomaly → tạo Problem
  2. Workflow tự động trigger — không cần human
  3. Task 1: JavaScript action — phân tích problem event, extract root cause entity
  4. Task 2: DQL query — lấy CPU metrics chi tiết cho affected host
  5. Task 3: HTTP action — gọi remediation webhook (restart pod, trigger scale-up)
  6. Task 4: Notification — gửi Slack message cho team: “Problem detected, auto-remediated”

Toàn bộ: 2 phút. Engineer nhận Slack message khi vẫn đang ngủ, sáng dậy review post-mortem.

Workflow as Code nghĩa là: automation này version controlled, test được trên staging trước khi promote lên production, rollback được nếu có bug.

config.yaml cho Automation type

Giải thích block type: automation:

FieldGiá trịGiải thích

Sub-typeMục đíchVí dụ

Parameters:

  • cpuThreshold (type: value): Giá trị cố định 90. Dùng trong template để define threshold.
  • webhookUrl (type: environment): URL webhook đọc từ env var. Khác type: value vì URL khác nhau per environment (staging webhook vs production webhook).

wf-auto-remediation.json — Workflow Template

Workflow template có cấu trúc: trigger → tasks (DAG of actions) → connections (implicit qua predecessors):

Giải thích từng phần chi tiết

Trigger block — Khi nào workflow chạy?

  • type: "davis-problem": Workflow trigger khi Davis AI phát hiện problem. Đây là trigger type phổ biến nhất.
  • categories.resource: true: Chỉ trigger cho problems category RESOURCE (CPU, memory, disk). Không trigger cho AVAILABILITY hay ERROR problems.
  • Trigger types khác: "event" (custom event), "schedule" (cron), "manual" (user trigger thủ công).

Task 1: detect_issue — JavaScript Action

Đây là task type mạnh nhất — chạy JavaScript code trong Dynatrace runtime. Code có access tới:

  • @dynatrace-sdk/automation-utils: Utilities cho workflow (get execution context, read previous task results)
  • @dynatrace-sdk/client-*: Full Dynatrace SDK (query APIs, create configs, send notifications)

Script trong task này:

  1. Import execution utility
  2. Lấy execution context (chứa trigger event data)
  3. Extract display_id (problem ID) và root_cause_entity_id (entity gây problem)
  4. Return object → task tiếp theo access qua result('detect_issue')

Task 2: run_dql_query — DQL Query Action

Chạy DQL (Dynatrace Query Language) query. DQL giống SQL nhưng cho observability data:

  • timeseries: Query time-series metrics
  • avg(dt.host.cpu.usage): Trung bình CPU usage
  • by:{dt.entity.host}: Group by host entity
  • filter:{...}: Filter cho specific host (root cause entity từ task trước)

Chú ý double curly braces escaped: {{ '{{' }} và {{ '}}' }}. Đây là Go template trick — workflow runtime dùng {{ }} cho expressions, nhưng Monaco template engine CŨNG dùng {{ }}. Để tránh Monaco interpret workflow expressions, wrap trong literal strings {{ '{{' }}.

Double template escaping — nguồn lỗi phổ biến nhất

Workflow template có 2 lớp template rendering:

  1. Monaco render {{ .name }}, {{ .cpuThreshold }}, {{ .webhookUrl }} → inject values
  2. Workflow runtime render {{ result('detect_issue').rootCause }} → inject task results

Monaco PHẢI KHÔNG render workflow expressions. Nên dùng {{ '{{' }} (literal {{ trong Go template). Nếu bạn thấy lỗi “undefined variable detect_issue” → Monaco đang render workflow expression. Check escaping.

Task 3: send_notification — HTTP Function

Gửi HTTP request tới external endpoint. Dùng cho:

  • Webhook (Slack, Discord, custom)
  • REST API calls (restart service, trigger pipeline)
  • Integration với third-party tools

predecessors — Task ordering trong workflow

predecessors define task DAG (Directed Acyclic Graph) — giống needs trong GitHub Actions hoặc dependencies trong Airflow. Task chỉ chạy khi TẤT CẢ predecessors hoàn thành thành công.

Flow trong workflow này:

4. Deploy Metric Event (Custom Alert)

Concept: Custom Alerting Rule

Davis AI rất giỏi detect anomalies tự động — nhưng đôi khi bạn cần alerting rule CỤ THỂ mà Davis không cover. Ví dụ:

  • “Alert khi CPU > 90% trong 5 phút liên tục” (absolute threshold)
  • “Alert khi disk usage > 85%” (capacity planning threshold)
  • “Alert khi custom metric order.count < 10 trong 1 giờ” (business metric anomaly)

Metric Event = custom alerting rule dựa trên metric threshold. Bạn define:

  • Metric: metric nào monitor (CPU, memory, custom metric)
  • Condition: threshold bao nhiêu (>, <, =)
  • Duration: bao lâu vi phạm mới fire (avoid false positives)
  • Entity filter: apply cho entities nào

Khi condition met → Dynatrace tạo Custom Event → event này flow qua Alerting Profile → Notification → team nhận alert.

So sánh: Metric Event giống PrometheusRule trong Prometheus/Alertmanager — define recording/alerting rules dựa trên metrics. Khác biệt: Metric Event tích hợp sẵn với Davis AI (auto-merge related events, root cause analysis).

Settings 2.0 schema: builtin:anomaly-detection.metric-events

config.yaml

Schema builtin:anomaly-detection.metric-events — đây là Settings 2.0, nên có đầy đủ schema validation. Dynatrace sẽ reject payload không match schema.

metric-event-cpu.json

Giải thích từng block chi tiết

modelProperties — Logic phát hiện anomaly

FieldGiá trịGiải thích
typeSTATIC_THRESHOLDDùng threshold cố định (90%). Option khác: AUTO_ADAPTIVE_BASELINE (Davis AI tự learn baseline, alert khi deviate)
threshold90Ngưỡng: 90% CPU
alertOnNoDatafalseKHÔNG alert khi không có data. true = alert khi host stop reporting (dùng cho availability monitoring)
alertConditionABOVEAlert khi metric TRÊN threshold. Options: ABOVE, BELOW
violatingSamples5Số data points phải VI PHẠM threshold
samples5Tổng data points trong sliding window
dealertingSamples3Số data points phải BÌNH THƯỜNG để tắt alert

Logic: 5 out of 5 samples phải > 90% → alert fires. Sau đó, 3 samples liên tục < 90% → alert clears.

Tại sao violatingSamples: 5 và samples: 5? Đây là strategy “all samples must violate” — nghiêm ngặt nhất, tránh false positive từ momentary spike. Nếu muốn lenient hơn: violatingSamples: 3, samples: 5 = 3 out of 5 samples vi phạm là đủ.

Chọn violatingSamples và samples phù hợp

  • Strict (5/5): Production critical metrics. Chỉ alert khi sustained issue. Ít false positives.
  • Moderate (3/5): Important metrics. Alert sớm hơn nhưng vẫn filter spikes.
  • Sensitive (1/5): Security/compliance metrics. Alert ngay khi có 1 violation. Nhiều false positives nhưng không miss real issues.

Default data point interval = 1 phút. Nên samples: 5 = 5 phút sliding window.

queryDefinition — Metric nào monitor

  • metricKey: "builtin:host.cpu.usage": Builtin metric cho host CPU usage (0-100%). Dynatrace có hàng nghìn builtin metrics — explore trong Data Explorer.
  • aggregation: "AVG": Trung bình trong mỗi data point interval. Options: AVG, MIN, MAX, SUM, COUNT, PERCENTILE.
  • entityFilter.dimensionKey: "dt.entity.host": Alert per host (mỗi host được evaluate independently).
  • conditions: []: Không filter host — apply cho TẤT CẢ hosts. Thêm conditions để scope cho specific hosts/host groups.

eventTemplate — Custom event khi alert fires

  • title: Tiêu đề event hiển thị trong Dynatrace Problems. {dims:dt.entity.host} là placeholder — Dynatrace inject host name thực tế.
  • davisMerge: true: Davis AI sẽ merge event này với related problems. Ví dụ: CPU high + memory high trên cùng host → Davis merge thành 1 problem.

Deploy & Verify

Verify trên Dynatrace UI:

  1. Settings → search “Custom events for alerting” (hoặc navigate Anomaly detection → Custom events for alerting)
  2. Tìm “High CPU Alert”
  3. Verify: threshold 90%, 5/5 samples, dealerting 3 samples
  4. Metric: builtin:host.cpu.usage, aggregation AVG

5. Deploy Request Attributes (Classic API)

Concept: Enriching traces với business context

Dynatrace tự động capture technical data từ traces — response time, error rate, throughput, database calls. Nhưng đôi khi bạn cần business context: Order ID, User Role, Tenant ID, Transaction Type.

Request Attributes capture business data từ HTTP requests/responses — extract giá trị từ headers, query parameters, request body, cookies, response headers. Dữ liệu này enrichment cho traces, cho phép:

  • Filter by business context: “Show me all traces for order #12345”
  • Multidimensional analysis: “Response time by tenant ID” → discover tenant nào có performance issue
  • Business impact assessment: “Problem này ảnh hưởng bao nhiêu premium users?”

So sánh: Request Attributes giống span attributes trong OpenTelemetry — thêm custom key-value vào traces. Khác biệt: Request Attributes capture data ở agent level (auto-instrumented), không cần sửa code application. OpenTelemetry span attributes cần explicit code instrumentation.

Request Attributes = zero-code data enrichment

Bạn KHÔNG cần sửa application code. Dynatrace agent (OneAgent) capture data từ HTTP layer. Define Request Attribute → agent bắt đầu capture → data available trong traces, filters, dashboards.

Đây là 1 trong những điểm mạnh nhất của Dynatrace so với pure open-source solutions: full-stack auto-instrumentation + runtime data capture.

  3. Verify 3 data sources: header, query param, POST param
  4. Test: gọi service với header X-Order-ID: TEST-123 → kiểm tra trace có attribute Order ID = “TEST-123”

Sử dụng Request Attributes trong phân tích

Sau khi deploy, Order ID available trong:

  • Service flow: Filter by Order ID → trace specific order’s journey
  • Multidimensional analysis: Group by Order ID → find slow orders
  • DQL queries: fetch spans | filter request.attribute.Order_ID == "ORD-12345" → full trace cho order cụ thể
  • Dashboard tiles: Filter by request attribute → business-context dashboard

6. Compound Parameters — Khi value đơn giản không đủ

Concept: Ghép nhiều giá trị thành 1 string

Trong các labs trước, parameters đều là giá trị đơn lẻ: 1 string, 1 number, 1 reference ID. Nhưng đôi khi bạn cần tạo string kết hợp nhiều giá trị từ nhiều nguồn.

Ví dụ thực tế: Auto-tagging rule cần tag value format {environment}-{team}-{region}. Giá trị cuối cùng: "production-checkout-ap-southeast-1". Bạn không thể dùng 1 type: value vì:

  • environment → biết trước, nhưng khác per deploy
  • team → giá trị cố định per config
  • region → đọc từ env var

Compound parameter giải quyết bằng cách kết hợp nhiều sub-values thành 1 formatted string.

Ví dụ config.yaml với compound parameter

Giải thích compound parameter structure:

FieldGiải thích
type: compoundParameter type — kết hợp nhiều sub-values
formatTemplate string. Dùng Go template syntax {{ .propertyName }} để reference sub-values
references[]Array các sub-values. Mỗi sub-value có property (name trong format string), type (value/environment/reference), và giá trị tương ứng

Kết quả: giả sử DEPLOY_REGION=ap-southeast-1:

  • Monaco resolve: envName = "production", serviceName = "checkout", region = "ap-southeast-1"
  • Format: "production-checkout-ap-southeast-1"
  • tagValue parameter = "production-checkout-ap-southeast-1"

Khi nào dùng compound vs các type khác

ScenarioParameter typeVí dụ
Giá trị cố định đơn giảntype: valuename: "Production MZ"
Giá trị từ env vartype: environmenturl: $SLACK_WEBHOOK_URL
ID/property từ config kháctype: referencemzId: ref → mz-production.id
String ghép từ nhiều sourcestype: compoundtag: "prod-checkout-apac"

Compound parameter có thể chứa reference sub-values

Đây là điều mạnh mẽ — bạn có thể compound 1 string từ: giá trị cố định + env var + ID của config khác. Ví dụ:

Kết quả: "production-Production Apps-slo" — kết hợp env var + MZ name từ deployed config.

7. OpenPipeline — Data Processing as Code

OpenPipeline là gì

OpenPipeline là data processing engine của Dynatrace — nó xử lý logs, metrics, events, traces TRƯỚC khi data được lưu vào Grail (Dynatrace data lakehouse). Hãy tưởng tượng nó như ETL pipeline cho observability data.

Tại sao cần processing trước khi lưu?

  • Data volume reduction: Log lines chứa nhiều noise → extract chỉ fields cần thiết, drop phần còn lại → giảm storage cost
  • Data enrichment: Thêm metadata vào records (business context, team ownership)
  • Routing: Route data vào đúng bucket (security logs → security bucket, app logs → app bucket)
  • Compliance: Mask PII data trước khi lưu (GDPR compliance)
  • Custom parsing: Parse custom log formats → structured fields → queryable trong DQL

OpenPipeline configs trong Monaco

OpenPipeline đang trong giai đoạn migration sang Settings 2.0. Hiện tại, Monaco hỗ trợ qua type: automation:

Vì OpenPipeline dùng type: automation → cần OAuth authentication (giống Workflow). Đảm bảo manifest.yaml có block oAuth.

OAuth scopes cần cho OpenPipeline

Ngoài automation scopes đã có, OpenPipeline cần thêm:

ScopeMục đích
openpipeline:configurations:readĐọc pipeline configurations
openpipeline:configurations:writeTạo/sửa pipeline configurations

Update OAuth client trong Account Management → thêm 2 scopes trên → regenerate secret nếu cần.

Trạng thái hiện tại và tương lai

OpenPipeline đang phát triển nhanh chóng:

  • Hiện tại: Monaco deploy qua automation.resource: openpipeline. Config format có thể thay đổi giữa các release.
  • Tương lai: Migrate sang Settings 2.0 schemas → stable API, schema validation, scope control.
  • Best practice: Dùng monaco download để lấy OpenPipeline config hiện có → modify → deploy. Đừng viết từ scratch vì format phức tạp và chưa ổn định.

OpenPipeline config phức tạp — dùng download-modify-deploy workflow

  1. Tạo/configure pipeline trên Dynatrace UI (visual editor dễ dùng hơn)
  2. monaco download → lấy config về local
  3. Clean up, add parameters, templatize
  4. Deploy bằng Monaco → version controlled

Đây là pattern phổ biến cho complex configs: UI for creation, Monaco for management.

OpenPipeline APIs đang evolving

Check Dynatrace docs thường xuyên. Schema có thể thay đổi giữa Dynatrace releases. Nếu deploy fail với schema error → check docs cho updated format.
