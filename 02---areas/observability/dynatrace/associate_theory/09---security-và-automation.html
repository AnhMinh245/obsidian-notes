NOTE

Chương này cover hai chủ đề MỚI trong đề thi 2025-2026: Application Security (runtime vulnerability detection) và Automation (Workflows). Dù tỷ trọng ~8%, câu hỏi thường rất specific — biết thì dễ, không biết thì đoán.

📖 Ref: Application Security | Workflows

IMPORTANT

Security capabilities phụ thuộc vào license, công nghệ/ngôn ngữ, và mức instrument thực tế. Khi ôn thi, hãy nhớ logic sản phẩm; khi triển khai thật, luôn kiểm tra matrix support mới nhất.

1. Application Security — Runtime Analysis ⭐

1.1 Tại Sao Runtime Analysis Chính Xác Hơn?

Hầu hết security tools dùng static analysis (SAST/DAST) — scan source code hoặc binary. Dynatrace dùng runtime analysis — monitor libraries đang thực sự chạy.

STATIC ANALYSIS (SCA/SAST):                RUNTIME ANALYSIS (Dynatrace):
                                            
Scan pom.xml / package.json                 OneAgent monitors JVM runtime
     │                                           │
     ▼                                           ▼
Tìm KHAI BÁO dependencies:                 Tìm LOADED libraries:
  ├── log4j 2.14.1 ← VULNERABLE            ├── log4j 2.14.1 ← VULNERABLE
  ├── commons-io 2.6                        └── commons-io 2.6
  └── unused-lib 1.0 ← VULNERABLE          
      (nằm trong pom.xml nhưng               (unused-lib KHÔNG loaded)
       KHÔNG đang chạy)                      (→ KHÔNG report → ít noise)
                                            
Kết quả: 2 vulnerabilities               Kết quả: 1 vulnerability
⚠️ FALSE POSITIVE: unused-lib              ✅ CHÍNH XÁC: chỉ libraries thật

💡 Ghi nhớ: Runtime = biết library nào thực sự loaded vào memory → chính xác hơn, ít false positive hơn.

1.2 Ba Feature Security

FeatureChức năngHoạt động
RVA (Runtime Vulnerability Analytics)Phát hiện vulnerable librariesScan loaded libs → cross-ref CVE databases
RAP (Runtime Application Protection)Block attacks real-timeDetect & block SQL injection, command injection, SSRF
Code-level VulnerabilitiesPhát hiện vulnerable code patternsAnalyze code execution patterns

1.3 Vulnerability Management — Chi Tiết

Mute/Unmute Vulnerability:

Scenario: RVA detect log4j vulnerability, nhưng team đã có WAF mitigation

Mute options:
  ✅ Vulnerability status = OPEN → CÓ THỂ mute
  ✅ Mute cho specific process group → "Mute trên order-service PG"
  ✅ Mute cho specific CVE → "Mute CVE-2021-44228"
  ✅ Mute cho specific management zone → "Mute cho MZ Production"
  
  ❌ Vulnerability status = RESOLVED → KHÔNG THỂ mute (đã fix rồi)

📝 Câu thi (MC): “Khi nào mute?” → Open + process group + CVE + management zone. KHÔNG resolved.

Security Problem Notifications:

📝 Câu thi (MC): “Types of notifications for security problems?”

  • ✅ PagerDuty
  • ✅ ServiceNow
  • ✅ Emails
  • ✅ Jira
  • ✅ Custom integrations
    → Tất cả 5 đều đúng

Public Internet Exposure:

📝 Câu thi: “Vulnerable component publicly accessible?” → Risk assessment “public internet exposed”

Dynatrace kết hợp Smartscape (🔗 01 - Kiến trúc Dynatrace > 6. Smartscape) để biết:

  • Service có public-facing? (exposed thông qua load balancer/ingress?)
  • → Nếu có + vulnerable → risk cao hơn → “public internet exposed” badge

Vulnerability Topology Levels:

📝 Câu thi (MC): “View third-party vulnerabilities ở topology levels nào?”

  • ✅ Process level — scan loaded libraries trong process
  • ✅ Host level — aggregate vulnerabilities trên host
  • ❌ Application → không phải topology level cho third-party vuln
  • ❌ Service → không phải topology level cho third-party vuln
  • ❌ Data center → KHÔNG

NOTE

Theo verified dump 2026-05-06: chỉ Process và Host là topology levels hỗ trợ. Third-party vulnerabilities (library dependencies) được detect ở process-level và aggregate lên host-level.

1.4 Security Investigator App ⭐

📝 Câu thi: “Describe functionality of Security Investigator app?”
→ Run multiple DQL queries to connect multiple types of data for the primary purpose of investigating security issues

Security Investigator cho phép chạy nhiều DQL queries đồng thời, kết nối logs, traces, events, vulnerabilities để investigate security incidents.

  • ❌ Memory pointing tests → không tồn tại
  • ❌ Check passwords in credential vault → không phải
  • ❌ Investigate user sessions for malicious actors → quá hẹp

2. Workflows (AutomationEngine) ⭐

2.1 Workflow = “Nếu X xảy ra, tự động làm Y”

Workflows kết nối problem detection (🔗 02 - Davis AI và Problem Detection) với automated response:

flowchart TB
    subgraph TRIGGER["🔔 TRIGGER — Khi nào chạy?"]
        T1["Problem detected<br/>Davis tạo problem"]
        T2["Scheduled<br/>cron: Mon 9AM"]
        T3["Manual<br/>User click Run"]
        T4["Event-based<br/>deployment, custom"]
    end

    subgraph CONDITION["❓ CONDITION — Thỏa điều kiện?"]
        C1["severity == RESOURCE<br/>AND entity.type == HOST<br/>AND tag env == production"]
    end

    subgraph ACTIONS["⚡ ACTIONS — Làm gì?"]
        A1["📧 Send Slack message"]
        A2["📝 Create Jira ticket"]
        A3["🔧 Call AWS API to resize"]
        A4["⏱️ Wait 5 minutes"]
        A5["✅ Verify CPU under 80%"]
        A1 --> A2 --> A3 --> A4 --> A5
    end

    TRIGGER --> CONDITION
    CONDITION -->|"Yes"| ACTIONS

💡 So sánh: Workflows ≈ GitLab CI/CD pipelines nhưng cho operations thay vì code deployment.

📝 Câu thi: “Workflows triggers?” → ALL: Problem, Scheduled, Manual, Event-based.

2.2 Action Types — “Làm Được Gì?” ⭐

Workflow actions là building blocks — mỗi step trong workflow dùng 1 action type:

Action TypeChức năngVí dụ thực tế
Run JavaScriptCustom logic, biến đổi dataParse problem details, tính toán, decision logic
Send notificationEmail, Slack, Teams, PagerDutyAlert team khi Davis detect problem
HTTP requestGọi external APIRestart service, scale infrastructure, create ticket
Run DQL queryQuery Dynatrace dataLấy metrics, logs, entities để inform decisions
Davis CoPilotAI-powered analysis”Summarize this problem”, “Suggest root cause”
Set variableLưu giá trị giữa stepsPass data từ step 1 sang step 3
ConditionBranching logic (if/else)“If CPU still > 80% → escalate, else → close”
WaitPause giữa stepsĐợi sau remediation trước khi verify
flowchart TB
    TRG["Trigger: Davis Problem"] --> S1["Step 1: Run DQL"]
    S1 --> S2{"Step 2: cpu > 90?"}
    S2 -->|"NO"| END1["End"]
    S2 -->|"YES"| S3["Step 3: HTTP Request"]
    S3 --> S4["Step 4: Wait 5 min"]
    S4 --> S5["Step 5: Re-query CPU"]
    S5 --> S6{"Step 6: cpu < 80?"}
    S6 -->|"YES"| OK["Resolved"]
    S6 -->|"NO"| ESC["Escalate"]

📝 Câu thi: “DQL trong Workflow?” → Run DQL query action — dùng để lấy data inform decisions.

2.3 Workflow Owner & Permissions

WORKFLOW OWNER
├── Người tạo workflow = default owner
├── Owner quyết định execution context (permissions)
├── Workflow chạy với permissions CỦA OWNER
│
├── ⚠️ Risks:
│   ├── Owner bị xóa account → workflow fail
│   ├── Owner mất permissions → workflow thiếu quyền
│   └── Best practice: dùng service user / shared identity
│
└── Transfer ownership:
    └── Settings > Automation > Workflows > [workflow] > Transfer

📝 Câu thi: “Workflow chạy với permissions của ai?” → Workflow owner (người tạo hoặc được transfer).

2.4 Execution History & Monitoring

Mỗi workflow execution được log:

InfoMô tả
StatusSuccess / Failed / Running
DurationTổng thời gian chạy
Trigger detailsProblem nào trigger, hoặc schedule nào
Step-by-step resultsOutput/error của từng action
RetryCó thể retry failed executions

Navigation: Automate > Workflows > [workflow] > Executions

📝 Câu thi: “Xem workflow đã chạy hay chưa, thành công hay thất bại?” → Execution history

2.5 AutomationEngine Gồm Những Gì?

AutomationEngine là umbrella term cho toàn bộ automation capabilities:

AutomationEngine
├── Workflows (core — xử lý ở trên)
├── Scheduling (cron-based triggers)
├── Business Calendar (business hours awareness)
└── Connections (reusable auth configs cho external services)

📝 Câu thi: “Khi nào dùng Workflow vs khi nào dùng manual process?”
→ Workflow khi: repetitive response, defined remediation, cross-tool orchestration
→ Manual khi: novel problem, complex investigation, human judgment needed

📖 Ref: Workflows

2.7 Tạo Workflow — Walkthrough Thực Tế Trên UI ⭐

NOTE

Phần này mô tả chính xác những gì bạn thấy khi tạo workflow trên giao diện Dynatrace. Bài thi có thể cho ảnh screenshot và hỏi về các thành phần.

Bước 1: Vào Automate → Workflows → Create workflow

Bước 2: Chọn Trigger Type

Trigger TypeMô tảConfigVí dụ
On demandManual — user click RunKhông cần configDebug, test
Time intervalSchedule theo khoảng thời gian cố địnhRun every (mins): 1–720 + Rule: Every day / Weekdays / CustomEmail report mỗi 30 phút
EventDavis event / problem triggerEvent type + filterAuto-remediate khi CPU high
Davis problemDavis detect problemSeverity filterNotify Slack khi ERROR
Davis eventMetric/custom event thresholdDavis Event typeSLO breach notification
Record changeEntity hoặc config thay đổiEntity type filterAudit log khi config changes

IMPORTANT

Schedule Trigger — các field chính (như trong UI thực tế):

  • Run every (mins): giá trị từ 1 đến 720 phút (= 12 giờ)
  • Rule: Every day | Weekdays | Custom (chọn ngày cụ thể)
  • Timezone: ví dụ Asia/Saigon (UTC+7)
  • Advanced options: filter, active window
  • Hiển thị: Next run (timestamp cụ thể) + Show next 10 runs

📝 Câu thi (screenshot): Bạn thấy workflow với Schedule trigger “Every 30 mins | Asia/Saigon” → Time interval trigger với Rule “Every day”

Bước 3: Thêm Actions

Sau trigger, bạn kéo thả actions theo thứ tự:

flowchart TB
    TRIGGER["⏰ Schedule Trigger<br/>Every 30 mins<br/>Asia/Saigon"] --> A1["send_email_1<br/>Send email<br/>To: team@company.com"]
    A1 --> A2["run_javascript_1<br/>Custom logic<br/>(optional next step)"]

Mỗi action có:

  • Name: tự đặt, ví dụ send_email_1
  • Type: Send email, HTTP request, Run DQL, JavaScript, etc.
  • Configuration: tùy type (recipients, query, URL, etc.)
  • Condition: chạy action này khi nào (conditional execution)

Bước 4: Save và Activate

Trạng tháiMô tả
DraftĐang soạn, chưa chạy tự động. Cho phép test Run
LiveĐang hoạt động. Saved updates có effect ngay lập tức

WARNING

Khi workflow ở trạng thái Live: banner “You are viewing a live workflow. Saved updates will be effective immediately.” xuất hiện. Mọi thay đổi apply ngay — cẩn thận!
Để sửa an toàn: click “Edit in draft” → sửa → test → re-activate.

📝 Câu thi (scenario): “Tạo workflow gửi email mỗi 30 phút, timezone Asia/Saigon?” → Schedule trigger, Run every = 30, Rule = Every day, Timezone = Asia/Saigon, Action = Send email

2.6 Workflow Scenarios Từ Dump ⭐

📝 Câu thi (scenario): “Reduce mean-time-to-identify critical security vulnerabilities, send notification to correct team’s Slack channel?”
→ Workflow with an Event Trigger, Ownership and Slack integration

  • Event Trigger = trigger khi Davis detect security vulnerability
  • Ownership = xác định team chịu trách nhiệm
  • Slack integration = gửi notification đúng channel

📝 Câu thi (scenario): “Ensure quality of Software Release, validate key Performance Indicators in Test Environment before promoting to Production?”
→ Workflow that is executed with an event trigger when a Software Release is part of my CI/CD pipeline

  • Workflow trigger bởi deployment event trong CI/CD
  • Actions: query metrics, compare baselines, validate KPIs
  • Pass/fail gate trước khi promote to prod

3. Extensions & Dynatrace Hub ⭐

Hub = marketplace chính thức — tìm extensions, integrations, apps:

Dynatrace Hub
├── Extensions (monitoring plugins)
│   ├── Database: PostgreSQL, MySQL, Oracle, MongoDB
│   ├── Cloud: AWS CloudWatch, Azure Monitor

├── Technology integrations

    ├── Cloud Automation

3.2 Import Metrics Từ Unsupported Platform

📝 Câu thi: “Import metrics từ platform không support OneAgent?“

Unsupported platform (VD: custom hardware, legacy system)
     │
     ├── ✅ Dynatrace Extension
     │   → Tìm hoặc tạo extension → install trên AG → pull metrics
     │
     ├── ✅ OpenTelemetry
     │   → Deploy OTLP exporter → push metrics đến Dynatrace endpoint
     │
     ├── ❌ Create Dynatrace App → App = UI, không import metrics
     │
     └── ❌ Install ActiveGate → AG đơn thuần không import metrics

4. IoT & Custom Devices

📝 Câu thi: “Smart IoT device, không support OneAgent hay agentless RUM?”
→ Dynatrace OpenKit — lightweight SDK cho custom devices / kiosk / non-standard frontends:

OpenKit SDK
├── C/C++ (embedded devices)
├── Java (Android, custom JVM)
├── .NET
└── JavaScript

Use cases:
├── Smart TV → track user interactions
├── Kiosk terminals → monitor crashes
├── Industrial IoT → track device telemetry
└── Custom POS systems → monitor transactions

NOTE

Nếu ứng dụng là mobile app chuẩn, ưu tiên nghĩ đến OneAgent for iOS/Android. OpenKit hợp hơn cho thiết bị hoặc frontend không nằm trong đường đi mobile/web chuẩn.

📖 Ref: OpenKit
