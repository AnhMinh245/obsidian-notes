Chương 4: Digital Experience — Synthetic Monitoring

IMPORTANT

RUM + Synthetic chiếm ~24% đề thi — tỷ trọng CAO NHẤT. Chương này cần nắm kỹ: loại monitor, locations, outage handling, performance thresholds, CI/CD integration, và đặc biệt là scenario-based questions (tình huống giả định dài).

📖 Ref: Synthetic Monitoring | Browser Monitors | HTTP Monitors

NOTE

Nếu RUM (03 - Digital Experience - RUM) theo dõi người dùng thật, Synthetic Monitoring giả lập người dùng — chạy tests tự động, 24/7, từ các locations khác nhau. Hai phương pháp bổ sung cho nhau:

  • RUM = “Users đang trải nghiệm gì?” (passive, real traffic)
  • Synthetic = “App có sẵn và nhanh không?” (active, scripted tests, kể cả khi chưa có user truy cập)

💡 Analogie:

  • HTTP Monitor = gõ cửa xem có ai ở nhà không (lightweight, fast)
  • Single-URL Browser = bước vào nhà, nhìn quanh phòng khách (page load, visual check)
  • Browser Clickpath = vào nhà, đi từ phòng này sang phòng khác, mở cửa, bật đèn (multi-step interaction)

📝 Câu thi: “Simulate user loading single webpage?” → Single-URL browser monitor

  • ❌ HTTP Monitor → không render page, chỉ HTTP request
  • ❌ Browser Clickpath → multi-step, overkill cho 1 URL
  • ❌ Ping test → không tồn tại trong Dynatrace Synthetic

1.2 Browser Engine

📝 Câu thi: “Browser nào cho Synthetic?” → Chromium-based browser engine

  • ❌ Firefox, ❌ Internet Explorer, ❌ Safari

1.3 Browser Clickpath — Chi Tiết Ghi Nhận & Playback

Clickpath được recorded bằng Dynatrace extension trong browser, sau đó replayed tự động:

flowchart LR
    REC["🎬 RECORD<br/>Dynatrace extension<br/>Record user actions"] --> EDIT["✏️ EDIT<br/>Add/remove events<br/>Add validation<br/>Add credentials"]
    EDIT --> LOCAL["▶️ LOCAL PLAYBACK<br/>Verify trước khi deploy<br/>Debug failed steps"]
    LOCAL --> DEPLOY["🚀 DEPLOY<br/>Schedule frequency<br/>Select locations"]
    DEPLOY --> RUN["🔄 AUTO-RUN<br/>Chromium headless<br/>Collect results"]

Clickpath Events (các loại event trong 1 clickpath):

  • Navigate — load URL (bắt buộc là event đầu tiên)
  • Click — click element
  • Keystroke — nhập text (username, search term)
  • JavaScript — execute custom JS code
  • Cookie — set/read cookies
  • Wait — chờ element xuất hiện

TIP

Mỗi clickpath bắt đầu bằng clean state — browser cache trống, local storage trống. Đảm bảo test deterministic.

3. Frequency & Scheduling ⭐

3.1 Execution Frequency Options

FrequencyUse case
5 minCritical apps, high SLA
10 minImportant apps
15 minStandard monitoring (default)
30 minLow-priority pages
1 / 2 / 4 hoursCost-saving, baseline only
On-demand onlyCI/CD trigger, manual test

3.2 Tính Toán Executions Per Hour

IMPORTANT

Công thức: Executions/hour = (60 / frequency_minutes) × number_of_locations

Ví dụ: 15 min interval × 3 locations = 4 × 3 = 12 executions/hour
→ Executions are evenly spaced: mỗi 5 phút có 1 execution (từ 1 location)

📝 Câu thi (tính toán): “Monitor 3 locations, 15 min frequency → how many executions per hour?” → 12

4. Configuration & Settings ⭐

4.1 Content Validation — Đảm Bảo Content Đúng

Bạn có single-URL browser monitor. Page load 200 OK nhưng content lỗi (blank page). Làm sao detect?

Validation Types:

TypeKiểm traVí dụ
Contains textText hiển thị trên page”Welcome to MyApp”
Contains elementCSS selector tồn tại#login-button
Contains text in elementText trong element cụ thể<h1> chứa “Dashboard”
Contains text in DOMText trong DOM/resourceAttribute values, comments
Content Validation Rule:
  Type: Text match
  Condition: Page must contain "Welcome to MyApp"
  Action: FAIL monitor if text NOT found

→ Page load 200 OK nhưng blank page → monitor FAIL → alert

📝 Câu thi: “Ensure page element loaded?” → Content validation rule

4.3 Performance Thresholds ⭐

📝 Câu thi: “Tại sao chờ 24h trước khi adjust thresholds?”

flowchart LR
    A["Activate monitor"] --> B["0-24h: Thu thập data<br/>VD: 15min × 3 loc = 288 points/day"]
    B --> C["24h: Data averaged<br/>→ Reference point chính xác"]
    C --> D["Set thresholds<br/>dựa trên 24h reference"]

→ Performance data averaged over 24h → dùng làm reference point

WARNING

Quy tắc 3-of-5 (từ docs chính thức):
Dynatrace generates a performance problem khi monitor vi phạm threshold trong 3 trong 5 lần chạy gần nhất tại cùng location.

  • Problem được close khi 5 lần chạy liên tiếp tại mỗi affected location đều pass.
  • Vi phạm ở nhiều locations → tất cả included trong cùng 1 problem.

📝 Câu thi: “When does Dynatrace generate a synthetic performance problem?” → Threshold violated in 3 of 5 most recent executions at same location

4.4 Outage Handling ⭐

Outage handling quyết định khi nào tạo problem khi monitor fail:

Global Outage:

  • Mặc định BẬT cho monitors mới
  • Alert khi TẤT CẢ locations fail cùng lúc
  • Default: all locations fail 1 lần → problem
  • Configurable: 1 đến 5 consecutive failures cho global outage

Local Outage:

  • Alert khi một số locations fail liên tiếp
  • Configurable: bao nhiêu locations + bao nhiêu consecutive failures
  • VD: 4 locations, problem khi 3 of 4 locations fail trong 2+ consecutive runs

Retry on Error:

  • Mặc định BẬT — auto-retry khi error
  • Nếu retry thành công → initial error data point discarded (không tính)
  • → Giảm false positives
  • Retry KHÔNG tiêu thêm DEM units

📝 Câu thi (scenario): “Reduce false positive alerts for synthetic monitors?” → Retry on error (enabled by default)

📝 Câu thi (scenario): “Configure alerting when ALL locations fail?” → Global outage setting

6. Performance Metrics ⭐

6.1 Key Performance Metrics

Mỗi browser monitor có thể chọn 1 key performance metric cho mỗi load action/XHR action:

MetricĐịnh nghĩaDefault?
Visually CompleteKhi tất cả elements hiển thị (visible portion) 100% loaded + rendered✅ Default
User Action DurationTổng thời gian từ start → finish của action
Speed IndexTốc độ nội dung visual được render (lower = better)
DOM InteractiveKhi DOM parsed xong, user có thể interact
Load Event StartKhi window load event fired
First Contentful PaintKhi browser render pixel đầu tiên

IMPORTANT

“Visually Complete” là default metric — câu hỏi thi rất hay hỏi!

📝 Câu thi: “How is ‘Visually Complete’ defined?”
→ When all of the elements visible to the user on a webpage are 100% loaded and rendered

  • ❌ “Largest element rendered” → đó là Largest Contentful Paint (LCP)
  • ❌ “Simulated test on browser to evaluate image render speed” → SAI

6.2 Waterfall Analysis

Waterfall graph hiển thị timeline chi tiết mỗi resource loaded trong page:

  • DNS lookup → TCP connect → SSL → Request → Response → Render
  • Identify bottlenecks: slow 3rd-party scripts, large images, render-blocking CSS

🔗 So sánh với RUM Waterfall: 03 - Digital Experience - RUM > 5. Waterfall Analysis

8. RUM vs Synthetic — So Sánh Tổng Hợp ⭐

Tiêu chíRUMSynthetic
Data sourceReal user trafficSimulated/scripted tests
WhenKhi có users truy cập24/7, scheduled
CoverageChỉ pages users truy cậpMọi pages bạn configure
Performance dataReal-world (diverse devices, networks)Controlled conditions
Proactive❌ (reactive — chỉ thấy khi user gặp lỗi)✅ (detect trước khi users ảnh hưởng)
BaselineDynamic (varies by user)Consistent (same conditions mỗi lần)
Off-hours monitoring❌ (no traffic = no data)✅ (chạy liên tục)
JavaScript injectionOneAgent inject vào pageChromium engine built-in

TIP

Khi nào dùng gì?

  • RUM = hiểu user experience thật, diverse conditions
  • Synthetic = SLA monitoring, proactive availability, baseline performance
  • Cả hai = best practice — complementary, không thay thế nhau

📝 Câu thi (scenario): “Ensure app available 24/7, even off-hours?” → Synthetic Monitoring
📝 Câu thi (scenario): “Understand real user experience across different devices?” → RUM

9. Session Replay — Phân Biệt Với Synthetic ⚠️

📝 Câu thi: “What is Session Replay?”
→ A way to capture and visually replay the complete digital experience of every user, similar to a video recording

  • ❌ “A function of synthetic tests to play back recorded tests locally” → SAI (đó là local playback của clickpath)
  • ❌ “Mobile monitoring feature showing notifications and home screen” → SAI
  • ❌ “Debugging tool for developers to replay test executions” → SAI

WARNING

Phân biệt cực kỳ quan trọng:

  • Session Replay = RUM feature, replay user sessions thật (🔗 03 - Digital Experience - RUM > 6. Session Replay)
  • Local Playback = Synthetic feature, chạy clickpath trên local browser để debug

10. Tình Huống Giả Định Thực Tế (Exam Scenarios) ⭐⭐

Scenario 1: Maintenance Window + Synthetic

📝 Câu thi: “I need to take my live environment offline for upgrade. The upgrade overlaps with scheduled synthetic tests. How to avoid false alerting?”
→ Maintenance Window

  • ❌ Delete synthetic monitors → mất config, phải tạo lại
  • ❌ Synthetic on-demand execution → trigger mechanism, không tránh false alerts
  • ❌ Credential Vault → lưu credentials, không liên quan

🔗 02 - Davis AI và Problem Detection > 7. Maintenance Windows

Scenario 2: E-commerce Login Flow

📝 Tình huống: “E-commerce site. Cần test flow: Login → Search product → Add to cart → Checkout. Tests chạy 24/7 từ 5 global locations.”

Giải pháp:

  1. Browser Clickpath — record multi-step flow
  2. Credential Vault — lưu login credentials securely
  3. Content Validation — mỗi step validate text/element
  4. 5 Public Locations — global coverage
  5. Frequency: 15 min → 20 executions/hour

Scenario 3: Internal HR Portal

📝 Tình huống: “HR portal trên intranet. Không accessible từ internet. Cần monitor availability.”

Giải pháp:

  1. Private Synthetic Location — cài trên Environment ActiveGate trong internal network
  2. Single-URL Browser hoặc Clickpath — tùy complexity
  3. Content Validation — verify login page renders

Scenario 4: API Health Check

📝 Tình huống: “Microservices architecture. 20 internal APIs. Cần check health endpoint mỗi 5 phút.”

Giải pháp:

  1. HTTP Monitor — lightweight, không cần browser
  2. Multi-request — chain multiple API calls nếu cần
  3. Response validation — check {"status": "healthy"}
  4. Frequency: 5 min
  5. Private Location nếu internal APIs

Scenario 5: Mobile App Performance Baseline

📝 Tình huống: “Mobile web app. Cần establish performance baseline trên 3G/4G networks.”

Giải pháp:

  1. Single-URL Browser — emulate mobile device
  2. Device profile: Mobile
  3. Bandwidth: Regular 3G hoặc Regular 4G
  4. Screen size: mobile resolution
  5. Sau 24h → set Performance Thresholds dựa trên averaged data

Scenario 6: Pre-deployment Validation

📝 Câu thi: “Ensure quality of software release. Validate KPIs in test environment before promoting to production. Synthetic tests should run automatically when code is deployed.”

Giải pháp:

  1. On-demand Execution — trigger synthetic từ CI/CD pipeline
  2. Hoặc Workflow with event trigger (🔗 09 - Security và Automation > 2.6 Workflow Scenarios)
