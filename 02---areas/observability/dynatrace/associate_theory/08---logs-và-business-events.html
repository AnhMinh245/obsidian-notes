Chương 8: Logs và Business Events

NOTE

Logs là một trong những data sources đổ vào Grail qua OpenPipeline (🔗 01 - Kiến trúc Dynatrace > 5. OpenPipeline). Chương này focus vào: cách ingest, xử lý, và sử dụng log data — đặc biệt là phân biệt Log Events vs Log Metrics (cực kỳ hay nhầm). Business Events là data source riêng, track business outcomes.

📖 Ref: Log Management | Business Events

IMPORTANT

Mốc auto-discovery mỗi 60 giây là kiến thức rất hay gặp trong câu hỏi Logs Classic / OneAgent log module. Khi học phần logs trên Grail/OpenPipeline, hãy nhớ thêm bối cảnh bucket, processing rules, và security context.

1.3 Log Processing Rules — Transform During Ingestion

📝 Câu thi: “Data transformation on logs during ingestion phase?” → Log Processing Rules

  • ❌ Service detection rules → SAI (cho services, không phải logs)
  • ❌ Custom process monitoring rules → SAI (cho processes)
  • ❌ Log Events → SAI (alert, không transform)
  • ❌ Anomaly Detection rules → SAI (detect anomalies, không transform)

Log Processing Rules capabilities:

CapabilityMô tảVí dụ
ParsingExtract structured fields từ textParse JSON logs → fields
MaskingẨn sensitive dataCredit card → ****-****-****-4444
EnrichmentThêm metadata fieldsAdd team:backend, env:prod
RoutingGửi logs vào bucket cụ thểSecurity logs → custom_security_logs
FilteringDrop logs không cần thiếtDrop debug logs trong production
TransformationModify field valuesNormalize log levels, convert formats
flowchart LR
    RAW["Raw Log<br/>Unstructured text"] --> PARSE["Parse<br/>Extract fields"]

📝 Câu thi: “Order of log processing?” → Parse → Mask → Enrich → Route → Store

2. Log Events vs Log Metrics vs Log Processing Rules ⭐⭐

Đây là bộ ba hay nhầm nhất trong phần Logs. Mỗi cái phục vụ mục đích KHÁC NHAU:

2.1 So Sánh Nhanh

Log EventsLog MetricsLog Processing Rules
PurposeALERTMEASURETRANSFORM
InputLog pattern matchLog entries countedRaw log data
OutputAlert / NotificationMetric data pointModified log record
TimingReal-time triggerAggregated over timeDuring ingestion
Ví dụ”OOM found → page team""Count errors/min → metric""Mask PII, enrich with tag”

2.2 Ví Dụ Cụ Thể Từng Loại

Log Events — ALERT khi pattern xuất hiện:

Scenario: Muốn thông báo support team khi có OutOfMemoryError

Config:
  Name: "OOM Alert"
  Pattern: content contains "OutOfMemoryError"
  Notification: → PagerDuty "Critical: OOM on {host}"

Khi log chứa "java.lang.OutOfMemoryError: Java heap space"
  → Log Event triggers → Notification gửi đến PagerDuty

📝 Câu thi: “Log chứa error → notify support?” → Log Events (scenario khi cần alert tức thì dựa trên pattern)

WARNING

⚠️ Phân biệt kỹ scenario:

  • “Notify support when error pattern occurs” → Log Events hoặc Log Metrics tùy cách hỏi
  • Verified dump hỏi “count occurrences + notify” → Log Metrics (vì focus là đếm + alert)
  • Nếu đề hỏi kiểu “whenever messages occur, notify” mà đáp án có Log Metrics → chọn Log Metrics

Log Metrics — ĐẾM/ĐO từ log data:

Scenario: Muốn theo dõi số lượng failed login attempts per minute

Config:
  Name: "failed_login_count"
  Source: fetch logs | filter content contains "Login failed"
  Aggregation: count() per 1 minute
  → Tạo metric: custom.log.failed_login_count

Kết quả: Metric plot trên dashboard, set alert threshold
  → "Alert nếu failed logins > 100/min"
  → 🔗 Dùng Davis AI static threshold (xem [[02 - Davis AI và Problem Detection#4. Thresholds]])

📝 Câu thi: “Count log entry occurrences?” → Log Metrics

📝 Câu thi: “Log files contain error messages, wish to notify support teams to investigate?” → Log Metrics

  • ℹ️ Theo verified dump, đáp án đúng là Log Metrics (không phải Log Events)
  • Log Metrics cho phép tạo metric từ log pattern → set threshold alert
  • ❌ Log Events, Log Viewer, Log Processing Rules, Anomaly Detection → SAI

Log Processing Rules — TRANSFORM data:

Scenario: Mask credit card numbers trong log trước khi store

Rule:
  Match: content matches "\\d{4}-\\d{4}-\\d{4}-\\d{4}"
  Action: Replace with "****-****-****-{last4}"

Raw log:  "Payment processed: card 4111-2222-3333-4444, amount $99"
Stored:   "Payment processed: card ****-****-****-4444, amount $99"

4. Log Access Control ⭐

📝 Câu thi: “Restrict log file access to specific users?”
→ Log Security Context — cơ chế phân quyền ACCESS logs (khác Management Zones).

Ví dụ:
  Log Security Context: "security-team-only"
  → Áp dụng cho security logs (audit trails, auth events)
  → Chỉ users với role "Security Analyst" mới query được

  Log Security Context: "app-team"
  → Áp dụng cho application logs
  → Developers của app đó mới thấy

4.1 Log Security Context vs Management Zones

Log Security ContextManagement Zones
ScopeLog data onlyAll entity types
GranularityPer log source/attributePer entity
Use caseRestrict PII logs, security auditTeam-based data access
Works withIAM policiesIAM policies, Dashboard scoping

🔗 Liên quan: Management Zones (🔗 06 - Configuration và Management > 1. Management Zones) cũng scope data — nhưng Log Security Context là mechanism riêng cho logs.

5. Business Events ⭐

5.1 Business Events Là Gì?

Business Events bridge technical monitoring với business outcomes. Nếu RUM cho biết “users đang trải nghiệm performance thế nào” (🔗 03 - Digital Experience - RUM), Business Events cho biết “business đang hoạt động thế nào”:

Technical metric:  order-service response time = 200ms    ← TECHNICAL
Business event:    order #12345 completed, value = $99    ← BUSINESS

RUM data:         "User clicked Buy button, load time 1.2s"  ← USER EXPERIENCE
Business event:   "Purchase completed: product=iPhone, qty=1" ← BUSINESS OUTCOME

5.2 Ingestion Methods

MethodMô tảVí dụ
OneAgent captureAuto-capture từ configured sourcesCapture from application code
Business Events APIREST pushPOST /api/v2/bizevents/ingest
OpenTelemetryVia OTel spans with bizevents attributesInstrument with OTel SDK

5.5 Fine-Grained Control

📝 Câu thi: “Fine-grained control over business events ingested?” → Thêm attribute dt.security_context
→ Cho phép filter WHO can access WHICH business event data.

5.6 RUM vs Business Events — Phân Biệt

📝 Câu thi (scenario dài): “Capture business-grade data: complete, graded, real-time, performance analysis, end-user experience?”
→ Business Events — vì focus là “business-grade data” + “complete, graded, unconstrained”

WARNING

⚠️ Phân biệt cực kỳ quan trọng:

  • Dump verified chọn Business Events (không phải RUM) vì từ khóa “business-grade” và “complete, graded”
  • Nếu đề hỏi về “user experience monitoring” hoặc “performance of user actions” → RUM
  • Nếu đề hỏi về “business-grade data”, “business outcomes” → Business Events

6.2 OpenPipeline Stages

StageOrderMô tả
Ingest1stReceive raw data
Processing2ndParse, mask PII, transform
Extraction3rdCreate metrics from log patterns
Routing4thDirect to appropriate Grail bucket
Storage5thStore in Grail with retention policy

TIP

OpenPipeline vs Log Processing Rules:

  • OpenPipeline = overall framework cho ALL data types
  • Log Processing Rules = specific rules WITHIN OpenPipeline cho logs

7. Tình Huống Giả Định (Exam Scenarios) ⭐

Scenario 1: PII Compliance

📝 “Company cần mask all email addresses trong logs trước khi store.”
→ Log Processing Rules — masking rule cho email pattern

Scenario 2: Error Rate Tracking

📝 “Track number of 5xx errors per minute, alert when > 50/min.”
→ Log Metrics — count log entries matching 5xx → create metric → set threshold

Scenario 3: Immediate Alert on Critical Error

📝 “Alert PagerDuty immediately when ‘FATAL’ appears in log.”
→ Log Events — pattern match “FATAL” → notification to PagerDuty

Scenario 4: Security Audit Logs

📝 “Security team needs exclusive access to audit logs, retain 1 year.”
→ Log Security Context + Custom Grail bucket (1 year retention) + OpenPipeline routing

Scenario 5: Business Revenue Tracking

📝 “Track total revenue per hour from completed orders.”
→ Business Events — capture purchase events → DQL query with sum(revenue) by hour
