Chương 6: Configuration và Management

NOTE

Các chương trước đã giải thích Dynatrace thu thập và phân tích data thế nào. Chương này trả lời: Làm sao tổ chức, phân quyền, và điều chỉnh monitoring? Đặc biệt cần nắm vững MZ vs HG — cặp khái niệm bị nhầm nhiều nhất trong kỳ thi.

📖 Ref: Management Zones | Tags & Metadata

1. Management Zones vs Host Groups ⭐⭐ CẶP KHÁI NIỆM HAY NHẦM NHẤT

1.1 Management Zones — “Ai Được Xem Gì?”

Mục đích: Kiểm soát visibility và access — phân chia data theo team/environment/geography.

graph TB
    subgraph MZ_PROD["MZ: Production"]
        H1["host-web-01<br/>OrderService"]
        H2["host-web-02<br/>PaymentService"]
        H3["host-db-01<br/>PostgreSQL"]
    end

    subgraph MZ_STG["MZ: Staging"]
        S1["host-stg-01<br/>OrderService-stg"]
    end

    subgraph MZ_FE["MZ: Team A Frontend"]
        F1["host-web-01<br/>FrontendAPI"]
    end

    DEVOPS["👤 DevOps Team<br/>Full access: Prod + Stg"] -.->|"access"| MZ_PROD
    DEVOPS -.->|"read-only"| MZ_STG
    DEV["👤 Dev Team<br/>Full access: Stg only"] -.->|"access"| MZ_STG
    TEAMA["👤 Team A<br/>Frontend only"] -.->|"access"| MZ_FE

Đặc điểm MZ:

  • Cross-entity: áp dụng cho hosts, services, apps, databases — TẤT CẢ entity types
  • Một entity có thể thuộc nhiều MZ (VD: host-web-01 thuộc cả “Production” và “Team A Frontend”)
  • Dùng cho: scoping, dashboard filtering, alerting profile filtering, và làm điều kiện trong IAM/RBAC policies
  • → Trong platform hiện tại, MZ thường đi cùng policy; MZ không tự thay thế toàn bộ cơ chế phân quyền

MZ Rule Types:

Rule TypeDựa trênVí dụ
Entity type + conditionsHost properties, service propertiesHosts with tag env:production
Dimensional data filterMetric dimensionsMetrics from specific host group
Service type filterWeb, background, messagingAll web services

1.2 Host Groups — “Monitor Host Này Thế Nào?”

Mục đích: Cấu hình monitoring settings khác nhau cho từng nhóm hosts.

graph LR
    subgraph HG_WEB["HG: web-servers"]
        W1["host-web-01"]
        W2["host-web-02"]
        CONFIG_W["Config:<br/>Full-stack mode<br/>Auto-injection: ON<br/>PHP monitoring: ON<br/>Log collection: ON<br/>Deep code-level: ON"]
    end

    subgraph HG_DB["HG: db-servers"]
        D1["host-db-01"]
        D2["host-db-02"]
        CONFIG_D["Config:<br/>Infrastructure mode<br/>Auto-injection: OFF<br/>PHP monitoring: OFF<br/>Log collection: ON<br/>Deep code-level: OFF"]
    end

Đặc điểm HG:

  • Chỉ hosts: KHÔNG cho services, apps, hay databases
  • Một host chỉ thuộc 1 Host Group (khác MZ!)
  • Assign khi install OneAgent hoặc bằng oneagentctl (🔗 01 - Kiến trúc Dynatrace > 2.5 Quản Lý OneAgent)

1.3 Tổng Kết: MZ vs HG

Tiêu chíManagement ZonesHost Groups
Câu hỏi trả lời”Ai được xem gì?""Monitor host này thế nào?”
ScopeCross-entity (mọi loại)Chỉ hosts
Entity membershipNhiều MZ per entity1 HG per host
Dùng choRBAC, scoping, alertingOneAgent config per group
Config ở đâuDynatrace UI: Settings > MZInstall time / oneagentctl
Ví dụ”Production”, “Team A""web-servers”, “db-servers”

📝 Câu thi: “Separate entities + only authorized users see data?” → Management Zones
📝 Câu thi: “Categorize hosts with similar characteristics?” → Host Groups
📝 MZ KHÔNG phải HG: “representing user groups” → ❌ HG, “enabling AG connectivity” → ❌ HG

2. Tags & Metadata ⭐

2.1 Metadata = Auto-Detected (Bạn KHÔNG tạo)

Metadata là thông tin Dynatrace tự động phát hiện khi OneAgent startup hoặc discover một entity:

  • Host name, IP address, OS type
  • Cloud provider (AWS, Azure), instance type, region
  • Container name, K8s namespace, pod name
  • Process technology (Java version, .NET version)

2.2 Tags = Bạn Tạo (Manually, Rules, hoặc Import)

Loại tagAi tạoFormatVí dụ
Manual tagsAdmin gắn tay trong UIkey hoặc key:valueteam:platform, priority:high
Auto-tagsRules tự động applykey:value (auto)Tag theo technology: tech:java
Host tags (current)CLI / installerkey:valueoneagentctl --set-host-tag
Legacy host tagsFile-based config cũ—hostautotag.conf
Imported tagsTừ cloud metadataProvider formatAWS tags, Azure tags auto-import

2.3 Tag Use Cases

flowchart TB
    TAG["Tags<br/>key:value pairs"] --> MZ["Management Zone rules<br/>Entities with tag env:prod"]
    TAG --> ALERT["Alerting profiles<br/>Alert only tag tier:1"]
    TAG --> DASH["Dashboard filtering<br/>Show hosts with team:devops"]
    TAG --> DQL["DQL queries<br/>filter matchesValue(tags, 'env:prod')"]
    TAG --> COST["Cost allocation<br/>Group by team tag"]

📝 Câu thi: “Tags vs metadata nguồn gốc?” → Metadata = auto-detected startup/discovery. Tags = manual, rules, import.

📝 Câu thi: “Cách set host tags hiện tại?” → Ưu tiên nhớ oneagentctl --set-host-tag / installer --set-host-tag

💡 DT_TAGS thường hữu ích khi nói về resource/process-level enrichment; đừng lẫn nó với cách đặt host tag kiểu câu hỏi exam classic.

⚠️ Legacy trap: trong dump cũ bạn vẫn có thể gặp câu hỏi file-based tagging. Nếu đề hỏi theo kiểu legacy, đáp án thường là hostautotag.conf, không phải hostcustomtags.conf.

📖 Ref: Tags & Metadata

3. Request Attributes vs Key Requests ⭐

Request AttributesKey Requests
Mục đíchCapture thêm data từ requestsĐánh dấu requests quan trọng
WhatExtract custom values (user ID, order ID)Mark specific endpoints
ResultData attach vào PurePath → query/filterRequest riêng metrics/SLA
Ví dụExtract X-User-Id header → gắn vào traceMark /api/checkout → riêng dashboard

3.1 Request Attributes — Config Flow

flowchart LR
    DEF["Define Attribute<br/>Name: OrderID<br/>Source: HTTP header<br/>Pattern: X-Order-Id"] --> CAPTURE["Capture<br/>OneAgent extract value<br/>từ mỗi request"]
    CAPTURE --> PUREPATH["Attach to PurePath<br/>OrderID = 12345<br/>Visible in trace"]
    PUREPATH --> QUERY["Query/Filter<br/>DQL, Dashboards<br/>Filter by OrderID"]

Request Attribute Sources (nơi extract):

SourceVí dụ
HTTP headerX-User-Id, X-Correlation-Id
HTTP parameterURL query params, form data
Method argumentJava method parameter values
Return valueMethod return values
SDKCustom OpenTelemetry attributes

3.2 Request Attributes — Confidential Data

Khi request attribute chứa sensitive data (VD: credit card number):

📝 Câu thi: “‘Contains confidential data’ checkbox → làm gì?”
→ Values masked (ẩn đi) — hidden from unauthorized access

  • ❌ KHÔNG remove (xóa) data
  • ❌ KHÔNG hide toàn bộ attribute
  • ❌ KHÔNG flag with password

3.3 Key Requests

Key Requests = đánh dấu endpoints quan trọng để:

  • Separate metrics — key request có riêng response time, error rate
  • Separate thresholds — custom Apdex T cho key request
  • Dedicated dashboarding — dễ track SLA

📝 Câu thi (scenario): “Checkout API cần riêng SLA + alert?” → Mark as Key Request

📖 Ref: Request Attributes

4. Alerting Profiles ⭐

4.1 Alerting Profile = “Gửi Alert Nào, Cho Ai?”

Alerting Profile là filter giữa Davis Problems và Notification Channels:

flowchart LR
    DAVIS["Davis AI<br/>Problems detected"] --> AP{"Alerting Profile<br/>Filter by:<br/>- Severity<br/>- MZ<br/>- Event type<br/>- Tags"}
    AP -->|"Match"| NOTIFY["📧 Notification<br/>Email, Slack, PagerDuty"]
    AP -->|"No match"| SILENT["🔇 Silent<br/>Problem exists but no alert"]

4.2 Alerting Profile Filters

FilterMô tảVí dụ
SeverityProblem severity levelOnly AVAILABILITY + ERROR
Management ZoneScope to specific MZOnly “Production” MZ
Event typeSpecific event categoriesCustom alerts, Custom deployment
DelayWait before alertingAlert after 5 min (avoid flaps)

📝 Câu thi (scenario): “Only notify Production team about Availability problems in Prod MZ?”
→ Alerting Profile filtering by: severity = AVAILABILITY + MZ = Production

🔗 Đã cover chi tiết ở 02 - Davis AI và Problem Detection > 7. Maintenance Windows. Recap nhanh:

OptionProblem DetectionNotifications

Detect, Don’t Alert✅ ON❌ Tắt

📝 Câu thi: “Cần ghi nhận problems nhưng không gửi notifications?” → Detect, Don’t Alert

6. Hosts Page

📝 Câu thi: “Hosts page hiển thị?”

  • ✅ Hosts with problems (có icon severity)
  • ✅ Physical machines with OneAgent
  • ✅ Virtual machines with OneAgent
  • ✅ Monitoring candidates (OneAgent chưa cài, nhưng Dynatrace detect)

7. Network Metrics

📝 Câu thi: “Key network metrics dashboard?”
→ Traffic, Retransmission, Connectivity

MetricMô tả
TrafficData volume in/out (bytes/sec)
RetransmissionPacket retransmits (network quality indicator)
ConnectivityConnection status between entities (connected/disconnected)

TIP

Network monitoring chạy tự động khi OneAgent deployed — không cần config riêng. Data visible ở: Infrastructure > Network hoặc Host details > Network.

📖 Ref: Network Monitoring

8. Credential Vault ⭐

Nơi lưu trữ an toàn credentials cho các tính năng cần authentication:

Tính năngCredential typeVí dụ
Synthetic browser monitorsUsername/passwordLogin flow testing
Synthetic HTTP monitorsAuth tokens, API keysAPI authentication
Extensions v2API keys, certificatesCloud/DB extensions
Dynatrace AppsApp credentialsApp authentication
Dynatrace API❌ KHÔNG—

8.1 Credential Vault Permissions

PermissionMô tả
PublicAnyone với access có thể sử dụng credential
Owner-onlyChỉ creator có thể view/edit credential

WARNING

Owner-only credential trong Synthetic:

  • Users khác có thể edit monitor name, frequency, locations, thresholds
  • Users khác KHÔNG thể edit URL, clickpath events, keystroke data
    → Credential value luôn encrypted, KHÔNG ai xem được plaintext value

🔗 Liên quan: 04 - Digital Experience - Synthetic > 5. Authentication & Credential Vault — synthetic monitors cần credentials cho login tests

📖 Ref: Credential Vault

8.5 Versioning Metadata ⭐

Dynatrace có thể hiển thị version information của các components đang monitor. Có 2 cách chính để configure versioning metadata:

Phương phápMô tảVí dụ
Environment variablesSet trên process/containerDT_RELEASE_VERSION=1.2.3, DT_RELEASE_STAGE=production, DT_RELEASE_PRODUCT=order-service
Kubernetes labelsGắn vào pod/deploymentapp.kubernetes.io/version: 1.2.3

📝 Câu thi (MC): “Configure versioning metadata?” → Environment variables và Kubernetes labels

  • ❌ Events ingestion → không phải cách configure version
  • ❌ Security vulnerability → không liên quan
  • ❌ Smartscape → topology map, không configure version

📖 Ref: Version detection

9. Settings Hierarchy ⭐

Dynatrace settings áp dụng theo hierarchy — cụ thể hơn override tổng quát hơn:

flowchart TB
    ENV["🌐 Environment-level<br/>Default settings<br/>Apply to ALL"] --> HG["🖥️ Host Group-level<br/>Override for specific HG<br/>e.g. web-servers"]
    HG --> HOST["💻 Host-level<br/>Override for specific host<br/>e.g. host-web-01"]
    HOST --> PG["⚙️ Process Group-level<br/>Override for specific PG<br/>e.g. order-service"]

📝 Câu thi (scenario): “Log collection ON ở environment level, OFF ở host group level cho db-servers?”
→ Host Group setting overrides environment → db-servers log collection = OFF

10. Tình Huống Giả Định (Exam Scenarios) ⭐

Scenario 1: Multi-team Access Control

📝 “3 teams (DevOps, Frontend, Backend). Mỗi team chỉ thấy entities liên quan.”
→ 3 Management Zones + RBAC policies mapped to MZs

Scenario 2: Different Config per Environment

📝 “Prod hosts: full-stack, deep code, log ON. Staging: infrastructure only.”
→ 2 Host Groups — prod-servers + staging-servers với different OneAgent configs

Scenario 3: Track Order IDs in Traces

📝 “Cần filter traces theo Order ID từ HTTP header X-Order-Id.”
→ Request Attribute — extract from HTTP header → attach to PurePath

Scenario 4: Planned Deployment Window

📝 “Deploy mới lúc 2AM. Không muốn false alerts nhưng muốn ghi nhận problems.”
→ Maintenance Window — Detect, Don’t Alert

Scenario 5: Alert Only Critical Prod Issues

📝 “Chỉ alert Slack khi Prod có Availability problems.”
→ Alerting Profile filtered by severity = AVAILABILITY + MZ = Production → Slack integration
