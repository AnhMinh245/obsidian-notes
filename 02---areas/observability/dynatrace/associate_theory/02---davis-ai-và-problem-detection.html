Chương 2: Davis AI và Problem Detection

NOTE

Ở 01 - Kiến trúc Dynatrace, bạn đã hiểu data đi từ OneAgent → OpenPipeline → Grail. Bây giờ câu hỏi tiếp theo: khi data đã nằm trong Grail, Dynatrace phân tích nó thế nào để phát hiện sự cố? Đó là công việc của Davis AI — “bộ não” phân tích, dùng Smartscape topology làm bản đồ.

📖 Ref: Davis AI | Problem Detection

1. Ba Loại AI Trong Davis ⭐

Davis không phải 1 AI duy nhất — nó kết hợp 3 loại AI, mỗi loại trả lời một câu hỏi khác:

Loại AICâu hỏi nó trả lờiPhương pháp
Causal AI”Tại sao xảy ra sự cố này?”Fault-tree analysis trên Smartscape
Predictive AI”Sự cố này sẽ xảy ra không?”Dynamic baselines + trend analysis
Generative AI”Giải thích và gợi ý giúp tôi?”Large Language Model + natural-language interface

1.1 Causal AI — Root Cause Analysis (TRỌNG TÂM) ⭐

Đặc điểm kỹ thuật cốt lõi:

  • Deterministic — cùng input → LUÔN cho cùng output (khác Machine Learning)
  • Không cần training data — hoạt động ngay từ ngày đầu
  • Không dùng ML/statistics — dùng graph traversal trên Smartscape
  • Input = Anomaly events + Smartscape topology
  • Output = 1 Problem card (root cause + impacted entities)

Quy trình xử lý 5 bước (⭐ cần thuộc):

Ví dụ thực tế — E-commerce app bị chậm:

Timeline thực tế:
  10:00 - host-db-01 CPU spike → 95% (disk I/O contention)
  10:01 - PostgreSQL queries chậm 5x (waiting for disk)
  10:01 - Order Service response time 200ms → 600ms (waiting for DB)
  10:02 - Frontend API error rate 0.1% → 20% (timeouts)
  10:02 - 500 users thấy lỗi "Unable to process order"

Davis Causal AI xử lý:

BƯỚC 1: DETECT (Phát hiện)
  │ Davis detect 5 anomalies — mỗi anomaly là 1 event riêng biệt:
  │ • Event #1: Resource contention (host-db-01 CPU)
  │ • Event #2: Slowdown (PostgreSQL service)
  │ • Event #3: Slowdown (Order Service)
  │ • Event #4: Error (Frontend API)
  │ • Event #5: Custom (user experience degraded)
  │
BƯỚC 2: TRAVERSE (Duyệt Smartscape)
  │ Davis lấy Smartscape graph (🔗 từ [[01 - Kiến trúc Dynatrace#6. Smartscape]]):
  │
  │   Frontend API ──calls──► Order Service ──calls──► PostgreSQL
  │                                                        │ runs on
  │                                                    host-db-01
  │
  │ → Tất cả 5 anomaly đều nằm trên CÙNG dependency tree
  │
BƯỚC 3: CORRELATE (Tương quan)
  │ Davis kiểm tra:
  │ • Cùng time window? ✅ (10:00 — 10:02)
  │ • Cùng dependency tree? ✅ (Frontend → Order → PostgreSQL → host-db-01)
  │ • Hướng ảnh hưởng? ✅ (bottom-up: host → DB → service → API → users)
  │
BƯỚC 4: IDENTIFY (Xác định)
  │ ROOT CAUSE: host-db-01 CPU saturation (nơi bắt đầu)
  │ IMPACT:
  │   ├── PostgreSQL service: slowdown (direct)
  │   ├── Order Service: slowdown (indirect)
  │   ├── Frontend API: errors (cascade)
  │   └── ~500 users affected (end impact)
  │
BƯỚC 5: CONSOLIDATE (Gộp)
  │ 5 anomaly events → 1 PROBLEM duy nhất
  │ → Chỉ 1 notification được gửi (không phải 5 alerts riêng!)
  └

💡 Tại sao Consolidation quan trọng?
Không có consolidation → DevOps team nhận 5 alerts cùng lúc → confusion, alert fatigue, mất thời gian tìm root cause. Với Davis: 1 Problem card → rõ ràng root cause, impacts, affected users.

💡 So sánh:

  • Prometheus/Alertmanager: bạn tự define alert rules → 5 rules fire → 5 alerts → phải tự correlate
  • Davis Causal AI: tự động correlate → 1 Problem → root cause identified → bạn bắt đầu fix ngay

📝 Câu thi: “Davis AI dùng gì để deterministic root cause?” → Causal AI
📝 Câu thi: “Khi nhiều anomaly liên quan?” → Consolidate → 1 Problem, root cause vs impact
📝 Câu thi: “Cách Davis xác định root cause?” → Phân tích dependencies (Smartscape), xây dựng model → xác định component most likely causing problem. (❌ KHÔNG phải “alert đầu tiên”, ❌ KHÔNG phải “alert nhiều nhất”)

3. Events — Phân Loại Sự Kiện ⭐

Khi Davis hoặc custom rules phát hiện bất thường, chúng tạo events. Events có phân loại severity và category riêng.

3.1 Event Categories (Đầy Đủ)

Dynatrace có 7 event categories (⭐ cần nhớ):

Severity (cao → thấp):

  🔴 MONITORING UNAVAILABLE  ← Monitoring agent mất liên lạc
  🔴 AVAILABILITY            ← Host/service/process DOWN
  🟠 ERROR                   ← Error rate tăng đáng kể
  🟡 SLOWDOWN                ← Response time degradation
  🟡 RESOURCE                ← CPU/memory/disk saturation
  🔵 CUSTOM                  ← Custom metric thresholds
  ⚪ INFO                    ← Config changes, deployments

📝 Câu thi: “Event type severity thấp nhất?” → Info
📝 Câu thi: “Đâu KHÔNG phải problem severity?” → “Unexpected” — không tồn tại trong danh sách
📝 Câu thi: “Tất cả event categories?” → monitoring unavailable, availability, error, slowdown, resource, custom, info (7 loại)

⚠️ Bẫy dump: Đáp án đúng là d. monitoring unavailable, availability, error, slowdown, resource, custom, info

  • ❌ c. critical, availability, error, slowdown, resource, warning, custom, info → SAI (thừa “critical” và “warning”)
  • ❌ b. availability, error, slowdown, resource → thiếu nhiều

3.3 Slowdown Event — Root Cause Entity Types ⭐

📝 Câu thi (MC): “Problem with event category ‘Slowdown’ — what entity types can be root cause?”

  • ✅ Applications — slow load, high user action duration
  • ✅ Services — slow response time
  • ✅ Hosts — CPU/memory bottleneck gây slowdown
  • ✅ Processes — resource starvation gây slowdown
  • ❌ Cloud providers — không phải entity type gây root cause Slowdown

3.2 Problem Severity vs Event Category

Nhiều events cùng severity có thể được consolidate thành 1 Problem với severity tương ứng:

Events → Davis Consolidation → Problem

  Event: CPU 95% (RESOURCE)       ─┐
  Event: DB slow 5x (SLOWDOWN)    ├──► Problem "Performance degradation"
  Event: API errors 20% (ERROR)   ─┘   Severity: ERROR (highest of group)

7. Maintenance Windows

Khi bạn biết sẽ có planned downtime (upgrade, migration), bạn tạo maintenance window để Davis không tạo false alerts.

3 Options

OptionDavis behaviorNotificationsKhi nào dùng
Detect + AlertVẫn detect & alert bình thường✅ GửiTesting — muốn biết chuyện gì xảy ra
Detect, Don’t AlertVẫn detect, ghi nhận❌ Không gửiBiết sẽ có issues, không muốn noise
Disable DetectionTắt hoàn toàn detection❌ KhôngMajor migration — mọi thứ sẽ loạn

📝 Câu thi: “Hệ thống offline để upgrade, overlap synthetic tests?” → Tạo maintenance window

8. Traffic Anomaly Detection

Davis AI cũng detect bất thường về traffic patterns — không chỉ performance.

Unexpected Traffic Problems

📝 Câu thi: “Unexpected low/high traffic problem là gì?” → Deviation giữa actual traffic và predicted traffic (Davis predicted dựa trên learned baseline).

Ví dụ:
  Baseline học: Monday 10AM traffic = 1000 req/min
  Actual: Monday 10AM traffic = 200 req/min
  → "Unexpected low traffic" problem
  → Có thể cho biết: upstream service bị lỗi, DNS issue, deployment bug

Điều Kiện Kích Hoạt

📝 Câu thi: “App cần chạy bao lâu trước khi traffic alerts?” → Ít nhất 1 tuần đầy đủ — Davis cần đủ data cho weekly patterns.
