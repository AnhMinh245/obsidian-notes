Chương 3: Digital Experience — Real User Monitoring (RUM)

IMPORTANT

RUM + Synthetic chiếm ~24% đề thi — tỷ trọng CAO NHẤT. Chương này đặc biệt quan trọng. Có rất nhiều chi tiết nhỏ (session timeout, Apdex thresholds, action types) mà đề thi hay hỏi — cần nắm chính xác, không đoán được.

📖 Ref: Real User Monitoring | User Sessions

NOTE

Với sản phẩm hiện tại, RUM có cả classic views lẫn new RUM experience. Khi ôn thi:

  • Các khái niệm nền tảng như session, action, Apdex, user tagging, session replay vẫn giữ giá trị
  • Một số hành vi rất chi tiết trong dump cũ cần đọc kèm bối cảnh legacy/classic

1. RUM Trong Bức Tranh Tổng Thể

Trước khi đi vào chi tiết, hiểu RUM nằm ở đâu trong data flow (🔗 01 - Kiến trúc Dynatrace > 1. Data Flow):

USER BROWSER ←→ WEB SERVER (OneAgent installed)
     │                    │
     │  1. Request page   │
     │ ──────────────────►│
     │                    │ 2. OneAgent inject JavaScript
     │  3. Response HTML  │    snippet vào <head>
     │ ◄──────────────────│
     │                    │
     │  4. Browser executes JS snippet:
     │     ├── Capture page load timing
     │     ├── Capture XHR/Fetch requests
     │     ├── Capture user clicks, forms
     │     ├── Capture JS errors
     │     ├── Inject x-dynatrace header
     │     │   → kết nối RUM data với PurePath backend
     │     │   → 🔗 [[05 - Services và Database Monitoring#5. PurePath]]
     │     └── Send beacon → Dynatrace cluster
     │
     │  5. Data → OpenPipeline → Grail → Davis AI
     │     → 🔗 [[02 - Davis AI và Problem Detection]]

💡 Điểm cốt lõi: RUM cho bạn biết user THẬT đang trải nghiệm gì — không phải server nghĩ performance thế nào, mà user THỰC SỰ thấy gì trên browser.

📝 Câu thi: “OneAgent cung cấp RUM bằng cách nào?” → Inject JavaScript tag vào HTML của mỗi trang.

2. Các Phương Pháp Thu Thập RUM ⭐

Không phải lúc nào cũng có OneAgent trên web server. Có 3 cách tiếp cận thường gặp để đưa RUM vào web app:

Phương phápCách hoạt độngĐiều kiệnUse case
Auto-injectionOneAgent trên web server tự inject JS vào HTML response✅ OneAgent trên serverStandard deployment
Manual injection (outbound)Dev copy-paste JS snippet vào <head>❌ Không cần OneAgentCDN, static hosting, 3rd party
Browser-side injection / agentlessInject từ phía browser hoặc không kiểm soát server-side❌ Không cần OneAgentKhi không chạm được host hoặc HTML gốc

📝 Câu thi: “Outbound deployment → inject RUM JS tag thế nào?” → Manually insert JavaScript tag vào mỗi HTML page
📝 Câu thi: “Agentless deployment → inject RUM JS tag thế nào?” → Manually insert JavaScript tag vào mỗi HTML page

NOTE

Hai câu “outbound” và “agentless” cùng đáp án. Trong dump xuất hiện cả 2 wording.

📝 Câu thi: “RUM khi không access host?”

  • ✅ Agentless monitoring + ✅ Browser Extension
  • ❌ OneAgent plugin, ActiveGate extension → SAI

RUM Browser Extension — khi nào dùng?

📝 Câu thi: “Khi nào dùng Browser Extension?” → Khi muốn RUM nhưng:

  • KHÔNG access đến application servers, VÀ
  • KHÔNG access đến HTML source
  • → Extension inject JS từ phía browser (browser-side injection)

IoT / Custom Devices:

📝 Câu thi: “IoT device không support OneAgent hay agentless RUM?” → Dynatrace OpenKit — lightweight SDK (🔗 09 - Security và Automation > 4. IoT)

📖 Ref: RUM Setup

3. Cấu Trúc RUM: Application → Session → Action ⭐

Về mặt ôn thi, RUM thường được suy nghĩ theo 3 lớp Application → Session → Action. Đây là mô hình đủ tốt để trả lời phần lớn câu hỏi Associate, dù ở mức implementation hiện đại một web session có thể được correlate qua nhiều applications/views.

APPLICATION "MyWebApp"  ←── được nhóm/nhận diện bởi Application Detection Rules
  │
  ├── USER SESSION #1  ←── bắt đầu khi user truy cập lần đầu
  │   │                    kết thúc khi idle 30 phút / close browser
  │   │
  │   ├── LOAD ACTION: "Loading Homepage"  ←── page load (full navigation)
  │   │   Duration: 1200ms
  │   │   Apdex: Satisfied (T=2000ms, 1200<2000)
  │   │   Resources: 45 (images, CSS, JS files)
  │   │
  │   ├── XHR ACTION: "Search products"  ←── AJAX/Fetch request
  │   │   Duration: 350ms
  │   │   Trigger: user typed in search box
  │   │   Response: JSON with 20 products
  │   │
  │   ├── LOAD ACTION: "Loading Product Detail"  ←── navigation to new page
  │   │   Duration: 800ms
  │   │
  │   └── XHR ACTION: "Add to cart"  ←── AJAX request
  │       Duration: 200ms
  │       → Conversion Goal: "Cart Addition" ✅
  │
  ├── USER SESSION #2  ←── different user
  │   └── ...
  │
  └── USER SESSION #N

📝 Câu thi: “Cấu trúc đúng của RUM?” → Application → User Sessions → User Actions

Default Application

Khi Dynatrace lần đầu detect web traffic trên host, nó tạo “My web application” (default application) làm catch-all:

Web traffic detected → "My web application" (default, catch-all)
                          │
                     Sau đó, admin tạo Application Detection Rules:
                          │
                     ┌────▼────────────────────────────────┐
                     │ Rule 1: domain "shop.example.com"   │──► "E-Commerce App"
                     │ Rule 2: domain "admin.example.com"  │──► "Admin Portal"
                     │ Rule 3: domain "api.example.com"    │──► "API Gateway"
                     │ Else: default application           │──► "My web application"
                     └─────────────────────────────────────┘

📝 Câu thi: “Khi Dynatrace detect app, dùng gì để capture data?” → Default application (catch-all). Customize bằng Application Detection Rules.

4. User Sessions — Mọi Chi Tiết Cần Biết ⭐

4.1 Session Lifecycle

SESSION START                                       SESSION SPLIT / END
     │                                                    │
     │  User truy cập app ────────────────────────────►  │
     │                                                    │
     │  Các mốc quan trọng cần nhớ:                      │
     │  ✅ 30 phút không hoạt động (inactive)             │
     │  ✅ 6 giờ thời lượng tối đa của session            │
     │  ✅ Khoảng 200 user actions thì session bị tách    │
     │                                                    │
     │  ⚠️ "Closing the application" ≠ khái niệm chính    │
     │     trong docs hiện tại. Khi làm bài, ưu tiên      │
     │     các mốc inactivity / duration / action count.  │
     └────────────────────────────────────────────────────┘

⚠️ Câu bẫy thi cực kỳ quan trọng: session web thường được hỏi theo các mốc 30 phút inactive, 6 giờ, và ~200 actions. Đừng trả lời theo cảm tính kiểu “đóng app là xong session”.

4.2 Xóa Cookies

📝 Câu thi: “User xóa cookies giữa session?” → Thực tế theo triển khai hiện tại, Dynatrace còn cơ chế backup cookie trong browser storage. Cách an toàn để nhớ khi ôn thi: xóa định danh session/cookie có thể làm Dynatrace bắt đầu session mới ở lượt tương tác kế tiếp.

4.3 Live vs Completed Sessions

📝 Câu thi: “Phân biệt live vs completed trên UI?” → Màu sắc khác nhau trên chart.

4.4 USQL — Khi Nào Query Được?

📝 Câu thi: “Session khả dụng cho USQL khi nào?” → Sau khi completed. Live sessions chưa query được bằng USQL (🔗 chi tiết USQL tại 07 - Data Analysis và Tools > 2. USQL).

4.5 User Session Properties

📝 Câu thi: Session properties:

  • ❌ Dùng 1 property across multiple applications → SAI
  • ❌ Retrospective (hồi tố) → SAI
  • ❌ Dùng trong “Service response time” metric → SAI

📖 Ref: User Sessions

5. User Actions — Ba Loại ⭐

LoạiTriggerVí dụKhi nào tạo
Load actionFull page load/navigationMở”Homepage”, click link sang page mớiBrowser navigates to new URL
XHR/Fetch actionAJAX/Fetch request nềnSearch, add to cart, submit formJavaScript gửi HTTP request
Custom actionJavaScript API (manual)Business-specific eventsDev gọi RUM JS API

📝 Câu thi: “Enable JavaScript frameworks support → giúp loại action nào?” → XHR actions — vì frameworks (Angular, React, Vue) dùng XHR/Fetch heavily.

User Action Classifications — Behavior Analysis ⭐

Trong Behavior Analysis (User Action Analysis), user actions được phân loại theo vị trí trong session:

ClassificationMô tả
Entry ActionsAction đầu tiên trong session (user đến từ đâu?)
Other ActionsCác actions giữa session (user làm gì?)
Exit ActionsAction cuối cùng trước khi user rời (user rời ở đâu?)

📝 Câu thi: “3 classifications of User Actions for Behavior Analysis?” → Entry Actions, Other Actions, Exit Actions

  • ❌ Start/Other/Final → sai tên
  • ❌ Entry/Middle/Exit → sai (Middle thay vì Other)
  • ❌ Initiation/Other/Bounce → sai

Waterfall Analysis

User action waterfall (based on W3C timings) group theo 3 loại resources:

  • ✅ Resource requests (images, CSS, JS files)
  • ✅ XHR requests (AJAX calls)
  • ✅ Document requests (HTML documents)

📝 Câu thi: “Which view provides detailed W3C timings of pages and resources?” → Waterfall analysis

  • ❌ Dynatrace Extension V2 → SAI
  • ❌ Distributed Trace → SAI (trace là backend, không phải W3C page timings)
  • ❌ Session Replay → SAI (replay là visual, không phải timing detail)

6. Apdex Score ⭐⭐ (CỰC KỲ QUAN TRỌNG — LUÔN RA THI)

6.1 Công Thức và Thang Đánh Giá

Apdex (Application Performance Index) đo mức độ hài lòng của user dựa trên response time:

Với ngưỡng T (threshold — admin cấu hình):

  ┌─────────────────────────────────────────────────────┐
  │                                                     │
  │  Response < T        → 😊 SATISFIED     (nhanh)    │
  │  T ≤ Response < 4T   → 😐 TOLERATING   (chấp nhận)│
  │  Response ≥ 4T       → 😡 FRUSTRATED   (quá chậm) │
  │                                                     │
  └─────────────────────────────────────────────────────┘

  Apdex Score = (Satisfied + 0.5 × Tolerating) / Total

  Ví dụ với T = 2s:
  ┌────────────────────────────────────┐
  │ 100 user actions:                  │
  │   70 Satisfied (< 2s)              │
  │   20 Tolerating (2s - 7.99s)       │
  │   10 Frustrated (≥ 8s)            │
  │                                    │
  │ Apdex = (70 + 0.5×20) / 100       │
  │       = 80 / 100                   │
  │       = 0.80 (Fair)                │
  └────────────────────────────────────┘
ScoreRatingÝ nghĩa
0.94 – 1.00ExcellentGần như tất cả users hài lòng
0.85 – 0.93GoodĐa số users hài lòng
0.70 – 0.84FairPerformance cần cải thiện
0.50 – 0.69PoorNhiều users bực bội
0.00 – 0.49UnacceptableCần fix ngay

📝 Câu thi: “Response time = 3T → phân loại?” → Tolerating (vì T ≤ 3T < 4T)

6.2 Apdex Tính Cho Cái Gì?

  • ✅ User actions — mỗi action có Apdex riêng
  • ✅ Application — Apdex tổng thể cho toàn app
  • ❌ Conversion goals, User tags, Errors → KHÔNG tính Apdex

6.3 Custom Apdex — Key User Actions

Mặc định, tất cả actions dùng chung T value của application. Muốn set T riêng cho action quan trọng:

1. Vào Application → User Actions
2. Tìm action quan trọng (VD: "Checkout")
3. Mark as "Key User Action" ← ĐÂY LÀ BƯỚC QUAN TRỌNG
4. Trong Key User Action settings → set custom Apdex T value

📝 Câu thi: “Set Apdex riêng cho 1 action?” → Mark as Key User Action → edit settings

  • ❌ KHÔNG phải “edit application settings, select actions”
  • ❌ KHÔNG phải “chỉ set cho Application level”

📖 Ref: Apdex Rating

7. Key User Actions & Conversion Goals ⭐

Hai khái niệm thường bị nhầm lẫn — mục đích khác nhau:

Key User ActionsConversion Goals
Mục đíchMonitor performance của action quan trọngTrack business outcome (mua hàng, đăng ký)
FocusResponse time, error rate, ApdexConversion rate (% users hoàn thành)
ConfigMark action → riêng metrics/thresholdsDefine goal → track completion
AlertAlert khi performance degradeTrack business KPI

Conversion Goals dựa trên:

  • ✅ Specific user action (“Click Buy”)
  • ✅ Number of actions per session (≥ 5 actions)
  • ✅ Session duration (session > 3 phút)
  • ✅ Destination URL (“/thank-you”)
  • ❌ Number of errors on session end

📝 Câu thi: “Track checkout completion?” → Conversion Goal
📝 Câu thi: “Action vừa key vừa conversion?” → CÓ (Yes)

  • Page metadata (meta tags)
  • JavaScript variables (window.userId)
  • Cookies
  • Server-side request attributes

Private IP Geolocation

10. Session Replay

📝 Câu thi: “Session Replay là gì?” → Capture và visually replay trải nghiệm user, trông giống video recording nhưng thực tế dựa trên DOM snapshots.

Kỹ thuật: DOM snapshots (không phải pixel-level video):

  • Record DOM changes, mouse movements, clicks, scrolls
  • Data masking tự động: passwords, credit cards
  • Configurable sampling rate → cost control
  • Custom masking rules cho specific elements

11. Mobile Application Monitoring

📝 Câu thi: “Default metrics cho mobile app?”
→ App usage: user experience, network performance, crashes, called services

IMPORTANT

Mobile app monitoring hiện tại tập trung vào iOS và Android.
Nếu bạn gặp dump cũ hỏi “OS mobile nào không support?”, đáp án Windows Phone là legacy trivia, không phải cách mô tả nên dùng cho sản phẩm hiện tại.

TIP

Mẹo phân biệt RUM vs Synthetic:

  • RUM = “Bác sĩ khám bệnh nhân thật” — data thật, nhưng phải chờ bệnh nhân đến
