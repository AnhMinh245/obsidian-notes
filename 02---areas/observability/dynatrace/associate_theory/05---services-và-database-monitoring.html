NOTE

Ở chương 3-4, bạn đã học cách monitor phía client (RUM + Synthetic). Bây giờ chuyển sang phía server — cách Dynatrace phát hiện, đặt tên, và monitor backend services. Services nằm ở tầng 4 trong Smartscape (🔗 01 - Kiến trúc Dynatrace > 6. Smartscape) — kết nối Application (tầng 5) với Process (tầng 3).

📖 Ref: Services | Distributed Traces

1. Service Detection — Cách Dynatrace Tìm Ra Services

1.1 Service Tự Động Được Tạo Từ Đâu?

OneAgent detect incoming requests đến một process → tạo Service:

Incoming HTTP request → port 8080 → Java process
  → OneAgent detect: "Có request đến Java process"
  → Tạo Service: "OrderService" (tên = context root + web server name)

Incoming SQL query → port 5432 → PostgreSQL
  → OneAgent detect: "Có query đến PostgreSQL"
  → Tạo Service: "PostgreSQL" (external service)

1.2 Service Identification & Naming ⭐

Dynatrace dùng 3 yếu tố để identify/name web request services:

Yếu tốVí dụDùng để identify?
Context root/api/orders, /api/users✅
Web server namenginx-frontend, tomcat-01✅
Web application IDApplication identifier trong request✅
Database requestsSQL queries❌
IP address10.0.1.50❌

📝 Câu thi: “Yếu tố nào?” → Context root + Web server name + Web application ID

1.3 Service Naming Rules

Khi tên service tự động không đẹp hoặc không chuẩn, bạn có thể tạo Service Naming Rules để tự động đặt tên lại:

Ví dụ:
  Auto-detected name: "Tomcat_8080_/api/v2/orders_host-web-01"
  
  Service Naming Rule:
    Condition: Web server name contains "Tomcat"
    Name format: "{ProcessGroup:Name} ({Host:Name})"
  
  Result: "order-service (host-web-01)"

📝 Câu thi: “Tự động name services?” → Service Naming Rules

  • ❌ Process Group Naming Rules → process groups, không services
  • ❌ Service Merging Rules → merge services, không naming
  • ❌ Service Detection Rules → detection logic, không naming

📖 Ref: Service Naming

2. Service Performance Analysis

2.1 Response Time Hotspots

Hotspots giúp identify đâu tốn thời gian nhất trong service:

Service: "Order Service"
Total response time: 500ms

Response Time Hotspots:
  ┌──────────────────────────────────────────────┐
  │ Database calls (PostgreSQL)    ████████ 300ms │ ← BOTTLENECK
  │ External service (Payment API) ███     120ms  │
  │ Code execution (Java)         ██       60ms   │
  │ Lock/wait time                █        20ms   │
  └──────────────────────────────────────────────┘
  → Database calls chiếm 60% thời gian → cần optimize SQL queries

📝 Câu thi: “Hotspots cho biết gì?” → Activities consuming most TIME (bottleneck)

  • ❌ KHÔNG phải “most resources” (CPU/memory)
  • ❌ KHÔNG phải “most database requests” (count)

2.2 Service Quality Report Score

📝 Câu thi: “Score tính bằng gì?” → % service calls affected by problems AND failed

2.3 Service Attributes

📝 Câu thi: “Xem attributes ở đâu?” → Properties and Tags section của Service overview page

3. Opaque Services ⚠️

Opaque Service = “Service Đục”

Dynatrace detect được request đến service, nhưng KHÔNG thể nhìn vào code — nó “thấy” service nhưng không có code-level visibility.

Normal Service (Full Visibility):
  ┌────────────────────────────────────┐
  │ OrderService (Java)                │
  │ ┌──────────────────────────────┐   │
  │ │ Method: processOrder()       │   │ ← Code-level detail
  │ │ Duration: 350ms              │   │
  │ │ SQL: SELECT * FROM orders    │   │
  │ │ Exception: NullPointerExc... │   │
  │ └──────────────────────────────┘   │
  └────────────────────────────────────┘

Opaque Service (Limited Visibility):
  ┌────────────────────────────────────┐
  │ ExternalPaymentGateway             │
  │ ┌──────────────────────────────┐   │
  │ │ ██████████████████████████   │   │ ← "Đục" — không thấy gì bên trong
  │ │ Chỉ biết: request sent,     │   │
  │ │ response received, duration  │   │
  │ └──────────────────────────────┘   │
  └────────────────────────────────────┘

Nguyên nhân:

  • ✅ Technology support nhưng code-level visibility không available (VD: agent chưa inject)
  • ✅ Technology không nhận diện/support (exotic language)
  • ❌ External dependencies → SAI
  • ❌ Aggregated services → SAI

4. Database Monitoring ⭐

4.1 Database = External Service — Nguyên Lý Cốt Lõi

Đây là concept rất quan trọng và hay ra thi. Dynatrace monitor database khác với monitor application:

Cách Dynatrace monitor APPLICATION:
  OneAgent install trên host → inject code → code-level visibility
  → Thấy: methods, SQL statements, exceptions, response time

Cách Dynatrace monitor DATABASE:
  OneAgent install trên APP SERVER (không nhất thiết trên DB server)
  → OneAgent capture SQL queries TỪ PHÍA CALLER (ứng dụng gọi DB)
  → Thấy: SQL statement, execution time, error nếu có
  → KHÔNG instrument database code trực tiếp
  → Database = "external service"

  ┌──────────────────┐          ┌──────────────────┐
  │ Java App Server  │          │ PostgreSQL       │
  │ (OneAgent ✅)     │          │ (OneAgent ❌ opt) │
  │                  │  SQL     │                  │
  │  orderDao.find() ├─────────►│ SELECT * FROM    │
  │    ↓             │          │ orders WHERE     │
  │  OneAgent capture│          │ id = 42          │
  │  SQL + duration  │          │                  │
  └──────────────────┘          └──────────────────┘
        ↓
  Service: "PostgreSQL" (external service type)
  Data: SQL statement, execution time, caller service

📝 Câu thi: “Database monitoring nghĩa là gì?” → Monitor calls đến database, không monitor DB processes

  • ❌ “Response time cannot be tracked” → SAI (track qua calls)
  • ❌ “OneAgent required on database host” → KHÔNG bắt buộc

4.2 Top Database Statements

📝 Câu thi: “Top DB statements = gì?” → Most frequent + most expensive

  • ❌ “Slowest” → SAI (slowest ≠ most expensive — có thể slow nhưng chạy 1 lần)
  • ❌ “Most optimized” → ngược lại
  • ❌ “Lowest error rates” → không liên quan

4.3 Full Database Visibility — Cần Gì?

Để có đầy đủ visibility vào database (code-level analysis + metric data), kết hợp:

                              Full DB Visibility
           ┌──────────────────────────────────────────┐
           │                                          │
           │  ┌── Source 1: OneAgent on App Servers ──┐│
           │  │ → Capture SQL queries, durations      ││
           │  │ → Code-level analysis (các method gọi DB)││
           │  │ → Caller-side view                    ││
           │  └───────────────────────────────────────┘│
           │                                          │
           │  ┌── Source 2: DB Extension ─────────────┐│
           │  │ → Technology-specific metrics         ││
           │  │ → VD: PostgreSQL extension → buffer   ││
           │  │   cache hit ratio, lock waits etc.    ││
           │  │ → Tìm trên Dynatrace Hub             ││
           │  │   🔗 [[09 - Security và Automation#3. Extensions]] │
           │  └───────────────────────────────────────┘│
           └──────────────────────────────────────────┘

📝 Câu thi (MC): “Features cho full DB visibility including code-level analysis + metric data?”

  • ✅ OneAgent on application servers making call to the database → caller-side, code-level
  • ✅ Extensions for the specific database technology → DB-specific metrics
  • ❌ OneAgent on DB host in full-stack mode → không cần full-stack trên DB host
  • ❌ RUM on the application → RUM là frontend, không liên quan DB visibility
  • ❌ OneAgent on DB host in infrastructure only mode → chỉ host metrics, không code-level

4.4 Database Performance Tools

📝 Câu thi: “Tìm DB performance info ở đâu?”

  • ✅ Service data for specific database
  • ✅ Databases app
  • ✅ Extension dashboards
  • ❌ Running synthetic tests against database → SAI

Database app metrics (hiển thị trong Databases app):

  • ✅ Memory Consumption — DB memory usage
  • ✅ User Calls — số lượng calls tới DB
  • ✅ Active Sessions — concurrent sessions
  • ❌ Code-level insights → cần OneAgent trên app server, không có trong Databases app
  • ❌ Database vulnerabilities → Security module riêng

5. PurePath — Distributed Tracing ⭐

5.1 PurePath = End-to-End Distributed Trace

PurePath kết nối RUM data (🔗 03 - Digital Experience - RUM) với backend services:

User clicks "Buy" on web page
     │
     │  RUM: User Action "Click Buy" (3200ms total)
     │  → x-dynatrace header injected vào XHR request
     │
     ▼
┌─────────────────────────────── PurePath ───────────────────────────┐
│                                                                     │
│  [nginx - Frontend API]                                             │
│    └─ POST /api/orders (3100ms)                                    │
│         │                                                           │
│  [Java - Order Service]                                             │
│    ├─ validateOrder() (50ms)                                       │
│    ├─ call Payment Service (2800ms)  ← BOTTLENECK                  │
│    │       │                                                        │
│    │  [Node.js - Payment Service]                                   │
│    │    ├─ processPayment() (2500ms)                               │
│    │    └─ DB: INSERT INTO payments (300ms)                        │
│    │         │                                                      │
│    │    [PostgreSQL] INSERT INTO payments... (280ms)                │
│    │                                                                │
│    └─ updateInventory() (200ms)                                    │
│                                                                     │
│  → Có thể thấy: Payment Service chiếm 2800ms trên tổng 3200ms     │
│  → Root cause: Payment Service processing (2500ms internal)         │
└─────────────────────────────────────────────────────────────────────┘

5.1b Benefits of Distributed Tracing ⭐

📝 Câu thi (MC): “Name the benefits of employing distributed tracing”

  • ✅ Faster time to market — debug hiệu quả → deploy nhanh hơn
  • ✅ Improved internal collaboration — các team nhìn cùng trace → phối hợp tốt
  • ✅ Reduced mean time to detect (MTTD) and mean time to repair (MTTR) — phát hiện + sửa lỗi nhanh hơn
  • ❌ Improved compliance with SLAs → không phải benefit trực tiếp
  • ❌ Protected bottom-line growth → không phải benefit trực tiếp
  • ❌ Session replay → RUM feature, không liên quan tracing

5.2 Span = Single Operation

Mỗi “node” trong PurePath = 1 Span:

📝 Câu thi: “Single operation within a trace?” → Span

  • ❌ Trace → tổng thể cả chuỗi
  • ❌ Context → metadata (trace ID, span ID)
  • ❌ Exporter → công cụ xuất data

5.3 PurePath Correlation — Trace-ID Propagation ⭐

OneAgent tự inject correlation headers:

  • HTTP: x-dynatrace header + W3C traceparent/tracestate headers (auto-inject vào outgoing requests)
  • Messaging: inject vào message properties (Kafka, RabbitMQ)
  • → Cho phép trace cross-service, cross-process, cross-host

📝 Câu thi: “How is trace-id propagated in distributed traces?” → HTTP header

  • ❌ JSON payload → body, không phải propagation mechanism
  • ❌ XML payload → body
  • ❌ TLS handshake → encryption layer

6. Tracing Options ⭐

OptionMô tảStatus
Dynatrace OneAgentAuto-instrumentation, zero config✅ Primary
Dynatrace OneAgent SDKExtend tracing cho custom code✅ Supplement
OpenTelemetryModern open standard (OTLP)✅ Supported
OpenTracingOlder standard✅ Supported (deprecated)
Dynatrace OperatorK8s deployment tool❌ KHÔNG phải tracing
Dynatrace RUMUser monitoring❌ KHÔNG phải distributed tracing

📝 Câu thi: “Tracing options?” → OneAgent SDK, OpenTracing, OpenTelemetry

6.1 OpenTelemetry — Cách Gửi Data Tới Dynatrace ⭐

📝 Câu thi (MC): “Which options exist to send OpenTelemetry data to Dynatrace?”

  • ✅ Dynatrace Operator — auto-inject OTel collector trong K8s
  • ✅ Dynatrace SaaS API — OTLP endpoint trực tiếp ({env-id}.live.dynatrace.com/api/v2/otlp/...)
  • ✅ Dynatrace ActiveGate API — proxy qua ActiveGate (dùng khi không direct access tới SaaS)
  • ❌ Dynatrace RUM → user monitoring, không phải OTel ingestion
  • ❌ Dynatrace OneAgent → Dynatrace native agent, không phải OTel receiver

📖 Ref: OpenTelemetry
