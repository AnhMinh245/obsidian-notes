Chương 1: Kiến Trúc Dynatrace

NOTE

Đây là chương nền tảng. Mọi chương sau đều dựa trên kiến trúc này. Nếu bạn hiểu data đi từ đâu, qua đâu, và lưu ở đâu, bạn có thể suy luận đáp án cho ~40% câu hỏi thi mà không cần thuộc lòng.

📖 Tham chiếu: Dynatrace Architecture | OneAgent | ActiveGate

IMPORTANT

Chương này cố tình tách rõ:

  • Host monitoring modes hiện hành: Full-stack, Infrastructure, Discovery hoặc Foundation & Discovery tùy licensing/UI
  • Cloud-native full-stack: mô hình triển khai trên Kubernetes, không phải “host mode thứ 4”

Ngoài ra, data flow bên dưới là mô hình khái quát để ôn thi. Một số signal/classic features có thể có pipeline và retention riêng.

  • ActiveGate = trạm bơm trung gian (compress, bundle trước khi đưa vào nhà máy)
  • OpenPipeline = hệ thống lọc và xử lý (loại tạp chất, thêm khoáng chất, phân loại)

  • DQL/Dashboards = vòi nước (người dùng cuối lấy kết quả)

2. OneAgent — Bộ Thu Thập Dữ Liệu ⭐

2.1 OneAgent Là Gì — Và Tại Sao Nó Đặc Biệt?

OneAgent là phần mềm cài trên mỗi host. Điểm khác biệt cốt lõi so với Datadog Agent, Prometheus Node Exporter, hay OpenTelemetry Collector:

Khả năngDynatrace OneAgentDatadog AgentPrometheus
Auto-discover processes✅ Tự động⚠️ Cần config❌ Cần scrape config
Auto-instrument code✅ Inject runtime⚠️ Cần library❌ Manual SDK
Distributed tracing✅ Tự động (PurePath)⚠️ Cần APM lib❌ Manual spans
Dependency mapping✅ Tự động Smartscape⚠️ Service Map❌ Không có
Near-zero config✅ Phần lớn auto-discover❌ Cần config files❌ Cần config

📖 Ref: OneAgent Overview

2.2 Quy Trình Auto-Discovery Chi Tiết

Khi OneAgent được cài lên một server (VD: Fedora chạy nginx + Java + PostgreSQL), nó thực hiện 6 bước tự động:

BƯỚC 1: PROCESS SCAN
  OneAgent quét /proc filesystem → phát hiện:
  • PID 1234: nginx (master + 4 workers)
  • PID 5678: java -jar order-service.jar
  • PID 9012: postgres (postmaster + backends)

BƯỚC 2: TECHNOLOGY DETECTION
  Từ process metadata, xác định:
  • nginx → Web Server technology
  • java → JVM technology (Tomcat/Spring Boot)
  • postgres → Database technology

BƯỚC 3: CODE INJECTION
  Với processes chạy full-stack mode:
  • nginx: inject monitoring vào worker processes
  • java: inject JVM agent (bytecode instrumentation)
  • postgres: KHÔNG inject (database = external service)
               → 🔗 Xem Chi Tiết tại [[05 - Services và Database Monitoring#4. Database Monitoring]]

BƯỚC 4: SERVICE DETECTION
  Từ incoming requests:
  • nginx nhận HTTP traffic port 80 → Service: "nginx web service"
  • Java nhận requests từ nginx → Service: "order-service"
  • Postgres nhận SQL queries → Service: "PostgreSQL" (external)

BƯỚC 5: DEPENDENCY MAPPING
  Từ outgoing calls + correlation headers:
  • nginx → calls → order-service
  • order-service → calls → PostgreSQL
  → Tự động xây dựng Smartscape topology
    → 🔗 Xem [[#6. Smartscape — Bản Đồ Quan Hệ Phụ Thuộc]]

BƯỚC 6: BASELINE LEARNING
  Davis AI bắt đầu học patterns:
  • nginx: avg response = 50ms, error rate = 0.1%
  • order-service: avg response = 200ms, throughput = 100 req/s
  • Sau vài ngày đến khoảng 1 tuần: baseline bắt đầu ổn hơn
    → 🔗 Xem [[02 - Davis AI và Problem Detection#2. Dynamic Baselines]]

WARNING

⚠️ Câu bẫy thi thường gặp:

  • “OneAgent cần config gì để instrument Java app?” → KHÔNG CẦN — auto-instrument
  • “Cần thêm code/library vào application?” → KHÔNG — inject tại runtime (bytecode level)
  • “OneAgent chỉ support Java?” → SAI — support Java, .NET, Node.js, Go, PHP, Python, nginx, Apache…
  • Ngoại lệ: Go cần OneAgent SDK cho deep instrumentation vì Go compile ra binary, không chạy trên VM

2.3 Ba Monitoring Modes + Cloud-Native Full-Stack ⭐

Không phải host nào cũng cần monitor giống nhau. Trong tài liệu hiện hành của Dynatrace, khi cài OneAgent trên host/server bạn thường chọn 3 monitoring modes. Cloud-native full-stack là mô hình triển khai cho Kubernetes, không phải host mode riêng.

graph LR
    subgraph Modes["OneAgent Monitoring Modes"]
        direction TB
        FS["🔴 FULL-STACK<br/>Host + Process + Service<br/>Code-level traces, SQL, exceptions<br/>→ Business-critical apps"]
        IF["🟡 INFRASTRUCTURE<br/>Host metrics + logs + process context<br/>KHÔNG deep code-level tracing<br/>→ DB, infra hosts"]
        DI["🟢 DISCOVERY<br/>Basic host health + inventory<br/>→ Survey, broad coverage"]
    end

    FS -.-|"Chi tiết ▲"| IF
    IF -.-|"Chi tiết ▲"| DI

TIP

Cloud-native full-stack là mô hình triển khai K8s (Operator + Webhook + CSI Driver), không phải host mode thứ 4.

TIP

Trong đề cũ, bạn vẫn có thể gặp cách diễn đạt khiến cloud-native full-stack trông như mode thứ 4. Với sản phẩm hiện tại, hãy hiểu đúng: đó là kiểu triển khai K8s dùng Operator, webhook, và CSI driver.

Tại sao Infrastructure mode cho database server?

Đây là câu hỏi hay ra thi. Logic:

  1. Database (PostgreSQL, MySQL, Oracle) = external service trong Dynatrace
  2. Dynatrace monitor database bằng cách capture SQL queries từ phía caller (Java app gọi DB)
  3. Vì vậy, trên DB server chỉ cần host metrics (CPU, RAM, disk I/O)
  4. Full-stack trên DB server = lãng phí tài nguyên mà không thêm giá trị APM
  5. → Infrastructure hoặc Discovery mode là phù hợp

📝 Câu thi: “MC: Mode khuyến nghị cho database server?” → Infrastructure + Discovery

  • ❌ Full-stack → lãng phí resource, không thêm APM value
  • ❌ Half stack, Full support → không tồn tại

📖 Ref: OneAgent Deployment

2.4 Cloud-Native Full-Stack — Kubernetes Details ⭐

Đây là mô hình triển khai dành riêng cho Kubernetes/OpenShift. Nó khác full-stack trên VM/host truyền thống:

Traditional Full-Stack:
  Cài OneAgent binary trực tiếp trên host OS
  OneAgent inject vào mọi process trên host

Cloud-Native Full-Stack:
  1. Dynatrace Operator deploy trên K8s cluster
  2. DaemonSet chạy OneAgent pod trên mỗi node
  3. Admission Webhook intercept pod creation events
  4. Khi pod mới deploy:
     → Webhook inject init container
     → Init container copy code modules vào shared volume
     → CSI Driver mount code modules vào app container
     → App container starts → auto-instrumented
  5. Ưu điểm:
     • Không cần privileged containers
     • Tránh race condition khi pod startup
     • Mỗi pod inject riêng → không ảnh hưởng pod khác

📝 Câu thi: “Chế độ nào dùng admission webhook + CSI driver?” → Cloud-native full-stack

🔗 Kết nối: Xem thêm về K8s monitoring tại 10 - Kubernetes và Cloud

2.5 Quản Lý OneAgent — Câu Hỏi Hay Gặp

Auto-update:

OneAgent tự động update lên phiên bản mới. Bạn có thể tắt auto-update ở 2 cấp độ:

  • ✅ Globally — tắt cho tất cả OneAgent trong environment
  • ✅ Per host — tắt trên từng host riêng lẻ

⚠️ Câu bẫy: “Chỉ khi có ActiveGate mới tắt được” → SAI. “Không tắt được” → SAI.

Assign Host Group:

Host Group dùng để nhóm hosts chia sẻ config giống nhau (🔗 xem 06 - Configuration và Management > 1. Management Zones vs Host Groups).

Cách assign:

  • ✅ oneagentctl --set-host-group=<name> (command-line tool)
  • ✅ Lúc install: ./Dynatrace-OneAgent-Linux.sh --set-host-group=web-servers
  • ❌ KHÔNG edit trong Host Settings trên UI
  • ❌ KHÔNG qua Management Zones API

Monitor PHP chỉ trên 1 host:

Scenario: Bạn có 10 hosts, chỉ muốn monitor PHP trên 1 host duy nhất.

Bước 1: Settings > Monitoring > Monitored technologies
        → Disable PHP monitoring globally

Bước 2: Specific host > Host settings
        → Enable PHP monitoring cho host cụ thể đó

→ Kết quả: PHP chỉ được monitor trên 1 host

3. ActiveGate — Cầu Nối Mạng ⭐

3.1 Tại Sao Cần ActiveGate?

Trong môi trường đơn giản, OneAgent gửi data trực tiếp đến Dynatrace cluster qua HTTPS. Nhưng trong enterprise, có nhiều lý do cần ActiveGate:

Scenario 1: SEALED NETWORK
  ┌─────────────────────────────┐
  │ Internal Network (no internet)│
  │ ┌─────────┐ ┌─────────┐    │    ┌────────────┐
  │ │ Host A  │ │ Host B  │    │    │ Dynatrace  │
  │ │ OneAgent│ │ OneAgent│────┼──X─│ Cluster    │  ← Blocked!
  │ └────┬────┘ └────┬────┘    │    └────────────┘
  │      └─────┬─────┘         │
  │      ┌─────▼─────┐         │    ┌────────────┐
  │      │ ActiveGate│─────────┼────│ Dynatrace  │  ← OK!
  │      │ (proxy)   │         │    │ Cluster    │
  │      └───────────┘         │    └────────────┘
  └─────────────────────────────┘
  → AG đặt trong DMZ, bridge giữa internal network và cloud

Scenario 2: NETWORK OPTIMIZATION
  100 OneAgents gửi data riêng lẻ → overhead lớn
  → 1 AG bundle + compress tất cả traffic → giảm bandwidth 50-70%

Scenario 3: CLOUD INTEGRATIONS
  Dynatrace cần pull metrics từ AWS CloudWatch / Azure Monitor
  → AG chạy trong VPC/VNet, có quyền access cloud APIs

4. Grail — Data Lakehouse ⭐

4.1 Vấn Đề Grail Giải Quyết

Trước Grail, Dynatrace (và hầu hết observability tools) có vấn đề data silos:

TRƯỚC GRAIL — 3 hệ thống riêng biệt:
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ Metrics Store│ │ Log Store    │ │ Trace Store  │
│ (custom DB)  │ │ (Elastic-    │ │ (custom DB)  │
│              │ │  search)     │ │              │
│ Query:       │ │ Query:       │ │ Query:       │
│ PromQL-like  │ │ Lucene/KQL   │ │ Trace viewer │
└──────────────┘ └──────────────┘ └──────────────┘
   Vấn đề: 3 hệ thống, 3 ngôn ngữ, 3 retention policies
            → Correlate data = nightmare

SAU GRAIL — 1 hệ thống duy nhất:
┌────────────────────────────────────────────────┐
│                    GRAIL                        │
│          (Unified Data Lakehouse)                │
│                                                  │
│  Metrics + Logs + Traces + Events +              │
│  Business Events + Security Events               │
│                                                  │
│  Query ALL data with → DQL (1 ngôn ngữ duy nhất)│
│  Retention: flexible per bucket                  │
└────────────────────────────────────────────────┘

💡 Analogie: Trước Grail giống như có 3 tủ hồ sơ riêng biệt (metrics, logs, traces) — muốn tìm liên quan phải mở cả 3 tủ. Grail giống 1 hệ thống tìm kiếm tập trung — search 1 lần, tìm tất cả.

4.2 Ba Đặc Tính Kỹ Thuật Cốt Lõi

1. Schema-on-read (vs Schema-on-write):

Schema-on-write (Elasticsearch):
  Bước 1: Define mapping (field types, analyzers) → TRƯỚC khi insert
  Bước 2: Insert data → phải match schema
  Bước 3: Query → nhanh (index đã build)
  ⚠️ Vấn đề: thêm field mới = reindex tất cả data

Schema-on-read (Grail):
  Bước 1: Ingest data AS-IS → không cần schema
  Bước 2: Khi query → Grail tự infer data types
  Bước 3: Thêm field mới? Data cũ vẫn query được
  ✅ Linh hoạt: bất kỳ data format nào đều ingest được

2. MPP analytics trên object storage:

Traditional search (Elasticsearch):
  Data → Build inverted index → Search index
  ✅ Search nhanh nếu query match index pattern
  ❌ Build index tốn CPU/storage
  ❌ Chỉ search được theo indexed fields

Grail:
  Data → lưu trên object storage + metadata phù hợp cho analytics
  → Query: tận dụng massively parallel processing (MPP)
  ✅ Query linh hoạt trên nhiều loại dữ liệu
  ✅ Không phụ thuộc hoàn toàn vào inverted-index kiểu cũ
  ✅ Dễ scale compute và storage độc lập

NOTE

Datawarping là cách gọi marketing/tài liệu cũ mà bạn có thể gặp trong dump. Khi ôn hiện tại, nên nhớ bản chất là MPP analytics trên Grail, không nhất thiết phải thuộc đúng từ đó.

3. Separation of Storage and Compute:

  • Storage = Cloud Object Storage (S3/Azure Blob/GCS) — scale theo data volume
  • Compute = DQL Engine — scale theo query complexity
  • → Scale độc lập — không bị bottleneck

4.3 Grail Buckets — Quản Lý Data Lifecycle

Buckets là cách Dynatrace tổ chức và quản lý data trong Grail:

Data arrives → OpenPipeline processes/routs → Grail Bucket

┌──────────────────────────────────────────────────┐
│                 GRAIL BUCKETS                     │
│                                                   │
│  ┌─────────────────┐  Retention: 35 days          │
│  │  default_logs   │  → Tất cả logs đổ vào đây   │
│  │                 │    nếu KHÔNG cấu hình routing │
│  └─────────────────┘                              │
│                                                   │
│  ┌─────────────────┐  Retention: 15 months        │
│  │ default_metrics │  → Metrics 1-min granularity  │
│  └─────────────────┘                              │
│                                                   │
│  ┌─────────────────┐  Retention: 10 days          │
│  │  default_spans  │  → Distributed traces/spans  │
│  └─────────────────┘                              │
│                                                   │
│  ┌─────────────────┐  Retention: 3 years          │
│  │ security_logs   │  → Custom bucket cho compliance│
│  │  (custom)       │    (GDPR, SOX audit trails)   │
│  └─────────────────┘                              │
│                                                   │
│  ┌─────────────────┐  Retention: 10 days          │
│  │  debug_logs     │  → Debug data, expire nhanh   │

Mỗi Bucket có:

  • Retention period riêng, nhưng range phụ thuộc bucket type
  • Permissions riêng (ai được query bucket nào — 🔗 liên quan 06 - Configuration và Management)
  • Query scope — DQL có thể filter theo bucket

IMPORTANT

Đừng học một con số 10 ngày → 10 năm cho mọi custom bucket.

  • Logs / events / business events / security events: thường từ 1 ngày đến 10 năm
  • Spans: thường từ 10 ngày đến 10 năm
  • Metrics trong Grail hiện mặc định nằm ở default_metrics với 15 tháng retention, không phải custom bucket linh hoạt như logs

📝 Câu thi: “Nhiều segments business event data, mỗi segment có data policy riêng?” → Custom Buckets

5. OpenPipeline — Xử Lý Data Real-Time ⭐

5.1 OpenPipeline Là Gì Và Tại Sao Quan Trọng?

OpenPipeline là cổng vào duy nhất — TẤT CẢ data phải đi qua đây trước khi vào Grail. Nó xử lý data real-time trong quá trình truyền (in-flight processing).

Raw data sources:
  OneAgent ──────────┐
  OpenTelemetry ─────┤
  Dynatrace API ─────┤──► OpenPipeline ──► Grail Buckets
  Extensions ────────┤
  Business Events ───┘

OpenPipeline processing stages:
┌─────────────────────────────────────────────┐
│ Stage 1: RECEIVE                            │
│   ← Data từ mọi nguồn                      │
│                                             │
│ Stage 2: PROCESS (6 chức năng)              │
│   ├── Privacy masking                       │
│   │   "4111-2222-3333-4444" →               │
│   │   "4111-****-****-4444"                 │
│   │                                         │
│   ├── Contextual enrichment                 │
│   │   Log {host: "host-01"} →               │
│   │   Log {host: "host-01", team: "platform",│
│   │        env: "prod", region: "us-east-1"} │
│   │                                         │
│   ├── Normalization                         │
│   │   "2026/04/04 03:00" →                  │
│   │   "2026-04-04T03:00:00Z" (ISO 8601)    │
│   │                                         │
│   ├── Metric extraction                     │
│   │   Log: "Order processed in 350ms" →     │
│   │   Metric: order.duration = 350          │
│   │   (không cần code change!)              │
│   │                                         │
│   ├── Filtering/Sampling                    │
│   │   Keep 100% error logs                  │
│   │   Keep 10% debug logs                   │
│   │   Drop health check logs                │
│   │                                         │
│   └── Routing                               │
│       Security logs → security_bucket       │
│       Debug logs → debug_bucket             │
│       Default → default_logs                │
│                                             │
│ Stage 3: DELIVER → Grail Buckets            │
└─────────────────────────────────────────────┘

WARNING

⚠️ Câu bẫy #1 trong thi:
“OpenPipeline chỉ routing data đến bucket” → SAI!
OpenPipeline = Ingest + Processing (6 chức năng) + Routing.
Routing chỉ là 1 trong 6 chức năng.

💡 So sánh với tool quen: OpenPipeline ≈ Logstash (ELK) hoặc Datadog Pipelines — nhưng xử lý tất cả loại data (không chỉ logs) và integrated với Grail Buckets.

6. Smartscape — Bản Đồ Quan Hệ Phụ Thuộc ⭐

6.1 Smartscape Là Gì?

Smartscape là bản đồ topology real-time — tự động phát hiện và hiển thị TẤT CẢ components trong môi trường IT và mối quan hệ giữa chúng. Đây là input chính cho Davis AI khi phân tích root cause (🔗 xem 02 - Davis AI và Problem Detection > 1. Ba Loại AI).

6.2 Năm Tầng — Chi Tiết Và Ví Dụ

graph BT
    DC["🏢 DATACENTERS<br/>AWS regions, Azure, VMware, K8s clusters"]
    HO["🖥️ HOSTS<br/>VMs, physical, EC2 instances"]
    PR["⚙️ PROCESSES<br/>JVM, .NET, nginx workers"]
    SV["🔗 SERVICES<br/>REST APIs, DB services"]
    AP["🌐 APPLICATIONS<br/>Web app, mobile app, SPA"]

    DC -->|"part of"| HO
    HO -->|"runs on"| PR
    PR -->|"runs on"| SV
    SV -->|"calls"| AP

💡 Ghi nhớ thứ tự: D-H-P-S-A (Đất-Hầm-Phòng-Sảnh-Áp mái) — từ nền móng lên mái nhà.

6.3 Entities, IDs, và Relationships

Entity = mỗi “node” trên Smartscape:

Entity TypeID PrefixVí dụ
HostHOST-HOST-ABC123DEF456
Process GroupPROCESS_GROUP-PROCESS_GROUP-GHI789
Process Group InstancePROCESS_GROUP_INSTANCE-PROCESS_GROUP_INSTANCE-JKL012
ServiceSERVICE-SERVICE-MNO345PQR
ApplicationAPPLICATION-APPLICATION-STU678VWX

Relationships = “edges” giữa entities:

Ví dụ thực tế — E-commerce app:

APPLICATION "MyWebApp"
  │ calls
SERVICE "Frontend API"
  ├── calls → SERVICE "Order Service"
  │             ├── calls → SERVICE "Payment Gateway"
  │             │             └── calls → SERVICE "PostgreSQL"
  │             └── calls → SERVICE "Inventory Service"
  │                           └── calls → SERVICE "Redis Cache"
  └── calls → SERVICE "Auth Service"
                └── calls → SERVICE "LDAP"

Mỗi SERVICE:
  └── runs on → PROCESS GROUP (java, .NET, nginx...)
       └── runs on → HOST (vm-web-01, vm-db-01...)
            └── part of → DATACENTER (AWS us-east-1)

Tại sao quan trọng? Khi PostgreSQL chậm → Davis AI traverse Smartscape graph → biết Order Service bị ảnh hưởng → biết Frontend API bị ảnh hưởng → biết users bị ảnh hưởng. Không cần ai configure relationships — tất cả auto-discovered.

6.4 Process Group vs Process Group Instance ⚠️

Process GroupProcess Group Instance
Là gìLogical group — tất cả processes cùng loại1 instance cụ thể đang chạy
Ví dụ”nginx” (group toàn bộ)“nginx on host-web-01 (PID 1234)“
ScopeAcross nhiều hosts1 process trên 1 host
MetricsAggregated across instancesPer-instance metrics

📝 Câu thi: “Process Group là gì?” → Nhóm processes cùng technology, cùng task, có thể chạy trên một hoặc nhiều hosts.

  • ❌ KHÔNG phải “different technology types”
  • ❌ KHÔNG phải “same technology, various tasks”

📝 Câu thi: “Smartscape timeframe?” → 72 giờ (cách hỏi kiểu classic Smartscape).

8. SaaS vs Managed — Khi Nào Dùng Gì? ⭐

Đặc điểmSaaSManaged
HostingDynatrace cloudCustomer’s data center
MaintenanceDynatrace loCustomer tự quản lý infra
Cluster AG❌ Không cần, không dùng✅ Bắt buộc (đặt ở DMZ)
Env AG✅ Optional (proxy, synthetic)✅ Optional (same)
User managementAccount Management PortalCluster Management Console (CMC)
UpdatesAutomatic (Dynatrace)Mandatory cluster updates
Mission ControlN/ACung cấp health checks, license validation, auto-updates

📝 Câu thi: “Update nào mandatory trong Managed?” → Managed cluster updates (KHÔNG phải OneAgent).

📝 Câu thi: “User management trong Managed ở đâu?” → CMC (Cluster Management Console).

📝 Câu thi: “Tại sao Managed cần Mission Control?” → Health checks, license validation, automatic updates.
