Chương 13: DQL Exercises — Luyện Tập Với EasyTrade

NOTE

15 bài tập DQL progressive — từ cơ bản đến nâng cao. Tất cả dùng data từ EasyTrade demo app chạy trên ThinkPad T460 với OneAgent + trial account.

Cách dùng: Mở Notebooks trên Dynatrace → paste DQL → chạy → so sánh output.

PHẦN 1: Logs (Bài 1-5)

Bài 1 🟢 — Xem Error Logs Gần Nhất

Đề: Lấy 20 error logs gần nhất (1 giờ qua) từ EasyTrade. Hiển thị timestamp, log level, và nội dung.

💡 Hint
  • Bắt đầu bằng fetch logs
  • Time range: from: -1h
  • Filter log level: loglevel == "ERROR"
  • Chọn fields cần hiển thị
  • Giới hạn kết quả
✅ Solution

Giải thích:

  • fetch logs, from: -1h — lấy logs trong 1 giờ qua (thu hẹp time range = best practice)
  • filter ngay sau fetch — DQL performance best practice (07 - Data Analysis và Tools > 1.4)
  • fields — chỉ lấy 3 columns cần thiết (giảm data transfer)
  • sort timestamp desc — mới nhất lên đầu
  • limit 20 — giới hạn output

Bài 2 🟢 — Đếm Logs Theo Level

Đề: Đếm số lượng logs theo từng log level trong 24 giờ qua. Sắp xếp từ nhiều đến ít.

💡 Hint
  • summarize = GROUP BY + aggregate
  • count() = đếm
  • by: { field } = group by field
✅ Solution

Giải thích:

  • summarize count(), by: { loglevel } — tương đương SQL: SELECT loglevel, COUNT(*) FROM logs GROUP BY loglevel
  • Named result log_count = giúp output dễ đọc hơn

📝 Câu thi pattern: “DQL equivalent of SQL GROUP BY?” → summarize ... by: { }

Bài 3 🟡 — Tìm Logs Của Một Service Cụ Thể

Đề: Tìm tất cả WARN và ERROR logs từ service BrokerService trong 2 giờ qua. Hiển thị timestamp, level, và 100 ký tự đầu của content.

💡 Hint
  • Filter nhiều giá trị: in("WARN", "ERROR")
  • Service entity: dt.entity.service
  • Cắt string: substring(field, start, length)
✅ Solution

Giải thích:

  • in("WARN", "ERROR") — filter cho nhiều values, tương đương SQL IN (...)
  • matchesPhrase() — tìm chính xác phrase trong service name
  • fieldsAdd — thêm computed column mà không xóa columns cũ
  • substring(content, 0, 100) — lấy 100 ký tự đầu, tránh output quá dài

Bài 4 🟡 — Error Rate Theo Giờ

Đề: Tính error rate (%) cho mỗi giờ trong 12 giờ qua. Error = logs có loglevel “ERROR”.

💡 Hint
  • countIf(condition) — đếm có điều kiện
  • bin(timestamp, 1h) — nhóm theo khoảng thời gian
  • Error rate = errors / total × 100
✅ Solution

Giải thích:

  • bin(timestamp, 1h) — nhóm logs theo khoảng 1 giờ (time bucketing)
  • countIf(condition) — đếm chỉ records thỏa condition
  • toDouble() — ép kiểu để phép chia cho decimal result
  • round(..., 2) — làm tròn 2 chữ số thập phân
  • Pattern này RẤT hay dùng trong dashboards

Bài 5 🟡 — Parse Log Content

Đề: EasyTrade logs thường chứa thông tin dạng "Processing order #12345 for user john@example.com". Parse ra order ID và email từ log content.

💡 Hint
  • Command parse với pattern matching
  • LD = any characters (Lazy Data)
  • LONG:name = capture số
  • LD:name = capture text
✅ Solution

Giải thích:

  • parse = extract data từ unstructured text → structured fields
  • LD = Lazy Data — match bất kỳ ký tự nào (skip)
  • 'order #' = literal string match
  • LONG:order_id = capture integer vào field order_id
  • LD:email = capture phần còn lại vào field email

📝 Câu thi: parse thường xuất hiện trong phần hands-on — biết cú pháp = dễ lấy điểm.

PHẦN 2: Spans / Traces (Bài 6-8)

Bài 6 🟢 — Tìm Slow Requests

Đề: Tìm 10 requests chậm nhất (duration > 1 giây) trong 1 giờ qua. Hiển thị service name, duration (giây), và status.

💡 Hint
  • fetch spans — lấy trace data
  • Duration lưu dạng nanoseconds → chia 1e9 để ra giây
  • span.kind == "SERVER" — chỉ lấy server-side spans
✅ Solution

Giải thích:

  • span.kind == "SERVER" — filter server-side spans (bỏ CLIENT, INTERNAL)
  • Duration trong Dynatrace = nanoseconds → ÷ 1e9 = seconds
  • Đây là pattern cơ bản nhất khi debug latency

Bài 7 🟡 — Top Services Theo Error Count

Đề: Tìm top 5 services có nhiều error spans nhất trong 6 giờ qua. Tính cả total spans và error rate.

💡 Hint
  • otel.status_code == "ERROR" — error spans
  • Combine count() + countIf() trong 1 summarize
✅ Solution

Giải thích:

  • Pattern giống Bài 4 nhưng trên spans thay vì logs
  • by: { dt.entity.service.name } — group by service
  • Kết quả: bảng ranked → dễ dàng pin lên Dashboard tile

Bài 8 🔴 — Latency Distribution Per Service

Đề: Tính P50, P90, P99 latency cho mỗi service trong 1 giờ qua. Chỉ lấy services có > 100 requests.

💡 Hint
  • percentile(field, percentage) — tính percentile
  • Filter sau summarize: dùng filter sau summarize để lọc theo total count
✅ Solution

Giải thích:

  • percentile(duration, 50) = P50 (median)
  • Chia 1e6 (thay vì 1e9) → output bằng milliseconds (trực quan hơn cho latency)
  • Filter request_count > 100 sau summarize — loại bỏ services ít traffic
  • P99 = 1% requests chậm nhất → metric quan trọng nhất cho SLOs

📝 Liên kết: Percentiles → ../../../Fundamentals/03 - Three Pillars Deep Dive - Metrics > 4. Percentiles

PHẦN 3: Business Events (Bài 9-10)

Bài 9 🟡 — Phân Tích Trading Events

Đề: EasyTrade tạo business events cho mỗi giao dịch mua/bán. Đếm số trades theo loại (BUY/SELL) trong 24 giờ qua.

💡 Hint
  • fetch bizevents — business events data
  • Field name phụ thuộc vào cách EasyTrade gửi events — check bằng fetch bizevents | limit 5 trước
✅ Solution

Giải thích:

  • Business Events = dữ liệu business logic gửi vào Dynatrace
  • Luôn khám phá data trước bằng fetch ... | limit 5 — đừng đoán field names
  • event.type = loại business event (convention chuẩn)

🔗 Business Events: 08 - Logs và Business Events > 4. Business Events

Bài 10 🔴 — Revenue Impact Analysis

Đề: Tính tổng giá trị giao dịch (trade amount) theo giờ trong 12 giờ qua. Tìm giờ có revenue cao nhất.

💡 Hint
  • sum(field) — tổng
  • bin(timestamp, 1h) — nhóm theo giờ
  • Combine sum + count + avg trong 1 summarize
✅ Solution

Giải thích:

  • Pattern “business analytics bằng DQL” — rất quan trọng cho exam domain Business Analytics
  • sum(), count(), avg() = 3 aggregate functions hay dùng nhất
  • Kết quả dạng time-series → dễ visualize bằng bar chart trong Dashboard

PHẦN 4: Events & Entities (Bài 11-13)

Bài 11 🟢 — Xem Davis Problems

Đề: Liệt kê tất cả Davis problems trong 7 ngày qua. Hiển thị thời gian, title, severity, và status.

💡 Hint
  • fetch events — Davis events
  • Filter event kind: event.kind == "DAVIS_PROBLEM"
✅ Solution

Giải thích:

  • event.kind == "DAVIS_PROBLEM" — lọc chỉ Davis-generated problems
  • dt.davis.event_type = severity type (AVAILABILITY, ERROR, SLOWDOWN, RESOURCE)
  • Pattern này hữu ích khi tạo dashboard “Problems overview”

🔗 Problem types: 02 - Davis AI và Problem Detection > 3.1 Event Categories

Bài 12 🟡 — Inventory: Liệt Kê Hosts

Đề: Liệt kê tất cả hosts đang được monitor, kèm OS type và trạng thái monitoring mode.

💡 Hint
  • fetch dt.entity.host — host entities
  • Entity data = metadata, không phải time-series
✅ Solution

Giải thích:

  • fetch dt.entity.<type> — query entity metadata (host, service, process group…)
  • Không cần from: — entities là trạng thái hiện tại, không phải time-series
  • monitoringMode = FULL_STACK / INFRASTRUCTURE / DISCOVERY

📝 Câu thi: “DQL để lấy entity information?” → fetch dt.entity.<type>

Bài 13 🟡 — Service Dependencies

Đề: Tìm tất cả services đang gọi đến database, kèm số lượng calls.

💡 Hint
  • Spans with span.kind == "CLIENT" = outgoing calls
  • Database calls thường có db.system attribute
✅ Solution

Giải thích:

  • span.kind == "CLIENT" + db.system exists → database calls
  • isNotNull(field) — filter records có field đó (không null)
  • Output: bảng service → database mapping với call volume
  • Trực quan hóa dependencies tương tự Smartscape nhưng data-driven

PHẦN 5: Metrics (Bài 14-15)

Bài 14 🟢 — CPU Usage Trend

Đề: Xem CPU usage trung bình theo host trong 6 giờ qua, interval 5 phút.

💡 Hint
  • timeseries — command đặc biệt cho metrics (KHÔNG dùng fetch)
  • avg() = aggregation function
  • interval: 5m = khoảng thời gian
✅ Solution

Giải thích:

  • timeseries = command dành riêng cho metrics (khác với fetch)
  • avg(dt.host.cpu.usage) — metric name + aggregation
  • interval: 5m — resolution (mỗi data point = 5 phút)
  • by: { dt.entity.host } — split theo host
  • Output tự động render thành line chart trong Notebooks

📝 Câu thi: “DQL command cho metrics?” → timeseries (KHÔNG phải fetch metrics)

Bài 15 🔴 — Correlate High CPU With Errors

Đề: Tìm hosts có CPU > 80% trung bình trong 1 giờ qua, rồi đếm error logs trên các hosts đó. (Advanced: multi-query correlation)

💡 Hint
  • Bước 1: Query metrics → tìm hosts CPU cao
  • Bước 2: Query logs → filter theo hosts từ bước 1
  • Trong Notebooks, bạn có thể chain queries hoặc dùng lookup
✅ Solution

Approach nâng cao (single query):

Giải thích:

  • Đây là correlation pattern — liên kết metrics với logs
  • lookup = JOIN giữa 2 data sources
  • Production workflow: CPU spike → xem error logs trên cùng host → tìm root cause
  • Trong thi, approach 2-query (Notebook sections) thực tế hơn — dễ demo

📝 Exam tip: Notebooks cho phép bạn chạy nhiều DQL query liên tiếp, mỗi query 1 section. Đây là cách investigation thực tế.
