Lab 05 — Problem Patterns & Feature Flags

Cách học lab này

Giá trị của lab này nằm ở việc so sánh nhiều failure modes, không chỉ trigger cho vui

  • Với mỗi pattern, hãy hỏi: tín hiệu nào thay đổi đầu tiên, tín hiệu nào là hệ quả, và Davis đã group chúng tốt tới đâu.
  • Feature flags trong EasyTrade cho bạn một môi trường rất hiếm để quan sát cùng một platform phản ứng ra sao trước các kiểu sự cố khác nhau mà không phải dựng incident từ đầu.
  • Alerting Profiles và notifications nên được hiểu như lớp phân phối thông tin sau khi detection đã xảy ra. Chúng quyết định ai biết về problem và biết theo cách nào, chứ không tự tạo ra causal analysis.

1. Problem Pattern: high_cpu_usage

1.1. Trigger

1.2. 🔍 Quan Sát

Trên Host page:

  • CPU usage tăng đáng kể (ThinkPad i5-6300U — bạn sẽ thấy rõ!)
  • Process CPU breakdown: service nào đang consume CPU

Trên Services page:

  • Response time tăng (CPU throttling → slower processing)
  • Throughput có thể giảm (requests queue lại)

💡 Dạng problem này khác db_not_responding:

Aspectdb_not_respondinghigh_cpu_usage
Root causeApplication logic (DB errors)Infrastructure (CPU)
Failure typeErrors (500s)Slowdown (latency increase)
Davis detectionFailure rate anomalyResponse time anomaly
User impactTrades failTrades slow

1.3. Davis AI Response

Davis sẽ tạo problem với:

  • Type: Performance degradation (không phải failure)
  • Root cause: Process group với CPU spike
  • Impact: Response time increase across dependent services

1.4. Resolve

⏱️ Chờ 5-10 phút để Davis close problem. Quan sát CPU return to baseline.

2. Problem Pattern: ergo_aggregator_slowdown

2.1. Trigger

2.2. 🔍 Quan Sát

Pattern này gây:

  • 40% traffic drop — loadgen giảm request rate
  • Slowdown trong aggregator service
  • Cascading slowdown đến downstream services

Timing theo easyTrade upstream

README của EasyTrade mô tả pattern này theo các cửa sổ thời gian kiểu 15 min hoặc 20 min: đầu tiên có slowdown ngắn, sau đó mới xuất hiện phase traffic giảm 40%. Nếu bạn bật rồi tắt quá sớm, Dynatrace có thể chưa đủ signal để tạo problem rõ ràng.

💡 Dạng problem này mô phỏng tình huống thực tế:
Trong production, traffic drop thường do: CDN issue, DNS problem, upstream service failure. Davis AI sẽ phân biệt được traffic anomaly vs performance issue.

2.3. Resolve

3. So Sánh 3 Problem Types

Sau khi trải nghiệm 3 patterns, so sánh cách Davis phản ứng:

PatternDavis SignalDetection SpeedRoot Cause TypeImpact Type
db_not_respondingFailure rate spikeNhanh (errors rõ ràng)ApplicationErrors
high_cpu_usageResponse time + CPUTrung bìnhInfrastructureSlowdown
ergo_aggregator_slowdownThroughput drop + latencyChậm hơn (subtle)ServiceMixed

💡 Observation quan trọng:

  • Davis phát hiện failure rate anomalies nhanh hơn performance anomalies
  • Performance degradation cần nhiều data points hơn để confirm (tránh false positives)
  • Traffic anomalies (throughput changes) là khó detect nhất — cần baseline chất lượng

🔗 Fundamentals: Ch.07 — Alert Types. Mỗi loại problem tương ứng với different alert conditions: error-based, latency-based, throughput-based.

4. Alerting Profiles — “Ai Nhận Alert Gì?“

4.1. Concept

Alerting Profile = filter cho problems:

  • “Team A chỉ quan tâm production problems”
  • “Team B chỉ quan tâm database problems”
  • “On-call chỉ nhận critical problems”

4.2. Tạo Alerting Profile

  1. Vào Settings → Alerting → Alerting profiles

  2. Click Add alerting profile

  3. Cấu hình:

    • Name: EasyTrade - All Problems
    • Severity filter: Chọn tất cả severities
      • ✅ Availability
      • ✅ Error
      • ✅ Slowdown
      • ✅ Resource
      • ✅ Custom
    • Event filter (optional): Có thể filter theo tag, management zone

  4. Save

4.3. Tạo thêm 1 profile chọn lọc

  1. Thêm profile mới:
    • Name: EasyTrade - Critical Only
    • Severity filter:
      • ✅ Availability
      • ✅ Error
      • ❌ Slowdown
      • ❌ Resource
      • ❌ Custom
    • Delay: Send notification immediately (hoặc after X minutes)

💡 Tại sao cần multiple profiles?

ProfileUse caseReal-world analogy
All ProblemsDevelopment/labDeveloper muốn thấy mọi thứ
Critical OnlyProduction on-callPagerDuty — chỉ wake up cho critical
PerformancePerformance teamSRE monitoring latency SLOs

🔗 Fundamentals: Ch.07 — Notification Routing. Alerting profiles = implementation của “right alert to right person” principle.

5. Problem Notifications

5.1. Setup Email Notification

Latest Dynatrace

Nhiều tenant latest khuyến nghị dùng Workflows để gửi email khi có problem, thay vì màn hình Problem notifications classic. Nếu không thấy path classic trong tenant, hãy tạo workflow “problem opened/updated” + task “Send email”.

  1. Nếu tenant của bạn có Problem notifications classic:
    • Vào Settings → Integration → Problem notifications
    • Click Add notification → chọn Email
  2. Nếu tenant của bạn dùng Workflows:
    • Tạo workflow mới với trigger kiểu problem opened/updated
    • Thêm task Send email
  3. Cấu hình:
    • Name: EasyTrade Email Alerts
    • Alerting profile: EasyTrade - All Problems (profile vừa tạo)
    • Recipients: Nhập email của bạn
    • Subject: [Dynatrace] {ProblemTitle}
    • Body: Dùng template mặc định hoặc customize với placeholders:
      • {ProblemTitle} — Tên problem
      • {ProblemSeverity} — Severity level
      • {ProblemImpact} — Mô tả impact
      • {ProblemURL} — Link đến Problem Card
  4. Send test notification / Run test workflow → kiểm tra email
  5. Save

6. Custom Alerting Rules (Metric Events)

6.1. Concept

Davis AI tự detect anomalies, nhưng đôi khi bạn cần custom rules:

  • “Alert khi CPU > 90% liên tục 5 phút” (static threshold)
  • “Alert khi error count > 100/min” (specific business rule)

6.2. Tạo Custom Metric Event

  1. Vào Settings → Anomaly detection → Custom events for alerting / Metric events (wording có thể khác tùy tenant)
  2. Click Add metric event
  3. Cấu hình:
    • Summary: High error rate on EasyTrade
    • Type: Metric selector
    • Metric: builtin:service.errors.total.rate
    • Condition: Value > 10% for 5 minutes
    • Alert preview: Xem dữ liệu hiện tại có trigger không
  4. Event properties:
    • Severity: Error
    • Description: Error rate exceeded 10% on {dims:dt.entity.service}
  5. Save

6.3. Test custom rule

  1. Enable db_not_responding pattern lại:
  2. Chờ 5 phút → custom metric event triggers
  3. Kiểm tra: Problem mới xuất hiện, có thêm custom event
  4. Disable flag:

💡 Davis problems vs Custom metric events:

Davis ProblemsCustom Metric Events
DetectionAutomatic (baseline-based)Manual rules (threshold-based)
ConfigurationZero-configRequires setup
FlexibilityDavis decidesYou decide
Best forUnknown unknownsKnown thresholds, business rules

🔗 Fundamentals: Ch.07 — Static vs Dynamic Thresholds. Davis = pure dynamic baselines. Custom metric events = bạn tự set threshold (static hoặc auto-adaptive).

⚠️ Troubleshooting

Feature flag không trigger effect

Notification email không nhận

  • Check spam folder
  • Verify Test notification hoạt động
  • Đảm bảo alerting profile được assign cho notification

Custom metric event không trigger

  • Kiểm tra Alert preview — có data matching condition không?
  • Metric name có thể khác tùy version — search trong Data Explorer
  • Thử giảm threshold (ví dụ: > 5% thay vì > 10%)
