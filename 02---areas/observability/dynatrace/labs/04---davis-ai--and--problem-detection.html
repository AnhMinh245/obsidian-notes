Lab 04 — Davis AI & Problem Detection

Sau lab này, bạn sẽ:

  • Hiểu vai trò của Davis AI / Dynatrace Intelligence trong problem detection và root-cause analysis
  • Trigger problem pattern bằng EasyTrade feature flag
  • Quan sát Davis AI phát hiện và phân tích problem
  • Đọc Problem Card — root cause analysis, impact, timeline
  • Resolve problem bằng cách disable flag → quan sát recovery
  • So sánh: Davis AI vs rule-based monitoring (Datadog monitors)

Cách học lab này

Hãy xem Davis như một công cụ tạo giả thuyết điều tra có ngữ cảnh topology

  • Problem card thường giúp bạn rút ngắn thời gian tìm điểm bắt đầu, nhưng không thay thế việc xác minh bằng timeline, impacted entities, traces, logs, và metrics.
  • Độ trễ detect trong lab này là một phần của bài học. Nếu bạn bật flag rồi tắt quá nhanh, Davis có thể chưa có đủ tín hiệu để tạo problem hoặc phân tích rõ root cause.
  • Câu hỏi quan trọng nhất khi đọc một problem card không phải “Davis nói gì?” mà là “Tín hiệu nào trong card này đủ mạnh để mình tin, và tín hiệu nào mình vẫn phải tự kiểm tra lại?“.

1. Davis AI — Không Giống AI Bạn Nghĩ

1.1. Davis AI không chỉ là “AI chatbot” hay anomaly detector

Hiểu lầm phổ biến

Nhiều người nghĩ “AI” = chỉ có LLM hoặc deep learning. Với Dynatrace, phần bạn thấy trong lab này chủ yếu là causal + topology-aware problem analysis.

Dynatrace docs hiện dùng umbrella Dynatrace Intelligence cho nhiều loại AI khác nhau. Riêng trong Problems workflow của lab này, phần quan trọng nhất là:

  • Input: Topology (Smartscape) + Metrics + Events
  • Core reasoning: Causal analysis dựa trên dependencies và thời gian phát sinh tín hiệu
  • Output: Root cause candidate + impacted entities + timeline giải thích được
Traditional monitoring:
  CPU > 80% → Alert! (rule-based, static threshold)
  → 100 services bị CPU spike → 100 alerts → ALERT STORM

Davis AI:
  CPU > baseline → anomaly detected
  → Correlate với Smartscape topology
  → Tìm root cause: Service X bị memory leak → gây cascade
  → TẠO 1 PROBLEM với root cause = Service X
  → Bao gồm tất cả impacted services trong 1 problem card

1.2. Davis AI Flow

     Metrics change detected
            │
            ▼
     Baseline comparison
     (tự học từ lịch sử)
            │
            ▼
     Anomaly confirmed?
     ├── NO → ignore
     └── YES
            │
            ▼
     Smartscape topology analysis
     (ai depend on ai?)
            │
            ▼
     Causal correlation
     (anomaly X gây ra anomaly Y?)
            │
            ▼
     Root cause identification
            │
            ▼
     PROBLEM CREATED
     ├── Root cause entity
     ├── Impacted entities
     ├── Timeline
     └── Suggested resolution

Baseline/anomaly detectionTự thích nghi hơn threshold tĩnhCó thể phát hiện “có gì đó lạ” nhưng chưa đủ root cause

🔗 Fundamentals: Ch.09 — AIOps. Davis AI = practical implementation của concept “intelligent correlation” — giảm noise, tìm root cause tự động.

3. Trigger Problem: db_not_responding

3.1. Tại sao chọn pattern này?

db_not_responding là pattern rõ ràng nhất:

  • Database bắt đầu throw errors
  • Services phụ thuộc DB lần lượt fail
  • Davis AI sẽ trace cascade: DB → services → user impact
  • Root cause rõ ràng: database entity

3.3. ⏱️ Chờ Davis AI detect

Davis AI cần thời gian!

Theo chính README của EasyTrade, pattern DbNotResponding thường cần khoảng 20 phút chạy liên tục mới đủ signal để tạo problem rõ ràng trên Dynatrace. Baseline quality và traffic thực tế vẫn có thể làm thời gian này ngắn hơn hoặc dài hơn.

Trong khi chờ, bạn có thể:

  1. Quan sát real-time trên Services page: Failure rate tăng dần

  3. Xem PurePath: Traces bắt đầu có error nodes

4.3. Deep dive: Root Cause

🔍 Quan sát:

Davis AI sẽ xác định root cause là database-related entity:

  • Root cause: MSSQL Database (hoặc database service)
  • Reason: Failure rate anomaly detected
  • Cascade: DB fail → broker-service errors → user impact

💡 Tại sao Davis biết database là root cause, không phải broker-service?

  1. Davis xem Smartscape topology: broker-service depends on MSSQL
  2. Davis thấy: MSSQL errors xuất hiện TRƯỚC broker-service errors
  3. Kết luận: MSSQL là nguyên nhân, broker-service là hệ quả

Đây là causal analysis — timeline + topology = root cause determination.

4.4. Deep dive: Impact Analysis

  1. Xem section Impacted services
  2. Davis liệt kê TẤT CẢ services bị ảnh hưởng bởi DB failure
  3. Bao gồm cả services không trực tiếp call DB nhưng bị ảnh hưởng gián tiếp
Root Cause: [MSSQL Database]
     ↓ impacts
[broker-service]  → Failure rate: 0% → 45%
     ↓ impacts
[pricing-service] → Failure rate: 0% → 30%
     ↓ impacts
[accountservice]  → Failure rate: 0% → 25%

4.5. Deep dive: Timeline

  1. Xem Timeline section
  2. Observerve sequence:
    • T+0: DB starts throwing errors
    • T+2min: broker-service failure rate increases
    • T+3min: pricing-service affected
    • T+5min: Davis creates problem (after confirming anomaly)
    • T+10min: Davis completes root cause analysis

🔗 Fundamentals: Ch.07 — Alert Correlation. Trong traditional monitoring (Datadog monitors), bạn sẽ nhận 3-5 separate alerts (1 cho DB, 1 cho broker, 1 cho pricing…). Davis tạo 1 problem covering tất cả — noise reduction.

5. Resolve Problem — Disable Flag

5.1. Disable problem pattern

5.2. 🔍 Quan sát recovery

  1. Trên Problems page, problem status sẽ chuyển sang RESOLVED (sau vài phút)
  2. Services failure rate giảm về 0%
  3. Timeline trên Problem Card ghi nhận thời điểm recovery

💡 Davis tự detect recovery:

  • Davis so sánh metrics sau khi disable flag với baseline
  • Khi metrics trở về baseline → Davis đánh dấu problem = RESOLVED
  • Bạn không cần manually close problem

5.3. Problem lifecycle summary

OPEN → Davis detects anomaly, creates problem
  ↓
CONFIRMED → Root cause identified, impact analyzed
  ↓
RESOLVED → Metrics return to baseline, auto-closed

6. So Sánh: Davis AI vs Datadog Monitors

AspectDatadog MonitorsDavis AI
ConfigurationManual — bạn phải tạo monitor cho mỗi metricZero-config — Davis monitor mọi thứ tự động
DetectionThreshold-based (static hoặc anomaly)Baseline-based (tự học) + topology-aware
CorrelationKhông có — mỗi monitor = 1 alert riêngTự correlate — gộp related alerts vào 1 problem
Root causeKhông có — bạn tự tìmTự xác định bằng causal analysis
False positivesPhụ thuộc threshold configurationÍt hơn — topology context giảm noise
FlexibilityRất flexible — configure bất kỳ metric/conditionÍt flexible — Davis quyết định, ít tuỳ chỉnh
TransparencyRõ ràng — bạn biết rule”Black box” — phải trust Davis

💡 Không có cái nào tốt hơn hoàn toàn:

  • Davis AI tốt cho: large-scale environments, microservices, khi bạn không biết monitor gì
  • Datadog Monitors tốt cho: specific business rules, custom conditions, khi bạn cần control

⚠️ Troubleshooting

Davis không tạo problem

  • Baseline chưa đủ: Đảm bảo EasyTrade chạy > 2 giờ trước khi trigger problem
  • Anomaly quá nhỏ: Có thể Davis coi anomaly không đủ significant
  • Kiểm tra: Settings → Anomaly detection → xem thresholds

Problem tạo nhưng không có root cause

  • Smartscape topology chưa đầy đủ
  • Restart EasyTrade để OneAgent re-inject:
  • Chờ 10-15 phút cho topology stabilize

Feature flag không hoạt động
