Lab 02 — Services, PurePath & Database

⏱️ Thời gian: ~60 phút
📋 Prerequisites: Lab 01 hoàn thành, EasyTrade chạy + OneAgent connected
🔗 Source: Dynatrace/easytrade

🎯 Mục Tiêu

Sau lab này, bạn sẽ:

  • Hiểu cách Dynatrace tự phát hiện và phân loại Services
  • Đọc thành thạo Service Flow diagram
  • Phân tích PurePath — distributed trace end-to-end
  • Sử dụng Response Time Hotspots để tìm bottleneck
  • Khám phá Database Monitoring cho MSSQL
  • So sánh PurePath vs Flame Graph (Datadog)

📚 Kiến Thức Nền

Fundamentals

  • Ch.04 — Distributed Tracing
    → PurePath là implementation của distributed tracing — mỗi PurePath = 1 complete trace
  • Ch.05 — Instrumentation
    → OneAgent tự inject tracing code — không cần manual instrumentation

Dynatrace Theory

  • Ch.05 — Services & DB Monitoring

Cách học lab này

Cách đọc lab này hiệu quả là đi từ rộng đến sâu

  • Bắt đầu ở Service List để thấy hệ thống đang hành xử ra sao trên diện rộng, sau đó vào Service Flow để hiểu dependencies, rồi mới xuống từng PurePath cụ thể.
  • PurePath đại diện cho một request end-to-end rất giàu chi tiết, nhưng nó không thay thế cho việc đọc pattern ở cấp service. Bạn cần cả hai: service-level trends để biết chuyện gì đang phổ biến, và PurePath để hiểu chính xác một request đã đi đâu.
  • Khi phân tích latency, cố tách ba lớp: thời gian ở service hiện tại, thời gian gọi dependency, và thời gian chờ DB/external resource. Lab này rất tốt để luyện tách các lớp đó ra thay vì chỉ nhìn tổng response time.

1.3. Hiểu Service detection tự động

💡 Dynatrace detect services bằng cách nào?

  1. OneAgent inject vào process (Java/.NET/Go/Node.js)
  2. Intercept incoming HTTP/gRPC/messaging calls
  3. Nhóm requests theo URL pattern → tạo “service”
  4. Tự link service → process group → host (Smartscape)

Ví dụ: broker-service nhận requests tại /api/trade, /api/balance, /api/status → tất cả được nhóm dưới 1 service.

  1. Click Service flow (tab hoặc button)
  2. Bạn sẽ thấy dependency diagram dạng cây:
[Frontend Nginx]

💡 Service Flow vs Smartscape:

  • Service Flow = dependency từ góc nhìn 1 service cụ thể (ai gọi nó, nó gọi ai)
  • Smartscape = toàn bộ topology (4 tầng, tất cả entities)

Cả hai đều dựa trên real traffic — không phải config files.

2.4. Top Requests

  2. Click vào 1 request type (ví dụ: /api/trade/buy)
  3. Bạn sẽ thấy:

    • Throughput
    • Failure rate
    • Link đến PurePaths (individual traces)

3. PurePath — “Đường Đi Nguyên Vẹn” Của Request

PurePath là Dynatrace's distributed tracing — feature cốt lõi

3.1. Khái niệm PurePath

PurePath = complete end-to-end trace từ user click đến database query — bao gồm mọi service call trên đường đi.

🔗 Fundamentals: Ch.04 — Trace structure. Nhớ diagram trace = tree of spans? PurePath hiển thị chính xác concept này, nhưng với method-level detail thay vì chỉ span-level.

3.2. Mở PurePath

  1. Từ broker-service → Top requests → click 1 request type
  2. Trong danh sách requests, click 1 request cụ thể → PurePath
  3. Hoặc: Distributed traces (menu chính) → chọn 1 trace

3.3. 🔍 Quan Sát: PurePath Waterfall

Bạn sẽ thấy waterfall view:

broker-service: POST /api/trade/buy       [=========================================] 245ms
  ├── pricing-service: GET /api/price      [======]                                   42ms
  │     └── MSSQL: SELECT price FROM...      [===]                                    18ms
  ├── accountservice: GET /api/balance      [=======]                                 55ms
  │     └── MSSQL: SELECT balance FROM...    [====]                                   22ms
  └── MSSQL: INSERT INTO trades...                    [========]                      68ms

Mỗi dòng = 1 node (tương đương span trong OTel):

  • Thanh ngang = thời gian execution
  • Indentation = parent-child relationship (ai gọi ai)
  • Màu sắc = technology (Java = xanh, .NET = tím, DB = cam)

3.4. PurePath method-level detail

💡 Điều Dynatrace làm mà Datadog không làm:

Click vào 1 node (ví dụ: broker-service) → bạn sẽ thấy code-level execution:

broker-service: POST /api/trade/buy [245ms]
  ├── main.handleTrade()            [240ms]  ← method-level!
  │   ├── http.Get(pricing-service) [42ms]   ← outgoing call
  │   ├── http.Get(accountservice)  [55ms]   ← outgoing call
  │   ├── validateTrade()           [5ms]    ← internal method
  │   └── db.Exec(INSERT...)        [68ms]   ← database call
  └── middleware.LogRequest()       [2ms]

Dynatrace OneAgent inject inside the runtime → thấy từng method, từng function call. Datadog APM chỉ thấy span boundaries (service-to-service), không thấy bên trong mỗi service.

Detail levelDatadog APMDynatrace PurePath
Service calls✅✅
Database queries✅✅
Method calls❌✅ (method hotspots)
CPU time vs wait time❌✅
Exception stack traces✅✅ + code context

3.5. PurePath analysis tips

Khi đọc PurePath, tìm:

  1. Longest bar → bottleneck (node chiếm nhiều thời gian nhất)
  2. Red nodes → failures (errors)
  3. Sequential calls → có thể parallel hóa để tăng performance
  4. Deep nesting → complexity, potential simplification

4. Response Time Hotspots — Tìm Bottleneck

4.1. Mở Hotspots

  1. Từ service page (broker-service) → Multidimensional analysis → Response time hotspots
    (hoặc tìm Response time analysis trong service details)

4.2. 🔍 Quan Sát

Response time hotspots phân tích thời gian ở đâu:

Total response time: 245ms
├── Lock/wait time:     12ms (5%)    ← đợi locks
├── Suspension time:     8ms (3%)    ← đợi thread pool
├── Database time:      108ms (44%)  ← 🔴 DB calls chiếm gần nửa!
├── Remote calls time:   97ms (40%)  ← gọi services khác
└── Code-level time:     20ms (8%)   ← actual computation

💡 Đây là cách tìm bottleneck real-world:

  • Database time cao → cần optimize queries, thêm indexes
  • Remote calls time cao → downstream services chậm
  • Code-level time cao → algorithm cần optimize
  • Lock/wait time cao → contention issues, thread pool nhỏ

🔗 Fundamentals: Ch.03 — Latency. Concept “where does time go?” từ theory → Dynatrace trả lời chính xác bằng hotspot analysis.

5. Database Monitoring — MSSQL

5.1. Mở Database page

  1. Vào Databases (trong navigation)
  2. Click vào MSSQL (EasyTrade database)

5.2. 🔍 Quan Sát: Database Overview

MetricÝ nghĩa
Response timeAvg query execution time
Failure rate% queries thất bại
ThroughputQueries/min
Top databasesDatabase names

5.3. Database Statements

  1. Click View database statements (hoặc tab Statements)
  2. Bạn sẽ thấy danh sách SQL queries đang chạy
  3. Sort by Response time → tìm slow queries

🔍 Quan sát:

  • SELECT statements → read operations (pricing, account lookup)
  • INSERT statements → write operations (trade execution)
  • Slow queries → potential optimization targets

5.4. Backtrace — “Ai gọi query này?”

  1. Click vào 1 database statement
  2. Click Backtrace
  3. Bạn sẽ thấy: Service nào gọi query này, qua method nào
broker-service
  └── handleTrade()
        └── db.Exec("INSERT INTO trades ...")  ← đây

💡 Tại sao Backtrace quan trọng?
Trong production, khi DBA thấy slow query, câu hỏi đầu tiên là: “Service nào gọi query này?” Backtrace trả lời ngay — không cần grep logs.

🔗 Fundamentals: Ch.01 — Database in context. Database performance ảnh hưởng trực tiếp đến application performance. Query time = phần lớn latency trong data-heavy apps.

Từ service page, tìm các analysis options:

Exception analysisGrouped exceptions by type

6.2. Exception analysis

  1. Mở Exception analysis cho 1 service
  2. Xem grouped exceptions:
    • Exception type (NullPointerException, SqlException, …)
    • Count — bao nhiêu lần xảy ra
    • Affected requests

💡 EasyTrade trong trạng thái “healthy” vẫn có thể có exceptions — đây là bình thường cho production apps. Distinction quan trọng: exception ≠ failure. Nhiều exceptions được handled gracefully.

Không thấy services

  • EasyTrade loadgen cần thời gian tạo traffic
  • Kiểm tra: docker compose logs loadgen --tail 10
  • Chờ 5-10 phút sau khi start
