Câu hỏi 1 — Synthetic monitor detection scenario

Which scenario is a synthetic monitor particularly good at detecting?

  • A. A slow SQL query that shows up only when concurrent sessions spike above a certain threshold
  • B. A broken authentication flow that has already been triggering bounces from thousands of real users in production
  • C. An outage at 3 in the morning in a region with no real traffic, which no real user would hit for hours
  • D. A privacy-law violation in how visitor PII is stored inside the backend database

💡 Đáp án & Giải thích

✅ Đáp án đúng: C

#Kết quảGiải thích
A❌Concurrency-driven slowness được phát hiện qua APM/traces dưới tải thực, không phải từ một synthetic probe nhỏ.
B❌Real-user bounces là tín hiệu RUM. Giá trị của Synthetic là phát hiện sự cố trước khi real user gặp phải.
C✅Đây là use case kinh điển của Synthetic: phát hiện sớm ngoài giờ làm việc hoặc ở region có ít/không có traffic thực.
D❌Synthetic không kiểm tra storage hay xử lý PII. Compliance nằm ngoài phạm vi của nó.

Giải thích tổng thể:
Synthetic tỏa sáng như một heartbeat trong các khung giờ ít traffic, ở các region muốn test chủ động, và trước khi launch khi chưa có real traffic.

Liên kết: Synthetic Monitoring · RUM · DEM

Câu hỏi 2 — JavaScript errors in RUM

Which statement about JavaScript errors in RUM is correct?

  • A. RUM aggregates JavaScript errors only at monthly boundaries and does not report individual occurrences
  • B. Errors are stored only on the visitor’s machine and are not transmitted back to the Dynatrace tenant
  • C. JavaScript errors are tracked server-side by OneAgent and never sent from the browser itself
  • D. RUM captures uncaught JavaScript exceptions, including a stack trace when one is available
  • E. RUM only captures errors explicitly logged via console.error; thrown exceptions are ignored

💡 Đáp án & Giải thích

✅ Đáp án đúng: D

#Kết quảGiải thích
A❌Errors được báo cáo per occurrence với context, không chỉ aggregate theo tháng. Mỗi uncaught error mang session attribution riêng.
B❌Nếu error chỉ ở trên thiết bị visitor thì không hữu ích. RUM agent gửi chúng về Dynatrace.
C❌JavaScript chạy ở browser, nên error phải được observe ở browser. OneAgent trên server không thể thấy chúng.
D✅Đúng. Uncaught errors được thu thập cùng stack trace khi browser cung cấp.
E❌Exceptions được capture. RUM hook vào window errors, không chỉ console output.

Giải thích tổng thể:
RUM capture uncaught JavaScript exceptions từ browser, đính kèm stack và context khi có, và gửi về Dynatrace để correlation với user actions.

Liên kết: RUM · OneAgent · JavaScript Errors

Câu hỏi 3 — Session Replay privacy controls

Which of the following are legitimate Session Replay privacy controls? (Select all that apply)

  • A. A forced consent banner that the RUM agent injects into the page before any events are captured
  • B. Automatic overwrite of the visitor’s session cookie each time a replay is produced
  • C. Allow-list and block-list rules that decide which URLs are even eligible to produce a replay
  • D. Masking rules that hide text or entire elements so sensitive fields are never captured in the replay
  • E. A setting that prevents the visitor’s IP address from being stored alongside the replay data

💡 Đáp án & Giải thích

✅ Đáp án đúng: C, D

#Kết quảGiải thích
A❌RUM agent không inject consent banner vào site của khách hàng. Disclosure wording là trách nhiệm của khách hàng trong privacy notice của họ.
B❌Dynatrace không rewrite session cookie của visitor. Replay là server-side artefact; client session state không bị modify bởi replay feature.
C✅Đúng. Recording có thể bị giới hạn cho specific URLs hoặc explicitly excluded khỏi các URL khác.
D✅Đúng. Masking là safeguard chính cho payment inputs, personal identifiers, hoặc health data.
E❌IP suppression không phải primary Session Replay privacy control. Masking và URL allow-listing là các safeguard chính; IP handling là tenant-level setting riêng.

Giải thích tổng thể:
Các privacy knob thực sự của Session Replay là masking (cái gì được capture bên trong replay) và URL allow/block rules (replay có được capture hay không).

Liên kết: Session Replay · RUM · Privacy Controls

Câu hỏi 4 — Mobile RUM data collection

Which of the following are valid ways Dynatrace collects RUM data from native mobile apps? (Select all that apply)

  • A. Custom instrumentation calls developers add through the mobile agent API to report domain-specific actions
  • B. An iOS SDK compiled into the app build that reports user actions, crashes, and network calls
  • C. A reverse proxy in front of the mobile backend that tags requests with session identifiers
  • D. An Android SDK compiled into the app build that reports user actions, crashes, and network calls
  • E. An MDM-managed profile that captures in-app telemetry through the device’s operating system APIs

💡 Đáp án & Giải thích

✅ Đáp án đúng: A, B, D

#Kết quảGiải thích
A✅Đúng. Agent expose API để team có thể record business actions như checkout step hoặc quote accept.
B✅Dynatrace iOS agent là đường chính thức cho native iOS apps; hook vào tại build time.
C❌Backend-side request tagging không phải mobile RUM. Mobile RUM phải observe device trực tiếp qua compiled SDK.
D✅Đúng. Android counterpart hoạt động tương tự và được thêm vào tại build time.
E❌Mobile RUM dựa vào Dynatrace SDK compiled vào app, không phải MDM profiles. OS-level device management không expose in-app action data.

Giải thích tổng thể:
Mobile RUM là build-time SDK (iOS hoặc Android) cộng thêm optional custom actions mà app code report qua agent API.

Liên kết: Mobile RUM · iOS SDK · Android SDK · RUM

Câu hỏi 5 — DEM consumption metering

How does Dynatrace typically meter DEM consumption?

  • A. Purely by CPU time used on OneAgents running inside the customer’s environment
  • B. Every byte of RUM data is charged at a linear rate on top of the core licensing line
  • C. Per synthetic monitor, with RUM and Session Replay billed together as a single static fee
  • D. A flat per-seat fee based on how many developers can log in to the Dynatrace tenant
  • E. In DEM units, with different session and monitor types consuming different unit counts

💡 Đáp án & Giải thích

✅ Đáp án đúng: E

#Kết quảGiải thích
A❌OneAgent CPU usage không phải billing dimension cho DEM.
B❌Byte-based metering được dùng ở phần khác của platform, không phải headline DEM unit.
C❌RUM và synthetic được metered riêng. Chúng không gộp vào một static fee.
D❌Seat-based pricing không phải cách DEM được metered. DEM usage phụ thuộc vào sessions, synthetic runs, và replays, không phải số người đăng nhập.
E✅Đúng. DEM units là mô hình metering: sessions, Session Replays, và synthetic runs mỗi loại tiêu thụ một số unit đã cấu hình.

Giải thích tổng thể:
DEM được metered bằng DEM units: real-user sessions, Session Replays, và synthetic runs mỗi loại tốn một số unit biết trước. Bạn theo dõi consumption so với allocation như bất kỳ metered resource nào khác.

Liên kết: DEM Units · RUM · Synthetic Monitoring · Session Replay

Câu hỏi 6 — Business events from RUM session

Why would a team emit business events from a RUM session?

  • A. Offloading some APM instrumentation from the server side to the RUM layer so the backend agent can run in a lighter-weight configuration
  • B. Attaching domain-specific facts (cart value, plan type, outcome) to the session in a structured way
  • C. Reducing RUM data volume by dropping user actions that did not lead to a business outcome
  • D. Feeding a live signal into Dynatrace autoscaling so infrastructure decisions can respond to session-level behaviour as it happens
  • E. Satisfying a licensing check inside OneAgent that only fires when a business event is present

💡 Đáp án & Giải thích

✅ Đáp án đúng: B

#Kết quảGiải thích
A❌Business events từ RUM không giảm server-side APM instrumentation. Server-side tracing và RUM business events là complementary layers, không thay thế nhau.
B✅Đúng. Business events là cách có cấu trúc để gắn những gì Dynatrace thấy với những gì quan trọng về mặt thương mại.
C❌Business events thêm data, không bớt. Chúng không drop user actions.
D❌Business events không phải autoscaling input. Mục đích của chúng là annotate session với domain facts để phân tích phong phú hơn, không phải drive infrastructure decisions real-time.
E❌OneAgent không gate bản thân sau business events. Không có licensing check như vậy.

Giải thích tổng thể:
Business events làm RUM sessions hữu ích cho phân tích: thay vì “user bounced from checkout”, bạn có thể thấy “a gold-tier customer with a large cart bounced after payment step 2”.

Liên kết: Business Events · RUM · OneAgent

Câu hỏi 7 — RUM visitor origin metadata

Which of the following does RUM expose out of the box about where users are coming from?

  • A. A per-visitor identity token generated by a signed-in authentication provider and attached to every session
  • B. The visitor’s full user agent stored together with their email address from the last-known login
  • C. Only a session ID, with no geographic or client metadata attached to it whatsoever
  • D. Country, region, and city derived from the visitor’s IP, plus browser and device information

💡 Đáp án & Giải thích

✅ Đáp án đúng: D

#Kết quảGiải thích
A❌Identity joins là opt-in và cần explicit setup. RUM không gắn authentication-provider token vào sessions mặc định.
B❌RUM không join sessions với email addresses mặc định. User-identifying joins cần explicit configuration trên tenant.
C❌Có nhiều context hơn thế: geo, browser, device, và network information đều visible.
D✅Country, region, city, browser, và device là standard metadata mà RUM agent và tenant enrichment cung cấp.

Giải thích tổng thể:
RUM thêm country, region, city, browser, device, và network metadata vào mỗi session, derived từ IP và user-agent data tại ingest.

Liên kết: RUM · Session Metadata · Geo Location

Câu hỏi 8 — Mobile agent capabilities

What does the Dynatrace mobile agent add on top of basic RUM for native apps?

  • A. It blocks the app from launching if the user’s OS version is behind by one point release
  • B. User actions, crashes with stack traces, and network requests are recorded from inside the app
  • C. Runtime rewriting of the app’s binary adds new product features that were not built into the release
  • D. Every other analytics SDK must be removed from the project before the Dynatrace agent will run

💡 Đáp án & Giải thích

✅ Đáp án đúng: B

#Kết quảGiải thích
A❌Agent không bao giờ block app. Đó sẽ là default behaviour tệ.
B✅Đúng. Actions, crashes với traces, và outgoing HTTP calls là core capture set.
C❌Agent instrument; nó không inject new product features. Điều đó nằm ngoài scope và rủi ro.
D❌Dynatrace coexist với các SDK khác. Nó không force removal bất kỳ thứ gì.

Giải thích tổng thể:
Mobile agent cho bạn user actions, crashes với stack traces, và network timings, joined back vào phần còn lại của platform bằng entity IDs.

Liên kết: Mobile RUM · Mobile Agent · Crash Analysis

Câu hỏi 9 — User action experience classification

How does Dynatrace classify the experience of a user action in RUM?

  • A. Pass, warn, fail, fatal, hard-fail, based only on the HTTP status code of the underlying call
  • B. Satisfied, tolerating, frustrated, based on how long the action took and whether it hit errors
  • C. Approved, suspicious, blocked, because the product uses the same model as an anti-fraud tool
  • D. A numeric score between zero and one, derived only from the HTTP response size of each request
  • E. Green, yellow, orange, red, purple, using a fixed threshold configured only at the server side

💡 Đáp án & Giải thích

✅ Đáp án đúng: B

#Kết quảGiải thích
A❌Status codes đơn thuần không mô tả UX. Một response 200 mất 8 giây vẫn là trải nghiệm tệ.
B✅Đúng. Ba label này đến từ Apdex-style bands mà Dynatrace áp dụng cho user actions.
C❌RUM không phải fraud tool. Labels mô tả perceived experience, không phải risk.
D❌Response size đơn thuần không mô tả experience. Apdex-style bands dựa trên duration và errors, không phải payload size.
E❌Không có five-colour grading như vậy trong RUM. Thresholds là per-action, và labels là satisfied, tolerating, frustrated.

Giải thích tổng thể:
User actions rơi vào satisfied, tolerating, hoặc frustrated, derived từ duration cộng với bất kỳ errors nào action gặp phải.

Liên kết: RUM · Apdex · User Actions

Câu hỏi 10 — RUM user-action types

Which of the following are user-action types RUM can report on? (Select all that apply)

  • A. API calls that administrators make to the Dynatrace tenant from their own scripts
  • B. Page loads and route changes inside single-page apps
  • C. Pod restarts that a platform engineer triggers on the underlying Kubernetes cluster
  • D. Tenant configuration changes applied inside the Dynatrace Settings area
  • E. XHR and fetch calls initiated from the page
  • F. Custom user actions the developer fires through the RUM API to represent domain events

💡 Đáp án & Giải thích

✅ Đáp án đúng: B, E, F

#Kết quảGiải thích
A❌API calls tới tenant là administrator activity, không phải end-user activity. RUM chỉ report trên những gì real visitors làm trên monitored app.
B✅Đúng. Classic loads và SPA route changes đều được nhận diện.
C❌Pod restarts là infrastructure events, không phải user actions. Chúng thuộc Infrastructure Monitoring, không phải RUM.
D❌Configuration changes trong tenant là audit events, không phải RUM user actions. RUM observe end-user behaviour trên monitored app.
E✅Đúng. RUM track AJAX-style calls với timing và status.
F✅Custom actions cho phép capture những thứ như quote confirmation không chỉ là clicks.

Giải thích tổng thể:
Loads, XHR/fetch, và custom actions là ba user-action families mà RUM được xây dựng xung quanh.

Liên kết: RUM · User Actions · SPA Monitoring · XHR

Câu hỏi 11 — RUM JavaScript auto-injection

When OneAgent injects the RUM JavaScript automatically, what mechanism does it typically use?

  • A. OneAgent silently proxies all outbound traffic and rewrites it mid-flight before it reaches the browser
  • B. OneAgent on the web server modifies outgoing HTML so the response carries the RUM script tag
  • C. A CDN operated by Dynatrace inlines the script on the way back to any requesting client
  • D. The browser downloads a helper extension, and that extension pulls the RUM script in afterwards

💡 Đáp án & Giải thích

✅ Đáp án đúng: B

#Kết quảGiải thích
A❌OneAgent không đứng trước wire như proxy. Injection xảy ra bên trong response path của web server, không phải trên network.
B✅Đúng. Với auto-injection enabled, OneAgent amend responses ở web-server side để mỗi page được serve mang tag.
C❌Dynatrace không đứng giữa làm man-in-the-middle CDN cho customer traffic. Injection được thực hiện server-side bởi OneAgent.
D❌Visitors không cài thêm gì. RUM tag phải đến cùng với original HTML.

Giải thích tổng thể:
Auto-injection là server-side behaviour: OneAgent amend HTML khi nó rời web server để visitors nhận được tagged page.

Liên kết: OneAgent · RUM · Auto-Injection

Câu hỏi 12 — Private synthetic location

To run synthetic monitors from inside your own network, which Dynatrace component do you deploy?

  • B. Davis AI worker pods scheduled onto an internal namespace
  • C. OneAgent installed on every target application host

#Kết quảGiải thích
A❌Grail là data lakehouse, không phải execution node. Nó không chạy probes.

C❌OneAgent observe app từ bên trong host. Nó không chạy synthetic checks từ bên ngoài.

Private synthetic locations chạy trên ActiveGate bạn deploy. ActiveGate là thành phần thực sự chạy HTTP calls hoặc headless browser bên trong network của bạn.

Câu hỏi 13 — DEM primary concern

What is Dynatrace Digital Experience Monitoring primarily concerned with?

  • A. How real visitors and synthetic checks perceive the front end, from page load to click-through
  • B. The health of backend microservices and the database tier that sit behind the user-facing layer
  • C. Firewall rule changes and perimeter routing decisions managed by the network team
  • D. Container resource limits and node pressure inside the Kubernetes platform where the app runs

💡 Đáp án & Giải thích

✅ Đáp án đúng: A

#Kết quảGiải thích
A✅Đúng. DEM kết hợp Real User Monitoring, Synthetic Monitoring, và Session Replay xung quanh UX side của stack.
B❌Phần đó thuộc APM và Smartscape. DEM ở xa hơn, tại browser, mobile, và synthetic-probe layer.
C❌Network policy changes nằm ngoài phạm vi DEM. DEM mô tả những gì xảy ra khi request đã đến app.
D❌Node và pod pressure hiển thị trong Infrastructure Monitoring. DEM scoped tới experience mà user thực sự nhận được.

Giải thích tổng thể:
Digital Experience Monitoring là user-facing layer của platform: RUM cho real sessions, Synthetic cho scheduled checks, Session Replay cho visual recordings, joined vào phần còn lại của topology.

Liên kết: DEM · RUM · Synthetic Monitoring · Session Replay · Smartscape

Câu hỏi 14 — Largest Contentful Paint

What does Largest Contentful Paint (LCP) measure?

  • A. Engagement time: how long the visitor kept interacting with the page after it had loaded
  • B. The instant the very first byte of the HTML response arrives at the browser
  • C. The point where the largest visible content element in the viewport finishes rendering
  • D. Load-event-end, i.e. the moment every request for the page has finished, including any late tracking pixel

💡 Đáp án & Giải thích

✅ Đáp án đúng: C

#Kết quảGiải thích
A❌Dwell time hoặc engagement, không phải LCP. LCP nói về load phase, không phải interaction phase.
B❌TTFB, không phải LCP. LCP xảy ra muộn hơn nhiều trong quá trình load, sau layout và main content rendering.
C✅Đúng. LCP là perceived-performance metric tập trung vào khi nào main content trở nên visible.
D❌Gần với load-event-end, không phải LCP. LCP nói về visible content, không phải mọi request hoàn thành.

Giải thích tổng thể:
LCP là thời điểm phần tử nội dung visible lớn nhất hoàn thành painting. Đây là headline metric của Google cho mức độ nhanh mà page cảm thấy khi load.

Liên kết: LCP · Core Web Vitals · RUM · Performance Metrics

Câu hỏi 15 — Synthetic Monitoring purpose

What is the point of Synthetic Monitoring?

  • A. Generating peak load against production during business hours to stress capacity
  • B. Crawling every public page of the site to build a search index for end-user queries
  • C. Running scheduled checks so the service is measured even when real traffic is low or absent
  • D. Replacing real user traffic so the application does not need to serve actual customers anymore

💡 Đáp án & Giải thích

✅ Đáp án đúng: C

#Kết quảGiải thích
A❌Đó là load test. Synthetic là small, paced traffic thiết kế để representative, không phải heavy.
B❌Full-site crawling và indexing thuộc search-engine tooling. Synthetic chạy một số ít scheduled checks để đo availability và performance.
C✅Đúng. Synthetic cho bạn heartbeat cho app overnight, ở market mới, hoặc trước launch.
D❌Synthetic không bao giờ thay thế real traffic. Nó bổ sung cho nó.

Giải thích tổng thể:
Synthetic Monitoring là scheduled, automated, outside-in checks: nó cho bạn biết service đang up và hoạt động ra sao, độc lập với lượng real traffic hiện có.

Liên kết: Synthetic Monitoring · RUM · DEM

Câu hỏi 16 — Synthetic monitor capture

Which of the following does a Dynatrace synthetic monitor typically capture? (Select all that apply)

  • A. Response status codes for each step of the monitor’s run
  • B. End-to-end duration of the run, broken down by step
  • C. Availability from each location the monitor was scheduled to run from
  • D. A visual screenshot on failure for browser clickpath monitors
  • E. The full list of concurrent real-user sessions active during the probe’s execution
  • F. A rolling average of real visitor satisfaction during the window of the synthetic run

💡 Đáp án & Giải thích

✅ Đáp án đúng: A, B, C, D

#Kết quảGiải thích
A✅Status per step là phần core mà synthetic run assert.
B✅Per-step timing cho thấy phần nào của clickpath bị regress.
C✅Availability được track theo từng location — cách nhìn thấy regional outage.
D✅Clickpath capture screenshot on failure để thấy browser thực sự nhìn thấy gì.
E❌Synthetic không enumerate concurrent real-user sessions. Session counts là RUM analytic, không phải synthetic capture field.
F❌Synthetic không observe real visitors; nó chạy scripted probe riêng. Visitor satisfaction là RUM metric, không phải synthetic.

Giải thích tổng thể:
Synthetic monitors capture step-level status, per-step timings, screenshots on failure (cho browser), và per-location availability. Chúng không capture real-user personal data.

🎯 DEM Overview

  • DEM = Real User Monitoring (RUM) + Synthetic Monitoring + Session Replay
  • Primary concern: cách real visitors và synthetic checks cảm nhận front end — từ page load đến click-through
  • ❌ KHÔNG phải: backend microservices, firewall rules, container resource limits
  • Metering: DEM units — mỗi session type, replay, synthetic run tiêu thụ số units khác nhau

👤 Real User Monitoring (RUM)

Collection mechanism

  • Browser RUM: JavaScript snippet (RUM JS agent) loaded cùng page
    • Auto-injection: OneAgent trên web server amend HTML outgoing response
    • Manual: thêm tag trực tiếp vào HTML
  • Mobile RUM: iOS SDK + Android SDK compiled vào app build
    • Custom actions qua mobile agent API (e.g. checkout step, quote accept)

User actions captured

  • ✅ Page loads và SPA route changes
  • ✅ XHR và fetch calls (AJAX)
  • ✅ Custom user actions (qua RUM API)
  • ❌ KHÔNG: pod restarts, API calls tới tenant, configuration changes

User action experience classification (Apdex-style)

LabelÝ nghĩa
SatisfiedAction hoàn thành nhanh, không lỗi
ToleratingAction hơi chậm hoặc có vấn đề nhỏ
FrustratedAction quá chậm hoặc có lỗi

Session definition

  • Series of user actions từ một visitor, grouped trong khi active
  • Inactivity timeout kết thúc session — không phải tab close hay login/logout

Out-of-box metadata

  • Country, region, city (từ IP), browser và device information
  • ❌ KHÔNG có sẵn (cần config thêm): email address, auth-provider token

JavaScript errors

  • Capture uncaught exceptions + stack trace khi browser cung cấp
  • Hook vào window.onerror — không chỉ console.error

Core Web Vitals trong RUM

MetricĐo gì
LCP (Largest Contentful Paint)Khi phần tử nội dung visible lớn nhất hoàn thành render
CLS (Cumulative Layout Shift)Visual instability — layout jump bất ngờ
INP (Interaction to Next Paint)Responsiveness tương tác (thay FID)
  • Navigation timing: dựa trên W3C Navigation Timing API (DNS, TCP, TTFB, DOM events)

Business events từ RUM

  • Mục đích: attach domain-specific facts (cart value, plan type, conversion outcome) vào session
  • ❌ KHÔNG: giảm server-side APM, drop user actions, drive autoscaling

Conversion funnel

  • Ordered steps over user actions hoặc business events với drop-off measurement

🤖 Synthetic Monitoring

Khi nào dùng Synthetic?

  • Phát hiện outage ở region không có real traffic (3am, new market)
  • Proactive check trước khi real user gặp phải
  • Scheduled heartbeat khi traffic thấp hoặc không có
  • ❌ KHÔNG: load testing, web crawling, thay real traffic

Monitor types

TypeUse case
HTTP monitorSingle URL/API check — status code + payload verification
Browser (clickpath) monitorMulti-step scripted journey trong real headless browser

Capture per synthetic run

  • ✅ Response status codes per step, End-to-end duration, Availability per location, Screenshot on failure (browser)
  • ❌ KHÔNG: concurrent real-user sessions, visitor satisfaction metrics

Locations

TypeOperated by
PublicDynatrace-hosted globally
PrivateCustomer-operated ActiveGate — để probe internal/firewalled services

Synthetic vs RUM

  • Complementary: Synthetic = outside-in check (heartbeat); RUM = first-person real user data
  • Session Replay chỉ gắn với RUM sessions — KHÔNG phải synthetic runs

🎬 Session Replay

  • Là gì: DOM-level visual playback của clicks, scrolls, form entries của visitor
  • Không phải: packet replay, traffic generator, server-side trace replay
  • Privacy controls: URL allow-list/block-list + masking rules (ẩn text/elements nhạy cảm)

📱 Mobile

  • Mobile agent: user actions, crashes với stack traces, network requests
  • Crash de-obfuscation: iOS = dSYM files; Android = mapping.txt / ProGuard mapping

⚡ Các điểm hay nhầm lẫn

  • RUM ≠ Synthetic — RUM = real visitors; Synthetic = scripted probes
  • RUM không cho SQL query details (phải kết hợp APM/traces)
  • HTTP monitor ≠ Browser monitor — HTTP cho single URL; browser cho multi-step JS journey
  • LCP ≠ TTFB (TTFB = first byte; LCP = largest visible element render)
  • Session = activity-bounded, không phải tab lifetime hay auth session
  • DEM units meter theo session/replay/synthetic run — không phải byte hay CPU
