Câu hỏi 1 — OpenPipeline ingest sources

Which of the following data sources can OpenPipeline ingest from? (Select all that apply)

  • A. OneAgent-collected signals such as host metrics, logs, and events
  • B. OpenTelemetry data arriving through OTLP and routed into Grail by the pipeline
  • C. External webhook sources such as SDLC events from GitHub or GitLab
  • D. Third-party APIs called by extensions or pulled on a schedule into the tenant
  • E. Database binlogs tailed in real time from a customer-managed PostgreSQL primary, with no agent or API layer
  • F. SNMP traps collected directly from network switches over UDP, without any intermediate forwarder

💡 Đáp án & Giải thích

✅ Đáp án đúng: A, B, C, D

#Kết quảGiải thích
A✅Agent-produced data flows through OpenPipeline into Grail.
B✅OTLP là core supported source; OpenPipeline configure bước tiếp theo.
C✅Webhook ingestion là first-class path cho SDLC và business events.
D✅API-driven ingest cho sources không tự push data.
E❌Direct binlog tailing không phải OpenPipeline capability. DB signals qua extensions, logs, hoặc OTLP.
F❌SNMP trap ingestion không phải first-class OpenPipeline source. Network telemetry thường qua extension framework.

Giải thích tổng thể:
OpenPipeline ingest từ agents, APIs, webhooks, và OTLP — single configurable door data vào Grail.

Liên kết: OpenPipeline · Grail · OneAgent · OpenTelemetry

What is the main role of Site Reliability Guardian (SRG) in Dynatrace?

💡 Đáp án & Giải thích

✅ Đáp án đúng: D

#Kết quảGiải thích
A❌Access control là IAM/RBAC. SRG là release evaluation, không phải permission layer.
B❌Data shaping at ingest là OpenPipeline. SRG không transform telemetry.
C❌Agent deployment là Operator/deployment tooling — tách khỏi SRG.
D✅SRG là gate “release looks safe” dựa trên SLOs, errors, performance platform đã có.
E❌SRG không phải dashboard library — là release và change guard.

Giải thích tổng thể:
SRG là automated quality gate cho releases/changes — evaluate signals đã collect và cho pass/fail pipeline.

NOTE

Phần này tổng hợp các điểm kiến thức cốt lõi được rút ra từ toàn bộ câu hỏi trong file. Dùng để ôn nhanh trước khi thi.

🔄 OpenPipeline — Ingestion & Processing Layer

  • Định nghĩa: configurable ingestion và processing layer chuẩn bị data cho Grail
  • Vị trí: nằm TRƯỚC Grail — nhận data IN, process, route vào đúng bucket
  • Không phải: dashboard builder, storage layer, OneAgent replacement

Ingest sources được hỗ trợ:

  • ✅ OneAgent signals (metrics, logs, events)
  • ✅ OpenTelemetry / OTLP
  • ✅ Webhooks (SDLC events từ GitHub, GitLab)
  • ✅ Third-party APIs (extension-driven hoặc pull-scheduled)
  • ❌ KHÔNG: direct database binlogs, raw SNMP traps không qua forwarder

Processing rules use cases:

  • ✅ Mask PII trước khi persist vào Grail (at ingest — không phải query time)
  • ✅ Normalize schemas giữa các source heterogeneous → DQL queries đơn giản hơn
  • ✅ Route: security logs → long-retention bucket; dev logs → short-retention bucket
  • ✅ Sample high-volume data, drop low-value events
  • ❌ KHÔNG thay authentication, KHÔNG tự tạo dashboards

SDLC webhooks:

  • Events từ GitHub qua webhook → OpenPipeline → Grail (events/SDLC dataset)
  • Queryable bằng DQL, dùng trong Workflows và dashboards
  • HTTP 401 on webhook = authentication missing/invalid (bad token, misconfigured auth header)

⚙️ Workflows — Automation Engine

Workflow = Tasks + Transitions

  • Task: single executable step — DQL query, HTTP request, Slack, Jira, ServiceNow…
  • Transitions: conditional branches quyết định flow tiếp theo dựa trên task output

Trigger types:

TypeMô tả
Event/Problem triggerDavis mở problem → workflow fire
Scheduled triggerCron-style cadence (daily report, weekly cleanup)
Manual triggerUser start từ UI với sample payload
❌ Query-timeDQL query KHÔNG trigger workflow
❌ Dashboard openRendering UI KHÔNG trigger

Design patterns:

PatternDùng cho
Parallel branchesHai tasks độc lập chạy đồng thời
For-each / LoopCùng task lặp trên list (services, entities, tickets)
Conditional transitionsBranch dựa trên output của task trước (e.g. DQL error rate)
Retry configChống transient failures (network blip, temporary 5xx)
DeduplicationAct only on first occurrence of problem (condition + timebox)

Jinja templating:

  • Inject dynamic strings và JSON payloads từ variables + previous task outputs
  • Dùng cho: problem IDs, entity names, metric values → Slack messages, Jira tickets, HTTP bodies
  • ❌ KHÔNG: security primitive, service discovery

Security best practices:

  • API token scopes: least-privilege — chỉ scope mà workflow thực sự cần
  • Secrets: lưu trong Dynatrace credential mechanism, reference by ID — KHÔNG hard-code, KHÔNG base64 encode
  • Testing: non-production environment + manual trigger + sample payload → arm real triggers sau

Execution history:

  • Audit trail: mỗi run, inputs, outputs, final status per task
  • ❌ KHÔNG thay Grail telemetry store

📊 SLO — Service Level Objectives

SLO definition = 3 thành phần:

  1. SLI (Service Level Indicator): thứ đo — fraction of successful requests
  2. Objective: target — e.g. 99.9%
  3. Evaluation window: rolling 7-day, 28-day…

Sound SLO alerting practices:

  • ✅ Burn-rate windows (short + long) — bắt fast regression VÀ slow leak
  • ✅ Supporting context (error-rate trends, release markers) → actionable alerts
  • ❌ KHÔNG: flat compliance threshold (bỏ qua burn rate)

🛡️ Site Reliability Guardian (SRG)

  • Vai trò: automated quality gate cho releases/changes
  • Evaluate: SLOs, error rate, performance — cho pass/fail vào pipeline
  • Kết hợp với Workflows: SRG guard fails → trigger Workflows rollback/notification/remediation
  • ❌ KHÔNG phải: permission layer, data converter, dashboard library

📍 Release Markers

  • Ingest deploy/PR merge events vào Dynatrace
  • Benefits:
    • ✅ Audit trail joined với Davis problems trên timeline
    • ✅ Correlate performance/reliability shifts với specific deployments

🔁 End-to-End Pattern

Signals → Grail (qua OpenPipeline)
    → Davis AI / DQL (detect/evaluate)
    → Workflows (notify/remediate)
  • Canonical shape: Ingest → Reason → Act
  • Impacted services trong problem: dùng Smartscape topology (live entity relationships)

⚡ Các điểm hay nhầm lẫn

  • Base64 ≠ encryption — KHÔNG dùng để “bảo vệ” secrets
  • Retry ≠ deduplication — retry cho transient errors; deduplication cho repeated triggers
  • Parallel branches ≠ loops — parallel = concurrency; loop = sequential iteration trên list
  • PII masking phải ở ingest (OpenPipeline) — không phải query time hay Workflow task
  • SRG + Workflows = complementary, không phải thay thế nhau
  • DQL query KHÔNG trigger workflows — chỉ là read operation
  • HTTP 401 = auth problem (không phải payload schema, không phải agent version)
