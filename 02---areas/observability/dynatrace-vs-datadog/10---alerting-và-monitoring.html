Alerting và Monitoring

1. Triết lý Alerting

Khía cạnhDynatraceDatadog
ApproachAI-first — Davis tự detect, consolidate, alertMonitor-first — user tạo monitors cho từng condition
DefaultTự phát hiện problems (zero config)Không alert gì cho đến khi user tạo monitor
ConsolidationDavis gộp 20 events → 1 ProblemUser tạo Composite Monitor hoặc Watchdog groups
Root causeProblem card = root cause + impactUser investigate từ monitor alert

Khác biệt cốt lõi

Dynatrace: “Cài OneAgent → Davis tự detect + alert → on-call nhận 1 notification rõ root cause”
Datadog: “Cài Agent → user phải tạo Monitor cho từng condition → config notification rules”

2. Alerting Flow — So sánh

Dynatrace

graph LR
    A["Davis detects anomaly"] --> E["Event<br/>(1 trong 7 categories)"]
    E --> C["Davis Consolidation<br/>(gộp related events)"]
    C --> P["Problem Card<br/>(root cause identified)"]
    P --> AP["Alerting Profile<br/>(filter severity/tags/MZ)"]
    AP --> N["Notification<br/>(PagerDuty, Slack...)"]
  • Alerting Profile = bộ lọc, quyết định Problem nào được gửi notification
  • Filter bằng: severity, Management Zone, tag, event type
  • Nhiều Alerting Profiles cho nhiều teams

Datadog

graph LR
    M["Monitor evaluates<br/>metric/log/trace"] --> S["State change<br/>(OK→Warn→Alert)"]
    S --> N["Notification<br/>(theo monitor config)"]
    N --> T["@team-backend<br/>@pagerduty-oncall"]
  • Monitor = 1 unit of monitoring — user define metric + condition + notification
  • Mỗi monitor có own lifecycle: OK → Warn → Alert → No Data
  • Notification trong monitor config (@slack-channel, @pagerduty)

EXAM TRAP — No Data state

Monitor states: OK → Warn → Alert → No Data
No Data ≠ metric = 0. No Data nghĩa là agent ngừng gửi data (agent crash, network issue, host down).
Phải config notify_no_data trong monitor để alert khi metric biến mất.

Exam keyword mapping

  • “Fixed threshold” → Metric Threshold
  • “Seasonal patterns” → Anomaly Monitor
  • “Proactive / will happen” → Forecast Monitor
  • “Peers / one server different” → Outlier Monitor
  • “Multiple conditions AND/OR” → Composite Monitor
  • “Reduce false positives” → Composite Monitor (AND logic)

4. SLO (Service Level Objectives)

Chuỗi khái niệm

SLI (Service Level Indicator) → SLO (target) → SLA (customer commitment) → Error Budget
ConceptMô tảVí dụ
SLIMetric đo service qualityAvailability %, Latency p99
SLOTarget internal cho SLI99.9% availability over 30 days
SLACommitment cho customer (hợp đồng)99.5% uptime (penalty nếu vi phạm)
Error Budget100% - SLO = allowed downtime99.9% → 43.2 phút/30 ngày

Chuỗi SLI → SLO → SLA → Error Budget

  • SLI (Indicator): metric đo lường quality — chọn metric nào?
  • SLO (Objective): target nội bộ — bao nhiêu % acceptable?
  • SLA (Agreement): cam kết với customer — penalty nếu vi phạm
  • Error Budget = 100% - SLO target = thời gian/lượng lỗi cho phép
  • Khi error budget cạn → freeze deployments, focus reliability
  • Error budget burn rate alert: cảnh báo khi budget bị tiêu nhanh hơn bình thường

Dynatrace SLO

  • Tạo trong SLO App
  • Based on: metric expression hoặc DQL query
  • Visualize trong Dashboard tiles
  • Alert khi burn rate cao (nhưng không native SLO alert type)

Datadog SLO — 3 Types

TypeTính SLO như thế nàoUse case
Metric-basedGood events / Total events (count-based, tỷ lệ)API success rate, latency thresholds
Monitor-based% time monitors KHÔNG ở ALERT state (time-based)Service availability
Time Slice% time condition = true (time-based, define threshold trực tiếp trên metric, KHÔNG cần monitor)”% thời gian CPU < 90%“
# Ví dụ Metric-based SLO:
Numerator: count of requests with status:2xx
Denominator: count of ALL requests
Target: 99.9% over 30 days
→ Error budget: 0.1% = 43.2 minutes

SLO Features So sánh

FeatureDynatraceDatadog
SLO typesMetric + DQL based3 types (Metric, Monitor, Time Slice)
Error budget✅ Calculated✅ Calculated + burn rate alerts
SLO widgetDashboard tileSLO Widget (7d/30d/90d, color-coded)
Alert on SLO⚠️ Custom metric event✅ SLO Alert (native monitor type)
Rolling windowConfigurable7d / 30d / 90d

6. Notification Routing

Dynatrace — Alerting Profiles

Problem → Alerting Profile 1 (severity: CRITICAL, MZ: Production)
             → PagerDuty on-call
       → Alerting Profile 2 (severity: ALL, MZ: Staging)
             → Slack #staging-alerts
       → Alerting Profile 3 (tag: team:payments)
             → Email payments-team

Datadog — Monitor Notification

  • Conditional notification với {{#is_alert}}, {{#is_warning}}
  • Template variables: {{value}}, {{host.name}}, {{threshold}}

So sánh routing

FeatureDynatraceDatadog
Routing unitAlerting Profile (filter Problems)Per-monitor notification config
Filter bySeverity, Management Zone, tagsPer-monitor scope (tags in query)
ConditionalDifferent profiles for different teams{{#is_alert}} / {{#is_warning}} blocks
EscalationExternal (PagerDuty)External (PagerDuty)

7. Maintenance / Downtime

FeatureDynatrace Maintenance WindowDatadog Downtime
Option 1Detect + Alert (testing)❌
Option 2Detect, Don’t Alert✅ Mute notifications, still detect
Option 3Disable Detection completely❌ Không thể disable detection
ScopeEntities, Management ZonesTags, monitor groups
ScheduleOne-time + recurringOne-time + recurring

Khác biệt

Dynatrace cho phép disable detection hoàn toàn (cho major migrations).
Datadog chỉ mute notifications — monitors vẫn evaluate, chỉ không alert.
