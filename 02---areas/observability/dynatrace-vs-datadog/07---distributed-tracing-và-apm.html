Distributed Tracing và APM

1. Tổng quan Distributed Tracing

Cả 2 nền tảng đều implement distributed tracing theo cùng nguyên lý:

Request vào → Trace ID được tạo → propagate qua HTTP headers → mỗi service tạo Span → tree of Spans = 1 Trace
Khái niệmDynatraceDatadog
Distributed tracePurePathTrace
Một đơn vị công việcSpan (node trong PurePath)Span
VisualizationPurePath waterfall + SmartscapeFlame Graph (waterfall ngang)
Dependency mapSmartscape (auto-discovered topology)Service Map (auto-generated từ traces)
Context propagationx-dynatrace + W3C traceparent (auto)X-Datadog-Trace-Id + X-Datadog-Parent-Id (auto)

2. PurePath vs Flame Graph

Dynatrace PurePath

Browser (RUM) → API Gateway → Order Service → Payment Service → Bank API
    │                              │                │
    └── User Action               └── DB Call      └── External Call
  • End-to-end: từ browser (RUM) đến backend đến DB
  • Tự động — OneAgent inject context, không cần code changes
  • Mỗi node = 1 Span, bao gồm:
    • Method-level code profiling (Full-Stack mode)
    • SQL query text
    • HTTP request/response headers
    • Exception stack traces
  • PurePath detail retention: 10 ngày (Grail có thể extend). PurePath nay backed bởi Grail → spans queryable trực tiếp qua DQL

Datadog Flame Graph

┌─────────────────────────────────── Gateway (950ms) ──────────────────────────────────┐
│  ┌────────────────────────────── Order Service (900ms) ──────────────────────────────┐│
│  │  ┌──── DB Query (50ms) ───┐  ┌──────── Payment Service (500ms) ─────────────────┐││
│  │  └────────────────────────┘  │  ┌────────── Bank API Call (450ms) ──────────────┐│││
│  │                              │  └──────────────────────────────────────────────────┘│││
│  │                              └────────────────────────────────────────────────────────┘││
│  └──────────────────────────────────────────────────────────────────────────────────────────┘│
└──────────────────────────────────────────────────────────────────────────────────────────────┘
  • Horizontal bars: mỗi bar = 1 span, width = duration
  • Bar càng rộng = càng tốn thời gian = bottleneck
  • Xem ngay: Bank API Call (450ms) là bottleneck!
  • Cần ddtrace library trong app (auto-instrument frameworks)

Datadog SSI (Single Step Instrumentation)

  • Zero-code APM: auto-inject tracing SDK vào application qua Datadog Agent — KHÔNG cần thêm ddtrace library thủ công
  • Hỗ trợ: Java, Python, Ruby, Node.js, .NET, PHP
  • SSI ≠ USM:
    • SSI = in-process deep tracing (code-level spans, method profiling)
    • USM (Universal Service Monitoring) = network-level service health (eBPF-based, KHÔNG có code-level visibility)

Exam: SSI vs USM vs ddtrace

SSI = zero-code, deep tracing (giống OneAgent auto-inject). USM = network-level only. ddtrace = manual library integration.

So sánh trực quan

AspectDynatrace PurePathDatadog Flame Graph
View styleVertical waterfall (tree)Horizontal flame graph (timeline)
DepthCode-level (method profiling)Framework-level (HTTP, DB calls)
RUM correlation✅ Auto-link User Action → PurePathCần RUM SDK setup
DB queriesCaptured + analyzedCaptured (need DBM for deep analysis)
SetupZero-config (OneAgent)Add ddtrace library

3. Context Propagation

Headers so sánh

HeaderStandardDynatraceDatadog
Proprietary—x-dynatraceX-Datadog-Trace-Id, X-Datadog-Parent-Id, X-Datadog-Sampling-Priority
W3C✅ Standardtraceparent, tracestateSupported (configurable)
B3Zipkin legacySupportedSupported

Cả 2 đều hỗ trợ W3C Trace Context — standard cho interoperability. Trong practice:

  • Dynatrace mặc định dùng x-dynatrace + W3C
  • Datadog mặc định dùng proprietary headers, W3C cần bật

4. Sampling Strategies

Dynatrace — Adaptive Traffic Management

ApproachMô tả
AdaptiveDynatrace tự quyết định sampling rate dựa trên traffic volume
Always captureErrors và slow requests luôn được capture
PurePathTối đa số lượng PurePath per interval, ưu tiên diverse paths
  • Không cần config sampling thủ công
  • Davis AI tự điều chỉnh

Datadog — Ingestion Controls

ApproachMô tả
Head-based samplingQuyết định tại entry point (agent-side)
Default rateAgent tự tính target rate
Retention FiltersServer-side: Intelligent Retention Filter (auto, default) + custom tag-based filters cho high-priority traces
Custom rulesPer-service sampling rates

So sánh sampling

Khía cạnhDynatraceDatadog
DefaultAdaptive (tự động)Agent tự tính rate
ErrorsLuôn captureLuôn capture (Error tracking)
ConfigMinimal — Dynatrace quyết địnhGranular — per-service rules
Server-sideOpenPipeline filteringRetention Filters
Philosophy”Trust the platform""Give me control”

5. Service Detection & Topology

Dynatrace — Smartscape

graph TB
    subgraph "5 Layers"
        DC["Data Centers"]
        H["Hosts"]
        P["Processes"]
        S["Services"]
        A["Applications"]
    end
    DC --> H --> P --> S --> A
  • Auto-discovered — OneAgent scan processes, detect requests, build topology
  • Real-time — cập nhật liên tục
  • Entity IDs: HOST-xxx, SERVICE-xxx, PROCESS_GROUP-xxx
  • Smartscape timeframe: 72 giờ
  • Service identified by: context root + web server name + web application ID

Datadog — Service Map

graph LR
    subgraph "Auto-generated from traces"
        GW["API Gateway"] --> OS["Order Service"]
        OS --> PS["Payment Service"]
        OS --> DB["PostgreSQL"]
        PS --> BANK["Bank API"]
    end
  • Auto-generated từ traces (cần có traces để build map)
  • Annotations: request rate, error rate, latency per edge
  • Depends on Unified Service Tagging (service tag) cho accurate mapping
  • Không có concept “layers” như Smartscape

So sánh topology

FeatureDynatrace SmartscapeDatadog Service Map
SourceOneAgent discovery (process scan)Traces (APM data)
Layers5 layers (DC-H-P-S-A)Flat service graph
Infrastructure✅ Host, Process, DC layers❌ Service-level only
Real-time✅ Live topologyNear real-time (from traces)
No traffic = no data?❌ Smartscape shows topology even without requests✅ Service Map only shows services with traces
DepthProcess Group → Process Group InstanceService → Resources (endpoints)

Smartscape vs Service Map

Smartscape phát hiện topology từ process scan — thấy dependencies ngay cả khi KHÔNG có traffic.
Service Map build từ traces — cần có requests đi qua services mới thấy dependencies.

6. APM Features — So sánh

FeatureDynatraceDatadog
Response timeService → Response time (p50, p90, p95)APM → Latency (p50, p75, p90, p95, p99)
Error trackingProblem card → error analysisError Tracking → group similar errors
Database monitoringService → Database calls (from caller)DBM — Database Monitoring (dedicated feature)
ProfilingCode-level profiling (Full-Stack)Continuous Profiler (separate product)
Deployment tracking❌ Không native✅ Deployment Tracking (version comparison)

Opaque Services (Dynatrace-specific)

Dynatrace concept: Opaque Service = service được phát hiện nhưng KHÔNG có code-level visibility (ví dụ: 3rd-party API, service chưa cài OneAgent).

Datadog không có concept tương tự — external services hiện trong Service Map nếu có traces gọi đến chúng.

Database Monitoring — Khác biệt approach

AspectDynatraceDatadog
ApproachMonitor DB từ caller side (app server)DBM — monitor từ DB side (dedicated integration)
DataSQL queries, execution time từ app’s perspectiveQuery plans, wait events, DB-side metrics
SetupOneAgent on app server (auto)DBM integration config on DB host
Full visibilityOneAgent app + Extension on DBAgent + ddtrace (app) + DBM integration (DB)

7. Apdex Score — Dynatrace-specific

Dynatrace dùng Apdex (Application Performance Index) cho RUM:

Apdex = (Satisfied + 0.5 × Tolerating) / Total
RangeLabel
Response < TSatisfied
T ≤ Response < 4TTolerating
Response ≥ 4TFrustrated
ScoreRating
0.94-1.00Excellent
0.85-0.93Good
0.70-0.84Fair
0.50-0.69Poor
0.00-0.49Unacceptable

Datadog: không dùng Apdex — focus vào Core Web Vitals (LCP, FID, CLS) và percentile latency.
