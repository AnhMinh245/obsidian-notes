🔥 Real-World Incident Scenarios

Mục đích

Mỗi scenario mô phỏng sự cố production thật mà bạn sẽ gặp ở công ty. Sau khi đọc scenario, thực hành phát hiện + debug bằng Datadog hoặc Dynatrace trong labs.

Cách dùng note này cho hiệu quả

  • Đọc tình huống trước, tự nghĩ xem bạn sẽ mở màn hình nào đầu tiên
  • Chỉ sau đó mới xem phần Approach
  • Khi đọc approach, đừng chỉ nhớ “click đâu”; hãy nhớ vì sao bước đó đứng trước bước kia

Mục tiêu của note này không phải là học thuộc UI, mà là luyện thứ tự tư duy khi điều tra incident.

Scenario 1: “Website Chậm — Khách Hàng Complain”

📞 Tình huống

9:15 AM — CS team nhận 5 tickets: “Trang web load quá chậm”
9:20 AM — PM hỏi: “Chuyện gì đang xảy ra?”
Bạn là SRE on-call. Bắt đầu investigate.

🔍 Approach — Datadog

1. Infrastructure → Host Map
   → HOST có đang overloaded? (CPU, Memory)
   → Nếu OK → không phải infra issue

2. APM → Service List
   → Service nào có Latency (Duration) tăng?
   → store-discounts: P99 = 2.5s (bình thường: 200ms) 🔴

3. APM → store-discounts → Traces
   → Filter: duration:>1s
   → Click trace → Flame Graph
   → postgres span = 2.3s (bình thường: 50ms) 🔴

4. postgres span details
   → sql.query: "SELECT * FROM discounts WHERE..." 
   → query timeout

5. Logs → service:store-discounts status:error
   → "Connection pool exhausted"

6. Infrastructure → Containers → postgres
   → CPU 95%, Memory 90%
   → ❌ Root cause: DB overloaded

Tại sao đi theo thứ tự này?

  • Bước 1 bắt đầu từ infra overview để trả lời câu hỏi rộng nhất: đây là sự cố toàn host hay chỉ một phần hệ thống?
  • Nếu host nhìn chung ổn, bạn chuyển sang APM Service List để thu hẹp blast radius xuống service nào đang tăng latency mạnh nhất
  • Trace / Flame Graph là bước biến symptom “web chậm” thành một request cụ thể đang tốn thời gian ở span nào
  • Logs được dùng sau trace để giải thích cơ chế lỗi, ví dụ timeout, connection pool exhaustion, retry storm
  • Cuối cùng quay lại container/DB metrics để xác nhận đây là DB thật sự quá tải, chứ không chỉ là app gọi DB kém hiệu quả

Decision points cần phân biệt

  • Nếu postgres span chậm nhưng host/container DB không quá tải, hãy nghĩ tới query xấu, thiếu index, lock contention, không nên kết luận ngay là “DB yếu”
  • Nếu logs báo connection pool exhausted, có ít nhất 2 khả năng:
    • DB quá chậm nên connections bị giữ quá lâu
    • App-side pool config hoặc connection leak có vấn đề
  • Vì vậy metrics + traces + logs phải đi cùng nhau; chỉ một tín hiệu riêng lẻ chưa đủ để chốt root cause

Giải pháp: Optimize query, tăng connection pool, hoặc scale DB.

Labs liên quan: DD-04, DD-01

🔍 Approach — Dynatrace

1. Problems page
   → Davis AI đã tạo Problem: "Response time degradation"
   → Root cause: PostgreSQL database

2. Problem Card
   → Timeline: 9:12 AM — DB response time anomaly detected
   → Impact: 3 services affected
   → Root cause: Database entity

3. Click root cause → Database statements
   → Slowest query identified
   → Backtrace → calling method in discount-service

4. Smartscape → Database → Host
   → Host CPU/Memory high

Điểm mạnh của Dynatrace ở scenario này

  • Dynatrace rút ngắn mạnh Detection + Correlation vì Problems page đã gom symptom vào một problem card
  • Problem Card cho bạn một hypothesis root cause ban đầu nhanh hơn Datadog
  • Nhưng bạn vẫn nên click vào database statements và host context để kiểm tra xem kết luận đó có khớp với dữ liệu thực tế không

Đừng hiểu “Davis tìm root cause” là bạn được bỏ qua verify

  • Davis giúp giảm thời gian tìm hướng điều tra
  • Quyết định remediation vẫn cần người vận hành xác nhận:
    • query nào chậm?
    • dịch vụ nào bị ảnh hưởng trực tiếp vs gián tiếp?
    • DB quá tải thật hay chỉ là một downstream dependency khác làm DB trông có vẻ là culprit?

Davis AI đã tìm root cause cho bạn. Thời gian: 2 phút thay vì 15 phút.

Labs liên quan: DT-04, DT-02

Scenario 2: “5xx Errors Spike Sau Deploy”

📞 Tình huống

14:30 — Team deploy version mới của discount service
14:45 — Monitor alert: “Error rate > 5% on store-discounts”
Cần xác nhận: Deploy gây ra issue? Hay coincidence?

🔍 Approach — Datadog

1. APM → store-discounts → Service Page
   → Error rate chart: spike lúc 14:35 (5 phút sau deploy) 🔴
   → Correlate với deploy marker (nếu có Events overlay)

2. Error Tracking → store-discounts
   → New error group xuất hiện: "TypeError: NoneType..."
   → First seen: 14:35 — TRÙNG với deploy ✅

3. Click error → Stack trace
   → File: discount_calculator.py, line 42
   → Bug: mới thêm code nhưng thiếu null check

4. Trace → Flame Graph
   → store-discounts span đỏ
   → Exception: TypeError

5. Logs → service:store-discounts status:error
   → Log message confirms: "Failed to calculate discount: NoneType"

Điều quan trọng nhất ở scenario deploy

Correlation không đồng nghĩa với causation.

Một spike lỗi xuất hiện gần thời điểm deploy là tín hiệu rất mạnh, nhưng bạn vẫn cần bằng chứng:

  • error group mới xuất hiện sau deploy
  • first seen trùng hoặc gần trùng thời điểm rollout
  • stack trace chỉ vào code path vừa thay đổi
  • logs xác nhận cùng một cơ chế lỗi

Decision points

  • Nếu chỉ thấy error rate tăng nhưng không có error group mới, hãy nghĩ tới traffic pattern change, dependency issue, hoặc bug cũ bị lộ rõ hơn
  • Nếu deploy marker không có, bạn vẫn có thể điều tra bằng cách so timeline lỗi với thời điểm team deploy
  • Nếu stack trace chỉ ra một file/hàm vừa sửa, lúc đó rollback hoặc hotfix mới là quyết định hợp lý

Kết luận: Deploy gây ra bug. Rollback hoặc hotfix.

Labs liên quan: DD-04, DD-07

🔍 Approach — Dynatrace

1. Problems page
   → New Problem: "Failure rate increase" on discount-service
   → Timeline: starts at 14:35

2. Problem Card → Events tab
   → Deployment event detected (nếu CI/CD integration)
   → Correlation: "Problem started after deployment"

3. PurePath → Error trace
   → Method-level: discount_calculator.calculate() → exception
   → Code-level visibility: thấy exact line

4. Davis AI suggestion
   → "This problem correlates with a recent deployment event"

Cách đọc scenario này trên Dynatrace

  • Nếu tenant có deployment event hoặc CI/CD integration, correlation sẽ rõ hơn rất nhiều
  • Nếu không có deployment event tự động, bạn vẫn phải so bằng tay:
    • problem start time
    • error increase
    • thời điểm release thực tế

Điều cần verify thêm

  • “Correlates with deployment” nghĩa là đáng nghi nhất là deploy, không phải bằng chứng tuyệt đối
  • PurePath / error trace mới là nơi xác nhận:
    • exception nào mới xuất hiện
    • method nào fail
    • có đúng là code path mới hay không

Labs liên quan: DT-04, DT-05

Scenario 3: “Disk Full — Sneaky Silent Killer”

📞 Tình huống

Không có alert — mọi thứ có vẻ OK
Nhưng: Users báo “một số features không hoạt động”
Debug khó: Vì không có alert nào fire

🔍 Approach — Datadog

1. Infrastructure → Host Map → Color by disk
   → Host hexagon = ĐỎ: system.disk.in_use = 97%

2. USE Method check:
   - Utilization: system.disk.in_use = 97% 🔴
   - Saturation: system.disk.write_time tăng 10x
   - Errors: Log "No space left on device"

3. Logs → "No space left"
   → postgres logs: "could not write to log file"
   → Cascading: DB không write → transactions fail → API errors

4. Root cause: Log rotation broken → disk fill → DB crash

Vì sao disk full là “silent killer”?

Disk full rất ít khi biểu hiện bằng một alert “đẹp” ngay từ đầu. Thay vào đó, bạn thường thấy:

  • DB ghi log lỗi
  • app ghi file tạm thất bại
  • container restart bất thường
  • transaction timeout hoặc 5xx ở tầng trên

Nghĩa là symptom xuất hiện xa root cause. Đây là lý do bạn phải quay lại USE method và host metrics.

Decision points

  • system.disk.in_use cao nhưng hệ thống chưa lỗi nặng: đây là giai đoạn nên cleanup ngay
  • disk.in_use cao + write_time tăng + log No space left on device: lúc này sự cố đã ảnh hưởng workload thật
  • Nếu DB fail ghi log/temporary files, lỗi ở app layer chỉ là hậu quả, không nên fix ở app trước

Bài học: Monitor system.disk.in_use ≥ 85% → alert TRƯỚC khi full.

Labs liên quan: DD-01, DD-07

🔍 Approach — Dynatrace

1. Smartscape → Host → Disk metrics
   → Disk usage 97%

2. Davis AI
   → Có thể TỰ PHÁT HIỆN: "Disk space running low"
   → Problem auto-created nếu baseline bị vi phạm

3. Log Viewer → DQL:
   fetch logs | filter contains(content, "No space")

Kỳ vọng thực tế trên Dynatrace

  • Davis có thể tạo problem cho disk pressure nếu dữ liệu đủ rõ, nhưng không nên phụ thuộc hoàn toàn vào điều đó
  • Với hạ tầng kiểu lab/single host, host view + logs thường vẫn là cách chắc chắn nhất để xác nhận

Điều cần nhớ

  • Nếu không có problem card cho disk, điều đó không có nghĩa là disk không phải root cause
  • Infrastructure metrics vẫn là nền tảng để kiểm tra các “sát thủ âm thầm” như disk, memory pressure, file descriptor exhaustion

Labs liên quan: DT-01, DT-03

Scenario 4: “Cascading Failure — 1 Service Down, Tất Cả Chết”

📞 Tình huống

11:00 AM — Nhận 12 alerts cùng lúc (alert storm!)
Mỗi alert cho 1 service khác nhau
Câu hỏi: Cái nào là ROOT CAUSE? Cái nào là SYMPTOM?

🔍 Approach — Datadog

Khó! Phải manual investigation:

1. Xem timeline: Alert nào fire ĐẦU TIÊN?
   → store-backend: 10:58
   → postgres: 10:57       ← FIRST! 🎯
   → store-discounts: 10:59
   → store-frontend: 11:00

2. Service Map → postgres node = ĐỎ
   → Tất cả edges từ postgres = error

3. Kết luận: postgres down → cascade

Thời gian tìm root cause: ~10-15 phút

Vì sao Datadog khó hơn ở scenario này?

Vì mô hình monitor rule-based rất dễ tạo ra nhiều symptom alerts riêng lẻ:

  • service A fail
  • service B fail
  • DB fail
  • error rate tăng
  • latency tăng

Tất cả đều đúng, nhưng chưa được tự gom thành một narrative thống nhất.

Decision points

  • Alert đến sớm nhất là heuristic tốt, nhưng không phải bằng chứng tuyệt đối
  • Monitor windows khác nhau có thể làm alert của symptom đến sau hoặc trước root-cause alert vài phút
  • Vì vậy bạn phải kết hợp:
    • timeline
    • dependency map
    • traces/logs
    • downstream common dependency

🔍 Approach — Dynatrace

Dễ! Davis AI tự làm:

1. Problems page → 1 Problem (không phải 12 alerts!)
   → Title: "Database failure causing cascading impact"
   → Root cause: PostgreSQL database

2. Problem Card → Impact tree:
   postgres (ROOT CAUSE)
    ├── store-backend (impacted)
    ├── store-discounts (impacted)
    └── store-frontend (impacted)

3. Timeline: Clear sequence from DB → services

Thời gian tìm root cause: ~30 giây (đọc Problem Card)

Đây là scenario thể hiện rõ nhất khác biệt triết lý

  • Datadog cho bạn nhiều building blocks để tự điều tra
  • Dynatrace cố gắng đưa ra một impact tree ngay từ đầu

Giá trị lớn nhất không chỉ là “nhanh hơn”, mà là giảm cognitive load trong lúc alert storm đang xảy ra.

Nhưng vẫn cần verify một điều

Nếu có nhiều sự cố độc lập xảy ra cùng lúc, một problem card đẹp không phải lúc nào cũng phản ánh toàn bộ picture. Hãy xem timeline và impacted entities để chắc rằng bạn không bỏ sót một failure song song khác.

💡 Key Insight: Đây là scenario mà Davis AI vượt trội so với rule-based monitoring. Alert storm → 1 problem.

Labs liên quan: DT-04

Scenario 5: “SLO Budget Sắp Hết — Sprint Planning”

📞 Tình huống

Sprint planning meeting — PM hỏi:
“Tháng này error budget còn bao nhiêu? Có nên deploy feature mới không?”

🔍 Approach — Datadog

1. Service Management → SLOs
   → "Store API Availability" SLO
   → Target: 99.9%
   → Current: 99.85%
   → Error budget remaining: 15% (cho tháng này)

2. Dashboard widget → SLO burn rate
   → Burn rate = 2.3x (nhanh hơn bình thường)
   → Nếu tiếp tục: budget hết trong 5 ngày

3. Recommendation:
   → "Có thể deploy, nhưng cần feature flag + canary"
   → "Nếu error rate tăng → auto-rollback"

Cách đọc SLO cho quyết định release

  • Budget remaining trả lời: “mình còn bao nhiêu room để fail?”
  • Burn rate trả lời: “mình đang đốt budget nhanh tới mức nào?”

Hai câu hỏi này khác nhau. Một service có thể còn 15% budget nhưng nếu burn rate đang 2.3x thì quyết định deploy phải cẩn thận hơn nhiều.

Decision framework đơn giản

  • Budget còn nhiều, burn rate bình thường: có thể release bình thường
  • Budget còn ít nhưng burn rate ổn: release nhỏ, có guardrails
  • Budget còn ít và burn rate cao: ưu tiên reliability work hơn feature rollout

Labs liên quan: DD-08

🔍 Approach — Dynatrace

1. SLOs → "EasyTrade Availability"
   → Target: 99.9%
   → Current status + remaining budget

2. DQL query cho trend:
   fetch dt.entity.service
   → Error budget consumption rate

3. Dashboard tile → SLO trend

Trên Dynatrace, câu hỏi release readiness vẫn là cùng một bài toán

Dù UI/query path khác Datadog, logic quyết định không đổi:

  • status hiện tại của SLO
  • budget còn lại
  • trend tiêu thụ budget
  • mức an toàn của rollout plan

Điều nên mang vào sprint planning

SLO không phải câu trả lời “deploy / không deploy” một cách máy móc. Nó là ngữ cảnh định lượng để đội ngũ thống nhất:

  • có cần feature flag không
  • có nên canary không
  • có cần rollback criteria rõ hơn không

Labs liên quan: DT-07

🎓 Bài Học Chung

1. MTTR = Mean Time To Resolve

MTTR = Detection + Investigation + Resolution

Datadog: Detection (manual) + Investigation (powerful tools) + Resolution (you)
Davis:   Detection (auto) + Investigation (auto RCA) + Resolution (you)

Điểm quan trọng là: không platform nào “resolve thay bạn”. Platform chỉ tối ưu những pha khác nhau của MTTR.

  • Datadog mạnh khi người vận hành giỏi, biết đặt câu hỏi đúng và tận dụng toolset tốt
  • Dynatrace mạnh khi bạn cần giảm thời gian correlation và root-cause narrowing

2. Observability != Monitoring

Monitoring:  "X metric > threshold → alert"  (reactive)
Observability: "Hệ thống đang ở trạng thái gì?" (proactive)
              → Tôi có thể hỏi BẤT KỲ câu hỏi nào
              → Và tìm được câu trả lời
              → MÀ KHÔNG CẦN biết trước sẽ hỏi gì

Monitoring vẫn rất cần, vì nó là thứ kéo bạn vào incident. Nhưng khi đã vào incident rồi, observability mới là thứ giúp bạn đi từ:

  • symptom
  • sang hypothesis
  • sang evidence
  • rồi mới tới root cause

3. Three Pillars Kết Hợp

Không bao giờ debug chỉ bằng 1 pillar:

  • Metrics → “CÁI GÌ đang xảy ra?” (CPU high, latency spike)
  • Logs → “TẠI SAO xảy ra?” (error message, stack trace)
  • Traces → “Ở ĐÂU xảy ra?” (which service, which request path)

4. Quy Tắc Điều Tra Thực Dụng

Một thứ tự rất hiệu quả trong hầu hết incidents:

  1. Bắt đầu rộng: blast radius ở mức host, service, hay toàn hệ thống?
  2. Thu hẹp phạm vi: service nào, endpoint nào, request path nào?
  3. Tìm bằng chứng cơ chế lỗi: logs, stack trace, exception, query, timeout
  4. Xác nhận root cause: quay lại infra/dependency/business context để chắc symptom không bị nhầm là nguyên nhân
  5. Chỉ remediation khi đã đủ evidence: đừng scale, restart, rollback chỉ vì một dashboard đỏ

Đây là thứ bộ labs này thực sự muốn bạn luyện: khả năng suy luận có thứ tự, không chỉ khả năng bấm UI.
