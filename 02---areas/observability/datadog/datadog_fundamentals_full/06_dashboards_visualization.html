Phần 6: Dashboards & Visualization — Hiểu Sâu Công Cụ Trực Quan Hóa

Tỷ trọng ước tính: ~10-12% đề thi · Độ khó: Trung bình

6.1 Tại Sao Cần Dashboard? — Vấn Đề Của Raw Data

Datadog có hàng trăm nghìn metrics từ hàng trăm hosts. Metrics Explorer cho phép query bất kỳ metric nào — nhưng mỗi lần xem phải gõ lại query từ đầu.

Dashboard giải quyết điều này bằng cách:

  1. Lưu lại queries dưới dạng widgets
  2. Sắp xếp nhiều widgets thành 1 view
  3. Chia sẻ với team (ai cũng xem cùng 1 view)
  4. Auto-refresh — không cần F5

6.2 Timeboard vs Screenboard — Hai Triết Lý Thiết Kế

⚠️ Cập nhật quan trọng: Datadog đã hợp nhất Timeboard và Screenboard thành một loại Dashboard duy nhất (từ ~2020). Trong UI hiện tại, bạn tạo “Dashboard” với layout grid-based (tương tự Timeboard cũ, synchronized time) hoặc free-form (tương tự Screenboard cũ, independent time ranges). Tuy nhiên, đề thi vẫn có thể hỏi concepts này để kiểm tra hiểu biết về khi nào cần synchronized time vs free-form layout.

Triết lý Timeboard: “Tất cả cùng thời gian”

Vấn đề cần giải quyết: Khi troubleshoot incident, bạn cần xem CPU, latency, error rate… cùng thời điểm để tìm correlation.

Timeboard giải quyết:

  [CPU widget]  [Latency widget]  [Error Rate widget]
  ─────────────────────────────────────────────────
  Mọi widget đều hiển thị data từ 14:00 - 14:15
  
  Bạn kéo timeline sang 13:55 - 14:10 → TẤT CẢ widgets update đồng bộ!
  
  Giờ bạn thấy: CPU spike lúc 14:02 → Latency tăng lúc 14:03 → Errors tăng lúc 14:04
  → Sequence rõ ràng: CPU bottleneck gây latency → gây errors

★ Timeboard = Debugging/Troubleshooting tool — correlation theo thời gian là tính năng cốt lõi.

Triết lý Screenboard: “Linh hoạt theo nhu cầu trình bày”

Vấn đề cần giải quyết: NOC (Network Operations Center) cần màn hình hiển thị nhiều loại thông tin khác nhau — không phải tất cả cần cùng time range.

Screenboard ví dụ cho NOC:

  [Last 5 min: Error Rate - REALTIME]  │  [Last 24h: Daily Traffic Summary]
  ──────────────────────────────────────│──────────────────────────────────
  [Current: Active Alerts - NO TIME]   │  [Last 7 days: Weekly Trend]
  
  → Widget trái trên: thời gian 5 phút (urgent alerts)
  → Widget phải trên: thời gian 24 giờ (business summary)
  → Widget trái dưới: không có time range (danh sách alerts)
  → Widget phải dưới: 7 ngày (trend analysis)

★ Screenboard = Presentation/Status Board — linh hoạt layout > synchronized time.

6.3 Widget Types — Chọn Đúng Công Cụ Cho Đúng Câu Hỏi

Framework chọn widget

Câu hỏi về THỜI GIAN ("trend qua thời gian?")?
  → Timeseries

Câu hỏi về GIÁ TRỊ HIỆN TẠI ("bây giờ bao nhiêu?")?
  → Query Value

Câu hỏi về XẾP HẠNG ("cái nào cao/thấp nhất?")?
  → Toplist

Câu hỏi về TỔNG QUAN INFRASTRUCTURE ("toàn bộ fleet như thế nào?")?
  → Hostmap

Câu hỏi về PHÂN BỐ ("distribution của latency?")?
  → Heatmap

Câu hỏi về THAY ĐỔI SO VỚI TRƯỚC ("tăng hay giảm so với tuần trước?")?
  → Change

Câu hỏi về NHIỀU METRICS CỦA NHIỀU ENTITIES ("structured overview?")?
  → Table

Timeseries — Biểu Đồ Thời Gian

Cơ chế: Query metric → vẽ line/area/bar chart theo timestamp.

Query: avg:system.cpu.user{env:production} by {host}

Timeline: 14:00 - 15:00

Kết quả: 50 lines (1 line per host), mỗi point = avg CPU tại 1 timestamp

Tính năng đặc biệt: Event Overlay — hiển thị events (deployments, alerts) dưới dạng vertical markers

[Timeseries graph]

CPU%
  │
80│        ╭─────────────╮
  │       ╱               ╲
60│──────╱─────────────────╲──────
  │     ╱                   ╲
40│────╱─────────────────────╲────
  │
  └────────────────────────────▶ time
       ▲
       │ Deploy event (vertical marker)
       │ "Deploy v2.1.0" at 14:23

→ Ngay lập tức thấy: deployment tại 14:23 gây CPU spike!

Query Value — Single KPI Display

Cơ chế: Query metric → lấy 1 giá trị aggregate (avg của last N phút) → hiển thị to.

Query: avg:http.error_rate{env:production}[last 5m]
  → Tính average error rate trong 5 phút qua → hiển thị: "2.3%"

Conditional formatting — đổi màu theo ngưỡng:

  < 1%   → Xanh lá  (OK)
  1-5%   → Vàng     (Warning)
  > 5%   → Đỏ       (Critical)

Khi nào dùng: KPIs quan trọng cần nhìn ngay không cần đọc graph (error rate, uptime %).

Hostmap — Bird-Eye View Infrastructure

Cơ chế: Mỗi host = 1 hexagon → Color = giá trị metric → Size = metric khác (optional)

  [●][●][●][●][●][●][●][●][●][●]
  [●][●][●][●][●][●][●][●][●][●]
  [●][●][●][●][●][●][●][●][●][●]
  [●][●][●][●][●][●][●][●][●][●]  ← Toàn bộ 50 hosts
  [●][●][●][●][●][●][●][●][●][●]
  
  Color scale:
  🟢 < 50% CPU → 🟡 50-80% → 🔴 > 80%
  
  Nhìn vào thấy ngay: 3 hexagons đỏ ở góc phải → SSH ngay vào 3 hosts đó

Tính năng: Click vào hexagon → xem chi tiết host đó, jump đến Infrastructure List.

Toplist — Ranked Leaderboard

Cơ chế: Query metric → group by tag → sort → lấy top/bottom N

Query: avg:system.cpu.user{env:production} by {host}
Sort: Descending (highest CPU first)
Top: 10

Kết quả:
  1. web-prod-07  : ████████████████ 94%
  2. web-prod-23  : ███████████████  91%
  3. web-prod-15  : ████████████     78%
  ...

Khi nào dùng: “Top 10 hosts CPU cao nhất”, “Services có error rate cao nhất”, “APIs slowest p99”.

Heatmap — Density Distribution

Cơ chế: X = thời gian, Y = giá trị metric, Color = mật độ (density) của data points tại (time, value)

Y: Latency (ms)

     Color: ░ = ít, █ = nhiều

Khi nào dùng: Muốn xem phân bố latency qua thời gian — thấy ngay bi-modal distributions (2 peaks) hoặc latency shifts.

6.4 Template Variables — Cơ Chế Hoạt Động

Không có template variables — vấn đề

Widget 1: avg:system.cpu.user{env:production, service:web-api}
Widget 2: avg:http.latency{env:production, service:web-api}
Widget 3: rate(http.errors{env:production, service:web-api})
... 20 widgets ...

Muốn xem staging thay vì production?
→ Phải vào từng widget, sửa `env:production` → `env:staging` × 20 lần!

Có template variables — giải pháp

Định nghĩa:
  Variable name: $env
  Tag key: env
  Default: production

Tất cả widgets dùng $env thay vì hardcode:
  avg:system.cpu.user{env:$env, service:web-api}
  avg:http.latency{env:$env, service:web-api}
  ...

Dropdown trên dashboard:
  [ production ▼ ]   ← Thay đổi ở đây...
  
  → Tất cả 20 widgets tự động update!

Multi-variable: Kết hợp nhiều template variables

[ production ▼ ] [ web-api ▼ ] [ us-east-1 ▼ ]
  $env          $service       $region

Queries dùng: {env:$env, service:$service, region:$region}

6.5 SLO Widget — Theo Dõi Error Budget Trên Dashboard

SLO Widget là gì?

SLO Widget cho phép hiển thị trạng thái SLO (Service Level Objective) trực tiếp trên dashboard. Thay vì phải vào trang SLO riêng, team nhìn dashboard là thấy ngay.

┌──────────────────────────────────────────┐
│  SLO: API Uptime          Target: 99.9% │
│                                          │
│  7-day:  ████████████████████ 99.95% ✅  │
│  30-day: ███████████████████░ 99.87% ⚠️  │
│  90-day: ████████████████████ 99.92% ✅  │
│                                          │
│  Error Budget remaining: 12.4 min        │
└──────────────────────────────────────────┘

Thông tin hiển thị

Thành phầnMô tả
TargetMục tiêu SLO (VD: 99.9%)
Status bars% uptime thực tế theo các time windows (7d, 30d, 90d)
Color coding✅ Xanh = đạt target, ⚠️ Vàng = gần target, 🔴 Đỏ = vi phạm
Error BudgetThời gian downtime còn lại trước khi vi phạm SLO

Khi nào dùng SLO Widget?

★ Use cases:
  1. NOC Dashboard: Team ops nhìn ngay tình trạng SLO của tất cả services
  2. C-level Dashboard: Hiển thị reliability hàng tuần cho stakeholders
  3. Sprint Dashboard: Dev team track error budget còn lại → quyết định deploy hay freeze

★ Error Budget còn nhiều → Deploy thoải mái
★ Error Budget gần hết → FREEZE deployments, focus stability!

6.5a Notebooks — Collaborative Investigation

Notebooks vs Dashboards

Dashboard = monitoring liên tục (real-time, auto-refresh)
Notebook  = investigation & documentation (point-in-time, collaborative)
FeatureDashboardNotebook
Mục đíchMonitor liên tụcĐiều tra, postmortem, runbook
Time rangeShared cho toàn bộ widgetsMỗi cell có thể khác time
TextWidget chỉ hiện dataCó rich text giải thích context
CollaborationView/edit dashboardReal-time editing, comments, @mention
SnapshotLive data (luôn thay đổi)Có thể lock time range → “snapshot”
ShareURL linkURL link + scheduled email report

Cấu trúc Notebook

Notebook = danh sách cells theo thứ tự:

  ┌─────────────────────────────────┐
  │ [Text Cell]                     │
  │ "Incident #4521: Spike latency  │
  │  payment service lúc 14:30 UTC" │
  ├─────────────────────────────────┤
  │ [Graph Cell] — Timeseries       │
  │ trace.flask.request.duration    │
  │ Time: 14:00 - 15:00 UTC        │
  ├─────────────────────────────────┤
  │ [Text Cell]                     │
  │ "Root cause: DB connection pool │
  │  exhausted do missing index"    │
  ├─────────────────────────────────┤
  │ [Graph Cell] — Query Value      │
  │ postgres.connections            │
  └─────────────────────────────────┘

Use cases chính

  • Postmortem: Ghi lại incident timeline + graphs + root cause analysis
  • Runbook: Step-by-step hướng dẫn troubleshoot với live graphs
  • Investigation: Share findings với team trong lúc đang điều tra

★ Exam tip: “Tool nào để ghi lại incident investigation với text + graphs?” → Notebooks (không phải Dashboard)

6.5b Dashboard Permissions & Sharing

Access control

PermissionAi đượcMô tả
Read-OnlyMọi member trong orgXem dashboard, không edit
EditCreator + designated users/teamsSửa widgets, layout
RestrictedChỉ creator + adminsDashboard nhạy cảm (security, billing)

Sharing options

  • URL Sharing: Ai có link trong org đều xem được
  • Public URL: Chia sẻ dashboard read-only ra ngoài org (embed vào wiki, status page)
  • Scheduled Reports: Email PDF snapshot định kỳ (daily/weekly)
  • TV Mode: Full-screen auto-rotate cho NOC displays

★ Key: Dashboard mặc định read-only cho mọi người trong org. Cần explicit grant edit permission.

6.6 Câu Hỏi Thường Gặp

Q: Timeboard vs Screenboard — dùng cái nào?
→ Trouble-shooting incident → synchronized time (grid-based layout, khái niệm Timeboard cũ). NOC/status display → free-form layout (khái niệm Screenboard cũ). Lưu ý: Datadog đã hợp nhất thành 1 loại Dashboard duy nhất.

Q: Widget nào hiện bird-eye view CPU color-coded cho tất cả hosts?
→ Hostmap (hexagons = hosts, color = metric value)

Q: Widget nào hiện 1 con số lớn (error rate current)?
→ Query Value (với conditional formatting)

Q: Widget nào xếp hạng top 10 CPU hosts?
→ Toplist

Q: Widget nào visualize phân bố latency qua thời gian?
→ Heatmap (density distribution)

Q: Template variables làm gì?
→ Cho phép filter dynamic toàn bộ dashboard bằng tag values, không cần sửa từng widget query

Q: Event Overlay trên Timeseries hiển thị gì?
→ Events (deployments, alerts) dưới dạng vertical markers → correlate với metric changes

Q: Change widget dùng khi nào?
→ So sánh metric hiện tại vs thời điểm trước (hour/day/week ago)

Q: SLO Widget hiển thị gì?
→ Trạng thái SLO (% uptime theo 7d/30d/90d), error budget còn lại, và color-coded theo target
