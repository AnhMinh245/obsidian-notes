PHẦN A: LOG MANAGEMENT

8.1 Log Lifecycle — Chuỗi Xử Lý Từ Đầu Đến Cuối

Tại sao cần pipeline phức tạp?

Logs từ các hệ thống khác nhau có format hoàn toàn khác nhau:

NGINX access log:
  192.168.1.1 - - [15/Mar/2024:14:23:01 +0700] "GET /api/users HTTP/1.1" 200 1234

Python app log:
  2024-03-15 14:23:01,412 ERROR web-api Connection refused to DB

JSON log (structured):
  {"timestamp":"2024-03-15T14:23:01Z","level":"ERROR","service":"web-api","message":"DB timeout"}

Syslog:
  Mar 15 14:23:01 web-01 nginx: 1234 bytes sent to 192.168.1.1

Bạn không thể search across tất cả logs nếu mỗi cái có timestamp format, severity level, IP address khác nhau. Pipelines chuẩn hoá chúng.

Routing — Chi tiết các đường đi

★ Logging Without Limits™ = Bạn CHỌN logs đi đâu sau khi xử lý:

  TẤT CẢ logs đã ingest → Live Tail (luôn có, free, realtime stream)
                        → Generate Metrics (tạo metric từ log, không cần index)

8.2 Logging Without Limits™ — Tại Sao Đây Là Innovation Quan Trọng

Trước khi có Logging Without Limits

Mô hình cũ:
  Thu thập logs → Index TẤT CẢ → Tính tiền theo volume indexed

Hệ quả:
  1. Team phải chọn: "Collect log gì? Không collect cái kia để tiết kiệm tiền"
  2. Khi có incident: "Ôi, chúng ta đã filter mất debug logs rồi!"
  3. Compliance: "Log retention 7 năm = chi phí index 7 năm = cực kỳ đắt"

Logging Without Limits — Mô Hình Mới

Ingest tất cả (cheap)
        │
        ├──→ Analyze/Search NOW → Index (searchable, expensive)
        │          │
        │          └─→ Chỉ logs quan trọng: errors, security, business-critical
        │          
        └──→ Archive ALL → S3/GCS (cheap, not searchable)
                   │
                   └─→ Rehydrate khi cần: giải nén từ archive vào index tạm thời

Lợi ích:

  • ✅ Thu thập 100% logs → không bao giờ mất data
  • ✅ Chỉ trả tiền index cho 10-20% logs quan trọng
  • ✅ Khi cần investigate debug logs → Rehydrate từ archive (pull tạm về index)
  • ✅ Long-term retention với chi phí thấp (S3 ~ 0.023$/GB/month)

8.3 Log Pipelines — Cơ Chế Xử Lý

Pipeline là gì trong code?

Các Processors Quan Trọng

1. Grok Parser — Parse unstructured text

Grok là pattern-matching language để extract cấu trúc từ text:

Raw log: "192.168.1.1 GET /api/users 200 1234ms"

Grok rule: %{IP:client_ip} %{WORD:method} %{DATA:path} %{NUMBER:status:integer} %{NUMBER:duration}ms

Extracted attributes:
  client_ip: "192.168.1.1"
  method: "GET"
  path: "/api/users"
  status: 200         (integer, not string!)
  duration: 1234      (integer)

Syntax breakdown: %{MATCHER:ATTRIBUTE_NAME:FILTER}

  • MATCHER: Pre-defined pattern: IP, WORD, NUMBER, DATA, DATE
  • ATTRIBUTE_NAME: Tên attribute sẽ có trong log
  • FILTER (optional): Post-processor biến đổi dữ liệu: integer, double, lowercase, keyvalue

Rule về Grok order: Nhiều rules trong 1 Grok parser → rule đầu tiên match sẽ được áp dụng, stop ở đó.

2. Log Date Remapper — Đặt đúng timestamp

Vấn đề: Log được Datadog nhận lúc 14:23:05 UTC, nhưng log xảy ra lúc 14:23:01 UTC
        (4 giây delay do batching, network)

Nếu không remap:
  Log hiển thị timestamp: 14:23:05 (thời điểm Datadog nhận)
  Thực tế event: 14:23:01

Với Log Date Remapper:
  Processor: "Dùng attribute 'timestamp' của log làm official timestamp"
  Kết quả: Log hiển thị 14:23:01 (thời điểm thực sự xảy ra)

3. Service Remapper — Định danh service

App emit logs với field "app_name": "web-api"
Datadog cần field "service" để correlate với APM traces

Service Remapper:
  "Dùng attribute 'app_name' làm official 'service' của log"
  → Log.service = log.app_name = "web-api"
  → Giờ log có thể correlate với APM traces của service web-api

4. GeoIP Parser — Location từ IP

Client IP: 203.113.145.12

GeoIP Parser lookup:
  → Country: Vietnam
  → City: Ho Chi Minh City
  → Lat: 10.8231, Lon: 106.6297
  → ISP: Viettel

Log được enrich với geo data → Dashboard "Users by Geography"!

5. Category Processor — Group values

HTTP status codes có hàng trăm values (200, 201, 301, 400, 404, 500...)

Category Processor:
  200-299 → "success"
  300-399 → "redirect"
  400-499 → "client_error"
  500-599 → "server_error"

→ Thay vì filter by exact status code, filter by category!
→ "Server errors trong 1 giờ qua" dễ hơn nhiều

8.4 Log Collection Config — Kích Hoạt và Cấu Hình

Bước 1: Enable log collection (Agent)

Tại sao default disabled? Logs có thể chứa sensitive data (PII, passwords). Datadog yêu cầu explicit opt-in để đảm bảo người dùng biết và đồng ý.

Bước 2: Config log source

source field quan trọng: Datadog dùng source để tự động apply pipeline phù hợp:

  • source: nginx → Auto apply NGINX pipeline (đã có sẵn)
  • source: python → Apply Python log pipeline
  • source: custom → Không apply pipeline nào tự động

8.5 Facets — Tìm Kiếm Và Lọc Logs Hiệu Quả

Facet là gì?

Khi bạn mở Log Explorer, thanh bên trái hiển thị các Facets — đây là các attributes được index và searchable, cho phép lọc, nhóm, và aggregate logs.

★ Attribute vs Facet:

  ATTRIBUTE = trường dữ liệu trong log (VD: status_code, duration, user_id)
             → Luôn tồn tại nếu pipeline extract ra
             → Nhưng KHÔNG THỂ filter/group trong Log Explorer!

  FACET = attribute được "đăng ký" để tìm kiếm
          → Xuất hiện ở sidebar Log Explorer
          → Dùng được trong filter, group by, analytics
          → Cần tạo THỦ CÔNG (không tự động!)

2 loại Facets

LoạiMô tảVí dụDùng khi
Facet (qualitative)Giá trị rời rạc, dùng để lọc và nhómstatus, env, service, endpointBạn muốn filter hoặc group by
Measure (quantitative)Giá trị số, dùng để tính toán (avg, sum, percentile)duration, response_size, status_codeBạn muốn aggregate (avg latency, max size)

Cách tạo Facet

Bước 1: Mở Log Explorer
Bước 2: Click vào 1 log có attribute bạn muốn
Bước 3: Hover lên attribute (VD: @http.status_code)
Bước 4: Click biểu tượng "⚙" → "Create facet for @http.status_code"
Bước 5: Chọn group (VD: "Web Access") và type (Facet hoặc Measure)
Bước 6: Save → Facet xuất hiện ở sidebar!

Chú ý: Facet chỉ áp dụng cho logs MỚI từ lúc tạo.
         Logs cũ KHÔNG được re-index.

Facets mặc định (built-in)

Datadog tự cung cấp một số facets sẵn có, không cần tạo:

FacetMô tả
HostHostname gửi log
ServiceService name (UST)
SourceNguồn log (nginx, python…)
StatusSeverity (info, warn, error)
TimestampThời gian log

★ Exam tip: “Để filter logs theo custom attribute, cần làm gì?” → Tạo Facet cho attribute đó trong Log Explorer.

8.6 Log Patterns — Tự Động Nhóm Logs Giống Nhau

Vấn đề: Log noise

Log Explorer hiển thị 50,000 logs trong 1 giờ.
95% là các dòng giống nhau:
  "Connection established to db-replica-01"
  "Connection established to db-replica-02"
  "Connection established to db-replica-03"
  ... 47,000 dòng tương tự

Bạn không thể tìm thấy 50 dòng ERROR thực sự quan trọng trong đống noise này!

Giải pháp: Log Patterns

Datadog tự động cluster logs có cấu trúc giống nhau thành Patterns:

Thay vì 47,000 dòng riêng lẻ:

  PATTERN: "Connection established to <db-replica-*>"  [47,000 logs]
  PATTERN: "Request processed in <*>ms"                [2,800 logs]
  PATTERN: "ERROR: Timeout connecting to <*>"          [50 logs]  ← ĐÂY MỚI QUAN TRỌNG!
  PATTERN: "User <*> logged in from <*>"               [150 logs]

→ 4 patterns thay vì 50,000 dòng rieng lẻ!

Cách sử dụng

Log Explorer → Tab "Patterns" (thay vì tab "List")

  Hiển thị:
  │ Pattern                              │ Count  │ Status │
  ├──────────────────────────────────────┼────────┼────────┤
  │ Connection established to <*>         │ 47,000 │ INFO   │
  │ Request processed in <*>ms            │ 2,800  │ INFO   │
  │ User <*> logged in from <*>           │ 150    │ INFO   │
  │ ERROR: Timeout connecting to <*>      │ 50     │ ERROR  │ ← Focus vào đây!

Click vào pattern → xem tất cả logs thuộc pattern đó

Lợi ích

  • Giảm noise: Từ 50,000 → 4 patterns, nhìn ngay được vấn đề
  • Phát hiện anomaly: Pattern mới xuất hiện = điều gì đó thay đổi
  • Tạo metric từ pattern: Đếm số lần xuất hiện của 1 pattern → alert khi spike

★ Exam tip: “Giảm log noise khi troubleshoot?” → Log Patterns (tab Patterns trong Log Explorer)

8.6a Index Management & Exclusion Filters — Kiểm Soát Chi Phí Logs

Vấn đề: Không phải log nào cũng cần search

Lưu TẤT CẢ logs vào index → search nhanh, nhưng:
  10 TB logs/tháng × $1.70/GB indexed = ~$17,000/tháng!
  
  Trong đó:
    Health check logs (GET /healthz)       → 60% volume, 0% giá trị troubleshoot
    Debug logs từ dev service              → 20% volume, thỉnh thoảng cần
    ERROR + WARN từ production             → 20% volume, luôn cần search ngay

Giải pháp: Multiple Indexes + Exclusion Filters

Log Pipeline Output → Routing Rules:

  Rule 1: status:error OR status:warn → Index "production-critical"
          Retention: 30 ngày. Không exclusion filter.
  
  Rule 2: env:staging → Index "staging"
          Retention: 7 ngày. Exclusion: healthcheck logs.
  
  Rule 3: * (tất cả còn lại) → Index "default"
          Retention: 3 ngày. Exclusion: debug + healthcheck.

Exclusion Filters

  • Nằm trên mỗi Index — lọc bỏ logs TRƯỚC khi index (tiết kiệm chi phí)
  • Filter dựa trên query syntax: source:nginx status:info @http.url_details.path:"/health*"
  • Logs bị exclude vẫn đi qua Live Tail (15 phút) và vẫn được Archive
  • Quan trọng: Exclusion filter chỉ ảnh hưởng indexing, KHÔNG ảnh hưởng ingestion hay archiving

Daily Quota

  • Mỗi index có thể set daily quota (events/ngày)
  • Khi đạt quota → logs bị drop (không index thêm)
  • Dùng để tránh cost spike bất ngờ

★ Exam tip: “Giảm chi phí log indexing?” → Exclusion Filters (trên Index) + Multiple Indexes (retention khác nhau)

8.6b Log Archives & Rehydration — Lưu Trữ Dài Hạn

Vấn đề: Index chỉ giữ logs 3-30 ngày

Sau retention period, logs biến mất khỏi Log Explorer. Nhưng compliance yêu cầu giữ 1-7 năm.

Log Archives

Luồng logs:
  Ingest → Pipeline Processing → Index (searchable, 3-30 ngày)
                                ↘ Archive (cold storage, 1-7+ năm)

Archive destinations:
  - Amazon S3
  - Google Cloud Storage (GCS)
  - Azure Blob Storage

Config:
  Logs → Configuration → Archives → New Archive
  - Chọn destination (S3 bucket, GCS bucket, etc.)
  - Filter query: "*" (tất cả) hoặc filter cụ thể
  - Archive path: logs/datadog/YYYY/MM/DD/HH/

Archive Routing

  • Có thể tạo nhiều archives với filter khác nhau
  • Ví dụ: env:production → S3 bucket compliance, * → GCS bucket general
  • Logs match nhiều archives → được archive vào tất cả

Rehydration — Khôi Phục Logs Từ Archive

Khi cần điều tra sự cố 3 tháng trước:

  Archives → chọn time range + filter → "Rehydrate"
  → Datadog tạo Historical Index (tạm thời)
  → Logs xuất hiện lại trong Log Explorer
  → Sau khi done → xoá Historical Index
  • Rehydration tốn thời gian (giờ đến ngày, tuỳ volume)
  • Rehydrated logs xuất hiện trong Historical Index riêng
  • Có thể query như logs bình thường trong Log Explorer

Tổng hợp: Logging Without Limits™ = 3 phần

PhầnMô tảRetention
IngestNhận TẤT CẢ logs, processing pipelineReal-time
IndexChỉ index logs cần search3-30 ngày (configurable)
ArchiveLưu raw logs vào cloud storage1-7+ năm

★ Exam tip: “Logging Without Limits gồm mấy phần?” → 3 phần: Ingest all → Index selective → Archive all. Rehydration = khôi phục logs từ archive.

PHẦN B: APM (Application Performance Monitoring)

8.9 Tại Sao APM Tồn Tại — Metrics Và Logs Còn Thiếu Gì?

Scenario: API gateway p99 latency = 3s (quá chậm!)

Với Metrics:
  system.cpu.user{service:api-gateway} = 25%    → CPU OK
  system.mem.usable{service:api-gateway} = 4GB  → Memory OK
  → Không rõ vấn đề ở đâu

Với Logs (api-gateway):
  "Request /api/checkout completed in 2987ms" → Thấy chậm
  → Nhưng 2987ms đi đâu? Internal compute? Gọi service khác? DB?

Với APM:
  [api-gateway: 3000ms]
   └─[auth-service: 25ms]          → OK
   └─[cart-service: 50ms]          → OK
   └─[payment-service: 2900ms]     → ĐÂY LÀ VẤN ĐỀ!
      └─[stripe-api call: 2850ms]  → External API timeout!

APM trả lời: Chính xác xem 2987ms đó tiêu vào đâu.

8.10 Distributed Tracing — Cơ Chế Propagation

Cách Trace ID truyền qua services

User Request → API Gateway
────────────────────────────────────────────────────
API Gateway nhận request, tạo:
  trace_id = "abc-123-xyz"
  span_id = "span-001" (root span)
  
API Gateway gọi Payment Service:
  HTTP Header: X-Datadog-Trace-Id: abc-123-xyz
               X-Datadog-Parent-Id: span-001
               X-Datadog-Sampling-Priority: 1
────────────────────────────────────────────────────
Payment Service nhận request:
  Đọc header: trace_id = "abc-123-xyz", parent = "span-001"
  Tạo span của mình: span_id = "span-003", parent = "span-001"
  
Payment Service gọi Stripe API:
  HTTP Header: X-Datadog-Trace-Id: abc-123-xyz
               X-Datadog-Parent-Id: span-003
────────────────────────────────────────────────────
Stripe API: (thường không có Datadog, nhưng có timeout span)
  Agent tạo span: "stripe.api.call" duration=2850ms

Kết quả: Datadog backend thu thập tất cả spans có cùng trace_id → tái tạo cây phân cấp → vẽ flame graph.

8.11 Span — Đơn Vị Cơ Bản Của Trace

Mỗi span chứa gì?

Root Span vs Child Span

Root Span: span_id="span-001", parent_id=null    ← Không có parent
  └─ Child: parent_id="span-001"
      └─ Grandchild: parent_id="span-002"

Root span = điểm bắt đầu của request (thường là API endpoint)
Tổng duration của trace ≈ duration của root span

8.13a Trace Retention & Ingestion Controls — Kiểm Soát Chi Phí APM

Vấn đề: Thu thập tất cả traces rất đắt

1 triệu requests/giờ × 5 spans/request = 5 triệu spans/giờ
Lưu tất cả → rất tốn kém và không cần thiết

Hai giai đoạn kiểm soát

                    Ingestion                    Retention
App → Tracer → Agent → Datadog Cloud ──→ ┌─────────────────────┐
                                          │ Live (15 phút)      │
                                          │ Retained (15 ngày)  │
                                          └─────────────────────┘

1. Ingestion Controls (quyết định traces nào GỬI về Datadog):

MechanismMô tả
Head-based samplingTracer quyết định TẠI ĐẦU request: sample hay không. Config DD_TRACE_SAMPLE_RATE=0.5 → giữ 50%
Ingestion rulesTrên Datadog UI: set tỉ lệ sample theo service/resource
Agent-level samplingAgent có thể drop spans trước khi gửi (rare, khi overloaded)

2. Retention Controls (quyết định traces nào GIỮ LẠI lâu):

LoạiRetentionMô tả
Live traces15 phútTất cả ingested spans, real-time search
Retained traces15 ngàySpans match retention filters (errors, high latency, specific tags)

Intelligent Retention

Datadog tự động giữ lại diverse traces ngay cả khi sample rate thấp:

  • Error traces: mọi trace có error span
  • Rare traces: endpoints ít traffic (ít nhất 1 trace/endpoint/interval)
  • High latency traces: top p95 latency
  • Manually retained: traces tagged @_dd.rule_psr:1 (retention rules)

Billing Impact

MetricẢnh hưởng
Ingested SpansTính theo volume (GB) ingested/tháng
Indexed SpansSpans retained quá 15 phút → tính phí thêm

★ Exam tip: APM có 2 cấp kiểm soát: Ingestion (sampling rate, trước khi gửi) và Retention (filter, sau khi gửi). Intelligent Retention tự giữ errors + rare + high latency.

8.14 Connect Three Pillars — Unified View

Correlation trong thực tế

PHÁT HIỆN: Alert fires "payment-service p99 latency > 2s"
    │
    ↓
INVESTIGATE với TRACES (APM):
  Filter: service=payment-service, latency > 2s, last 30min
  Thấy: 90% slow traces đều có span "stripe.api.call" > 2000ms
    │
    ↓
ROOT CAUSE với LOGS:
  Click "See Logs" từ trace → tự filter: service=payment-service, trace_id=abc-123
  Log: "Stripe API timeout after 2000ms, retrying (attempt 2/3)"
  Log: "Circuit breaker OPEN: stripe-api-connection"
    │
    ↓
CONFIRM với METRICS:
  Metric: stripe_api.timeout_rate{service:payment} → Tăng từ 0.1% → 45%!
  External dependency issue xác nhận
    │
    ↓
ACTION:
  Bypass Stripe: dùng backup payment processor
  Create incident ticket
  Notify stakeholders

UST (env/service/version tags) enables automatic linking giữa metrics → logs → traces.

8.15 Câu Hỏi Thường Gặp

Q: Log lifecycle thứ tự?
→ Ingest → Process (Pipelines) → Index → Archive

Q: Logging Without Limits cho phép gì?
→ Ingest 100% logs, chỉ index phần quan trọng → tiết kiệm chi phí mà không mất data

Q: Tại sao logs_enabled: true phải set explicitly?
→ Default disabled vì logs có thể chứa sensitive data — explicit opt-in

Q: Grok Parser syntax?
→ %{MATCHER:ATTRIBUTE_NAME:FILTER} — ví dụ %{IP:client_ip} %{NUMBER:status:integer}. Lưu ý: thành phần thứ 3 là FILTER (không phải TYPE)

Q: Service Remapper làm gì?
→ Map một attribute của log thành official “service” field → enable APM correlation

Q: Trace gồm nhiều gì?
→ Spans — mỗi span = 1 unit of work (API call, DB query, external call)

Q: APM Agent nhận traces qua protocol và port nào?
→ TCP port 8126

Q: Flame graph trong APM?
→ Horizontal bars = spans theo thời gian. Rộng = nhiều thời gian = potential bottleneck

Q: Service Map generated từ đâu?
→ Tự động extracted từ traces (Datadog thấy service A gọi B → vẽ edge)

Q: Tại sao cần APM? Metrics + Logs không đủ?
→ APM cho thấy distributed flow — request đi qua service A → B → C → biết chính xác cái nào slow

Q: Events gửi qua những cách nào?
→ API (POST request), DogStatsD (statsd.event()), Custom Agent Check (self.event()), và Email. Hỗ trợ format JSON và Plain Text

Q: Logging endpoints dùng port nào?
→ Tất cả đều dùng port 443 (HTTPS hoặc TCP+TLS). Config site US/EU trong datadog.yaml

Q: Facet vs Attribute khác gì?
→ Attribute = trường dữ liệu có trong log. Facet = attribute được đăng ký để search/filter trong Log Explorer. Cần tạo Facet thủ công.

Q: Giảm log noise khi troubleshoot?
→ Dùng Log Patterns (tab Patterns trong Log Explorer) — tự động cluster logs giống nhau
