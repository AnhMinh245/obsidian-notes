Phần 4: Metrics & Timeseries — Cơ Chế Đo Lường

Tỷ trọng ước tính: ~15% đề thi · Độ khó: Trung bình–Cao

4.1 Time-Series Data — Nền Tảng Của Metrics

Metric là gì ở tầng dữ liệu?

Một metric không phải là “1 con số” — nó là chuỗi vô tận các cặp (timestamp, value):

system.cpu.user {host:web-01, env:production}:

[
  (1710500000, 45.2),   ← 14:00:00 UTC
  (1710500015, 52.1),   ← 14:00:15 UTC
  (1710500030, 78.4),   ← 14:00:30 UTC
  (1710500045, 81.2),
  (1710500060, 55.8),
  ...
]

Tại sao time-series? Vì bạn không chỉ muốn biết “CPU bây giờ là bao nhiêu” — bạn muốn biết “CPU thay đổi thế nào theo thời gian”, “có pattern gì không”, “khi nào nó spike”.

4.2 Metric Categories — Phân Loại Metrics Theo Mục Đích

Khi làm việc với metrics, cần hiểu chúng thuộc 2 nhóm chính + Events:

Work Metrics — Đo “output có ích” của hệ thống

Work metrics cho biết sức khoẻ tổng thể bằng cách đo những gì hệ thống sản xuất ra. Đây là metrics quan trọng nhất vì chúng phản ánh trực tiếp trải nghiệm người dùng.

Sub-categoryMô tảVí dụ metric
ThroughputLượng công việc hoàn thànhRequests/giây, orders/phút
SuccessTỷ lệ thành công% requests trả 2xx
ErrorTỷ lệ lỗi% requests trả 5xx, exception count
PerformanceHiệu suất xử lýLatency p99, response time

Resource Metrics — Đo “tài nguyên hệ thống dùng”

Resource metrics giúp điều tra và chẩn đoán vấn đề. Khi work metrics báo lỗi, bạn xem resource metrics để tìm nguyên nhân gốc.

Sub-categoryMô tảVí dụ metric
Utilization% tài nguyên đang dùngCPU %, memory %, disk I/O %
SaturationMức độ “quá tải”Queue length, thread pool full
ErrorLỗi tài nguyênDisk errors, network packet drops
AvailabilityTài nguyên có sẵn sàng?Disk free space, available connections

Events — Sự kiện rời rạc

Events không phải metrics liên tục — chúng là sự kiện xảy ra tại 1 thời điểm:

Sub-categoryMô tảVí dụ
Code ChangesDeployment, releases”Deployed v2.1.0 to production”
AlertsMonitor triggered”CPU > 90% for 5 mins”
Scaling EventsAuto-scaling”ASG scaled from 3 to 5 instances”
EtcBất kỳ event tuỳ chỉnhConfig change, feature flag toggle
★ Chiến lược monitoring:

  1. Work Metrics → Phát hiện VẤN ĐỀ (error rate tăng, latency cao)
  2. Resource Metrics → Chẩn đoán NGUYÊN NHÂN (CPU full? Disk full? Network?)
  3. Events → Tìm TRIGGER (deploy mới? Config change? Scaling?)

  Mỗi resource trong hệ thống nên có metrics bao phủ CẢ 3 nhóm.

📚 Tham khảo: Monitoring 101

4.3 Năm Metric Types — Cơ Chế Hoạt Động Khác Nhau

Tại sao cần 5 types khác nhau?

Bởi vì bản chất của dữ liệu khác nhau. Không có “one size fits all”:

  • Nhiệt độ CPU: là snapshot — bạn muốn giá trị tại thời điểm đó
  • Số requests: là tổng — bạn muốn count trong interval
  • Latency API: là phân bố — bạn muốn biết p99, không phải average

Gauge — Snapshot Model

Bản chất: Đo giá trị tại thời điểm hiện tại — không nhớ quá khứ.

Cơ chế Agent xử lý:

DogStatsD nhận Gauge values trong 10s flush interval:
  t=0.1s:  statsd.gauge('active_users', 100)
  t=2.3s:  statsd.gauge('active_users', 120)
  t=5.6s:  statsd.gauge('active_users', 115)
  t=8.9s:  statsd.gauge('active_users', 108)

Flush tại t=10s:
  → Chỉ gửi GIÁ TRỊ CUỐI CÙNG: active_users = 108
  → Các values trước đó bị DISCARD

Tại sao giữ value cuối? Không phải trung bình?

Vì Gauge mô tả trạng thái hiện tại của 1 thứ gì đó. “Nhiệt độ CPU lúc này”, “số user đang active lúc này”. Giá trị cuối cùng nhất là “lúc này nhất”.

Nguyên tắc nhận dạng Gauge: “Nếu tôi hỏi ‘bao nhiêu/như thế nào lúc này?’ → dùng Gauge.”

Count — Accumulation Model

Bản chất: Cộng dồn số events xảy ra trong interval.

Cơ chế Agent:

DogStatsD nhận Count values trong 10s:
  t=0.05s: statsd.increment('http.requests')  → +1
  t=0.12s: statsd.increment('http.requests')  → +1
  t=0.18s: statsd.increment('http.requests')  → +1
  ... (500 lần trong 10s)

Flush:
  → Gửi: http.requests = 500 (TỔNG)

Tại sao cộng tất cả?

Vì Count đo “bao nhiêu events đã xảy ra?” — bạn muốn tổng số requests, tổng số lỗi trong window, không phải giá trị cuối.

★ Phân biệt với Gauge: statsd.increment('users') ≠ statsd.gauge('users', current_count):

  • increment: “có thêm 1 event xảy ra” → Count
  • gauge: “số users hiện tại là X” → Gauge

Rate — Normalized Count

Bản chất: Count chia cho thời gian → đơn vị “per second”.

Tại sao Rate tốt hơn Count trong nhiều trường hợp?

Vấn đề với Count thô:
  t=0-10s: 500 requests (flush interval 10s)
  t=10-20s: 300 requests (check interval 15s trùng flush)

  Count hiển thị: 500, 300 → "Traffic giảm?!" 
  Thực ra: flush interval thay đổi → con số không comparable!

Rate giải quyết: Normalize về "per second"
  t=0-10s: 500 / 10 = 50 req/s
  t=10-25s: 300 / 15 = 20 req/s

  Rate hiển thị: 50, 20 → "Traffic giảm thật" (comparable vì đã normalize)

Datadog tự tính Rate từ Count: Rate = (Count_current - Count_previous) / time_delta

Histogram — Client-Side Distribution (Per Host)

Bản chất: Ghi lại phân bố thống kê của các giá trị trong 1 flush interval.

Cơ chế:

Đo latency mỗi API request trên HOST A:
  statsd.histogram('api.latency', 150)   ← 150ms
  statsd.histogram('api.latency', 200)   ← 200ms
  statsd.histogram('api.latency', 850)   ← 850ms (outlier!)
  statsd.histogram('api.latency', 180)
  statsd.histogram('api.latency', 175)
  ... (1000 requests trong 10s)

Flush: Agent TÍNH TOÁN và gửi 5 metrics (mặc định):
  api.latency.avg  = 192.3
  api.latency.count = 1000
  api.latency.median = 180    ← p50
  api.latency.95percentile = 850
  api.latency.max = 850

⚠️ 5 metrics là DEFAULT — có thể cấu hình trong datadog.yaml:
  histogram_aggregates: ["max", "median", "avg", "count"]
  histogram_percentiles: [0.75, 0.95, 0.99]   ← thêm p75, p99

Vấn đề cốt lõi — Tại sao Histogram sai khi cross-host?

Cluster 2 hosts, mỗi host gửi 1000 requests:

HOST A latency distribution:
  50ms: 400 requests
  100ms: 500 requests
  5000ms: 100 requests     ← nhiều slow requests!
  
  HOST A p95 = 5000ms (vì 100/1000 = 10% slow → p95 là slow)

HOST B latency distribution:
  50ms: 950 requests
  100ms: 50 requests
  
  HOST B p95 = 100ms (gần như tất cả nhanh)

❌ Aggregate (sai):
  Datadog nhận: Host A p95 = 5000ms, Host B p95 = 100ms
  avg(p95) = (5000 + 100) / 2 = 2550ms
  
  Đây KHÔNG PHẢI p95 thực sự của 2000 requests!

✅ P95 thực sự:
  2000 requests tổng, xếp theo thứ tự → request thứ 1900 (95%) là khoảng 100ms
  (Vì HOST A chỉ có 100 slow requests / 2000 total = 5% slow → p95 < 5000ms)

→ Histogram aggregation across hosts = kết quả sai về mặt toán học.

Distribution — Server-Side Distribution (Globally Accurate)

Bản chất: Gửi raw data lên Datadog server, để server tính percentiles trên toàn bộ data.

Cơ chế:

Mỗi request gửi raw value lên Datadog:
  statsd.distribution('api.latency', 150)

DogStatsD vẫn aggregate → gửi compressed representation (không phải từng value riêng lẻ)
Nhưng Datadog server có đủ thông tin để tính percentiles CHÍNH XÁC across all hosts.

Giống như: thay vì mỗi host tính điểm trung bình của học sinh trong lớp mình,
Distribution cho trường (server) biết điểm của TẤT CẢ học sinh → tính percentile chính xác.

★ Key difference summary:

HistogramDistribution
Tính percentiles ở đâuAgent (tại host)Datadog server
Chính xác single host✅✅
Chính xác across hosts❌✅
Khi nào dùngSingle instance appKhi cần global percentiles
RecommendationLegacy✅ Recommended

4.4 Query Metric — Cơ Chế Aggregation Hai Chiều

Vấn đề: 50 hosts, mỗi host gửi 1 data point mỗi 15s

Khi bạn visualize CPU của cả 50 hosts trên 1 graph, Datadog phải tổng hợp:

  • Across không gian (50 hosts → 1 line): Space aggregation
  • Across thời gian (zoom out → fewer points): Time aggregation

Space Aggregation — “Gom nhiều hosts thành 1”

Query: avg:system.cpu.user{env:production}

Tại timestamp T, 50 hosts có values:
  web-01: 65%, web-02: 72%, web-03: 45%, ... (50 values)

Space aggregation "avg" tính: (65 + 72 + 45 + ...) / 50 = 61.4%
→ 1 data point duy nhất cho timestamp T

Kết quả: 1 line trên graph = trung bình CPU của tất cả production hosts

Query: avg:system.cpu.user{env:production} by {host}

→ Không gom, group by host → 50 lines trên graph, mỗi line = 1 host

Các space aggregation functions:

FunctionÝ nghĩaKhi nào dùng
avgTrung bìnhXem mức CPU trung bình của cluster
sumTổngTổng requests all servers (tổng throughput)
maxCao nhấtHost nào đang CPU cao nhất?
minThấp nhấtHost nào nhàn rỗi nhất?

Time Aggregation — “Gom nhiều data points thành ít hơn khi zoom out”

Zoom 1 giờ → Datadog hiển thị 1 data point mỗi 15s (4 points/phút × 60 = 240 points)
Zoom 1 ngày → 240 points/giờ × 24 giờ = 5760 points → quá nhiều!
→ Datadog ROLLUP: gom 1 giờ thành 1 point
→ 24 points thay vì 5760

Mỗi "bucket" 1 giờ có hàng trăm raw points → aggregate bằng avg, sum, max, min, count

★ Rollup exam tip: “Zoom out từ 1h → 1 tuần, Datadog làm gì với data?” → Rollup — tự động aggregate thành buckets lớn hơn.

4.5 Query to the Graph — Cấu Trúc Metric Query

Khi tạo graph trên dashboard, SLO, hoặc monitor, bạn đang query hệ thống metric của Datadog. Mỗi query gồm 5 thành phần:

Anatomy của Query

 avg : system.io_r_s { app:shopist } by {host} .rollup(avg, 3600)
  │        │              │             │            │
  │        │              │             │            └─ 3. TIME AGGREGATION
  │        │              │             │               (aggregator, interval)
  │        │              │             │
  │        │              │             └─ 4. SPACE AGGREGATION
  │        │              │                (Grouping by tag)
  │        │              │
  │        │              └─ 2. FILTER / SCOPE
  │        │                 (instances nào?)
  │        │
  │        └─ 1. METRIC NAME
  │           (tên metric cần query)
  │
  └─ 4. SPACE AGGREGATION
     (aggregator: avg|sum|max|min)

5 thành phần chi tiết

#Thành phầnBắt buộc?Mô tảVí dụ
1Metric✅Tên metric cần querysystem.io_r_s, http.requests
2Scope✅Lọc instances nào (dùng tags trong {}){app:shopist}, {env:prod,service:web}
3Time Aggregation⚠️ OptionalGom datapoints theo thời gian khi zoom out.rollup(avg, 3600) = avg mỗi 1 giờ
4Space Aggregation✅Gom dữ liệu từ nhiều sourcesavg: (prefix), by {host} (group)
5Function⚠️ OptionalBiến đổi dữ liệu.count(), .rank(), .timeshift()

Giải thích từng phần

1 — Metric Name: Tên metric mà Agent hoặc integration gửi lên.

system.cpu.user         ← System check
nginx.net.connections   ← NGINX integration
myapp.page_views        ← Custom metric (DogStatsD)

2 — Scope (Filter): Dùng tags trong {} để chọn subset data.

{env:production}                      ← Chỉ production
{env:production, service:web-api}     ← Production VÀ web-api
{host:web-01}                         ← Chỉ host web-01
{*}                                   ← Tất cả (không filter)

3 — Time Aggregation: Khi biểu đồ có nhiều datapoints hơn pixels, cần gom lại.

.rollup(avg, 3600)    ← Trung bình mỗi 1 giờ
.rollup(max, 300)     ← Giá trị cao nhất mỗi 5 phút
.rollup(sum, 60)      ← Tổng mỗi 1 phút

Nếu không chỉ định → Datadog tự chọn interval phù hợp với zoom level

4 — Space Aggregation: Khi có nhiều sources (hosts, containers), cần gom lại.

avg:system.cpu.user{env:prod}               ← 1 line = trung bình tất cả hosts
max:system.cpu.user{env:prod}               ← 1 line = host cao nhất
avg:system.cpu.user{env:prod} by {host}     ← N lines = mỗi host 1 line
avg:system.cpu.user{env:prod} by {service}  ← Group theo service

5 — Function (optional): Biến đổi kết quả.

.as_count()              ← Hiển thị Count thay vì Rate
.as_rate()               ← Hiển thị Rate
.rank(5)                 ← Top 5
.timeshift(1w)           ← So sánh với 1 tuần trước
.log10()                 ← Scale logarithmic
.forecast(linear, 1w)    ← Dự đoán 1 tuần tiếp theo

Ví dụ Query hoàn chỉnh

★ "Trung bình CPU production, group theo host, rollup max mỗi 5 phút":
   avg:system.cpu.user{env:production} by {host}.rollup(max, 300)

★ "Tổng requests web-api, so sánh với tuần trước":
   sum:http.requests{service:web-api}.timeshift(1w)

★ "Top 5 services theo error rate":
   sum:http.errors{env:production} by {service}.rank(5)

★ Exam tip: Đề hay cho query và hỏi “query này hiển thị gì?”. Đọc từ trái: Space Agg → Metric → Scope → Group by → Time Agg/Function.

4.6 Metric Submission — Ba Con Đường Khác Nhau

Agent Checks (Collector)

Flow: System/Service → Agent Collector (đọc trực tiếp) → Forwarder → Datadog
Ví dụ: CPU từ /proc/stat, NGINX từ HTTP status endpoint
Đặc điểm: Built-in, không cần code app

DogStatsD

Flow: Application code → UDP:8125 → DogStatsD → Forwarder → Datadog
Ví dụ: Custom business metrics, latency measurements
Đặc điểm: App phải gọi StatsD library

Datadog API

Flow: Script/Service → HTTPS POST /api/v2/series → Datadog
Ví dụ: CI/CD pipeline metrics, external system integration
Đặc điểm: Chỉ cần HTTP client, không cần Agent

4.7a Metric Metadata — Mô Tả Metrics Cho Người Dùng

Metric Metadata là gì?

Mỗi metric có thể gán metadata để mô tả ý nghĩa, đơn vị, và context:

FieldMô tảVí dụ
typeLoại metric (gauge, count, rate, distribution)gauge
unitĐơn vị đobyte, millisecond, percent
per_unitĐơn vị mẫu số (cho rate metrics)second (bytes/second)
descriptionMô tả ngắn gọn”Total CPU time consumed by process”
short_nameTên hiển thị ngắn”CPU Usage”
integrationIntegration nào tạo metricsystem, nginx, postgres

Tại sao quan trọng?

Không có metadata:
  Graph title: system.cpu.user = 0.85
  Đơn vị gì? Percent? Ratio? Cores?

Có metadata (unit: percent):
  Graph title: system.cpu.user = 85%
  → Tự động format đúng đơn vị trên graph!

Thay đổi metadata

  • Built-in metrics (từ integrations): metadata đã có sẵn, không cần set
  • Custom metrics (DogStatsD): default không có unit → nên set qua API hoặc UI
  • Set qua Metrics Summary page → click metric → Edit metadata
  • Hoặc qua API: PUT /api/v1/metrics/<metric_name> (cần Application Key)

★ Key: Thay đổi metric type (vd gauge → count) sẽ ảnh hưởng cách Datadog aggregate data trên graphs. Chỉ đổi khi thực sự cần.

4.8 Câu Hỏi Thường Gặp

Q: CPU usage → dùng Gauge hay Count?
→ Gauge — cpu% là snapshot tại thời điểm hiện tại

Q: Đếm total HTTP requests → dùng type gì?
→ Count — cộng dồn events

Q: Histogram tạo ra bao nhiêu metrics?
→ 5: avg, count, median (p50), p95, max

Q: Tại sao Distribution tốt hơn Histogram cho cross-host percentiles?
→ Histogram tính percentiles per-host → avg(p95 của từng host) ≠ p95 toàn cục. Distribution gửi raw data → server tính globally chính xác.

Q: Gauge nhận 100 values trong 1 flush interval, gửi giá trị nào?
→ Giá trị cuối cùng (last value)

Q: Rate = gì?
→ Count chia cho thời gian → per second, normalize để comparable

Q: Zoom out graph, Datadog làm gì?
→ Rollup — aggregate nhiều data points trong 1 time bucket

Q: system.mem.free vs system.mem.usable?
→ usable > free vì bao gồm page cache OS có thể giải phóng ngay khi app cần

Q: Work Metrics vs Resource Metrics?
→ Work = đo output (throughput, error, latency). Resource = đo tài nguyên (CPU, memory, disk). Work phát hiện vấn đề, Resource chẩn đoán nguyên nhân.

Q: Metric query gồm mấy phần?
→ 5 phần: Metric name, Scope (filter bằng tags), Time Aggregation (rollup), Space Aggregation (avg/sum/max + group by), Function (optional)

Q: avg:system.cpu{env:prod} by {host} hiển thị gì?
→ Nhiều lines, mỗi line = 1 host trong production. by {host} tách riêng từng host thay vì gom lại.

Q: .rollup(avg, 3600) nghĩa là gì?
→ Gom datapoints thành bucket 3600 giây (1 giờ), mỗi bucket lấy trung bình. Dùng khi zoom out nhiều.

Q: .timeshift(1w) dùng khi nào?
→ So sánh metric hiện tại với 1 tuần trước — hữu ích để phát hiện seasonal patterns.
