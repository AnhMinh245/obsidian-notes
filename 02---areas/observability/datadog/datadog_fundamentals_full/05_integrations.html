Phần 5: Integrations — Cơ Chế Kết Nối Với 800+ Technologies

Tỷ trọng ước tính: ~8-10% đề thi · Độ khó: Trung bình

5.1 Vấn Đề: Datadog Phải Thu Thập Data Từ Hàng Trăm Loại Hệ Thống

Datadog monitors:

  • Databases: MySQL, PostgreSQL, MongoDB, Redis, Elasticsearch
  • Web servers: NGINX, Apache, IIS
  • Cloud: AWS EC2, RDS, Lambda, Azure, GCP
  • Message queues: Kafka, RabbitMQ
  • Container: Docker, Kubernetes
  • … 800+ thứ khác

Mỗi thứ có cách lấy data khác nhau. Không có cách nào “one-size-fits-all”. Điều này dẫn đến 2 architecture patterns khác nhau.

5.2 Hai Patterns — Hiểu Nguyên Lý Thiết Kế

Pattern 1: Agent-based — “Thu thập từ bên trong host”

Khi nào phù hợp:

  • Service chạy trong hoặc cạnh host bạn kiểm soát
  • Data cần realtime (mỗi 15s)
  • Service expose local endpoint (HTTP, socket, port)

Cơ chế:

Agent đọc data từ service qua local connection:

[NGINX Integration]
  Agent → HTTP GET http://localhost/nginx_status → Parse response → Metrics

[MySQL Integration]
  Agent → MySQL connection localhost:3306 → SHOW STATUS query → Parse → Metrics

[Redis Integration]
  Agent → Redis INFO command localhost:6379 → Parse → Metrics

Ưu điểm:

  • Low latency — data mỗi 15 giây
  • Detailed — có thể lấy metrics chi tiết mà cloud API không expose
  • Secure — chỉ local connection, không expose ra ngoài

Nhược điểm: Phải cài Agent và config trên từng host

Pattern 2: Crawler-based — “Kéo từ bên ngoài qua cloud API”

Khi nào phù hợp:

  • Service là fully managed (AWS Lambda, RDS, Azure App Service)
  • Không thể/không cần cài Agent
  • Data không cần realtime (tối thiểu 2-10 phút delay tuỳ provider)

Cơ chế:

Datadog Backend (không phải Agent) kéo data từ cloud API:

[AWS Integration]
  Datadog Backend → AWS CloudWatch API → GetMetricData → Process → Store

Quy trình setup:
  1. Bạn tạo IAM Role cho Datadog với quyền đọc CloudWatch
  2. Cung cấp Role ARN cho Datadog
  3. Datadog backend poll CloudWatch mỗi ~10 phút (AWS default)
  4. Datadog hiển thị metrics

Ưu điểm:

  • Không cần cài gì trên infrastructure
  • Works với fully managed services (Lambda, RDS…)
  • Auto-discovers new resources

Nhược điểm:

  • Chậm hơn (2-10 phút delay tuỳ provider)
  • Phụ thuộc cloud API rate limits
  • Metrics ít granular hơn

Bảng So Sánh Trực Tiếp

Agent-basedCrawler-based
Ai thu thậpAgent trên hostDatadog backend
Tần suất15 giây~2-10 phút (tuỳ provider)
SetupSửa conf.d/conf.yamlConfigure trên Datadog UI
Cần Agent✅❌
Ví dụNGINX, MySQL, RedisAWS, Azure, GCP, Slack

5.3 Ba Loại Integration Chính Thức (Integration Types)

Datadog phân loại integrations thành 3 loại chính thức. Đề thi hay hỏi sự khác biệt giữa chúng.

Tổng quan 3 loại

1. AGENT-BASED INTEGRATION
   Agent trên host chạy check code → thu thập metrics từ local service
   Ví dụ: NGINX, MySQL, Redis, PostgreSQL, Docker
   
   [Agent] ──local──→ [Service] ──→ Parse ──→ Metrics ──→ Datadog

2. CRAWLER-BASED INTEGRATION  
   Datadog backend (không phải Agent) kéo data từ cloud API
   Ví dụ: AWS, Azure, GCP, Slack, PagerDuty
   
   [Datadog Backend] ──API call──→ [Cloud Provider API] ──→ Metrics ──→ Datadog

3. LIBRARY / API-BASED INTEGRATION
   Application code gửi data trực tiếp qua Datadog SDK/API
   Ví dụ: DogStatsD client libraries, Datadog API, APM tracing libraries
   
   [Your App Code] ──SDK──→ [DogStatsD/API] ──→ Metrics/Traces ──→ Datadog

Bảng So Sánh 3 Loại

Agent-basedCrawler-basedLibrary/API-based
Ai thu thậpAgent trên hostDatadog backendApplication code
Cần Agent✅❌✅ (cho DogStatsD) hoặc ❌ (cho API)
Tần suất15 giây~2-10 phút (tuỳ provider)Tuỳ app (realtime)
Config ở đâuconf.d/*.d/conf.yamlDatadog UI (Integration tile)Trong source code
Cài đặtAgent + conf.yamlThêm credentials trên UICài SDK vào app

Use caseInfra bạn kiểm soátManaged servicesCustom metrics, APM

Library/API-based — Chi tiết

Đây là loại mà developer chủ động gửi data từ application code:

Cách nhận biết loại nào cho đề thi

Từ khoá trong câu hỏi          → Loại Integration
─────────────────────────────────────────────────────
"conf.yaml", "Agent check"      → Agent-based
"CloudWatch", "IAM Role", "UI"  → Crawler-based
"SDK", "client library", "code" → Library/API-based
"DogStatsD", "statsd"           → Library-based
"API endpoint", "POST request"  → API-based

★ Exam tip: Khi đề hỏi “intergration type” hay “what kind of intergration”, nhớ rằng Datadog có 3 loại chứ không phải 2. Library/API-based thường bị bỏ quên nhưng hay xuất hiện trong đề.

5.4 Anatomy của conf.yaml — Cấu Trúc Bên Trong

Tại sao structure lại như vậy?

Lý do tách init_config và instances:

  • init_config: Cấu hình một lần cho toàn bộ integration (thư viện, timeouts, global settings)
  • instances: Mỗi instance là 1 server/endpoint khác nhau — Agent chạy check cho từng cái

→ 1 conf.yaml có thể monitor nhiều targets của cùng loại.

5.5 Quy Trình Cài Integration — Từng Bước Với Lý Do

BƯỚC 1: Cài integration package (nếu cần)
  datadog-agent integration install datadog-nginx==X.Y.Z
  
  Lý do: Một số integrations cần thêm Python dependencies.
  Integrations phổ biến (NGINX, MySQL, Redis...) đã built-in sẵn trong Agent.

BƯỚC 2: Tạo/sửa conf.yaml
  cp /etc/datadog-agent/conf.d/nginx.d/conf.yaml.example \
     /etc/datadog-agent/conf.d/nginx.d/conf.yaml
  # Sửa file theo nhu cầu

BƯỚC 3: RESTART AGENT (BẮT BUỘC!)
  systemctl restart datadog-agent
  
  Lý do: Agent load config files KHI KHỞI ĐỘNG, không watch file changes.
  Không restart = Agent vẫn dùng config cũ!

BƯỚC 4: Verify
  datadog-agent check nginx
  
  Lý do: Chạy integration 1 lần, xem có lỗi không, xem metrics nào được emit.
  Không cần đợi 15s cho Collector tự chạy.

★ Exam trap: “Sau khi sửa integration config, bước nào BẮT BUỘC?” → Restart Agent (không phải restart nginx)

Khi không có integration sẵn có cho:

5.7 Service Checks — Binary Health Status

Tại sao cần loại riêng biệt (khác với metrics)?

Metric: nginx.net.connections = 47   ← Số liệu liên tục
Service Check: nginx.can_connect = OK/CRITICAL  ← Trạng thái rời rạc

Bạn có thể tạo Monitor trên cả hai:
  Metric monitor: Alert khi connections > 10,000
  Service check monitor: Alert khi nginx.can_connect = CRITICAL

4 States của Service Check:

StatusIntegerÝ nghĩa
OK0Service healthy
WARNING1Service có vấn đề nhẹ
CRITICAL2Service down hoặc critical issue
UNKNOWN3Không thể xác định (timeout, error fetching)

5.8 Câu Hỏi Thường Gặp

Q: AWS integration thuộc loại nào?
→ Crawler-based — Datadog backend poll CloudWatch API, không cần Agent

Q: Agent-based vs Crawler-based — tần suất thu thập?
→ Agent-based: 15 giây | Crawler-based: ~2-10 phút (tuỳ provider: AWS ~10 min, GCP ~5 min, Azure ~2 min)

Q: Sau khi sửa conf.yaml, bước bắt buộc?
→ Restart Agent — không tự reload config

Q: Trong conf.yaml, instances section chứa gì?
→ Danh sách targets cần monitor (endpoint, credentials, custom tags)

Q: Custom check Python đặt ở đâu?
→ /etc/datadog-agent/checks.d/

Q: Service Check khác Metric như thế nào?
→ Metric = số liệu liên tục. Service Check = trạng thái rời rạc (OK/Warning/Critical/Unknown)

Q: init_config vs instances?
→ init_config = settings dùng chung cho integration. instances = danh sách targets cụ thể

Q: Datadog có bao nhiêu loại integration?
→ 3 loại: Agent-based (15s, local check), Crawler-based (~2-10 phút tuỳ provider, cloud API), Library/API-based (app code gửi qua SDK/API)

Q: Library/API-based integration khác gì?
→ Developer chủ động gửi data từ code qua DogStatsD client hoặc Datadog API — không phải Agent tự thu thập
