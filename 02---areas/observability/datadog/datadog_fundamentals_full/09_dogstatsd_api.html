9.1 Tại sao Applications Cần Cơ Chế Riêng Để Gửi Metrics?

Agent Collector thu thập metrics từ hệ thống (CPU, memory) và services (NGINX, MySQL) — những thứ mà Agent có thể “nhìn vào” từ bên ngoài.

Nhưng Agent không thể biết:

  • Có bao nhiêu user đang active trong app của bạn?
  • Doanh thu 1 giờ qua là bao nhiêu?
  • Tỷ lệ cache hit trong application cache của bạn?
  • Số bước trong checkout flow user đã hoàn thành?

→ Chỉ application code mới biết những thứ này. DogStatsD tạo ra cổng để app gửi custom metrics.

9.2 DogStatsD — Protocol và Cơ Chế Aggregation

Tại sao architecture này?

Application Code
      │
      │ UDP (fire-and-forget, không block)
      ↓
  DogStatsD server
  (lắng nghe UDP:8125)
      │
      │ Aggregate trong 10 giây
      │ (không phải từng packet)
      ↓
  Forwarder
      │
      │ HTTPS:443
      ↓
  Datadog Backend

Lý do không gửi từng packet thẳng lên Datadog:

  1. Quá nhiều requests: App gửi 1000 counter increments/giây → 1000 HTTPS requests/giây → overwhelm cả app lẫn Datadog
  2. HTTPS overhead: Mỗi request có SSL handshake, HTTP headers → very expensive
  3. DogStatsD batching: Aggregate 10 giây → 1 HTTPS request chứa summary

Aggregation theo từng metric type

Trong 10 giây flush window, DogStatsD nhận:

GAUGE (app.connections):
  t=1s: 150, t=3s: 155, t=7s: 148, t=9s: 152
  → Flush: GIÁ TRỊ CUỐI: 152

COUNT (http.requests):
  t=0.1s: +1, t=0.2s: +1, ..., t=9.9s: +1 (500 lần)
  → Flush: TỔNG: 500

HISTOGRAM (api.latency):
  t=...: 150, 200, 850, 180, 175, ... (1000 values)
  → Flush: avg=192, count=1000, p50=180, p95=850, max=850 (5 metrics!)

DISTRIBUTION (api.latency):
  t=...: 150, 200, 850, ... (1000 values)
  → Flush: compressed sketch (DDSketch algorithm)
  → Server tính percentiles từ sketch

SET (unique.visitors):
  t=...: "user_a", "user_b", "user_a", "user_c", "user_b"
  → Flush: CARDINALITY của unique set: 3

9.3 Wire Format — Hiểu Để Debug

Format đầy đủ

<metric_name>:<value>|<type>|@<sample_rate>|#<tag1>,<tag2>

Ví dụ:
  http.requests:1|c|#endpoint:/api/users,method:GET,env:prod
  │            │ │  │ └── Tags (comma separated, no space)
  │            │ │  └── Sample rate prefix
  │            │ └── Type: c=count
  │            └── Value
  └── Metric name

Sample Rate — Optimization Quan Trọng

Vấn đề: API xử lý 100,000 requests/giây
  → Gửi 100,000 UDP packets/giây → overhead quá lớn!

Giải pháp: Sample Rate 0.1 (10%)
  → Chỉ gửi 10,000 packets/giây (ngẫu nhiên 10%)
  → DogStatsD nhân với 1/sample_rate: 10,000 × 10 = 100,000 (estimate)

Wire format với sample rate:
  http.requests:1|c|@0.1|#env:prod
                    ^^^
                    Chỉ gửi 10% packets
                    DogStatsD tự scale up × 10

Kết quả: Overhead giảm 10x, accuracy chỉ giảm 1 chút (statistical sampling)

★ Sample rate hỗ trợ cho COUNT, HISTOGRAM, DISTRIBUTION, và TIMER — không dùng cho Gauge (Gauge cần giá trị chính xác cuối cùng, sampling có thể miss giá trị đó).

9.5 Datadog API — Khi Nào Dùng Và Khi Nào Không

Architecture của Datadog API

Datadog API = REST API để tương tác với Datadog platform
URL: https://api.datadoghq.com

Security model:
  Header: DD-API-KEY      ← Required cho TẤT CẢ requests
  Header: DD-APPLICATION-KEY  ← Required cho GET/PUT/DELETE (read + manage)

Tại sao 2 loại keys vẫn được dùng cùng nhau (không phải 1)?

API Key sở hữu bởi: Organization
Application Key sở hữu bởi: User

Khi audit security:
  "Ai đã xoá monitor X lúc 3am?"
  → Header: DD-API-KEY: org-key-123, DD-APPLICATION-KEY: john.doe-key
  → Datadog audit log: "john.doe deleted monitor at 03:00"
  
Nếu chỉ có 1 key = Organization key → không biết USER nào làm

9.6 Câu Hỏi Thường Gặp

Q: DogStatsD dùng UDP port nào?
→ 8125

Q: Tại sao UDP thay TCP?
→ App không bị block chờ monitoring — performance của app là ưu tiên #1

Q: DogStatsD flush mỗi bao lâu?
→ 10 giây — aggregate rồi batch gửi cho Forwarder

Q: Set metric dùng để làm gì?
→ Đếm unique values (unique visitors, unique IPs) — không cần lưu tất cả values

Q: Sample rate 0.1 có nghĩa gì?
→ Chỉ gửi 10% packets → DogStatsD scale up × 10 → giảm overhead 10x

Q: Submit metrics qua API cần keys nào?
→ Chỉ API Key (DD-API-KEY header)

Q: Tạo monitor qua API cần keys nào?
→ Cả hai: API Key + Application Key

Q: Tại sao API cần 2 keys?
→ Application Key gắn với user → audit trail, biết ai làm gì

Q: DogStatsD trong container cần config gì?
→ dogstatsd_non_local_traffic: true trong Agent config (mặc định chỉ accept localhost)
