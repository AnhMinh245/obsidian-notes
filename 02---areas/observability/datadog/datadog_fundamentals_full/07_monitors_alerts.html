Phần 7: Monitors & Alerts — Cơ Chế Alert Thông Minh

Tỷ trọng ước tính: ~15% đề thi · Độ khó: Trung bình–Cao

7.1 Vấn Đề: Threshold Cố Định Không Đủ

Hãy xem scenario điển hình:

Website traffic của bạn:
  Thứ Hai - Thứ Sáu: 50,000 req/min (giờ làm việc)
  Thứ Bảy - Chủ Nhật: 8,000 req/min (cuối tuần)
  
Team ops set alert: "Traffic < 10,000 req/min → cảnh báo"

Thứ Bảy 9:00am: Traffic = 8,500 req/min → ALERT FIRED!
→ Oncall engineer bị đánh thức → check → mọi thứ bình thường (đây là weekend traffic)
→ FALSE POSITIVE! Alert fatigue!

Thứ Tư 2:00pm: Traffic = 30,000 req/min (thấp hơn bình thường 40%)
→ KHÔNG có alert (vẫn > 10,000)
→ Thực ra: đây là SỰ CỐ NGHIÊM TRỌNG — traffic bị mất 40%!
→ FALSE NEGATIVE! Miss!

Threshold cố định thất bại trong thế giới có seasonality (mùa vụ).

→ Đây là lý do Datadog có nhiều loại monitor khác nhau.

7.2 Metric Monitor (Threshold) — Ngưỡng Cố Định

Khi nào đúng

Metric Monitor phù hợp khi giá trị tuyệt đối có ý nghĩa, bất kể context:

  • CPU > 95% = luôn là vấn đề, không cần biết đây là sáng hay tối
  • Disk > 90% = luôn cần action
  • Error rate > 10% = luôn critical

Cơ chế hoạt động

Evaluation window: "last 5 minutes"
Threshold: Alert if avg > 90%

Mỗi 1 phút (hoặc theo config), Datadog:
  1. Lấy tất cả data points trong 5 phút qua
  2. Tính avg
  3. So sánh với threshold
  4. Nếu vượt → chuyển trạng thái

Ví dụ evaluation:
  14:00: data points = [85, 88, 87, 90, 89] → avg = 87.8% → OK
  14:01: data points = [88, 92, 95, 94, 93] → avg = 92.4% → ALERT!

Warning và Alert thresholds

Warning threshold: 80%
Alert threshold: 90%

State machine:
  CPU 55% → OK
  CPU 82% → cpu.user > 80%! → WARNING (cảnh báo nhẹ, chưa urgent)
  CPU 95% → cpu.user > 90%! → ALERT (urgent!)
  CPU 72% → under alert, under warning → RECOVERY → OK

7.3 Anomaly Monitor — Machine Learning Phát Hiện Bất Thường

Cơ chế: Học Từ Lịch Sử Để Biết “Bình Thường” Là Gì

Anomaly Monitor xây dựng model từ historical data:

  "Thứ Hai 2pm lịch sử thường có traffic 50,000 req/min"
  "Thứ Bảy 2pm lịch sử thường có traffic 8,000 req/min"
  
  Bounds (dải "bình thường") cho mỗi thời điểm:
    Thứ Hai 2pm: [40,000 - 60,000]  ← dải thay đổi hàng tuần
    Thứ Bảy 2pm: [5,000 - 11,000]   ← dải khác hoàn toàn!
  
  Thứ Hai 2pm, traffic = 45,000 → trong bounds → OK ✅
  Thứ Bảy 2pm, traffic = 8,500  → trong bounds → OK ✅ (không cảnh báo!)
  Thứ Tư 2pm, traffic = 30,000  → NGOÀI BOUNDS (40,000-60,000) → ALERT! ✅

Ba thuật toán Anomaly:

AlgorithmMô tảKhi nào dùng
BasicLagging rolling quantile computation — không nhận dạng seasonal patternsMetrics mới hoặc metrics không có seasonal cycles rõ ràng
AgileDùng SARIMA (Seasonal Autoregressive Integrated Moving Average) — adapt nhanh vào level shiftsMetrics có seasonal patterns và expected to shift
RobustDùng seasonal-trend decomposition — conservative hơn Agile, không bị ảnh hưởng bởi anomalies gần đâyMetrics có seasonal patterns và expected to be stable

⚠️ Lưu ý: Agile và Robust cần ~3 tuần historical data để nhận dạng weekly seasonality.

★ Key insight: Anomaly Monitor trả lời câu hỏi “Có bất thường so với lịch sử không?” — không phải “có vượt ngưỡng cố định không?“.

7.4 Forecast Monitor — Dự Đoán Tương Lai

Cơ chế: Time Series Forecasting

Forecast Monitor phân tích xu hướng (trend) của metric và extrapolate:

Disk usage qua 30 ngày:
  Day 1:  60%
  Day 7:  65%
  Day 14: 70%
  Day 21: 75%
  Day 28: 80%
  
  Trend: +0.7% per day
  
  Forecast model:
    Day 35: ~85%
    Day 42: ~90% ← BỊ VƯỢT NGƯỠNG!
  
  Datadog alert NGAY BÂY (ngày 28):
    "Disk sẽ đạt 90% trong ~14 ngày nữa"

Lợi ích:

  • Proactive — cảnh báo trước khi vấn đề xảy ra
  • Actionable — “14 ngày nữa mới đầy” → đủ thời gian mua thêm storage
  • Nếu không có Forecast: Alert chỉ khi thực sự vượt 90% → quá muộn!

Hai thuật toán Forecast:

AlgorithmMô tảKhi nào dùng
LinearOLS regression — extrapolate xu hướng tuyến tínhMetrics có trend đều, không có seasonal patterns
SeasonalHolt-Winters exponential smoothing — nhận dạng seasonal cyclesMetrics có repeating patterns (daily/weekly)

Forecast vs Anomaly:

  • Anomaly: Nhìn vào quá khứ, so sánh với hiện tại → “Hôm nay có lạ không?”
  • Forecast: Nhìn vào hiện tại, dự đoán tương lai → “Bao giờ sẽ có vấn đề?“

7.5 Outlier Monitor — Ai Khác Biệt Trong Nhóm?

Cơ chế: Peer Comparison

Scenario: 10 web servers với role giống nhau

  Server 1-9: CPU = 25-35% (tương đồng nhau)
  Server 10:  CPU = 95%    (khác biệt!)

Threshold Monitor: Có thể không alert nếu threshold = 90% và server 10 vừa vượt
  → Đúng vì 95% > 90% → sẽ alert
  → Nhưng: nếu threshold = 90% và server 10 ở 88%? → MISS! (88% < 90%)

Anomaly Monitor per server: Check từng server vs lịch sử riêng của server đó
  → Server 10 có thể bình thường ở 88% (nếu lịch sử cũng cao)

Outlier Monitor: So sánh server vs NHAU
  → Server 1-9: ~30% CPU
  → Server 10: 88% CPU → ALERT! (khác biệt 58% so với peers!)

Outlier algorithms:

  • DBSCAN: Cluster-based — tìm points nằm ngoài cluster chính
  • MAD (Median Absolute Deviation): Robust — ít bị ảnh hưởng bởi multiple outliers

★ Use case điển hình:

  • Load balancer phân phối đều request nhưng 1 server bị lệch → Outlier
  • All databases slow (cluster issue) vs 1 database slow → Chỉ Outlier phát hiện cái sau

7.6 Process Monitor — Kiểm Tra Process Có Đang Chạy?

Vấn đề: Process chết mà không biết

Scenario: NGINX process bị crash lúc 3am
  → Metric monitor không phát hiện vì không có metric nào liên quan
  → Error rate = 0 (không có request nào được xử lý)
  → CPU metric vẫn có (host còn sống, chỉ NGINX chết)
  → Sáng mai mới phát hiện khi user report!

Cơ chế

Process Monitor kiểm tra số lượng process matching tên hoặc command line:

Config:
  Process name: nginx
  Threshold: Alert if running instances < 1

Datadog kiểm tra liên tục:
  14:00 → nginx processes = 4 → OK ✅
  14:05 → nginx processes = 4 → OK ✅
  14:10 → nginx processes = 0 → ALERT! 🚨 "Không còn NGINX process nào!"

Yêu cầu

★ Process Agent phải được enable:
  # datadog.yaml
  process_config:
    process_collection:
      enabled: true    ← Default: partial (chỉ containers)

★ Exam tip: “NGINX process không chạy” → Process Monitor (không phải Metric Monitor).

7.7 Service Check Monitor — Health Check Binary

Khác gì với Metric Monitor?

Metric Monitor: "CPU HIỆN TẠI là bao nhiêu?"  → Con số (85.2%)
Service Check:  "Service CÓ SỐNG KHÔNG?"        → Binary (OK / CRITICAL)

Cơ chế

Integrations gửi service checks về Datadog với trạng thái:

StatusGiá trịÝ nghĩa
OK0Service hoạt động bình thường
WARNING1Có vấn đề nhưng chưa critical
CRITICAL2Service không hoạt động
UNKNOWN3Không xác định được trạng thái
Ví dụ: NGINX integration gửi service check:
  nginx.can_connect:
    14:00 → OK        (NGINX trả lời health endpoint)
    14:05 → OK
    14:10 → CRITICAL  (NGINX không trả lời!) → ALERT!

Ví dụ: MySQL integration:
  mysql.can_connect:
    OK = Agent kết nối MySQL được
    CRITICAL = Không kết nối được (wrong password, port blocked, service down)

So sánh nhanh

Process MonitorService Check Monitor
Đo gìSố processes đang chạyHealth status của integration
Kiểu dữ liệuSố (count)Binary (OK/WARN/CRITICAL)
NguồnProcess AgentIntegration checks
Ví dụ”NGINX processes = 0""nginx.can_connect = CRITICAL”
Use caseProcess crash detectionConnectivity/health checks

★ Exam tip: “NGINX health check fail” → Service Check Monitor. “NGINX process không chạy” → Process Monitor.

7.8 Composite Monitor — Boolean Logic

Vấn đề: False Positives

Scenario: Alert khi error rate cao

  Thực tế: Error rate = 8%
  Metric Monitor (threshold 5%) → ALERT!
  
  Nhưng: traffic = 100 req/min (thấp — 8% = 8 lỗi)
  Ở traffic thấp, error rate cao là NORMAL (1 request lỗi = 10%!)
  → FALSE POSITIVE → Alert fatigue!
  
Giải pháp: Composite Monitor
  Monitor A: error_rate > 5%
  Monitor B: traffic > 1000 req/min
  
  Composite = A AND B
  
  → Alert CHỈ KHI error cao VÀ traffic cao đồng thời
  → 100 req/min + 8% → KHÔNG alert (Monitor B = OK)
  → 10,000 req/min + 8% → ALERT (A=Alert, B=Alert → Alert)

Cơ chế Boolean Logic

Monitor A:  OK  | Warn | Alert | NoData
Monitor B:  OK  | Warn | Alert | NoData

Composite = A AND B:
  A=Alert, B=Alert → ALERT
  A=Alert, B=OK    → OK (không đủ điều kiện)
  A=OK, B=Alert    → OK
  A=OK, B=OK       → OK

Composite = A OR B:
  A=Alert, B=OK    → ALERT (đủ 1 điều kiện)
  A=OK, B=Alert    → ALERT
  A=OK, B=OK       → OK

Limits: Composite kết hợp tối đa 10 monitors, có thể là bất kỳ types (metric + anomaly + process…).

7.9 Monitor States — State Machine

                          Metric về dưới recovery threshold
                    ┌────────────────────────────────────────┐
                    │                                        │
                 ┌──▼──┐   Vượt warning    ┌──────┐         │
  Agent boot →  │ OK  │─────────────────→ │ WARN │         │
                └──┬──┘                   └──┬───┘         │
                   │                         │              │
                   │   Vượt ALERT            │ Vượt ALERT   │
                   │   threshold             │              │
                   │                         ▼              │
                   └────────────────→   ┌──────────┐   ────┘
                                        │  ALERT   │
                                        └──────────┘
                                              │
                   Agent stop/network fail    │
                                        ┌──────────┐
                                        │ NO DATA  │
                                        └──────────┘

No Data state: Xảy ra khi Datadog ngừng nhận data trong evaluation window:

  • Agent bị stop
  • Network connectivity lost
  • Host bị terminate (EC2 instance stopped)
  • Monitor query trả về null (tất cả hosts offline)

Quan trọng: No Data ≠ metric = 0. Nó là “không có data point nào cả”.

7.10 Notification System — Cơ Chế Alert Delivery

Notify handles

Notification message:
  
  🚨 High CPU on {{host.name}}!
  Current value: {{value}}% (threshold: {{threshold}}%)
  
  Please investigate immediately.
  @pagerduty-critical           ← Tạo PagerDuty incident
  @slack-ops-alerts             ← Post vào Slack
  @john.doe@company.com         ← Email

Template variables được resolve dynamically khi alert fires:

  • {{host.name}} → “web-prod-07”
  • {{value}} → “94.2”
  • {{threshold}} → “90”

Re-notify và Escalation

Alert fires at 14:00 → Slack notification
No acknowledgment for 30 min → Re-notify at 14:30
Still no acknowledgment → Escalate to @pagerduty-critical at 15:00

7.11 SLOs — Service Level Objectives

Chain: SLI → SLO → SLA → Error Budget

SLI (Service Level Indicator):
  Metric đo lường = "% HTTP requests với status 2xx"
  Ví dụ: 99.95% của requests trong tháng là 2xx

SLO (Service Level Objective):
  Target nội bộ = "Phải đạt ≥ 99.9% uptime"
  (Thường strict hơn SLA để có buffer)

SLA (Service Level Agreement):
  Cam kết với khách hàng = "Đảm bảo 99.5% uptime"
  Nếu vi phạm → có penalty (tiền hoàn lại, v.v.)

Error Budget:
  = 100% - SLO target = 100% - 99.9% = 0.1%
  = 0.1% × 30 ngày × 24h × 60 phút = 43.2 phút downtime/tháng

Tại sao Error Budget hữu ích?

Không có Error Budget:
  SRE team: "Không được deploy! Uptime phải 100%!"
  Dev team: "Không deploy được gì cả!"
  → Stagnation

Có Error Budget:
  Error Budget còn 40 phút → "OK, deploy feature mới. Nếu outage < 40 phút thì OK."
  Error Budget còn 2 phút → "FREEZE deployments. Focus on stability."
  → Balanced, data-driven decision

Ba loại SLO trong Datadog

TypeĐo bằng gìVí dụ
Metric-basedRatio: good_events/total_events99.9% requests là 2xx
Monitor-based% thời gian monitors ở trạng thái OK99.9% thời gian không có Alert
Time Slice% thời gian condition đúng99.9% thời gian latency < 200ms

7.12 Câu Hỏi Thường Gặp

Q: Traffic thấp bất thường vào thứ Hai (seasonal pattern) — dùng monitor nào?
→ Anomaly — học seasonal patterns từ lịch sử, biết thứ Hai bình thường là bao nhiêu

Q: Disk đầy trong bao lâu? — dùng monitor nào?
→ Forecast — dự đoán proactively khi nào vượt threshold

Q: 1/10 servers CPU cao hơn 9 cái kia — dùng monitor nào?
→ Outlier — so sánh peers vs peers

Q: Alert CHỈ KHI error > 5% VÀ traffic > 1000 — dùng monitor nào?
→ Composite (AND logic) — kết hợp 2 monitors

Q: Monitor states là gì?
→ OK → Warn → Alert → No Data. Ngoài ra còn có Unknown (cho service checks khi không xác định được). Skipped không phải monitor state mà là evaluation status (khi monitor skip evaluation do thiếu data + “Require Full Window” setting).

Q: No Data state khác metric = 0 như thế nào?
→ No Data = không có data point nào cả (Agent down/host gone). Metric = 0 = giá trị thực cũng là 0.

Q: Error Budget 99.9% SLO trong 30 ngày = bao nhiêu phút?
→ 0.1% × 30 × 24 × 60 = 43.2 phút

Q: Template variable {{value}} trong notification?
→ Giá trị metric hiện tại gây ra alert

Q: NGINX process không chạy — dùng monitor nào?
→ Process Monitor — kiểm tra số process instances đang chạy

Q: MySQL không kết nối được — dùng monitor nào?
→ Service Check Monitor — kiểm tra mysql.can_connect status

Q: Process Monitor vs Service Check Monitor?
→ Process = đếm số processes. Service Check = health check binary (OK/CRITICAL) từ integration
