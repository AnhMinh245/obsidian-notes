Phần 3: Tagging — Hệ Thống Tổ Chức Dữ Liệu

Tỷ trọng ước tính: ~10-12% đề thi · Độ khó: Trung bình

3.1 Vấn Đề Mà Tagging Giải Quyết

Bức tranh trước khi có tagging

Hãy tưởng tượng Datadog là một kho hàng khổng lồ:

  • 500 hosts gửi data lên
  • Mỗi host gửi 100 metrics × 4 lần/phút × 60 phút/giờ = 24,000 data points/host/giờ
  • 500 hosts × 24,000 = 12 triệu data points mỗi giờ

Không có tags, khi bạn vào Datadog và hỏi “CPU của servers production đang như thế nào?” — bạn không thể filter vì không biết host nào là production.

Tags là metadata gắn vào data — giúp bạn sau này truy vấn, lọc, nhóm data theo bất kỳ chiều nào bạn muốn.

💡 Analogy: Tags giống như metadata của file Excel. Mỗi row có cột “Bộ phận”, “Khu vực”, “Tháng”. Sau đó bạn có thể filter, pivot, group theo bất kỳ cột nào.

3.2 Format và Cơ Chế Xử Lý Tags

Format: key:value

env:production
service:web-api
team:backend
region:us-east-1
version:2.1.0

Tại sao lowercase bắt buộc?

Datadog tự động lowercase tất cả tags trước khi store:

Input:   Env:Production
Stored:  env:production

Input:   Team:BackEnd
Stored:  team:backend

Lý do: Nếu không, env:production và env:Production sẽ là 2 tags khác nhau → data bị phân mảnh, filter không thể match.

Tại sao phải bắt đầu bằng chữ cái?

Tags được dùng làm identifiers trong hệ thống. Bắt đầu bằng số có thể gây ambiguity về type:

123:value   ← Số? String? 
env:value   ← Rõ ràng là string identifier

Tại sao tối đa 80 ký tự?

Tổng chiều dài tag (bao gồm key:value) tối đa 80 ký tự (không phải 200). Storage và indexing optimization — tag quá dài tốn storage, ảnh hưởng performance query.

3.3 Unified Service Tagging — Cơ Chế Correlation

Vấn đề khi thiếu UST

Scenario: Sau deployment phiên bản mới, user báo lỗi.

Không có UST:
  Logs:    service=order-backend, version=unknown
  Metrics: host=web-prod-01, service=unknown
  Traces:  service=orders, version=v2.1

  → Không thể biết: Lỗi này thuộc version nào? Chỉ ảnh hưởng production?
  → Phải thủ công correlate từng nguồn dữ liệu

Giải pháp: Ba Tags Bắt Buộc Cùng Tên + Giá Trị

env:production
service:order-backend
version:2.1.0

Khi 3 tags này có mặt trên TẤT CẢ ba pillars, Datadog có thể tự động:

Flow sau khi có UST:

1. Anomaly alert: "order-backend metrics bất thường lúc 14:30"
   → Filter: service=order-backend, env=production, version=2.1.0

2. Click "See Traces" → APM tự filter đúng service + version + environment

3. Click "See Logs" từ trace → Log Explorer tự filter đúng service + version

4. So sánh version:
   avg:system.cpu.user{service:order-backend, env:production, version:2.0.0}  ← baseline
   avg:system.cpu.user{service:order-backend, env:production, version:2.1.0}  ← sau deploy

Semantic của mỗi tag

TagGắn cho loại entity nàoMô tả
envTẤT CẢ (host, service, container)Deployment environment — phân biệt prod/staging/dev
serviceApplication servicesLogical service name — không gắn cho hosts nếu host chạy nhiều services
versionApplication servicesSemantic versioning của application binary

★ Exam note: version tag không nên gắn cho infrastructure (hosts, databases) — chỉ gắn cho application services.

3.4 Cardinality — Nguyên Lý Kinh Tế Của Tags

Từ tag đến timeseries — cơ chế nội bộ

Datadog lưu metrics dưới dạng timeseries — mỗi unique combination của metric name + tags = 1 timeseries riêng biệt.

Metric: http.requests
Tags: env, service, host

Timeseries được tạo ra:
  http.requests {env:production, service:web, host:web-01}   ← timeseries 1
  http.requests {env:production, service:web, host:web-02}   ← timeseries 2
  http.requests {env:production, service:api, host:api-01}   ← timeseries 3
  http.requests {env:staging, service:web, host:stg-web-01}  ← timeseries 4
  ...

Tổng: 2 envs × 3 services × 50 hosts = 300 timeseries cho 1 metric
→ 300 timeseries là hoàn toàn manageable!

High cardinality gây ra gì?

Thêm tag request_id (có 1 triệu unique values mỗi ngày):

http.requests {env:production, service:web, host:web-01, request_id:abc123}
http.requests {env:production, service:web, host:web-01, request_id:def456}
...

Tổng: 300 × 1,000,000 = 300,000,000 timeseries!
→ Chi phí storage tăng 1 triệu lần
→ Query performance giảm thậm tệ
→ Datadog có thể từ chối hoặc charge rất nhiều tiền

Rule of thumb

Số unique valuesCardinalityVí dụ tags phù hợp
< 10Very low ✅env (prod/staging/dev)
10 - 100Low ✅service, region, team
100 - 1,000Medium ⚠️host (nếu cluster nhỏ)
1,000+High ❌user_id, request_id, ip_address
1M+Very high ❌❌timestamp, uuid

★ Exam insight: Timestamp và request ID là anti-patterns nguy hiểm nhất vì chúng có cardinality gần vô hạn.

3.5 Cách Gán Tags — Luồng Dữ Liệu Đầy Đủ

Nguồn 1: datadog.yaml — áp dụng rộng nhất

Cơ chế: Collector attach các tags này vào tất cả data trước khi gửi cho Forwarder. Mọi metric, log, trace từ host này đều có các tags này.

Dùng khi: Host có identity rõ ràng (ví dụ: tất cả servers trong cùng 1 environment/team).

Nguồn 2: Integration config — áp dụng hẹp hơn

Cơ chế: Chỉ metrics từ integration NGINX cụ thể mới có tags này. Metrics từ disk, CPU, MySQL sẽ không có service:web-frontend.

Dùng khi: Host chạy nhiều services—cần tag riêng cho mỗi service.

Nguồn 3: Automatic từ cloud integrations

AWS EC2 instance có tags:
  Name: web-server-prod-01
  Environment: production
  Team: backend
  
↓ Datadog AWS Crawler import:

Datadog metrics từ EC2 này tự động có:
  host:web-server-prod-01
  environment:production
  team:backend

Cơ chế: Crawler-based integration đọc resource tags từ cloud provider API → tự động gắn vào metrics.

Nguồn 4: Kubernetes labels → tags

Datadog Agent tự đọc labels này → attach vào tất cả data từ pod đó.

Tags Là Dimensions — Thêm Chiều Cho Data

Khi bạn gắn tag key:value vào metric, bạn đang thêm 1 chiều mới (key) với 1 giá trị (value) vào data. Hãy hình dung data là khối 3D:

                    AVAILABILITY ZONE
                         ↑
                         │   sa-east-1a
                         │   eu-west-1a
                         │   us-east-1a
                         │
    INSTANCE TYPE ───────┼───────────────────→ ROLE
    b3.medium            │                     database
    t2.small             │                     cache
    c3.large             │                     appserver

Mỗi "ô" trong khối 3D = 1 unique combination:
  (us-east-1a, t2.small, cache)   ← 1 timeseries
  (us-east-1a, c3.large, database) ← 1 timeseries khác
  ...

Tag "key" = chọn CHIỀU nào để nhìn data
Tag "value" = chọn ĐIỂM nào trên chiều đó

Ví dụ thực tế:

Metric: system.cpu.user

Không tag: 1 con số duy nhất → "CPU trung bình toàn hệ thống"
Thêm role: → Nhìn CPU theo database vs cache vs appserver
Thêm az:   → Nhìn CPU theo us-east-1a vs eu-west-1a
Thêm cả 2: → Nhìn CPU theo từng role TRONG từng AZ

→ Càng nhiều tags = càng nhiều chiều = càng chi tiết
→ Nhưng quá nhiều chiều = high cardinality = tốn tiền! (xem 3.4)

3.7 Template Variables — Cơ Chế Hoạt Động Trên Dashboard

Bài toán

Bạn có dashboard với 20 widgets, mỗi widget có query như:

avg:system.cpu.user{env:production, service:web-api} by {host}

Khi muốn xem staging thay vì production, bạn phải sửa 20 queries một cách thủ công?

Giải pháp: Template Variables

Định nghĩa template variable:
  Name: $env
  Default: production
  Allowed values: production, staging, development

Tất cả widgets tự động sử dụng $env thay vì hardcode:
  avg:system.cpu.user{env:$env, service:web-api} by {host}

Người dùng chọn "staging" từ dropdown → tất cả 20 widgets tự update!

Cơ chế hoạt động: Dashboard UI thay thế $env bằng giá trị được chọn trước khi gửi query đến Datadog API. Không cần sửa queries.

3.8 Tagging Best Practices — 5 Nguyên Tắc Vàng

Datadog khuyến nghị 5 best practices khi thiết kế hệ thống tags:

1. Sử dụng Tags nhất quán — Đừng bỏ qua cardinality!

❌ Sai:  Team A dùng "environment:prod", Team B dùng "env:production"
       → 2 tags khác nhau, không filter chung được!

✅ Đúng: Thống nhất toàn org dùng "env:prod"
       → Tất cả data từ mọi team đều filter được cùng nhau

⚠️ Cardinality: Đừng gắn tag có triệu unique values (user_id, request_id)
   → Gây bùng nổ timeseries → tốn tiền storage + chậm query

2. Chỉ định người sở hữu (Owner) cho Tag Value Propositions

Mỗi tag key nên có 1 team/người chịu trách nhiệm:

  Tag key "env"     → Owner: Platform team (quyết định giá trị nào hợp lệ)
  Tag key "service" → Owner: Mỗi team sở hữu service của mình
  Tag key "team"    → Owner: Engineering Manager

Lý do: Tránh ai cũng tạo tag bừa → inconsistency, tag rác

3. Tập trung vào Required và Conditionally Required Tags

Phân loại tags:

  REQUIRED (bắt buộc mọi resource):
    ✅ env          → prod / staging / dev
    ✅ service      → tên dịch vụ
    ✅ team         → team sở hữu

  CONDITIONALLY REQUIRED (bắt buộc tuỳ ngữ cảnh):
    ✅ version      → chỉ cho application services
    ✅ cluster_name → chỉ cho Kubernetes resources
    ✅ db_engine    → chỉ cho database services

  OPTIONAL (tuỳ chọn):
    ⚠️ cost_center  → nếu cần cost tracking
    ⚠️ project      → nếu cần project-based grouping

4. Bắt đầu nhỏ — Start Small

❌ Sai:  Ngày đầu tạo 50 tag keys → phức tạp, khó maintain

✅ Đúng: Bắt đầu với 3 UST tags (env, service, version)
        → Sau đó thêm dần khi có nhu cầu rõ ràng

⚠️ Lưu ý: Thay đổi tag SAU KHI đã deploy → phải update TẤT CẢ:
   - Agent configs
   - Dashboard queries  
   - Monitor definitions
   - SLOs
   → Nên nghĩ kỹ trước khi thêm, nhưng đừng overthink

5. Thiết kế tags phục vụ nhiều mục đích

Tags tốt có thể dùng cho nhiều use cases cùng lúc:

Mục đíchTags phù hợpVí dụ sử dụng
Access Controlteam, envChỉ team backend xem data production
Cost Trackingservice, team, envPhân bổ chi phí Datadog theo team
Automationenv, roleAuto-scaling rules theo role
Organizationservice, business_unitNhóm services theo business domain
Troubleshootingenv, service, versionFilter data khi debug
★ Tag "env" phục vụ cả 5 mục đích trên!
→ Đây là lý do env là 1 trong 3 UST tags bắt buộc

3.9 Câu Hỏi Thường Gặp

Q: Tại sao tag phải lowercase?
→ Để tránh data fragmentation — Env:Prod và env:prod sẽ là 2 tags khác nhau, không filter được cùng nhau

Q: Tại sao tránh high cardinality tags?
→ Mỗi unique tag combination = 1 timeseries riêng biệt → triệu unique values = triệu timeseries → chi phí storage/query khổng lồ

Q: Tags trong datadog.yaml vs integration config?
→ datadog.yaml = TẤT CẢ data từ host. Integration config = ONLY data từ integration đó

Q: service tag nên gắn cho gì?
→ Application services — không phải hosts hoặc infrastructure

Q: Tag 123:value có hợp lệ không?
→ Không — tag phải bắt đầu bằng chữ cái

Q: Auto-tagging từ cloud?
→ Crawler integrations (AWS/GCP/Azure) tự import resource tags từ cloud provider API
