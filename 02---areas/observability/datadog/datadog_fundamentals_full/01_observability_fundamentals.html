Phần 1: Observability & Computer Fundamentals

Tỷ trọng ước tính: ~10% đề thi · Độ khó: Thấp–Trung bình

1.1 Vấn Đề Mà Observability Giải Quyết — Bức Tranh Toàn Cảnh

Thế giới phần mềm đã thay đổi như thế nào?

Ngày xưa (monolith era), một ứng dụng web chỉ là 1 process lớn chạy trên 1 server. Khi bị lỗi, bạn có thể:

  • SSH vào server đó
  • Xem log file
  • Restart service

Đủ. Đơn giản.

Ngày nay (microservices era), 1 request của user có thể đi qua:

User click "Mua hàng"
    │
    ├─→ API Gateway (Kubernetes pod, Node A)
    │        │
    │        ├─→ Auth Service (Pod, Node B) ─→ Database (RDS, us-east-1a)
    │        │
    │        ├─→ Cart Service (Pod, Node C) ─→ Redis Cache
    │        │
    │        ├─→ Payment Service (Pod, Node D) ─→ 3rd-party Stripe API
    │        │        │
    │        │        └─→ Fraud Detection ML (Lambda function)
    │        │
    │        └─→ Order Service (Pod, Node E) ─→ PostgreSQL
    │                 │
    │                 └─→ Email Service (SQS + Lambda)
    │
    └── User nhận "Đặt hàng thành công" sau 2.3 giây

Khi user báo “website chậm”, bạn hỏi câu gì?

  • Pod nào? Node nào? Service nào? Deployment nào? Database replica nào?
  • Lỗi xuất hiện lúc nào? Cho mọi user hay chỉ 1 user? Khu vực địa lý nào?

Không thể SSH vào từng pod để xem. Không thể “nhìn vào” system để tìm vấn đề.

→ Đây là vấn đề observability giải quyết: Thay vì nhìn trực tiếp vào hệ thống, bạn suy luận trạng thái bên trong từ dữ liệu mà hệ thống phát ra.

1.2 Observability — Định Nghĩa Chính Xác

Observability là khả năng trả lời bất kỳ câu hỏi nào về trạng thái của hệ thống chỉ dựa vào dữ liệu đầu ra — không cần code thêm, không cần biết trước câu hỏi.

💡 Ví dụ minh hoạ: Bác sĩ chẩn đoán bệnh nhân không cần “mở ra xem” — họ dùng nhiệt độ, huyết áp, xét nghiệm máu, X-quang. Hệ thống observable cho phép bạn “chẩn đoán” software tương tự.

Monitoring ≠ Observability

Đây là nhầm lẫn cực kỳ phổ biến:

Traditional MonitoringObservability
Triết lý”Tôi biết cần kiểm tra gì""Tôi có thể hỏi bất kỳ điều gì”
Cách tiếp cậnĐặt cảnh báo → chờ ngưỡng bị vượtThu thập dữ liệu phong phú → khám phá
Vấn đề phát hiệnKnown-knowns (lỗi đã biết)Known + Unknown unknowns
Khi lỗi mớiKhông có alert → không biếtĐủ dữ liệu để điều tra
Ví dụCPU > 90% → alertTại sao user ở Việt Nam chậm hơn EU 3 lần?

★ Exam tip: Câu hỏi phân biệt Monitoring vs Observability thường nhấn mạnh: Monitoring = phản ứng với known issues, Observability = khám phá unknown issues.

1.3 Ba Trụ Cột — Nguyên Lý Hoạt Động Của Từng Pillar

Tại sao lại cần đúng 3 trụ cột này?

Bởi vì mỗi trụ cột trả lời một loại câu hỏi khác nhau, và bạn cần cả ba để hiểu đầy đủ:

Hệ thống bị chậm → Bạn cần biết:

WHAT happened?   → METRICS  → "Latency tăng từ 200ms lên 2s lúc 3:47pm"
WHERE happened?  → TRACES   → "Bottleneck ở DB call trong Order Service"
WHY happened?    → LOGS     → "Slow query vì query plan chọn sai index"

Nếu thiếu 1 trong 3:

  • Chỉ có Metrics → Biết có vấn đề nhưng không biết ở đâu, tại sao
  • Chỉ có Logs → Biết chi tiết từng sự kiện nhưng không thấy flow tổng quan
  • Chỉ có Traces → Biết luồng request nhưng không có context lịch sử

Pillar 1: METRICS — “What happened?”

Bản chất

Metric là chuỗi số liệu thống kê theo thời gian (time-series). Mỗi data point là một cặp (timestamp, value).

system.cpu.user (tại host: web-01, tag: env:production)

timestamp     value
14:00:00  →   45.2%
14:00:15  →   52.1%
14:00:30  →   78.4%   ← spike!
14:00:45  →   81.2%
14:01:00  →   55.8%

Tại sao Metrics lại nhẹ và rẻ nhất?

Vì metrics bỏ hầu hết thông tin. Thay vì ghi “user abc gửi request X lúc 14:00:30 với payload 2KB và nhận response 500ms”, metrics chỉ ghi latency.avg = 500 tại timestamp đó.

  • Chi phí lưu trữ: 1 data point = vài chục bytes
  • 1 host gửi ~100 metrics mỗi 15 giây = 6,000 points/phút = rất nhỏ

Khi nào Metrics là đủ? Khi nào không đủ?

Đủ khi: Bạn muốn biết xu hướng, mức độ tải, health status tổng thể.

Không đủ khi: Bạn cần biết cụ thể request nào bị lỗi, ai gặp vấn đề, lý do cụ thể.

Pillar 2: LOGS — “Why did it happen?”

Bản chất

Log là bản ghi văn bản mô tả từng sự kiện đã xảy ra — chi tiết nhất trong 3 pillars.

2024-03-15 14:00:30.412 ERROR [order-service] [trace_id=abc123] [user_id=7823]
  OrderProcessingException: Payment gateway timeout after 5000ms
  at PaymentClient.charge(PaymentClient.java:142)
  at OrderService.processOrder(OrderService.java:87)
  Caused by: java.net.SocketTimeoutException: Read timed out
  Context: {order_id: 9876, amount: 150.00, currency: VND, retry_attempt: 3}

Từ 1 dòng log này, bạn biết:

  • Khi nào: 14:00:30.412 (chính xác đến millisecond)
  • Ở đâu: Order Service
  • Ai: user_id=7823, order_id=9876
  • Cái gì: Payment gateway timeout
  • Tại sao: Socket timeout sau 5000ms, đây là lần retry thứ 3

Tại sao Logs đắt nhất?

Logs giữ toàn bộ thông tin → volume khổng lồ. Một ứng dụng nhỏ có thể tạo ra hàng GB logs mỗi ngày. Lưu trữ, index, và search logs = chi phí chính của observability.

→ Logging Without Limits ra đời để giải quyết: Ingest tất cả, chỉ index (tìm kiếm được) phần quan trọng.

Pillar 3: TRACES — “Where in the chain?”

Bản chất

Trace theo dõi hành trình của 1 request khi nó đi qua nhiều services — điều mà Metrics và Logs đơn lẻ không thể làm được.

Cơ chế hoạt động (quan trọng để hiểu)

Khi request bắt đầu, tracing library inject một Trace ID duy nhất:

User request → API Gateway
│
│ Trace ID: abc-123-xyz (tạo ở đây)
│ Span ID: span-001 (root span)
│ Bắt đầu: 14:00:30.000
│
├─→ Auth Service
│   Trace ID: abc-123-xyz    ← CÙNG Trace ID, truyền qua HTTP header!
│   Span ID: span-002
│   Parent: span-001
│   Bắt đầu: 14:00:30.050, Kết thúc: 14:00:30.080 (30ms)
│
└─→ Order Service
    Trace ID: abc-123-xyz    ← Vẫn truyền theo
    Span ID: span-003
    Parent: span-001
    Bắt đầu: 14:00:30.080, Kết thúc: 14:00:32.080 (!!2000ms!!)
    │
    └─→ Database Query
        Span ID: span-004
        Parent: span-003
        Duration: 1800ms ← BỐT LỔ Ở ĐÂY!

Flame graph visualize điều này: bạn nhìn ngay thấy span-004 (DB query) chiếm 90% thời gian của toàn trace.

Tại sao Traces mạnh hơn Logs?

Logs từng service đều riêng lẻ — bạn phải tự correlate chúng. Với Traces, Datadog tự động kết nối các phases lại thành 1 picture hoàn chỉnh nhờ Trace ID truyền qua tất cả services.

Cách 3 Pillars Phối Hợp — Workflow Điều Tra

BƯỚC 1: Monitor Dashboard (METRICS)
  Phát hiện: p99 latency tăng từ 300ms → 3s lúc 14:00
  Tool: Datadog metric alert fired!

BƯỚC 2: Drill down vào Traces (TRACES)
  Filter traces: service=web-api, latency > 2s, time=14:00-14:10
  Phát hiện: 80% slow traces đều có span "db.query.orders" mất 2s+
  Tool: APM → Trace Explorer → click vào 1 slow trace → Flame Graph

BƯỚC 3: Tìm Root Cause trong Logs (LOGS)
  Filter: service=order-service, time=14:00, level=WARN|ERROR
  Phát hiện: "Slow query: SELECT * FROM orders WHERE customer_id=? (no index)"
  Tool: Log Explorer → correlate từ trace (click "See related logs")

KẾT QUẢ: Missing index trên cột customer_id → thêm index → latency về bình thường
Thời gian điều tra: 5-10 phút (thay vì hours không có observability)

1.4 Computer Fundamentals — Cơ Chế Hoạt Động

CPU — Cách Đọc Metrics Đúng

CPU là gì dưới góc nhìn OS?

CPU tại bất kỳ thời điểm nào đang ở 1 trong các trạng thái này:

CPU StateMetricÝ nghĩa
Usersystem.cpu.userĐang chạy code ứng dụng (user space)
Systemsystem.cpu.systemĐang chạy OS kernel code (system calls)
Wait (I/O)system.cpu.iowaitĐang chờ disk hoặc network — không chạy gì!
Stolensystem.cpu.stolenHypervisor lấy CPU (VM bị “cướp” CPU)
Idlesystem.cpu.idleCPU hoàn toàn rảnh, không làm gì

Quy tắc vàng: Tổng các states = 100%

Ví dụ đọc metrics:
  cpu.user = 60%    → App đang dùng 60% CPU
  cpu.system = 10%  → OS dùng thêm 10%
  cpu.iowait = 25%  → CPU chờ disk/network 25% thời gian → DISK BOTTLENECK!
  cpu.idle = 5%     → Chỉ 5% thời gian rảnh

  ⚠️ Dù cpu.user + cpu.system "chỉ" 70%, nhưng iowait 25% = hệ thống đang bị slow disk!

Load Average — Nguyên Lý

Load Average là số processes đang chờ được CPU phục vụ tại 1 thời điểm (trung bình theo thời gian 1/5/15 phút).

Analogy: Hàng đợi tại quầy tính tiền siêu thị

  4 cores = 4 quầy
  Load 4.0 = 4 người đang được phục vụ, hàng chờ = 0 → 100% máy đang làm việc
  Load 8.0 = 4 người đang phục vụ + 4 người đang chờ → overloaded!
  Load 2.0 = 2 người phục vụ, 2 quầy trống → 50% utilized, nhàn rỗi

  Quy tắc: Load > số cores = hệ thống OVERLOADED

★ Exam trap cực kỳ phổ biến:

system.cpu.idle = 5% KHÔNG có nghĩa là “CPU đang dùng 5%”!

Nó có nghĩa là: CPU rảnh 5% → đang bận 95% thời gian!

Cách nhớ: idle = "nhàn" → 5% idle = 5% nhàn = 95% bận!

Memory — Tại Sao available > free?

Cơ chế OS quản lý RAM

Linux có một tối ưu hoá thông minh: Khi RAM rảnh, OS không để trống — nó dùng RAM rảnh làm disk cache (page cache) để đọc disk lần sau nhanh hơn.

Máy có 16GB RAM. App đang dùng 6GB.

  mem.used = 10GB    ← ??? Sao dùng nhiều vậy?
  mem.free = 2GB     ← Còn ít quá!
  mem.cached = 4GB   ← OS đang cache disk data
  mem.available = 6GB ← Thực sự có thể dùng (free + cache có thể giải phóng)

  ⟹ mem.available = 6GB: Nếu App cần thêm 4GB, OS sẽ giải phóng cache ngay!
  ⟹ Chỉ nhìn mem.free = 2GB → PANIC không cần thiết!
  ⟹ Số thực sự cần quan tâm: mem.available hoặc mem.usable

Khi nào cần lo:

  • mem.available < 10% tổng RAM → thực sự thiếu RAM
  • system.swap.used > 0 → OS đang dùng disk làm RAM → RẤT CHẬM → mua thêm RAM hoặc tối ưu app

Networking — TCP vs UDP: Cơ Chế Bắt Tay

TCP — Reliable connection

Sender                    Receiver
  │─── SYN ─────────────→│   "Tôi muốn kết nối"
  │←── SYN-ACK ──────────│   "OK, tôi sẵn sàng"
  │─── ACK ─────────────→│   "Đã nhận"
  │─── DATA ────────────→│   "Gửi data"
  │←── ACK ──────────────│   "Đã nhận data"
  
  → Mỗi packet đều được xác nhận
  → Nếu mất packet → tự động gửi lại
  → RELIABLE nhưng SLOW hơn (overhead handshake + ACK)

Datadog dùng TCP cho APM traces (port 8126) vì traces không thể mất — mất 1 span = mất toàn bộ picture.

UDP — Fast, connectionless

Sender                    Receiver
  │─── DATA ────────────→│   "Gửi và quên"
  
  → Không handshake, không ACK
  → Mất packet? Không biết, không retry
  → NHANH vì không cần đợi

Datadog dùng UDP cho DogStatsD (port 8125) vì:

  • Mất 1 metric data point trong 10 giây? Không sao, 10 giây sau gửi tiếp
  • App KHÔNG BAO GIỜ bị chặn chờ monitoring → đây là ưu tiên #1

Ports — Tại Sao Những Con Số Này?

Port 443 (HTTPS) — Agent → Datadog Backend:
  Firewall corp thường BLOCK tất cả ports ngoại trừ 80 (HTTP) và 443 (HTTPS)
  → Datadog chọn 443 để hoạt động trong môi trường corp mà không cần đặc quyền firewall

Port 8125 (UDP) — DogStatsD:
  Port trong range 8000-9000 không cần root privilege để mở.
  UDP để app gửi nhanh mà không block.

Port 8126 (TCP) — APM:
  Adjacent với DogStatsD (8125) để dễ nhớ.
  TCP vì traces quan trọng hơn, không thể mất.

1.5 YAML — Cơ Chế Parse và Lỗi Phổ Biến

Tại sao YAML dùng spaces thay tabs?

YAML được thiết kế để human-readable và unambiguous. Tab width có thể khác nhau giữa editors (tab = 2 spaces? 4 spaces? 8 spaces?). Spaces thì luôn là 1 space = 1 space — không có ambiguity.

Cách phát hiện lỗi YAML tab/space:

1.6 Câu Hỏi Thường Gặp (Với Giải Thích Tại Sao)

Q: Ba pillars of observability?
→ Metrics, Logs, Traces — mỗi cái trả lời: What, Why, Where

Q: system.cpu.idle = 5% nghĩa là gì?
→ CPU đang dùng 95% (idle = % thời gian CPU rảnh, không phải % CPU đang dùng!)

Q: Load Average 8.0 trên máy 4 cores = điều gì?
→ Overloaded: 4 processes đang chờ CPU không có để dùng

Q: mem.available vs mem.free?
→ available > free vì available bao gồm cả page cache mà OS có thể giải phóng ngay

Q: Tại sao DogStatsD dùng UDP?
→ Để app KHÔNG bao giờ bị block chờ monitoring — performance của app là ưu tiên #1

Q: Tại sao Agent gửi data qua port 443?
→ Port 443 (HTTPS) luôn được firewall cho phép trong môi trường enterprise

Q: Lỗi YAML phổ biến nhất?
→ Dùng tabs thay spaces (YAML parser từ chối tab characters)

Q: monitoring vs observability — khác nhau thế nào?
→ Monitoring = phản ứng với known issues qua predefined thresholds. Observability = khám phá bất kỳ unknown issue nào qua dữ liệu phong phú.
