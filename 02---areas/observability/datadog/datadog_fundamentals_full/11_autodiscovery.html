Phần 11: Datadog Autodiscovery (Chuyên Sâu)

11.1 Vấn Đề Của Môi Trường Động (Dynamic Environments)

Trước khi có container và orchestration, kiến trúc chủ yếu là tĩnh (Static). Bạn có một server, bạn cài đặt Redis trên đó, địa chỉ IP cố định, port cố định. Bạn cài Datadog Agent và cấu hình tĩnh file conf.d/redisdb.yaml trỏ đến IP và Port đó.

Nhưng trong thế giới Container (Kubernetes, Docker Swarm, ECS):

  • Phù du (Ephemeral): Các container/pod liên tục được tạo ra, tiêu diệt, và thay thế dựa trên nhu cầu scaling, deployment, hoặc node failures.
  • Biến động IP/Port: Mỗi lần một container được tạo lại, nó nhận một IP mới. Nếu bạn sử dụng dynamic port mapping, port cũng thay đổi.
  • Mật độ cao (High Density): Một node (server vật lý/ảo) có thể chạy hàng chục pod, mỗi pod chứa nhiều loại dịch vụ khác nhau. Datadog Agent chạy dưới dạng DaemonSet (1 agent per node) phải giám sát TẤT CẢ các pod trên node đó.

Vấn đề: Không thể dùng cấu hình tĩnh. Nếu bạn cấu hình tĩnh, mỗi khi một pod restart, bạn phải sửa lại file cấu hình của Agent và khởi động lại Agent. Điều này bất khả thi.

Giải pháp: Datadog Autodiscovery. Agent tự động “lắng nghe” các sự kiện tạo/hủy container, nhận diện dịch vụ chạy bên trong, và tự động áp dụng cấu hình giám sát phù hợp.

11.2 Autodiscovery Hoạt Động Như Thế Nào?

Autodiscovery bao gồm hai thành phần chính bên trong Datadog Agent: Listeners và Configuration Providers.

1. Listeners (Lắng nghe sự kiện)

Agent liên tục lắng nghe API của Container Runtime (ví dụ: Docker daemon, containerd socket, kubelet).

  • Khi có một container mới khởi tạo, Listener phát hiện ra.
  • Listener thu thập các thông tin (metadata) của container: Tên image, container name, Kubernetes labels, Kubernetes annotations, Docker labels, môi trường (env).

2. Configuration Providers (Nguồn cung cấp cấu hình)

Agent lấy các “Mẫu cấu hình” (Configuration Templates) từ các nguồn khác nhau.

  • Các nguồn này bao gồm: Các file local (nằm trong thư mục conf.d/ của Agent), Kubernetes Annotations gắn trực tiếp trên Pod, Docker Labels, hoặc từ một Key-Value Store (như Consul, Zookeeper, etcd).

11.3 Các Biến Template (Template Variables)

Để cấu hình linh hoạt mà không cần biết trước IP/Port, Datadog cung cấp các biến Template. Khi Agent render cấu hình, nó sẽ thay thế các biến này bằng thông tin thực tế của container.

Các biến quan trọng nhất:

  • %%host%%: IP của container (trong K8s, thường là Pod IP).
  • %%port%%: Port của container.
    • Nếu container mở nhiều port, bạn có thể dùng chỉ mục: %%port_0%%, %%port_1%%.
    • Nếu bạn dùng Kubernetes, Datadog thường tự động tìm port được đánh dấu (exposed port).
  • %%pid%%: Process ID của quy trình chạy trong container (hữu ích cho các integration cần bắt PID như JMX).
  • %%env_<ENV_VAR>%%: Lấy giá trị của một biến môi trường cụ thể trong container.

11.4 Ba Phương Pháp Cấu Hình Autodiscovery

Khi Agent đã phát hiện ra một container mới, nó cần biết CÁCH giám sát container đó. Có 3 phương pháp chính để cung cấp “Mẫu cấu hình” (Configuration Templates) cho Agent.

Cách 1: Sử Dụng Kubernetes Annotations (Hoặc Docker Labels)

Đây là phương pháp Best Practice (Khuyên dùng nhất).

  • Tại sao? Cấu hình giám sát được định nghĩa cùng với cấu hình triển khai ứng dụng (Infrastructure as Code). Khi Developer viết Deployment cho NGINX, họ viết luôn cách Datadog nên lấy metrics của NGINX đó. Nó giúp tách biệt trách nhiệm: Ops lo cài Agent, Dev lo cấu hình giám sát app của mình.
  • Cơ chế: Bạn thêm các thẻ (annotations/labels) chứa cấu hình JSON trực tiếp vào Pod Spec (K8s) hoặc lệnh docker run (Docker).

Cấu trúc chuẩn của Annotations (K8s):
Để định nghĩa một Autodiscovery template hợp lệ bằng Annotations (hoặc Docker Labels), BẮT BUỘC phải có 3 thành phần cấu hình (components) sau:

  1. check_names: Tên của Datadog integration (ví dụ: nginx, redisdb, postgres). Datadog Agent sẽ dựa vào tên này để nạp đúng module python/go tương ứng để thu thập metrics.
  2. init_configs: Chứa cấu hình khởi tạo áp dụng chung (globally) cho toàn bộ integration đó. Lưu ý cực kỳ quan trọng: Ngay cả khi bạn không có cấu hình chung nào, bạn VẪN PHẢI khai báo một mảng chứa object rỗng, tức là [{}]. Nếu thiếu dòng này, Agent sẽ báo lỗi parse template.
  3. instances: Chứa danh sách các tham số cấu hình cụ thể cho từng instance (thường chứa host, port, username, password, tags). Agent sẽ thay thế các biến template (%%host%%) ở trong phần này.

(Lưu ý: <container_name> phải khớp ĐÚNG với thuộc tính name trong mảng containers của Pod spec, KHÔNG phải tên của pod hay deployment).

Cách 2: Sử Dụng Agent Local Files (Tự động nhận diện qua ad_identifiers)

Trong phương pháp này, bạn KHÔNG sửa đổi manifest của ứng dụng. Thay vào đó, bạn đặt các file cấu hình .yaml trực tiếp vào thư mục /conf.d/ của Datadog Agent.

  • Cơ chế: Bạn thêm một trường đặc biệt gọi là ad_identifiers vào file cấu hình. Khi Agent phát hiện một container mới, nó sẽ so sánh Tên Image (hoặc một label cụ thể) của container đó với danh sách ad_identifiers. Nếu khớp, nó áp dụng cấu hình.
  • Ưu điểm: Phù hợp với các dịch vụ chuẩn (Redis, Postgres) không yêu cầu cấu hình quá đặc thù, hoặc khi team Ops không có quyền chỉnh sửa YAML của team Dev.

Agent đã tích hợp sẵn hàng chục file auto_conf.yaml cho các dịch vụ phổ biến dùng phương pháp này. Do đó, bạn thường thấy NGINX hay Redis tự động được collect metrics mà không cần cấu hình gì, vì Datadog Agent đã có sẵn mẫu ad_identifiers: ["nginx"] rồi.

Cách 3: Sử Dụng Key-Value Store (Consul, etcd, ZooKeeper)

Thay vì lưu cấu hình vào Agent hay gắn vào Pod, bạn có thể lưu toàn bộ cấu hình giám sát vào một hệ thống Key-Value store trung tâm.

  • Cơ chế: Datadog Agent được cấu hình để “poll” (hỏi liên tục) KV Store. Bạn đẩy một cấu hình JSON vào Consul/etcd với một key nhất định. Khi một container khởi chạy, Agent hỏi KV Store xem có cấu hình nào khớp với container này không.
  • Ưu điểm: Quản lý tập trung cực tốt. Bạn sửa cấu hình trên Consul, lập tức hàng ngàn Datadog Agent trên các cluster khác nhau tự động nhận cấu hình mới mà không cần restart Agent hay redeploy Pod.
  • Nhược điểm: Tăng độ phức tạp cho hệ thống (phải duy trì thêm Consul/etcd, quản lý access control, v.v.). Thường chỉ dùng cho các doanh nghiệp có kiến trúc siêu phân tán.

11.5 Tổ Chức File Cấu Hình & Tích Hợp Với Agent

Để hiểu rõ hơn về Cách 2 (Agent Local Files) và cách Agent quản lý cấu hình Autodiscovery, bạn cần nắm được cấu trúc thư mục bên trong container của Datadog Agent.

1. Cấu Trúc Thư Mục /conf.d/

Mọi cấu hình cho các integrations (kiểm tra dịch vụ) đều nằm trong thư mục /etc/datadog-agent/conf.d/ của Agent.
Mỗi integration sẽ có một thư mục riêng biệt. Ví dụ:

  • /etc/datadog-agent/conf.d/redisdb.d/
  • /etc/datadog-agent/conf.d/nginx.d/

Bên trong các thư mục này, Agent mong đợi tìm thấy file có đuôi .yaml (như conf.yaml hoặc auto_conf.yaml).

2. Các Loại File Cấu Hình Mặc Định

Khi bạn cài đặt Datadog Agent, nó đi kèm với hàng chục integration được cài sẵn. Trong thư mục của mỗi integration, bạn sẽ thấy các loại file sau:

  • conf.yaml.example: File ví dụ mẫu, chứa TẤT CẢ các tùy chọn cấu hình có thể có kèm theo comment giải thích. Agent sẽ BỎ QUA file này. Bạn dùng nó làm tài liệu tham khảo.
  • conf.yaml.default: File cấu hình mặc định (chỉ có ở một số integration cơ bản như CPU, Memory, Disk). Agent sẽ TỰ ĐỘNG CHẠY file này nếu có.
  • auto_conf.yaml: Đây chính là linh hồn của Autodiscovery nội bộ. File này chứa sẵn cấu hình template có biến %%host%%, %%port%% và mảng ad_identifiers. Datadog cung cấp sẵn auto_conf.yaml cho các dịch vụ cực kỳ phổ biến (như Redis, Apache, Tomcat). Do đó, nếu bạn chạy container tên là redis, Agent tự động khớp và chạy thu thập mà bạn không cần phải làm gì thêm!

3. Mount Cấu Hình Tùy Chỉnh Bằng Kubernetes ConfigMap

Nếu bạn muốn dùng Local Files (Cách 2) trong môi trường Kubernetes thay vì Annotations (Cách 1), bạn không thể SSH vào Agent pod để sửa file được. Thay vào đó, bạn sử dụng Kubernetes ConfigMap.

Quy trình:

  1. Tạo một file redis-custom.yaml chứa cấu hình Autodiscovery (có ad_identifiers, init_config, instances).
  2. Đẩy file này lên Kubernetes dưới dạng ConfigMap:
    kubectl create configmap datadog-redis-config --from-file=redisdb.yaml=redis-custom.yaml
  3. Mount ConfigMap này vào DaemonSet của Datadog Agent thông qua Helm hoặc Operator: Helm chart của Datadog sẽ tự động tạo ConfigMap và mount file này vào đúng đường dẫn /etc/datadog-agent/conf.d/redisdb.d/conf.yaml bên trong pod của Agent.

11.6 Các Tính Năng Autodiscovery Nâng Cao

1. Bỏ qua (Ignore) các container không cần giám sát

Đôi khi có các sidecar containers hoặc các batch jobs ngắn hạn bạn không muốn tốn chi phí giám sát.
Bạn dùng biến môi trường cho Agent: DD_AC_INCLUDE và DD_AC_EXCLUDE.

Ví dụ (Cấu hình trên Agent):

  • DD_AC_EXCLUDE = name:datadog-agent image:fluentd (Bỏ qua container tên là datadog-agent và image fluentd)
  • DD_AC_INCLUDE = image:fluentd-custom (Ngoại trừ image fluentd-custom, vẫn lấy)

Hoặc dùng Annotation gắn vào pod cụ thể để bỏ qua (Disable Autodiscovery cho pod đó):

2. Autodiscovery cho Logs

Không chỉ Metrics, bạn dùng Autodiscovery để gán Source, Service, và các custom Tags cho Logs của container.

Nếu không có annotation này, Agent vẫn có thể thu thập logs (nếu bật tính năng Log collection), nhưng source và service có thể sẽ là docker hoặc tên image mặc định, khiến việc filter/search trên UI Datadog rất khó khăn.

3. Autodiscovery & Unified Service Tagging

Autodiscovery tự động liên kết Metrics, Logs, và Traces lại với nhau thông qua Unified Service Tagging (env, service, version).
Bằng cách thêm các chuẩn K8s labels (như tags.datadoghq.com/env, tags.datadoghq.com/service, tags.datadoghq.com/version), Agent tự động trích xuất các nhãn này và gắn vào mọi metric, log, và trace sinh ra từ container đó.

11.7 Troubleshooting (Sửa Lỗi Autodiscovery)

Autodiscovery thường rất “thần kỳ”, nhưng khi nó hỏng, bạn cần biết cách debug từ bên trong Datadog Agent Pod.

Bước 1: Chạy lệnh agent status

  • Truy cập vào terminal của Agent pod (vd: kubectl exec -it <agent-pod-name> -- bash).
  • Chạy agent status.
  • Tìm kiếm mục Collector hoặc Autodiscovery. Kiểm tra xem Integration bạn cần có đang ở trạng thái OK hay ERROR.

Bước 2: Lệnh agent configcheck (Quan trọng nhất)
Lệnh này in ra TẤT CẢ các cấu hình mà Agent đã nhận diện và render thành công, hoặc nguyên nhân thất bại.

Bạn sẽ nhìn thấy file cấu hình cuối cùng (đã được thay thế IP và port thực tế). Nếu biến %%host%% không đổi thành IP, nghĩa là quá trình match bị lỗi.

Các nguyên nhân phổ biến nhất:

  1. Sai Container Name Identifier: Bạn copy/paste annotation từ docs nhưng quên đổi ad.datadoghq.com/nginx... thành ad.datadoghq.com/app-backend... cho khớp với tên container thực tế của bạn.
  2. Lỗi cú pháp JSON trong YAML: Phần giá trị của instances và init_configs BẮT BUỘC phải là JSON Array hợp lệ. Thiếu dấu ngoặc kép ", dấu phẩy , hoặc dùng sai kiểu dấu ngoặc sẽ làm hỏng toàn bộ cấu hình. Datadog khuyên dùng toán tử | (Block scalar) trong YAML để viết JSON nhiều dòng dễ đọc.
  3. Endpoint chưa sẵn sàng: Agent Autodiscovery thành công nhưng ứng dụng (ví dụ Redis) cấu hình sai, không mở port, hoặc NGINX thiếu location /nginx_status, dẫn đến Integration bị Connection Refused. Cần kiểm tra lại cấu hình của chính ứng dụng đó.
