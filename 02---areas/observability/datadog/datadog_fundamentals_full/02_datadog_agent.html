Phần 2: Datadog Agent — Cơ Chế Hoạt Động Từ Bên Trong

Tỷ trọng ước tính: ~15-20% đề thi · Độ khó: Trung bình

2.1 Tại Sao Cần Agent? — Vấn Đề Cơ Bản

Có 2 cách thu thập dữ liệu từ môi trường của bạn:

Cách 1: Pull model — Datadog backend chủ động kéo dữ liệu từ servers của bạn

Datadog Cloud ───── polling ────→ Your Server (HTTP endpoint)

Vấn đề: Server phải expose endpoint ra internet. Firewall phải cho phép inbound từ Datadog. Với hàng nghìn hosts → Datadog phải poll hàng nghìn endpoints → không scale.

Cách 2: Push model + Agent — Agent trên host chủ động gửi dữ liệu lên Datadog

Your Server (Agent) ───── push HTTPS 443 ─────→ Datadog Cloud

Lợi ích:

  • Chỉ cần 1 outbound port 443 — firewall gần như luôn cho phép port này
  • Không cần expose server ra internet
  • Agent biết rõ nhất về host của nó (có thể đọc /proc, local sockets, etc.)
  • Agent có thể buffer data nếu network tạm thời bị mất

→ Datadog chọn push model + Agent.

Resource Footprint (từ Official Workshop)

Agent rất nhẹ:
  CPU:  ~0.08%
  RAM:  ~130 MB
  Disk: ~830-880 MB

★ Exam question: "CPU and memory overhead of Agent?" → ~0.08% CPU / ~130MB RAM

Component 1: COLLECTOR — “Người thu thập chủ động”

Cơ chế hoạt động

Collector là một scheduler — nó lên lịch và chạy các checks theo định kỳ.

Mặc định 15 giây — tại sao 15?

  • Đủ thường xuyên để catch spikes ngắn
  • Không quá thường xuyên để gây overhead
  • Tạo ra 4 data points/phút — đủ smooth cho graphs

System Check: Tự động chạy không cần config, đọc từ /proc/stat, /proc/meminfo, /proc/net/dev (Linux).

Integration Check — Cổng kết nối đến services

Mỗi integration check biết cách “nói chuyện” với 1 loại service:

NGINX check:
  1. HTTP GET http://localhost/nginx_status
  2. Parse response:
     Active connections: 47
     server accepts handled requests
      123456 123456 789012
     Reading: 1 Writing: 12 Waiting: 34
  3. Emit metrics: nginx.net.connections=47, nginx.net.request_count=789012...

Component 2: FORWARDER — “Người vận chuyển thông minh”

Tại sao cần Forwarder riêng biệt?

Hãy tưởng tượng nếu Collector gửi thẳng lên Datadog:

Network outage xảy ra:
  Collector → HTTP request failed!
  → Mất toàn bộ data trong khoảng outage!
  → Khi network khôi phục, không retry!

Forwarder giải quyết:

Network outage xảy ra:
  Collector → Forwarder (data vào buffer trong memory)
  Network khôi phục
  Forwarder → gửi toàn bộ buffered data lên Datadog (retry với exponential backoff)

Cơ chế Forwarder

Forwarder nhận data từ Collector/DogStatsD/APM:
  1. Nhóm (batch) nhiều metrics lại → 1 HTTP request thay vì nhiều
  2. Nén (compress) bằng gzip → giảm bandwidth
  3. Gửi qua HTTPS POST → https://api.datadoghq.com/api/v2/series
  4. Nếu thất bại → exponential backoff (1s, 2s, 4s, 8s...) → retry
  5. Nếu queue đầy → drop oldest data (nhưng log warning)

Dual Shipping — Gửi Data Đến Nhiều Datadog Org Cùng Lúc

Vấn đề thực tế: Công ty bạn có 2 Datadog organizations (ví dụ: Prod org và Security org), hoặc đang migrate từ org cũ sang org mới. Bạn muốn Agent gửi cùng dữ liệu đến cả hai nơi.

Giải pháp: Dual Shipping — cấu hình Agent gửi data song song đến nhiều endpoints.

Luồng Dual Shipping:

  Collector ──→ Forwarder ──→ HTTPS POST ──→ Org 1 (api_key chính)
                    │
                    └──→ HTTPS POST (song song) ──→ Org 2 (additional_endpoints)

  ⚠️ Lưu ý:
  - Bandwidth × 2 (gửi 2 lần cùng data)
  - Nếu Org 2 down → không ảnh hưởng Org 1 (gửi độc lập)
  - Mỗi loại data (metrics, logs, traces) cấu hình additional_endpoints riêng

★ Use cases phổ biến:

  • Migration giữa 2 orgs (gửi song song, sau đó cắt org cũ)
  • Compliance: Security team có org riêng nhận cùng logs
  • Multi-region: gửi data đến cả US và EU Datadog sites

is_reliable setting (từ Official Workshop)

★ Exam question: “What does is_reliable do in dual shipping?” → Đảm bảo endpoint phụ có cùng priority với primary → data không bị dropped.

Agent Proxy Configuration — Gửi Data Qua Proxy

Trong enterprise environments, servers thường không có internet trực tiếp — mọi traffic outbound phải qua proxy.

Config trong datadog.yaml

Hoặc qua environment variables:

HAProxy / NGINX as Agent Proxy

Khi có nhiều Agents (50+ hosts), có thể dùng 1 HAProxy tập trung thay vì config proxy trên mỗi host:

Agents (50 hosts) → HAProxy/NGINX → Corporate Proxy → Internet → Datadog Cloud
  • Giảm số connections ra ngoài (từ 50 → 1)
  • Centralize TLS termination
  • Buffering khi Datadog endpoint tạm unavailable

★ Key: Agent chỉ cần outbound trên port 443 — proxy chỉ cần mở 1 port duy nhất.

Component 3: DogStatsD — “Cổng nhận custom metrics từ applications”

Vấn đề mà DogStatsD giải quyết

Bạn có một web app. Bạn muốn đo:

  • Số active users hiện tại
  • Latency của từng API endpoint
  • Doanh thu theo từng loại sản phẩm

Những metrics này không có trong system, Agent không thể tự đo. Chỉ application code mới biết.

DogStatsD tạo ra một “cổng” để app gửi custom metrics vào Agent một cách nhanh chóng.

Tại sao UDP và tại sao 10 giây?

UDP: App gửi metric → “bay” vào socket → làm việc tiếp ngay. Không đợi confirmation. Nếu DogStatsD bận hoặc down → packet bị drop nhưng app không bị ảnh hưởng. App performance là ưu tiên #1, monitoring là #2.

10 giây flush: Trong 10 giây, app có thể gửi hàng nghìn data points (ví dụ: mỗi request gửi 1 counter increment). DogStatsD aggregate tất cả lại → gửi 1 data point cho Forwarder mỗi 10 giây. Hiệu quả hơn nhiều so với gửi thô từng packet.

Ví dụ Count aggregation trong 10 giây:
  t=0.1s: request increment → DogStatsD nhận: 1
  t=0.3s: request increment → DogStatsD nhận: 1
  t=0.7s: request increment → DogStatsD nhận: 1
  ... (tổng 500 requests trong 10 giây)

  t=10s: Flush!
  → Forwarder nhận: app.requests = 500 (tổng count trong 10s window)
  → Gửi lên Datadog: 1 data point

2.3 API Key vs Application Key — Hai Loại Credential Hoàn Toàn Khác Nhau

Mô hình bảo mật của Datadog

Datadog thiết kế 2 loại key với mục đích hoàn toàn khác nhau:

API Key    = "Tôi được phép GỬI data vào tổ chức này"
           → Như chìa khoá vào "hòm thư" (chỉ bỏ thư vào được)

App Key    = "Tôi được phép ĐỌC và QUẢN LÝ data của người dùng X"
           → Như chìa khoá vào "văn phòng" (đọc và sửa mọi thứ)

Tại sao tách ra?

Scenario hiểu tại sao cần tách:

  • Bạn có 500 servers, mỗi server cần API Key để gửi metrics
  • Nếu API Key = Application Key → mỗi server có thể đọc data nhạy cảm, xoá monitors, sửa dashboards
  • Khi 1 server bị hack → attacker có toàn quyền

Giải pháp:

  • API Key chỉ cho phép write → server bị hack chỉ có thể gửi sai data (đã đủ tệ, nhưng ít hơn)
  • Application Key gắn với 1 user cụ thể → audit trail, revoke khi user rời công ty

Bảng so sánh chi tiết

API KeyApplication Key
Mục đíchSubmit (gửi) data lên DatadogRead + Manage (đọc/quản lý) resources
Scoped toOrganizationUser (cá nhân)
Agent cần?✅ Bắt buộc❌ Không cần
Số lượng limit50 per organization (mặc định, có thể xin thêm)Không giới hạn
Khi user bị disabled?API Keys vẫn activeApplication Keys tự động bị revoked

★ Official Workshop: Datadog không hỗ trợ xoá user vĩnh viễn, chỉ disable. Khi disable:

  • Application Keys → tự động revoked
  • API Keys → vẫn active trong org

★ Rule nhớ mãi: Nếu bạn gửi data → chỉ cần API Key. Nếu bạn đọc hoặc quản lý → cần cả hai.

2.4 Cách Datadog Agent Xác Định Hostname — Thứ Tự Ưu Tiên

Tại sao Hostname quan trọng?

Hostname là định danh duy nhất của host trong Datadog. Mọi metrics, logs, traces đều gắn với hostname. Nếu hostname sai hoặc thay đổi → data bị tách ra thành 2 hosts khác nhau → billing ×2, graphs bị vỡ.

Thứ tự Agent xác định hostname (từ cao đến thấp)

Agent quyết định hostname theo thứ tự ưu tiên (priority):

  1. hostname trong datadog.yaml / DD_HOSTNAME  ← Nếu set → dùng ngay, bỏ qua tất cả
  2. Hostname từ Cloud Provider API             ← EC2 instance ID, GCE instance name...
  3. Kubernetes/Orchestrator API                ← Kubelet API (containerized environments)
  4. OS hostname (os.Hostname())                ← Output của `hostname` command

  ┌────────────────────────────────────────────────────────┐
  │ Priority 1: datadog.yaml → hostname: "web-prod-01"    │ ← Nếu có → DONE
  │ Priority 2: AWS EC2 → i-0abc123def456               │ ← Nếu P1 trống
  │ Priority 3: Kubelet → pod/node name                  │ ← Container env
  │ Priority 4: OS → ip-172-16-0-15.ec2.internal         │ ← Fallback cuối
  └────────────────────────────────────────────────────────┘

Vấn đề thường gặp

Scenario 1: EC2 instance bị terminate rồi tạo mới
  → Instance ID mới (i-0abc → i-0xyz)
  → Datadog thấy 2 hosts khác nhau!
  → Fix: Set hostname cố định trong datadog.yaml

Scenario 2: Container/Pod restart
  → Hostname = container ID (random mỗi lần restart)
  → Fix: Map hostname về pod name hoặc node name

Scenario 3: Auto Scaling Group
  → Instances tạo/xoá liên tục
  → Hostname thay đổi liên tục
  → Fix: Dùng tags (autoscaling_group, service) thay vì hostname

Cấu hình trong datadog.yaml

Proxy Configuration (từ Official Workshop)

★ Exam tip: “Host not appearing” hoặc “duplicate hosts” → kiểm tra hostname resolution. Agent xem hostname đầu tiên từ datadog.yaml, sau đó Cloud Provider, sau đó Kubelet (container), sau đó OS.

Tại sao không cần restart?

★ Exam scenario: “Đổi log level không restart” → config set log_level debug. “Đổi vĩnh viễn” → sửa datadog.yaml + restart.

2.7 Autodiscovery — Vấn Đề Containers Động

Bối cảnh: Tại sao static config không đủ với containers?

Static config (thế giới bare-metal):
  Server web-01: luôn chạy NGINX → conf.yaml cố định → OK

Container world:
  09:00: Pod A (NGINX) khởi động trên Node 1, IP: 172.16.0.15
  09:30: Pod A chết, Pod B (NGINX) mới start trên Node 2, IP: 172.16.1.42
  10:00: Scale lên 5 NGINX pods, IPs: 172.16.0.15-.19
  
  → IP thay đổi liên tục
  → Số lượng thay đổi liên tục  
  → Không thể hardcode conf.yaml!

Giải pháp: Template-based Configuration

Thay vì config với IP cố định, Autodiscovery dùng templates với placeholders:

%%host%% sẽ tự động được thay bằng IP của container đang chạy.

Tắt Autodiscovery cho integration cụ thể (từ Official Workshop)

Luồng Autodiscovery

Bước 1: Container mới start
Container start → Docker daemon event → Agent nhận event

Bước 2: Identify template
Agent kiểm tra container metadata:
  - Docker labels (com.datadoghq.ad.check_names)  
  - Kubernetes pod annotations (ad.datadoghq.com/<name>.checks)
  - Image name → match với built-in template

Bước 3: Resolve template
  Template: http://%%host%%/nginx_status
  → %%host%% = 172.16.0.15 (từ container network info)
  → Result: http://172.16.0.15/nginx_status

Bước 4: Apply và start monitoring
  Agent load resolved config → start NGINX check cho container này

Bước 5: Container stop
  Agent nhận stop event → remove check → cleanup

Kubernetes Annotation Example (Cần hiểu format)

Container Labels — Cấu Hình Autodiscovery Bằng Docker Labels

Ngoài Kubernetes Annotations, bạn có thể dùng Docker labels để cấu hình Autodiscovery. Đây là cách phổ biến khi chạy Docker thuần (không dùng K8s).

Cơ chế

Khi container start:
  Agent đọc Docker labels từ container metadata
  → Nếu thấy labels bắt đầu bằng com.datadoghq.ad.*
  → Parse config từ labels
  → Tạo integration check tự động

Khi container stop:

2.8.1 Agent Flare — Chi Tiết Cơ Chế Debug Bundle

datadog-agent flare làm gì?

Khi bạn gặp vấn đề mà không tự giải quyết được và cần Datadog Support hỗ trợ, flare tạo một ZIP bundle chứa toàn bộ thông tin debug rồi gửi trực tiếp đến Datadog Support.

Flare thu thập những gì?

datadog-agent flare <CASE_ID>

Flare bundle bao gồm:
  ┌──────────────────────────────────────────────────────────┐
  │ 📁 flare-<hostname>-<timestamp>.zip                     │
  │                                                          │
  │ 📄 agent-status.txt          ← Output của `status`      │
  │ 📄 config-check.txt          ← Output của `configcheck` │
  │ 📄 datadog.yaml              ← Config chính (REDACTED!) │
  │ 📄 conf.d/**/*.yaml          ← Tất cả integration configs│
  │ 📄 agent.log                 ← Log files gần nhất       │
  │ 📄 process-agent.log         ← Process Agent logs       │
  │ 📄 trace-agent.log           ← APM Agent logs           │
  │ 📄 diagnose.log              ← Kết quả connectivity test│
  │ 📄 metadata.json             ← Host/Agent metadata      │
  │ 📄 permissions.log           ← File permission issues   │
  │ 📄 secrets.log               ← Secret backend status    │

  ✅ Passwords     → ********

2.9 Agent Version 6 vs Version 7 — Khác Biệt Chính

Tại sao cần biết?

Đề thi có thể hỏi về sự khác biệt giữa Agent v6 và v7. Trong thực tế, nhiều hệ thống legacy vẫn chạy v6, nên việc hiểu khác biệt giúp bạn lên kế hoạch migration.

Bảng so sánh

Agent v6Agent v7
PythonPython 2 (embedded)Python 3 only
Hỗ trợ Python 2✅ Có❌ Dropped
Ngôn ngữ chínhGo + Python 2Go + Python 3
PerformanceTốtTốt hơn (Go improvements)
Config filedatadog.yamldatadog.yaml (tương thích)
Custom checksPython 2 hoặc 3Chỉ Python 3
OS supportNhiều OS cũDrop một số OS cũ
End of LifeĐã EOL (ngừng hỗ trợ)Current (stable)

Điểm khác biệt quan trọng

1. PYTHON VERSION
   v6: Chạy custom checks bằng Python 2 hoặc 3 (có flag chọn)
   v7: CHỈ Python 3 → custom checks Python 2 sẽ KHÔNG hoạt động!
   
   Migration impact:
     Nếu bạn có custom check dùng syntax Python 2:
     → print "hello"        ← Python 2 (v6 OK, v7 LỖI!)
     → print("hello")       ← Python 3 (v6 OK, v7 OK)

2. DEFAULT BEHAVIORS
   v7 thay đổi một số default values so với v6:
   - `use_dogstatsd` mặc định = true (giống v6)
   - Một số integrations deprecated hoặc thay thế

3. UPGRADE PATH
   v6 → v7: "In-place upgrade" — config file tương thích
   v5 → v7: Cần migration tool (v5 dùng config format khác)

Lệnh kiểm tra version

★ Exam tip: “Custom check fails after upgrade” → Kiểm tra Python 2 syntax. Agent v7 chỉ hỗ trợ Python 3.

2.10 Câu Hỏi Thường Gặp

Q: Ba components của Agent?
→ Collector (thu thập, 15s), Forwarder (gửi/buffer, HTTPS 443), DogStatsD (nhận custom, UDP 8125)

Q: Tại sao DogStatsD dùng UDP?
→ Để app không bao giờ bị block chờ monitoring — performance > reliability của metrics

Q: API Key vs Application Key?
→ API Key = gửi data (Agent cần). App Key = đọc/quản lý data (API queries cần)

Q: Sau khi sửa config cần làm gì?
→ Restart Agent (systemctl restart datadog-agent) — Agent không tự reload

Q: Đổi log level không restart?
→ datadog-agent config set log_level debug (reset về default sau khi restart)

Q: Container gửi DogStatsD cần config gì?
→ dogstatsd_non_local_traffic: true trong datadog.yaml (default chỉ accept localhost)

Q: Autodiscovery giải quyết vấn đề gì?
→ Tự động detect và config monitoring cho containers dynamic (IP/count thay đổi liên tục)

Q: datadog-agent flare dùng khi nào?
→ Khi cần Datadog Support giúp debug — tạo ZIP bundle chứa config, logs, status (tự scrub credentials)

Q: Agent v6 vs v7 khác gì?
→ v7 chỉ hỗ trợ Python 3 (drop Python 2). Custom checks Python 2 sẽ lỗi sau khi upgrade.

Q: Hostname được xác định thế nào?
→ Ưu tiên: datadog.yaml / DD_HOSTNAME > Cloud Provider API > Kubelet (container) > OS hostname

Q: Dual Shipping là gì?
→ Gửi cùng data đến nhiều Datadog orgs cùng lúc qua additional_endpoints trong config.

Q: Docker Labels Autodiscovery prefix là gì?
→ com.datadoghq.ad.* (khác K8s annotations: ad.datadoghq.com/*)
