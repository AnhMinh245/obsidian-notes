Phần 10: Kubernetes, Cloud & Chiến Lược Thi

PHẦN A: KUBERNETES MONITORING

10.1 Tại Sao Kubernetes Phức Tạp Hơn Bare-Metal?

Bare-metal/VM (đơn giản):
  Server A: Luôn chạy NGINX → cài Agent → static config → xong

Kubernetes (phức tạp):
  Pod lifecycle: start → stop → reschedule → scale up/down
  Mỗi Pod có IP riêng, thay đổi mỗi lần restart
  1 Node có thể chạy 50 pods, mỗi pod 1 app khác nhau
  
  → Không thể static config cho từng pod!
  → Agent phải auto-discover và auto-configure (Autodiscovery)
  → Cần 1 Agent per Node (DaemonSet) không phải per Pod

10.2 DaemonSet — Tại Sao Không Phải Sidecar?

Option 1: Sidecar (Không phải cách Datadog dùng)

Mỗi pod có container agent riêng:
  [pod-A: app + dd-agent]
  [pod-B: app + dd-agent]
  [pod-C: app + dd-agent]
  
  Vấn đề:
  ❌ 50 pods × 256MB RAM (Agent) = 12.8GB RAM overhead!
  ❌ 50 agents gửi data = 50× API requests
  ❌ 50 agents cho same node → duplicate node-level metrics

Option 2: DaemonSet (Cách Datadog dùng)

1 Agent per NODE (không phải per pod):

Node 1:
  [dd-agent pod] ← 1 Agent
  [app-pod-A]    ← Monitor bởi dd-agent trên Node 1
  [app-pod-B]    ← Monitor bởi dd-agent trên Node 1
  [app-pod-C]    ← Monitor bởi dd-agent trên Node 1

Node 2:
  [dd-agent pod] ← 1 Agent
  [app-pod-D]
  [app-pod-E]

K8s DaemonSet đảm bảo: Mỗi Node có đúng 1 Agent Pod
→ Khi thêm Node mới → Agent Pod tự động deploy
→ Khi bớt Node → Agent Pod tự động removed

Node Agent vs Cluster Agent:

Node Agent (DaemonSet):
  - Chạy trên MỖI node
  - Thu thập: Pod metrics, container logs, node metrics
  - Chạy autodiscovery checks cho pods trên node đó

Cluster Agent (Deployment):
  - Chạy 1 instance (hoặc 2 cho HA)
  - Thu thập: Cluster-level events, Kubernetes state metrics
  - Serves as proxy cho Kubernetes API → giảm tải API server
  - Quản lý cluster-level checks (HPA, DaemonSet state, PV...)

Lý do cần Cluster Agent:
  50 Node Agents đều query K8s API riêng → 50 × N queries/giây
  Cluster Agent query K8s API 1 lần → cache → Node Agents hỏi Cluster Agent
  → Kubernetes API server không bị overload

10.3 AWS Integration — Crawler-Based Chi Tiết

Cách setup:

1. Tạo IAM Role trong AWS:
   AWS Account (your) → IAM Role → Trust Policy: Allow Datadog to assume
   Permissions: AmazonEC2ReadOnlyAccess, CloudWatchReadOnlyAccess, ...

2. Provide Role ARN to Datadog:
   Datadog UI → Integrations → AWS → thêm Account ID + Role ARN

3. Datadog backend:
   Assume IAM Role → Call CloudWatch GetMetricData → Process → Store
   Tần suất: mỗi ~10 phút (AWS default, khác theo provider: GCP ~5 min, Azure ~2 min)

Metrics tự động available:
  aws.ec2.cpuutilization
  aws.rds.freestoragespace
  aws.lambda.duration
  aws.alb.requestcount
  ...

Tags được import:
  AWS resource tags → Datadog tags (tự động!)
  EC2 tag "Environment:production" → Datadog tag "environment:production"

10.3a Operator vs Helm — Hai Cách Deploy Agent Trên K8s

So sánh

Helm ChartDatadog Operator
MechanismTemplate engine → generate K8s manifestsCRD (DatadogAgent) → Operator reconciles
Configvalues.yamlDatadogAgent custom resource YAML
Installhelm install datadog datadog/datadog -f values.yamlkubectl apply -f datadog-agent.yaml
Upgradeshelm upgrade (manual)Operator auto-reconcile khi thay đổi CR
LifecycleUser quản lýOperator quản lý (self-healing)
ComplexityĐơn giản hơn, phổ biến hơnMạnh hơn, phù hợp GitOps

Khi nào dùng cái nào?

Helm Chart (phổ biến nhất, đủ cho 90% use cases):
  - Team đã quen Helm
  - Setup đơn giản, ít customization
  - Phù hợp cho labs, POC, small-medium clusters

Datadog Operator (advanced):
  - GitOps workflow (ArgoCD, FluxCD)
  - Cần tự động upgrades, self-healing
  - Multi-cluster deployment chuẩn hoá
  - Operator quản lý DaemonSet + Cluster Agent + Cluster Checks Runner

Fleet Automation

  • Datadog cung cấp Fleet Automation (beta) để quản lý Agent ở quy mô lớn
  • Centralized: xem status, config, version của tất cả Agents từ Datadog UI
  • Remote Configuration: push config changes không cần SSH/kubectl

★ Exam tip: Helm là cách phổ biến nhất. Operator là cách declarative hơn, quản lý lifecycle tự động.

10.5 Top 38 “Must Know” — Sự Thật Cần Thuộc Lòng

Agent & Architecture

  1. 3 components: Collector (15s), Forwarder (HTTPS 443), DogStatsD (UDP 8125)
  2. APM Agent: TCP 8126
  3. Config chính: /etc/datadog-agent/datadog.yaml
  4. Integration configs: /etc/datadog-agent/conf.d/<name>.d/conf.yaml
  5. logs_enabled: true phải explicit (default = false!)
  6. datadog-agent status = first command for any troubleshooting
  7. Component defaults: Collector ✅, Forwarder ✅, DogStatsD ✅, APM ✅(v6+/v7), Logs ❌, Process ⚠️, NPM ❌, Security ❌
  8. Agent Flare: datadog-agent flare <CASE_ID> → tạo ZIP debug bundle, tự động scrub credentials trước khi gửi Support
  9. Hostname Resolution: datadog.yaml / DD_HOSTNAME → Cloud Provider API → Kubelet (container) → OS hostname (thứ tự ưu tiên)
  10. Dual Shipping: Gửi data đến nhiều Datadog org bằng additional_endpoints trong datadog.yaml
  11. Agent v7 vs v6: v7 chỉ Python 3, v6 hỗ trợ Python 2. Custom checks Python 2 phải migrate trước khi upgrade

Metrics

  1. Gauge = giá trị cuối (snapshot)
  2. Count = tổng (sum of events)
  3. Rate = count ÷ time (per second)
  4. Histogram = client-side, 5 metrics per histogram (mặc định, configurable), inaccurate cross-host
  5. Distribution = server-side, globally accurate percentiles
  6. High cardinality tags → exponential timeseries growth → avoid!
  7. Metric Categories: Work Metrics (throughput/success/error/performance), Resource Metrics (utilization/saturation/error/availability), Events
  8. Metric Query = 5 phần: Metric name + Scope + Time Agg + Space Agg + Function

Tagging

  1. 3 UST tags: env, service, version
  2. Tag format: key:value, lowercase, starts with letter
  3. Tags trong datadog.yaml → áp dụng TẤT CẢ data từ host

Monitor Types (Quan trọng nhất!)

  1. Threshold → ngưỡng cố định (biết exact cutoff)
  2. Anomaly → ML so sánh với lịch sử (seasonal patterns)
  3. Forecast → dự đoán tương lai proactively (disk capacity)
  4. Outlier → so sánh peers vs peers (1 server different từ cluster)
  5. Composite → AND/OR logic (reduce false positives)

Integrations

  1. 3 loại: Agent-based (15s, local check), Crawler-based (~2-10 phút tuỳ provider, cloud API), Library/API-based (app code gửi qua SDK/API)
  2. AWS = Crawler-based (CloudWatch)
  3. DogStatsD custom metrics = Library-based

Logs

  1. Journey of a Log (10 bước): Emission → Ingestion → JSON Preprocessing → Pipeline Processing → Standard Attributes → Sensitive Data Scanner → Security Rules → Error Tracking → Anomaly Detection → Routing
  2. Routing destinations: Live Tail (bắt buộc, free), Generate Metrics, Indexes, Log Forwarding (Archives + Custom Destinations), Cloud SIEM
  3. Logging Without Limits™ = ingest all, index only important, archive all
  4. Grok Parser: %{MATCHER:ATTRIBUTE:TYPE}

API Keys

  1. API Key = submit data (Agent cần duy nhất cái này)
  2. Application Key = read + manage data (cần cả hai cho API queries)

Dashboards

  1. Timeboard (nay là grid-based Dashboard) = correlated time range (troubleshooting)
  2. Screenboard (nay là free-form Dashboard) = free-form layout (NOC, status)

⚠️ Datadog đã hợp nhất Timeboard/Screenboard thành 1 loại Dashboard duy nhất (~2020), nhưng concepts vẫn hỏi trong đề thi.

10.8 Chiến Lược Làm Bài

Time management

90 câu / 120 phút = 1.3 phút/câu

Strategy:
  Pass 1 (60 phút): Câu chắc chắn → làm ngay
  Pass 2 (40 phút): Câu không chắc → phân tích, loại sai
  Pass 3 (20 phút): Review toàn bộ, đặc biệt câu đã skip

Đọc câu hỏi — từ khoá quan trọng

Từ khoáThường ý muốn
”First step”Dùng datadog-agent status hoặc check <name>
”Without restarting”config set log_level debug
”Support bundle”datadog-agent flare
”Globally accurate percentiles”Distribution (không phải Histogram)
“Cross-host percentiles”Distribution
”Seasonal patterns”Anomaly Monitor
”Proactive”Forecast Monitor
”Peers”Outlier Monitor
”Reduce false positives”Composite Monitor (AND)
“Cost optimization logs”Logging Without Limits
”Non-indexed logs”Archive (không phải deleted!)
”Send debug info to support”datadog-agent flare (tự scrub credentials)
“Logs not appearing”Kiểm tra logs_enabled: true (default disabled!)
”SDK”, “client library”Library/API-based integration
”Multiple Datadog orgs”Dual Shipping (additional_endpoints)
“Which components enabled”Collector ✅, DogStatsD ✅, APM ✅(v6+/v7), Logs ❌

Kỹ thuật loại đáp án

4 answers → thường 2 clearly wrong (loại ngay), 2 plausible (phân tích)

Ví dụ:
  "Cần debug integration NGINX"
  A. datadog-agent status         ← Possible (tổng quan)
  B. datadog-agent check nginx    ← CORRECT (specific integration!)
  C. cat /var/log/datadog/agent.log    ← Manual, không structured
  D. datadog-agent flare          ← Chỉ khi cần Support, không phải debug
  
  Loại D (flare = support bundle, không phải local debug)
  Loại C (không phải first structured step)
  A vs B: B cụ thể hơn → B wins
