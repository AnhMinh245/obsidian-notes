Lab 08 — SLOs & Database Monitoring (Kubernetes)

⏱️ Thời gian: ~45 phút
📋 Prerequisites: Lab 07 hoàn thành, Storedog đang chạy trên Minikube
🔗 Source: DataDog/storedog

🎯 Mục Tiêu

Sau lab này, bạn sẽ:

  • Tạo SLO (Service Level Objective) trên Datadog
  • Hiểu Error Budget visualization và burn rate
  • Cấu hình Database Monitoring cho PostgreSQL trên Kubernetes
  • Tạo SLO-based alert (burn rate monitor)
  • Nắm kiến trúc tổng thể Datadog trên Kubernetes sau 8 labs

📚 Kiến Thức Nền

Fundamentals

  • Ch.06 — SLI, SLO & Error Budgets
    → SLI definition, SLO targets, error budget, burn rate, budget policies

Cách học lab này

Lab này gồm hai kỹ năng khác nhau: định nghĩa độ tin cậy và chẩn đoán database

  • Phần SLO dạy bạn tư duy chính sách: service nào quan trọng, “good” nghĩa là gì, và mức lỗi nào còn chấp nhận được trong một khoảng thời gian dài.
  • Phần DBM dạy bạn tư duy điều tra ngắn hạn: query nào chậm, database đang nghẽn ở đâu, và app có đang bị ảnh hưởng bởi DB behavior hay không.
  • Phần K8s-specific: PostgreSQL chạy như Deployment (hoặc StatefulSet) với PersistentVolumeClaim, DBM config qua Autodiscovery annotation trên Pod — pattern giống các integration khác bạn đã thấy ở labs trước.

1. SLO — Service Level Objectives

1.1. Nhắc lại concept

🔗 Fundamentals: Ch.06

SLI (Indicator)  = "Bao nhiêu % requests thành công?"
SLO (Objective)  = "SLI phải ≥ 99.5% trong 30 ngày"
Error Budget     = "Được phép có 0.5% requests thất bại (250/50000)"

1.2. SLO types trên Datadog

Datadog hỗ trợ 3 loại SLO:

TypeBased onCách tính
Metric-basedMetric queriesGood events / Total events
Monitor-basedMonitor uptime% time monitor in OK state
Time SliceGood time slices% time windows đạt điều kiện SLI

3 types, không phải 2

Một số tài liệu cũ chỉ nhắc Metric-based và Monitor-based. Time Slice là loại thứ ba — nó chia timeline thành các khoảng nhỏ (slices) và đếm bao nhiêu % slices đạt SLI.

1.3. Tạo Metric-based SLO

  1. Vào Service Management → SLOs → New SLO
    • Nếu menu thay đổi, dùng global search (Ctrl/Cmd + K) và tìm SLO
  2. Chọn Metric-based
  3. Cấu hình:

Good events (Numerator):

sum:trace.flask.request.hits{service:store-discounts}.as_count()
-
sum:trace.flask.request.errors{service:store-discounts}.as_count()

(Tổng requests - errors = successful requests)

Total events (Denominator):

sum:trace.flask.request.hits{service:store-discounts}.as_count()

Hoặc đơn giản hơn:

  • Good: trace.flask.request.hits (all requests)
  • Bad: trace.flask.request.errors (error requests)
  • Datadog tự tính: good = total - bad

trace.flask.request.* chỉ đúng cho service entrypoint dùng Flask

Nếu metric này không autocomplete trong tenant của bạn, dùng Metrics Summary để tìm đúng prefix của service. Trên K8s, service name có thể khác (phụ thuộc DD_SERVICE env var hoặc tags.datadoghq.com/service label trên Pod).

  1. Target & Timeframe:

    • Target: 99.5%
    • Warning: 99.8%
    • Timeframe: 7 days (rolling)

  2. Name & Description:

    • Name: Storedog Discounts Availability
    • Description: Availability of discount service — percentage of successful requests
    • Tags: service:store-discounts, env:dev

  3. Click Create

1.5. Hiểu Error Budget

Error Budget = “giấy phép được fail”

SLO Target: 99.5% over 7 days
Total requests in 7 days: ~50,000

Error Budget = 50,000 × 0.5% = 250 requests
  → Bạn ĐƯỢC PHÉP có 250 failed requests

If actual failures = 45:
  Budget used:  45/250 = 18%
  Budget left:  82%  ← SAFE! Có thể deploy features

If actual failures = 200:
  Budget used:  200/250 = 80%
  Budget left:  20%  ← DANGER! Freeze deploys, fix reliability

🔗 Fundamentals: Ch.06 — Error Budget Policies. Error budget = decision-making tool: budget > 50% → ship features, budget < 20% → focus reliability.

2. SLO Performance (Latency)

2.1. Tạo thêm 1 SLO

  1. New SLO → Metric-based
  2. Cấu hình:
    • Good events: Requests với latency < 500ms
    • Total: All requests
  3. Target: 95% (95% requests < 500ms)
  4. Name: Storedog Discounts Performance

Latency SLO phức tạp hơn

Latency SLO cần metric với percentile data hoặc custom metric. Nếu khó cấu hình, focus vào Availability SLO (section 1) — concept error budget giống nhau.

3. SLO Burn Rate Alert

3.1. Concept: Burn Rate

Burn rate = “error budget đang bị consume nhanh như thế nào?“

Normal burn rate = 1x (consume đều 0.5% over 30 days)
Burn rate 2x = consume gấp đôi → budget hết trong 15 days
Burn rate 10x = consume gấp 10 → budget hết trong 3 days → CRITICAL!

3.2. Tạo SLO Alert

  1. Từ SLO page → click SLO vừa tạo
  2. Click Set up Alerts (hoặc Create Alert)
  3. Cấu hình:
    • Alert type: Burn Rate
    • Alert: Burn rate > 10x over 5 minutes
    • Warning: Burn rate > 2x over 30 minutes
  4. Notification: 
    ## SLO Burn Rate Alert — {{slo.name}}

Error budget for **{{slo.name}}** is being consumed at {{value}}x rate.

**Current SLI**: {{slo.value}}
**Target**: {{slo.target}}
**Budget remaining**: {{slo.remaining_budget}}%

@yourname@email.com
  5. Click Create

Error budget alerts không áp dụng y hệt cho mọi SLO type

Datadog hiện hỗ trợ burn-rate/error-budget alerts cho metric-based SLOs, nhiều monitor-based SLOs đủ điều kiện, và Time Slice SLOs. Nếu nút/option không xuất hiện, kiểm tra lại loại SLO bạn đã tạo.

Tại sao Burn Rate alert > Static threshold alert?

ApproachVấn đề
”Alert khi error rate > 5%“Quá trễ — budget có thể đã hết
”Alert khi error rate > 0.5%“Quá sớm — false positives nhiều
Burn rate alertJust right — alert khi budget BỊ CONSUME NHANH

🔗 Fundamentals: Ch.06 — Burn Rate Alerting. Multi-window burn rate = best practice cho SLO alerting. Google SRE Handbook recommends this approach.

  1. Click Query Metrics tab
  2. Bạn sẽ thấy:

    • Avg latency — thời gian trung bình mỗi query
    • Rows per query — bao nhiêu rows returned
    • Calls per second — query throughput

4.7. Query Samples & Explain Plans

  1. Click Query Samples tab
  2. Xem individual query executions:
    • Exact query text
    • Execution time
    • Plan — query execution plan (EXPLAIN)
    • Source — which service called this query

Query Samples là sampled view, không phải exhaustively mọi query

Nếu bạn không thấy đúng câu query vừa chạy, có thể query đó chưa lọt vào sample window hiện tại.

Explain Plans giúp optimize:

  • Seq Scan trên bảng lớn → cần thêm INDEX
  • Nested loop với nhiều rows → cần optimize JOIN
  • High cost → query cần rewrite

Không phải query sample nào cũng có Explain Plan. Availability phụ thuộc query type, database permissions, và cách Datadog thu thập sample.

🔗 Fundamentals: Ch.01 — Database Monitoring. Database = critical infrastructure component. Slow queries ảnh hưởng toàn bộ application performance.

⚠️ Troubleshooting

SLO shows “Insufficient data”

  • SLO cần metric data within timeframe (7 days)
  • Nếu vừa setup Storedog, chờ vài giờ có đủ data
  • Thử đổi timeframe sang shorter (1 day)

DBM không hiện data

Checklist DBM trên K8s:

  • Annotation ad.datadoghq.com/postgres.checks đúng cú pháp JSON
  • Container name trong annotation khớp với container name trong Pod spec
  • User datadog có role pg_monitor
  • Agent DaemonSet Pod đang chạy trên cùng node với postgres Pod

SLO alert không trigger

  • Burn rate threshold quá cao? Thử giảm threshold
  • Error rate quá thấp (Storedog healthy) → không đủ trigger
  • Verify SLO data đang được collected trên SLO page

Agent không phát hiện postgres Pod
