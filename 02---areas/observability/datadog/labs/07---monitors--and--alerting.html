Lab 07 — Monitors & Alerting

⏱️ Thời gian: ~45 phút
📋 Prerequisites: Lab 06 hoàn thành, Storedog chạy trên Minikube
🔗 Source: DataDog/storedog

🎯 Mục Tiêu

Sau lab này, bạn sẽ:

  • Hiểu Datadog Monitor types (Metric, APM, Log, Composite, Anomaly, Forecast)
  • Tạo Metric Monitor: alert khi CPU > threshold
  • Tạo APM Monitor: alert khi error rate > threshold
  • Tạo K8s-specific monitors: Pod restart, Deployment replicas
  • Cấu hình Notification message với template variables
  • Sử dụng Monitor Status page và Downtime scheduling
  • So sánh: Datadog Monitors (rule-based) vs Davis AI (automatic)

📚 Kiến Thức Nền

Fundamentals

  • Ch.07 — Alerting & Incident Management
    → Alert types, thresholds, notification routing, alert fatigue

Cách học lab này

Một alert tốt luôn có 5 thành phần: signal, scope, window, threshold, và routing

  • Lab này sẽ hữu ích hơn nhiều nếu bạn tự hỏi vì sao mình chọn metric đó, vì sao là 5 phút chứ không phải 1 phút hoặc 15 phút, và ai mới là người nên nhận notification đó.
  • Monitor trigger không đồng nghĩa incident đã được hiểu. Datadog monitors cho bạn biết “có điều bất thường cần chú ý”; phần điều tra root cause vẫn cần quay lại dashboards, logs, traces, và infra context.
  • Nếu thấy alert quá ồn hoặc quá im lặng, nguyên nhân thường không nằm ở message template mà ở scope, grouping, no-data behavior, hoặc threshold design ngay từ đầu.

1. Monitor Types — Concept

TypeTriggerUse case
Metric MonitorMetric crosses thresholdCPU > 80%, memory usage
APM MonitorAPM metric (error rate, latency)Service degradation
Log MonitorLog count/pattern matchesError log spike
Composite MonitorCombine multiple monitors”CPU > 80% AND disk > 90%“
Anomaly MonitorMetric deviates from learned baselineUnusual traffic pattern
Forecast MonitorPredicted future value crosses thresholdDisk full in 3 days
Outlier MonitorHost deviates from peers1 node in cluster behaving differently
Process MonitorProcess up/downCritical daemon stopped

1.1. Anomaly Detection — Algorithms

Anomaly Monitor sử dụng 3 algorithms, mỗi loại phù hợp use case khác nhau:

AlgorithmKỹ thuậtĐặc điểmUse case
BasicLagging rolling quantileKhông giả định seasonality, phản ứng chậmMetric không có pattern tuần/ngày
AgileSARIMA (Seasonal ARIMA)Adapts nhanh khi level shiftMetric có seasonality + cần phát hiện thay đổi nhanh
RobustSeasonal-trend decompositionConservative, bỏ qua anomalies gần đây khi tính baselineMetric ổn định, ít false positives

Agile và Robust cần ~3 tuần historical data

Cả hai algorithm cần tối thiểu khoảng 3 tuần dữ liệu lịch sử để học weekly seasonality. Với metric mới, chỉ Basic hoạt động ngay.

1.2. Forecast Monitor — Algorithms

AlgorithmKỹ thuậtUse case
LinearOLS regression (Ordinary Least Squares)Metric tăng đều (disk usage, data growth)
SeasonalHolt-Winters exponential smoothingMetric có weekly/daily patterns (traffic)

1.3. Monitor States

┌──────────────────────────────────────────────────┐
│              Monitor State Machine               │
│                                                  │
│   OK ──→ Warn ──→ Alert                          │
│    ↑       │        │                            │
│    └───────┴────────┘  (recovery)                │
│                                                  │
│   No Data   (Agent stopped / metric missing)     │
│   Unknown   (service checks only)                │
│   Skipped   (evaluation status, NOT a state)     │
└──────────────────────────────────────────────────┘
  • OK / Warn / Alert / No Data: monitor states thực sự
  • Unknown: chỉ xuất hiện với service check monitors
  • Skipped: trạng thái evaluation (monitor bị skip do downtime hoặc dependency), không phải state

🔗 Fundamentals: Ch.07 — Static vs Dynamic Thresholds. Metric Monitor = static threshold. Anomaly Monitor = dynamic (Datadog tự learn baseline).

2. Tạo Metric Monitor — CPU Alert

2.1. Tạo Monitor

  1. Vào Monitors → New Monitor → Metric
  2. Cấu hình:

Step 1 — Choose detection method:

  • ✅ Threshold Alert

Step 2 — Define the metric:

avg(last_5m):avg:system.cpu.user{*} > 80
  • Metric: system.cpu.user
  • Scope: {*} (all hosts — trong K8s, Minikube node)
  • Function: avg: averaged over sources
  • Evaluation window: last_5m (5 phút)

Step 3 — Set alert conditions:

  • Alert threshold: > 80 (CPU > 80% → ALERT)
  • Warning threshold: > 60 (CPU > 60% → WARNING)
  • Recovery: < 70 (alert auto-resolves when CPU < 70%)

Step 4 — Notify your team:

## CPU Alert on {{host.name}}

CPU usage is {{#is_alert}}**CRITICAL** at {{value}}%{{/is_alert}}
{{#is_warning}}elevated at {{value}}%{{/is_warning}}
{{#is_recovery}}recovered to {{value}}%{{/is_recovery}}

**Host**: {{host.name}}
**Last Value**: {{value}}%

@yourname@email.com
  1. Click Create

2.2. Hiểu template variables

VariableÝ nghĩa
{{host.name}}Hostname triggering alert
{{value}}Current metric value
{{#is_alert}}...{{/is_alert}}Conditional: chỉ hiện khi ALERT state
{{#is_warning}}...{{/is_warning}}Conditional: chỉ hiện khi WARNING state
{{#is_recovery}}...{{/is_recovery}}Conditional: chỉ hiện khi RECOVERY
@emailNotification recipient

3. Tạo APM Monitor — Error Rate Alert

3.1. Tạo Monitor

  1. Monitors → New Monitor → APM
  2. Cấu hình:

Service: store-discounts
Type: Error Rate
Condition: Error rate > 5% over last_10m
Warning: > 2%

Notification:

## Error Rate Alert — {{service.name}}

Error rate on **{{service.name}}** is at {{value}}%

This may indicate:
- Database connection issues (PostgreSQL Pod healthy?)
- Application bugs in discounts service
- Upstream dependency failures

**Service**: {{service.name}}
**Environment**: {{env.name}}

@yourname@email.com
  1. Click Create

3.2. Tại sao APM Monitor riêng?

APM Monitor hiểu service context:

  • Tự tính error rate từ traces (không cần manual metric)
  • Có thể alert theo service, resource (endpoint), env
  • So sánh: Metric Monitor generic → APM Monitor service-aware

4. K8s-Specific Monitors

Trong Kubernetes, có những failure modes đặc trưng mà Docker Compose không có. Phần này tạo monitors cho các tín hiệu K8s quan trọng nhất.

4.1. Pod Restart Monitor (CrashLoopBackOff Detection)

  1. Monitors → New Monitor → Metric
  2. Cấu hình:
change(avg(last_5m),last_5m):avg:kubernetes.containers.restarts{kube_namespace:storedog} by {pod_name} > 3
  • Metric: kubernetes.containers.restarts
  • Detection: Change Alert (delta trong 5 phút)
  • Scope: kube_namespace:storedog
  • Group by: pod_name → mỗi pod alert riêng
  • Threshold: > 3 restarts trong 5 phút

Notification:

## Pod Restart Alert — {{pod_name.name}}

Pod **{{pod_name.name}}** has restarted {{value}} times in 5 minutes.

Likely causes:
- CrashLoopBackOff (OOMKilled, app crash)
- Liveness probe failure
- Missing ConfigMap/Secret

**Debug:**
```kubectl describe pod {{pod_name.name}} -n storedog```
```kubectl logs {{pod_name.name}} -n storedog --previous```

@yourname@email.com

4.2. Deployment Replica Monitor

  1. Monitors → New Monitor → Metric
  2. Cấu hình:
avg(last_5m):avg:kubernetes.deployment.replicas_available{kube_namespace:storedog} by {kube_deployment} < 1
  • Metric: kubernetes.deployment.replicas_available
  • Scope: kube_namespace:storedog
  • Group by: kube_deployment
  • Alert: < 1 (không còn replica available)
  • Warning: < 2 (nếu desired > 1)

K8s monitors = early warning trước khi user thấy downtime

Pod restart monitor bắt CrashLoopBackOff. Replica monitor bắt Deployment unhealthy. Kết hợp cả hai với APM error rate monitor → coverage rộng hơn nhiều so với chỉ dùng infrastructure metrics.

5. Monitor Status Page

5.1. Xem monitor status

  1. Vào Monitors → Manage Monitors
  2. Bạn sẽ thấy danh sách monitors + current status
StatusColorÝ nghĩa
OK🟢 GreenMetric within normal range
Warn🟡 YellowWarning threshold crossed
Alert🔴 RedAlert threshold crossed
No Data⚪ GrayNo data received

5.2. Monitor history

  1. Click vào 1 monitor
  2. Xem Status & History tab:
    • Timeline: state transitions over time
    • Events: khi nào trigger, khi nào recover
    • Group-by: nếu monitor scoped by tag (vd pod_name), xem mỗi group riêng

5.3. “No Data” is a problem too!

Đừng ignore "No Data" status

Trong K8s context, “No Data” thường nghĩa: Agent DaemonSet pod bị evict, node NotReady, hoặc Cluster Agent mất kết nối. Configure Notify on No Data trong monitor settings — đặc biệt quan trọng cho K8s monitors vì pod lifecycle thay đổi liên tục.

6. Downtime — Scheduled Maintenance

6.1. Concept

Downtime = “tôi biết service sẽ down, đừng alert”

Ví dụ trong K8s:

  • Rolling update Deployment (pods restart có chủ đích)
  • Node drain cho maintenance
  • Cluster upgrade (Minikube stop/start)

6.2. Schedule Downtime

  1. Vào Monitors → Manage Downtime → Schedule Downtime
  2. Cấu hình:
    • Scope: Chọn monitors hoặc tags (kube_namespace:storedog)
    • Start/End: Thời gian downtime
    • Message: “Planned rolling update for discounts service”
    • Recurring: Hàng tuần? Hàng tháng?
  3. Click Schedule

Downtime vs Mute:

  • Downtime = scheduled, có thời gian kết thúc
  • Mute = manual silence, phải tự unmute

7. So Sánh: Datadog Monitors vs Davis AI

FeatureDatadog MonitorsDynatrace Davis AI
SetupManual: bạn tạo mỗi monitorZero-config: Davis tự monitor
DetectionRule-based (threshold/anomaly)Baseline + topology-aware
CorrelationComposite Monitors, Watchdog gợi ý; nhưng không “1 problem” tự động như DavisTự correlate → 1 problem
Root causeChủ yếu bạn phân tích; Watchdog/related signals gợi ýDavis tự xác định qua Smartscape
Flexibility✅ Rất flexible — custom conditions❌ Ít tuỳ chỉnh — Davis decides
Transparency✅ Bạn biết exactly rule gì⚠️ “Black box” — trust Davis
Custom rules✅ Bất kỳ metric/condition❌ Limited custom alerting
Alert storm⚠️ Possible — nhiều monitors = nhiều alerts✅ Davis tự gộp
K8s awarenessTag-based (kube_*) + K8s integrationTopology-based (process → pod → node)

Practical advice:

  • Start with Datadog monitors → bạn hiểu rõ hệ thống trước
  • Davis AI tốt hơn cho large-scale → nhưng kém transparent
  • Production nên dùng cả hai: platform-specific (Davis) + custom rules (monitors)

🔗 Fundamentals: Ch.09 — Alert Correlation. Trọng tâm của lab này là Monitors. Datadog có Watchdog, Event Management và Incident workflows, nhưng chúng không thay thế hoàn toàn mô hình auto-problem correlation kiểu Davis.

8. Test Monitor — Trigger Alert Thật

Bài tập thực hành

Thử trigger CPU monitor bạn vừa tạo bằng stress test bên trong pod.

Option A: Stress CPU từ bên trong Pod (khuyến nghị)

Giải thích command:

  • for i in $(seq 1 4) → tạo 4 background processes
  • while true; do :; done → infinite CPU loop (: = no-op command)
  • sleep 60 → chờ 60 giây
  • kill $(jobs -p) → kill tất cả background jobs

Option B: Stress trên Minikube node

Verify

  1. Chờ ~5 phút (evaluation window last_5m)
  2. Vào Monitors → Manage Monitors → xem CPU monitor chuyển trạng thái
  3. Check email notification (nếu đã cấu hình @email)
  4. Sau stress kết thúc → monitor tự Recovery
  5. Xem Monitor History → timeline hiện state transitions

⚠️ Troubleshooting

Monitor shows “No Data”

K8s metrics không xuất hiện

Alert triggered nhưng không nhận notification

  • Check email (including spam folder)
  • Verify @email đúng trong notification message
  • Check Monitor Status → Events tab → verify event sent
  • Verify Datadog account email settings: Organization Settings → Notifications

Pod restart monitor false positives

  • Rolling updates tạo restarts hợp lệ → dùng Downtime trước khi deploy
  • Adjust threshold: > 3 restarts trong 5 phút đủ để lọc noise từ single restart
