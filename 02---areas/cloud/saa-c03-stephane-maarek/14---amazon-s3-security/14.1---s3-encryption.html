14.1 – S3 Encryption & Security

Cách đọc note này: Phần đầu (Encryption) đã có sẵn — giữ nguyên. Phần sau (từ “CORS” trở đi) là các tính năng bảo mật S3 khác ngoài encryption, bổ sung ngày 2026-09-13 để lấp đầy các topic từng bị đánh dấu “chưa có ghi chú” ở 14.0 - S3 Security Index. Đối chiếu thêm với 1.4 - Data Protection - KMS, ACM, Encryption và 1.5 - Security Services - WAF, Shield, GuardDuty nếu cần.

Amazon S3 hỗ trợ mã hóa dữ liệu ở hai giai đoạn:

  • At-Rest: dữ liệu được mã hóa khi lưu trong S3.
  • In-Transit: dữ liệu được mã hóa khi truyền giữa client và S3.

Server-Side Encryption (SSE) — S3 tự mã hóa

Với SSE, client upload bình thường — S3 tự mã hóa trước khi ghi xuống storage, tự giải mã khi đọc. Người dùng không phải tự encrypt/decrypt.

Có 3 biến thể SSE:

SSE-S3 — Mặc định (đơn giản nhất)

sequenceDiagram
    participant Client
    participant S3
    participant Storage

    Client->>S3: PUT object (plaintext)
    S3->>S3: Encrypt với S3-managed key (AES-256)
    S3->>Storage: Store ciphertext
    Client->>S3: GET object
    S3->>Storage: Fetch ciphertext
    S3->>S3: Decrypt với S3-managed key
    S3->>Client: Return plaintext
  • Key do AWS tạo, quản lý, lưu trữ — người dùng không thấy key.
  • Thuật toán: AES-256.
  • Mặc định cho mọi bucket và object mới từ 2023.
  • Không phát sinh chi phí thêm.
  • Không audit được việc sử dụng key.

Header để chỉ định SSE-S3 khi upload:

x-amz-server-side-encryption: AES256

Khi nào chọn: Chỉ cần mã hóa at-rest, không có yêu cầu audit/compliance.

SSE-KMS — Kiểm soát key qua KMS

sequenceDiagram
    participant Client
    participant S3
    participant KMS
    participant Storage

    Client->>S3: PUT object
    S3->>KMS: GenerateDataKey (log vào CloudTrail)
    KMS->>S3: Data key
    S3->>Storage: Store ciphertext + encrypted data key
    Client->>S3: GET object
    S3->>KMS: Decrypt data key (log vào CloudTrail)
    KMS->>S3: Plaintext data key
    S3->>Client: Return decrypted object
  • Key được quản lý bởi AWS KMS.
  • Có thể dùng AWS-managed key (aws/s3) hoặc Customer-managed key (CMK).
  • Mọi thao tác với key đều log vào CloudTrail → audit được.
  • Kiểm soát ai được dùng key qua IAM + KMS Key Policy.
  • Có thêm chi phí KMS API calls.

Header để chỉ định SSE-KMS:

x-amz-server-side-encryption: aws:kms

Lưu ý KMS Throttling:

  • Mỗi GET/PUT object đều gọi KMS API.
  • Khi throughput S3 cao → có thể bị KMS throttle (API limit 5.000–30.000 req/sec tùy region).
  • Giải pháp: tăng KMS quota hoặc dùng S3 Bucket Key để giảm số KMS calls.

Keyword trong đề thi: audit, compliance, regulatory, CloudTrail + encryption → SSE-KMS.

SSE-C — Key do khách hàng tự cung cấp

  • Key gửi trong HTTP header mỗi request (AWS không lưu key).
  • Amazon S3 chỉ dùng key để encrypt/decrypt trong lúc xử lý request.
  • Bắt buộc HTTPS — key trong header, nếu HTTP thì key bị lộ.
  • Mỗi GET/PUT đều phải gửi key kèm theo.
  • Rất khó vận hành, gần như không dùng trong thực tế.

Header khi upload với SSE-C:

x-amz-server-side-encryption-customer-algorithm: AES256
x-amz-server-side-encryption-customer-key: <base64-encoded-key>
x-amz-server-side-encryption-customer-key-MD5: <MD5-of-key>

Khi nào chọn: Chính sách bảo mật không cho phép key nằm trong AWS dưới bất kỳ hình thức nào.

Client-Side Encryption — Client tự mã hóa

  • Client mã hóa dữ liệu trước khi upload lên S3.
  • S3 chỉ lưu ciphertext — AWS không thể đọc dữ liệu.
  • Khi download, client tự decrypt.
  • Toàn quyền quản lý key và vòng đời mã hóa.
  • Phức tạp hơn SSE — gánh nặng vận hành cho ứng dụng.

Keyword trong đề thi: “AWS must never have access to unencrypted data” → Client-Side Encryption.

Encryption in Transit (SSL/TLS)

  • S3 cung cấp cả endpoint HTTP và HTTPS.
  • HTTPS luôn được khuyến nghị — mã hóa dữ liệu khi truyền.
  • Bắt buộc khi dùng SSE-C.
  • In-transit và at-rest là hai cơ chế độc lập — dùng cả hai cùng lúc.

Ép buộc HTTPS bằng Bucket Policy

  • Deny mọi request nếu SecureTransport = false (tức là HTTP).
  • Áp dụng cho mọi client, kể cả cross-account.

Keyword: “Ensure all data is encrypted in transit” → Bucket Policy với aws:SecureTransport.

CORS — Cross-Origin Resource Sharing

Origin = scheme (protocol) + host (domain) + port. Ví dụ https://www.example.com (port ngầm định 443).

  • Same origin: http://example.com/app1 và http://example.com/app2.
  • Different origin: http://www.example.com và http://other.example.com.

CORS là cơ chế của trình duyệt (không phải server) cho phép trang web ở origin A gọi API/tài nguyên ở origin B — nhưng chỉ khi origin B trả về đúng CORS Header (Access-Control-Allow-Origin, Access-Control-Allow-Methods…).

Preflight request: trước khi gửi request thật, browser gửi OPTIONS để hỏi “tôi có được phép gọi không?”. Server trả lời qua CORS header, sau đó browser mới cho phép request thật đi qua.

Với S3: nếu 1 bucket host static website (vd my-bucket-html) cần gọi tài nguyên từ 1 bucket khác (vd my-bucket-assets), phải bật CORS configuration trên bucket đích, allow origin cụ thể hoặc * (mọi origin).

Keyword đề thi: “web app ở domain A gọi S3 ở domain khác bị lỗi trình duyệt chặn” → cấu hình CORS trên bucket S3, không phải bucket policy.

S3 MFA Delete

Bắt buộc user nhập mã MFA trước khi thực hiện thao tác nhạy cảm trên object version.

MFA bắt buộc khi:

  • Xóa vĩnh viễn 1 object version.
  • Suspend Versioning trên bucket.

MFA KHÔNG bắt buộc khi:

  • Enable Versioning.
  • List các version đã xóa.

Điều kiện: Versioning phải đang bật trên bucket. Chỉ root account (bucket owner) mới bật/tắt được MFA Delete.

Keyword đề thi: “ngăn xóa nhầm/xóa ác ý version của object” → MFA Delete (khác với Object Lock — MFA Delete chỉ cần mã MFA, Object Lock khóa hẳn theo retention period).

S3 Access Logs

Ghi lại mọi request (kể cả bị từ chối) vào bucket sang một logging bucket riêng, phục vụ audit.

  • Logging bucket phải cùng region với bucket được giám sát.
  • KHÔNG BAO GIỜ đặt logging bucket = chính bucket đang giám sát → tạo logging loop, bucket phình to vô hạn (mỗi log ghi vào bucket lại sinh ra 1 request mới cần log tiếp).

Keyword đề thi: “audit purpose”, “log every request to a bucket” → S3 Access Logs. Nếu đề hỏi ai chỉnh sửa/xóa bucket (API-level, cả ngoài S3) thì đó là CloudTrail, không phải Access Logs.

S3 Pre-Signed URLs

URL tạm thời cho phép người không có quyền IAM trực tiếp vẫn GET/PUT được 1 object cụ thể trong bucket private.

  • Tạo qua S3 Console, AWS CLI, hoặc SDK.
  • Thời hạn URL:
    • S3 Console: 1 phút – 720 phút (12 giờ).
    • AWS CLI: tham số --expires-in (giây), mặc định 3600s, tối đa 604800s (~168 giờ).
  • User dùng URL kế thừa đúng quyền của người đã tạo URL (owner) cho hành động GET/PUT đó.

Use case điển hình:

  • Chỉ cho user đã đăng nhập tải video premium.
  • Cấp quyền tải file cho danh sách user thay đổi liên tục (generate URL động).
  • Cho phép user upload tạm thời vào đúng 1 vị trí trong bucket.

Keyword đề thi: “cho phép truy cập tạm thời vào object private mà không cần đổi IAM permission” → Pre-Signed URL.

S3 Object Lock & Glacier Vault Lock

Cả hai đều theo mô hình WORM (Write Once Read Many) — object không thể bị ghi đè/xóa trong một khoảng thời gian.

S3 Object Lock (yêu cầu bật Versioning)

Retention modeAi bị chặn?
ComplianceKHÔNG ai xóa/đổi được — kể cả root user. Không thể rút ngắn hay đổi retention mode.
GovernanceHầu hết user bị chặn, nhưng vẫn có user được cấp quyền đặc biệt để xóa/đổi retention.
  • Retention Period: bảo vệ object trong khoảng thời gian cố định, có thể gia hạn thêm.
  • Legal Hold: bảo vệ vô thời hạn, độc lập với Retention Period — gắn/gỡ tự do bằng quyền IAM s3:PutObjectLegalHold.

S3 Glacier Vault Lock

  • Tạo Vault Lock Policy, sau đó khóa policy lại — từ đó không ai sửa/xóa được nữa (kể cả root).
  • Dùng cho compliance & data retention dài hạn trên Glacier.

Keyword đề thi: “không ai được xóa kể cả root/admin” → Compliance mode (Object Lock) hoặc Glacier Vault Lock. “Vẫn có một số người có quyền override” → Governance mode.

S3 Access Points

Đơn giản hóa việc quản lý quyền truy cập khi 1 bucket lớn được dùng bởi nhiều nhóm user khác nhau (ví dụ Finance, Sales, Analytics).

  • Mỗi Access Point có: DNS name riêng (Internet Origin hoặc VPC Origin) + Access Point Policy riêng (tương tự Bucket Policy nhưng áp dụng scope hẹp hơn, ví dụ chỉ 1 prefix).
  • Thay vì 1 Bucket Policy khổng lồ quản lý hết mọi nhóm user, tách thành nhiều Access Point — mỗi cái quản lý 1 phần quyền, dễ maintain hơn.
  • VPC Origin: giới hạn Access Point chỉ truy cập được từ trong VPC — bắt buộc phải tạo VPC Endpoint (Gateway hoặc Interface) trỏ tới Access Point, và VPC Endpoint Policy phải cho phép cả bucket lẫn access point đích.

Keyword đề thi: “bucket lớn, nhiều team, mỗi team chỉ được truy cập đúng prefix của mình, cần dễ quản lý ở quy mô lớn” → S3 Access Points.

S3 Object Lambda

Chèn 1 AWS Lambda function vào giữa để biến đổi object trước khi trả về cho ứng dụng gọi — mà KHÔNG cần tạo thêm bucket hay copy dữ liệu.

Kiến trúc: chỉ cần 1 S3 bucket gốc + 1 Supporting Access Point + nhiều S3 Object Lambda Access Point (mỗi cái gắn 1 Lambda function xử lý riêng).

Use case:

  • Redact thông tin PII (personally identifiable information) trước khi trả cho môi trường analytics/non-production.
  • Convert định dạng dữ liệu (XML → JSON).
  • Resize/watermark ảnh động theo từng caller.

Keyword đề thi: “biến đổi/xử lý object trước khi trả về client, không muốn tạo bản copy” → S3 Object Lambda (khác Lambda@Edge/CloudFront Functions — cái đó xử lý ở edge cho CDN, còn Object Lambda gắn thẳng vào S3 Access Point).

Điểm hay ra thi

  • SSE-S3 là mặc định — kể cả không cấu hình gì.
  • SSE-KMS khi cần CloudTrail audit + key control.
  • SSE-C bắt buộc HTTPS — key gửi trong HTTP header mỗi request.
  • Client-Side khi “AWS must never access plaintext”.
  • aws:SecureTransport = false → Deny HTTP → ép HTTPS.
  • KMS Throttling có thể xảy ra khi S3 throughput cao — dùng S3 Bucket Key để giảm.
  • CORS: preflight request/response, header Access-Control-Allow-Origin — rất hay ra thi.
  • MFA Delete ≠ Object Lock: MFA Delete chỉ yêu cầu mã MFA khi xoá version/suspend versioning; Object Lock khoá theo retention period, kể cả root cũng không xoá được ở Compliance mode.
  • Access Logs: không đặt logging bucket = bucket đang giám sát (logging loop).
  • Pre-Signed URL: quyền = quyền của người tạo URL, không phải quyền của người dùng URL.
  • Access Points: chia nhỏ Bucket Policy khổng lồ theo từng nhóm user/prefix; VPC Origin cần VPC Endpoint.
  • Object Lambda: biến đổi object on-the-fly (redact/convert/resize), tái dùng 1 bucket duy nhất.

Takeaway cá nhân

  • SSE-KMS = compliance & audit — chọn khi đề nhắc đến CloudTrail hay regulatory.
  • Decision: audit → KMS; key ngoài AWS → Client-Side; đơn giản → SSE-S3.
  • Đừng quên: in-transit (HTTPS) và at-rest (SSE) là hai lớp độc lập, nên bật cả hai.
  • Nhóm tính năng “bảo mật khác” (CORS, MFA Delete, Access Logs, Pre-Signed URL, Object Lock, Access Points, Object Lambda) dễ bị nhầm lẫn với nhau vì đều có chữ “security/access” — phân biệt bằng câu hỏi: kiểm soát origin trình duyệt (CORS) vs audit ai xoá (MFA Delete/Access Logs) vs cấp quyền tạm (Pre-Signed URL) vs khoá không cho xoá (Object Lock/Vault Lock) vs chia nhỏ quyền theo team (Access Points) vs biến đổi dữ liệu khi trả về (Object Lambda).
