18 – Containers on AWS: ECS, Fargate, ECR & EKS

Cách đọc note này: (1) Vì sao container/Docker → (2) Bản đồ dịch vụ container trên AWS → (3) Khái niệm nền tảng ECS (Cluster/Service/Task/Task Definition) → (4) 2 launch type (EC2 vs Fargate) → (5) IAM roles (điểm hay nhầm nhất) → (6) Load Balancer & Data Volumes → (7) Auto Scaling → (8) Event-driven pattern → (9) ECR → (10) EKS → (11) So sánh & chọn đáp án thi.

1. Vì sao cần container? (Docker cơ bản)

1.1 Docker là gì?

  • Nền tảng đóng gói + chạy ứng dụng dưới dạng container
  • Container gồm app + toàn bộ dependency → chạy giống hệt nhau trên mọi máy, mọi OS
  • Lợi ích: hết lo compatibility, hành vi predictable, dễ maintain & deploy, chạy được bất kỳ ngôn ngữ / OS / công nghệ nào
  • Use case: kiến trúc microservices, lift-and-shift app on-premises lên AWS

1.2 Docker vs Virtual Machine

Docker (container)Virtual Machine
Ảo hoá”Giống” ảo hoá nhưng không hẳn — share OS kernel với hostẢo hoá phần cứng đầy đủ, mỗi VM có OS riêng
Tài nguyênNhiều container share tài nguyên trên 1 serverMỗi VM có tài nguyên riêng → overhead cao hơn
Khởi độngVài giâyVài phút
Mật độChạy được nhiều container / serverÍt VM / server hơn

1.3 Docker image lưu ở đâu?

RegistryLoạiGhi chú
Docker HubPublicBase image cho nhiều công nghệ/OS (Ubuntu, MySQL…)
Amazon ECRPrivate (+ Public Gallery tại gallery.ecr.aws)Tích hợp IAM, dùng cho workload trên AWS

Push/pull image từ ECR cần auth trước qua aws ecr get-login-password.

3. Khái niệm nền tảng ECS — 4 thứ dễ nhầm

Trước khi vào launch type, cần phân biệt rõ 4 khái niệm:

Khái niệmLà gì
Task DefinitionBlueprint dạng JSON: image nào, bao nhiêu CPU/RAM, port, IAM role, volume…
TaskMột lần chạy thực tế của Task Definition (giống 1 container instance đang sống)
ServiceGiữ đúng số Task mong muốn luôn chạy, tự thay Task chết, gắn Load Balancer
ClusterNhóm logic chứa Service/Task (và EC2 instance, nếu dùng EC2 launch type)
graph LR

    TaskDef -.-> Task2["Task 2"]
    Cluster["ECS Cluster"] --> Service["ECS Service<br/>(giữ N task chạy)"]
    Service --> Task1
    Service --> Task2

Nhớ: sửa Task Definition không đổi Task đang chạy — phải tạo revision mới rồi Service tự rolling-update sang Task mới.

4. Amazon ECS — 2 Launch Type

4.1 EC2 Launch Type — tự quản lý hạ tầng

  • Bạn phải provision & maintain EC2 instance
  • Mỗi EC2 instance phải chạy ECS Agent để đăng ký vào Cluster
  • AWS chỉ lo phần start/stop container trên các instance đó

4.2 Fargate Launch Type — serverless

  • Không quản lý EC2 — hoàn toàn serverless
  • Chỉ cần tạo Task Definition, AWS tự chạy Task theo đúng CPU/RAM khai báo
  • Scale = tăng số lượng Task — không cần lo thêm EC2 instance

4.3 So sánh nhanh

Tiêu chíEC2 Launch TypeFargate
Quản lý hạ tầngBạn tự làm (patch OS, scale ASG)AWS lo hết
BillingTrả tiền EC2 (kể cả lúc rảnh)Trả theo vCPU/RAM × thời gian Task chạy
Kiểm soátCao (SSH vào instance, chọn instance type/GPU)Thấp — không SSH, không chọn instance type
ScalePhải tự thêm EC2 (ASG / Capacity Provider)Chỉ cần tăng số Task
Networking modebridge / host / awsvpcBắt buộc awsvpc — mỗi Task có ENI + IP riêng
Dùng khiCần tối ưu chi phí ở scale lớn, cần GPU/instance đặc thùMuốn đơn giản, ít vận hành, workload không liên tục

Fargate Spot: chạy Task trên capacity dư thừa, rẻ hơn đáng kể (giống Spot Instance) nhưng có thể bị interrupt — chỉ dùng cho workload chịu được gián đoạn.

5. IAM Roles cho ECS — điểm hay gây nhầm lẫn nhất

RoleDùng choAi dùng
EC2 Instance Profile (chỉ EC2 Launch Type)Gắn vào EC2 instance chạy ECS AgentECS Agent — gọi API ECS để đăng ký cluster
Task Execution RoleViệc “hạ tầng” của Task: pull image từ ECR, gửi log CloudWatch, đọc secret từ Secrets Manager/SSM Parameter StoreECS/Fargate thực hiện thay mặt Task — dùng cho cả 2 launch type
Task RoleViệc code bên trong container cần làm: gọi S3, DynamoDB…Application code chạy trong container

Bẫy hay thi: Task báo lỗi AccessDenied khi code gọi S3 → sửa Task Role. Task không pull được image ECR hoặc không đọc được secret → sửa Task Execution Role. Nhầm 2 role này là lỗi rất phổ biến trong đề thi lẫn thực tế.

6. Load Balancer cho ECS

Loại LBHỗ trợ Fargate?Khi nào dùng
Application Load Balancer✔Mặc định, phù hợp hầu hết use case (HTTP/HTTPS, path-based routing)
Network Load Balancer✔Throughput/performance cao, hoặc cần đi kèm PrivateLink
Classic Load Balancer❌Không khuyến nghị — thiếu tính năng nâng cao, không hỗ trợ Fargate

7. Data Volumes cho ECS

  • Mount EFS vào ECS Task — hoạt động với cả EC2 và Fargate launch type
  • Task chạy ở AZ khác nhau vẫn share chung data trên EFS (multi-AZ)
  • Fargate + EFS = hoàn toàn serverless, không phải tự quản lý storage layer
  • Use case: shared storage bền vững giữa nhiều container
  • S3 không mount được như file system — muốn dùng S3 phải gọi qua SDK/API, không phải volume

Ephemeral storage (Fargate): mỗi Task có sẵn 20 GiB storage tạm miễn phí, có thể tăng tới 200 GiB (tính phí thêm) — dùng cho dữ liệu tạm trong lúc container chạy, mất khi Task dừng.

8. ECS Service Auto Scaling

Tự động tăng/giảm số Task mong muốn, dùng nền tảng AWS Application Auto Scaling.

Metric để scaleÝ nghĩa
ECS Service Average CPU UtilizationScale theo CPU
ECS Service Average Memory UtilizationScale theo RAM
ALB Request Count Per TargetScale theo lượng request ALB đẩy vào
PolicyCách hoạt động
Target TrackingGiữ 1 metric CloudWatch quanh giá trị mục tiêu (giống target tracking của ASG)
Step ScalingScale theo bậc, dựa trên CloudWatch Alarm
Scheduled ScalingScale theo thời điểm định trước — hợp với traffic dự đoán được

ECS Service Auto Scaling (task-level) ≠ EC2 Auto Scaling (instance-level) — 2 tầng scale khác nhau, dễ bị đánh lừa trong đề thi.

Fargate Auto Scaling setup đơn giản hơn nhiều vì serverless — không phải lo thêm EC2 instance.

8.1 EC2 Launch Type — Auto Scaling cả EC2 instance

Với EC2 Launch Type, scale Task thôi chưa đủ — phải đảm bảo đủ EC2 instance làm “chỗ chứa”:

CáchÝ nghĩa
Auto Scaling Group ScalingASG tự thêm EC2 theo CPU Utilization trung bình của ASG
ECS Cluster Capacity ProviderTự động provision/scale hạ tầng theo nhu cầu thật của Task (đi kèm 1 ASG); thêm EC2 khi thiếu capacity (CPU/RAM)

Capacity Provider “thông minh” hơn ASG scaling thường vì nhìn thẳng vào nhu cầu của Task (thay vì chỉ CPU trung bình instance) để quyết định scale. Fargate cũng có capacity provider mặc định (FARGATE, FARGATE_SPOT) nhưng thường dùng ngầm, không cần tự cấu hình ASG.

9. ECS Event-driven — kết hợp EventBridge & SQS

ECS Task không nhất thiết phải chạy 24/7 — có thể trigger theo sự kiện:

PatternDùng khi
EventBridge → chạy ECS TaskMột sự kiện AWS xảy ra (vd object mới lên S3) cần xử lý bằng container
EventBridge Schedule → chạy ECS TaskCron job định kỳ, không muốn giữ Task chạy sẵn
SQS → ECS Task poll queueWorker xử lý job trong hàng đợi (giống pattern Lambda nhưng chạy container)
EventBridge bắt sự kiện Task dừngGiám sát/alert khi Task chuyển trạng thái STOPPED (vd để biết lý do crash)

10. Amazon ECR — registry lưu Docker image

  • ECR = Elastic Container Registry
  • Repository Private (mặc định) hoặc Public (ECR Public Gallery)
  • Backed bởi Amazon S3 — tích hợp sẵn với ECS/EKS/Fargate
  • Access control qua IAM — lỗi permission khi pull/push → kiểm tra IAM policy trước
  • Tính năng: vulnerability scanning (Basic scan miễn phí dùng Clair; Enhanced scan trả phí dùng Amazon Inspector, quét liên tục), versioning (image tag), lifecycle policy (tự xoá image cũ để tiết kiệm chi phí lưu trữ)

11. Amazon EKS — managed Kubernetes

11.1 Tổng quan

  • EKS = cách chạy Kubernetes cluster được AWS quản lý
  • Kubernetes: hệ thống mã nguồn mở tự động deploy/scale/quản lý ứng dụng container hoá (thường là Docker)
  • Cùng mục tiêu với ECS nhưng khác API — Kubernetes cloud-agnostic (chạy được trên Azure, GCP, on-premises…)
  • Worker node chạy trên EC2 hoặc Fargate (serverless)
  • Use case chính: công ty đã dùng Kubernetes on-premises/cloud khác, muốn migrate sang AWS mà giữ nguyên tooling/API Kubernetes
  • Multi-region → deploy 1 EKS cluster / region (EKS không tự multi-region)
  • Logs & metrics → CloudWatch Container Insights

Chi phí: EKS control plane tính phí cố định (~$0.10/giờ/cluster), cộng thêm chi phí worker node (EC2 hoặc Fargate) — khác ECS (control plane miễn phí, chỉ trả tiền compute).

11.2 Node Types

Loại NodeAi quản lý EC2Ghi chú
Managed Node GroupsAWS tạo & quản lý (nằm trong ASG do EKS quản lý)Hỗ trợ On-Demand hoặc Spot
Self-Managed NodesBạn tự tạo, tự đăng ký vào cluster, tự quản lý qua ASGCó thể dùng Amazon EKS Optimized AMI dựng sẵn; hỗ trợ On-Demand/Spot
AWS FargateKhông quản lý node nào cảServerless hoàn toàn, không cần maintain

11.3 Data Volumes cho EKS

  • Cần khai báo StorageClass manifest trong cluster
  • Dùng driver tuân theo chuẩn Container Storage Interface (CSI)
  • Hỗ trợ: Amazon EBS, Amazon EFS (dùng được cả với Fargate), Amazon FSx for Lustre, Amazon FSx for NetApp ONTAP

Điểm hay ra thi

  • Docker share OS kernel với host, không phải VM đầy đủ; image lưu ở Docker Hub (public) hoặc ECR (private).
  • ECS: phân biệt Task Definition (blueprint) – Task (instance đang chạy) – Service (giữ N task + gắn LB) – Cluster (nhóm logic).
  • 2 launch type: EC2 (tự quản lý, trả tiền theo instance) vs Fargate (serverless, trả theo vCPU/RAM × thời gian).
  • 3 loại IAM role dễ nhầm: EC2 Instance Profile (ECS Agent, chỉ EC2) / Task Execution Role (pull image, log, secret — cả 2 launch type) / Task Role (code trong container gọi AWS API).
  • Load Balancer: ALB & NLB hỗ trợ Fargate; Classic LB không hỗ trợ Fargate.
  • EFS mount được vào ECS Task (multi-AZ share); S3 không mount được như file system.
  • Fargate ephemeral storage: mặc định 20 GiB, tăng được tới 200 GiB.
  • Auto Scaling ECS: scale theo CPU/RAM/ALB Request Count; Target Tracking / Step / Scheduled; task-level ≠ instance-level (ASG/Capacity Provider lo phần EC2).
  • ECS có thể trigger bởi EventBridge (event hoặc schedule) và SQS — không cần chạy 24/7.
  • ECR: private + public gallery, backed bởi S3, IAM kiểm soát access, có vulnerability scanning (Basic/Enhanced) + lifecycle policy.
  • EKS = Kubernetes managed, cloud-agnostic, API khác ECS; node có thể EC2 (managed/self-managed) hoặc Fargate; multi-region = nhiều cluster; data volume qua CSI driver (EBS/EFS/FSx).

Takeaway cá nhân

  • Container ≠ VM: nhẹ hơn, nhanh hơn vì share kernel — nhưng cô lập kém hơn VM.
  • ECS là lựa chọn “mặc định” khi làm việc thuần AWS; chỉ nhảy sang EKS khi có lý do rõ ràng (đã dùng K8s sẵn, cần portable đa cloud).
  • Nhầm lẫn dễ gặp nhất trong domain này: Task Role vs Task Execution Role — luôn tự hỏi “đây là code trong container cần quyền, hay ECS cần quyền để chạy được Task?” trước khi chọn role.
  • Fargate là câu trả lời an toàn cho câu hỏi “làm sao serverless hoá container” — nhớ luôn đi kèm networking mode awsvpc.
