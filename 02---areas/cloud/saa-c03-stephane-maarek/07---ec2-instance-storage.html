7. EC2 Instance Storage

Cách đọc note này: Trục chính của cả bài là “bound to AZ” hay không, và ai chịu trách nhiệm backup”. EBS/Instance Store/EFS/AMI đều xoay quanh 2 câu hỏi đó. Đọc 2 bảng so sánh cuối bài (6 loại EBS, EBS vs EFS) là đủ để trả lời phần lớn câu hỏi thi. Xem thêm lựa chọn storage tổng quát ở 3.1 - Storage Solutions - S3, EBS, EFS, FSx.

EBS Volume — Elastic Block Store

EBS là gì?

EBS (Elastic Block Store) là network drive (ổ đĩa mạng) có thể gắn vào EC2 instance khi chạy. Hãy tưởng tượng như một “USB stick qua mạng”.

Đặc điểm cốt lõi:

Đặc điểmMô tả
Network driveGiao tiếp qua network → có thể có latency nhỏ
PersistenceDữ liệu vẫn còn sau khi instance terminate
Bound to AZEBS ở us-east-1a không gắn được cho instance ở us-east-1b
Di chuyển AZPhải snapshot trước, rồi restore ở AZ mới
1 instanceThông thường chỉ 1 instance (trừ io1/io2 Multi-Attach)
ProvisionedPhải chọn dung lượng (GB) và IOPS trước → trả tiền theo provisioned

Volume ở us-east-1a chỉ gắn được cho instance trong us-east-1a — volume “10 GB unattached” ở us-east-1b không thể gắn ngược lại instance ở AZ khác. Muốn di chuyển → phải snapshot rồi restore.

Delete on Termination

Khi terminate EC2 instance:

  • Root EBS volume → mặc định bị xóa (attribute DeleteOnTermination: true).
  • Các EBS volume khác gắn thêm → mặc định KHÔNG bị xóa.

Có thể thay đổi hành vi qua Console hoặc CLI — ví dụ giữ root volume để backup.

EBS Snapshots

Snapshot = bản sao lưu của EBS volume tại một thời điểm.

AMI — Amazon Machine Image

AMI là gì?

AMI là template để launch EC2 instance — bao gồm OS, cấu hình, phần mềm, monitoring agent đã được đóng gói sẵn.

3 nguồn AMI:

LoạiNguồnGhi chú
Public AMIAWS cung cấpAmazon Linux 2, Ubuntu, Windows Server…
Custom AMIBạn tự tạoCấu hình sẵn, boot nhanh hơn
Marketplace AMIBên thứ 3 (có thể trả phí)Các phần mềm thương mại (Nginx Plus, Oracle…)

Tại sao dùng Custom AMI?

  • Boot nhanh hơn vì phần mềm đã pre-packaged.
  • Không cần chạy User Data script dài mỗi lần launch.
  • Đảm bảo configuration nhất quán giữa các instances.

Quy trình tạo Custom AMI

flowchart LR
    Launch["Launch EC2\n(từ Public AMI)"]
    Custom["Customize\n(cài phần mềm, config)"]
    Stop["Stop instance\n(đảm bảo data integrity)"]
    Build["Build AMI\n(tạo EBS snapshots)"]
    Deploy["Launch EC2 mới\ntừ Custom AMI"]

    Launch --> Custom --> Stop --> Build --> Deploy

AMI được build cho một region cụ thể nhưng có thể copy sang region khác.

EC2 Instance Store — Ephemeral Storage

Instance Store là gì?

EC2 Instance Store là ổ cứng vật lý gắn trực tiếp vào server chạy EC2 — không phải network drive như EBS.

EBS VolumeEC2 Instance Store
LoạiNetwork drivePhysical hardware disk
I/O PerformanceTốt (giới hạn bởi network)Cực cao (local NVME/SSD)
Persistence✔ Persistent❌ Ephemeral — mất khi stop/terminate
Dùng choDatabase, OS volume, long-termBuffer, cache, scratch, tmp
BackupSnapshotBạn tự lo

Quan trọng: Instance Store mất toàn bộ dữ liệu khi:

  • EC2 bị stop hoặc terminate.
  • Hardware bị fail.

Chỉ dùng Instance Store cho dữ liệu không cần lưu lâu dài — cache, temp files, scratch data.

EBS Volume Types — 6 loại

Nhóm SSD (Solid State Drive) — Tối ưu IOPS

gp3 — General Purpose SSD (Mặc định hiện tại)

  • IOPS và Throughput cấu hình độc lập với dung lượng.
  • Baseline: 3.000 IOPS + 125 MB/s throughput.
  • Max: 16.000 IOPS + 1.000 MB/s throughput.
  • Rẻ hơn gp2 và linh hoạt hơn.

Dùng cho: Hầu hết workload — web server, app server, container nodes, database nhỏ/vừa.

gp2 — General Purpose SSD (Legacy)

  • IOPS tăng theo dung lượng: 3 IOPS/GB (100 GB → 300 IOPS).
  • Max: 16.000 IOPS (đạt được ở 5.334 GB).
  • AWS khuyến cáo chuyển sang gp3.

Dùng cho: Legacy system, snapshot restore từ hệ thống cũ.

io1 / io2 — Provisioned IOPS SSD

  • Cấu hình IOPS chính xác: 100 – 64.000 IOPS.
  • io2 bền hơn io1 (99.999% durability vs 99.9%).
  • io2 Block Express: tối đa 256.000 IOPS + 4.000 MB/s throughput.
  • Giá cao.

Dùng cho:

  • Database lớn cần IOPS cao và ổn định (MySQL, PostgreSQL, Oracle, MongoDB).
  • High-transaction OLTP.
  • SAP HANA, enterprise DB.

io2 vs io1: Cùng giá, io2 durable hơn → luôn chọn io2.

Nhóm HDD (Hard Disk Drive) — Tối ưu Throughput

st1 — Throughput Optimized HDD

  • Tối ưu throughput (MB/s), không phải IOPS.
  • Max: 500 MB/s throughput.
  • Rẻ hơn SSD.
  • ❌ Không dùng được làm boot volume.

Dùng cho: Big Data (Hadoop, Spark), streaming data, log processing, ETL.

sc1 — Cold HDD (Rẻ nhất)

  • Throughput thấp nhất trong tất cả volume types.
  • Dành cho dữ liệu ít truy cập.
  • ❌ Không dùng được làm boot volume.

Dùng cho: Archive data, cold storage, ít truy cập.

EBS Multi-Attach — io1/io2

  • Gắn cùng 1 EBS volume vào nhiều EC2 trong cùng AZ.
  • Tối đa 16 EC2 instances đồng thời.
  • Mỗi instance có full read/write.
  • Phải dùng cluster-aware filesystem (không phải XFS, EXT4…).

Dùng cho: Clustered Linux apps cần highly available shared storage (Teradata).

EBS Encryption

Khi tạo EBS volume đã encrypted:

  • Data at rest: encrypted.
  • Data in-flight (instance ↔ volume): encrypted.
  • Mọi snapshot: encrypted.
  • Volume tạo từ snapshot: encrypted.
  • Encryption/Decryption xử lý transparent — không cần làm gì thêm.
  • Sử dụng AWS KMS (AES-256).
  • Gần như không ảnh hưởng latency.

Quy trình mã hóa một EBS volume chưa encrypt

flowchart LR
    Unencrypted["EBS Volume\n(Unencrypted)"] -->|"1. Tạo snapshot"| Snap1["Snapshot\n(Unencrypted)"]
    Snap1 -->|"2. Copy với\nencryption enabled"| Snap2["Snapshot\n(Encrypted)"]
    Snap2 -->|"3. Tạo EBS volume\nfrom encrypted snapshot"| EncVol["EBS Volume\n(Encrypted)"]
    EncVol -->|"4. Gắn vào instance"| EC2["EC2 Instance"]

❌ Không thể bật encryption trực tiếp trên volume đang chạy.

Amazon EFS — Elastic File System

EFS là gì?

EFS (Elastic File System) là managed NFS (Network File System) có thể mount lên nhiều EC2 cùng lúc qua nhiều AZ.

graph LR
    EFS["Amazon EFS\n(Managed NFS)"]
    EC2_A["EC2 (AZ1)"]
    EC2_B["EC2 (AZ2)"]
    EC2_C["EC2 (AZ3)"]
    EFS --- EC2_A
    EFS --- EC2_B
    EFS --- EC2_C

Đặc điểm:

  • Highly available, scalable, đắt hơn EBS ~3x gp2.
  • Pay per use — không cần provision dung lượng trước.
  • Multi-AZ mặc định (Standard tier).
  • Tương thích Linux only (NFSv4.1 protocol, POSIX-compliant).
  • Mã hóa at rest với KMS.
  • Dung lượng tự động scale — không giới hạn.

Performance Modes

ModeMô tảDùng cho
General Purpose (mặc định)Latency thấpWeb server, CMS
Max I/OLatency cao hơn, throughput và parallelism cao hơnBig data, media processing

Throughput Modes

ModeMô tả
BurstingThroughput scale theo dung lượng (1 TB = 50 MiB/s + burst 100 MiB/s)
ProvisionedĐặt throughput cố định bất kể dung lượng
ElasticTự scale theo workload, tối đa 3 GiB/s read, 1 GiB/s write

Storage Tiers (Lifecycle Management)

TierMô tả
StandardFile truy cập thường xuyên
Infrequent Access (EFS-IA)File ít truy cập, rẻ hơn để lưu, tốn phí khi đọc
ArchiveFile hiếm khi truy cập (vài lần/năm), rẻ nhất

Có thể cài Lifecycle Policy để tự động move file giữa tiers.

Availability Options

OptionMô tảDùng cho
Standard (Multi-AZ)Replicate qua nhiều AZProduction
One ZoneChỉ 1 AZ, rẻ hơn, compatible với IADev, backup

Mỗi AZ có một “EFS Mount Target” riêng — instance Linux ở AZ nào cũng mount vào cùng 1 EFS file system, đây là điểm khác biệt cốt lõi so với EBS (chỉ 1 AZ, trừ Multi-Attach).

Bảng từ khoá đề thi

Từ khoá trong đềChọn
”DB cần IOPS cao và ổn định, mission-critical”io2 (Block Express) — luôn ưu tiên io2 hơn io1 (cùng giá, durable hơn)
“Đa số workload, web/app server, chi phí hợp lý”gp3
”Big Data streaming/log processing, không cần boot”st1
”Archive, ít truy cập nhất, rẻ nhất”sc1
”Clustered Linux app, nhiều EC2 cùng ghi 1 volume”EBS Multi-Attach (io1/io2), tối đa 16 instance, cần cluster-aware filesystem
”Cache/buffer/scratch, không cần persist”EC2 Instance Store (ephemeral)
“Nhiều EC2 (Linux) cùng mount 1 file system, multi-AZ”EFS, không dùng EBS (trừ Multi-Attach vẫn giới hạn 1 AZ)
“Mã hoá volume đang chạy mà không tạo instance mới”Không thể trực tiếp → snapshot → copy encrypted → tạo volume mới
”Boot volume nhưng cần rẻ, throughput cao”❌ Không dùng st1/sc1 — chỉ gp2/gp3/io1/io2 mới boot được

Điểm hay ra thi

  • EBS là network drive — giao tiếp qua network, có latency.
  • EBS bound to AZ — move sang AZ khác phải snapshot rồi restore.
  • gp3 tốt hơn gp2 — IOPS/throughput độc lập, rẻ hơn.
  • io2 vs io1: cùng giá, io2 durable hơn → luôn chọn io2.
  • st1/sc1 là HDD → không dùng làm boot volume.
  • EBS Multi-Attach (io1/io2): tối đa 16 instances, cần cluster-aware filesystem.
  • Không thể bật encryption trực tiếp → phải: snapshot → copy với encryption → restore.
  • Instance Store = ephemeral (mất khi stop/terminate) → chỉ cho cache/tmp.
  • EFS = managed NFS, Linux only, mount nhiều EC2, auto scale dung lượng.
  • EFS đắt hơn EBS ~3x, nhưng có thể share qua nhiều AZ.
  • AMI được build cho 1 region nhưng có thể copy sang region khác.

Takeaway cá nhân

  • Storage hierarchy: Instance Store (fastest, ephemeral) → EBS (persistent, 1 instance) → EFS (shared, multi-AZ, Linux only).
  • gp3 là default tốt nhất cho đa số workload hiện nay.
  • EFS giải quyết bài toán “shared file system cho nhiều EC2” — EBS không làm được nếu không dùng Multi-Attach.
  • Mã hóa EBS: snapshot → copy encrypted → restore.
  • Liên kết: RDS dùng EBS (gp2/gp3/io1/io2) làm storage backend.
