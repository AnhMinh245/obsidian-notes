Domain 3: Design High-Performing Architectures (24%)

Domain 3 của kỳ thi AWS Certified Solutions Architect - Associate (SAA-C03) chiếm tỷ trọng 24% số điểm của bài thi. Trọng tâm của domain này là khả năng thiết kế các hệ thống kiến trúc không chỉ hoạt động được mà còn phải hoạt động với hiệu suất cao (high performance), có khả năng mở rộng linh hoạt (scalable/elastic), và đáp ứng được các yêu cầu về tốc độ truy xuất, băng thông, xử lý dữ liệu phức tạp của doanh nghiệp.

Important

Khác với Domain 1 tập trung vào tính an toàn (Security) hay Domain 2 tập trung vào tính bền bỉ (Resilience), Domain 3 chú trọng vào việc lựa chọn các công cụ/service sao cho nhanh nhất, mạnh mẽ nhất, mở rộng tốt nhất và đáp ứng đúng use case nhất. Hãy luôn tự hỏi: “Dịch vụ nào cung cấp throughput cao nhất ở đây?”, “Cấu hình nào giảm latency tốt nhất?“.

2. Phân Tích Cực Kỳ Chi Tiết 5 Task Statements

Task 3.1: Determine high-performing and/or scalable storage solutions

Yêu cầu bạn có khả năng đánh giá và lựa chọn giải pháp lưu trữ có hiệu năng cao và dễ dàng mở rộng.

  • Kiến thức cần nắm: Hybrid storage, storage services (S3, EFS, EBS), các loại storage (object, file, block).
  • Phân tích sâu: Storage performance trên AWS không chỉ là dung lượng. Nó liên quan đến IOPS (Input/Output Operations Per Second), Throughput (MB/s), và Latency (độ trễ). Bạn phải biết chính xác khi nào dùng Block Storage (EBS) cho database cần random R/W nhanh, khi nào dùng File Storage (EFS/FSx) cho multi-attach shared system, và khi nào dùng Object Storage (S3) cho massive scale data lake.

Mẹo thi

Khi đề bài nhắc đến hàng triệu IOPS (millions of IOPS) với độ trễ siêu thấp (sub-millisecond), hãy nghĩ ngay đến EC2 Instance Store. Tuy nhiên, nếu yêu cầu dữ liệu phải được lưu trữ lâu dài (persistent), thì EBS io2 Block Express hoặc EBS Multi-Attach có thể là câu trả lời.
Nếu đề bài yêu cầu “POSIX-compliant file system”, câu trả lời chắc chắn là EFS hoặc FSx.

Cảnh báo Storage Limits

S3 có limit 3,500 PUT/COPY/POST/DELETE và 5,500 GET/HEAD requests per second per prefix. Nếu ứng dụng của bạn vượt quá số này, bạn PHẢI tạo multiple prefixes (ví dụ: s3://bucket/2023-01/ và s3://bucket/2023-02/) để scale performance.

Task 3.2: Design high-performing and elastic compute solutions

Năng lực thiết kế giải pháp điện toán linh hoạt và đáp ứng hiệu suất lớn.

  • Kiến thức cần nắm: Compute services (AWS Batch, Amazon EMR, AWS Fargate), distributed computing, queuing/messaging (SQS, SNS để decouple), scalability (EC2 Auto Scaling), serverless (AWS Lambda), containers (ECS, EKS).
  • Phân tích sâu: Sự đàn hồi (Elasticity) là cốt lõi. Một hệ thống High-Performing phải biết tự động scale out khi tải tăng và scale in khi tải giảm để tiết kiệm chi phí. Phải nắm vững các khái niệm decoupled architecture bằng SQS (buffering requests) để tránh quá tải backend.

Ví dụ thực tế Decoupling

Một hệ thống web bị quá tải do quá trình xử lý ảnh nặng (image processing) ngay trên web server. Kiến trúc High-Performing sẽ tách phần xử lý ảnh ra: Web server chỉ nhận ảnh và đẩy message vào SQS, một nhóm worker instances (dưới sự quản lý của Auto Scaling Group) sẽ pull message từ SQS để xử lý. Điều này giúp web server đáp ứng cực nhanh và hệ thống xử lý ảnh có thể mở rộng độc lập.

Task 3.3: Determine high-performing database solutions

Lựa chọn các loại cơ sở dữ liệu phù hợp với patterns truy xuất dữ liệu.

  • Kiến thức cần nắm: Global infrastructure, caching (ElastiCache), data access patterns, capacity planning, kết nối DB (RDS Proxy), database engines, read replicas, các loại DB (relational, non-relational, in-memory).
  • Phân tích sâu: Không có một Database nào phù hợp cho mọi bài toán. RDBMS (RDS/Aurora) tốt cho ACID, JOINs. NoSQL (DynamoDB) tốt cho scale vô hạn, key-value lookup cực nhanh với độ trễ millisecond. Caching (Redis/Memcached/DAX) là lớp bọc phía ngoài để giảm tải read và tăng tốc truy xuất xuống microsecond.

Mẹo thi Database

Nếu đề bài nói về việc “offload read traffic” (giảm tải đọc) cho cơ sở dữ liệu SQL, hãy chọn Read Replicas. Nhưng nếu họ nói về giảm tải cho các “frequently accessed queries” (truy vấn lặp đi lặp lại nhiều lần với dữ liệu ít thay đổi), hãy chọn ElastiCache.
Nhớ rằng DynamoDB có DAX, giúp caching read queries tự động không cần sửa code app nhiều.

Task 3.4: Determine high-performing and/or scalable network architectures

Xây dựng một nền tảng mạng tốc độ cao và linh hoạt.

  • Kiến thức cần nắm: Edge services (CloudFront, Global Accelerator), cấu trúc VPC, load balancing, các lựa chọn kết nối (Site-to-Site VPN, Direct Connect, VPC endpoints/PrivateLink).
  • Phân tích sâu: Mạng mẽo là đường cao tốc của dữ liệu. Nếu bạn có compute/storage siêu mạnh nhưng network bị nghẽn (bottleneck) tại NAT Gateway hoặc đi vòng qua public internet với độ trễ cao, performance tổng thể sẽ tồi tệ. Phải biết cách dùng VPC Endpoints để đưa traffic qua mạng backbone nội bộ AWS, dùng CloudFront/Global Accelerator để đưa điểm kết nối ra sát người dùng cuối.

Cảnh báo Hybrid Network

AWS Direct Connect mất rất nhiều thời gian để thiết lập (từ vài tuần đến vài tháng) vì yêu cầu kéo cáp quang vật lý tới Data Center. Nếu đề bài yêu cầu “high bandwidth network connection immediately” (kết nối mạng băng thông cao ngay lập tức), bạn phải thiết lập Site-to-Site VPN trên nền internet trong lúc chờ thiết lập Direct Connect.

Task 3.5: Determine high-performing data ingestion and transformation solutions

Xử lý dữ liệu lớn, ingest và transform dữ liệu với hiệu năng cao.

  • Kiến thức cần nắm: Analytics (Athena, QuickSight), Data ingestion patterns, Data transfer (DataSync, Storage Gateway), Transformation (AWS Glue), Streaming (Amazon Kinesis).
  • Phân tích sâu: Thế giới Data Analytics và Big Data. Bạn phải biết ingest luồng dữ liệu khổng lồ (Kinesis) mà không làm rớt gói tin nào, biết cách ETL (Glue/EMR) để chuyển format dữ liệu thành columnar format (Parquet/ORC) để tăng tốc query trên Athena.

Thông tin Streaming

Streaming data (dữ liệu luồng) như IoT sensors, log phân tích web thường yêu cầu Kinesis Data Streams để xử lý theo thời gian thực (real-time) với độ trễ < 200ms. Nếu chỉ cần đưa dữ liệu từ nguồn vào S3, Redshift hoặc OpenSearch với near real-time (thời gian trễ cỡ 60 giây), Kinesis Data Firehose là lựa chọn tiết kiệm, tự động scale và không cần quản lý shard.

Common Bottlenecks & Troubleshooting

  1. API Rate Limits (Throttling): Mọi dịch vụ AWS đều có API limit (ví dụ: DynamoDB WCU/RCU vượt quá sẽ ném ProvisionedThroughputExceededException).
    • Cách khắc phục: Áp dụng Exponential Backoff và Jitter trong code client (AWS SDK đã tích hợp sẵn). Nếu là DynamoDB, cân nhắc On-Demand hoặc thêm DAX.
  2. Network Bandwidth (EC2/NAT): EC2 instance sizes quyết định Network Bandwidth (ví dụ: t3.micro chỉ có “Up to 5 Gigabit”, trong khi c6gn.16xlarge có 100 Gbps). NAT Gateway hỗ trợ tối đa 100 Gbps.
    • Cách khắc phục: Chọn instance lớn hơn, hoặc dùng EFA (Elastic Fabric Adapter) cho HPC workload. Nếu nghẽn ở NAT, cân nhắc đổi kiến trúc sang VPC Endpoints (PrivateLink).
  3. Database Connection Limits: RDS có giới hạn số lượng kết nối đồng thời dựa trên dung lượng RAM của instance. Nếu dùng Lambda (có thể tự động scale lên hàng ngàn concurrent executions), RDS sẽ bị cạn kiệt connection (Too many connections error).
    • Cách khắc phục: Dùng RDS Proxy để gom và tái sử dụng connection (connection pooling) thay vì để Lambda mở connection mới liên tục.

4. Case Studies Kiến Trúc Thực Tế (Cực Khó)

Case Study 1: Hệ thống Bán Vé Sự Kiện Trực Tuyến (Flash Sale)

Bài toán: Hệ thống mở bán vé concert của nghệ sĩ nổi tiếng. Dự kiến traffic sẽ tăng đột biến (Spike) từ 100 user lên 500,000 user trong chưa đầy 1 phút. Yêu cầu: Không sập hệ thống, không bán vé lố (Overselling), độ trễ thấp.

Giải pháp Kiến trúc High-Performing:

  • Sử dụng CloudFront kết hợp WAF để chặn DDoS và cache mọi nội dung tĩnh (HTML/CSS/JS) ở Edge, giảm 90% tải cho server.
  • Sử dụng kiến trúc Serverless: API Gateway kết hợp với AWS Lambda (cấu hình Provisioned Concurrency để tránh Cold Start).
  • Backend lưu vé dùng DynamoDB (On-Demand Mode) để hấp thụ tải spike khổng lồ. Để tránh bán vé lố, dùng tính năng Conditional Writes của DynamoDB.
  • Hàng đợi request vé có thể dùng SQS FIFO để xử lý lần lượt theo thứ tự, đảm bảo công bằng.

Case Study 2: Hệ Thống Phân Tích Dữ Liệu Gen (HPC & Big Data)

Bài toán: Viện nghiên cứu sinh học cần phân tích 500 TB dữ liệu bộ gen người mỗi ngày. Yêu cầu compute cluster cực lớn, share data tốc độ siêu cao (POSIX-compliant), và chi phí tối ưu.

Giải pháp Kiến trúc High-Performing:

  • Compute: Sử dụng AWS Batch chạy trên các EC2 Spot Instances được nhóm lại bằng Cluster Placement Group để tối ưu hóa băng thông mạng giữa các node với nhau (tối đa hóa low-latency, high network throughput).
  • Lưu trữ chia sẻ: Gắn hệ thống file Amazon FSx for Lustre, liên kết trực tiếp với Amazon S3 (nơi chứa data thô). FSx for Lustre thiết kế chuyên biệt cho HPC (High Performance Computing) cung cấp tốc độ R/W cực khủng.

5. Checklist Kế hoạch Ôn tập Domain 3

Để đảm bảo bạn hoàn thành toàn bộ kiến thức Domain 3, hãy theo dõi checklist chi tiết sau đây. Tuyệt đối không bỏ qua mục nào nếu muốn pass kỳ thi.

Storage & Compute (Dự kiến: 10 giờ)

  • Đọc và tóm tắt 3.1 - Storage Solutions - S3, EBS, EFS, FSx
  • Phân biệt rõ 7 loại S3 Storage Classes và Lifecycle policies (Đặc biệt: Standard-IA, Glacier Instant Retrieval vs Flexible).
  • Hiểu cơ chế S3 Transfer Acceleration và S3 Byte-Range Fetches.
  • So sánh các loại EBS Volume (gp2/gp3 vs io1/io2 vs st1/sc1) và biết công thức tính IOPS.
  • Nắm vững Use Case của EFS so với FSx (Windows, Lustre, NetApp). Biết EFS Bursting vs Elastic Throughput.
  • Đọc và tóm tắt 3.2 - Compute - EC2, Lambda, Fargate
  • Nắm vững cách chọn EC2 Instance Family (C cho Compute, R cho RAM, M cho General, T cho Burstable, I cho Storage, G/P cho GPU).
  • Hiểu EC2 Placement Groups (Cluster, Spread, Partition) và use case thực tế.
  • Biết khi nào dùng AWS Batch vs EMR vs Elastic Beanstalk.
  • Thực hành tính toán Lambda concurrency, hiểu Lambda Cold Starts và Fargate scaling.

Database & Caching (Dự kiến: 12 giờ)

  • Đọc và tóm tắt 3.3 - Database - RDS, Aurora, DynamoDB
  • Phân biệt Multi-AZ (High Availability) vs Read Replicas (High Performance) trong RDS.
  • Hiểu kiến trúc lưu trữ của Aurora (6 copies, 3 AZs) và Aurora Serverless v2.
  • Tính toán chính xác RCU/WCU cho DynamoDB (Strongly vs Eventually Consistent).
  • Nắm rõ Global Secondary Index (GSI) vs Local Secondary Index (LSI) trong thiết kế NoSQL.
  • Đọc và tóm tắt 3.4 - Caching - ElastiCache, CloudFront
  • So sánh chuyên sâu Redis (Multi-AZ, AOF, Pub/Sub, Data structures) và Memcached (Multi-threaded, Simple).
  • Nắm vững chiến lược caching: Lazy Loading (Read-Aside) vs Write-Through.
  • Hiểu DAX (DynamoDB Accelerator) dùng khi nào và cách nó Write-Through xuống DB.

Networking & Data Ingestion (Dự kiến: 15 giờ)

  • Đọc và tóm tắt 3.5 - Networking - VPC, Route 53, Direct Connect
  • Cấu hình chi tiết Route 53 Routing Policies (Latency, Geolocation, Failover, Multivalue, Weighted).
  • So sánh CloudFront (HTTP/HTTPS, Caching) và Global Accelerator (TCP/UDP, Static Anycast IPs, No Caching).
  • Hiểu VPC Endpoints (Gateway Endpoint cho S3/DynamoDB vs Interface Endpoint/PrivateLink cho dịch vụ khác).
  • Cấu hình Transit Gateway cho kiến trúc Hub-and-Spoke.
  • Đọc và tóm tắt 3.6 - Data Ingestion - Kinesis, Glue, Athena
  • Phân biệt rõ rệt Kinesis Data Streams (Realtime, cần code consumer) và Kinesis Data Firehose (Near-realtime, no code, bắn thẳng vào S3/Redshift).
  • Hiểu vai trò của AWS Glue (ETL & Data Catalog, Crawler).
  • Dùng Athena để query logs trên S3 hiệu quả bằng định dạng Parquet và phân vùng (Partitioning).
  • Thuộc lòng use case vận chuyển dữ liệu lớn: AWS DataSync (Online) vs Snow Family (Offline).

Triết Lý High-Performance

Performance không chỉ phụ thuộc vào một dịch vụ đơn lẻ mà là sự kết hợp trơn tru của toàn bộ stack. Tối ưu DB bằng Redis siêu tốc sẽ hoàn toàn vô nghĩa nếu Network có độ trễ cao do định tuyến sai qua public internet thay vì dùng VPC Endpoint. Tư duy Solutions Architect là tư duy tìm kiếm “Chai lọ ở đâu?” (Where is the bottleneck?).
