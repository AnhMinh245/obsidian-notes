Quản Lý Bí Mật và Chứng Chỉ (Secrets & Credentials)

Việc quản lý danh tính và khóa bí mật của ứng dụng là một phần không thể thiếu trong kiến trúc bảo mật. Phần này tập trung vào cách lưu trữ an toàn cấu hình ứng dụng và quản lý danh tính người dùng đầu cuối (End-users) thay vì người dùng nội bộ (IAM).

1. Lưu Trữ Bí Mật: AWS Secrets Manager vs SSM Parameter Store

Các ứng dụng thường cần chuỗi kết nối DB, API Keys. KHÔNG BAO GIỜ hardcode các chuỗi này trong source code. AWS cung cấp 2 giải pháp:

AWS Secrets Manager

Là dịch vụ lưu trữ bí mật cao cấp.

  • Tính năng nổi bật - Auto Rotation (Xoay khóa tự động): Bí mật có thể tự động thay đổi sau X ngày. Tính năng này được tích hợp “Out-of-the-box” (dùng ngay không cần code) với RDS, Amazon DocumentDB, Amazon Redshift.
  • Cách thức xoay khóa: Sử dụng AWS Lambda function ở backend để đổi password trên DB, sau đó cập nhật lại password mới vào Secrets Manager.
  • Mã hóa bắt buộc: Mọi dữ liệu đều được mã hóa bằng KMS.
  • Cross-account: Hỗ trợ chia sẻ bí mật giữa các tài khoản thông qua resource-based policy.
  • Replication: Hỗ trợ sao chép bí mật sang Multi-Region tự động.

AWS Systems Manager (SSM) Parameter Store

Dịch vụ lưu trữ cấu hình có cấu trúc dạng phân cấp (Hierarchy).

  • Phân cấp (Hierarchy): Lưu dưới dạng đường dẫn. VD: /prod/db/url, /dev/db/password. Giúp dễ dàng IAM policy restriction (VD: developer chỉ được đọc path /dev/*).
  • Standard Tier vs Advanced Tier:
    • Standard: Miễn phí. Giới hạn 4KB/giá trị. 10,000 thông số.
    • Advanced: Trả phí. Giới hạn 8KB/giá trị. Có Parameter Policies (Tự động hết hạn - expiration). 100,000 thông số.
  • Bảo mật: Hỗ trợ 2 kiểu:
    • String / StringList: Plaintext (Dùng lưu config bình thường).
    • SecureString: Mã hóa bằng AWS KMS (Dùng lưu mật khẩu).

So sánh: Parameter Store không có Rotation tự động gốc. Muốn rotate mật khẩu RDS bằng Parameter Store, bạn phải TỰ CODE Lambda để gọi API cập nhật DB và gọi API cập nhật Parameter Store. (Vất vả hơn nhiều so với Secrets Manager).

2. Quản Lý Danh Tính Người Dùng Ứng Dụng (Amazon Cognito)

Khi bạn xây dựng ứng dụng Web/Mobile và cần chức năng Đăng ký (Sign Up) / Đăng nhập (Sign In) cho hàng triệu người dùng, bạn dùng Amazon Cognito. Cognito chia làm 2 thành phần rõ rệt:

Cognito User Pools (Authentication - Xác thực)

  • Là cơ sở dữ liệu người dùng (User Directory).
  • Quản lý quá trình: Đăng nhập, Đăng ký, Quên mật khẩu, Xác minh Email/SĐT.
  • Tính năng: Hỗ trợ MFA, Social Sign-in (Login with Google, Facebook, Apple).
  • Kết quả trả về: Sau khi đăng nhập thành công, Cognito trả về một JSON Web Token (JWT) cho ứng dụng.
  • Triggers: Có thể gọi AWS Lambda ở các giai đoạn (VD: Gọi Lambda trước khi lưu User để chặn email có đuôi @spam.com, hoặc gọi Lambda để Custom Welcome Email).

Cognito Identity Pools (Authorization - Cấp quyền)

  • Nơi chuyển đổi token (từ User Pool hoặc Facebook/Google) thành Temporary AWS Credentials.
  • Giúp người dùng di động/web truy cập TRỰC TIẾP vào tài nguyên AWS (ví dụ: Tải ảnh lên S3, Ghi dữ liệu vào DynamoDB) mà không cần đi qua backend server.
  • Sử dụng IAM Roles đính kèm theo người dùng: Một Role dành cho Guest (Unauthenticated) và một Role dành cho User đã đăng nhập (Authenticated).

Sơ Đồ Xác Thực Cognito

sequenceDiagram
    participant User
    participant App
    participant UserPool as Cognito User Pool
    participant IdPool as Cognito Identity Pool
    participant S3 as Amazon S3 / API

Exam Tip

  • Đề cập đến “Cơ sở dữ liệu lưu trữ User” hoặc “JWT Token” → User Pools.
  • Đề cập đến “Cấp quyền cho Mobile App truy cập trực tiếp S3/DynamoDB” → Identity Pools (Federated Identities).

3. Liên Kết Danh Tính (Identity Federation)

Doanh nghiệp thường đã có hệ thống quản lý danh tính (như Active Directory) và họ không muốn tạo lại tài khoản bên AWS.

SAML 2.0 Federation (Doanh nghiệp)

  • SAML 2.0 (Security Assertion Markup Language) là chuẩn công nghiệp phổ biến dùng bởi Microsoft AD FS, Okta.
  • Quá trình:
    1. User truy cập vào cổng portal của công ty (Identity Provider - IdP).
    2. IdP xác thực và trả về một SAML Assertion.
    3. Client dùng SAML này gọi API sts:AssumeRoleWithSAML.
    4. AWS cấp chứng chỉ tạm thời và cho phép login vào AWS Console hoặc truy cập API.

Web Identity Federation (Công cộng)

  • Sử dụng chuẩn OpenID Connect (OIDC). Phù hợp cho Facebook, Google.
  • Thay vì gọi API sts:AssumeRoleWithWebIdentity trực tiếp (Rất phức tạp), AWS khuyên dùng Amazon Cognito Identity Pools như là một bộ đệm (Broker) ở giữa quản lý tất cả các nguồn đăng nhập.

4. AWS Directory Service

Dịch vụ chạy Active Directory trên AWS dành cho các tải công việc Windows Enterprise.

  1. AWS Managed Microsoft AD:
    • AWS tạo một Active Directory thực sự chạy trên Windows Server.
    • Hỗ trợ Trust Relationships đa chiều (two-way trust) với On-Premises AD. Bạn có thể dùng user từ On-Prem để đăng nhập thẳng vào hệ thống trên AWS.
  2. AD Connector:
    • Là một proxy, cổng chuyển tiếp (gateway) để kết nối (redirect) các truy vấn xác thực từ AWS thẳng về On-Premises AD.
    • Lưu ý: Dữ liệu không được sao chép/cache lên AWS. Nếu đường link VPN/DirectConnect bị đứt, AD Connector ngừng hoạt động.
  3. Simple AD:
    • AD cấp thấp chạy trên nền Samba 4, tương thích cơ bản nhưng thiếu tính năng nâng cao (không hỗ trợ Trust, không Group Policy nâng cao).

5. IAM Identity Center (Single Sign-On - SSO)

Tích hợp tất cả các kiến thức về Federation và Multi-Account, đây là dịch vụ thay thế cho IAM truyền thống khi công ty có nhiều AWS Accounts.

  • Hỗ trợ ABAC (Attribute-Based Access Control): Gán quyền dựa trên thuộc tính (Tag). Ví dụ: IAM Role có thể đọc S3 nếu giá trị tag Project của User khớp với tag Project của S3 bucket.
  • Cho phép kết nối trực tiếp với AWS Managed Microsoft AD hoặc External SAML IdPs để user đăng nhập một lần, hiển thị dashboard chọn account AWS họ muốn truy cập.

7. Under the Hood: Secrets Manager Auto-Rotation

Tính năng tự động xoay khóa của Secrets Manager nghe có vẻ “magic” nhưng thực tế nó là một Lambda Function chạy ngầm.

  1. AWS cung cấp sẵn (blueprint) các hàm Lambda cho RDS, Redshift, DocumentDB.
  2. Bạn phải đảm bảo hàm Lambda này có quyền:
    • Truy cập vào Secrets Manager API (đọc password cũ, ghi password mới).
    • Truy cập vào RDS Database (cần có ENI nằm trong cùng VPC với RDS).
    • Nếu Lambda nằm trong Private Subnet (để gọi RDS), nó sẽ bị mất kết nối Internet. Lúc này nó không thể gọi ngược ra Secrets Manager API. Bắt buộc phải tạo VPC Endpoint cho Secrets Manager.

10. Case Study: RDS Password Auto-Rotation Architecture

Ngữ cảnh: Cần xoay mật khẩu database RDS tự động mỗi 30 ngày một cách an toàn mà không làm downtime ứng dụng.

sequenceDiagram
    participant SM as Secrets Manager
    participant Lambda as Rotation Lambda
    participant KMS as AWS KMS
    participant RDS as RDS Database
    participant App as App EC2

    Note over SM: Chu kỳ 30 ngày kích hoạt
    SM->>Lambda: 1. Trigger Rotation Event
    Lambda->>SM: 2. Gọi API tạo mật khẩu mới (Pending)
    Lambda->>RDS: 3. Đăng nhập DB bằng pass cũ<br>và đổi sang pass mới
    RDS-->>Lambda: Đổi thành công
    Lambda->>SM: 4. Đánh dấu mật khẩu mới là "Current" (AWSCURRENT)
    
    Note over App: App định kỳ fetch password
    App->>SM: 5. aws secretsmanager get-secret-value
    SM->>KMS: 6. Giải mã bí mật
    KMS-->>SM: (Plaintext)
    SM-->>App: 7. Trả về Password mới
    App->>RDS: 8. Login bằng Password mới

Bí kíp thiết kế: Mật khẩu được cập nhật qua hai bước nháp (AWSPENDING) và chính thức (AWSCURRENT) để nếu quá trình đổi trong database thất bại, ứng dụng vẫn có thể đọc mật khẩu cũ và duy trì hoạt động (Zero Downtime).

Checklist Bảo Mật Bí Mật và Danh Tính

  • KHÔNG lưu trữ mật khẩu trong file cấu hình hay System Variables, bắt buộc đẩy vào Secrets Manager.
  • Thay vì tự code backend để tải file ảnh từ client lên S3, dùng Cognito Identity Pool kết hợp S3 Bucket Policy giới hạn quyền user vào đúng prefix của họ.
  • Nếu lưu chuỗi kết nối vào Parameter Store, dùng dạng dữ liệu SecureString.
  • Thay vì dùng SAML IAM trực tiếp cho nhiều account, hãy ưu tiên IAM Identity Center.
