Decoupling: SQS, SNS, EventBridge Deep Dive

Thiết kế kiến trúc liên kết lỏng lẻo (Loosely Coupled Architecture) là nguyên tắc cốt lõi nhất của Domain 2 để chống lại hiệu ứng Domino (khi một component sập kéo theo cả hệ thống sập). Bằng cách chèn các “bộ đệm” (buffers) hoặc “người đưa thư” (event routers) vào giữa các module, hệ thống của bạn có thể scale độc lập, chịu lỗi tốt, và dễ bảo trì. AWS cung cấp 3 trụ cột chính cho việc này: Amazon SQS (Queuing), Amazon SNS (Pub/Sub), và Amazon EventBridge (Event Routing).

1. Amazon SQS (Simple Queue Service) Chuyên Sâu

Amazon SQS là dịch vụ lưu trữ thông điệp (Message Queue) được quản lý hoàn toàn lâu đời nhất của AWS (Ra đời trước cả EC2). Nó hoạt động theo mô hình Pull-based (Consumer/Worker phải chủ động gọi API ReceiveMessage để lấy message về).

1.1 SQS Standard vs SQS FIFO

Sự khác biệt này là câu hỏi kinh điển trong bài thi AWS.

Tính năngStandard Queue (Hàng đợi chuẩn)FIFO Queue (First-In-First-Out)
Thứ tự (Ordering)Best-effort: Cố gắng giữ thứ tự nhưng không bảo đảm 100%. Thông điệp A gửi trước có thể bị Worker nhận sau thông điệp B.Strict ordering: Đảm bảo 100% đúng thứ tự gửi vào. A vào trước, A chắc chắn ra trước.
Bảo vệ trùng lặpAt-least-once: Có rủi ro nhỏ một thông điệp bị gửi cho Worker 2 lần (do lỗi network lúc báo xóa).Exactly-once processing: Bảo đảm không bao giờ trùng lặp thông điệp (Dùng Deduplication ID).
Throughput (Tốc độ)Vô hạn (Không giới hạn số lượng API calls mỗi giây). Rất hợp cho scale lớn.Hạn chế trần: 300 msg/s (Hoặc lên tới 3000 msg/s nếu bật tính năng High Throughput Batching).
Naming ConventionTên đặt tự do (ví dụ: my-queue)Tên bắt buộc kết thúc bằng .fifo (ví dụ: my-queue.fifo)

Under the Hood: Message Group ID trong SQS FIFO

Nếu bạn chỉ dùng 1 luồng FIFO duy nhất, chỉ có 1 Worker có thể xử lý tại một thời điểm (để giữ thứ tự). Điều này kìm hãm scale-out. Để vừa giữ thứ tự vừa xử lý song song, AWS tạo ra Message Group ID. Các message có chung Group ID (ví dụ: UserID=123) sẽ được xử lý tuần tự một cách nghiêm ngặt. Các message có Group ID khác nhau (UserID=456) sẽ được phân phát song song cho các Worker khác nhau.

1.2 Cơ Chế Visibility Timeout (Giờ Tàng Hình)

Khi Worker A kéo (Pull) thành công 1 message từ Queue, message đó KHÔNG BỊ XÓA ngay lập tức. Nó chuyển sang trạng thái “In-flight” và bị TÀNG HÌNH (ẩn đi) đối với các Worker khác trong khoảng thời gian gọi là Visibility Timeout (Mặc định: 30 giây, Max: 12 giờ).

  • Luồng thành công: Worker A xử lý xong, gọi API DeleteMessage trước khi timeout hết. Message biến mất vĩnh viễn.
  • Luồng thất bại: Worker A bị crash hoặc xử lý quá lâu. Timeout trôi qua, message lập tức “hiện hình” trở lại trong Queue. Worker B sẽ kéo nó về để xử lý lại.
  • Khắc phục: Nếu Worker A biết job này sẽ mất nhiều thời gian hơn 30s, nó có thể chủ động gọi API ChangeMessageVisibility để xin thêm thời gian.

1.3 Long Polling vs Short Polling

  • Short Polling (Mặc định): SQS trả lời ngay lập tức. Nếu queue trống, nó trả về empty array. Nó chỉ lấy mẫu một phần các server backend của SQS, nên đôi khi queue có hàng nhưng trả về rỗng. Gây tốn tiền (vì tính phí mỗi API call) và tốn CPU worker.
  • Long Polling (Bắt buộc dùng trong thực tế): Cấu hình ReceiveMessageWaitTimeSeconds > 0 (Thường max 20 giây). Nếu queue trống, Worker sẽ giữ kết nối mở trong 20s chờ đợi. Ngay khi có message rớt vào queue, nó lập tức trả về. Giảm số lượng API calls vô ích, tiết kiệm tiền, giảm độ trễ.

1.4 Dead-Letter Queue (DLQ)

Nếu một message chứa data lỗi ({"age": "hai mươi"} thay vì int), Worker không thể parse và crash. Message quay lại queue. Lặp đi lặp lại tạo thành Poison Pill cản trở luồng công việc.

  • Giải pháp: Tạo một queue phụ gọi là DLQ. Cấu hình maxReceiveCount (ví dụ = 3) trên queue chính. Nếu một message bị nhận quá 3 lần mà không bị xóa, SQS tự động vứt nó sang DLQ để developer điều tra.
  • DLQ Redrive: Tool cho phép bạn sửa bug trong code của Worker, sau đó click 1 nút để đẩy toàn bộ message từ DLQ về lại queue gốc để xử lý.

2. Amazon SNS (Simple Notification Service)

Khác với SQS (người nhận chủ động vào lấy), SNS là mô hình Push-based (Loa phát thanh). Khi sự kiện (Publish) xảy ra, SNS chủ động đẩy (đá) message đến tất cả những ai đăng ký theo dõi (Subscribers).

2.1 Đặc Điểm & Cơ Chế

  • Nhà phát hành (Publishers): Ứng dụng EC2, Lambda, S3 Event Notifications, CloudWatch Alarms.
  • Người đăng ký (Subscribers): Amazon SQS, AWS Lambda, Kinesis Data Firehose, HTTP/HTTPS webhooks, Email, SMS.
  • SNS FIFO: Đảm bảo đúng thứ tự và không trùng lặp giống SQS FIFO. Tuy nhiên, Subscriber của SNS FIFO BẮT BUỘC phải là SQS FIFO (Không hỗ trợ Email/SMS/Lambda trực tiếp).

2.2 Message Filtering

Một Topic SNS có thể có 100 Subscribers. Nhưng Subscriber A chỉ muốn nhận thông báo “Đơn hàng thành công”, Subscriber B chỉ muốn “Đơn hàng thất bại”.
Thay vì Subscriber nhận tất cả rồi tự if-else trong code (tốn tiền compute), ta dùng Filter Policies bằng JSON ngay trên SNS. SNS sẽ lọc giùm và chỉ đẩy đúng message khớp policy.

3. Kiến Trúc Fanout Pattern (Vua Của Decoupling)

Sự cố phổ biến: Bạn có hệ thống E-commerce. Khi có Đơn Hàng Mới, bạn cần: (1) Lưu Database, (2) Gửi Email, (3) Tạo file PDF Invoice. Nếu code ứng dụng gọi tuần tự 3 dịch vụ này, phản hồi cho User sẽ cực kỳ chậm. Nếu 1 dịch vụ chết (VD Server Email sập), toàn bộ luồng mua hàng sập.

4. Amazon EventBridge (Tương Lai Của Serverless Events)

EventBridge (phiên bản tiến hóa của CloudWatch Events) là một Serverless Event Bus. Nó dùng để định tuyến (route) các sự kiện dựa trên quy tắc (Rule/Pattern matching).

4.1 Tại Sao Không Dùng SNS?

SNS sinh ra để broadcast (phát thanh diện rộng). EventBridge sinh ra để Lọc và Định tuyến thông minh (Routing).

  • Schema Registry: EventBridge hiểu cấu trúc JSON của data (Schema). Hỗ trợ tự sinh code binding cho Java/Python/TypeScript để dev gọi type-safe trực tiếp.
  • Targets (Đích đến): EventBridge kết nối được với nhiều dịch vụ đích hơn SNS (Gọi thẳng Step Functions, ECS Task, API Gateway, Batch).
  • Archive & Replay: SNS gửi xong là quên. EventBridge có tính năng Archive (lưu trữ sự kiện hàng tháng trời) và Replay (phát lại sự kiện cũ để test lại bug fix).

4.2 Các Loại Event Bus

  • Default Event Bus: Lắng nghe bẩm sinh các sự kiện từ hệ sinh thái AWS (EC2 bị stop, S3 có file mới, GuardDuty phát hiện hack).
  • Partner Event Bus: Nhận trực tiếp sự kiện từ các dịch vụ SaaS bên ngoài (Zendesk, Datadog, Shopify, Auth0) mà không cần bạn phải tự viết Webhook server hay setup API Gateway. Cực kỳ mạnh mẽ!
  • Custom Event Bus: Cho phép app của bạn tự định nghĩa và bắn sự kiện vào.

5. Các Mô Hình Decoupling Khác: Amazon MQ & Step Functions

5.1 Amazon MQ (Dành cho Lift & Shift)

  • Là dịch vụ managed của Apache ActiveMQ và RabbitMQ.
  • KHÔNG NÊN dùng Amazon MQ cho các ứng dụng viết mới trên Cloud (Cloud-native).
  • BẮT BUỘC DÙNG khi câu hỏi thi yêu cầu “Migrate hệ thống On-premise lên AWS mà không cần viết lại mã nguồn, đang sử dụng giao thức chuẩn như AMQP, MQTT, STOMP, OpenWire, WSS”. SQS/SNS chỉ dùng HTTP API độc quyền của AWS, nên không xài cho Migration được.

5.2 AWS Step Functions (State Machine Orchestrator)

EventBridge và SNS/SQS là kiến trúc Choreography (Các diễn viên tự múa, không ai chỉ huy ai, dễ sinh lỗi ngầm). Step Functions là kiến trúc Orchestration (Có một nhạc trưởng chỉ huy trung tâm, theo dõi tiến trình của cả một Workflow dài hạn).

  • Standard Workflow: Chạy tối đa 1 năm. Có ghi log toàn bộ các bước chuyển trạng thái một cách visual. Dành cho quy trình có con người duyệt (Human approval) hoặc Machine Learning pipeline. Tính tiền theo số lần chuyển bước (State transitions).
  • Express Workflow: Chạy tối đa 5 phút. Dùng cho IoT data processing hoặc web request tốc độ siêu cao (100k events/sec). Tính tiền theo GB-giây.

7. Troubleshooting & Lỗi Điển Hình

  1. Worker nhận message, xử lý thành công, nhưng ngày hôm sau lại nhận chính thông điệp đó:
    • Nguyên nhân: Code của bạn quên gọi API DeleteMessage sau khi xử lý xong. Dẫn tới Visibility Timeout hết hạn và SQS đưa message hiện hình trở lại queue.
  2. EventBridge Rule không bao giờ Trigger:
    • Nguyên nhân 1: Bạn viết Event Pattern JSON sai cấu trúc (Phân biệt chữ hoa/chữ thường, thiếu list bracket []).
    • Nguyên nhân 2: Lỗi phân quyền IAM. Target của bạn (ví dụ Lambda) thiếu Resource-based Policy cho phép Principal events.amazonaws.com gọi hành động lambda:InvokeFunction.
  3. Lambda làm Subscriber của SQS Queue bị Throttling cực độ:
    • Nguyên nhân: SQS có bao nhiêu message, Lambda scale ra bấy nhiêu con (tối đa 1000 con) làm cháy nổ DB bên dưới.
    • Fix: Chỉnh thông số Batch Size (Ví dụ lấy 10 messages/lần) trong Event Source Mapping của Lambda, kết hợp Reserved Concurrency để giới hạn số Lambda bật lên.

8. Case Studies Kiến Trúc Điều Phối (Orchestration vs Choreography)

Case Study: Hệ Thống Xử Lý Đơn Hàng E-Commerce Phức Tạp (Saga Pattern)

Yêu cầu: Một giao dịch liên quan đến trừ tiền thẻ, báo kho hàng (Zendesk SaaS), và hệ thống vận chuyển. Phải quản lý lỗi: Nếu trừ tiền thành công nhưng kho hết hàng, phải tự động Rollback (hoàn tiền) cho khách.

        Inventory_Check --> Fail : Item Out of Stock

        Refund_CreditCard --> Notify_Failure : SNS Email

    Notify_Failure --> [*]
    Dispatch_Delivery --> [*]

Lợi ích: Thay vì các module tự gọi nhau lung tung (Choreography) làm bạn không biết đơn hàng đang bị kẹt ở đâu, Step Functions cho bạn một bảng điều khiển trực quan màu xanh/đỏ (Visual Graph) biết chính xác luồng chạy. Cực kỳ mạnh để xử lý Rollback trong Distributed Systems.

10. Checklist Ôn Tập Domain 2.3

Đừng vào phòng thi nếu bạn chưa đánh dấu tick toàn bộ phần này:

  • Phân biệt tuyệt đối SQS Standard (Best effort, duplicates) và SQS FIFO (Strict order, no duplicates).
  • Tính năng Delay Queues (tàng hình lúc MỚI gửi) vs Visibility Timeout (tàng hình lúc ĐÃ nhận).
  • Phân biệt EventBridge (Router, Rule, SaaS Partner) vs SNS (Loa phát thanh, Pub/Sub, Email/SMS).
  • Hiểu rõ mô hình Fanout: Đẩy 1 lần vào SNS -> Tự động nảy ra nhiều SQS Queues.
  • Nhìn thấy “Legacy MQ, ActiveMQ, AMQP, Migrate” -> Tick thẳng Amazon MQ.
  • Nhìn thấy “Visual workflow”, “State machine”, “Long running saga pattern” -> Tick Step Functions.
  • Khắc phục bài toán quá giới hạn 256KB của SQS bằng Extended Client (S3).
  • Biết DLQ (Dead-Letter Queue) dùng để gom rác/lỗi (Poison pills) chống lặp vô tận.

Mẹo Tối Ưu Chi Phí (Cost Optimization Tip)

Trong thực tế, thiết kế serverless SQS + Lambda có thể tốn kém nếu lưu lượng của bạn là hàng chục triệu tin nhắn mỗi giờ. Lúc này phí API Call của API Gateway và SQS sẽ vượt mặt tiền thuê EC2. Decoupling không phải luôn rẻ, nó chỉ giúp hệ thống không chết. Khi scale quá lớn, hãy cân nhắc Kinesis Data Streams kết hợp với ECS Fargate.
