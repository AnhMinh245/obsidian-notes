Serverless và Containers trên AWS: Deep Dive

Task 2.1 của kỳ thi SAA-C03 đặc biệt nhấn mạnh vào việc thiết kế kiến trúc phân tán dùng Serverless và Containerization. Đây là hai mô hình tính toán hiện đại giúp giảm bớt gánh nặng quản lý hạ tầng (undifferentiated heavy lifting), tối ưu chi phí (trả tiền theo giây/mili-giây), và tăng tính co giãn nhanh chóng (Horizontal Scaling) lên tới hàng nghìn concurrent requests.

1. AWS Lambda: Kiến Trúc Thực Thi & Vòng Đời

AWS Lambda là dịch vụ Compute Serverless mang tính biểu tượng của AWS. Nó cho phép bạn chạy mã code mà không cần cung cấp hay quản lý máy chủ.

1.1 Vòng Đời Của Một Lambda Execution Environment (Under the Hood)

Khi một Lambda được trigger, AWS thực hiện 3 giai đoạn chính:

  1. Init (Khởi tạo): AWS tìm kiếm hoặc tạo một Execution Environment (một vi-VM Firecracker). Nó tải mã nguồn của bạn (hoặc tải Docker image từ ECR), chạy các lệnh khởi tạo (ví dụ: khởi tạo DB connection, khởi tạo SDK bên ngoài hàm handler()). Quá trình này gây ra Cold Start. Việc tính tiền không bao gồm thời gian Init (trừ khi dùng Provisioned Concurrency).
  2. Invoke (Thực thi): Hàm handler chính của bạn bắt đầu chạy để xử lý request payload. Thời gian này được tính tiền từng mili-giây.
  3. Shutdown (Tắt): Nếu Lambda không nhận được request nào trong một khoảng thời gian, AWS sẽ tắt environment này đi.

1.2 Đặc điểm kỹ thuật và Thông số cấu hình

  • Memory (RAM): Cấu hình từ 128 MB đến 10,240 MB (10 GB), với bước nhảy 1MB.
  • CPU và Network: Bạn KHÔNG THỂ chọn CPU hay Network. Tỉ lệ sức mạnh CPU được AWS tự động cấp phát tỷ lệ thuận với lượng RAM. Ví dụ: Cấp 1,769 MB RAM tương đương với 1 vCPU. Nếu code tính toán (như render ảnh) chạy chậm, hãy cấp nhiều RAM hơn, CPU sẽ mạnh hơn, code chạy nhanh hơn và có khi tiết kiệm tiền hơn!
  • Timeout: Mặc định 3 giây, tối đa 15 phút (900 giây). Tuyệt đối không dùng Lambda cho các task chạy lâu hơn 15 phút. Thay vào đó, hãy dùng AWS Step Functions, ECS Fargate, hoặc AWS Batch.
  • Ephemeral Storage (/tmp): Dung lượng lưu trữ tạm thời cung cấp từ 512 MB lên đến 10 GB. Rất hữu ích để lưu cache file, giải nén ZIP lớn, hoặc download file từ S3 xuống xử lý. Lượng data này bị xóa khi môi trường Lambda bị dọn dẹp.
  • Lambda Layers: Cho phép bạn tách các thư viện dùng chung (như thư viện numpy của Python, hoặc SDK chung) ra khỏi code chính. Một hàm có thể gắn tối đa 5 Layers. Giúp code nhẹ gọn và deploy siêu nhanh.

1.3 Cơ chế Concurrency (Đồng thời)

  • Unreserved Concurrency: Số lượng execution environments dùng chung cho toàn bộ tài khoản AWS của bạn trong 1 Region (thường mặc định là 1000). Nếu một hàm bị vòng lặp vô tận, nó có thể ăn hết quota của các hàm khác.
  • Reserved Concurrency: Giới hạn cứng số lượng môi trường tối đa mà 1 hàm được phép sử dụng. Vừa giúp bảo vệ hàm đó luôn có chỗ chạy, vừa giúp bảo vệ hệ thống backend (ví dụ DB) không bị sập do Lambda tạo quá nhiều kết nối.
  • Provisioned Concurrency: AWS sẽ khởi chạy sẵn môi trường (chạy luôn phase Init). Giải quyết triệt để vấn đề Cold Start, đặc biệt quan trọng cho ứng dụng Java hoặc C# có thời gian khởi tạo chậm. Bạn sẽ phải trả tiền “đặt chỗ” (hourly) cho tính năng này.

1.4 VPC Integration với Hyperplane ENI

Mặc định Lambda chạy trên VPC của riêng AWS, không thể giao tiếp với RDS Private hay EC2 Private. Khi cấu hình Lambda chui vào VPC của bạn:

  • Trước đây: Lambda tạo ra 1 ENI (Elastic Network Interface) riêng cho từng môi trường thực thi. Gây ra Cold Start cực lâu (có khi >10s) và làm cạn kiệt IP trong Subnet.
  • Hiện tại (từ 2019): AWS dùng công nghệ AWS Hyperplane ENI. Một ENI dùng chung (shared) được tạo sẵn và giữ kết nối tĩnh. Nhờ vậy, Lambda scale trong VPC cực kỳ nhanh (như chạy public) và chỉ tốn 1 IP cho mỗi cặp Subnet-Security Group.

2. Amazon API Gateway: Chuyên Sâu Cấu Hình

API Gateway là cổng giao tiếp (Entry Point) managed hoàn toàn. Nó đứng trước kiến trúc microservices và hứng mọi luồng HTTP traffic từ internet.

2.1 Các Loại Hình (API Types)

  • REST API: Trưởng lão đầy đủ tính năng. Hỗ trợ Data Transformation (Biến đổi request/response body dùng VTL template), Caching, Request Validation, API Keys, Usage Plans, X-Ray tracing. Tính phí dựa trên số request + phí transfer.
  • HTTP API: Thế hệ mới. Rẻ hơn REST API 71%, độ trễ thấp hơn. Chuyên dùng để làm proxy “chuyển phát nhanh” trực tiếp vào Lambda hoặc bất kỳ backend HTTP nào. Hỗ trợ JWT Authorizers mặc định. Không có Caching, không có WAF.
  • WebSocket API: Quản lý kết nối TCP hai chiều (Stateful connection). Tuyệt vời cho ứng dụng Chat, Ticker chứng khoán thời gian thực. API Gateway duy trì kết nối cho bạn, Lambda chỉ được gọi khi có tin nhắn thực sự tới.

2.2 Các Loại Tích Hợp Backend (Integration Types)

  • Lambda Proxy Integration: (Phổ biến nhất) API Gateway gom toàn bộ request (Headers, Body, Query Parameters) đóng gói vào 1 cục JSON và ném cho Lambda. Lambda tự viết logic bóc tách và trả về JSON có form {statusCode: 200, body: "hello"}.
  • Lambda Non-Proxy (Custom) Integration: API Gateway sẽ trích xuất tham số, đổi format (ví dụ từ XML sang JSON) trước khi ném vào Lambda. Đòi hỏi cấu hình Mapping Template.
  • HTTP Proxy: Đẩy thẳng request về một web server truyền thống (EC2 / On-premise).
  • AWS Service Integration: Kỹ năng sát thủ cho SAA-C03. API Gateway gọi trực tiếp một dịch vụ AWS khác (ví dụ DynamoDB, SQS, Kinesis) không cần đi qua Lambda. Cực kỳ tối ưu, giảm chi phí và giảm độ trễ.

2.3 Bảo Mật, Throttling và Quản Lý Lưu Lượng

  • Endpoint Types:
    • Edge-Optimized: Tự động deploy lên mạng lưới CloudFront Edge Locations toàn cầu. Giảm latency cho global user.
    • Regional: Deploy tại 1 Region cụ thể. Phù hợp nếu khách hàng và EC2/Lambda đều nằm chung 1 Region.
    • Private: Chỉ truy cập được từ bên trong VPC (thông qua VPC Endpoint), hoàn toàn vô hình với internet.
  • Throttling & Burst: Mặc định 10,000 request/s steady-state và 5,000 burst. Dùng Token Bucket algorithm. Nếu vượt ngưỡng -> HTTP 429 (Too Many Requests).
  • Usage Plans & API Keys: Tạo các gói dịch vụ (Basic, Premium) cấp phát API Key cho khách hàng B2B, giới hạn quota (ví dụ 1 triệu req/tháng) và rate limit (10 req/s).

3. Container Orchestration: ECS & EKS Deep Dive

Khi ứng dụng không thể dùng Lambda (Cần chạy nền lâu dài 24/7, cần tùy chỉnh OS, sử dụng framework monolithic không rã ra được), ta đóng gói nó vào Docker Container.

3.1 Amazon Elastic Container Registry (ECR)

  • Kho lưu trữ Docker Image do AWS quản lý, an toàn cao.
  • Tính năng nổi bật:
    • Image Scanning: Quét mã nguồn tự động để tìm lỗ hổng CVEs (Common Vulnerabilities and Exposures).
    • Lifecycle Policies: Tự động dọn dẹp các Image cũ (ví dụ: chỉ giữ 50 bản release gần nhất) để tối ưu chi phí lưu trữ S3 bên dưới.
    • Cross-Region Replication: Tự động đồng bộ Image sang Region khác dùng cho Disaster Recovery.

3.2 Amazon ECS (Elastic Container Service)

ECS là giải pháp orchestration bẩm sinh của AWS.

  • Task Definition: Bản vẽ mô tả cách container chạy. Khai báo Docker Image ARN, vCPU, RAM, cổng mở (Ports), cấu hình log (đẩy lên CloudWatch), biến môi trường, IAM Task Role.
  • Task: Một bản thực thi (instance) đang chạy thực tế sinh ra từ Task Definition.
  • Service: Người quản lý đảm bảo có X Tasks luôn chạy. Tự động kết nối Tasks vào Application Load Balancer (ALB), tự động thay thế Task chết, hỗ trợ Auto Scaling dựa trên CPU/Memory của toàn bộ Service.
  • Launch Types (Cách lấy compute resource):
    • EC2 Launch Type: Bạn phải tự spin up EC2 instances, cài ECS Agent. Các EC2 này lập thành một Cluster. ECS sẽ xếp các Task chạy lên các EC2 này. Ưu: Tận dụng được Spot Instance siêu rẻ, cấu hình sâu vào OS. Khuyết: Phải lo vá lỗ hổng OS, cấu hình Auto Scaling rườm rà (ASG cho EC2 + ASG cho Tasks).
    • Fargate Launch Type (Serverless Compute for Containers): Quên EC2 đi. Bạn chỉ cần ném Task Definition cho AWS, nói “Cho tôi chạy container này với 2 vCPU, 4GB RAM”. AWS tự kiếm phần cứng chạy nó, cô lập hoàn toàn bằng firecracker VM. Ưu: Nhàn nhã cực độ, bảo mật tuyệt đối, không quản lý OS. Trả tiền chính xác theo vCPU/RAM cấu hình.

3.3 Amazon EKS (Elastic Kubernetes Service)

EKS là Managed Kubernetes.

  • Control Plane: K8s Master Nodes, etcd database do AWS vận hành ngầm, đảm bảo HA qua 3 AZs. Trả phí cứng ~$70/tháng/cluster.
  • Worker Nodes: Các máy chủ chạy Pods. Hỗ trợ Managed Node Groups (AWS quản lý việc update OS cho bạn, chạy trên EC2), Fargate (tự cấp phát capacity từng Pod), hoặc Self-managed nodes.
  • Use Case: Các team đã thành thạo Kubernetes. Các dự án muốn Cloud-Agnostic (Không bị khóa vào môi trường AWS, có thể nhấc cluster đem qua GCP hoặc On-premise chạy y hệt).

5. Troubleshooting & Lỗi Phổ Biến Thực Tế

  1. Lambda bị Cold Start quá nặng, người dùng than phiền ứng dụng load chậm lần đầu:

    • Nguyên nhân: Mã nguồn quá cồng kềnh, tải nhiều dependencies không dùng, khởi tạo DB connection trong handler.
    • Fix: Đưa code khởi tạo ra ngoài hàm handler (để nó chỉ chạy 1 lần ở phase Init). Xóa bớt thư viện. Nếu vẫn chậm, mua Provisioned Concurrency.

  2. Lỗi 504 Gateway Timeout tại API Gateway:

    • Đây là cái bẫy kinh điển. Dù Lambda của bạn cấu hình timeout 15 phút, API Gateway LUÔN CẮT kết nối sau 29 giây. Nếu Lambda chạy 35 giây xong báo success, thì client đã nhận lỗi 504 từ đời nào rồi.
    • Fix: Chuyển kiến trúc sang bất đồng bộ (Trả về HTTP 202 Accepted lập tức, ném task vào SQS để Lambda xử lý nền).

  3. Lỗi 429 Too Many Requests ở Lambda (Throttling Exception):

    • Nguyên nhân: Lượng request đập vào vượt quá giới hạn Concurrent Executions của tài khoản (VD > 1000). Hoặc bạn set Reserved Concurrency = 10 mà có 15 requests đến cùng lúc.
    • Fix: Với Async invokes, AWS tự động retry lên đến 6 giờ. Với Sync invokes, client phải cài đặt thuật toán Exponential Backoff (đợi 1s, 2s, 4s, 8s rồi gửi lại). Đề nghị AWS tăng quota tài khoản.

  4. Lambda kết nối RDS làm kiệt quệ Database (Too Many Connections):

    • Nguyên nhân: Khi có 2000 request, 2000 Lambda environments được sinh ra, mỗi cái mở 1 connection tĩnh tới Database MySQL/PostgreSQL. Rất nhanh, Database hết RAM hoặc hết slot kết nối (Max_Connections) và từ chối phục vụ.
    • Fix: Phải cài đặt Amazon RDS Proxy. Proxy duy trì connection pool ổn định tới RDS, Lambda chỉ kết nối vào Proxy.

6. Case Studies Kiến Trúc Chuyên Sâu

Case Study 1: Serverless Web Application Hiện Đại

Bài toán: Xây dựng một trang web tin tức cực nhanh, chi phí siêu rẻ khi không có khách, chịu được hàng triệu truy cập đột biến.

sequenceDiagram
    participant User as Browser Client
    participant CF as Amazon CloudFront
    participant S3 as Amazon S3 (Static Web)
    participant API as API Gateway (HTTP API)
    participant Lam as AWS Lambda
    participant DB as DynamoDB (On-Demand)

    User->>CF: 1. Request trang chủ index.html
    CF->>S3: 2. Lấy static files (HTML, React JS)
    S3-->>User: Trả về file, trình duyệt render UI
    
    User->>API: 3. REST /api/news/latest (Gọi API)
    API->>Lam: 4. Route request tới Lambda
    Lam->>DB: 5. Query dữ liệu tin tức NoSQL
    DB-->>Lam: Trả về Item JSON
    Lam-->>API: Trả HTTP 200 + Body JSON
    API-->>User: 6. Hiển thị tin tức lên UI

Phân tích: Frontend lưu hoàn toàn tĩnh trên S3 + CloudFront (chi phí gần như $0, tốc độ siêu nhanh toàn cầu). Backend dùng HTTP API + Lambda + DynamoDB On-Demand. Đây là kiến trúc “Zero Maintenance” hoàn hảo.

7. AWS AppSync

  • Dịch vụ quản lý GraphQL hoàn toàn (tương tự như API Gateway dùng cho REST).
  • Nó gộp (aggregate) dữ liệu từ nhiều nguồn: DynamoDB, ElasticSearch, Lambda, RDS thành 1 endpoint GraphQL duy nhất. Tránh lỗi over-fetching hay under-fetching của REST.
  • Hỗ trợ Real-time (qua WebSockets tự động) và Offline Sync (Dữ liệu thay đổi trên mobile khi mất mạng sẽ được tự động đồng bộ lên cloud khi có mạng lại qua AWS Amplify).

9. Cẩm Nang Checklist Ôn Tập Domain 2.1

  • So sánh kỹ Lambda vs Fargate vs EC2 (Khi nào dùng cái nào).
  • Phân biệt Reserved Concurrency và Provisioned Concurrency.
  • Nắm vững cách Lambda gắn vào VPC (Sử dụng Hyperplane ENI).
  • Hiểu rõ bài toán “Timeout API Gateway 29s” và “S3 URL Payload” để giải quyết giới hạn Lambda.
