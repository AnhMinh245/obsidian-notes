Elastic Load Balancing (ELB)

Elastic Load Balancing (ELB) tự động phân phối incoming application traffic (lưu lượng truy cập) trên nhiều targets, chẳng hạn như Amazon EC2 instances, containers, IP addresses, Lambda functions, và virtual appliances. Nó hỗ trợ phân phối traffic trên một hoặc nhiều Availability Zones (AZs) để đảm bảo 2.3 - High Availability - Multi-AZ, Multi-Region.

Important

ELB là một managed service của AWS. AWS đảm bảo tính khả dụng, bảo mật và mở rộng của chính Load Balancer, bạn không cần lo về việc quản lý EC2 instance chạy ELB.

1. Các Loại Load Balancers

AWS hiện cung cấp 4 loại Load Balancer. Trong đó, Classic Load Balancer đã lỗi thời và không nên dùng cho ứng dụng mới.

1.1 Application Load Balancer (ALB)

ALB hoạt động ở Layer 7 (Application Layer) của mô hình OSI.

  • Protocols: Hỗ trợ HTTP, HTTPS, WebSocket, HTTP/2.
  • Routing Rules: Cực kỳ mạnh mẽ. Hỗ trợ định tuyến dựa trên:
    • Path-based routing: example.com/images/* trỏ đến Target Group A, example.com/api/* trỏ đến Target Group B.
    • Host-based routing: api.example.com trỏ đến Target Group A, web.example.com trỏ đến Target Group B.
    • Query string / Headers routing: Dựa trên HTTP headers hoặc query parameters (ví dụ: ?version=v1).
  • Target Groups: Có thể là EC2 instances, IP addresses (kể cả on-premise), ECS containers, và Lambda functions.
  • Authentication: Tích hợp trực tiếp với Amazon Cognito hoặc OIDC (OpenID Connect) provider để xác thực người dùng trước khi route traffic tới backend.
  • Fixed Response & Redirect: Có thể trả về mã lỗi HTTP trực tiếp (ví dụ 404) hoặc chuyển hướng (ví dụ: HTTP sang HTTPS) ở level ALB.

Under the Hood: HTTP Headers trong ALB

Khi một ALB định tuyến traffic tới target, nó sẽ đóng gói thông tin client ban đầu vào các HTTP headers đặc biệt vì backend EC2 chỉ thấy IP của ALB:

  • X-Forwarded-For: IP address thực sự của client.
  • X-Forwarded-Proto: Protocol mà client dùng (HTTP hay HTTPS).
  • X-Forwarded-Port: Port client kết nối tới ALB.

Exam Tip

Nếu câu hỏi đề cập đến “HTTP/HTTPS”, “path routing”, “host routing”, “microservices”, “containers (ECS)”, “Lambda”, hãy chọn ALB.

1.2 Network Load Balancer (NLB)

NLB hoạt động ở Layer 4 (Transport Layer).

  • Protocols: Hỗ trợ TCP, UDP, TLS.
  • Hiệu năng: Ultra-low latency (độ trễ cực thấp) và khả năng xử lý hàng triệu requests mỗi giây. Phù hợp cho extreme performance.
  • Static IP: NLB cấp cho bạn một Static IP address trên mỗi AZ. Nó cũng hỗ trợ gán Elastic IP (ALB không làm được điều này).
  • Preserve Source IP: Nếu target được chỉ định bằng instance ID, NLB bảo toàn IP nguồn của client. Nếu target là IP address, IP nguồn bị thay đổi trừ khi dùng Proxy Protocol.
  • AWS PrivateLink: Tích hợp chặt chẽ với VPC Endpoint Services (PrivateLink).

Under the Hood: Cách NLB hoạt động

Khác với ALB hoạt động như một reverse proxy hoàn chỉnh, NLB sử dụng một cơ chế phân phối traffic ở mức network driver. Nó forward các TCP session thay vì ngắt kết nối. Do đó, độ trễ thường <100ms so với ~400ms của ALB. Khi một target fails, NLB mất thời gian lâu hơn một chút (so với ALB) để phát hiện và route lại traffic (vì nó không phân tích sâu ở L7).

Exam Tip

Nếu đề bài yêu cầu “TCP/UDP”, “ultra-low latency”, “static IP”, “Elastic IP”, hoặc “PrivateLink”, hãy chọn NLB.

1.3 Gateway Load Balancer (GLB)

GLB hoạt động ở Layer 3 (Network Layer).

  • Giao thức: Sử dụng GENEVE protocol (Generic Network Virtualization Encapsulation) trên cổng UDP 6081.
  • Use Case: Dùng để triển khai, mở rộng và quản lý các third-party virtual appliances như firewalls (Tường lửa), Intrusion Detection and Prevention Systems (IDS/IPS), và Deep Packet Inspection (DPI) systems.
  • Nó hoạt động như một transparent network gateway (nghĩa là source và destination không nhận ra sự tồn tại của GLB) và load balancer.

Exam Tip

Keyword cho GLB: “third-party appliance”, “firewall”, “IDS/IPS”, “transparent inspection”.

1.4 Classic Load Balancer (CLB) - Legacy

  • Hoạt động ở L4 và L7.
  • Hiện được coi là Legacy (Cũ). AWS khuyên dùng ALB/NLB cho các kiến trúc mới.
  • Không hỗ trợ Server Name Indication (SNI) cho nhiều SSL certificates trên một IP.

3. Các Tính Năng Quan Trọng Cần Biết

Cross-Zone Load Balancing

  • Khi BẬT, Load Balancer sẽ phân phối traffic đều qua tất cả các registered targets trong tất cả các AZs đã được kích hoạt.
  • Khi TẮT, traffic được chia đều cho các AZs trước, sau đó trong mỗi AZ traffic mới chia đều cho các targets. Điều này có thể dẫn đến việc mất cân bằng tải giữa các instances nếu số lượng instances trong các AZ không đồng đều.
  • ALB: Cross-zone load balancing luôn được kích hoạt ở cấp độ load balancer (không thể tắt) và bạn KHÔNG bị tính phí transfer data liên vùng cho chức năng này.
  • NLB / GLB: Bị vô hiệu hóa mặc định. Bạn có thể bật lên, nhưng sẽ bị tính phí inter-AZ data transfer.

Health Checks

ELB sử dụng Health Checks để kiểm tra xem một target có thể xử lý request hay không.

  • Nếu target fail health check (Unhealthy Threshold), ELB ngừng gửi traffic đến target đó.
  • Nếu target pass health check trở lại (Healthy Threshold), ELB sẽ tiếp tục gửi traffic.
  • Cấu hình bao gồm: Protocol, Port, Path, Timeout, Interval, và Thresholds.

Connection Draining (Deregistration Delay)

  • Thời gian (từ 1 đến 3600 giây, mặc định là 300s) mà ELB chờ đợi để hoàn thành các kết nối “in-flight” (đang xử lý) đến một target trước khi nó hoàn toàn deregister target đó (hoặc khi target báo unhealthy).
  • Rất quan trọng khi phối hợp với 2.2 - Auto Scaling để tránh ngắt đột ngột request của người dùng khi scale-in.

SSL/TLS Termination

  • Load Balancer có thể giải mã SSL/TLS traffic, do đó EC2 instances backend không cần tốn CPU để làm việc này (gọi là SSL Offloading).
  • Tích hợp với AWS Certificate Manager (ACM) để quản lý chứng chỉ dễ dàng.
  • SNI (Server Name Indication): Cho phép ALB/NLB host nhiều SSL certificates cho các domain khác nhau trên cùng một Load Balancer.

Access Logs

  • ELB hỗ trợ ghi nhận toàn bộ access logs (Ai truy cập, thời gian, IP, HTTP status, thời gian phản hồi) và lưu trữ trực tiếp vào Amazon S3.
  • Mặc định là TẮT. Dữ liệu logs được mã hóa (SSE-S3).
  • Không mất thêm phí cho chức năng ghi log, chỉ trả phí lưu trữ S3.

Sticky Sessions (Session Affinity)

  • Đảm bảo rằng các requests từ cùng một client luôn được định tuyến đến cùng một backend target.
  • Sử dụng cookie để tracking.
  • Dùng cho ALB và CLB. Có 2 loại:
    • Duration-based cookies: ELB tự tạo cookie với tên AWSALB, có thời hạn tự định.
    • Application-based cookies: Backend application tự tạo cookie (ví dụ session id), ELB sẽ dựa vào đó. Custom cookie name không được là AWSALB, AWSALBAPP, hay AWSALBTG (đây là các tên dành riêng cho AWS).

Lỗi phổ biến

Khi dùng Sticky Sessions, traffic có thể bị phân phối không đều giữa các backend instances (vì một user có thể gửi nhiều request hơn những người khác). Thường dùng cho các ứng dụng legacy dạng stateful. Với cloud-native, nên để ứng dụng stateless và lưu session vào ElastiCache.

Pre-warming & ALB Scaling

ELB có thể tự động scale theo traffic. Quá trình scale của ALB thực chất là AWS tự động spin up thêm các LB nodes ẩn bên dưới và cập nhật bản ghi DNS của ALB để chứa nhiều IP address hơn.

  • Tuy nhiên, nếu bạn dự kiến có một sự đột biến traffic khổng lồ và đột ngột (flash crowd, ví dụ mở bán Flash Sale TV trong 1 phút), tốc độ auto-scale (cập nhật DNS) của ELB có thể không kịp (vì DNS caching tại máy client).
  • Trong trường hợp này, bạn phải liên hệ AWS Support để họ thực hiện “Pre-warm” (khởi động trước) Load Balancer của bạn đến mức công suất mong muốn.

5. Troubleshooting & Common Errors

Đối với ALB, các HTTP Status Codes là dấu hiệu rõ ràng nhất để biết lỗi đang nằm ở đâu. Nếu lỗi là 5xx, nó có thể đến từ ALB hoặc từ backend EC2:

  1. HTTP 502 (Bad Gateway):
    • ALB không thể parse response từ backend (response bị malformed).
    • Backend EC2 đóng kết nối (TCP RST) đột ngột.
  2. HTTP 503 (Service Unavailable):
    • Target Group rỗng (không có target nào registered).
    • Tất cả target đều Unhealthy (ALB không có chỗ để route).
  3. HTTP 504 (Gateway Timeout):
    • Backend application không phản hồi kịp trong thời gian timeout định sẵn của ALB (Idle Timeout, mặc định 60s).
    • Cách fix: Tăng Idle Timeout trên ALB hoặc tối ưu code ở backend, hoặc kiểm tra Security Group có block traffic từ ALB tới EC2 hay không.
  4. EC2 Instances Status Out of Service:
    • Thường do Health Check failed (sai path, EC2 CPU 100%, hoặc Security Group EC2 không cho phép IP của ALB vào port tương ứng).

Security Group cho ALB và EC2

Best practice: Security Group của EC2 backend chỉ cho phép Inbound traffic từ Security Group ID của ALB. Tuyệt đối không allow 0.0.0.0/0 trên EC2 web tier.

Case Study 1: ALB Routing for Microservices với AWS Fargate

Một công ty thương mại điện tử muốn phân tách monolithic app thành 2 microservices: Users API và Orders API. Cả hai chạy trên ECS Fargate. Họ dùng duy nhất 1 ALB để định tuyến thay vì tạo nhiều LB (tiết kiệm chi phí).

Luồng xử lý: ALB phân tích HTTP request path. Nhờ đó, 1 ALB có thể phục vụ nhiều microservices, giảm chi phí tĩnh cho LB.

Case Study 2: Fixed IP cho ALB (Kết hợp NLB và ALB)

Vấn đề: Một đối tác (Partner) yêu cầu công ty bạn phải cung cấp một dải IP cố định (Static IP) để họ đưa vào whitelist tường lửa của họ. Nhưng công ty bạn lại cần sử dụng ALB vì ứng dụng web cần Host-based routing và WAF (Web Application Firewall). ALB không hỗ trợ Static IP.
Giải pháp: Đặt một NLB (có Elastic IPs) ở phía trước, và đặt ALB làm Target của NLB đó.

8. Tóm tắt

  1. ALB (Layer 7): HTTP/HTTPS, Path/Host routing, tích hợp tốt với microservices, Lambda, ECS. Cân bằng tải linh hoạt. Dùng Security Groups. IP động.
  2. NLB (Layer 4): TCP/UDP, Ultra-low latency, Static IP (Elastic IP), triệu request/s. Không có Security Group ở cấp LB (phải gắn ở EC2). Hiệu suất tối đa.
  3. GLB (Layer 3): Phân phối traffic tới các Virtual Appliances (Firewall, IPS) của bên thứ 3.
  4. Troubleshooting: Lỗi 504 Gateway Timeout -> do EC2 phản hồi chậm; Lỗi 503 -> Target group rỗng/unhealthy.
  5. Nhớ kỹ các tính năng: Cross-zone (giúp cân bằng tốt hơn), Health Check (loại bỏ server lỗi), Connection Draining (thoát an toàn), Sticky Sessions (giữ session).

Xem tiếp bài 2.2 - Auto Scaling để biết cách kết hợp ELB với khả năng co giãn tự động của AWS.
