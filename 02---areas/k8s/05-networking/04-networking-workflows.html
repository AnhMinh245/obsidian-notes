ClusterIP chỉ là Virtual IP

  • ClusterIP không tồn tại trên bất kỳ interface nào
  • Nó chỉ là entry trong iptables → DNAT thành Pod IP thật
  • Không thể ping ClusterIP (ICMP không qua iptables DNAT)
  • Nhưng TCP/UDP connections hoạt động bình thường!

kube-proxy Modes

ModeMechanismPerformanceFeature
iptables (default)Kernel iptables rules⭐⭐⭐Random LB only
IPVSLinux Virtual Server⭐⭐⭐⭐⭐rr, lc, wrr, sh, dh, sed
nftables (K8s 1.29+)nftables (successor of iptables)⭐⭐⭐⭐Modern replacement

Production large clusters (≥500 Services): Consider IPVS mode for better performance.

NodePort Cross-Node Routing

Traffic đến Node 1 có thể route đến Pod trên Node 2!

  • Packet: Client → Node 1:30080 → DNAT → Pod on Node 2
  • Extra network hop + SNAT → source IP bị mất
  • Fix: externalTrafficPolicy: Local (chỉ route đến Pods trên cùng Node)

Ingress hoạt động ở Layer 7 (HTTP)

  • Hiểu Host header, URL path, HTTP methods
  • Có thể terminate TLS/SSL
  • Có thể rewrite URLs, add headers
  • Cần Ingress Controller (NGINX, Traefik, HAProxy) chạy trong cluster

Service (NodePort/LB) hoạt động ở Layer 4 (TCP/UDP) — không hiểu HTTP

Kubernetes Network Model — 3 Rules

  1. Every Pod gets its own IP — không share, không NAT giữa Pods
  2. All Pods can communicate with each other without NAT
  3. Node can communicate with all Pods without NAT

→ CNI Plugin (Calico, Flannel, Cilium) implement these rules

🎓 Kiểm Tra Hiểu Biết

Câu 1: Trace the Packet

Tình huống: User truy cập https://shop.example.com/api/products. Cluster dùng Ingress Controller + ClusterIP Services. Trace packet journey.

Xem đáp án 
1. DNS: shop.example.com → 35.x.x.x (Cloud LB IP)
2. Client → Cloud LB (35.x.x.x:443)
3. Cloud LB → Node (random):NodePort
4. NodePort → kube-proxy → Ingress Controller Pod
5. Ingress Controller:
   - Match rule: Host=shop.example.com, Path=/api/*
   - TLS termination (decrypt HTTPS)
   - Forward to Service: api-svc:80
6. api-svc (ClusterIP) → iptables DNAT
7. iptables → random Pod IP (10.244.x.x:8080)
8. Pod processes request → Response reverse path

Tổng cộng: 7 hops! (Client → LB → Node → Ingress → Service → iptables → Pod)

Câu 2: DNS Troubleshooting

Tình huống: Pod trong namespace staging không thể resolve backend (Service ở namespace production). Tại sao?

Xem đáp án

Short name backend sẽ search theo thứ tự:

  1. backend.staging.svc.cluster.local → ❌ (Service không có trong staging)
  2. backend.svc.cluster.local → ❌
  3. backend.cluster.local → ❌
  4. backend. → ❌

Fix: Phải dùng full name bao gồm namespace:

Cross-namespace: PHẢI specify namespace trong DNS name!

Câu 3: externalTrafficPolicy

Tình huống: NodePort Service có externalTrafficPolicy: Local. Node 1 có 2 Pods, Node 2 có 0 Pods. Client gửi request đến Node 2. Chuyện gì xảy ra?

Xem đáp án

Connection refused / timeout!

Với externalTrafficPolicy: Local:

  • Node 2 KHÔNG forward traffic đến Pods trên Node 1
  • Vì không có Pod nào trên Node 2 → request dropped
  • Health check của LB sẽ mark Node 2 là unhealthy

Giải pháp:

  1. Dùng externalTrafficPolicy: Cluster (default) — nhưng mất source IP
  2. Đảm bảo mỗi Node có ít nhất 1 Pod (dùng DaemonSet hoặc pod topology spread)
  3. Dùng Cloud LB health check → tự skip Node không có Pods
