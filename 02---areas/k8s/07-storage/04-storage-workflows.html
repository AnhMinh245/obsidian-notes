🔄 Workflow 1: Static Provisioning

Scenario: Admin tạo PV trước → Dev tạo PVC → Kubernetes bind

sequenceDiagram
    autonumber
    participant Admin as 👨‍🔧 Admin
    participant API as 🔀 API Server
    participant PVC as ⚙️ PV Controller
    participant Dev as 👨‍💻 Developer
    participant KL as 🔧 kubelet

    Note over Admin: Phase 1: Admin prepares storage

    Admin->>Admin: Create actual storage<br/>(AWS EBS, NFS share, etc.)
    Admin->>API: Create PV (100Gi, RWO,<br/>storageClass: manual)
    API->>API: Save PV (status: Available)

    Note over PVC: 👁️ Watch: PV available<br/>but no matching PVC yet

    Note over Dev: Phase 2: Developer requests storage

    Dev->>API: Create PVC (50Gi, RWO,<br/>storageClass: manual)
    API->>API: Save PVC (status: Pending)

    Note over PVC: 👁️ Watch: New PVC!<br/>Search for matching PV...

    PVC->>PVC: Match criteria:<br/>✅ accessModes match (RWO)<br/>✅ capacity ≥ request (100 ≥ 50)<br/>✅ storageClass match (manual)<br/>✅ PV is Available

    PVC->>API: Bind PVC ↔ PV
    Note over API: PV: Available → Bound<br/>PVC: Pending → Bound<br/>⚠️ 1:1 binding (100Gi reserved,<br/>even though PVC only needs 50Gi!)

    Note over Dev: Phase 3: Use in Pod

    Dev->>API: Create Pod with PVC reference
    KL->>KL: Attach volume to Node
    KL->>KL: Format filesystem (if first use)
    KL->>KL: Mount to container path
    Note over KL: ✅ Container sees<br/>/data mounted and ready!

🔄 Workflow 2: Dynamic Provisioning (StorageClass)

Scenario: Dev tạo PVC → StorageClass auto-creates PV → Bind

sequenceDiagram

    participant API as 🔀 API Server
    participant PVC as ⚙️ PV Controller
    participant SC as 💜 StorageClass<br/>Provisioner
    participant CLOUD as ☁️ Cloud API<br/>(AWS/GCP/Azure)

    Note over PVC: 👁️ Watch: New PVC!<br/>No existing PV matches...<br/>BUT StorageClass "gp3" has provisioner!

    PVC->>SC: Trigger dynamic provisioning

    SC->>CLOUD: Create 50Gi volume<br/>(API: aws ec2 create-volume<br/>type=gp3, size=50)
    CLOUD-->>SC: Volume ID: vol-abc123

    SC->>API: Create PV object<br/>capacity: 50Gi<br/>volumeHandle: vol-abc123<br/>claimRef → PVC

    PVC->>API: Bind PVC ↔ PV
    Note over API: ✅ PV auto-created!<br/>PV: Bound<br/>PVC: Bound

    Dev->>API: Create Pod with PVC
    KL->>CLOUD: Attach vol-abc123 to Node
    KL->>KL: Format ext4 + Mount
    Note over KL: ✅ Ready!

Dynamic Provisioning = Best Practice cho Production

  • Admin chỉ cần setup StorageClass 1 lần
  • Developer tự create PVC → PV tự động tạo
  • Không cần admin can thiệp cho mỗi PVC request
  • Phù hợp với self-service model

CSI = Container Storage Interface

CSI là standard interface cho storage drivers trong K8s:

  • CSI Controller (centralized): Provision, Attach, Detach, Delete
  • CSI Node (per-node): Format, Mount, Unmount
  • Mỗi cloud provider implement CSI driver riêng (EBS CSI, GCE PD CSI, Azure Disk CSI)

🔄 Workflow 4: Reclaim Policies — Impact Flow

Scenario: PVC bị xoá — chuyện gì xảy ra với PV và data?

flowchart TD
    DELETE_PVC["🗑️ kubectl delete pvc my-pvc"] --> PV_STATUS["PV status: Bound → Released"]

    PV_STATUS --> POLICY{"persistentVolumeReclaimPolicy?"}

    POLICY -->|"Retain"| RETAIN_PV["PV status: Released<br/>Data: ✅ INTACT<br/>Storage: ✅ EXISTS"]
    RETAIN_PV --> ADMIN_ACTION["👨‍🔧 Admin must manually:<br/>1. Backup data if needed<br/>2. Delete PV object<br/>3. Optionally cleanup disk<br/>4. Recreate PV for reuse"]
    ADMIN_ACTION --> REUSE["PV Available again<br/>(or create new PV)"]

    POLICY -->|"Delete"| DELETE_PV["PV: AUTO-DELETED<br/>Storage: AUTO-DELETED<br/>(EBS volume deleted!)"]
    DELETE_PV --> GONE["💀 Data GONE FOREVER!<br/>No recovery possible!"]

    POLICY -->|"Recycle<br/>(deprecated)"| RECYCLE["PV: rm -rf /volume/*<br/>Then status: Available"]
    RECYCLE --> AVAILABLE["PV ready for<br/>new PVC binding"]

    style DELETE_PVC fill:#e74c3c,stroke:#c0392b,color:#fff
    style RETAIN_PV fill:#27ae60,stroke:#1e8449,color:#fff
    style REUSE fill:#27ae60,stroke:#1e8449,color:#fff
    style GONE fill:#e74c3c,stroke:#c0392b,color:#fff
    style RECYCLE fill:#f39c12,stroke:#d68910,color:#fff

Production Rules

  • Production data: ALWAYS use Retain → admin controls data lifecycle
  • Dev/test environments: Delete OK → auto-cleanup saves cost
  • NEVER assume data survives PVC deletion with Delete policy!
  • Dynamic provisioning default: Usually Delete ← Cẩn thận!

StatefulSet + Storage Rules

  1. PVC per Pod: Mỗi Pod có PVC riêng naming convention <template-name>-<pod-name>
  2. Scale down ≠ delete PVC: Scale 3→1, PVC-1 và PVC-2 vẫn tồn tại!
  3. Scale up = reuse PVC: Scale 1→3, postgres-1 re-attach PVC-1 (data vẫn còn!)
  4. Delete StatefulSet: PVCs vẫn tồn tại — phải xoá manual nếu cần

🔄 Workflow 6: Volume Expansion

Scenario: PVC cần thêm dung lượng 10Gi → 50Gi

flowchart TD
    REQUEST["👨‍💻 kubectl edit pvc my-pvc<br/>spec.resources.requests.storage: 50Gi"] --> CHECK{"StorageClass<br/>allowVolumeExpansion<br/>= true?"}

    CHECK -->|"❌ false"| DENIED["❌ Expansion denied<br/>Must use StorageClass with<br/>allowVolumeExpansion: true"]

    CHECK -->|"✅ true"| EXPAND_PV["CSI Controller:<br/>ControllerExpandVolume()<br/>Cloud API: resize vol to 50Gi"]

    EXPAND_PV --> EXPAND_FS{"Volume type<br/>supports online<br/>expansion?"}

    EXPAND_FS -->|"Yes (EBS, GCE PD)"| ONLINE["kubelet: NodeExpandVolume()<br/>resize2fs /dev/xvdf<br/>(online, no downtime!)"]

    EXPAND_FS -->|"No"| OFFLINE["⚠️ Need Pod restart<br/>Delete Pod → Recreate<br/>kubelet expands FS on mount"]

    ONLINE --> DONE["✅ PVC: 50Gi<br/>Container sees 50Gi at /data"]
    OFFLINE --> DONE

    style REQUEST fill:#3498db,stroke:#2980b9,color:#fff
    style DENIED fill:#e74c3c,stroke:#c0392b,color:#fff
    style ONLINE fill:#27ae60,stroke:#1e8449,color:#fff
    style DONE fill:#27ae60,stroke:#1e8449,color:#fff
    style OFFLINE fill:#f39c12,stroke:#d68910,color:#fff

Volume Expansion Limitations

  • ✅ Expand: PVC size can ONLY increase (10Gi → 50Gi)
  • ❌ Shrink: CANNOT decrease PVC size (50Gi → 10Gi)
  • StorageClass MUST have allowVolumeExpansion: true
  • Some CSI drivers support online expansion, some need Pod restart

🎓 Kiểm Tra Hiểu Biết

Câu 1: Dynamic vs Static

Tình huống: Team muốn mỗi developer tự tạo PVC cho test database (10Gi mỗi người). Nên dùng Static hay Dynamic provisioning?

Xem đáp án

Dynamic Provisioning!

  • Admin setup StorageClass 1 lần (ví dụ: storageClass: standard)
  • Mỗi developer tự tạo PVC → PV auto-create
  • Không cần admin approve mỗi request
  • Cost-efficient: volume chỉ tạo khi cần

Static provisioning không phù hợp vì admin phải pre-create PV cho mỗi developer → không scalable.

Câu 2: Reclaim Policy Incident

Tình huống: Production database PVC bị xoá nhầm. StorageClass có reclaimPolicy: Delete. Chuyện gì xảy ra? Có recover được không?

Xem đáp án

Thảm hoạ!

  1. PVC deleted → PV auto-deleted
  2. PV deleted → underlying storage (EBS volume) deleted
  3. Data GONE FOREVER! Không thể recover!

Prevention:

  • Production StorageClass: reclaimPolicy: Retain
  • Enable Volume snapshots (backup before delete)
  • RBAC: Restrict PVC delete permission in production namespace
  • Use kubectl diff trước khi kubectl delete

Câu 3: StatefulSet Scale Down

Tình huống: StatefulSet redis (3 replicas) scale xuống 1. Rồi scale lên 3 lại. Data có mất không?

Xem đáp án

Data KHÔNG mất!

Scale 3 → 1:

  • Pod redis-2 deleted, Pod redis-1 deleted
  • PVC data-redis-2 và data-redis-1 KHÔNG bị xoá
  • PV vẫn Bound (với PVC, dù Pod không còn)

Scale 1 → 3:

  • Pod redis-1 created → re-attach data-redis-1 → data vẫn còn!
  • Pod redis-2 created → re-attach data-redis-2 → data vẫn còn!

→ StatefulSet preserve storage qua scale events — đây là designed behavior!
