Cascade Delete

Khi xoá Deployment:

  1. Deployment Controller xoá tất cả ReplicaSets (cả old revisions)
  2. ReplicaSet Controller xoá tất cả Pods thuộc RS đó
  3. kubelet stop containers → cleanup → GC

→ Xoá Deployment = tất cả sạch. Xoá Pod = RS tạo lại ngay.

Ordered Deletion (ngược lại Creation)

Scale down 3 → 1:

  • Xoá postgres-2 trước → chờ Terminated
  • Xoá postgres-1 → chờ Terminated
  • postgres-0 giữ lại (Pod cuối)

PVCs KHÔNG bị xoá khi scale down → dữ liệu an toàn!

StatefulSet DNS Format

Mỗi Pod có DNS riêng theo format:

<pod-name>.<service-name>.<namespace>.svc.cluster.local

Ví dụ:

postgres-0.postgres.default.svc.cluster.local  → Pod 0
postgres-1.postgres.default.svc.cluster.local  → Pod 1
postgres-2.postgres.default.svc.cluster.local  → Pod 2

→ Dùng DNS này cho replication connection giữa DB nodes!

DaemonSet vs Deployment — Key Difference

  • DaemonSet: Exactly 1 Pod per eligible Node — Pod gắn liền Node
  • Deployment: N Pods phân phối trên các Nodes — Pod có thể di chuyển

Node bị xoá → DaemonSet Pod mất luôn (không reschedule)
Node bị xoá → Deployment Pod được tạo lại trên Node khác!

🔄 Workflow 5: CronJob — Scheduling Decision

Scenario: Backup database mỗi ngày lúc 2:00 AM

sequenceDiagram
    autonumber
    participant CC as ⏰ CronJob<br/>Controller
    participant API as 🔀 API Server
    participant JC as ⚙️ Job<br/>Controller
    participant KL as 🔧 kubelet

    Note over CC: schedule: "0 2 * * *"<br/>Check every 10s

    loop Mỗi 10 giây
        CC->>CC: Is it 2:00 AM?
    end

    Note over CC: ⏰ 2:00 AM triggered!

    CC->>CC: Check concurrencyPolicy
    alt concurrencyPolicy: Forbid
        Note over CC: Previous Job running?<br/>→ SKIP this run
    else concurrencyPolicy: Replace
        Note over CC: Previous Job running?<br/>→ DELETE old, CREATE new
    else concurrencyPolicy: Allow (default)
        Note over CC: Create regardless
    end

    CC->>API: Create Job<br/>db-backup-28495320
    API->>API: Save Job → etcd

    JC->>API: Create Pod for Job
    KL->>KL: Run backup script
    KL->>API: Pod completed (exit 0)

    JC->>API: Job status: Complete

    Note over CC: Check history limits:<br/>successfulJobsHistoryLimit: 3<br/>failedJobsHistoryLimit: 1
    CC->>API: Cleanup old Jobs<br/>(keep last 3 successful)

Missed Schedules

Nếu CronJob Controller bị down > startingDeadlineSeconds (default 100s):

  • Missed schedules ≥ 100 → CronJob ngừng schedule, cần manual intervention
  • Missed < 100 → Run ngay khi Controller khôi phục

🎓 Kiểm Tra Hiểu Biết

Câu 1: StatefulSet Ordering

Tình huống: StatefulSet redis có 5 replicas. Bạn scale down từ 5 → 2. Thứ tự xoá Pods là gì? PVCs có bị xoá không?

Xem đáp án 
Thứ tự xoá (reverse ordinal):
1. redis-4 → Terminated ✅
2. redis-3 → Terminated ✅
3. redis-2 → Terminated ✅
→ Còn lại: redis-0, redis-1

PVCs: KHÔNG bị xoá!
- pvc-redis-data-redis-2 → vẫn tồn tại (Bound, nhưng không ai dùng)
- pvc-redis-data-redis-3 → vẫn tồn tại
- pvc-redis-data-redis-4 → vẫn tồn tại

Nếu scale up lại → Pods sẽ re-attach PVCs cũ → Data vẫn còn!

Câu 2: DaemonSet vs Deployment

Tình huống: Bạn cần deploy Fluentd log collector. Nên dùng Deployment hay DaemonSet? Tại sao?

Xem đáp án

DaemonSet! Vì:

  1. Fluentd cần chạy trên MỌI Node để collect logs từ tất cả containers
  2. DaemonSet đảm bảo exactly 1 Pod/Node — không thừa không thiếu
  3. Khi Node mới join → Auto-deploy Fluentd (không cần manual)
  4. Fluentd cần access Node-level resources (/var/log, hostPath)

Deployment không phù hợp vì:

  • Không đảm bảo mỗi Node đều có Pod
  • Scheduler có thể dồn tất cả Pods lên 1 Node
  • Không auto-react khi Node join/leave

Câu 3: Job Failure

Tình huống: Job có backoffLimit: 4, completions: 1. Pod fail liên tục. Chuyện gì xảy ra?

Xem đáp án 
Attempt 1: Pod created → Failed (exit 1)
  → Backoff: 10s wait
Attempt 2: Pod created → Failed (exit 1)
  → Backoff: 20s wait
Attempt 3: Pod created → Failed (exit 1)
  → Backoff: 40s wait
Attempt 4: Pod created → Failed (exit 1)
  → Backoff: 80s wait
Attempt 5: Would be attempt #5 → BUT backoffLimit=4 reached!

→ Job status: Failed
→ Reason: BackoffLimitExceeded
→ Tổng cộng 5 Pods (1 original + 4 retries)
→ All Pods remain (status: Failed) until TTL cleanup

backoffLimit counts retries, không phải total attempts.
Exponential backoff: 10s → 20s → 40s → 80s → 160s → … (max 6 min)
