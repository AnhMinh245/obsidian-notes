🔭 Ba Trụ Cột Observability

Tổng Quan

┌─────────────────────────────────────────────────────────────┐
│                    OBSERVABILITY STACK                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  📊 METRICS (Prometheus + Grafana)                         │
│  ├── "WHAT is happening?" — Số liệu định lượng            │
│  ├── CPU usage, memory, request rate, error rate           │
│  ├── Time-series data → trends, alerts                     │
│  └── Query: PromQL                                         │

│  ├── "WHY did it happen?" — Chi tiết events                │
│  ├── Application logs, error messages, stack traces        │
│  ├── Text/JSON data → search, filter                       │
│  └── Query: LogQL                                          │
│                                                             │
│  🔍 TRACES (Jaeger / OpenTelemetry)                        │
│  ├── "WHERE did it happen?" — Request flow                 │
│  ├── Cross-service request paths, latency breakdown        │
│  ├── Span data → dependency maps, bottlenecks             │
│  └── Query: Trace ID, service name                         │
│                                                             │
│  Combined → Full picture:                                   │
│  Metric alert → Find relevant logs → Trace the request     │
│                                                             │
└─────────────────────────────────────────────────────────────┘

├── Pull model: Prometheus PULL metrics từ targets

├── TSDB: Time-series database (efficient storage)

Custom dashboard best practices:

✅ DO:
├── Dùng variables ($namespace, $pod) để dynamic
├── Set reasonable refresh intervals (30s-1m)
├── Group related panels thành rows
├── Add descriptions cho mỗi panel
└── Use consistent color schemes

❌ DON'T:
├── Quá nhiều panels (>20 per dashboard)
├── Query quá nặng (range quá dài)
├── Miss units (%, bytes, seconds)
└── Forget to save dashboard as JSON (version control!)

📝 Logging với Loki

Tại Sao Loki?

ELK Stack (Elasticsearch + Logstash + Kibana):
├── Powerful full-text search
├── Complex, heavy, expensive
└── Overkill cho nhiều use cases

Loki Stack (Loki + Promtail + Grafana):
├── "Prometheus but for logs"
├── Lightweight — chỉ index labels, không index log content
├── Cost-effective — lưu logs compressed, query khi cần
├── Grafana integration — logs + metrics cùng 1 UI
└── LogQL — query language giống PromQL

🔍 Distributed Tracing

Tại Sao Cần?

Microservices problem:
User → API Gateway → Auth Service → User Service → Database
                  └→ Product Service → Cache → Database

Request chậm → Service nào gây ra?
Error → Service nào lỗi?

Distributed Tracing giải quyết:
├── Track request path qua ALL services
├── Measure latency từng service
├── Identify bottlenecks
└── Visualize service dependencies

OpenTelemetry (Recommended — Industry Standard)

OpenTelemetry = Vendor-neutral observability framework
├── Collect: metrics, logs, traces
├── Process: transform, filter, batch
├── Export: To any backend (Jaeger, Zipkin, Datadog, etc.)
└── SDKs: Go, Java, Python, Node.js, .NET, etc.

Alert Best Practices

✅ DO:
├── Alert on SYMPTOMS, not causes
│   ✅ "Error rate > 5%" (symptom)
│   ❌ "CPU > 80%" alone (might not be problem)
├── Include runbook URLs
├── Set appropriate "for" durations (tránh flapping)
├── Group related alerts
├── Test alerts regularly
└── Have on-call rotation

❌ DON'T:
├── Alert on everything (alert fatigue)
├── Miss severity classification
├── Forget to update runbooks
├── Have too many receivers
└── Ignore silenced alerts long-term

📈 SLI/SLO/SLA

Definitions

SLI (Service Level Indicator):
├── Metric đo lường chất lượng service
├── Ví dụ: "Percentage of successful requests"
└── Data-driven, measurable

SLO (Service Level Objective):
├── Target cho SLI
├── Ví dụ: "99.9% requests successful"
└── Internal goal, engineering team owns

SLA (Service Level Agreement):
├── Contract với customers
├── Ví dụ: "99.9% uptime, refund nếu vi phạm"
└── Business commitment, có consequences

Relationship:
SLI (what we measure) → SLO (our target) → SLA (customer promise)
SLO should be stricter than SLA!

Define SLIs

SLO Targets

Availability SLO: 99.9% (3 nines)
├── 43.2 minutes downtime/month
├── 8.76 hours downtime/year
└── Error budget: 0.1% of requests can fail

Latency SLO: 95% of requests < 500ms
├── Cho phép 5% requests chậm hơn 500ms
└── Monitor P95 latency

Common SLO targets:
├── 99%    → 7.2 hours/month downtime (development)
├── 99.9%  → 43.2 min/month downtime (production)
├── 99.95% → 21.6 min/month downtime (critical)
└── 99.99% → 4.3 min/month downtime (financial)

Error Budget

Error Budget = 1 - SLO = allowed failures

Example:
├── SLO: 99.9%
├── Error Budget: 0.1%
├── Monthly requests: 100 million
├── Budget: 100,000 failed requests/month
│
├── Current errors: 50,000 → Budget remaining: 50%
│   → OK to deploy new features, experiment
│
├── Current errors: 95,000 → Budget remaining: 5%
│   → STOP deployments, focus on reliability
│
└── Budget depleted → Freeze changes, fix issues

🎓 Key Takeaways

  1. Three Pillars: Metrics (Prometheus) + Logs (Loki) + Traces (Jaeger/OTel)
  2. Golden Signals: Latency, Traffic, Errors, Saturation — monitor these first
  3. Prometheus: Pull model, ServiceMonitor cho auto-discovery, PromQL cho queries
  4. Grafana: Unified dashboards cho metrics + logs + traces
  5. Loki: “Prometheus for logs” — lightweight, label-based, LogQL
  6. Alerting: Alert on symptoms, include runbooks, avoid alert fatigue
  7. SLI/SLO/SLA: Define targets, track error budget, drives reliability decisions
  8. OpenTelemetry: Industry standard cho instrumentation — vendor-neutral
