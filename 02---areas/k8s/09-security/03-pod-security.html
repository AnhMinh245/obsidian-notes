9.3. Pod Security - Hardening Pods

SecurityContext, Pod Security Standards, Image Security — chạy containers an toàn

🎯 Mục Tiêu Học

Sau khi học xong phần này, bạn sẽ:

  • ✅ Cấu hình SecurityContext (container-level và Pod-level)
  • ✅ Hiểu Pod Security Standards: Privileged, Baseline, Restricted
  • ✅ Áp dụng Pod Security Admission controller
  • ✅ Implement runAsNonRoot, readOnlyRootFilesystem
  • ✅ Quản lý Capabilities và Seccomp profiles
  • ✅ Cấu hình AppArmor và SELinux cho containers
  • ✅ Triển khai Image Security: scanning, signing, admission control
  • ✅ Sử dụng Policy Engines: OPA/Gatekeeper, Kyverno

🔐 SecurityContext

Giải Thích Bằng Ví Dụ

🏢 VÍ DỤ: PHÂN QUYỀN TRONG TÒA NHÀ VĂN PHÒNG

Nhân viên bình thường (container bình thường):
├── Chỉ vào được phòng làm việc (non-root user)
├── Không mang theo đồ cấm (drop capabilities)
├── Không sửa đổi cơ sở vật chất (readOnlyRootFilesystem)
├── Badge chỉ cho phép tầng 3 (seccomp profile)
└── Camera theo dõi (audit logging)

Admin tòa nhà (privileged container — tránh dùng!):
├── Vào được mọi phòng (root user)
├── Có master key (all capabilities)
├── Sửa đổi hệ thống điện nước (write filesystem)
└── Rủi ro: nếu badge bị mất, attacker có full access!

→ Principle: Give MINIMUM permissions needed

Pod-Level SecurityContext

Linux Capabilities Explained

Linux chia root privileges thành ~37 capabilities riêng lẻ:

Capabilities hay dùng:
├── NET_BIND_SERVICE  → Bind ports < 1024 (web servers)
├── NET_ADMIN         → Network configuration (CNI plugins)
├── SYS_ADMIN         → Mount filesystems, manage namespaces
├── SYS_PTRACE        → Debug/trace processes (profiling)
├── DAC_OVERRIDE      → Bypass file permission checks
└── CHOWN             → Change file ownership

Best Practice:
  drop: ["ALL"]     → Remove everything
  add: ["NET_BIND_SERVICE"]  → Add back ONLY what's needed

❌ KHÔNG BAO GIỜ dùng:
  privileged: true  → Equivalent root trên host!
  capabilities.add: ["SYS_ADMIN"]  → Gần như root

📋 Pod Security Standards (PSS)

3 Levels

┌─────────────────────────────────────────────────────┐
│           POD SECURITY STANDARDS                    │
├─────────────────────────────────────────────────────┤
│                                                     │
│  Level 1: PRIVILEGED (Không hạn chế)               │
│  ├── Cho phép mọi thứ                             │
│  ├── Dùng cho: System components, CNI, monitoring  │
│  ├── Namespaces: kube-system, monitoring           │
│  └── KHÔNG dùng cho application Pods!              │
│                                                     │
│  Level 2: BASELINE (Hạn chế cơ bản)               │
│  ├── Block những thứ nguy hiểm nhất               │
│  ├── No hostNetwork, hostPID, hostIPC              │
│  ├── No privileged containers                      │
│  ├── No hostPath volumes (ngoại trừ approved)      │
│  └── Dùng cho: Hầu hết workloads                  │
│                                                     │
│  Level 3: RESTRICTED (Hạn chế chặt)               │
│  ├── Strict security requirements                  │
│  ├── runAsNonRoot required                         │
│  ├── Drop ALL capabilities                         │
│  ├── readOnlyRootFilesystem enforced               │
│  ├── Seccomp profile required                      │
│  └── Dùng cho: Security-critical workloads         │
│                                                     │
└─────────────────────────────────────────────────────┘

Pod Security Admission Modes

3 modes có thể kết hợp:

enforce: Reject Pods vi phạm (BLOCK)
audit:   Log violations nhưng vẫn cho run (LOG)
warn:    Show warning nhưng vẫn cho run (WARN)

Strategy khuyến nghị:
├── Production:  enforce: restricted
├── Staging:     enforce: baseline, warn: restricted
├── Development: warn: restricted (không block, chỉ warn)
└── kube-system: enforce: privileged (system components cần)

🛡️ AppArmor

Tại Sao Cần?

SecurityContext: Kiểm soát WHAT container có thể làm (capabilities, user)
AppArmor:       Kiểm soát HOW container interact với OS (file access, network)

AppArmor = Mandatory Access Control (MAC) trên Linux
├── Restrict file read/write paths
├── Restrict network access
├── Restrict capability usage
└── Per-container profiles

Cách Dùng

Profile types:

runtime/default  → Container runtime default profile (recommended)
localhost/<name> → Custom profile loaded trên Node
unconfined       → Không áp dụng AppArmor (không khuyến khích)

Custom AppArmor Profile

# /etc/apparmor.d/k8s-myapp (load trên mỗi Node)
#include <tunables/global>

profile k8s-myapp flags=(attach_disconnected) {
  #include <abstractions/base>
  
  # Allow read /etc/
  /etc/** r,
  
  # Allow read/write /tmp/
  /tmp/** rw,
  
  # Deny write to /var/ (trừ /var/log/)
  deny /var/** w,
  /var/log/** rw,
  
  # Network: chỉ TCP
  network tcp,
  deny network udp,
}

⚠️ K8s 1.30+: AppArmor annotation đang migrate sang field trong SecurityContext. Kiểm tra version cluster trước khi dùng.

🐧 SELinux

Khi Nào Cần?

SELinux (Security-Enhanced Linux):
├── Enforcing trên: RHEL, CentOS, Fedora, Amazon Linux
├── Mandatory Access Control
├── Label-based: Mỗi process và file có label
├── Policy: Rules quyết định label A có access label B không
└── Multi-Category Security (MCS): Isolate containers

Cấu Hình SELinux cho Containers

💡 Best Practices Summary

🎯 Key Takeaways

  1. SecurityContext kiểm soát security settings cho Pods và Containers
  2. runAsNonRoot + readOnlyRootFilesystem + drop ALL capabilities = baseline security
  3. Pod Security Standards (Restricted) enforce ở namespace level — dùng cho production
  4. AppArmor/SELinux thêm layer MAC (Mandatory Access Control) trên top of SecurityContext
  5. Image scanning (Trivy) là first line of defense — integrate vào CI/CD
  6. Image signing (Cosign) đảm bảo image integrity
  7. Policy Engines (Kyverno/Gatekeeper) enforce organizational security policies
  8. Defense in depth = kết hợp TẤT CẢ layers: RBAC + NetworkPolicy + PSS + AppArmor + Image Security
