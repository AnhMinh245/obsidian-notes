🔄 Workflow 1: Complete Self-Healing Pipeline

Scenario: Pod crash → Detection → Recovery → Traffic restored

sequenceDiagram
    autonumber
    participant C as 📦 Container
    participant KL as 🔧 kubelet
    participant API as 🔀 API Server
    participant EP as Endpoints<br/>Controller
    participant KP as ⚙️ kube-proxy
    participant RSC as ⚙️ ReplicaSet<br/>Controller

    Note over C: 💥 Container crashes!<br/>(OOMKill / App Error / Segfault)

    KL->>KL: Detect container exit<br/>exitCode: 137 (OOMKill)<br/>or exitCode: 1 (App Error)

    KL->>API: Update Pod status<br/>containerStatus: Terminated<br/>Ready: false

    par Remove from traffic
        EP->>EP: 👁️ Watch: Pod not Ready!
        EP->>API: Remove Pod IP from Endpoints
        KP->>KP: Update iptables<br/>❌ No traffic to this Pod
    and Restart container
        KL->>KL: Check restartPolicy
        Note over KL: restartPolicy: Always<br/>→ Restart with backoff
        KL->>KL: ⏱️ Backoff delay<br/>0s → 10s → 20s → 40s<br/>→ 80s → 160s → 300s (max)
        KL->>C: Pull image (if needed)<br/>Create + Start container
    end

    alt Container starts OK
        C-->>KL: Process running
        KL->>KL: readinessProbe passes
        KL->>API: Update: Ready=true
        EP->>API: Add Pod IP back to Endpoints
        KP->>KP: Update iptables<br/>✅ Traffic restored!
    else Container crashes again (CrashLoopBackOff)
        C-->>KL: Exit code non-zero
        KL->>KL: Increase backoff<br/>Status: CrashLoopBackOff
        Note over KL: Keep retrying with<br/>exponential backoff (max 5min)
    end

Node Failure Timeline

timeline
    title Node Failure → Pod Recovery Timeline

    T+0s : 💀 Worker Node dies
         : kubelet stops sending heartbeats
         : Pods still "Running" in API

    T+10-40s : Node Controller misses heartbeats
             : nodeStatusUpdateFrequency = 10s
             : 4 consecutive misses

    T+40s : Node marked NotReady
          : kubectl get nodes → STATUS: NotReady
          : Endpoints Controller removes Pods
          : kube-proxy removes iptables rules
          : 🚫 Traffic stops going to dead Node

    T+40s-5min : Grace Period (pod-eviction-timeout)
               : Pods still "Running" status on dead Node
               : But NO traffic reaching them
               : Other healthy Pods handle traffic

    T+5min : Pod Eviction begins
           : Taint added → node.kubernetes.io/unreachable:NoExecute
           : All Pods evicted from dead Node
           : ReplicaSet Controller detects actual < desired

    T+5min+ : Recovery Complete ✅
            : New Pods created by RS Controller
            : Scheduler assigns to healthy Nodes
            : kubelet starts containers
            : Endpoints + kube-proxy updated
            : Full service restored!

5 phút downtime cho affected Pods!

  • Pods trên dead Node → 5 phút trước khi bị evict và reschedule
  • Traffic bị cut sau 40s (Node NotReady)
  • Pods trên healthy Nodes vẫn serve traffic bình thường
  • → Reason to always run ≥2 replicas trên ≥2 Nodes!

Scenario: Auto-scale dựa trên CPU utilization

Complete HPA Decision Flow

flowchart TD
    subgraph "Metrics Pipeline"
        CADVISOR["cAdvisor<br/>(per Node)"] -->|"container metrics"| KUBELET["kubelet<br/>/metrics/resource"]
        KUBELET --> MS["📊 Metrics Server<br/>kube-system"]
    end

    subgraph "HPA Controller Loop (mỗi 15s)"
        MS -->|"metrics.k8s.io API"| HPA["📈 HPA Controller"]

        HPA --> FETCH["Fetch current metrics<br/>for all Pods in target"]

        FETCH --> CALC["🧮 Calculate desired replicas:<br/>desired = ⌈current × (actual/target)⌉"]

        CALC --> EXAMPLE["Example:<br/>Current: 3 Pods<br/>Target CPU: 50%<br/>Actual CPU: avg 75%<br/><br/>desired = ⌈3 × (75/50)⌉ = ⌈4.5⌉ = 5"]

        EXAMPLE --> BOUNDS{"Within<br/>min/max?"}
        BOUNDS -->|"desired < min"| USE_MIN["Use minReplicas"]
        BOUNDS -->|"desired > max"| USE_MAX["Use maxReplicas"]
        BOUNDS -->|"min ≤ desired ≤ max"| USE_CALC["Use calculated value"]
    end

    subgraph "Scale Action"
        USE_MIN & USE_MAX & USE_CALC --> DIRECTION{"Scale<br/>direction?"}

        DIRECTION -->|"Scale UP"| SCALE_UP["▲ Immediate scale up<br/>Update Deployment replicas<br/>→ RS Controller → new Pods<br/>→ Scheduler → kubelet"]

        DIRECTION -->|"Scale DOWN"| STABILIZE["⏳ Stabilization window<br/>(default: 5 min)<br/>Pick HIGHEST recommendation<br/>in last 5 min"]
        STABILIZE --> SCALE_DOWN["▼ Gradual scale down"]

        DIRECTION -->|"No change"| WAIT["⏳ Wait 15s<br/>Check again"]
    end

HPA Formula 

desiredReplicas = ⌈ currentReplicas × (currentMetric / targetMetric) ⌉
  • Scale UP: Ngay lập tức (fast reaction)
  • Scale DOWN: Chờ stabilization window 5 phút (tránh flapping)
  • Tolerance: ±10% (default) — không scale nếu trong khoảng này

VPA vs HPA

  • HPA: Scale horizontally (thêm/bớt Pods) — dựa trên CPU/memory/custom metrics
  • VPA: Scale vertically (tăng/giảm resources per Pod) — dựa trên usage history
  • ⚠️ KHÔNG dùng HPA + VPA cùng metric (CPU) — conflicts!
  • ✅ Có thể kết hợp: HPA on custom metrics + VPA on CPU/memory

🔄 Workflow 5: Cluster Autoscaler

Scenario: Pods Pending → Cluster Autoscaler thêm Nodes

sequenceDiagram
    autonumber
    participant HPA as 📈 HPA
    participant RSC as ⚙️ ReplicaSet<br/>Controller
    participant S as 📋 Scheduler
    participant CA as 🖥️ Cluster<br/>Autoscaler
    participant CLOUD as ☁️ Cloud<br/>Provider
    participant KL as 🔧 kubelet

    HPA->>RSC: Scale to 10 replicas

    RSC->>RSC: Create 7 new Pods<br/>(already have 3)

    loop For each new Pod
        S->>S: Try to schedule Pod
        Note over S: ❌ No Node has enough<br/>CPU/Memory!<br/>Events: "0/3 nodes available:<br/>insufficient cpu"
    end

    Note over S: 7 Pods stuck in Pending!

    CA->>CA: Check every 10s:<br/>Pending Pods exist?
    Note over CA: ✅ Found 7 Pending Pods!<br/>Simulate: Would adding Nodes fix it?

    CA->>CLOUD: Request 3 new Nodes<br/>(node group: n2-standard-4)
    CLOUD-->>CA: Provisioning...

    Note over CLOUD: VM creation: ~2-5 min

    CLOUD->>KL: 3 new Nodes ready
    KL->>KL: kubelet registers with<br/>API Server
    Note over S: 👁️ New Nodes available!

    S->>S: Schedule Pending Pods<br/>to new Nodes
    KL->>KL: Start containers

    Note over CA: Later: CPU usage drops<br/>Nodes underutilized<br/>→ Scale DOWN (cordon + drain)

Cluster Autoscaler Decision Flow

flowchart TD
    CHECK["🔍 Check every 10s"] --> PENDING{"Unschedulable<br/>Pods exist?"}

    PENDING -->|"Yes"| SIMULATE["Simulate: Would new Node<br/>allow scheduling?"]
    SIMULATE -->|"Yes"| SCALE_UP["▲ Request new Nodes<br/>from Node Group"]
    SIMULATE -->|"No"| NO_ACTION["Cannot help<br/>(affinity, taints, etc.)"]

    PENDING -->|"No"| UTIL_CHECK{"Node utilization<br/>< threshold?<br/>(default: 50%)"}

    UTIL_CHECK -->|"Yes (underutilized)"| DRAIN_CHECK{"Can Pods be<br/>moved safely?<br/>(check PDB, local storage)"}
    DRAIN_CHECK -->|"Yes"| SCALE_DOWN["▼ Cordon + Drain Node<br/>→ Terminate VM"]
    DRAIN_CHECK -->|"No"| SKIP["⏳ Skip this Node<br/>check again later"]

    UTIL_CHECK -->|"No"| WAIT["⏳ No action<br/>Check again in 10s"]

Scaling Layers 

Layer 1: HPA        — Scale Pods (seconds)
Layer 2: Cluster AS — Scale Nodes (minutes)
Layer 3: VPA        — Right-size Pods (hours/days)

Traffic spike:
1. HPA sees high CPU → Scale Pods: 3 → 10
2. Scheduler: "Not enough Nodes!" → Pods Pending
3. Cluster AS: Add 3 Nodes → ~3 min
4. Scheduler: Place Pending Pods on new Nodes
5. Later: Traffic drops → HPA scale down Pods
6. Later: Cluster AS removes empty Nodes

PDB chỉ bảo vệ voluntary disruptions

  • ✅ Bảo vệ: kubectl drain, cluster autoscaler scale-down, maintenance
  • ❌ KHÔNG bảo vệ: Node crash, OOMKill, hardware failure
  • → PDB + multi-AZ deployment = best availability

🎓 Kiểm Tra Hiểu Biết

Câu 1: Probe Configuration

Tình huống: Java app mất 90s để start, nhưng sau đó rất stable. Bạn cấu hình probes như thế nào?

Xem đáp án

Tại sao startupProbe? Nếu không có nó, livenessProbe sẽ kill app trước khi nó kịp start!

Câu 2: HPA Calculation

Tình huống: HPA target CPU = 60%, min=2, max=15. Hiện tại 4 Pods, CPU avg = 90%. Bao nhiêu replicas?

Xem đáp án 
Formula: desired = ⌈ current × (actual / target) ⌉

desired = ⌈ 4 × (90 / 60) ⌉
        = ⌈ 4 × 1.5 ⌉
        = ⌈ 6.0 ⌉
        = 6

Check bounds: min=2 ≤ 6 ≤ max=15 ✅

→ Scale from 4 → 6 Pods
→ Scale UP immediate (no stabilization delay)

Câu 3: PDB vs kubectl drain

Tình huống: 3 Pods trên Node-1, PDB minAvailable=2. kubectl drain node-1 --timeout=30s. Chuyện gì xảy ra?

Xem đáp án 
Pod 1: Evict OK (3-1=2 ≥ minAvailable=2) ✅
→ Wait for replacement Pod to be Ready...

Pod 2: Can evict? 2-1=1 < minAvailable=2 ❌
→ WAIT until replacement Pod-1 is Ready
→ Then 3-1=2 ≥ 2 ✅, evict Pod 2

Pod 3: Same logic, wait for Pod-2 replacement...

Nếu timeout=30s và replacement Pods chưa kịp Ready:
→ drain command: ERROR - timeout!
→ Node vẫn có Pods (drain chưa hoàn thành)
→ Tăng --timeout hoặc dùng --force (bỏ qua PDB)

--force flag bỏ qua PDB → có thể gây downtime!
