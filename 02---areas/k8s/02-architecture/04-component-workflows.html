2.4. Component Workflows - Luồng Hoạt Động Giữa Các Thành Phần

Chi tiết cách các thành phần Kubernetes phối hợp với nhau trong mọi tình huống

🎯 Mục Tiêu Học

Sau khi học xong phần này, bạn sẽ:

  • ✅ Hiểu luồng hoạt động end-to-end giữa tất cả components
  • ✅ Trace được mọi workflow từ request đến kết quả
  • ✅ Nắm rõ thứ tự tương tác giữa Control Plane và Worker Nodes
  • ✅ Debug được issues bằng cách hiểu flow đang bị stuck ở đâu
  • ✅ Hiểu watch mechanism và event-driven architecture

📋 Tổng Quan Communication Patterns

Nguyên Tắc Giao Tiếp Cốt Lõi

4 Quy Tắc Vàng

  1. MỌI component giao tiếp qua API Server — không ai nói chuyện trực tiếp
  2. CHỈ API Server đọc/ghi etcd — Controllers, Scheduler, kubelet KHÔNG truy cập etcd
  3. Components WATCH API Server cho thay đổi — event-driven, không polling
  4. Mọi thay đổi state: Request → API Server → Validate → etcd → Notify watchers

Chi Tiết Từng Bước

Bước 1-4: API Server xử lý Request

  1. kubectl gửi HTTP POST đến API Server: POST /apis/apps/v1/namespaces/default/deployments
  2. Authentication: Xác minh identity (Client cert? Bearer token? SA token?)
  3. Authorization (RBAC): Kiểm tra quyền — Can user create deployments in default namespace?
  4. Admission Control:
    • MutatingAdmissionWebhook: Add defaults, inject sidecar (Istio), set LimitRange
    • ValidatingAdmissionWebhook: Check PodSecurityStandard, image policy, quotas

Bước 5-6: Lưu vào etcd và Notify

  1. API Server ghi Deployment vào etcd — Key: /registry/deployments/default/webapp
  2. API Server trả HTTP 201 Created → User thấy: deployment.apps/webapp created

Bước 7-8: Deployment Controller tạo ReplicaSet

  1. Deployment Controller (đang watch API Server) phát hiện Deployment mới
    • Tính toán ReplicaSet hash (pod-template-hash)
    • Tạo ReplicaSet webapp-7d8bc4c5d với ownerReferences → Deployment/webapp
  2. API Server lưu ReplicaSet, notify watchers

Bước 9-10: ReplicaSet Controller tạo Pods

  1. ReplicaSet Controller: “Desired: 3, Actual: 0” → Tạo 3 Pod objects
    • Mỗi Pod có ownerReferences → ReplicaSet, status: Pending, spec.nodeName: ""
  2. API Server lưu 3 Pods vào etcd (status: Pending)

Bước 11-12: Scheduler phân công Nodes

  1. Scheduler watch Pods không có nodeName:
    • Filtering: Node đủ CPU/RAM? Taint/toleration? NodeSelector? MaxPods?
    • Scoring: LeastRequested, BalancedResource, SelectorSpread, ImageLocality
    • Binding: Update Pod.spec.nodeName = "worker-X"
  2. API Server cập nhật etcd — Pod vẫn Pending (container chưa running)

Bước 13-15: kubelet khởi động Containers

  1. kubelet trên Worker Node:
    • Init Containers (tuần tự) → Pod Sandbox (network namespace, Pod IP) → Pull image → Create + Start containers → PostStart hook
  2. Health Checks: startupProbe → livenessProbe → readinessProbe
  3. kubelet → API Server: Update Pod status {phase: Running, Ready: True}

Bước 16: kube-proxy cập nhật Network Rules

Endpoints Controller add Pod IP vào Endpoints → kube-proxy update iptables/IPVS → Pod bắt đầu nhận traffic!

Node Failure Recovery

Nếu Node chết (không phải chỉ container crash):

  1. Node Controller detects heartbeat lost (40s) → Mark NotReady
  2. After 5 minutes → Evict Pods, add taint unreachable:NoExecute
  3. ReplicaSet Controller tạo Pods mới → Scheduler đưa lên Nodes khác
  4. → Xem chi tiết tại Workflow 5: Node Failure

Rollback

Deployment Controller lấy ReplicaSet cũ (revision 1), scale UP old RS, scale DOWN current RS — cùng rolling process.

Zero Downtime

Trong suốt quá trình rolling update:

  • Endpoints Controller thêm Pod mới Ready vào Service endpoints
  • Endpoints Controller xóa Pod cũ đang terminate
  • kube-proxy cập nhật iptables → Traffic luôn có healthy backends

Các bước setup Service routing

  1. Service tạo → API Server lưu → ClusterIP assigned (10.96.50.100)
  2. Endpoints Controller watch Services + Pods → tạo Endpoints object với Pod IPs
  3. kube-proxy trên MỌI Node → tạo iptables DNAT rules hoặc IPVS virtual server
  4. CoreDNS watch Services → tạo DNS record backend.default.svc.cluster.local
  5. CNI Plugin routes packet: Same Node → veth pair; Different Node → overlay (VXLAN)

🔄 Workflow 5: Node Failure & Recovery

Scenario: Worker Node mất kết nối (crash, network issue)

Timeline

timeline
    title Node Failure Detection & Recovery Timeline
    
    T=0s : Node stops sending heartbeats
         : kubelet gửi heartbeat mỗi 10s qua NodeLease
    
    T=0-40s : Node Controller chờ heartbeats
            : nodeStatusUpdateFrequency 10s
            : 4 lần miss → trigger
    
    T=40s : Node marked NotReady
          : kubectl get nodes → STATUS=NotReady
          : Endpoints Controller remove Pods từ Service
          : kube-proxy remove iptables rules
    
    T=40s-5min : Grace Period
               : Pods vẫn ghi nhận trên Node cũ
               : Traffic không đến dead Node nữa
    
    T=5min : Pod Eviction
           : Taint unreachable:NoExecute added
           : Pods evicted → Terminating
           : ReplicaSet Controller tạo Pods mới
    
    T=5min+ : Recovery Complete ✅
            : New Pods on healthy Nodes
            : Endpoints + kube-proxy updated

    style HPA fill:#9b59b6,stroke:#8e44ad,color:#fff

Tính toán ví dụ

  • Setup: HPA min=2, max=10, targetCPU=50%, mỗi Pod request 500m CPU
  • Current: 3 Pods — Pod1: 450m (90%), Pod2: 400m (80%), Pod3: 420m (84%)
  • Average: (90 + 80 + 84) / 3 = 84.67%
  • Formula: ceil(3 × (84.67 / 50)) = ceil(5.08) = 6
  • Decision: Scale 3 → 6 Pods (trong giới hạn max=10)

Scale Down Behavior

  • Stabilization window: 5 phút (mặc định) — chờ metrics ổn định
  • Gradual decrease: Không scale down đột ngột, giảm từ từ
  • Tránh “flapping” (scale up/down liên tục)

🔄 Workflow 7: Pod Termination (Graceful Shutdown)

Scenario: kubectl delete pod webapp-abc12

sequenceDiagram
    autonumber
    participant U as 👤 User
    participant API as 🔀 API Server
    participant EP as Endpoints<br/>Controller
    participant KP as kube-proxy
    participant KL as 🔧 kubelet
    participant C as 📦 Container

    U->>API: kubectl delete pod webapp-abc12
    API->>API: Set deletionTimestamp<br/>Set gracePeriod=30s<br/>Status: Terminating

    par Parallel Actions
        API->>EP: Pod has deletionTimestamp
        EP->>KP: Remove Pod IP from Endpoints
        Note over KP: iptables updated<br/>❌ No new traffic
    and
        API->>KL: Pod update notification
        KL->>C: Execute preStop hook
        Note over C: nginx -s quit
        KL->>C: Send SIGTERM (PID 1)
        Note over C: ⏳ Graceful shutdown...<br/>Close connections<br/>Finish in-flight requests<br/>Flush buffers
    end

    alt Container exits within 30s
        C-->>KL: Exit code 0
        Note over C: ✅ Clean shutdown
    else Container still running at 30s
        KL->>C: 💀 Send SIGKILL (force kill)
        Note over C: ❌ Immediate termination
    end

    KL->>API: Pod terminated
    API->>API: Remove Pod from etcd
    Note over API: Pod no longer exists

Grace Period quan trọng!

preStop hook + SIGTERM chia sẻ terminationGracePeriodSeconds!

Ví dụ: gracePeriod = 30s

  • preStop hook mất 25s → SIGTERM chỉ còn 5s trước SIGKILL
  • Nếu app cần 15s để shutdown → tăng terminationGracePeriodSeconds: 60

🎓 Kiểm Tra Hiểu Biết

Câu 1: Trace the Flow

Tình huống: Bạn chạy kubectl scale deployment webapp --replicas=5

Liệt kê THỨ TỰ các components tham gia và actions của chúng.

Xem đáp án 
1. kubectl → API Server: PATCH Deployment (replicas: 5)
2. API Server: Authn → Authz → Admission → Validate
3. API Server → etcd: Update Deployment.spec.replicas = 5
4. Deployment Controller (watch): Detect replicas changed
5. Deployment Controller → API Server: Update ReplicaSet.spec.replicas = 5
6. ReplicaSet Controller (watch): "Desired: 5, Actual: 3"
7. ReplicaSet Controller → API Server: Create 2 new Pods (Pending)
8. API Server → etcd: Save 2 new Pods
9. Scheduler (watch Pending Pods): Assign Pods to Nodes
10. Scheduler → API Server: Update Pod.spec.nodeName
11. kubelet on target Nodes (watch): Pull image, create, start containers
12. kubelet → API Server: Update Pod status (Running, Ready)
13. Endpoints Controller: Add new Pod IPs to Endpoints
14. kube-proxy: Update iptables/IPVS rules
15. → 5 Pods running, receiving traffic ✅

Câu 2: Troubleshooting

Tình huống: Pod stuck ở Pending rất lâu. Dựa vào workflow knowledge, bạn sẽ debug ở đâu?

Xem đáp án

Pod Pending = stuck ở Scheduler phase. Kiểm tra:

Root causes phổ biến

  • Insufficient CPU/Memory trên tất cả Nodes
  • Node taints không có tolerations
  • PVC chưa bound
  • nodeSelector/nodeAffinity không match Node nào
  • Pod priority thấp hơn, bị preempted

Câu 3: Architecture Design

Tình huống: Tại sao tất cả components phải nói chuyện qua API Server thay vì trực tiếp?

Xem đáp án

1. Security — Centralized Auth

  • ✅ Một điểm authentication/authorization + audit logging
  • ❌ Direct: Mỗi component phải tự implement auth

2. Consistency — Single Source of Truth

  • ✅ Tất cả state qua 1 gateway → etcd, optimistic concurrency
  • ❌ Direct: Data inconsistency, race conditions, lost updates

3. Extensibility

  • ✅ Admission webhooks, custom controllers, CRDs sử dụng cùng API
  • ❌ Direct: Hard to extend, tight coupling

4. Watch Mechanism

  • ✅ Efficient event notification, async architecture
  • ❌ Direct: Polling overhead, missed events
