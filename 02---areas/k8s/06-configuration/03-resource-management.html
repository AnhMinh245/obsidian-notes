6.3. Resource Management - Quản Lý Tài Nguyên

Requests, Limits, Quotas — kiểm soát CPU và Memory cho Pods

🎯 Mục Tiêu Học

Sau khi học xong phần này, bạn sẽ:

  • ✅ Hiểu Resource Requests và Limits hoạt động thế nào
  • ✅ Biết QoS Classes (Guaranteed, Burstable, BestEffort) và ảnh hưởng
  • ✅ Cấu hình LimitRange để set defaults cho namespace
  • ✅ Dùng ResourceQuota để giới hạn tổng tài nguyên per namespace
  • ✅ Troubleshoot OOMKilled, CPU throttling, Pending Pods

📦 Tại Sao Cần Resource Management?

Problem: Không giới hạn tài nguyên

Cluster: 3 Nodes, mỗi Node 4 CPU + 16 GB RAM

Scenario 1: Greedy Pod
┌──────────────────────────────────────────────┐
│ Node 1                                        │
│ ┌────────────────────────────────────────┐   │
│ │ Pod A: Memory leak → dùng 15 GB RAM!  │   │
│ └────────────────────────────────────────┘   │
│ ┌──────┐                                     │
│ │Pod B │ → OOMKilled! (hết RAM)             │
│ └──────┘                                     │
│ ┌──────┐                                     │
│ │Pod C │ → OOMKilled!                       │
│ └──────┘                                     │
└──────────────────────────────────────────────┘

❌ 1 Pod "ăn" hết tài nguyên
❌ Các Pods khác bị kill
❌ Node unstable
❌ Không kiểm soát được

Scenario 2: Overcommitment
Dev team deploy 100 Pods, không ai set limits
→ Node overloaded → random Pods bị kill
→ Và không biết Pod nào quan trọng hơn Pod nào!

Solution: Resource Requests & Limits

Cluster: 3 Nodes, mỗi Node 4 CPU + 16 GB RAM

Với Resource Management:
┌──────────────────────────────────────────────┐
│ Node 1: Available 4 CPU, 16 GB               │
│                                               │
│ ┌──────────────────┐  Request: 1 CPU, 2 GB  │
│ │ Pod A            │  Limit:   2 CPU, 4 GB  │
│ │ (OK, within limit)│                        │
│ └──────────────────┘                         │
│                                               │
│ ┌──────────────────┐  Request: 1 CPU, 2 GB  │
│ │ Pod B            │  Limit:   2 CPU, 4 GB  │
│ │ (OK, within limit)│                        │
│ └──────────────────┘                         │
│                                               │
│ Remaining: 2 CPU, 12 GB                      │
│ ✓ Scheduler biết còn bao nhiêu tài nguyên   │
│ ✓ Pod không thể dùng quá limits             │
│ ✓ Node stable!                               │
└──────────────────────────────────────────────┘

🎯 Resource Requests & Limits

Definitions

REQUESTS (Yêu cầu tối thiểu):
├── "Pod cần ÍT NHẤT bao nhiêu tài nguyên để chạy"
├── Scheduler dùng để quyết định đặt Pod ở Node nào
├── Node phải có ĐỦ request resources
└── Guaranteed cho Pod

LIMITS (Giới hạn tối đa):
├── "Pod KHÔNG ĐƯỢC dùng QUÁ bao nhiêu tài nguyên"
├── Container bị throttle (CPU) hoặc kill (Memory) nếu vượt
├── Bảo vệ Node khỏi 1 Pod "ăn" hết tài nguyên
└── Ceiling cho Pod

YAML Example

CPU vs Memory Units

CPU:
├── 1 CPU = 1 vCPU (AWS) / 1 Core (GCP) / 1 Hyperthread
├── 1000m = 1 CPU
├── 500m = 0.5 CPU
├── 100m = 0.1 CPU (minimum practical)
└── 1m = 0.001 CPU (smallest unit)

Memory:
├── Suffixes: Ki, Mi, Gi, Ti (powers of 2)
├── 128Mi = 128 MiB = 134,217,728 bytes
├── 1Gi = 1 GiB = 1,073,741,824 bytes
└── Cũng hỗ trợ: K, M, G (powers of 10, không khuyến khích)

CPU vs Memory Behavior Khi Vượt Limits

CPU vượt limit:
├── Container bị THROTTLE (chậm lại)
├── KHÔNG bị kill
├── Giảm performance nhưng vẫn chạy
└── Giống như internet bị giới hạn bandwidth

Memory vượt limit:
├── Container bị OOMKilled (Out Of Memory)
├── BỊ KILL ngay lập tức!
├── Kubernetes restart container (restartPolicy)
└── Giống như hết RAM → crash

🏷️ QoS Classes (Quality of Service)

K8s tự động phân loại Pods

Kubernetes phân 3 QoS classes dựa trên requests/limits:

1. Guaranteed (Cao nhất)
   ├── Requests = Limits cho TẤT CẢ containers
   ├── Last to be evicted
   └── Dùng cho: Critical workloads (databases, APIs)

2. Burstable (Trung bình)
   ├── Có requests nhưng requests ≠ limits
   ├── Evicted trước Guaranteed
   └── Dùng cho: Hầu hết workloads

3. BestEffort (Thấp nhất)
   ├── KHÔNG có requests VÀ limits
   ├── First to be evicted (bị kill đầu tiên!)
   └── Dùng cho: Non-critical batch jobs

Ví Dụ Từng Class

Eviction Order Khi Node Hết Tài Nguyên

Node Memory Pressure → kubelet evicts Pods

Eviction Order:
1st: BestEffort Pods     → Kill first! (không có guarantee)
2nd: Burstable Pods      → Kill nếu vượt requests
3rd: Guaranteed Pods     → Kill cuối cùng (very rare)

→ Critical workloads PHẢI là Guaranteed!
→ Dev/test có thể là Burstable
→ Batch jobs có thể là BestEffort

📐 LimitRange — Defaults Cho Namespace

Tại Sao Cần?

Problem: Developer quên set resources → Pod là BestEffort → dễ bị kill

LimitRange giải quyết:
├── Set DEFAULT requests/limits cho Pods trong namespace
├── Set MIN/MAX cho containers
├── Enforce policy: "Mọi Pod phải có limits"
└── Per-namespace scope

Ví Dụ LimitRange

📊 ResourceQuota — Giới Hạn Tổng Per Namespace

Tại Sao Cần?

Problem: Team A deploy 100 Pods trong shared cluster
→ Hết tài nguyên, Team B không deploy được

ResourceQuota giải quyết:
├── Giới hạn TỔNG tài nguyên mà 1 namespace có thể dùng
├── Giới hạn SỐ LƯỢNG objects (Pods, Services, ConfigMaps...)
├── Fair sharing giữa các teams
└── Per-namespace scope

Ví Dụ ResourceQuota

⚠️ Quan trọng: Khi ResourceQuota enabled cho namespace, TẤT CẢ Pods PHẢI có requests/limits. Nếu không → Pod bị reject. Kết hợp với LimitRange để auto-set defaults.

💡 Best Practices

🎯 Key Takeaways

  1. Requests = Scheduling guarantee, Limits = Maximum ceiling
  2. CPU vượt limit = throttle (chậm), Memory vượt limit = OOMKilled (chết)
  3. QoS Classes: Guaranteed > Burstable > BestEffort (eviction priority)
  4. LimitRange: Auto-set defaults cho namespace
  5. ResourceQuota: Giới hạn tổng resources per namespace
  6. Production: Luôn set requests/limits, dùng LimitRange + ResourceQuota
