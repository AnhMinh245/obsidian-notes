🔄 Workflow 2: Secret Lifecycle

Scenario: Database password từ creation → encryption → Pod consumption

sequenceDiagram
    autonumber
    participant U as 👤 User
    participant API as 🔀 API Server
    participant ENCRYPT as 🔐 Encryption<br/>Provider
    participant ETCD as 💾 etcd
    participant KL as 🔧 kubelet
    participant C as 📦 Container

    U->>API: kubectl create secret generic db-creds<br/>--from-literal=password=s3cret!
    Note over U: ⚠️ Value gửi dạng plaintext qua HTTPS<br/>Base64 encoded trong object

    API->>API: Validate + Base64 encode<br/>password → czNjcmV0IQ==

    alt Encryption at Rest enabled
        API->>ENCRYPT: Encrypt data before storing
        Note over ENCRYPT: AES-CBC / AES-GCM / KMS
        ENCRYPT-->>API: Encrypted payload
    end

    API->>ETCD: Store Secret (encrypted)
    API-->>U: secret/db-creds created

    Note over KL: Pod starts, references Secret

    KL->>API: Fetch Secret data (HTTPS)
    API->>ETCD: Read Secret
    API->>ENCRYPT: Decrypt
    ENCRYPT-->>API: Decrypted data
    API-->>KL: {password: "czNjcmV0IQ=="}

    alt Volume Mount
        KL->>KL: Base64 decode → plaintext
        KL->>KL: Write to tmpfs (memory-backed)
        KL->>C: Mount at /etc/secrets/password
        Note over C: cat /etc/secrets/password<br/>→ "s3cret!"<br/><br/>tmpfs = in-memory, NOT on disk!
    end

    alt Environment Variable
        KL->>C: Set env: DB_PASSWORD=s3cret!
        Note over C: process.env.DB_PASSWORD<br/>→ "s3cret!"<br/><br/>⚠️ Visible in 'kubectl describe'<br/>⚠️ Visible in /proc/env
    end

Secret Pitfalls

  1. Base64 ≠ Encryption! echo czNjcmV0IQ== | base64 -d → s3cret!
  2. Env vars visible qua kubectl describe pod và /proc/<pid>/environ
  3. Default: etcd stores Secrets unencrypted — phải enable EncryptionConfiguration
  4. Anyone with etcd access = access ALL Secrets

🔄 Workflow 4: OOMKill Decision Flow

Scenario: Node hết memory — Kubernetes quyết định kill Pod nào?

flowchart TD
    PRESSURE["⚠️ Node Memory Pressure!<br/>Available < eviction threshold<br/>(default: 100Mi)"] --> KUBELET["kubelet: Eviction Manager<br/>activated"]

    KUBELET --> SORT["Sort Pods by<br/>eviction priority"]

    SORT --> PHASE1["Phase 1: BestEffort Pods<br/>(no requests/limits)<br/>✂️ Kill first"]
    PHASE1 --> ENOUGH1{"Memory<br/>recovered?"}
    ENOUGH1 -->|"✅ Yes"| STABLE["✅ Node stable"]
    ENOUGH1 -->|"❌ No"| PHASE2

    PHASE2["Phase 2: Burstable Pods<br/>exceeding their requests<br/>✂️ Kill by usage ratio"]
    PHASE2 --> ENOUGH2{"Memory<br/>recovered?"}
    ENOUGH2 -->|"✅ Yes"| STABLE
    ENOUGH2 -->|"❌ No"| PHASE3

    PHASE3["Phase 3: Guaranteed Pods<br/>(only if system critical)<br/>✂️ Last resort"]
    PHASE3 --> STABLE

    subgraph "Burstable Kill Order"
        B_SORT["Within Burstable class:<br/>Sort by (usage - request) / request<br/>= % over request<br/><br/>Pod A: 400Mi used / 200Mi req = 100% over<br/>Pod B: 300Mi used / 256Mi req = 17% over<br/><br/>→ Kill Pod A first (highest over-request ratio)"]
    end

LimitRange vs ResourceQuota

  • LimitRange: Constraints trên từng Pod/Container (min, max, default)
  • ResourceQuota: Constraints trên tổng namespace (total CPU, memory, object count)
  • Cả hai đều enforce qua Admission Controller — Pod bị reject nếu vi phạm!

Immutable ConfigMap Pattern

Why Immutable?

  1. Performance: kubelet stops watching → reduces API Server load
  2. Safety: Prevents accidental changes to production config
  3. Audit: Version history via ConfigMap names (v1, v2, v3…)
  4. Rollback: Just point Deployment back to previous ConfigMap version

🎓 Kiểm Tra Hiểu Biết

Câu 1: ConfigMap Update

Tình huống: Bạn update ConfigMap app-config (LOG_LEVEL: info → debug). Pod A dùng env var, Pod B dùng volume mount. Ai thấy thay đổi?

Xem đáp án
  • Pod A (env var): ❌ Vẫn thấy info — env var frozen tại container start time
    • Fix: kubectl rollout restart deployment/pod-a-deploy
  • Pod B (volume mount): ✅ Sau ~60-120s, file sẽ cập nhật thành debug
    • Nếu app watch file changes (inotify) → auto-reload
    • Nếu không → cần restart app process

Câu 2: QoS Kill Order

Tình huống: Node có 3 Pods. Memory pressure xảy ra. Pod nào bị kill trước?

  • Pod A: Guaranteed (requests=limits=512Mi, using 500Mi)
  • Pod B: Burstable (request=256Mi, limit=1Gi, using 800Mi)
  • Pod C: BestEffort (no resources, using 300Mi)
Xem đáp án

Kill order:

  1. Pod C (BestEffort) — kill đầu tiên, ưu tiên thấp nhất
  2. Pod B (Burstable) — đang dùng 800Mi / request 256Mi = 212% over request!
  3. Pod A (Guaranteed) — kill cuối cùng, chỉ khi system critical

Trong Burstable class, Pod dùng nhiều nhất so với request bị kill trước.

Câu 3: LimitRange Default

Tình huống: Namespace có LimitRange với default CPU limit = 500m. User tạo Pod KHÔNG specify resources. Chuyện gì xảy ra?

Xem đáp án

LimitRange Admission Controller tự động inject defaults:

→ Pod được tạo có resources dù user không specify!
→ QoS class: Burstable (requests ≠ limits)
