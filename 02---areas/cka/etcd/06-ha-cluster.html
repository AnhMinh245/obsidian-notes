etcd HA Cluster

Tại sao HA?

Single-node etcd = single point of failure. Mất node = mất toàn bộ cluster state. Production Kubernetes bắt buộc chạy etcd HA (thường 3 hoặc 5 node).

Raft Consensus — Nền tảng

etcd dùng Raft consensus algorithm để đảm bảo consistency giữa các node.

Các role trong cluster

┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  etcd-1     │   │  etcd-2     │   │  etcd-3     │
│  LEADER     │──→│  FOLLOWER   │   │  FOLLOWER   │
│             │──→│             │   │             │
└─────────────┘   └─────────────┘   └─────────────┘
       │                 ↑                 ↑
       └─────────────────┴─────────────────┘
              Replicate logs (WAL)
RoleNhiệm vụ
LeaderNhận mọi write request, replicate sang followers
FollowerNhận log từ leader, apply vào local state
CandidateNode đang tranh cử leader (khi leader chết)

Write flow

Client → Leader → Replicate → Quorum ACK → Commit → Response
  1. Client gửi write request tới bất kỳ node nào
  2. Nếu node đó là follower → forward tới leader
  3. Leader ghi WAL → replicate sang followers
  4. Khi quorum (majority) ACK → commit
  5. Trả response cho client

Quorum — Khái niệm then chốt

Quorum = majority = (N/2) + 1

Cluster sizeQuorum cầnTolerate failuresKhuyên dùng?
110❌ Dev only
220❌ Tệ hơn 1 node
321✅ Minimum HA
431⚠️ Không tốt hơn 3
532✅ Production lớn
743⚠️ Hiếm khi cần

Tại sao luôn số lẻ?

  • 3 node: tolerate 1 failure (quorum = 2)
  • 4 node: vẫn chỉ tolerate 1 failure (quorum = 3)
  • 4 node tốn thêm resource nhưng không tăng fault tolerance
  • Luôn dùng số lẻ: 3, 5, 7

Cluster 2 node

2 node cần quorum = 2. Mất 1 node → không có quorum → cluster read-only. Tệ hơn 1 node (vì 1 node có quorum = 1, luôn hoạt động).

Failure Scenarios

Scenario 1: Mất 1 node trong cluster 3 node

etcd-1 (LEADER) ✓
etcd-2 (FOLLOWER) ✓
etcd-3 (FOLLOWER) ✗ ← chết

Kết quả: Cluster vẫn hoạt động. Quorum = 2, còn 2 node sống.

Scenario 2: Leader chết

etcd-1 (LEADER) ✗ ← chết
etcd-2 (FOLLOWER) ✓
etcd-3 (FOLLOWER) ✓

Kết quả:

  1. Followers không nhận heartbeat từ leader
  2. Timeout → bầu leader mới (election)
  3. Một trong 2 node thắng → trở thành leader mới
  4. Cluster tiếp tục hoạt động (~1-2 giây downtime)

Scenario 3: Mất quorum (2 trong 3 node chết)

etcd-1 (LEADER) ✗
etcd-2 (FOLLOWER) ✗
etcd-3 (FOLLOWER) ✓ ← sống nhưng vô dụng

Kết quả: Cluster read-only. Không thể write → K8S không thể tạo/update object.

Khôi phục:

  • Phục hồi ít nhất 1 node nữa để có quorum
  • Hoặc restore từ snapshot (xem 04-backup-restore)

Scenario 4: Mất toàn bộ cluster

Kết quả: Mọi data mất. Phải restore từ snapshot backup.

Luôn có backup

Đây là lý do snapshot backup là bắt buộc trong production.

Network Partition (Split-Brain)

┌─────────────────┐     ┌─────────────────┐
│ Partition A     │     │ Partition B     │
│ etcd-1 (LEADER) │  ✗  │ etcd-2          │
│                 │     │ etcd-3          │
└─────────────────┘     └─────────────────┘

Kết quả:

  • Partition B có quorum (2 node) → bầu leader mới → tiếp tục hoạt động
  • Partition A (leader cũ) không có quorum → từ chối write
  • Raft đảm bảo không có split-brain data corruption

Member Management

Liệt kê members

Thêm member mới

Trình tự

  1. Chạy member add trên cluster trước
  2. Rồi mới start etcd trên node mới
  3. Nếu đảo ngược → lỗi cluster ID mismatch

Xóa member

Cẩn thận mất quorum

Đừng xóa member đến mức mất quorum. Ví dụ: cluster 3 node, xóa 1 → còn 2, vẫn OK. Xóa 2 → disaster.

Thay thế member bị hỏng

Learner Member (etcd 3.4+)

Trước khi add member chính thức, có thể add dạng learner để nó sync data trước:

Learner:

  • Nhận log từ leader, sync data
  • Không tham gia quorum (an toàn, không ảnh hưởng cluster)
  • Khi sync xong, promote thành member:

Best practice

Luôn add member mới dạng learner trước, chờ sync xong rồi promote. Tránh trường hợp member mới chưa có data mà đã tính vào quorum.
