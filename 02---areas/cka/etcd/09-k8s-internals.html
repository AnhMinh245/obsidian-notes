Mục tiêu

Hiểu cách Kubernetes thật sự lưu trữ object trong etcd. Không phải lý thuyết — đọc raw data trực tiếp.

Kubernetes dùng etcd như thế nào?

kubectl create deployment nginx --image=nginx
         │
         ↓
    kube-apiserver
         │
         ↓ (serialize → protobuf/json)
         │
    etcd: /registry/deployments/default/nginx

Key path convention

/registry/<resource-type>/<namespace>/<name>

Ví dụ:

K8S Objectetcd Key
Pod nginx trong default/registry/pods/default/nginx
Deployment web trong prod/registry/deployments/prod/web
Secret db-creds trong default/registry/secrets/default/db-creds
Node worker-1/registry/minions/worker-1
Namespace kube-system/registry/namespaces/kube-system
ClusterRole admin/registry/clusterroles/admin
ServiceAccount default/registry/serviceaccounts/default/default

minions chứ không phải nodes

Vì lý do lịch sử, Nodes được lưu ở path /registry/minions/ (tên cũ của Node trong K8S).

Event System trong etcd

Mỗi khi K8S object thay đổi:

kubectl edit deployment nginx
         │
         ↓
    apiserver ghi vào etcd
         │
         ↓
    etcd tăng mod_revision
         │
         ↓
    watch stream gửi event
         │
         ↓
    controller nhận event → reconcile

Kubernetes Informer Pattern

┌─────────────┐   watch    ┌────────────┐   event   ┌──────────────┐
│ etcd        │ ─────────→ │ apiserver  │ ────────→ │ controller   │
│ (storage)   │            │ (watch     │           │ (informer +  │
│             │            │  cache)    │           │  work queue) │
└─────────────┘            └────────────┘           └──────────────┘
  • apiserver watch etcd (dùng mod_revision làm cursor)
  • Controller watch apiserver (dùng resourceVersion)
  • resourceVersion trong K8S = mod_revision trong etcd

Tại sao etcd chứ không phải database khác?

Yêu cầuetcdPostgreSQLRedis
Strong consistency✅ Raft✅ ACID❌ Eventual
Native watch✅ Built-in❌ Cần extension⚠️ Pub/sub (khác)
Distributed✅ Multi-node⚠️ Replication⚠️ Cluster mode
Lease/TTL✅ Native❌✅ EXPIRE
Transaction (CAS)✅ Native✅ SQL transactions❌
Designed for config✅❌ General purpose❌ Cache

Kết luận

etcd được thiết kế chuyên biệt cho distributed configuration và coordination. Không có database nào khác cung cấp đầy đủ: strong consistency + watch + lease + CAS trong cùng một package đơn giản.

Security Implications

Ai access được etcd = admin cluster

etcd access → đọc tất cả Secrets, ConfigMaps, RBAC rules
           → sửa tất cả Pods, Deployments, Services
           → xóa tất cả data → cluster chết

Best practices

  • Giới hạn network access — chỉ apiserver được connect tới etcd
  • TLS everywhere — encrypt mọi traffic (client + peer)
  • Client cert auth — không dùng password auth
  • Encrypt at rest — xem 05-encryption
  • Restrict file permissions — cert files chmod 600
  • Backup encryption — snapshot cũng chứa sensitive data
  • Separate etcd network — VLAN riêng cho etcd traffic nếu có thể
