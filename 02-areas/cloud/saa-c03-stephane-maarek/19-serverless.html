1. Serverless là gì?

  • Paradigm mà developer không còn quản lý server — chỉ deploy code / function
  • Ban đầu: Serverless == FaaS (Function as a Service), khai sinh bởi AWS Lambda
  • Hiện nay mở rộng cho mọi dịch vụ managed: database, messaging, storage…

Hiểu đúng: Serverless không có nghĩa là không có server. Server vẫn tồn tại — chỉ là bạn không provision, không quản lý, không nhìn thấy chúng. AWS lo hết phần đó.

1.1 Các dịch vụ Serverless trên AWS

Nhóm Dịch vụ
Compute AWS Lambda, AWS Fargate
Database DynamoDB, Aurora Serverless
Storage Amazon S3
API / Auth API Gateway, Amazon Cognito
Messaging SNS, SQS, Kinesis Data Firehose
Orchestration AWS Step Functions

2. AWS Lambda — nền tảng của Serverless

2.1 Vì sao dùng Lambda thay EC2?

Amazon EC2 AWS Lambda
Bản chất Virtual server trên cloud Virtual function — không có server để quản lý
Giới hạn Bị giới hạn bởi RAM & CPU Bị giới hạn bởi thời gian — chỉ chạy ngắn (tối đa 15 phút)
Vòng đời Chạy liên tục (trả tiền kể cả lúc rảnh) Chạy on-demand — chỉ khi được gọi
Scaling Phải can thiệp (thêm/bớt server) Tự động hoàn toàn

2.2 Lợi ích chính

  • Pricing đơn giản: trả theo số request + thời gian compute
    • Free tier: 1.000.000 request và 400.000 GB-giây compute mỗi tháng
  • Tích hợp sẵn với gần như toàn bộ hệ sinh thái AWS
  • Hỗ trợ nhiều ngôn ngữ lập trình
  • Monitoring dễ dàng qua CloudWatch
  • Tăng tài nguyên đơn giản — lên tới 10 GB RAM/function

Điểm quan trọng hay ra thi: Trong Lambda bạn chỉ chỉnh được RAM, không chỉnh CPU trực tiếp. Tăng RAM → CPU và network cũng tăng theo. Vì vậy câu hỏi kiểu "function chạy chậm vì CPU-bound, làm sao tăng tốc?" → tăng memory allocation.

2.3 Ngôn ngữ được hỗ trợ

  • Node.js (JavaScript), Python, Java, C# (.NET) / PowerShell, Ruby
  • Custom Runtime API — community support (ví dụ Rust, Golang)
  • Lambda Container Image — image phải implement Lambda Runtime API

Bẫy thi: Muốn chạy một Docker image bất kỳ (không implement Lambda Runtime API) → dùng ECS / Fargate, KHÔNG phải Lambda. Lambda container image chỉ dành cho image được viết theo chuẩn Lambda.

2.4 Các tích hợp chính

Ví dụ 1 — Tạo thumbnail serverless: Upload ảnh lên S3 → S3 Event trigger Lambda → Lambda resize ảnh → ghi thumbnail vào S3 + metadata vào DynamoDB.

Ví dụ 2 — CRON job serverless: EventBridge Schedule (rate/cron expression) → trigger Lambda định kỳ. Thay thế cron server chạy 24/7 → chỉ trả tiền vài giây mỗi lần chạy.

3. Ba cách Lambda được gọi (Invocation Types)

Đây là nền tảng để hiểu phần throttling & retry ở §4 — rất hay bị bỏ qua.

Kiểu gọi Ai gọi Hành vi khi lỗi
Synchronous API Gateway, ALB, gọi trực tiếp qua CLI/SDK Client tự retry — Lambda trả lỗi về ngay
Asynchronous S3 Events, SNS, EventBridge Lambda tự retry 2 lần (tổng 3 lần), rồi đẩy vào DLQ / Destinations
Event Source Mapping (Lambda tự poll) SQS, Kinesis Data Streams, DynamoDB Streams Lambda poll nguồn, xử lý theo batch

Lambda Destinations (mới hơn DLQ): định tuyến kết quả cả thành công lẫn thất bại tới SQS/SNS/Lambda/EventBridge. AWS khuyến nghị dùng Destinations thay DLQ vì linh hoạt hơn.

4. Concurrency, Throttling & Cold Start

4.1 Concurrency limit & Throttling

  • Giới hạn mặc định: 1.000 concurrent executions / region (dùng chung cho mọi function trong region đó)
  • Có thể đặt Reserved Concurrency ở mức từng function (= vừa đảm bảo vừa giới hạn)
  • Mỗi lần gọi vượt quá giới hạn → bị Throttle

Kiểu gọi khi bị throttle Hành vi
Synchronous Trả về lỗi ThrottleError – HTTP 429 ngay
Asynchronous Tự retry, sau đó đẩy vào DLQ

Cần giới hạn cao hơn 1.000 → mở support ticket xin tăng quota.

4.2 Vấn đề khi KHÔNG đặt Reserved Concurrency

Nếu không "đặt chỗ" concurrency, một function bị traffic spike có thể ăn hết 1.000 slot của cả region → các function khác (kể cả function quan trọng) bị throttle theo. Đây là kiểu "hàng xóm ồn ào" (noisy neighbour) trong Lambda.

Cách xử lý: đặt Reserved Concurrency cho từng function → mỗi function có phần riêng, không giẫm chân nhau.

4.3 Concurrency với Asynchronous Invocation

  • Nếu function không đủ concurrency để xử lý hết event → request bị throttle
  • Với lỗi throttling (429) và lỗi hệ thống (5xx), Lambda trả event về queue và thử lại trong tối đa 6 giờ
  • Khoảng cách retry tăng theo cấp số nhân (exponential backoff): từ 1 giây sau lần đầu, tối đa 5 phút

4.4 Cold Start & Provisioned Concurrency

Cold Start là gì?

  • Instance mới được tạo → phải load code và chạy phần ngoài handler (init)
  • Init nặng (nhiều dependency, SDK…) → mất thời gian đáng kể
  • → Request đầu tiên vào instance mới có latency cao hơn các request sau

Provisioned Concurrency — cách khắc phục:

  • Concurrency được cấp phát trước khi function được gọi
  • → Cold start không bao giờ xảy ra, mọi invocation đều low-latency
  • Application Auto Scaling có thể quản lý mức này (theo lịch hoặc target utilization)

Cold start trong VPC đã được cải thiện rất nhiều từ tháng 10–11/2019 (Lambda dùng ENI dùng chung thay vì tạo ENI mỗi lần) — không còn là lý do lớn để tránh Lambda-in-VPC nữa.

4.5 Reserved vs Provisioned Concurrency — đừng nhầm

Reserved Concurrency Provisioned Concurrency
Mục đích Chia phần concurrency giữa các function Loại bỏ cold start
Cơ chế Đặt trần (và sàn) số concurrent execution Khởi tạo sẵn N instance đã "warm"
Chi phí Miễn phí Tính phí (trả tiền cho instance giữ sẵn)
Giải quyết Function này không "ăn" hết quota của function khác Latency ổn định cho workload nhạy cảm

4.6 Lambda SnapStart

  • Cải thiện performance tới 10 lần, không tốn thêm phí — cho Java, Python, .NET
  • Khi bật: function được gọi từ trạng thái đã khởi tạo sẵn (không init lại từ đầu)
  • Cơ chế khi publish version mới:
    1. Lambda khởi tạo function
    2. Chụp snapshot của memory + disk state sau khởi tạo
    3. Snapshot được cache để truy cập với latency thấp

SnapStart vs Provisioned Concurrency: SnapStart miễn phí nhưng chỉ hỗ trợ Java/Python/.NET; Provisioned Concurrency tính phí nhưng dùng được cho mọi runtime. Đề thi hỏi "giảm cold start không tăng chi phí" → SnapStart.

5. Customization at the Edge — chạy code sát người dùng

5.1 Edge Function là gì?

  • Code bạn viết và gắn vào CloudFront distribution
  • Chạy gần người dùng → giảm latency tối đa
  • CloudFront cung cấp 2 loại: CloudFront Functions và Lambda@Edge
  • Không quản lý server nào, deploy toàn cầu, trả tiền theo mức dùng — fully serverless

Use case chung: bảo mật & quyền riêng tư website, dynamic web app tại edge, SEO, định tuyến thông minh giữa các origin/data center, chống bot, biến đổi ảnh real-time, A/B testing, xác thực & phân quyền user, ưu tiên user, tracking & analytics.

5.2 CloudFront Functions

  • Function nhẹ, viết bằng JavaScript
  • Dành cho customization CDN quy mô lớn, cực nhạy latency
  • Startup dưới 1 ms, chịu được hàng triệu request/giây
  • Chỉ can thiệp được 2 điểm:
    • Viewer Request — sau khi CloudFront nhận request từ viewer
    • Viewer Response — trước khi CloudFront trả response về viewer
  • Là tính năng native của CloudFront (quản lý code hoàn toàn trong CloudFront)

5.3 Lambda@Edge

  • Lambda function viết bằng Node.js hoặc Python
  • Scale tới hàng nghìn request/giây
  • Can thiệp được cả 4 điểm trong vòng đời request:
    • Viewer Request — sau khi CloudFront nhận request từ viewer
    • Origin Request — trước khi CloudFront gửi request tới origin
    • Origin Response — sau khi CloudFront nhận response từ origin
    • Viewer Response — trước khi CloudFront trả về viewer
  • Viết function ở một region duy nhất: us-east-1, CloudFront tự replicate ra các edge location

CloudFront Functions chỉ chạm được bước (1) và (4). Lambda@Edge chạm được cả (1)(2)(3)(4).

5.4 So sánh CloudFront Functions vs Lambda@Edge

Tiêu chí CloudFront Functions Lambda@Edge
Runtime JavaScript (thuần) Node.js, Python
Scale Triệu request/giây Nghìn request/giây
Thời gian chạy < 1 ms Vài ms (dài hơn)
Trigger Viewer Request/Response Viewer + Origin Request/Response
Truy cập network Không Có (gọi được service khác)
Truy cập file system / body của request Không Có
Thư viện bên thứ 3 (vd AWS SDK) Không Có
CPU / Memory Cố định Điều chỉnh được
Chi phí Rẻ hơn nhiều Đắt hơn
Deploy Native trong CloudFront Viết ở us-east-1, tự replicate

Dùng CloudFront Functions khi:

  • Chuẩn hoá cache key — biến đổi header/cookie/query string/URL để tạo Cache Key tối ưu
  • Thao tác header — thêm/sửa/xoá HTTP header trong request hoặc response
  • URL rewrite / redirect
  • Xác thực & phân quyền request — tạo và validate token do user sinh (ví dụ JWT) để cho phép/từ chối request

Dùng Lambda@Edge khi:

  • Cần thời gian chạy dài hơn (vài ms)
  • Cần điều chỉnh CPU hoặc memory
  • Code phụ thuộc thư viện bên thứ 3 (vd AWS SDK để gọi service khác)
  • Cần truy cập network ra ngoài để xử lý
  • Cần truy cập file system hoặc đọc body của HTTP request

6. Lambda & Networking

6.1 Lambda mặc định — nằm NGOÀI VPC của bạn

  • Mặc định Lambda chạy trong một VPC do AWS sở hữu
  • → Không truy cập được tài nguyên trong VPC của bạn (RDS, ElastiCache, internal ELB…)

6.2 Lambda trong VPC

  • Phải khai báo VPC ID, Subnets, và Security Groups
  • Lambda sẽ tạo ENI (Elastic Network Interface) trong subnet của bạn

Lưu ý quan trọng: Lambda đặt trong private subnet sẽ mất kết nối Internet (kể cả gọi API AWS public như S3, DynamoDB). Muốn có Internet → cần NAT Gateway; muốn gọi service AWS mà không qua Internet → dùng VPC Endpoint. Đây là bẫy rất hay gặp.

6.3 Lambda với RDS Proxy

Vấn đề: Lambda scale tự động → dưới tải cao có thể mở quá nhiều connection tới database, làm DB quá tải.

RDS Proxy giải quyết:

Lợi ích Chi tiết
Scalability Pool và share connection tới DB thay vì mỗi Lambda mở riêng
Availability Giảm 66% thời gian failover và giữ nguyên connection khi failover
Security Bắt buộc IAM authentication, lưu credential trong Secrets Manager

Bắt buộc: Lambda phải được deploy trong VPC của bạn, vì RDS Proxy không bao giờ truy cập được công khai (never publicly accessible).

6.4 Gọi Lambda TỪ RDS & Aurora (chiều ngược lại)

  • Invoke Lambda function từ bên trong DB instance
  • Cho phép xử lý data event ngay trong database
  • Chỉ hỗ trợ RDS for PostgreSQL và Aurora MySQL
  • Yêu cầu:
    • DB instance phải có outbound traffic tới Lambda (qua Public, NAT Gateway, hoặc VPC Endpoint)
    • DB instance phải có đủ quyền (Lambda Resource-based Policy + IAM Policy)

6.5 RDS Event Notifications

  • Thông báo về bản thân DB instance (created, stopped, started…)
  • Không cho biết gì về dữ liệu bên trong — muốn theo dõi dữ liệu phải dùng cách khác (vd Lambda invocation ở §6.4)
  • Subscribe theo các nhóm event: DB instance, DB snapshot, DB Parameter Group, DB Security Group, RDS Proxy, Custom Engine Version
  • Near real-time — độ trễ tới 5 phút
  • Gửi thông báo tới SNS, hoặc subscribe event qua EventBridge

7. Amazon DynamoDB — NoSQL serverless

7.1 Tổng quan

  • Fully managed, highly available với replication qua nhiều AZ (mặc định 3 AZ)
  • Database NoSQL — không phải relational — nhưng có hỗ trợ transaction
  • Scale tới khối lượng khổng lồ, database phân tán:
    • Hàng triệu request/giây, hàng nghìn tỷ dòng, hàng trăm TB dữ liệu
  • Performance nhanh và ổn định — latency single-digit millisecond
  • Tích hợp IAM cho security/authorization/administration
  • Chi phí thấp, có auto-scaling
  • Không cần maintenance hay patching, luôn sẵn sàng
  • Có 2 Table Class: Standard và Infrequent Access (IA) — IA rẻ hơn khi dữ liệu ít truy cập

7.2 Kiến thức cơ bản

  • DynamoDB gồm nhiều Table
  • Mỗi table có một Primary Key — phải quyết định lúc tạo table, không đổi được sau
  • Mỗi table chứa số lượng item (= dòng) không giới hạn
  • Mỗi item có các attribute — có thể thêm dần theo thời gian, có thể null
  • Kích thước tối đa của 1 item: 400 KB
  • Kiểu dữ liệu hỗ trợ:
    • Scalar Types — String, Number, Binary, Boolean, Null
    • Document Types — List, Map
    • Set Types — String Set, Number Set, Binary Set
  • → Nhờ vậy DynamoDB cho phép thay đổi schema rất nhanh (schema-less)

Item > 400 KB? Giống pattern claim-check của SQS — lưu payload lớn lên S3, chỉ giữ pointer (S3 key) trong DynamoDB.

7.3 Read/Write Capacity Modes

Kiểm soát cách quản lý throughput (read/write) của table:

Provisioned Mode (mặc định) On-Demand Mode
Cách hoạt động Bạn tự chỉ định số read/write mỗi giây Tự động scale up/down theo workload
Lập kế hoạch Phải plan capacity trước Không cần plan gì cả
Trả tiền Theo RCU (Read Capacity Unit) & WCU (Write Capacity Unit) đã provision Trả theo thực tế dùng — đắt hơn
Auto-scaling Có thể bật auto-scaling cho RCU & WCU Có sẵn
Phù hợp Workload ổn định, dự đoán được Workload không dự đoán được, spike đột ngột

Tình huống thi: "traffic không dự đoán được / spike bất chợt / mới launch chưa biết tải" → On-Demand. "Traffic ổn định, muốn tối ưu chi phí" → Provisioned + Auto Scaling.

7.4 DynamoDB Accelerator (DAX)

  • Cache in-memory cho DynamoDB: fully managed, highly available, seamless
  • Giải quyết vấn đề nghẽn đọc (read congestion) bằng cách cache
  • Latency ở mức microsecond cho dữ liệu đã cache (so với millisecond của DynamoDB)
  • Không cần sửa logic ứng dụng — tương thích với API DynamoDB hiện có
  • TTL cache mặc định: 5 phút

DAX vs ElastiCache:

DAX ElastiCache
Cache cái gì Từng object / kết quả Query & Scan của DynamoDB Kết quả tổng hợp (aggregation), kết quả tính toán phức tạp
Sửa code Không cần (tương thích API DynamoDB) Phải sửa code để đọc/ghi cache
Dùng khi Chỉ cache DynamoDB Cache cho bất kỳ nguồn nào (RDS, kết quả tính toán…)

Bẫy thi: cả hai đều là cache, nhưng câu hỏi có chữ "không muốn sửa application code" + DynamoDB → chọn DAX. Câu hỏi có "lưu kết quả aggregation/leaderboard/session" → chọn ElastiCache.

7.5 DynamoDB Streams — bắt thay đổi dữ liệu

  • Luồng có thứ tự các thay đổi ở mức item (create/update/delete) trong table
  • Use case:
    • Phản ứng thay đổi real-time (vd gửi email chào mừng khi có user mới)
    • Analytics real-time
    • Insert vào các bảng phái sinh (derivative tables)
    • Triển khai cross-region replication
    • Gọi AWS Lambda khi table thay đổi

Hai lựa chọn stream:

DynamoDB Streams Kinesis Data Streams (mới hơn)
Retention 24 giờ 1 năm
Số consumer Hạn chế Nhiều
Cách xử lý Lambda Trigger, hoặc DynamoDB Stream Kinesis adapter Lambda, Kinesis Data Analytics, Kinesis Data Firehose, AWS Glue Streaming ETL…

7.6 DynamoDB Global Tables

  • Cho phép truy cập table với latency thấp ở nhiều region
  • Replication Active-Active: app có thể READ và WRITE ở bất kỳ region nào
  • Điều kiện tiên quyết: phải bật DynamoDB Streams

Tình huống thi: "user toàn cầu, cần đọc và ghi với latency thấp ở nhiều region" → Global Tables. (Khác Aurora Global Database — chỉ ghi được ở primary region.)

7.7 Time To Live (TTL)

  • Tự động xoá item sau một timestamp hết hạn
  • Use case: giảm dữ liệu lưu trữ (chỉ giữ item còn hiệu lực), tuân thủ quy định pháp lý, quản lý web session

7.8 Backup cho disaster recovery

Loại backup Chi tiết
Continuous backups — Point-in-Time Recovery (PITR) Bật tuỳ chọn cho 35 ngày gần nhất; khôi phục về bất kỳ thời điểm nào trong cửa sổ đó
On-demand backups Backup đầy đủ, giữ lâu dài cho tới khi bị xoá thủ công; không ảnh hưởng performance/latency; quản lý được qua AWS Backup (hỗ trợ copy cross-region)

Cả hai cách khôi phục đều tạo ra một table MỚI, không ghi đè lên table cũ.

7.9 Tích hợp với Amazon S3

Export to S3 (bắt buộc bật PITR):

  • Export được bất kỳ thời điểm nào trong 35 ngày gần nhất
  • Không tiêu tốn read capacity của table
  • Dùng để: phân tích dữ liệu trên DynamoDB, giữ snapshot phục vụ audit, ETL trên S3 rồi import ngược lại
  • Định dạng export: DynamoDB JSON hoặc ION

Import from S3:

  • Import được CSV, DynamoDB JSON, hoặc ION
  • Không tiêu tốn write capacity
  • Tạo ra một table mới
  • Lỗi import được ghi vào CloudWatch Logs

8. Amazon API Gateway

8.1 Vai trò & tính năng

Cửa ngõ để expose Lambda (và các backend khác) ra thành REST/WebSocket API.

  • Lambda + API Gateway = không có hạ tầng nào phải quản lý
  • Hỗ trợ WebSocket Protocol
  • Quản lý versioning API (v1, v2…) và nhiều môi trường (dev, test, prod…)
  • Xử lý security (Authentication & Authorization)
  • Tạo API keys, throttling request
  • Import Swagger / OpenAPI để định nghĩa API nhanh
  • Transform và validate request/response
  • Sinh SDK và API specification
  • Cache response của API

AWS Service Expose bất kỳ AWS API nào qua API Gateway (vd start Step Functions workflow, gửi message vào SQS) Thêm authentication, deploy public, kiểm soát rate…

8.3 Endpoint Types

Loại Đặc điểm
Edge-Optimized (mặc định) Cho client toàn cầu. Request đi qua CloudFront Edge location → giảm latency. API Gateway vẫn chỉ nằm ở 1 region
Regional Cho client trong cùng region. Có thể tự kết hợp CloudFront để kiểm soát caching & distribution chi tiết hơn

Hiểu đúng Edge-Optimized: nó không replicate API ra nhiều region — chỉ dùng mạng CloudFront để rút ngắn đường đi. Bản thân API Gateway vẫn ở một region duy nhất.

9. AWS Step Functions — điều phối workflow

  • Xây dựng workflow trực quan (visual) serverless để orchestrate các Lambda function
  • Tính năng: chạy tuần tự (sequence), song song (parallel), điều kiện (conditions), timeout, xử lý lỗi (error handling)…
  • Tích hợp được với EC2, ECS, server on-premises, API Gateway, SQS queue…
  • Hỗ trợ bước human approval (chờ người duyệt)
  • Use case: xử lý đơn hàng (order fulfillment), data processing, web application, bất kỳ workflow nào

Hai loại workflow (hay ra thi):

Standard Workflow Express Workflow
Thời gian chạy tối đa 1 năm 5 phút
Mô hình thực thi Exactly-once At-least-once (Async) / At-most-once (Sync)
Tốc độ ~2.000 execution/giây Trên 100.000 execution/giây
Lịch sử execution Xem được trong Step Functions API Gửi vào CloudWatch Logs
Trả tiền theo Số state transition Số request + thời gian chạy
Phù hợp Workflow dài, cần audit đầy đủ Xử lý event lượng lớn, chạy ngắn (IoT, streaming)

Vì sao dùng Step Functions thay vì để Lambda gọi Lambda? Vì Step Functions lo giúp retry, error handling, state, và cho phép nhìn thấy workflow đang ở bước nào — Lambda gọi Lambda thì logic đó phải tự viết và rất khó debug.

10. Amazon Cognito — identity cho user

Cung cấp identity để user tương tác với web/mobile app của bạn.

10.1 Hai thành phần — phân biệt cho rõ

Cognito User Pools (CUP) Cognito Identity Pools (Federated Identities)
Trả lời câu hỏi "Bạn là ai?" (Authentication) "Bạn được làm gì trên AWS?" (Authorization)
Cung cấp Chức năng sign-in cho app user AWS credentials tạm thời để user truy cập thẳng tài nguyên AWS
Tích hợp với API Gateway & Application Load Balancer Cognito User Pools (làm identity provider), login bên thứ 3

Cognito vs IAM: thấy các cụm từ "hàng trăm/hàng triệu user", "mobile users", "authenticate với SAML" → nghĩ ngay tới Cognito, không phải IAM. IAM dùng cho user/service nội bộ AWS, không scale cho end-user của ứng dụng.

10.2 Cognito User Pools (CUP) — tính năng

  • Tạo database serverless chứa user cho web & mobile app
  • Đăng nhập đơn giản: Username (hoặc email) / password
  • Reset password
  • Xác minh Email & số điện thoại
  • Multi-factor authentication (MFA)
  • Federated Identities: user từ Facebook, Google, SAML…

10.3 Cognito Identity Pools (Federated Identities)

  • Cấp identity cho "user" để họ nhận được AWS credentials tạm thời

Điểm hay ra thi

  • Serverless ≠ không có server — chỉ là không quản lý server.
  • Lambda: chỉ chỉnh RAM (128 MB – 10 GB), CPU/network tăng theo RAM; timeout tối đa 15 phút; /tmp 512 MB – 10 GB; deployment zip 50 MB / giải nén 250 MB; concurrency mặc định 1.000/region.
  • Payload: sync 6 MB, async 256 KB.
  • 3 kiểu invoke: sync (client retry) / async (Lambda retry 2 lần → DLQ) / event source mapping (Lambda poll SQS, Kinesis, DynamoDB Streams).
  • Throttle: sync → 429 ThrottleError; async → retry, tối đa 6 giờ, backoff từ 1 giây tới 5 phút.
  • Reserved Concurrency (chia quota, miễn phí) ≠ Provisioned Concurrency (diệt cold start, tính phí) ≠ SnapStart (diệt cold start, miễn phí, chỉ Java/Python/.NET).
  • CloudFront Functions: JS, sub-ms, chỉ Viewer Request/Response, không network/SDK. Lambda@Edge: Node/Python, cả 4 trigger, có network/SDK, viết ở us-east-1.
  • Lambda mặc định ngoài VPC của bạn; đưa vào VPC thì mất Internet → cần NAT GW hoặc VPC Endpoint.
  • RDS Proxy không public → Lambda bắt buộc phải trong VPC; giảm 66% thời gian failover.
  • DynamoDB: item tối đa 400 KB; Primary Key chọn lúc tạo không đổi được; Provisioned vs On-Demand; DAX cache 5 phút TTL, không sửa code; Streams 24h vs Kinesis Data Streams 1 năm; Global Tables cần bật Streams; PITR 35 ngày; export/import S3 không tốn capacity và tạo table mới.
  • API Gateway: 3 endpoint type (Edge-Optimized / Regional / Private); ACM cert cho Edge-Optimized phải ở us-east-1; auth qua IAM / Cognito / Custom Authorizer.
  • Step Functions: Standard (1 năm, exactly-once) vs Express (5 phút, throughput cực cao).
  • Cognito User Pools = authentication (bạn là ai) ≠ Identity Pools = AWS credentials tạm (bạn làm được gì).

Takeaway cá nhân

  • Mạch học Serverless: compute (Lambda) → data (DynamoDB) → cửa vào (API Gateway) → điều phối (Step Functions) → danh tính (Cognito).
  • Lambda bị loại khỏi đáp án chủ yếu vì 2 lý do: chạy quá 15 phút, hoặc cần chạy Docker image tuỳ ý. Nhớ 2 cái này là loại nhanh được nhiều đáp án sai.
  • 3 cơ chế "concurrency" của Lambda rất dễ lẫn — mẹo nhớ: Reserved = chia phần, Provisioned = giữ chỗ nóng sẵn, SnapStart = chụp ảnh trạng thái.
  • DynamoDB không phải "RDS phiên bản NoSQL" — thiết kế xoay quanh access pattern và Primary Key chọn một lần là xong, khác hẳn tư duy relational.
  • Cognito User Pools vs Identity Pools: cứ hỏi "đang nói về đăng nhập, hay đang nói về quyền gọi AWS API?" là chọn đúng.
