Cách đọc note này: (0) Ba câu hỏi khác nhau mà ba dịch vụ trả lời → (1) CloudWatch (performance/monitoring) → (2) CloudTrail (audit — ai làm gì) → (3) Config (compliance — cấu hình có đúng chuẩn không, thay đổi theo thời gian) → (4) Bảng so sánh → (5) Case study "For an ELB" → (6) So sánh & chọn đáp án thi.

0. Ba dịch vụ, ba câu hỏi khác nhau

Đây là điểm dễ nhầm nhất của cả bài: cả ba đều dính tới "theo dõi" hệ thống, nhưng mỗi dịch vụ trả lời một câu hỏi hoàn toàn khác:

Dịch vụ Câu hỏi nó trả lời Ví dụ
CloudWatch "Hệ thống đang chạy như thế nào?" (performance) CPU đang bao nhiêu %? Có bao nhiêu lỗi 5xx trong 1 giờ qua?
CloudTrail "Ai đã làm gì, khi nào?" (audit) Ai xoá bucket này? Ai gọi API DeleteTable?
Config "Cấu hình hiện tại có đúng chuẩn không, và nó đã đổi ra sao theo thời gian?" (compliance) Security Group này có đang mở SSH cho 0.0.0.0/0 không? Cấu hình ALB tuần trước khác tuần này thế nào?

Ghi nhớ nhanh: CloudWatch nhìn vào số liệu/log runtime. CloudTrail nhìn vào API call. Config nhìn vào trạng thái cấu hình (snapshot theo thời gian + có tuân thủ rule hay không). Ba dịch vụ này bổ sung cho nhau, không thay thế nhau — một hệ thống production nghiêm túc dùng cả ba.

1. Amazon CloudWatch — performance monitoring

1.1 CloudWatch Metrics

  • Metric = một biến số được theo dõi (CPUUtilization, NetworkIn…) — CloudWatch cung cấp metric cho mọi service AWS
  • Metric thuộc về một namespace (gom nhóm theo service/ứng dụng)
  • Dimension = thuộc tính của metric (instance id, environment…) — tối đa 30 dimension/metric
  • Metric luôn có timestamp
  • Dựng được CloudWatch Dashboard từ metric
  • Custom Metrics: metric AWS không tự cung cấp sẵn (ví dụ RAM — CloudWatch mặc định KHÔNG có metric RAM cho EC2, phải tự đẩy lên)

1.2 CloudWatch Metric Streams — đẩy metric ra ngoài gần thời gian thực

  • Stream liên tục metric CloudWatch tới đích mong muốn, độ trễ thấp, near-real-time
  • Đích: Kinesis Data Firehose (rồi đi tiếp S3, Redshift, Athena, OpenSearch) hoặc 3rd-party (Datadog, Dynatrace, New Relic, Splunk, Sumo Logic…)
  • Có thể filter để chỉ stream một tập con metric, không cần đẩy hết

Đây chính là cách kết nối CloudWatch với các công cụ observability ngoài AWS như Dynatrace — hợp với domain observability trong vault này.

1.3 CloudWatch Logs

  • Log Group: tên tuỳ ý, thường đại diện cho một ứng dụng
  • Log Stream: các instance/log file/container bên trong một log group
  • Đặt được retention policy (never expire, từ 1 ngày đến 10 năm)
  • Log group gửi được sang: S3 (export), Kinesis Data Streams, Kinesis Data Firehose, Lambda, OpenSearch
  • Mã hoá mặc định; đặt được KMS key riêng nếu cần

Nguồn log — ai đẩy log vào CloudWatch Logs:

Nguồn Ghi chú
SDK, CloudWatch Logs Agent, CloudWatch Unified Agent Cho EC2/on-prem
Elastic Beanstalk Log ứng dụng
ECS Log container
AWS Lambda Log function
VPC Flow Logs Log riêng cho VPC
API Gateway Log request/response
CloudTrail Chỉ khi có filter
Route 53 Log DNS query

1.4 CloudWatch Logs Insights — công cụ query, không phải real-time engine

  • Tìm kiếm & phân tích dữ liệu đã nằm sẵn trong CloudWatch Logs (vd tìm 1 IP cụ thể, đếm số lần "ERROR")
  • Có ngôn ngữ query riêng; tự động phát hiện field từ AWS service và JSON log event
  • Fetch field, filter theo điều kiện, tính aggregate, sort, giới hạn số event
  • Lưu query lại, gắn vào CloudWatch Dashboard
  • Query được nhiều Log Group ở nhiều account khác nhau cùng lúc
  • Bẫy quan trọng: đây là query engine, KHÔNG PHẢI real-time engine — dữ liệu đã ghi vào log group rồi mới query được, không phải luồng streaming.

Xuất log ra S3 (CloudWatch Logs → S3):

  • API: CreateExportTask
  • Dữ liệu có thể mất tới 12 giờ mới export xong
  • Không near-real-time, không real-time → cần thời gian thực thì dùng Logs Subscriptions thay vì export

Logs Subscriptions — muốn near-real-time/real-time thì dùng cái này:

  • Lấy log event real-time từ CloudWatch Logs để xử lý/phân tích
  • Gửi tới Kinesis Data Streams, Kinesis Data Firehose, hoặc Lambda
  • Subscription Filter: lọc chỉ những log nào được đẩy sang đích

Ghi nhớ: đẩy thẳng tới Lambda/OpenSearch = real-time. Đẩy qua Kinesis Data Streams/Firehose rồi mới tới đích = near-real-time.

Cross-Account & Cross-Region Subscription — gom log nhiều account/region về một chỗ:

  • Cross-Account Subscription: gửi log event sang tài nguyên ở account khác (Kinesis Data Streams/Firehose bên account nhận)
  • Account gửi cần Subscription Filter trỏ tới đích ở account nhận
  • Account nhận cần: Destination (vd Kinesis Data Streams) + Destination Access Policy (cho phép account gửi ghi vào) + IAM Role (cross-account, account gửi assume để PutRecord)

Use case thi hay gặp: gom log của toàn bộ AWS Organization về một account trung tâm để phân tích tập trung.

1.5 CloudWatch Logs Agent & Unified Agent — đẩy log/metric từ EC2 và on-prem

  • Mặc định EC2 KHÔNG tự gửi log gì sang CloudWatch — phải tự cài agent
  • CloudWatch Logs Agent (bản cũ): chỉ gửi được log, chạy được cả EC2 lẫn on-premises
  • CloudWatch Unified Agent (khuyến nghị):
    • Thu thêm metric hệ thống (RAM, process…) mà EC2 mặc định không có
    • Gửi log sang CloudWatch Logs
    • Cấu hình tập trung qua SSM Parameter Store
  • Cần IAM permission đúng để agent hoạt động

Metric mà Unified Agent thu được trực tiếp trên server (Linux/EC2):

Nhóm Chi tiết
CPU active, guest, idle, system, user, steal
Disk free/used/total; Disk IO: writes, reads, bytes, iops
RAM free, inactive, used, total, cached
Netstat số kết nối TCP/UDP, packet, byte
Processes total, dead, blocked, idle, running, sleep
Swap free, used, used %

Nhắc lại: metric out-of-the-box của EC2 (không cần agent) chỉ có disk, CPU, network ở mức cao (tổng quát) — muốn chi tiết như RAM, process phải qua Unified Agent.

1.6 CloudWatch Alarms

  • Trigger notification dựa trên một metric — nhiều tuỳ chọn đánh giá (sampling, %, max, min…)
  • Alarm State: OK · INSUFFICIENT_DATA · ALARM
  • Period: khoảng thời gian (giây) để đánh giá metric; high-resolution custom metric: 10s, 30s, hoặc bội số của 60s

Alarm target — báo động xong thì làm gì:

Target Hành động
EC2 Instance Stop, Terminate, Reboot, hoặc Recover
EC2 Auto Scaling Trigger scaling action
Amazon SNS Gửi notification — từ đây làm được gần như mọi thứ (email, Lambda, SQS…)

Composite Alarms — giảm "alarm noise":

  • Một Alarm thường chỉ theo dõi một metric
  • Composite Alarm theo dõi trạng thái của nhiều alarm khác, kết hợp bằng AND/OR
  • Hữu ích để tránh spam alarm (vd chỉ báo khi cả CPU lẫn IOPS cùng bất thường, thay vì báo riêng từng cái)

Status Check — 3 loại:

Loại Kiểm tra gì
Instance status Bản thân EC2 VM
System status Phần cứng bên dưới (host)
Attached EBS status Các volume EBS đính kèm

EC2 Instance Recovery: khi StatusCheckFailed_System → Alarm trigger recovery, instance được khôi phục với cùng Private IP, Public IP, Elastic IP, metadata, placement group (không phải chạy lại từ đầu như instance mới).

Alarm từ CloudWatch Logs Metric Filter: đặt filter trên log group → filter đó tạo ra metric → gắn Alarm vào metric đó → báo SNS khi khớp pattern (vd đếm số dòng "ERROR" vượt ngưỡng).

Test alarm bằng CLI (không cần đợi điều kiện thật xảy ra):

aws cloudwatch set-alarm-state --alarm-name "myalarm" --state-value ALARM --state-reason "testing purposes"

1.7 CloudWatch Network Monitor

  • Giám sát vấn đề mạng giữa app trên AWS và data center on-premises
  • Phát hiện suy giảm hiệu năng mạng: packet loss, latency, jitter
  • Không cần cài agent
  • Test ICMP hoặc TCP tới đích on-premises (IPv4) qua Direct Connect hoặc Site-to-Site VPN
  • Kết quả publish vào CloudWatch Metrics như metric bình thường

1.8 Amazon EventBridge (tên cũ: CloudWatch Events)

  • Schedule: chạy theo lịch (cron job) → trigger Lambda (vd chạy mỗi giờ)
  • Event Pattern: rule phản ứng khi một service AWS "làm gì đó" (vd IAM Root User sign-in → gửi SNS email cảnh báo)
  • Trigger được: Lambda, SQS/SNS, Kinesis Data Streams, Step Functions, CodePipeline, CodeBuild, SSM, EC2 Actions, ECS Task, AWS Batch

Nguồn sự kiện (Event Source) thường gặp: EC2 (vd Start Instance), CodeBuild (build fail), S3 Event (upload object), CloudTrail (bất kỳ API call nào), Trusted Advisor (finding mới), Schedule/Cron.

Event Bus — 3 loại:

Loại Ai gửi vào
Default Event Bus AWS services
Partner Event Bus AWS SaaS Partners
Custom Event Bus Ứng dụng tự viết
  • Event Bus truy cập được từ account khác qua Resource-based Policy
  • Có thể archive event gửi tới bus (toàn bộ hoặc theo filter), giữ vô thời hạn hoặc theo period, và replay lại archive khi cần
  • Use case Resource-based Policy hay gặp: gom toàn bộ event của AWS Organization về một account trung tâm (giống pattern Cross-Account Subscription của CloudWatch Logs ở §1.4)

Schema Registry: EventBridge tự phân tích event trong bus và suy ra schema, cho phép generate code để ứng dụng biết trước cấu trúc dữ liệu; schema được version hoá.

1.9 Nhóm "CloudWatch Insights" — 4 loại, đừng nhầm lẫn

Loại Áp dụng cho Làm gì
Container Insights ECS, EKS, Kubernetes trên EC2, Fargate (cả ECS lẫn EKS) Thu thập, gộp, tóm tắt metric + log từ container; trên EKS/K8s cần agent CloudWatch dạng container
Lambda Insights AWS Lambda Metric hệ thống (CPU, memory, disk, network) + chẩn đoán (cold start, worker shutdown); phân phối dưới dạng Lambda Layer
Contributor Insights Bất kỳ log nào AWS tạo ra (VPC Flow Logs, DNS…) Tìm Top-N contributor (IP xấu, user tốn network nhất, URL lỗi nhiều nhất); dùng rule tự viết hoặc rule mẫu có sẵn
Application Insights App chạy trên EC2 (Java, .NET, IIS, database…) + resource khác (EBS, RDS, ELB, ASG, Lambda, SQS, DynamoDB, S3, ECS, EKS, SNS, API Gateway) Dashboard tự động phát hiện vấn đề, chạy trên nền SageMaker; finding/alert gửi tới EventBridge và SSM OpsCenter

Cách phân biệt nhanh: Container/Lambda Insights = thu thập metric/log chuyên biệt cho một loại compute. Contributor Insights = phân tích ai/cái gì đang gây tải nhiều nhất từ log có sẵn. Application Insights = dashboard tự động phát hiện vấn đề cho cả một stack ứng dụng.

2. AWS CloudTrail — audit, ai đã làm gì

  • Cung cấp governance, compliance, audit cho AWS Account
  • Bật mặc định! (không cần tự enable)
  • Ghi lại lịch sử API call/event trong account, gọi qua Console, SDK, CLI, hoặc do AWS Service tự gọi
  • Log được đẩy vào CloudWatch Logs hoặc S3
  • Một trail áp dụng cho All Regions (mặc định) hoặc một region duy nhất
  • Bẫy kinh điển: resource nào đó bị xoá trong AWS → luôn kiểm tra CloudTrail đầu tiên để biết ai/API nào đã xoá

2.1 Ba loại event của CloudTrail

Loại Mặc định có log không Ví dụ
Management Events Có, mặc định bật Cấu hình security (AttachRolePolicy), cấu hình routing (CreateSubnet), setup logging (CreateTrail); tách được Read Events (không đổi resource) vs Write Events (có thể đổi resource)
Data Events KHÔNG (vì volume rất cao) S3 object-level (GetObject, PutObject, DeleteObject — tách Read/Write được); Lambda Invoke
CloudTrail Insights Events Phải tự bật Xem §2.2

2.2 CloudTrail Insights — phát hiện hoạt động bất thường

  • Bật để phát hiện: provisioning tài nguyên bất thường, chạm giới hạn service, bùng nổ IAM action, khoảng trống trong hoạt động bảo trì định kỳ
  • Cơ chế: phân tích Management Events bình thường để tạo baseline, rồi liên tục phân tích Write Events để tìm pattern bất thường
  • Anomaly xuất hiện trong CloudTrail Console, event được gửi vào S3, và sinh ra một EventBridge event (để tự động hoá phản ứng)

2.3 Retention — lưu bao lâu?

  • Event lưu 90 ngày trong CloudTrail
  • Cần giữ lâu hơn → log ra S3 + dùng Athena để phân tích

3. AWS Config — compliance & lịch sử cấu hình

  • Giúp audit và ghi nhận compliance cho resource trong AWS
  • Ghi lại cấu hình đã thay đổi ra sao theo thời gian
  • Câu hỏi Config trả lời được:
    • Security Group nào đang mở SSH không giới hạn?
    • Bucket nào đang có public access?
    • Cấu hình ALB đã đổi ra sao theo thời gian?
  • Nhận alert qua SNS khi có thay đổi
  • Config là dịch vụ theo từng region — có thể aggregate dữ liệu qua nhiều region/account
  • Lưu dữ liệu cấu hình vào S3 để phân tích bằng Athena

3.1 Config Rules

  • Dùng AWS Managed Config Rules có sẵn (hơn 75 rule)
  • Hoặc viết Custom Rule (bắt buộc định nghĩa bằng Lambda) — vd kiểm tra mọi EBS volume có phải type gp2, mọi EC2 có phải t2.micro
  • Rule được đánh giá/trigger theo:
    • Mỗi lần có thay đổi cấu hình, và/hoặc
    • Theo chu kỳ thời gian cố định
  • Bẫy quan trọng nhất của Config: Config Rules KHÔNG NGĂN CHẶN hành động xảy ra (không deny) — nó chỉ phát hiện (detective), không phải preventive. Muốn ngăn chặn phải dùng SCP/IAM policy, không phải Config.
  • Pricing: không có free tier; $0,003 / configuration item được ghi nhận / region; $0,001 / lần đánh giá config rule / region

3.2 AWS Config Resource — xem được gì cho một resource

Xem được Ý nghĩa
Compliance timeline Resource này compliant/non-compliant qua từng thời điểm
Configuration timeline Cấu hình resource đã đổi ra sao theo thời gian
CloudTrail API calls timeline Ai gọi API nào lên resource này, khi nào

Đây là 3 thứ ghép lại đúng bằng 3 câu hỏi ở §0 — Config tự thân đã tích hợp cả góc nhìn CloudTrail (API calls) vào trong resource view của nó.

3.3 Config Rules — Remediation (tự sửa resource không tuân thủ)

  • Tự động remediation cho resource non-compliant bằng SSM Automation Documents
  • Dùng AWS-Managed Automation Documents có sẵn, hoặc tạo custom Automation Document
  • Mẹo: custom Automation Document có thể invoke Lambda function bên trong để xử lý logic phức tạp hơn
  • Đặt được Remediation Retries nếu sau khi auto-remediate xong resource vẫn còn non-compliant

3.4 Config Rules — Notifications

  • Dùng EventBridge để trigger notification khi resource non-compliant
  • Hoặc gửi mọi loại event (thay đổi cấu hình + trạng thái compliance) thẳng tới SNS — lọc bằng SNS Filtering hoặc filter ở phía client

5. Case study — For an Elastic Load Balancer

Ví dụ tổng hợp trong slide: cùng một ELB, ba dịch vụ đóng ba vai trò khác nhau, minh hoạ trực tiếp cho bảng ở §4.

Dịch vụ Vai trò với ELB
CloudWatch Theo dõi metric Incoming Connections; trực quan hoá % error code theo thời gian; dựng dashboard để nắm nhanh hiệu năng của load balancer
Config Theo dõi rule của Security Group gắn với ELB; theo dõi cấu hình đã thay đổi ra sao; đảm bảo luôn có SSL certificate gắn vào ELB (compliance)
CloudTrail Theo dõi ai đã gọi API nào để thay đổi cấu hình ELB

Bài học kiến trúc: đây chính là ba câu hỏi ở §0 áp vào một resource cụ thể. Bất kỳ đề bài nào hỏi "giám sát toàn diện resource X" đều nên trả lời theo đúng khuôn: CloudWatch (hiệu năng) + Config (cấu hình/compliance) + CloudTrail (ai làm gì).

7.1 RDS đẩy log sang CloudWatch, muốn Alarm khi log có "Error"

Đề bài:

You have an RDS DB instance that's configured to push its database logs to CloudWatch. You want to create a CloudWatch alarm if there's an Error found in the logs. How would you do that?

Đáp án:

  1. Create a scheduled CloudWatch Event that triggers an AWS Lambda every 1 hour, scans the logs, and notify you through SNS topic
  2. Create a CloudWatch Logs Metric Filter that filter the logs for the keyword Error, then create a CloudWatch Alarm based on that Metric Filter
  3. Create an AWS Config Rule that monitors Error in your database logs and notify you through SNS topic

Phân tích:

Phương án Đúng/Sai Vì sao
1 — Scheduled Lambda mỗi 1 giờ scan log → SNS Sai Không real-time (trễ tới 1 giờ giữa hai lần scan), tự viết logic scan/parse log trong Lambda trong khi CloudWatch đã có cơ chế native làm sẵn việc này — thừa và kém hiệu quả
2 — CloudWatch Logs Metric Filter lọc Error → CloudWatch Alarm dựa trên Metric Filter đó Đúng Đây đúng là cơ chế native: Metric Filter quét log group theo pattern → mỗi lần khớp thì tăng một custom metric → Alarm gắn thẳng vào metric này, đánh giá gần real-time, trigger SNS khi vượt ngưỡng (vd >= 1 trong 1 phút)
3 — AWS Config Rule monitor Error trong log DB → SNS Sai Config trả lời câu hỏi "cấu hình có đúng chuẩn không" (§0, §3) — nó theo dõi trạng thái cấu hình resource, không đọc nội dung dòng log ứng dụng/database

Đáp án đúng: phương án 2 — CloudWatch Logs Metric Filter + CloudWatch Alarm.

Đây chính là cơ chế đã ghi ở §1.6: "Alarm từ CloudWatch Logs Metric Filter: đặt filter trên log group → filter đó tạo ra metric → gắn Alarm vào metric đó → báo SNS khi khớp pattern (vd đếm số dòng "ERROR" vượt ngưỡng)." Câu hỏi này là ví dụ áp dụng trực tiếp của dòng đó, chỉ đổi ngữ cảnh từ log chung sang log RDS.

Bẫy của đề: cả 2 phương án sai đều có vẻ "làm được việc" (scan bằng Lambda vẫn báo được lỗi; Config vẫn giám sát được resource RDS) — nhưng đều không phải là công cụ đúng cho tìm kiếm nội dung log gần real-time. Ghi nhớ: tìm keyword trong log → luôn nghĩ tới Metric Filter trước tiên, không phải viết thêm Lambda hay dùng Config.

7.2 ASG đã ở minimum capacity, Alarm scale-in vẫn ở trạng thái ALARM thì sao?

Đề bài:

You have an application hosted on a fleet of EC2 instances managed by an Auto Scaling Group that you configured its minimum capacity to 2. Also, you have created a CloudWatch Alarm that is configured to scale in your ASG when CPU Utilization is below 60%. Currently, your application runs on 2 EC2 instances and has low traffic and the CloudWatch Alarm is in the ALARM state. What will happen?

Đáp án:

  1. One EC2 instance will be terminated and the ASG desired and minimum capacity will go to 1
  2. The CloudWatch Alarm will remain in ALARM state but never decrease the number of EC2 instances in the ASG
  3. The CloudWatch Alarm will be detached from my ASG
  4. The CloudWatch Alarm will go in OK state

Phân tích:

Phương án Đúng/Sai Vì sao
1 — Terminate 1 instance, ASG min capacity tự giảm xuống 1 Sai Minimum capacity là ràng buộc cứng do người dùng đặt — ASG không bao giờ tự ý sửa đổi con số min/max mình đã cấu hình chỉ vì một alarm scale-in kích hoạt
2 — Alarm vẫn ở ALARM, nhưng ASG không giảm thêm instance nào Đúng ASG scale-in policy luôn tôn trọng min capacity: dù alarm liên tục báo ALARM (CPU < 60%), ASG đã ở đúng minimum (2) nên không terminate thêm — action scale-in bị "chặn" ở biên dưới, alarm vẫn giữ nguyên trạng thái vì metric CPU vẫn đang dưới ngưỡng
3 — Alarm bị gỡ (detach) khỏi ASG Sai Không có cơ chế nào tự động detach alarm khỏi ASG chỉ vì đã chạm min capacity; alarm vẫn gắn liền, chỉ là scaling action không thực thi được
4 — Alarm chuyển sang OK Sai Trạng thái Alarm (OK/ALARM/INSUFFICIENT_DATA) chỉ phụ thuộc vào giá trị metric CPU so với threshold, hoàn toàn độc lập với việc ASG có scale được hay không — CPU vẫn dưới 60% thì alarm vẫn ALARM

Đáp án đúng: phương án 2.

Liên hệ §1.6: Alarm State (OK/INSUFFICIENT_DATA/ALARM) được tính từ metric, tách biệt hoàn toàn khỏi việc target (EC2 Auto Scaling) có thực thi được hành động hay không. Đây là điểm dễ nhầm nhất: nhiều người nghĩ "alarm không scale được thì phải đổi trạng thái hoặc bị gỡ" — thực ra alarm chỉ là cái đồng hồ đo, còn ASG mới là bên quyết định có hành động hay không dựa trên giới hạn min/max đã cấu hình sẵn.

Bẫy của đề: đề đánh vào trực giác "min capacity phải mềm dẻo theo tải" — nhưng thực tế min/max của ASG là con số cứng do người dùng chủ động đặt, chỉ thay đổi khi người dùng (hoặc Scheduled Action/Predictive Scaling) chủ động sửa, không bao giờ tự do bị alarm scale-in "vượt rào" xuống dưới.

7.3 Muốn theo dõi memory usage của EC2 trong CloudWatch thì làm sao?

Đề bài:

How would you monitor your EC2 instance memory usage in CloudWatch?

Đáp án:

  1. Enable EC2 Detailed Monitoring
  2. By default, the EC2 instance pushes memory usage to CloudWatch
  3. Use the Unified CloudWatch Agent to push memory usage as a custom metric to CloudWatch

Phân tích:

Phương án Đúng/Sai Vì sao
1 — Bật EC2 Detailed Monitoring Sai Detailed Monitoring chỉ đổi tần suất thu thập các metric có sẵn từ 5 phút xuống 1 phút (CPU, network, disk ở mức tổng quát) — nó không thêm metric mới, RAM vẫn không xuất hiện dù bật tính năng này
2 — Mặc định EC2 tự đẩy memory usage lên CloudWatch Sai Đây là hiểu lầm phổ biến nhất của bài — theo §1.5: mặc định EC2 KHÔNG tự gửi log/metric RAM nào cả, hypervisor bên dưới không có quyền nhìn vào bộ nhớ bên trong OS của instance
3 — Dùng Unified CloudWatch Agent để đẩy memory usage như một custom metric Đúng RAM là metric không có sẵn trên EC2 (out-of-the-box chỉ có CPU/disk/network tổng quát) → phải cài Unified Agent bên trong instance, agent chạy trong OS nên đọc được RAM thật và đẩy lên CloudWatch dưới dạng Custom Metric

Đáp án đúng: phương án 3.

Liên hệ §1.1 và §1.5: RAM luôn là ví dụ kinh điển cho Custom Metric trong SAA-C03 — vì nó nằm bên trong hệ điều hành, AWS (ở tầng hypervisor) không thấy được, chỉ agent chạy trong OS (Unified Agent) mới đọc và đẩy lên được.

Bẫy của đề: "Detailed Monitoring" nghe rất giống "theo dõi chi tiết hơn = thấy được nhiều thứ hơn (kể cả RAM)" — thực ra nó chỉ tăng tần suất (1 phút thay vì 5 phút) cho các metric đã có sẵn, hoàn toàn không liên quan tới việc thêm metric RAM.

Nhưng câu hỏi thực chất tách làm hai vế — "resource bị non-compliant" là việc của Config, còn "ai đã sửa" vẫn luôn là CloudTrail, đúng như phân loại "3-trong-1" đã ghi ở §3.2: Config Resource view = compliance timeline + configuration timeline + CloudTrail API calls timeline — CloudTrail vẫn là nguồn gốc của mảnh "ai gọi API".

7.11 Config phát hiện SG mở SSH không giới hạn — feature nào tự sửa lại đúng chuẩn?

Đề bài:

You have enabled AWS Config to monitor Security Groups if there's unrestricted SSH access to any of your EC2 instances. Which AWS Config feature can you use to automatically re-configure your Security Groups to their correct state?

Đáp án:

  1. AWS Config Remediations
  2. AWS Config Rules
  3. AWS Config Notifications

Phân tích:

Phương án Đúng/Sai Vì sao
1 — AWS Config Remediations Đúng Đúng chức năng ở §3.3: remediation dùng SSM Automation Document để tự động sửa lại resource non-compliant về đúng trạng thái — đây là bước duy nhất thực sự "hành động sửa", không chỉ phát hiện
2 — AWS Config Rules Sai Rule chỉ làm nhiệm vụ phát hiện/đánh giá compliance (SG có mở SSH không) — bản thân Rule không tự sửa gì cả, đây chính là bẫy "Config không deny/không tự sửa" đã nhấn mạnh ở §3.1
3 — AWS Config Notifications Sai Notifications chỉ báo cho người/hệ thống khác biết (qua EventBridge/SNS) rằng resource đang non-compliant — không tự thực hiện hành động sửa cấu hình

Đáp án đúng: phương án 1 — AWS Config Remediations.

Chuỗi đúng của Config luôn là: Config Rule phát hiện non-compliant → Remediation (SSM Automation Document) tự sửa → Notifications (EventBridge/SNS) báo cho người liên quan biết. Ba phương án trong câu này chính là ba bước khác nhau của đúng một pipeline — dễ nhầm vì cả ba đều "đúng ngữ cảnh Config" nhưng chỉ có Remediations mới thực sự "re-configure".

7.12 Config phát hiện SG bị đổi — feature nào để nhận email báo tin?

Đề bài:

You are running a critical website on a set of EC2 instances with a tightened Security Group that has restricted SSH access. You have enabled AWS Config in your AWS Region and you want to be notified via email when someone modified your EC2 instances' Security Group. Which AWS Config feature helps you do this?

Đáp án:

  1. AWS Config Remediations
  2. AWS Config Rules
  3. AWS Config Notifications

Phân tích:

Phương án Đúng/Sai Vì sao
1 — AWS Config Remediations Sai Remediation dùng để tự động sửa resource non-compliant (như câu 7.11) — đề bài này chỉ cần được báo tin qua email, không yêu cầu tự sửa gì cả
2 — AWS Config Rules Sai Rule chỉ đánh giá compliance, không tự gửi email; muốn nhận thông báo phải đi thêm bước Notifications
3 — AWS Config Notifications Đúng Đúng chức năng ở §3.4: gửi mọi loại event (thay đổi cấu hình) thẳng tới SNS, SNS gắn subscription email là xong — hoặc qua EventBridge nếu cần lọc thêm

Đáp án đúng: phương án 3 — AWS Config Notifications.

So với câu 7.11 (cùng bối cảnh SG, cùng 3 lựa chọn): 7.11 hỏi "tự sửa" → Remediations; câu này hỏi "được báo qua email" → Notifications. Hai câu là cặp đối chiếu chuẩn để phân biệt hai tính năng hay bị lẫn của Config.

7.13 Điền vào chỗ trống: đẩy CloudWatch metric near real-time ra S3/3rd-party

Đề bài:

……………………… is a CloudWatch feature that allows you to send CloudWatch metrics in near real-time to S3 bucket (through Kinesis Data Firehose) and 3rd party destinations (e.g., Splunk, Datadog, …).

Đáp án:

  1. CloudWatch Metric Stream
  2. CloudWatch Log Stream
  3. CloudWatch Metric Filter
  4. CloudWatch Log Group

Phân tích:

Phương án Đúng/Sai Vì sao
1 — CloudWatch Metric Stream Đúng Đúng nguyên văn định nghĩa ở §1.2: stream liên tục metric, near-real-time, đích là Kinesis Data Firehose → S3 hoặc 3rd-party (Datadog, Splunk…)
2 — CloudWatch Log Stream Sai Đây là khái niệm hoàn toàn khác — Log Stream là instance/container/log file bên trong một Log Group (§1.3), không liên quan tới việc đẩy metric ra ngoài
3 — CloudWatch Metric Filter Sai Metric Filter dùng để lọc log theo pattern rồi tạo metric (vd đếm dòng "ERROR", xem §1.6) — không phải cơ chế stream metric ra 3rd-party
4 — CloudWatch Log Group Sai Log Group chỉ là nơi chứa log (§1.3), không phải tính năng đẩy metric

Đáp án đúng: phương án 1 — CloudWatch Metric Stream. Câu này chỉ là kiểm tra trực tiếp định nghĩa ở §1.2 — 3 phương án còn lại đều là các khái niệm "CloudWatch ... Stream/Filter/Group" na ná tên nhưng khác hẳn chức năng, cố tình gây nhiễu.

7.14 VPC Flow Logs trong CloudWatch Log Group — tìm top IP nghi tấn công

Đề bài:

A DevOps engineer is working for a company and managing its infrastructure and resources on AWS. There was a sudden spike in traffic for the main application for the company which was not normal in this period of the year. The application is hosted on a couple of EC2 instances in private subnets and is fronted by an Application Load Balancer in a public subnet. To detect if this is normal traffic or an attack, the DevOps engineer enabled the VPC Flow Logs for the subnets and stored those logs in CloudWatch Log Group. The DevOps wants to analyze those logs and find out the top IP addresses making requests against the website to check if there is an attack. Which of the following can help the DevOps engineer to analyze those logs?

Đáp án:

  1. CloudWatch Metric Stream
  2. CloudWatch Alarm
  3. CloudWatch Contributor Insights
  4. CloudWatch Metric Filter

Phân tích:

Phương án Đúng/Sai Vì sao
1 — CloudWatch Metric Stream Sai Dùng để đẩy metric ra ngoài (S3/3rd-party), không phải công cụ để phân tích top-N trong log
2 — CloudWatch Alarm Sai Alarm chỉ phản ứng khi một metric vượt ngưỡng — không tự tính toán "IP nào request nhiều nhất"
3 — CloudWatch Contributor Insights Đúng Đúng thiết kế ở §1.9: áp dụng cho bất kỳ log nào AWS tạo ra, bao gồm cả VPC Flow Logs, chuyên tìm Top-N contributor — chính là "IP xấu gây tải nhiều nhất" nêu ngay trong bảng đó
4 — CloudWatch Metric Filter Sai Metric Filter chỉ đếm số lần khớp một pattern cố định (vd đếm dòng chứa "ERROR") — không tự xếp hạng Top-N theo một trường như IP address

Đáp án đúng: phương án 3 — CloudWatch Contributor Insights.

Đây là ví dụ áp dụng trực tiếp của dòng trong bảng ở §1.9: "Contributor Insights — tìm Top-N contributor (IP xấu, user tốn network nhất, URL lỗi nhiều nhất)" — VPC Flow Logs là ví dụ nguồn log kinh điển nhất cho tính năng này.

7.15 Ngăn xoá nhầm bảng DynamoDB + cảnh báo khi có ai cố xoá — chọn thiết kế nào?

Đề bài:

A company is developing a Serverless application on AWS using Lambda, DynamoDB, and Cognito. A junior developer joined a few weeks ago and accidentally deleted one of the DynamoDB tables in the dev AWS account which contained important data. The CTO asks you to prevent this from happening again and there must be a notification system to monitor if there is an attempt to make such deletion actions for the DynamoDB tables. What would you do?

Đáp án:

  1. Assign developers to a certain IAM group which prevents deletion of DynamoDB tables. Configure EventBridge to capture any DeleteTable API calls through S3 and send a notification using KMS
  2. Assign developers to a certain IAM group which prevents deletion of DynamoDB tables. Configure EventBridge to capture any DeleteTable API calls through CloudTrail and send a notification using SNS
  3. Assign developers to a certain IAM group which prevents deletion of DynamoDB tables. Configure EventBridge to capture any DeleteTable API calls through CloudTrail and send a notification using KMS

Phân tích:

Cả 3 phương án đều giống nhau ở vế đầu (IAM group chặn quyền DeleteTable — đúng cách phòng ngừa, dùng IAM chứ không phải Config vì cần ngăn chặn thật sự, khớp bẫy "Config không deny" ở §3.1). Khác biệt nằm ở vế sau — nguồn event và kênh notify:

Phương án Đúng/Sai Vì sao
1 — EventBridge bắt DeleteTable qua S3, notify bằng KMS Sai EventBridge không "bắt API call qua S3" — nguồn sự kiện API call đúng phải là CloudTrail (§1.8, §2.4); và KMS là dịch vụ quản lý key mã hoá, không phải kênh gửi thông báo
2 — EventBridge bắt DeleteTable qua CloudTrail, notify bằng SNS Đúng Đúng pattern chuẩn ở §2.4: mọi API call (kể cả DeleteTable) đều được CloudTrail ghi lại → EventBridge bắt event đó → gửi cảnh báo qua SNS (đúng dịch vụ notification, xem §1.6 và ghi chú SNS/SQS ở note §17 — Decoupling Applications)
3 — EventBridge bắt DeleteTable qua CloudTrail, notify bằng KMS Sai Nguồn event đúng (CloudTrail) nhưng kênh notify sai — KMS không gửi được thông báo cho người dùng, đó là việc của SNS

Đáp án đúng: phương án 2.

Công thức đầy đủ: IAM (ngăn chặn) + CloudTrail ghi API call + EventBridge bắt event + SNS báo tin — đúng chuỗi đã minh hoạ ở §2.4 (ví dụ AssumeRole/AuthorizeSecurityGroupIngress), chỉ đổi API thành DeleteTable. Bẫy của câu là KMS — dễ bị chọn nhầm vì nghe "an toàn/bảo mật" nhưng KMS chỉ quản lý encryption key, không phải dịch vụ notification.

7.16 Muốn tái sử dụng lại EventBridge event của prod cho dev, 6 tháng sau mới cần

Đề bài:

A company has a running Serverless application on AWS which uses EventBridge as an inter-communication channel between different services within the application. There is a requirement to use the events in the prod environment in the dev environment to make some tests. The tests will be done every 6 months, so the events need to be stored and used later on. What is the most efficient and cost-effective way to store EventBridge events and use them later?

Đáp án:

  1. Use EventBridge Archive and Replay feature
  2. Create a Lambda function to store the EventBridge events in an S3 bucket for later usage
  3. Configure EventBridge to store events in a DynamoDB table

Phân tích:

Phương án Đúng/Sai Vì sao
1 — Dùng EventBridge Archive và Replay Đúng Đúng tính năng native đã ghi ở §1.8: EventBridge tự archive event gửi tới bus (toàn bộ hoặc theo filter), giữ vô thời hạn hoặc theo period, và replay lại khi cần — không cần dựng thêm hạ tầng nào, đúng nghĩa "hiệu quả và tiết kiệm chi phí" nhất vì dùng thẳng tính năng có sẵn của chính EventBridge
2 — Tự viết Lambda lưu event vào S3 Sai Làm được việc nhưng là tự chế lại đúng thứ Archive/Replay đã làm sẵn — tốn công viết/vận hành Lambda, không phải phương án "hiệu quả nhất" khi câu hỏi đã có tính năng native
3 — Cấu hình EventBridge lưu event vào DynamoDB Sai EventBridge không có cơ chế cấu hình sẵn để lưu thẳng event vào DynamoDB — phải tự viết thêm Lambda target để làm việc này, phức tạp hơn cả phương án 2

Đáp án đúng: phương án 1 — EventBridge Archive and Replay.

Câu này kiểm tra trực tiếp chi tiết ở §1.8: "Có thể archive event gửi tới bus (toàn bộ hoặc theo filter), giữ vô thời hạn hoặc theo period, và replay lại archive khi cần." Bẫy nằm ở việc đề bài mô tả một nhu cầu nghe rất "custom" (dùng lại event prod cho dev, test định kỳ 6 tháng) khiến người học nghĩ phải tự xây pipeline (Lambda + S3/DynamoDB) — trong khi EventBridge đã có sẵn tính năng đúng y chang cho việc này.

Điểm hay ra thi

  • Nhớ khung 3 câu hỏi ở §0: CloudWatch = hiệu năng, CloudTrail = audit API call, Config = compliance/cấu hình theo thời gian.
  • CloudWatch Dimension: tối đa 30/metric. High-resolution custom metric period: 10s, 30s, bội số 60s.
  • CloudWatch Logs Insights là query engine, không phải real-time engine; S3 Export trễ tới 12 giờ → cần real-time thì dùng Subscriptions.
  • Cross-Account Subscription: account nhận cần Destination Access Policy + IAM Role.
  • Unified Agent > Logs Agent cũ (thêm metric hệ thống: CPU/RAM/disk/netstat/process/swap), cấu hình qua SSM Parameter Store.
  • Composite Alarm dùng AND/OR để giảm alarm noise; Status Check có 3 loại (Instance/System/EBS); Recovery giữ nguyên IP/metadata.
  • EventBridge (tên cũ CloudWatch Events): Schedule/Cron + Event Pattern; 3 loại Event Bus (Default/Partner/Custom); archive + replay; Schema Registry.
  • 4 loại Insights dễ nhầm: Container (ECS/EKS), Lambda (cold start), Contributor (top-N từ log), Application (dashboard tự động, chạy trên SageMaker).
  • CloudTrail bật mặc định; Management Events log sẵn, Data Events phải tự bật (S3 object-level, Lambda Invoke); retention 90 ngày, dài hạn → S3 + Athena.
  • CloudTrail Insights: baseline từ Management Events, phân tích liên tục Write Events, sinh EventBridge event khi phát hiện bất thường.
  • Config Rules KHÔNG NGĂN CHẶN hành động (no deny) — chỉ phát hiện; 75+ managed rule, custom rule viết bằng Lambda.
  • Config Remediation dùng SSM Automation Document (managed hoặc custom, custom gọi được Lambda); có Remediation Retries.
  • Config Resource view = 3-trong-1: compliance timeline + configuration timeline + CloudTrail API calls timeline.
  • Case study ELB là khuôn mẫu chuẩn: CloudWatch đo hiệu năng, Config kiểm cấu hình/SSL cert, CloudTrail biết ai đổi.

Takeaway cá nhân

  • Bài này không khó về mặt kỹ thuật — khó ở chỗ nhớ đúng dịch vụ nào trả lời câu hỏi nào. Cứ hỏi lại bản thân: "đây là hỏi về hiệu năng runtime, ai gọi API, hay cấu hình đúng chuẩn không?" là chọn được ngay CloudWatch / CloudTrail / Config.
  • Trong CloudWatch, phần dễ nhầm nhất là Logs Insights vs Logs Subscriptions vs S3 Export — cả ba đều liên quan tới log nhưng mục đích khác hẳn: query lịch sử (Insights), real-time streaming (Subscriptions), xuất nguyên khối chậm (Export).
  • Chi tiết "Config không deny" rất dễ bị đánh lừa vì tên nghe giống một security guard — thực ra nó chỉ là camera giám sát + báo cáo, muốn chặn thật phải dùng SCP/IAM.
  • Case study ELB ở §5 là công thức trả lời chuẩn cho mọi câu hỏi dạng "giám sát toàn diện resource X" trong đề thi — nhớ công thức này thay vì học thuộc từng resource riêng lẻ.
  • Liên hệ ngược §17 (SNS/SQS là đích quen thuộc của Alarm và EventBridge) và §22 (Athena dùng để phân tích CloudTrail/Config log lưu dài hạn trong S3).
  • Bộ 16 câu ôn tập ở §7 cho thấy rõ 3 cặp bẫy lặp lại nhiều lần nhất: (a) "làm được việc" bằng Lambda tự chế (scheduled scan, lưu S3/DynamoDB thủ công) so với tính năng native sẵn có (Metric Filter, Config Rules, EventBridge Archive/Replay) — đề thi luôn ưu tiên đáp án native, hiệu quả hơn; (b) mốc 90 ngày retention của CloudTrail quyết định tra trực tiếp hay phải qua S3 + Athena (so 7.5 vs 7.7); (c) Config luôn tách ba việc — Rules (phát hiện) / Remediations (tự sửa) / Notifications (báo tin) — dễ chọn nhầm giữa ba khi đề chỉ đổi động từ ("tự sửa" vs "được báo").
