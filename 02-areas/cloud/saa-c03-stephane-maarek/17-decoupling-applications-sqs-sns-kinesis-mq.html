17 – Decoupling Applications: SQS, SNS, Kinesis, Amazon MQ

Cách đọc note này: (1) Vì sao cần decouple → (2) SQS (queue) → (3) SNS (pub/sub) → (4) Kinesis (stream) → (5) Amazon MQ (legacy) → (6) So sánh & chọn đáp án thi.

1. Vì sao cần decoupling?

Khi có nhiều application, chúng phải giao tiếp. Có 2 cách:

Pattern Cách hoạt động Rủi ro khi spike
Synchronous A gọi thẳng B B quá tải → A timeout, mất request
Asynchronous (decoupled) A ↔ B qua queue / topic / stream Buffer được; scale A và B độc lập

Ví dụ: Thường encode 10 video; đột nhiên 1000. Gọi sync encoder → sập. Đưa job vào hàng đợi → worker xử lý dần.

Lợi ích: chịu spike, retry khi consumer lỗi, scale độc lập, phù hợp microservices / event-driven.

Bản đồ 4 dịch vụ (nhớ trước, chi tiết sau)

Dịch vụ Mô hình Consumer Một câu nhớ
SQS Queue Pull “Hàng đợi job — làm xong thì xóa”
SNS Pub/Sub Push “1 message → nhiều subscriber”
Kinesis Stream Pull / EFO push “Luồng real-time, đọc lại được (replay)”
Amazon MQ Broker ActiveMQ/RabbitMQ Theo protocol cũ “App legacy JMS/AMQP, ít đổi code”

2. Amazon SQS — hàng đợi job

2.1 Queue là gì?

Producer gửi message vào queue → consumer poll lấy ra → xử lý → delete.

2.2 Standard Queue — mặc định dùng nhiều nhất

Thuộc tính Chi tiết
Throughput Gần như unlimited
Retention Mặc định 4 ngày, tối đa 14 ngày
Latency < 10 ms
Message size Tối đa 256 KB
Message attributes Tối đa 10 attribute/message (metadata key-value, tách khỏi body)
Encryption SSE-SQS mặc định (AWS owned key, miễn phí) từ 2023; đổi sang SSE-KMS nếu cần key riêng để audit (tính phí theo request KMS)
Delivery At-least-once → có thể trùng → consumer nên idempotent
Ordering Best-effort → có thể lộn thứ tự

Idempotent: xử lý trùng không làm sai (ví dụ đã ghi orderId rồi thì bỏ qua).

Message > 256 KB? SQS không tăng giới hạn được — dùng pattern claim-check: lưu payload thật lên S3, chỉ gửi pointer (S3 key) qua SQS. SDK có sẵn Amazon SQS Extended Client Library làm tự động việc này (Java/Python).

2.3 Vòng đời message: Produce → Consume → Delete

Produce

  • SDK: SendMessage / SendMessageBatch (batch tới 10 message hoặc 256 KB/lần)
  • Message persist đến khi bị delete
  • Ví dụ payload: Order id, Customer id, attributes…

Mẹo tiết kiệm chi phí: SQS tính tiền theo số request. Ưu tiên *Batch API (SendMessageBatch, DeleteMessageBatch, ReceiveMessage với MaxNumberOfMessages tới 10) để gộp nhiều message/lần thay vì gọi lẻ từng message.

Consume (EC2 / server / Lambda)

  1. Poll — tối đa 10 messages / lần
  2. Xử lý (ví dụ ghi RDS)
  3. DeleteMessage — bắt buộc; quên xóa → message hiện lại sau visibility timeout

Lambda + SQS: Event source mapping — Lambda poll giúp bạn, scale theo backlog.

2.4 Visibility Timeout — tránh 2 worker cùng làm 1 job

Poll xong → message tạm ẩn. Mặc định 30 giây.

  • Xử lý xong + delete trong cửa sổ này → ổn
  • Hết giờ mà chưa delete → message hiện lại → có thể xử lý hai lần
  • Cần thêm thời gian → ChangeMessageVisibility (heartbeat)

Đặt timeout Hệ quả
Quá thấp Duplicate dù vẫn đang xử lý
Quá cao + consumer crash Phải chờ rất lâu mới retry
Đúng ≥ thời gian xử lý tối đa kỳ vọng

2.5 Long Polling — đừng hỏi queue trống liên tục

Short Polling Long Polling (khuyến nghị)
Hành vi Trả về ngay (kể cả rỗng) Đợi có message hoặc hết WaitTime
Wait ~0 1–20 s (nên 20 s)
API calls Nhiều, tốn hơn Ít hơn, hiệu quả hơn

Bật ở queue level hoặc API (WaitTimeSeconds).

2.6 Delay — trì hoãn lúc message mới vào

Cơ chế Ý nghĩa
DelaySeconds (từng message) Chưa visible trong 0–15 phút
Delay queue Mọi message vào queue đều delay mặc định

Dùng cho: nhắc sau N phút, backoff đơn giản.

2.7 Scale & pattern kiến trúc

Nhiều consumer song song

  • At-least-once + best-effort order
  • Scale ngang số worker → tăng throughput

SQS + Auto Scaling Group

Metric Ý nghĩa
ApproximateNumberOfMessagesVisible Đang chờ xử lý
ApproximateAgeOfOldestMessage Backlog nghiêm trọng (message già)

Decouple giữa các tier — có queue thì spike không làm mất request dễ như sync.

Không có buffer → transaction có thể mất:

Buffer trước khi ghi DB — queue hấp thụ spike; worker ghi RDS từ từ.

2.8 FIFO Queue — cần thứ tự & không trùng

Standard FIFO
Thứ tự Best-effort Đúng thứ tự trong Message Group
Duplicate Có thể có Dedup (ID hoặc content-based), cửa sổ 5 phút
Throughput Unlimited 300/s không batch; 3.000/s có batch
Throughput cao hơn — Bật High Throughput Mode → vượt xa 3.000/s nếu traffic trải đều trên nhiều Message Group ID
Parallel Tự do Khác Message Group ID → vẫn song song
Tên queue Tuỳ ý Bắt buộc hậu tố .fifo

Cùng orderId = Message Group → một order đúng thứ tự; nhiều order khác nhau vẫn parallel.

2.9 Dead Letter Queue (DLQ)

Fail quá maxReceiveCount lần → chuyển sang DLQ (điều tra poison message / bug).

  • Standard queue → Standard DLQ; FIFO → FIFO DLQ
  • Fix xong có thể redrive về queue gốc

2.10 Security SQS

Lớp Cách
In-flight HTTPS
At-rest KMS (SSE-SQS / SSE-KMS)
Client-side Tự encrypt trước khi gửi
IAM Ai được gọi API
Access Policy Cross-account; cho SNS/S3 ghi vào queue

Fan-out SNS→SQS hay lỗi vì quên queue policy cho sns.amazonaws.com + SourceArn topic.

3. Amazon SNS — pub/sub & fan-out

3.1 Bài toán: 1 message → nhiều người nhận?

  • Producer chỉ publish vào 1 Topic
  • Nhiều subscription lắng nghe (có thể filter)
  • Tới 12,5 triệu subscriptions / topic; 100.000 topics
  • Message size tối đa 256 KB (giống SQS)

Bẫy hay thi: SNS không lưu trữ message. Nếu topic không có subscriber nào → message mất luôn, không retry, không DLQ (vì chẳng có subscription nào để gắn DLQ vào). Đây là lý do pattern SNS + SQS fan-out (§3.2) an toàn hơn gửi thẳng vào HTTP endpoint — SQS sẽ persist hộ.

Subscriber Vai trò
SQS Fan-out bền, persist + retry
Lambda Xử lý ngay
HTTP/HTTPS, Email/SMS, Mobile push Notification / webhook
Data Firehose Đổ S3 / analytics

Nhiều AWS service publish thẳng vào SNS:

Publish: Topic Publish (SDK) hoặc Direct Publish (mobile: GCM / APNS / ADM…).

Security: HTTPS, KMS, IAM, SNS Access Policy (cross-account / cho S3 publish).

3.2 Pattern vàng: SNS + SQS Fan-out

Push một lần vào SNS → mọi SQS subscriber đều nhận.

Vì sao dùng
Decouple Publisher không biết danh sách consumer
Bền Mỗi SQS tự persist / retry / scale
Mở rộng Thêm queue mới không sửa publisher
Cross-region SNS → SQS region khác được
Bắt buộc SQS Access Policy cho phép SNS ghi

Raw Message Delivery: mặc định SNS bọc message gốc trong một JSON envelope (kèm MessageId, TopicArn…) rồi mới đẩy vào SQS. Bật Raw Message Delivery trên subscription để consumer nhận đúng message gốc, khỏi tự parse envelope — cần khi hệ thống cũ đã quen định dạng message gốc hoặc cần đọc trực tiếp message attributes.

S3 Events → nhiều queue: cùng event type + prefix chỉ có 1 S3 Event rule → phải S3 → SNS → nhiều SQS (hoặc EventBridge).

SNS → Firehose → S3 (lưu / analytics notification stream):

3.3 SNS FIFO + filtering

FIFO Topic — ordering theo Message Group ID; dedup giống SQS FIFO; subscriber có thể SQS Standard hoặc FIFO; throughput giới hạn như SQS FIFO.

Cần fan-out + order + dedup → SNS FIFO → SQS FIFO:

Message Filtering: JSON filter policy trên subscription — chỉ nhận message khớp; không có filter = nhận hết.

Ví dụ: topic orders — A filter status=shipped, B filter status=cancelled.

4. Amazon Kinesis — streaming real-time

Khác queue: đây là luồng liên tục. Nhiều consumer đọc cùng data; có thể replay trong cửa sổ retention. Không “delete sau khi xử lý” như SQS.

4.1 Kinesis Data Streams

Thuộc tính Chi tiết
Retention Mặc định 24 giờ, tăng tối đa 365 ngày (tính phí thêm) → replay trong cửa sổ này
Xóa tay Không — chỉ hết hạn
Record Tối đa 1 MiB/record
Ordering Cùng Partition Key → cùng shard → có thứ tự
Encryption KMS at-rest, HTTPS in-flight
Lib KPL (producer — tự batch/nén/retry), KCL (consumer — checkpoint tiến độ vào DynamoDB)

Ghi chú số liệu: record tối đa 1 MiB (không phải 10) — dễ nhầm với giới hạn 10 MB của SQS extended message.

Partition key

  • Phân tán đều giữa shards (tránh hot shard)
  • Cần order theo entity → userId / deviceId
  • Key luôn "all" → một shard quá tải

Resharding — đổi số shard theo tải

Thao tác Khi nào dùng Hiệu ứng
Shard Splitting 1 shard quá tải (hot shard) Tách 1 → 2 shard, tăng capacity, tốn thêm tiền
Shard Merging 2 shard ít traffic Gộp 2 → 1 shard, giảm chi phí

Ở Provisioned mode, resharding phải làm thủ công (API/Console). On-demand mode tự scale, không cần resharding tay.

Capacity

Mode Ý chính Trả tiền
Provisioned Chọn shard: 1 MB/s in (hoặc 1000 records/s), 2 MB/s out shared Shard-hour
On-demand Auto scale; default ~4 MB/s in Stream-hour + GB

Shared vs Enhanced Fan-Out (EFO)

Shared EFO
Bandwidth Consumers chia 2 MB/s out / shard Mỗi consumer app riêng ~2 MB/s / shard
Mô hình Pull Push (HTTP/2)
Khi nào Ít consumer Nhiều consumer real-time

4.2 Amazon Data Firehose

Tên cũ: Kinesis Data Firehose.

Fully managed load stream → S3 / Redshift / OpenSearch / Splunk / Datadog / HTTP endpoint…

  • Near real-time (buffer theo size/time)
  • Convert Parquet/ORC, nén, transform bằng Lambda
  • Không lưu lâu, không replay
Data Streams Data Firehose
Vai trò Thu thập + tự xử lý Load vào đích
Latency Real-time Near real-time
Replay ✔ ❌
Code consumer Tự viết Managed

Pattern: Streams (xử lý real-time) + Firehose (archive S3) chạy song song.

5. Amazon MQ — broker cho app legacy

SQS/SNS dùng protocol proprietary AWS. App on-prem hay dùng JMS, AMQP, MQTT, STOMP, OpenWire, WSS.

Không muốn viết lại → Amazon MQ (managed ActiveMQ / RabbitMQ): có queue (~SQS) và topic (~SNS), chạy trên broker instance (không phải serverless).

  • Scale: chạy trên 1 server, hoặc active/standby 2 AZ cho HA — không tự scale ngang như SQS/SNS; muốn tăng throughput phải tăng size instance (hoặc cluster nếu RabbitMQ).
  • Multi-AZ: bật active/standby → failover tự động khi broker chính chết.

SQS / SNS Amazon MQ
Protocol AWS SDK Industry standard
Scale Gần unlimited (SQS Standard) Theo instance
Migrate Đổi code Minimal change
App mới trên AWS ✔ Ưu tiên Chỉ khi bắt buộc legacy

6. So sánh & chọn đáp án

6.1 SQS vs SNS vs Kinesis

Tiêu chí SQS SNS Kinesis
Mô hình Pull queue Push pub/sub Stream (pull / EFO)
Sau khi đọc Delete → hết Không phải job queue Còn đến hết retention → replay
Ordering FIFO + Message Group FIFO topic Theo shard / partition key
Delay / DLQ DelaySeconds, DLQ Filter; DLQ tùy subscription Không giống SQS
Use case Job / worker / buffer DB Notification / fan-out Real-time analytics, IoT, ETL

6.2 Chọn nhanh theo nhu cầu

Nhu cầu Chọn
Decouple tier / job / buffer DB SQS
Order + exactly-once SQS FIFO
Poison message DLQ
Trì hoãn vài phút DelaySeconds
1 → nhiều SNS (± SQS fan-out)
S3 cùng event/prefix → nhiều queue S3 → SNS → SQS
Subset subscriber SNS filter
Stream + replay Kinesis Data Streams
Nhiều consumer không giành bandwidth EFO
Chỉ đổ vào S3/Redshift Data Firehose
JMS/ActiveMQ ít đổi code Amazon MQ

6.3 Tình huống thi

Đề bài (rút gọn) Đáp án
Web nhận order, worker encode, scale theo backlog SQS + ASG
Thanh toán đúng thứ tự từng user, không trùng SQS FIFO (Group = user/order)
Message lỗi mãi làm worker stuck DLQ
1 event → billing + analytics + fraud SNS → nhiều SQS
S3 images/ ObjectCreated → 3 queue S3 → SNS → 3 SQS
Chỉ notify khi severity=high SNS + filter
Clickstream, replay 7 ngày Kinesis Data Streams
IoT → S3, không tự viết consumer Data Firehose
Lift ActiveMQ/JMS Amazon MQ
RDS quá tải vì spike write App → SQS → worker → RDS
Hệ thống cũ cần nhận message gốc từ SQS (không muốn envelope SNS) Bật Raw Message Delivery
1 shard Kinesis bị hot, còn lại rảnh Shard Splitting
Message > 256 KB (video, file lớn) qua SQS Claim-check: SQS Extended Client Library + S3

Điểm hay ra thi

  • Decouple khi sync không chịu nổi spike.
  • SQS: DeleteMessage bắt buộc; Visibility 30s mặc định; Long Poll 20s; Standard vs FIFO; DLQ; DelaySeconds.
  • SQS mã hoá SSE-SQS mặc định (từ 2023, miễn phí); message > 256 KB → claim-check qua S3 (Extended Client Library).
  • FIFO High Throughput Mode: gần như unlimited nếu trải đều nhiều Message Group ID; tên queue luôn có hậu tố .fifo.
  • SNS fan-out → SQS: nhớ Access Policy; S3 1 rule/event+prefix → qua SNS.
  • SNS filter = JSON policy trên subscription.
  • SNS không lưu trữ: không subscriber = mất message; bật Raw Message Delivery khi cần message gốc qua SQS.
  • Kinesis ≠ SQS: stream + replay; partition key; record tối đa 1 MiB (dễ nhầm với 10); retention mặc định 24h, tối đa 365 ngày.
  • Kinesis resharding: Split (tăng, tốn thêm) / Merge (giảm, tiết kiệm); KCL checkpoint vào DynamoDB.
  • Provisioned vs On-demand; Shared vs EFO.
  • Firehose = delivery near real-time, không replay.
  • Amazon MQ chỉ khi protocol legacy / minimal refactor; scale bằng tăng size instance, không auto-scale ngang.

Takeaway cá nhân

  • Học theo mạch: queue (SQS) → pub/sub (SNS) → stream (Kinesis) → legacy (MQ).
  • Combo thi nhiều nhất: SNS + SQS fan-out và SQS mechanics (visibility / DLQ / FIFO group).
  • Đừng gọi Kinesis là “SQS xịn” — khác mô hình hoàn toàn.
