9.4 – ElastiCache

ElastiCache là gì?

ElastiCache là dịch vụ managed in-memory cache của AWS, hỗ trợ hai engine:

  • Redis — đa năng, HA, persistence.
  • Memcached — đơn giản, scale-out tốt.

Cache = dữ liệu trong RAM → nhanh hơn RDS/DB nhiều lần (microseconds vs milliseconds).

Tương tự cách RDS quản lý database, ElastiCache quản lý cache — không cần lo OS/patching/monitoring.

Tại sao cần ElastiCache?

Lợi ích Mô tả
Giảm tải DB Các read query phổ biến không cần đến RDS/Aurora
Cực nhanh In-memory, microsecond latency
Giúp app stateless Lưu session vào cache → không phụ thuộc vào instance
Giảm chi phí DB Ít query đến DB → ít IOPS → ít tiền

⚠️ Quan trọng: Sử dụng ElastiCache cần sửa code ứng dụng để thêm cache logic.

Kiến trúc 1: Database Cache Pattern

Luồng hoạt động:

  1. App query ElastiCache.
  2. Cache hit → trả data ngay (microseconds).
  3. Cache miss → đọc từ RDS → lưu vào cache → trả về user.
  4. Lần sau đọc lại → luôn nhanh.

Phải có chiến lược invalidation để tránh dùng dữ liệu cũ (stale data).

Kiến trúc 2: User Session Store

Lợi ích: App trở thành stateless — các request của cùng 1 user có thể đến bất kỳ EC2 nào mà vẫn login bình thường. Dễ scale ngang.

Redis vs Memcached — Chọn cái nào?

Tiêu chí Redis Memcached
Multi-AZ + Auto Failover ✔ Có ❌ Không
Read Replicas ✔ Có ❌ Không
Persistence (dữ liệu không mất khi restart) ✔ Có (AOF) ❌ Không
Backup & Restore ✔ Có ❌ Không
Cấu trúc dữ liệu phong phú ✔ String, Hash, List, Set, Sorted Set ❌ Chỉ String
Multi-threading ❌ Single-thread ✔ Multi-thread
Scale-out (sharding) ✔ Có ✔ Tốt hơn Redis
Độ đơn giản Trung bình Rất đơn giản

Khi nào chọn Redis:

  • Cần HA (Multi-AZ failover).
  • Cần persistence (không mất cache khi restart).
  • Cần backup/restore.
  • Dùng Sorted Sets (leaderboard, ranking).
  • Session store quan trọng.
  • Pub/Sub messaging.

Khi nào chọn Memcached:

  • Cache thuần, dữ liệu không quan trọng.
  • Muốn scale-out dễ dàng bằng sharding.
  • Cần multi-thread để tận dụng CPU.
  • Không cần HA hay persistence.

3 Cache Patterns quan trọng nhất

1. Lazy Loading (Cache-Aside) — Phổ biến nhất

Ưu điểm: Đơn giản, chỉ cache data thực sự được đọc.

Nhược điểm: Lần đầu luôn chậm (cache miss). Dữ liệu có thể cũ (stale).

2. Write-Through

App ghi vào DB → đồng thời ghi luôn vào cache.

Ưu điểm: Cache luôn đồng bộ với DB, không bao giờ stale.

Nhược điểm: Mọi write đều chậm hơn (double write). Cache chứa nhiều data không cần thiết.

3. Session Store

Lưu session user (login state) vào Redis. Các instance app đọc Redis để kiểm tra session.

App trở thành stateless → scale ngang thoải mái.

ElastiCache Security

Redis AUTH

  • Tạo Redis cluster → set password/token.
  • Client gửi AUTH <password> mới truy cập được.
  • Hỗ trợ TLS/SSL in-flight encryption.
  • Đây là cách bảo vệ phổ biến nhất trong thực tế.

IAM Authentication (chỉ cho Redis)

  • Bảo vệ cấp API (quản lý ElastiCache trên AWS Console/CLI).
  • Không bảo vệ runtime traffic giữa app ↔ Redis.

Security Group

  • Kiểm soát ai được kết nối vào Redis (port 6379) / Memcached (port 11211).
  • Luôn là lớp bảo vệ bắt buộc.

Memcached

  • Chỉ hỗ trợ SASL authentication (phức tạp, ít dùng).
  • Bảo vệ chủ yếu qua Security Group.

Redis Use Case đặc biệt: Sorted Sets cho Leaderboard

Vấn đề: Cần cập nhật bảng xếp hạng real-time với hàng triệu người dùng.

Giải pháp: Redis Sorted Sets:

  • Đảm bảo unique key và sorted order theo score.
  • Khi user có điểm mới → Redis xếp hạng lại real-time.
  • Không cần query DB phức tạp (ORDER BY, aggregate…).

Use cases thi hay hỏi: Game leaderboard, ranking system, social score, top-N queries → Redis Sorted Set.

Bảng từ khoá đề thi

Từ khoá trong đề Chọn
"Cần HA, persistence, backup/restore cho cache" Redis
"Cần scale-out đơn giản, multi-thread, không quan tâm mất data khi restart" Memcached
"Leaderboard/ranking real-time hàng triệu user" Redis Sorted Sets
"Giảm tải DB cho read phổ biến, chấp nhận data có thể cũ" Lazy Loading (Cache-Aside)
"Cache không bao giờ được stale, chấp nhận write chậm hơn" Write-Through
"Giúp app stateless để scale ngang" Session Store (Redis)
"Bảo vệ runtime traffic app ↔ cache" Redis AUTH (không phải IAM — IAM chỉ bảo vệ API-level)

Xem thêm góc nhìn "domain thi": 3.4 - Caching - ElastiCache, CloudFront.

Điểm hay ra thi

  • ElastiCache cần sửa code — không transparent như RDS.
  • Redis khi cần HA, persistence, Sorted Sets.
  • Memcached khi cần scale-out đơn giản, multi-thread.
  • Lazy Loading = phổ biến nhất, nhưng có thể stale.
  • Write-Through = không stale, nhưng write chậm hơn.
  • Session Store = giúp app stateless → scale ngang.
  • Redis AUTH (password) là bảo vệ runtime, không phải IAM.

Takeaway cá nhân

  • ElastiCache là lớp cache giữa app và DB — giảm tải DB, tăng tốc response.
  • Chọn Redis khi cần bất cứ tính năng HA/persistence/data structures; chọn Memcached khi chỉ cần cache đơn giản + scale-out.
  • Session Store pattern là cách phổ biến nhất để làm app stateless trong kiến trúc Cloud.
