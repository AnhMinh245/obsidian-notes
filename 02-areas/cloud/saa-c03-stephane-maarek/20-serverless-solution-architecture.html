20 – Serverless Solution Architecture: 4 case study kiến trúc

Cách đọc note này: Đây là bài tổng hợp và vận dụng — không giới thiệu dịch vụ mới mà ghép các dịch vụ đã học (§19 Serverless, §15 CloudFront, §17 Decoupling) thành kiến trúc thật. Đọc theo 4 case study: (1) Mobile app → (2) Website toàn cầu → (3) Microservices → (4) Offload chi phí bằng CloudFront.

Cách học hiệu quả nhất: với mỗi case, hãy đọc requirement trước, tự vẽ kiến trúc, rồi mới xem đáp án. Đề thi SAA-C03 hỏi đúng kiểu này — cho requirement, chọn kiến trúc.

1. Case study 1 — Mobile App "MyTodoList"

1.1 Yêu cầu đề bài

# Yêu cầu Dịch ra dịch vụ
1 Expose dưới dạng REST API với HTTPS API Gateway
2 Kiến trúc serverless Lambda (không EC2)
3 User truy cập trực tiếp folder riêng của mình trên S3 Cognito Identity Pools + IAM policy theo user
4 User xác thực qua managed serverless service Cognito User Pools
5 User đọc nhiều hơn ghi to-do Cần cache
6 Database phải scale và có read throughput cao DynamoDB + DAX

1.2 Bước 1 — Tầng REST API

Luồng: Mobile client → API Gateway (HTTPS) → Lambda → DynamoDB

  • API Gateway lo phần HTTPS, routing, throttling, versioning
  • Lambda chứa business logic — không có server nào phải quản lý
  • DynamoDB lưu to-do, scale tự động

Đây là kiến trúc serverless kinh điển nhất trong SAA-C03: API Gateway → Lambda → DynamoDB. Thấy đề bài nói "REST API serverless" thì gần như chắc chắn đáp án chứa bộ ba này.

1.3 Bước 2 — Cho user truy cập trực tiếp S3

Vấn đề: Nếu bắt file đi qua Lambda thì tốn tiền, chậm, và vướng giới hạn payload (6 MB). Muốn client upload/download thẳng vào S3 nhưng mỗi user chỉ được vào folder của mình.

Giải pháp — Cognito Identity Pools:

  1. User đăng nhập qua Cognito User Pools → nhận JWT token
  2. Đổi token đó ở Cognito Identity Pools → nhận AWS credentials tạm thời (qua STS)
  3. Credentials gắn IAM policy giới hạn theo user_id → chỉ truy cập được prefix riêng
  4. Client gọi thẳng S3 API với credentials đó

Pattern quan trọng: cách này áp dụng được cho cả DynamoDB và Lambda, không chỉ S3 — bất cứ khi nào muốn end-user gọi thẳng AWS API với quyền giới hạn theo từng người.

IAM policy dùng biến ${cognito-identity.amazonaws.com:sub} trong Resource ARN để tự động khoá user vào folder của họ.

1.4 Bước 3 — Read throughput cao với DAX

Vấn đề: User đọc nhiều hơn ghi rất nhiều → DynamoDB bị nghẽn đọc (read congestion), tốn RCU.

Giải pháp — DynamoDB Accelerator (DAX):

  • Cache in-memory ngay trước DynamoDB
  • Latency xuống mức microsecond
  • Không cần sửa code (tương thích API DynamoDB)
  • TTL mặc định 5 phút

1.5 Bước 4 — Cache thêm ở tầng API Gateway

Vấn đề: DAX đã cache database, nhưng Lambda vẫn phải chạy mỗi request → vẫn tốn tiền và tốn thời gian.

Giải pháp — API Gateway Caching: cache response ngay tại API Gateway → request trùng nhau không chạm tới Lambda luôn.

Hai tầng cache khác nhau — đừng nhầm:

DAX API Gateway Caching
Cache cái gì Kết quả query DynamoDB Response HTTP hoàn chỉnh
Nằm ở đâu Giữa Lambda và DynamoDB Trước Lambda
Tiết kiệm RCU của DynamoDB Cả Lambda invocation lẫn DynamoDB
Ảnh hưởng Chỉ giảm tải DB Giảm tải toàn bộ backend

Nguyên tắc kiến trúc: cache càng gần client càng tiết kiệm — vì chặn được nhiều tầng phía sau hơn. Nhưng cũng càng khó invalidate khi data đổi.

1.6 Tổng kết case 1

Thành phần Vai trò
API Gateway REST API + HTTPS + caching
Lambda Business logic serverless
DynamoDB Database scale tự động
DAX Cache read cho DynamoDB
Cognito User Pools Authentication (đăng nhập)
Cognito Identity Pools Cấp AWS credentials tạm, giới hạn theo user

2. Case study 2 — Website serverless toàn cầu "MyBlog.com"

2.1 Yêu cầu đề bài

# Yêu cầu Dịch ra dịch vụ
1 Scale toàn cầu CloudFront
2 Blog ít ghi, đọc rất nhiều Cache + read replica toàn cầu
3 Một phần static file, phần còn lại là REST API động S3 + API Gateway/Lambda
4 Cache ở mọi nơi có thể CloudFront + API Gateway cache
5 User đăng ký mới → nhận email chào mừng DynamoDB Streams → Lambda → SES
6 Ảnh upload lên blog → tự tạo thumbnail S3 Event → Lambda

2.2 Bước 1 — Phục vụ static content toàn cầu

S3 lưu static file (HTML/CSS/JS/ảnh) + CloudFront phân phối qua edge location toàn cầu → user ở đâu cũng tải nhanh, và S3 chỉ bị gọi khi cache miss.

2.3 Bước 2 — Phục vụ static content một cách BẢO MẬT

Vấn đề: Nếu S3 bucket để public thì user có thể bypass CloudFront, gọi thẳng S3 URL → mất khả năng kiểm soát, mất WAF, mất log, và tốn tiền hơn.

Giải pháp: Khoá bucket lại (block public access) và chỉ cho CloudFront đọc:

Cơ chế Trạng thái
OAC — Origin Access Control Khuyến nghị hiện nay — hỗ trợ SSE-KMS, mọi region, tất cả HTTP method
OAI — Origin Access Identity Legacy — vẫn hoạt động nhưng AWS không khuyến khích dùng cho thiết kế mới

Bẫy thi: Đề nói "static website toàn cầu, bucket không được public" → đáp án là CloudFront + OAC (hoặc OAI trong đề cũ) + bucket policy chỉ cho phép CloudFront.

2.4 Bước 3 — Thêm REST API serverless công khai

Phần động dùng lại bộ ba quen thuộc: API Gateway → Lambda → DynamoDB.

Điểm khác case 1: API này public, ai cũng đọc blog được → không cần Cognito. Chỉ khi cần phân biệt danh tính user mới cần authentication. Đây là chi tiết quan trọng — đừng nhét Cognito vào mọi kiến trúc.

2.5 Bước 4 — DynamoDB Global Tables cho dữ liệu toàn cầu

  • Blog được đọc từ khắp thế giới → nếu DynamoDB chỉ ở 1 region thì user xa vẫn chịu latency cao
  • Global Tables replicate Active-Active sang nhiều region → đọc/ghi ở region nào cũng được
  • Điều kiện tiên quyết: phải bật DynamoDB Streams

Lựa chọn thay thế: có thể dùng Aurora Global Database nếu cần dữ liệu quan hệ. Khác biệt: Aurora Global Database chỉ ghi được ở primary region (secondary là read-only), còn DynamoDB Global Tables ghi được ở mọi region.

2.6 Bước 5 — Luồng gửi email chào mừng

Các mắt xích cần nhớ:

  • DynamoDB Streams bắt sự kiện item mới được insert
  • Lambda được trigger bởi stream, có IAM role cho phép gọi SES
  • Amazon SES (Simple Email Service) gửi email theo cách serverless

SES là dịch vụ gửi email serverless của AWS — hay xuất hiện trong đề thi ở tình huống "gửi email transactional/notification". Đừng nhầm với SNS (SNS gửi được email nhưng chỉ dạng notification đơn giản cho subscriber, không phù hợp email marketing/transactional có template).

2.7 Bước 6 — Luồng tạo thumbnail

S3 có thể trigger 3 đích: SQS, SNS, hoặc Lambda (và EventBridge). Nhớ lại giới hạn ở §17: mỗi cặp event type + prefix chỉ có 1 rule → muốn fan-out nhiều đích thì đi qua SNS hoặc EventBridge.

2.8 Tổng kết case 2

Bài học Nội dung
Static content CloudFront + S3, bảo mật bằng OAC/OAI
REST API Serverless (API Gateway + Lambda), không cần Cognito vì public
Data toàn cầu DynamoDB Global Tables (có thể thay bằng Aurora Global Database)
Event từ database Bật DynamoDB Streams → trigger Lambda
Quyền cho Lambda Lambda có IAM role để gọi SES
Gửi email serverless Amazon SES
Event từ storage S3 trigger SQS / SNS / Lambda

3. Case study 3 — Kiến trúc Microservices

3.1 Bối cảnh

  • Muốn chuyển sang kiến trúc microservices
  • Nhiều service gọi lẫn nhau trực tiếp qua REST API
  • Mỗi microservice có thể có kiến trúc riêng, khác nhau hoàn toàn — không bắt buộc đồng nhất
  • Mục tiêu: development lifecycle gọn nhẹ hơn cho từng service (deploy độc lập, team độc lập)

3.2 Hai nhóm pattern giao tiếp

Nhóm Dịch vụ Đặc điểm
Synchronous API Gateway, Load Balancer (ALB/NLB) Gọi và chờ response ngay; đơn giản nhưng dễ sập dây chuyền khi service đích quá tải
Asynchronous SQS, Kinesis, SNS, Lambda trigger (từ S3) Qua trung gian; chịu spike tốt, scale độc lập — xem [[17 - Decoupling Applications - SQS SNS Kinesis MQ

3.3 Thách thức của microservices

  • Overhead lặp lại mỗi lần tạo microservice mới (CI/CD, monitoring, logging… phải dựng lại từ đầu)
  • Khó tối ưu mật độ/hiệu suất sử dụng server (server density/utilization) — mỗi service chiếm tài nguyên riêng, dễ lãng phí
  • Phức tạp khi chạy đồng thời nhiều version của nhiều microservice
  • Bùng nổ code phía client để tích hợp với hàng loạt service riêng lẻ

3.4 Serverless giải quyết được gì?

Thách thức Serverless xử lý thế nào
Server utilization thấp, tốn tiền lúc rảnh API Gateway & Lambda tự scale, trả tiền theo mức dùng — không có "server rảnh"
Overhead dựng môi trường mới Clone API dễ dàng, tái tạo môi trường (dev/test/prod) nhanh
Client phải tự viết code tích hợp Sinh client SDK tự động qua tích hợp Swagger/OpenAPI của API Gateway

Ý chính cần nhớ: Serverless không xoá hết thách thức của microservices, nhưng xử lý gọn 3 vấn đề tốn kém nhất: scaling, chi phí lúc idle, và công sức dựng môi trường.

4. Case study 4 — Offload chi phí phân phối phần mềm

4.1 Bối cảnh & vấn đề

  • Ứng dụng chạy trên EC2, thỉnh thoảng phát hành bản cập nhật phần mềm
  • Khi có bản mới: request tăng vọt, nội dung được phân phối ồ ạt qua mạng → rất tốn tiền (bandwidth + EC2 phải scale)
  • Ràng buộc quan trọng: KHÔNG được sửa ứng dụng — chỉ được tối ưu chi phí và CPU

4.2 Giải pháp — đặt CloudFront lên phía trước

4.3 Vì sao CloudFront là đáp án?

Lý do Giải thích
Không đổi kiến trúc Chỉ thêm CloudFront ở phía trước — ứng dụng giữ nguyên, đúng ràng buộc đề bài
Cache file update tại edge File update là static, không bao giờ đổi → cache cực hiệu quả (hit rate rất cao)
EC2 không serverless, nhưng CloudFront thì có CloudFront tự scale thay cho bạn
ASG scale ít hơn Tiết kiệm lớn chi phí EC2
Tiết kiệm bandwidth Traffic từ CloudFront ra Internet rẻ hơn từ EC2/ALB ra Internet
Tăng availability Origin ít bị dội → ổn định hơn

Pattern cần thuộc lòng: đề bài có các cụm "không muốn thay đổi ứng dụng" + "nội dung tĩnh" + "giảm chi phí / giảm tải EC2" → đáp án là thêm CloudFront ở phía trước. Đây là cách dễ nhất biến một ứng dụng có sẵn thành scalable + rẻ hơn.

5. Tổng hợp — quy tắc rút ra từ 4 case

5.1 Bản đồ pattern

Nhu cầu trong đề bài Pattern
REST API serverless API Gateway → Lambda → DynamoDB
Cho end-user gọi thẳng AWS API với quyền riêng từng người Cognito User Pool → Identity Pool → STS → S3/DynamoDB
Đọc nhiều, giảm tải database DAX (cache DB)
Đọc nhiều, giảm luôn cả Lambda API Gateway Caching (cache response)
Static content toàn cầu, bucket không được public CloudFront + OAC + S3 (block public access)
Dữ liệu đọc/ghi ở nhiều region DynamoDB Global Tables (cần Streams)
Phản ứng khi database thay đổi DynamoDB Streams → Lambda
Gửi email serverless Amazon SES
Xử lý file ngay khi upload S3 Event → Lambda
Fan-out từ S3 tới nhiều đích S3 → SNS → nhiều SQS (hoặc EventBridge)
Giảm chi phí app EC2 có sẵn, không sửa code Thêm CloudFront phía trước

5.2 Nguyên tắc thiết kế rút ra

  1. Cache theo tầng, càng gần client càng lời — CloudFront (edge) → API Gateway (response) → DAX (query) → DynamoDB.
  2. Đừng nhét authentication khi không cần — API public (như blog) thì bỏ Cognito, đơn giản và rẻ hơn.
  3. Cho client gọi thẳng AWS thay vì proxy qua Lambda khi có thể (S3 upload/download) — tránh giới hạn payload và tiết kiệm chi phí compute.
  4. Event-driven thay vì polling — DynamoDB Streams, S3 Events tự đẩy, không cần job quét định kỳ.
  5. Khoá origin lại — bucket public là lỗ hổng kiến trúc, luôn dùng OAC.
  6. Ràng buộc "không được sửa app" gần như luôn dẫn tới CloudFront hoặc một lớp managed đặt phía trước.

5.3 Tình huống thi

Đề bài (rút gọn) Đáp án
Mobile app cần REST API serverless, user đăng nhập API Gateway + Lambda + DynamoDB + Cognito User Pool
User mobile cần upload thẳng lên folder riêng trên S3 Cognito Identity Pool + IAM policy theo user_id
DynamoDB đọc rất nhiều, muốn microsecond, không sửa code DAX
Muốn giảm cả số lần gọi Lambda cho request lặp lại API Gateway Caching
Static website toàn cầu, bucket phải private CloudFront + OAC
Blog đọc toàn cầu, cần ghi ở nhiều region DynamoDB Global Tables
Cần email chào mừng khi có user mới trong DynamoDB Streams → Lambda → SES
Ảnh upload S3 cần tạo thumbnail tự động S3 Event → Lambda
App EC2 phân phối file update tốn tiền, không được sửa code CloudFront phía trước
Microservices cần giao tiếp chịu được spike Pattern async: SQS/SNS/Kinesis

Điểm hay ra thi

  • Bộ ba serverless kinh điển: API Gateway → Lambda → DynamoDB.
  • Cognito User Pool = đăng nhập; Cognito Identity Pool = cấp AWS credentials tạm để client gọi thẳng S3/DynamoDB với quyền theo user_id.
  • Hai tầng cache khác nhau: DAX cache query DynamoDB; API Gateway cache response HTTP (chặn luôn Lambda).
  • CloudFront + S3 cho static content; bảo mật bằng OAC (khuyến nghị) hoặc OAI (legacy) + block public access.
  • DynamoDB Global Tables cần bật Streams; ghi được ở mọi region (khác Aurora Global Database chỉ ghi ở primary).
  • DynamoDB Streams → Lambda → SES là luồng chuẩn để gửi email khi có thay đổi dữ liệu.
  • S3 có thể trigger SQS / SNS / Lambda (và EventBridge).
  • API public thì không cần Cognito — đừng thêm authentication thừa.
  • Microservices: sync (API Gateway, ALB) vs async (SQS, SNS, Kinesis, Lambda trigger); Serverless giải quyết scaling, chi phí idle, và việc clone môi trường.
  • "Không được thay đổi ứng dụng" + "nội dung tĩnh" + "giảm chi phí" → thêm CloudFront.

Takeaway cá nhân

  • Bài này không dạy dịch vụ mới — nó dạy cách ghép. Giá trị nằm ở việc đọc requirement rồi map ra dịch vụ, đúng kỹ năng đề thi kiểm tra.
  • Mẹo làm bài: gạch chân từng từ khoá ràng buộc trong đề (serverless / toàn cầu / không sửa code / đọc nhiều / mỗi user riêng) — mỗi từ khoá thường khoá chặt đúng một dịch vụ.
  • Nhớ nhất 2 pattern "kiếm điểm dễ": CloudFront phía trước để offload, và Cognito Identity Pool để client gọi thẳng AWS.
  • Cache là chủ đề xuyên suốt bài này — luôn tự hỏi "có thể cache ở tầng nào cao hơn nữa không?".
