1. Lambda, SNS & SQS — pattern retry & DLQ

Cùng một câu hỏi: Lambda fail thì chuyện gì xảy ra? — câu trả lời khác nhau tuỳ Lambda được trigger bởi cái gì. Đây là 3 tình huống hay bị gộp nhầm với nhau.

1.1 SNS → Lambda (asynchronous invocation)

  • SNS gọi Lambda theo kiểu asynchronous invocation — SNS "ném" event rồi đi tiếp, không chờ Lambda trả lời.
  • Lambda fail → tự động retry (mặc định tối đa 2 lần, có backoff giữa các lần).
  • Retry hết vẫn fail → event được đẩy vào Lambda Destination hoặc DLQ (SQS/SNS) cấu hình trực tiếp trên function Lambda.

1.2 SQS Standard → Lambda (poll-based, DLQ nằm ở SQS)

  • Lambda không được SNS/S3 "gọi thẳng" — Lambda tự poll SQS qua Event Source Mapping.
  • Mỗi lần poll xong, Lambda được invoke synchronous với batch message đó.
  • Lambda fail → message không bị xoá → hiện lại sau visibility timeout → retry.
  • Fail đủ số lần maxReceiveCount → message sang DLQ của chính SQS queue đó (không phải DLQ của Lambda).

Khác biệt cốt lõi so với §1.1: DLQ nằm ở đâu quyết định bởi ai chủ động gọi ai. SNS chủ động push vào Lambda → DLQ cấu hình trên Lambda. Lambda chủ động poll SQS → DLQ cấu hình trên SQS.

1.3 SQS FIFO → Lambda — rủi ro "blocking"

  • SQS FIFO xử lý tuần tự theo Message Group (xem lại §17).
  • Lambda fail khi xử lý 1 message trong group → toàn bộ message sau nó trong cùng group bị block (không được xử lý tiếp, vì FIFO không cho phép "nhảy cóc" thứ tự).
  • Chuỗi retry lặp lại tới maxReceiveCount → message lỗi chuyển sang FIFO DLQ → group được unblock, các message còn lại xử lý tiếp.

Bẫy hay thi: SQS FIFO + Lambda dùng đúng khi cần thứ tự tuyệt đối, nhưng phải ý thức đánh đổi: 1 message "poison" có thể chặn đứng cả group cho tới khi nó rơi vào DLQ. Đây là lý do SQS Standard vẫn được ưu tiên mặc định trừ khi đề bài đòi hỏi ordering rõ ràng.

1.4 Tổng kết 3 pattern

Trigger Kiểu invoke Retry mặc định DLQ đặt ở đâu Rủi ro riêng
SNS → Lambda Asynchronous 2 lần, có backoff Lambda (Destination/DLQ) Mất order hoàn toàn (SNS không giữ thứ tự)
SQS Standard → Lambda Poll rồi invoke sync Tới maxReceiveCount SQS queue Có thể xử lý trùng (at-least-once)
SQS FIFO → Lambda Poll rồi invoke sync, theo group Tới maxReceiveCount FIFO DLQ 1 message lỗi block cả group

3 pattern gốc từ slide: SQS→Lambda (poll), SQS FIFO→Lambda (retry blocking), SNS→Lambda (asynchronous, có vòng lặp retries riêng trước khi rơi vào DLQ).

2. Fan-out: PUT trực tiếp vào nhiều SQS vs qua SNS

Bài toán quen: 1 producer cần đẩy dữ liệu tới nhiều SQS queue (ví dụ: billing, analytics, fraud).

2.1 Option 1 — Producer tự PUT vào từng queue

Producer dùng SDK gọi SendMessage lần lượt vào từng queue (PUT #1, PUT #2…).

Nhược điểm Giải thích
Producer phải biết trước danh sách toàn bộ queue đích Thêm queue mới → phải sửa code producer
Chậm hơn N lần gọi API thay vì 1
Không atomic PUT #1 thành công, PUT #2 fail → dữ liệu lệch giữa các queue

2.2 Option 2 — Fan-out qua SNS (khuyến nghị)

Producer chỉ PUT một lần vào SNS Topic; mỗi SQS queue là một subscription. Muốn thêm queue thứ 3 (PUT #3) → chỉ cần subscribe thêm, không đụng code producer.

Đây chính là Fan-out Pattern đã học kỹ ở §17.3.2 — note này chỉ nhấn thêm lý do vì sao Option 2 luôn thắng Option 1: tách rời hoàn toàn producer khỏi danh sách consumer, đúng tinh thần decoupling.

3. S3 Event Notifications — recap và mở rộng với EventBridge

3.1 S3 Event Notifications cơ bản

  • Sự kiện: S3:ObjectCreated, S3:ObjectRemoved, S3:ObjectRestore, S3:Replication…
  • Filter được theo tên object (ví dụ *.jpg).
  • Đích: SNS, SQS, hoặc Lambda Function trực tiếp.
  • Use case kinh điển: upload ảnh lên S3 → tự tạo thumbnail.
  • Có thể tạo nhiều "S3 event" rule tuỳ ý, nhưng nhớ giới hạn đã học: 1 rule / (event type + prefix) — muốn fan-out nhiều đích cho cùng 1 event+prefix thì phải qua SNS.
  • Độ trễ: sự kiện thường tới trong vài giây, nhưng đôi khi có thể mất tới một phút hoặc hơn.

3.2 S3 Event Notifications với Amazon EventBridge

Khi cần filter phức tạp hơn hoặc nhiều đích hơn, route tất cả S3 event qua EventBridge thay vì cấu hình rule riêng lẻ:

Khả năng Chi tiết
Filtering nâng cao JSON rule theo metadata, object size, tên object… (linh hoạt hơn filter theo prefix/suffix cơ bản)
Đích Trên 18 AWS service làm target — ví dụ Step Functions, Kinesis Data Streams/Firehose
Khả năng riêng của EventBridge Archive (lưu trữ sự kiện), Replay (phát lại sự kiện cũ), reliable delivery

Chọn nhanh: cần đơn giản, ít đích, filter theo tên/prefix → S3 Event Notifications cơ bản. Cần filter theo metadata/size, nhiều đích cùng lúc, hoặc cần archive & replay sự kiện → S3 Event Notifications qua EventBridge.

4. EventBridge — chặn API call nguy hiểm (case study)

Bài toán: muốn được báo động ngay lập tức khi có ai đó gọi một API nguy hiểm — ví dụ DeleteTable trên DynamoDB.

Luồng:

  1. CloudTrail ghi log mọi API call trong account (đã bật by default cho management events).
  2. EventBridge có rule khớp đúng loại event (DeleteTable, hoặc rộng hơn: bất kỳ API call nào match pattern).
  3. Match → EventBridge trigger SNS → gửi alert cho team vận hành.

Pattern cần nhớ: "CloudTrail + EventBridge + SNS" = công thức chuẩn để giám sát/chặn cảnh báo cho một API call cụ thể mà không cần build hệ thống logging riêng. Đây là cách dùng EventBridge như một interceptor cho control-plane API, khác hẳn với việc dùng nó cho data event (S3, đơn hàng…).

5. API Gateway — gọi thẳng AWS service (Service Integration)

Bài toán: Client gửi record liên tục, muốn lưu xuống S3 dạng .json mà không cần Lambda làm trung gian.

  • API Gateway hỗ trợ gọi thẳng một AWS service khác (không qua Lambda) — gọi là AWS Service Integration.
  • Ở đây: API Gateway map request trực tiếp vào Kinesis Data Streams → Kinesis Data Firehose đọc lại và lưu S3 dưới dạng file .json.
  • Lợi ích: bớt một tầng Lambda → giảm latency, giảm chi phí invocation cho những luồng chỉ cần "nhận rồi chuyển tiếp", không có business logic phức tạp.

Khi nào chọn: đề bài nói "không cần business logic", chỉ cần nhận request rồi đẩy thẳng vào service khác (Kinesis, SQS, SNS, DynamoDB, Step Functions…) → nghĩ ngay tới API Gateway Service Integration thay vì mặc định chèn Lambda vào giữa.

7. Case study — Chặn một địa chỉ IP

Series slide này cho thấy cùng một yêu cầu ("chặn 1 IP xấu") đòi hỏi kiến trúc khác nhau tuỳ layer đang dùng — rất hay bị hỏi dạng "which of the following can you use to block a specific IP".

7.1 Chỉ EC2 + Security Group — KHÔNG chặn được

  • Security Group chỉ có allow rule, không có deny → không thể dùng SG để chặn riêng 1 IP xấu.
  • Muốn chặn ở layer network → phải dùng NACL (Network ACL) — đây là thành phần duy nhất trong VPC có deny rule tường minh theo IP.

7.2 Thêm ALB — client IP bị "che" khỏi EC2

  • ALB terminate connection — EC2 phía sau chỉ thấy private IP của ALB, không thấy IP gốc của client (IP gốc chỉ còn nằm trong header X-Forwarded-For).
  • Vì vậy: Security Group của EC2 không thể chặn theo IP client thật. Việc chặn IP phải làm trước ALB, ở tầng NACL của public subnet.

7.3 Thay bằng NLB — client IP vẫn "sống"

  • NLB hoạt động ở Layer 4, không terminate connection như ALB — client IP thật vẫn tới được EC2.
  • Vì vậy Security Group của EC2 có thể chặn theo IP client thật khi đứng sau NLB — khác hẳn trường hợp ALB ở §7.2.

7.4 Thêm AWS WAF — công cụ đúng để chặn IP

  • Thay vì loay hoay với NACL/SG, AWS WAF sinh ra đúng để làm việc này: gắn IP set rule vào ALB (hoặc CloudFront, API Gateway) để filter theo IP — quản lý tập trung, dễ update runtime, không cần đổi hạ tầng mạng.

7.5 Thêm CloudFront — chặn ở edge, xa client nhất có thể

  • Nếu chỉ chặn IP trực tiếp tại ALB public thì không hiệu quả — traffic đã đi xa vào hạ tầng, và IP nguồn khi qua CloudFront sẽ là dải IP của CloudFront, không phải IP client gốc nữa.
  • Giải pháp đúng: gắn WAF vào CloudFront (không phải ALB) để lọc theo IP ngay tại edge, kết hợp thêm CloudFront Geo Restriction nếu cần chặn theo quốc gia.

7.6 Tổng kết — chọn đúng layer để chặn IP

Kiến trúc Chặn IP ở đâu Vì sao
EC2 trần NACL SG không có deny rule
EC2 sau ALB NACL trước ALB, không phải SG của EC2 ALB che IP client thật
EC2 sau NLB SG của EC2 vẫn dùng được NLB pass-through IP client
Có ALB AWS WAF gắn vào ALB Công cụ chuẩn, quản lý tập trung
Có CloudFront AWS WAF gắn vào CloudFront (+ Geo Restriction) Chặn ở edge, gần client nhất; chặn tại ALB lúc này vô nghĩa vì nguồn traffic đã là IP CloudFront

8. High Performance Computing (HPC) trên AWS

8.1 Vì sao cloud hợp để làm HPC

  • Tạo rất nhiều resource gần như tức thì.
  • Rút ngắn thời gian ra kết quả bằng cách thêm resource (scale out thay vì chờ).
  • Chỉ trả tiền cho phần đã dùng.
  • Use case: genomics, computational chemistry, financial risk modeling, dự báo thời tiết, machine learning/deep learning, xe tự lái.

8.2 Data management & transfer

Dịch vụ Dùng khi
AWS Direct Connect Chuyển GB/s dữ liệu lên cloud qua mạng riêng, bảo mật, ổn định
Snowball & Snowmobile Chuyển PB dữ liệu — khối lượng quá lớn để đi qua network
AWS DataSync Chuyển lượng dữ liệu lớn giữa on-premises và S3 / EFS / FSx for Windows

8.3 Compute & Networking

EC2:

  • Instance CPU optimized, GPU optimized tuỳ loại workload.
  • Spot Instances / Spot Fleet để tiết kiệm chi phí, kết hợp Auto Scaling.

Placement Group — Cluster:

  • Gom EC2 vào cùng rack, cùng AZ → network performance tốt (băng thông cao, latency thấp) — đúng nhu cầu HPC là các node giao tiếp với nhau liên tục.

Enhanced Networking (SR-IOV):

Option Băng thông Ghi chú
Elastic Network Adapter (ENA) Tới 100 Gbps Khuyến nghị hiện nay
Intel 82599 VF Tới 10 Gbps Legacy

Elastic Fabric Adapter (EFA):

  • Phiên bản nâng cấp của ENA dành riêng cho HPC, chỉ chạy trên Linux.
  • Tối ưu cho giao tiếp giữa các node (inter-node communication), workload tightly coupled.
  • Dùng chuẩn Message Passing Interface (MPI).
  • Bypass OS Linux bên dưới để đạt latency thấp, transport đáng tin cậy.

Phân biệt nhanh: ENA = network card tốc độ cao cho mọi loại EC2. EFA = ENA "độ" thêm riêng cho HPC multi-node, chỉ Linux, chỉ có giá trị khi các node cần nói chuyện với nhau liên tục (không phải khi chỉ cần băng thông ra ngoài internet).

9. Case study — Highly Available EC2 instance

Bối cảnh chung: một EC2 instance đơn lẻ (không phải web farm phía sau load balancer) cần tự phục hồi khi AZ gặp sự cố, mà vẫn giữ nguyên 1 địa chỉ truy cập cố định cho client — ví dụ một server nội bộ, một API endpoint duy nhất mà hệ thống khác đã hard-code IP.

9.1 Cách A — Auto Scaling Group + Elastic IP

Kiến trúc — từng bước:

  1. Auto Scaling Group cấu hình min = 1, max = 1, desired = 1, trải trên ≥ 2 Availability Zone.
  2. Instance chết (health check fail) → ASG tự launch instance thay thế ở một AZ khác.
  3. Instance mới chạy EC2 User Data script ngay lúc boot → script này tự gọi AWS API để attach Elastic IP đã biết trước (tìm theo Tag, hoặc parameter cố định).
  4. Instance cần có IAM Role cho phép gọi API AssociateAddress để tự attach Elastic IP đó.

Vì sao thiết kế vậy:

  • min=max=desired=1 đảm bảo luôn có đúng 1 instance chạy, không hơn không kém — ASG ở đây dùng như một "supervisor" tự phục hồi, không phải để scale ngang.
  • Elastic IP là địa chỉ không đổi dù instance vật lý phía sau thay đổi liên tục — client/DNS chỉ cần trỏ vào 1 IP duy nhất, không cần biết instance nào đang sống.

ASG (1 min/1 max/1 desired, ≥ 2 AZ) — instance mới lên luôn tự attach lại đúng Elastic IP nhờ EC2 User Data + Tag, nhờ IAM Role cho phép gọi API attach.

  • Việc attach diễn ra tự động qua User Data, không cần con người can thiệp → thời gian phục hồi nhanh, đúng tinh thần HA.

Giới hạn của cách A: chỉ khôi phục lại được compute (EC2 chạy lại) và network identity (Elastic IP). Toàn bộ dữ liệu trên ổ đĩa cũ bị mất vì instance mới là instance trắng (từ AMI gốc) — nếu ứng dụng cần giữ lại state/data trên đĩa, phải dùng cách B.

9.2 Cách B — Auto Scaling Group + EBS Snapshot lifecycle hook

Kiến trúc — từng bước:

  1. Vẫn là ASG min=max=desired=1, trải nhiều AZ, giống cách A.
  2. Trước khi ASG terminate một instance (scale-in, thay thế do unhealthy…), Lifecycle Hook "Terminating" kích hoạt: tạo EBS Snapshot của volume dữ liệu, gắn kèm Tag để nhận diện lại sau này.
  3. Khi ASG launch instance mới thay thế, Lifecycle Hook "Launching" kích hoạt: tìm snapshot mới nhất theo Tag → tạo EBS Volume mới từ snapshot đó → attach vào instance mới.
  4. Instance mới tiếp tục dùng EC2 User Data để tự attach lại Elastic IP (giống hệt cách A) → vừa có lại dữ liệu, vừa giữ nguyên địa chỉ truy cập.

Vì sao thiết kế vậy:

  • Lifecycle Hook là cơ chế đúng để "chen" một hành động tuỳ ý (custom action) vào giữa vòng đời instance của ASG, thay vì ASG chỉ biết launch/terminate trần trụi.
  • Snapshot-trước-khi-terminate đảm bảo không mất dữ liệu ghi gần nhất — khác hẳn cách A nơi dữ liệu trên đĩa bị bỏ lại hoàn toàn.
  • Kết hợp cả 2 cơ chế (EBS lifecycle hook + Elastic IP User Data) → instance mới vừa giữ danh tính mạng, vừa giữ dữ liệu — gần như "instance clone lại chính nó" sau sự cố.

Lifecycle Hook Terminate tạo EBS Snapshot + tag trước khi instance cũ mất; Lifecycle Hook Launch tạo lại EBS Volume từ snapshot đó và attach vào instance mới.

9.3 So sánh nhanh 2 cách

Tiêu chí Cách A — chỉ Elastic IP Cách B — thêm EBS Snapshot
Khôi phục network identity ✔ ✔
Khôi phục dữ liệu trên đĩa ✖ (instance mới từ AMI gốc, trắng) ✔ (volume phục hồi từ snapshot mới nhất)
Độ phức tạp Thấp — chỉ cần User Data + IAM Role Cao hơn — cần cấu hình 2 Lifecycle Hook
Phù hợp khi App stateless hoặc state đã nằm ngoài EC2 (DB, S3…) App stateful, dữ liệu quan trọng nằm ngay trên đĩa EC2

Điểm hay ra thi

  • 3 kiểu retry/DLQ khác nhau tuỳ Lambda được gọi bởi ai: SNS→Lambda (DLQ trên Lambda), SQS Standard→Lambda (DLQ trên SQS), SQS FIFO→Lambda (1 message lỗi block cả group cho tới khi rơi DLQ).
  • Fan-out qua SNS luôn thắng PUT trực tiếp nhiều SQS: thêm consumer mới không cần sửa producer.
  • S3 Event Notifications cơ bản → SNS/SQS/Lambda; cần filter nâng cao/nhiều đích/archive & replay → route qua EventBridge.
  • Pattern giám sát API nguy hiểm: CloudTrail → EventBridge → SNS.
  • API Gateway Service Integration: gọi thẳng AWS service (Kinesis, SQS, DynamoDB…) mà không cần Lambda khi không có business logic.
  • Chặn 1 IP: SG không deny được; NACL deny được nhưng chỉ hiệu quả nếu client IP còn "sống" tới đó; ALB che IP client (chặn phải làm ở NACL trước ALB), NLB pass-through IP client (SG của EC2 vẫn chặn được); công cụ chuẩn để chặn IP là AWS WAF, gắn ở CloudFront nếu có CloudFront (chặn tại ALB lúc đó vô nghĩa).
  • HPC: Direct Connect/Snowball/DataSync để đưa data lên; Placement Group Cluster + EFA (MPI, Linux-only) cho giao tiếp giữa node; FSx for Lustre cho file system HPC; AWS Batch (multi-node parallel job) vs AWS ParallelCluster (open-source, deploy cả cụm bằng text config).
  • HA EC2 đơn lẻ: ASG min=max=desired=1 + Elastic IP qua User Data/Tag (mất data) hoặc thêm EBS Snapshot Lifecycle Hook (giữ data) — chọn theo app có stateful hay không.

Takeaway cá nhân

  • Bài này giống §20 ở chỗ "không dạy gì mới", nhưng khác ở độ lắt léo: nhiều case study đòi hỏi phân biệt rất tinh (SG vs NACL vs WAF; SQS Standard vs FIFO khi gắn Lambda) — dễ chọn nhầm nếu học hời hợt.
  • 2 case study "HA EC2 + ASG" là dạng câu hỏi kinh điển kiểu "so sánh 2 phương án, chọn theo yêu cầu app có cần giữ data hay không" — nhớ tách bạch rõ: Elastic IP giải quyết network identity, EBS Snapshot giải quyết data, hai cái độc lập nhau và có thể dùng riêng hoặc cùng lúc.
  • Ghi chú riêng: slide gốc trong khoảng trang 802-824 không đề cập Amazon SES — phần "gửi email qua S3 event" chỉ xuất hiện ở §20 (DynamoDB Streams → Lambda → SES), không phải section 29 này. Nếu tài liệu khoá học của mình có thêm slide SES ở đây, cần bổ sung lại sau khi đối chiếu PDF gốc.
