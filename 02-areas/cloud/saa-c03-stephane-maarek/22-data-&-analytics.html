Đọc note này thế nào? Đây là chủ đề dễ bị "ngộp" vì có quá nhiều dịch vụ tên lạ. Nhưng thực chất tất cả chỉ phục vụ một câu chuyện duy nhất: dữ liệu chảy từ nguồn → được lưu → được xử lý → được truy vấn → được vẽ thành biểu đồ. Mỗi dịch vụ chỉ đứng ở một chặng trong dòng chảy đó.

0. Sáu khái niệm nền tảng — đọc phần này trước

0.1 OLTP vs OLAP — hai thế giới hoàn toàn khác nhau

Đây là ranh giới quan trọng nhất của cả bài.

OLTP (Online Transaction Processing) OLAP (Online Analytical Processing)
Làm gì Chạy ứng dụng hằng ngày Phân tích để ra quyết định
Câu hỏi điển hình "Đơn hàng #12345 của ai?" "Doanh thu 3 năm qua theo từng tỉnh, chia theo nhóm tuổi?"
Mỗi query đụng vào Vài dòng Hàng triệu/tỷ dòng
Số lượng query Rất nhiều, rất nhanh Ít hơn, mỗi cái nặng
Ghi dữ liệu Ghi liên tục Chủ yếu đọc, ghi theo lô
Dịch vụ AWS RDS, Aurora, DynamoDB Redshift, Athena, EMR

Vì sao không dùng chung một database? Vì tối ưu ngược nhau hoàn toàn. Database OLTP tối ưu để "tìm nhanh 1 dòng"; database OLAP tối ưu để "quét nhanh 1 tỷ dòng". Bắt Aurora chạy report quét 3 năm dữ liệu sẽ làm ứng dụng thật bị chậm theo — đó là lý do người ta tách hẳn ra hệ thống analytics riêng.

0.2 Row storage vs Columnar storage — vì sao Parquet lại rẻ hơn

Đây là chìa khoá để hiểu Athena và Redshift. Giả sử có bảng:

id name city age salary
1 An Hà Nội 30 20
2 Bình Huế 25 18
3 Chi Đà Nẵng 41 32

Lưu theo dòng (row-based — CSV, MySQL): trên đĩa các giá trị nằm cạnh nhau theo từng dòng

1,An,Hà Nội,30,20 | 2,Bình,Huế,25,18 | 3,Chi,Đà Nẵng,41,32

Lưu theo cột (columnar — Parquet, ORC, Redshift): các giá trị cùng một cột nằm cạnh nhau

id:   1,2,3
name: An,Bình,Chi
city: Hà Nội,Huế,Đà Nẵng
age:  30,25,41
salary: 20,18,32

Bây giờ chạy query: SELECT AVG(salary) FROM employees

Kiểu lưu Phải đọc gì Kết quả
Row-based Đọc toàn bộ file (vì mỗi dòng chứa lẫn lộn tất cả cột) Quét 100% dữ liệu
Columnar Chỉ đọc cột salary Quét ~20% dữ liệu

Hai lợi ích cộng dồn:

  1. Đọc ít hơn → nhanh hơn, và với Athena (tính tiền theo lượng data quét) thì rẻ hơn trực tiếp
  2. Nén tốt hơn → các giá trị cùng cột thường giống nhau (cùng kiểu, cùng miền giá trị) nên thuật toán nén hiệu quả hơn nhiều

Ghi nhớ: OLAP luôn dùng columnar. Thấy chữ Parquet / ORC / Redshift là nghĩ tới columnar.

0.3 Partitioning — chia thư mục để khỏi phải quét hết

Nếu để toàn bộ dữ liệu trong một thư mục phẳng, mọi query đều phải quét hết. Partition = sắp dữ liệu vào thư mục theo giá trị, để công cụ query bỏ qua thư mục không liên quan.

s3://bucket/flights/year=1991/month=1/day=1/data.parquet
s3://bucket/flights/year=1991/month=1/day=2/data.parquet
s3://bucket/flights/year=1992/month=3/day=7/data.parquet

Query WHERE year=1991 AND month=1 → Athena chỉ mở 2 thư mục đó, hoàn toàn không đụng tới year=1992.

Các cột year, month, day được gọi là virtual column (cột ảo) — chúng không nằm trong file, mà nằm ở tên thư mục, nhưng vẫn query được như cột bình thường.

0.4 Data Lake vs Data Warehouse

Data Lake (hồ dữ liệu) Data Warehouse (kho dữ liệu)
Chứa gì Mọi thứ, thô, chưa xử lý Dữ liệu đã làm sạch, có cấu trúc
Định dạng Bất kỳ (JSON, CSV, log, ảnh, video) Bảng có schema chặt
Schema Schema-on-read (định nghĩa lúc query) Schema-on-write (định nghĩa lúc ghi vào)
Chi phí lưu Rẻ (S3) Đắt hơn
Trên AWS S3 (+ Lake Formation quản lý) Redshift

Ví von: Data Lake giống kho hàng đổ đống — quăng vào trước, phân loại sau. Data Warehouse giống siêu thị — mọi thứ đã lên kệ, gắn nhãn, sẵn sàng lấy dùng.

0.5 ETL — Extract, Transform, Load

Dữ liệu thô hầu như không dùng ngay được. ETL là quy trình 3 bước biến nó thành dùng được:

Bước Nghĩa Ví dụ
Extract Lấy dữ liệu từ nguồn Đọc log từ S3, đọc bảng từ RDS
Transform Làm sạch, đổi định dạng, gộp Bỏ dòng lỗi, đổi CSV → Parquet, join 2 bảng
Load Nạp vào đích Ghi vào Redshift, ghi lại S3

Trên AWS, dịch vụ ETL managed là AWS Glue.

0.6 Batch vs Streaming

Batch (theo lô) Streaming (luồng liên tục)
Cách xử lý Gom dữ liệu rồi xử lý một lượt Xử lý ngay khi dữ liệu tới
Độ trễ Phút → giờ Giây → mili giây
Dịch vụ Glue, EMR, Athena Kinesis, MSK, Flink

1. Bản đồ toàn cảnh — mỗi dịch vụ đứng ở đâu?

Trước khi đi vào chi tiết, hãy nhìn dòng chảy dữ liệu. Đây là bức tranh giúp bạn không bị lạc.

Chặng Dịch vụ Một câu mô tả

Lưu trữ S3, Lake Formation Data lake trung tâm

Tìm kiếm OpenSearch Tìm full-text trên mọi trường
Trực quan hoá QuickSight Vẽ dashboard cho người kinh doanh

2. Amazon Athena — chạy SQL thẳng trên S3

2.1 Athena là gì?

  • Dịch vụ query serverless để phân tích dữ liệu đang nằm trong S3
  • Dùng SQL chuẩn để query file (xây trên Presto)
  • Hỗ trợ định dạng: CSV, JSON, ORC, Avro, Parquet
  • Giá: $5,00 cho mỗi TB dữ liệu được quét
  • Thường dùng chung với Amazon QuickSight để làm report/dashboard
  • Use case: BI / analytics / reporting, phân tích VPC Flow Logs, ELB Logs, CloudTrail trails…

Điểm mấu chốt phải hiểu: Athena không có database, không có server, không phải nạp dữ liệu vào đâu cả. File vẫn nằm nguyên trong S3; Athena chỉ đọc file rồi trả lời. Bạn không trả tiền khi không query.

Exam Tip (nguyên văn trong slide): "analyze data in S3 using serverless SQL, use Athena" — thấy 3 yếu tố S3 + SQL + serverless là chọn Athena.

2.2 Tối ưu hiệu năng & chi phí — 4 kỹ thuật

Vì Athena tính tiền theo lượng data quét, tối ưu hiệu năng cũng chính là tối ưu chi phí. Bốn cách:

# Kỹ thuật Vì sao hiệu quả
1 Dùng định dạng columnar — khuyến nghị Apache Parquet hoặc ORC Chỉ quét cột cần thiết → giảm mạnh data scanned (xem §0.2). Dùng AWS Glue để convert sang Parquet/ORC
2 Nén dữ liệu (bzip2, gzip, lz4, snappy, zlib, zstd…) File nhỏ hơn → đọc ít byte hơn
3 Partition dataset trong S3 Query chỉ chạm partition liên quan (xem §0.3)
4 Dùng file lớn (> 128 MB) Nhiều file nhỏ tạo overhead mở file rất lớn; gộp lại thì nhanh hơn nhiều

Cấu trúc partition chuẩn trên S3:

s3://yourBucket/pathToTable
   /<PARTITION_COLUMN_NAME>=<VALUE>
   /<PARTITION_COLUMN_NAME>=<VALUE>
   /<PARTITION_COLUMN_NAME>=<VALUE>
   /etc...

Ví dụ thật:

s3://athena-examples/flight/parquet/year=1991/month=1/day=1/

Nhớ combo này: đề bài hỏi "làm sao giảm chi phí Athena?" → đáp án gần như luôn là chuyển sang Parquet/ORC + partition + nén. Ba thứ này đi cùng nhau.

2.3 Athena Federated Query — query cả những nơi không phải S3

  • Cho phép chạy SQL trên nhiều nguồn khác nhau: relational, non-relational, object store, và nguồn tuỳ chỉnh — trên AWS hoặc on-premises
  • Dùng Data Source Connector chạy trên AWS Lambda để thực hiện Federated Query (vd connector cho CloudWatch Logs, DynamoDB, RDS…)
  • Kết quả có thể lưu ngược về Amazon S3

Giá trị thực tế: thay vì phải copy dữ liệu từ DynamoDB + RDS + CloudWatch về một chỗ rồi mới join, Federated Query cho bạn join thẳng giữa chúng bằng một câu SQL duy nhất.

3. Amazon Redshift — data warehouse

3.1 Tổng quan

  • Redshift dựa trên PostgreSQL, nhưng không dùng cho OLTP
  • Nó là OLAP — online analytical processing (analytics và data warehousing)
  • Hiệu năng tốt hơn 10 lần các data warehouse khác, scale tới hàng petabyte
  • Columnar storage (thay vì row-based) và parallel query engine (chia query ra nhiều node chạy song song)
  • Hai chế độ: Provisioned cluster hoặc Serverless cluster
  • Có giao diện SQL để chạy query
  • Công cụ BI như Amazon QuickSight hoặc Tableau tích hợp được
  • So với Athena: query / join / aggregation nhanh hơn nhờ có index

Vì sao Redshift nhanh hơn Athena? Vì Redshift nạp dữ liệu vào bên trong và tổ chức lại (index, sort key, distribution key, thống kê). Athena thì đọc file "nguyên trạng" trong S3 mỗi lần query. Đổi lại, Redshift phải trả tiền cluster liên tục còn Athena chỉ trả khi query.

3.2 Redshift Cluster — kiến trúc

Thành phần Nhiệm vụ
Leader node Lập kế hoạch query (query planning) và tổng hợp kết quả (results aggregation)
Compute node Thực thi query, gửi kết quả về leader node

Provisioned mode:

  • Chọn instance type trước
  • Có thể reserve instance để tiết kiệm chi phí

Cách hoạt động: Leader node nhận query, chia nhỏ thành nhiều phần, phát cho các compute node chạy song song trên phần dữ liệu của mình, rồi gom kết quả lại. Đây chính là "parallel query engine" — lý do Redshift quét petabyte vẫn nhanh.

3.3 Snapshots & Disaster Recovery

  • Redshift có chế độ "Multi-AZ" cho một số cluster
  • Snapshot = backup point-in-time của cluster, lưu nội bộ trong S3
  • Snapshot có tính incremental — chỉ lưu phần đã thay đổi
  • Có thể restore snapshot vào một cluster MỚI
Loại snapshot Chi tiết
Automated Mỗi 8 giờ, hoặc mỗi 5 GB thay đổi, hoặc theo lịch. Retention đặt được từ 1 đến 35 ngày
Manual Giữ cho tới khi bạn tự xoá
  • Có thể cấu hình Redshift tự động copy snapshot (cả automated lẫn manual) sang AWS Region khác → phục vụ DR cross-region

Bẫy thi: restore snapshot luôn tạo ra cluster mới, không ghi đè cluster cũ (giống DynamoDB PITR tạo table mới).

3.4 Nạp dữ liệu vào Redshift

Insert theo lô lớn TỐT HƠN RẤT NHIỀU (Large inserts are MUCH better)

Vì sao? Redshift là columnar và tối ưu cho ghi hàng loạt. Mỗi lệnh INSERT một dòng đều tốn overhead rất lớn. Cách đúng:

Cách nạp dữ liệu Ghi chú
Lệnh COPY từ S3 Cách chuẩn và nhanh nhất — nạp song song từ nhiều file
Kinesis Data Firehose → Redshift Firehose gom thành lô rồi tự COPY vào
Từ EC2 qua JDBC Nên batch nhiều dòng trong một lần, tránh insert từng dòng

3.5 Redshift Spectrum — query S3 mà không cần nạp vào

  • Query dữ liệu đã nằm sẵn trong S3 mà không cần load vào Redshift
  • Bắt buộc phải có một Redshift cluster đang chạy để khởi động query
  • Query sau đó được đẩy sang hàng nghìn node Redshift Spectrum để xử lý

Spectrum vs Athena — điểm khác biệt cốt lõi: cả hai đều query S3, nhưng Spectrum BẮT BUỘC phải có cluster Redshift, còn Athena hoàn toàn serverless. Đề thi nhấn mạnh "không muốn quản lý hạ tầng nào" → Athena. Đề nói "đã có Redshift, muốn join dữ liệu trong warehouse với dữ liệu lịch sử trên S3" → Spectrum.

3.6 Athena vs Redshift — bảng chọn

Tiêu chí Athena Redshift
Hạ tầng Serverless hoàn toàn Cluster (hoặc Serverless mode)
Dữ liệu nằm ở S3 (nguyên trạng) Bên trong Redshift (phải load)
Trả tiền $5/TB quét Theo giờ cluster
Hiệu năng join/aggregation phức tạp Chậm hơn Nhanh hơn (có index)
Phù hợp Query thỉnh thoảng, ad-hoc, phân tích log Query liên tục, dashboard BI, warehouse doanh nghiệp
Setup Gần như không cần Phải thiết kế schema, sort key, load dữ liệu

4. Amazon OpenSearch Service — tìm kiếm toàn văn

4.1 Vì sao cần OpenSearch?

  • OpenSearch là thế hệ kế tiếp của Amazon ElasticSearch
  • Vấn đề nó giải quyết: trong DynamoDB, bạn chỉ query được theo primary key hoặc index. Muốn tìm "tất cả sản phẩm có chữ sữa trong mô tả" thì DynamoDB chịu
  • Với OpenSearch, bạn tìm được trên bất kỳ trường nào, kể cả khớp một phần (partial match)
  • Vì vậy OpenSearch thường dùng BỔ SUNG cho một database khác, không thay thế nó

Mô hình điển hình: DynamoDB làm source of truth (lưu dữ liệu chính, đọc/ghi theo key), OpenSearch làm lớp tìm kiếm (đồng bộ từ DynamoDB sang). Tìm xong lấy được id, rồi quay lại DynamoDB lấy dữ liệu đầy đủ.

4.2 Đặc điểm

Khía cạnh Chi tiết
Chế độ Managed cluster hoặc Serverless cluster
SQL Không hỗ trợ SQL natively (bật được qua plugin)
Ingestion Từ Kinesis Data Firehose, AWS IoT, và CloudWatch Logs
Security Qua Cognito & IAM, mã hoá KMS, TLS
Visualization Đi kèm OpenSearch Dashboards

4.3 Ba pattern tích hợp cần nhớ

Pattern 1 — DynamoDB + OpenSearch

Pattern 2 — CloudWatch Logs + OpenSearch

CloudWatch Logs → Subscription Filter → Lambda (real-time) hoặc Kinesis Data Firehose (near real-time) → OpenSearch.

Pattern 3 — Kinesis Data Streams & Kinesis Data Firehose + OpenSearch

Kinesis Data Streams → (Lambda transform) → Kinesis Data Firehose → OpenSearch. Firehose có thể ghi thẳng vào OpenSearch.

5. Amazon EMR — cụm Hadoop có quản lý

  • EMR = Elastic MapReduce
  • Giúp tạo cụm Hadoop (Big Data) để phân tích và xử lý khối lượng dữ liệu khổng lồ
  • Cluster có thể gồm hàng trăm EC2 instance
  • Đi kèm sẵn Apache Spark, HBase, Presto, Flink…
  • EMR lo toàn bộ việc provisioning và configuration
  • Có auto-scaling và tích hợp Spot Instances
  • Use case: data processing, machine learning, web indexing, big data…

5.1 Ba loại node — điểm hay ra thi

Node Nhiệm vụ Vòng đời
Master Node Quản lý cluster, điều phối, quản lý health Long running
Core Node Chạy task VÀ lưu dữ liệu Long running
Task Node (tuỳ chọn) Chỉ chạy task, không lưu dữ liệu Thường dùng Spot

Vì sao Task Node hợp với Spot mà Core Node thì không? Vì Core Node giữ dữ liệu (HDFS) — mất node là mất dữ liệu. Task Node chỉ tính toán, bị thu hồi thì chạy lại trên node khác, không mất gì. Đây là logic hay được hỏi trong đề thi.

5.2 Purchasing options

Lựa chọn Đặc điểm
On-demand Tin cậy, dự đoán được, không bị terminate
Reserved (tối thiểu 1 năm) Tiết kiệm chi phí — EMR tự động dùng nếu có sẵn
Spot Instances Rẻ hơn, có thể bị terminate, kém tin cậy hơn

Kiểu cluster:

  • Long-running cluster — chạy liên tục
  • Transient cluster — cluster tạm thời, chạy xong job thì tự tắt (tiết kiệm chi phí)

6. Amazon QuickSight — dashboard BI

6.1 Tổng quan

  • Dịch vụ business intelligence serverless, có machine learning, dùng để tạo dashboard tương tác
  • Nhanh, tự động scale, nhúng được (embeddable), tính tiền theo phiên (per-session pricing)
  • Use case: business analytics, xây dựng visualization, phân tích ad-hoc, rút ra insight từ dữ liệu
  • Tích hợp với RDS, Aurora, Athena, Redshift, S3…
  • SPICE engine — tính toán in-memory khi dữ liệu được import vào QuickSight
  • Enterprise edition: thiết lập được Column-Level Security (CLS)

SPICE = Super-fast, Parallel, In-memory Calculation Engine. Nếu dữ liệu import vào SPICE thì dashboard chạy cực nhanh vì không phải query lại nguồn mỗi lần. Nếu dùng direct query thì mỗi lần mở dashboard là query thẳng xuống nguồn (chậm hơn nhưng dữ liệu luôn mới).

6.2 Dashboard & Analysis — cơ chế chia sẻ

  • Định nghĩa Users (bản standard) và Groups (bản enterprise)
  • Rất quan trọng: những user & group này chỉ tồn tại trong QuickSight, KHÔNG phải IAM!

Dashboard là gì?

  • Là bản snapshot chỉ-đọc của một analysis mà bạn có thể chia sẻ
  • Giữ nguyên cấu hình của analysis: filtering, parameters, controls, sort
  • Chia sẻ được analysis hoặc dashboard cho Users hoặc Groups
  • Muốn chia sẻ dashboard thì phải publish trước
  • Người xem dashboard cũng xem được dữ liệu nền (underlying data)

Bẫy thi: "user và group của QuickSight không phải IAM" là chi tiết hay bị hỏi. Và "người xem dashboard thấy được cả dữ liệu nền" — nghĩa là muốn giới hạn thì phải dùng Column-Level Security (Enterprise) hoặc Row-Level Security.

Khái niệm Là gì
Analysis Bản "đang làm việc" — chỉnh sửa được
Dashboard Bản chỉ-đọc đã publish, để chia sẻ

7. AWS Glue — ETL serverless

7.1 Glue là gì?

  • Dịch vụ ETL (extract, transform, load) có quản lý
  • Hữu ích để chuẩn bị và biến đổi dữ liệu phục vụ analytics
  • Hoàn toàn serverless

7.2 Dùng Glue để convert sang Parquet

Đây là pattern kinh điển nhất của Glue trong đề thi: dữ liệu đổ vào S3 dạng CSV/JSON → Glue convert sang Parquet → Athena query với chi phí thấp hơn nhiều. Nhớ nối được 2 mắt xích này (§0.2 giải thích vì sao).

7.3 Glue Data Catalog — danh mục dataset

Glue Data Catalog là catalog (danh mục) của các dataset — nó lưu metadata: có những table nào, mỗi table có cột gì, kiểu dữ liệu ra sao, dữ liệu nằm ở đâu trong S3.

  • Glue Crawler quét dữ liệu trong S3/RDS/DynamoDB → tự suy ra schema → ghi vào Data Catalog
  • Athena, Redshift Spectrum, EMR đều đọc schema từ Data Catalog này

Hiểu vai trò: dữ liệu thô trong S3 chỉ là file — không ai biết nó có cột gì. Data Catalog chính là "mục lục" cho biết file đó là bảng gì, có cột nào. Không có nó thì Athena không biết phải query cái gì.

7.4 Các thành phần Glue cần biết ở mức tổng quan

Thành phần Chức năng
Glue Job Bookmarks Chống xử lý lại dữ liệu cũ — nhớ đã xử lý tới đâu
Glue DataBrew Làm sạch và chuẩn hoá dữ liệu bằng các transformation dựng sẵn (giao diện, không cần code)
Glue Studio GUI mới để tạo, chạy và giám sát ETL job trong Glue
Glue Streaming ETL Xây trên Apache Spark Structured Streaming; tương thích Kinesis Data Streams, Kafka, MSK

Job Bookmarks hay ra thi: đề nói "job ETL chạy lại và xử lý trùng dữ liệu cũ, làm sao tránh?" → Glue Job Bookmarks.

8. AWS Lake Formation — dựng data lake nhanh

  • Data lake = nơi tập trung toàn bộ dữ liệu phục vụ mục đích analytics
  • Dịch vụ fully managed giúp dựng data lake trong vài ngày
  • Discover, cleanse, transform, và ingest dữ liệu vào Data Lake
  • Tự động hoá nhiều bước thủ công phức tạp (thu thập, làm sạch, di chuyển, catalog dữ liệu…) và khử trùng lặp bằng ML Transforms
  • Kết hợp được cả dữ liệu có cấu trúc và phi cấu trúc
  • Có sẵn source blueprint: S3, RDS, Relational & NoSQL DB…
  • Fine-grained Access Control cho ứng dụng — tới mức hàng (row) và cột (column)
  • Xây dựng trên nền AWS Glue

8.1 Ví dụ quản lý permission tập trung

Giá trị chính của Lake Formation trong đề thi: quản lý permission TẬP TRUNG một chỗ cho toàn bộ data lake, tới mức row-level và column-level. Nếu không có nó, bạn phải đi cấu hình IAM/bucket policy rời rạc cho từng dịch vụ. Thấy đề nói "fine-grained access control ở mức hàng/cột cho data lake" → Lake Formation.

9. Amazon Managed Service for Apache Flink

  • Tên cũ: Kinesis Data Analytics for Apache Flink
  • Flink (viết bằng Java, Scala hoặc SQL) là một framework để xử lý luồng dữ liệu (data streams)

Dịch vụ managed này cho phép:

  • Chạy bất kỳ ứng dụng Apache Flink nào trên cluster có quản lý trên AWS
  • Provisioned compute resources, tính toán song song, automatic scaling
  • Backup ứng dụng (triển khai dưới dạng checkpoint và snapshot)
  • Dùng mọi tính năng lập trình của Apache Flink để biến đổi dữ liệu

⚠️ Điểm cực hay ra thi: Flink KHÔNG đọc được từ Amazon Data Firehose. Flink đọc được từ Kinesis Data Streams và Amazon MSK. Nếu đề bài đưa Firehose làm nguồn cho Flink → đáp án SAI.

10. Amazon MSK — Managed Streaming for Apache Kafka

10.1 Kafka là gì? (nền tảng cần hiểu trước)

Apache Kafka là hệ thống streaming phổ biến nhất thế giới, hoạt động rất giống Kinesis Data Streams:

Khái niệm Kafka Nghĩa Tương đương bên Kinesis
Topic Một "kênh" dữ liệu Stream
Partition Đơn vị chia nhỏ trong topic để chạy song song Shard
Producer Bên gửi dữ liệu vào Producer
Consumer Bên đọc dữ liệu ra Consumer
Broker Server chạy Kafka (Kinesis quản lý ngầm)

10.2 Amazon MSK

  • Giải pháp thay thế cho Amazon Kinesis
  • Apache Kafka fully managed trên AWS
  • Cho phép tạo, cập nhật, xoá cluster
  • MSK tạo và quản lý giúp bạn các Kafka broker node và Zookeeper node
  • Deploy cluster MSK trong VPC của bạn, multi-AZ (tối đa 3 AZ) cho HA
  • Tự động phục hồi khỏi các lỗi Kafka thường gặp
  • Dữ liệu lưu trên EBS volume, giữ bao lâu tuỳ bạn

MSK Serverless:

  • Chạy Apache Kafka trên MSK mà không cần quản lý capacity
  • MSK tự provision tài nguyên và tự scale compute & storage

10.3 Kinesis Data Streams vs Amazon MSK — bảng so sánh

Tiêu chí Kinesis Data Streams Amazon MSK
Kích thước message Tối đa 1 MB Mặc định 1 MB, cấu hình được cao hơn (vd 10 MB)
Đơn vị chia nhỏ Shards Kafka Topic với Partition
Thay đổi quy mô Shard Splitting & Merging (tăng và giảm được) Chỉ THÊM được partition vào topic (không giảm)
Mã hoá in-flight TLS (bắt buộc) PLAINTEXT hoặc TLS (chọn được)
Mã hoá at-rest KMS KMS
Security Qua IAM policy Mutual TLS (authentication) + Kafka ACL (authorization), SASL/SCRAM, IAM Access Control

Ba điểm phân biệt dễ nhớ nhất:

  1. Message > 1 MB → chỉ MSK làm được
  2. Giảm số partition/shard → chỉ Kinesis làm được (MSK chỉ thêm)
  3. Đề nhắc "đã dùng Kafka on-premises, muốn migrate" → MSK (giống logic EKS với Kubernetes ở §18)

10.4 MSK Consumers

Ai đọc được dữ liệu từ MSK:

Consumer Ghi chú
Managed Service for Apache Flink Xử lý stream real-time
AWS Glue Streaming ETL ETL trên luồng (chạy trên Spark Streaming)
AWS Lambda Event source mapping
Ứng dụng tự viết trên EC2 / ECS / EKS Dùng thư viện Kafka consumer

11. Case study — Big Data Ingestion Pipeline

11.1 Yêu cầu đề bài

# Yêu cầu Ngụ ý
1 Pipeline hoàn toàn serverless Không EC2, không cluster tự quản
2 Thu thập dữ liệu real-time Kinesis
3 Biến đổi dữ liệu Lambda / Firehose transformation
4 Query dữ liệu đã biến đổi bằng SQL Athena
5 Report từ query phải nằm trong S3 Athena tự ghi kết quả ra S3
6 Nạp dữ liệu vào warehouse và tạo dashboard Redshift + QuickSight

11.2 Kiến trúc

11.3 Giải thích từng mắt xích

Mắt xích Vai trò
IoT Core Cho phép thu thập dữ liệu từ thiết bị IoT
Kinesis Rất tốt cho thu thập dữ liệu real-time
Firehose Giúp đưa dữ liệu vào S3 ở mức near real-time (1 phút)
Lambda Hỗ trợ Firehose thực hiện biến đổi dữ liệu
Amazon S3 Có thể trigger notification tới SQS
Lambda (thứ 2) Subscribe SQS (cũng có thể nối S3 thẳng tới Lambda)
Athena Dịch vụ SQL serverless, kết quả lưu vào S3
Reporting bucket Chứa dữ liệu đã phân tích, dùng bởi công cụ reporting như QuickSight, Redshift…

Bài học kiến trúc: đây là mẫu pipeline serverless "chuẩn sách giáo khoa" — thu thập (Kinesis) → giao hàng (Firehose) → lưu (S3) → thông báo (SQS) → điều phối (Lambda) → truy vấn (Athena) → hiển thị (QuickSight). Thuộc mạch này là trả lời được rất nhiều câu hỏi kiến trúc dữ liệu.

12. So sánh & chọn đáp án thi

12.1 Bảng từ khoá → dịch vụ

Từ khoá trong đề bài Chọn
Query SQL serverless trên dữ liệu trong S3 Athena
Giảm chi phí Athena Parquet/ORC + partition + nén + file lớn
Convert CSV/JSON → Parquet AWS Glue
Query SQL trên nhiều nguồn khác nhau (RDS + DynamoDB + on-prem) Athena Federated Query
Data warehouse, OLAP, BI, petabyte Amazon Redshift
Đã có Redshift, muốn query thêm dữ liệu trên S3 mà không load Redshift Spectrum
Không muốn quản lý cluster nào để query S3 Athena (không phải Spectrum)
Tìm kiếm full-text, khớp một phần, tìm trên mọi trường Amazon OpenSearch
Bổ sung khả năng search cho DynamoDB DynamoDB Streams → Lambda → OpenSearch
Hadoop, Spark, HBase, Presto, Flink Amazon EMR
Node EMR nào dùng Spot được Task Node (không phải Core Node)
Dashboard BI, biểu đồ tương tác Amazon QuickSight
Tính toán in-memory trong QuickSight SPICE
Giới hạn cột người dùng được xem trong QuickSight Column-Level Security (Enterprise)
ETL serverless, chuẩn bị dữ liệu AWS Glue
Tránh ETL job xử lý lại dữ liệu cũ Glue Job Bookmarks

Đã dùng Kafka on-premises, muốn migrate Amazon MSK

12.2 Bốn cặp cực dễ nhầm

Cặp Cách phân biệt
Athena vs Redshift Spectrum Cả hai query S3. Athena serverless hoàn toàn; Spectrum bắt buộc có cluster Redshift.
Athena vs Redshift Athena = ad-hoc, thỉnh thoảng, trả theo query. Redshift = warehouse chạy liên tục, join/aggregation phức tạp nhanh hơn.
Kinesis Data Streams vs MSK MSK: message > 1 MB, chỉ thêm partition, có Kafka ACL/mTLS. Kinesis: 1 MB, split/merge shard, IAM.
Glue vs Lake Formation Glue = công cụ ETL + catalog. Lake Formation = xây trên Glue, thêm quản lý permission tập trung row/column cho cả data lake.

12.3 Số liệu cần thuộc

Dịch vụ Con số
Athena $5,00 / TB dữ liệu quét
Athena File nên > 128 MB
Redshift snapshot tự động Mỗi 8 giờ, hoặc mỗi 5 GB, hoặc theo lịch
Redshift snapshot retention 1 – 35 ngày
Redshift hiệu năng Tốt hơn 10 lần data warehouse khác
Firehose độ trễ Near real-time — khoảng 1 phút
Kinesis Data Streams message Tối đa 1 MB
MSK message Mặc định 1 MB, cấu hình được (vd 10 MB)
MSK multi-AZ Tối đa 3 AZ
EMR Reserved Instance Tối thiểu 1 năm

Điểm hay ra thi

  • Athena = SQL serverless trên S3, $5/TB quét; giảm chi phí bằng Parquet/ORC + partition + nén + file > 128 MB.
  • Athena Federated Query dùng connector chạy trên Lambda để query RDS/DynamoDB/CloudWatch/on-prem.
  • Redshift = OLAP data warehouse dựa trên PostgreSQL, columnar + parallel; Leader node lập kế hoạch, Compute node thực thi.
  • Redshift snapshot: incremental, lưu trong S3, automated mỗi 8 giờ / 5 GB, retention 1–35 ngày, copy được sang region khác; restore luôn tạo cluster mới.
  • Nạp dữ liệu vào Redshift: insert theo lô lớn tốt hơn nhiều — dùng COPY từ S3.
  • Redshift Spectrum bắt buộc có cluster; Athena thì không — đây là điểm phân biệt số 1.
  • OpenSearch cho phép tìm trên mọi trường, khớp một phần — thứ mà DynamoDB (chỉ primary key/index) không làm được; không hỗ trợ SQL natively.
  • EMR: Master (quản lý) / Core (chạy + lưu dữ liệu) / Task (chỉ chạy, hợp với Spot).
  • QuickSight: SPICE = in-memory; user/group của QuickSight KHÔNG phải IAM; dashboard là snapshot chỉ-đọc đã publish; người xem thấy được dữ liệu nền.
  • Glue: ETL serverless; Data Catalog là mục lục schema cho Athena/Spectrum/EMR; Job Bookmarks chống xử lý lại dữ liệu cũ; DataBrew làm sạch không cần code.
  • Lake Formation xây trên nền Glue, điểm mạnh là fine-grained access control tới row và column, quản lý permission tập trung.
  • Apache Flink KHÔNG đọc được từ Amazon Data Firehose — chỉ từ Kinesis Data Streams và MSK.
  • MSK vs Kinesis: MSK message cấu hình được > 1 MB, chỉ thêm được partition, security bằng mTLS + Kafka ACL / SASL-SCRAM / IAM; Kinesis giới hạn 1 MB, split & merge shard, security bằng IAM.

Takeaway cá nhân

  • Chủ đề này chỉ khó ở chỗ nhiều tên lạ, nhưng bản chất là một dây chuyền: thu thập → lưu → biến đổi → truy vấn → hiển thị. Nhớ được dây chuyền ở §1 thì mỗi dịch vụ tự có chỗ đứng.
  • Hai khái niệm nền tảng đáng đầu tư nhất là columnar storage và partitioning (§0.2, §0.3) — hiểu chúng là tự giải thích được vì sao Parquet rẻ hơn, vì sao Redshift nhanh, vì sao phải partition.
  • S3 là trung tâm của mọi thứ trong chủ đề này — Athena query nó, Glue biến đổi nó, Lake Formation quản lý nó, Firehose đổ vào nó, Redshift Spectrum đọc nó. Cứ hình dung S3 ở giữa là dễ nối các dịch vụ còn lại.
  • Ba chi tiết "bẫy" đáng khoanh đỏ: Spectrum cần cluster, Flink không đọc Firehose, user QuickSight không phải IAM.
  • Liên hệ ngược lại §17 (Kinesis) và §21 (OLTP vs OLAP) — bài này là phần mở rộng tự nhiên của cả hai.
