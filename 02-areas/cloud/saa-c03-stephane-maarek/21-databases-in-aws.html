21 – Databases in AWS: chọn đúng database cho từng bài toán

Cách đọc note này: Đây là bài tổng hợp & so sánh, không dạy chi tiết từng dịch vụ. Mục tiêu duy nhất: nhìn requirement → chọn đúng database. Đọc theo mạch: (1) Khung câu hỏi để chọn → (2) Bản đồ các loại database → (3) Tóm tắt từng dịch vụ → (4) Bảng từ khoá đề thi.

Đây là một trong những bài "ăn điểm" nhất của SAA-C03 — đề thi liên tục hỏi "database nào phù hợp nhất?". Phần §12 (từ khoá → dịch vụ) là phần đáng thuộc nhất trong cả note.

1. Khung câu hỏi để chọn đúng database

AWS có rất nhiều managed database. Trước khi chọn, trả lời 7 nhóm câu hỏi sau:

# Nhóm câu hỏi Cần làm rõ
1 Workload Đọc nhiều, ghi nhiều, hay cân bằng? Throughput bao nhiêu? Có thay đổi/dao động trong ngày không? Có cần scale không?
2 Dữ liệu Lưu bao nhiêu, lưu bao lâu? Có tăng trưởng không? Kích thước trung bình mỗi object? Truy cập theo cách nào?
3 Độ bền (durability) Đây có phải source of truth không? Mất dữ liệu thì hậu quả thế nào?
4 Hiệu năng Yêu cầu latency? Bao nhiêu user đồng thời?
5 Mô hình dữ liệu Query kiểu gì? Có join không? Structured hay semi-structured?
6 Schema Schema chặt hay cần linh hoạt? Có cần reporting? Có cần search? → RDBMS hay NoSQL?
7 Chi phí license Đang trả tiền license (Oracle, SQL Server)? Có nên chuyển sang cloud-native như Aurora?

Mẹo làm bài thi: đề bài luôn cài sẵn đáp án qua 3 từ khoá: (1) mô hình dữ liệu (join / JSON / graph / time-series), (2) yêu cầu vận hành (serverless / managed / scale), (3) ràng buộc (latency / chi phí / không đổi code). Đọc đề là gạch chân 3 thứ đó.

2. Bản đồ các loại database trên AWS

Loại Dịch vụ Đặc trưng nhận diện
RDBMS (SQL / OLTP) RDS, Aurora Rất mạnh về join, transaction, schema chặt
NoSQL (không join, không SQL) DynamoDB (~JSON), ElastiCache (key/value), Neptune (graph), DocumentDB (MongoDB), Keyspaces (Cassandra) Schema linh hoạt, scale ngang
Object Store S3 (object lớn), Glacier (backup / archive) Lưu file, không phải database truy vấn
Data Warehouse (SQL Analytics / BI) Redshift (OLAP), Athena, EMR Phân tích khối lượng lớn, không phải OLTP
Search OpenSearch (JSON) Tìm kiếm full-text, dữ liệu phi cấu trúc
Graph Amazon Neptune Thể hiện quan hệ giữa các dữ liệu
Ledger Amazon QLDB (Quantum Ledger Database) Sổ cái bất biến, có thể kiểm chứng bằng mật mã
Time series Amazon Timestream Dữ liệu theo thời gian (IoT, metrics)

Nhóm Redshift / Athena / EMR / OpenSearch được nói kỹ ở phần Data & Analytics (bài sau) — ở đây chỉ cần nhận diện đúng loại.

3. Amazon RDS — quan hệ có quản lý

Khía cạnh Chi tiết
Engine PostgreSQL, MySQL, Oracle, SQL Server, DB2, MariaDB, RDS Custom
Provisioning Bạn chọn instance size + EBS volume type & size
Storage Có auto-scaling cho storage
HA & scale đọc Read Replicas và Multi-AZ
Security IAM, Security Groups, KMS, SSL in transit
Backup Automated Backup + Point-in-Time Restore tới 35 ngày
Backup dài hạn Manual DB Snapshot
Maintenance Có lịch bảo trì do AWS quản lý — có downtime
Auth Hỗ trợ IAM Authentication, tích hợp Secrets Manager
RDS Custom Cho phép truy cập và tuỳ biến instance nền — chỉ Oracle & SQL Server

Use case: lưu dữ liệu quan hệ (RDBMS / OLTP), chạy SQL query, transaction.

RDS Custom hay ra thi ở tình huống: "cần SSH vào OS, cài agent hoặc patch tuỳ chỉnh cho Oracle/SQL Server nhưng vẫn muốn managed" → RDS Custom (RDS thường không cho truy cập OS).

4. Amazon Aurora — bản cloud-native của RDS

Khía cạnh Chi tiết
Tương thích API của PostgreSQL / MySQL — tách rời storage và compute
Storage Dữ liệu lưu 6 bản sao trên 3 AZ — highly available, self-healing, auto-scaling
Compute Cluster nhiều DB instance qua nhiều AZ, auto-scaling Read Replicas
Cluster endpoint Custom endpoint riêng cho writer và reader
Security / monitoring / maintenance Giống hệt RDS
Aurora Serverless Cho workload không dự đoán được / gián đoạn — không cần capacity planning
Aurora Global Tới 16 Read Instance mỗi region, replication storage < 1 giây
Aurora Machine Learning Chạy ML bằng SageMaker & Comprehend ngay trên Aurora
Aurora Database Cloning Tạo cluster mới từ cluster có sẵn — nhanh hơn restore snapshot

Use case: giống RDS, nhưng ít bảo trì hơn / linh hoạt hơn / hiệu năng cao hơn / nhiều tính năng hơn.

4.1 RDS vs Aurora — chọn cái nào?

Tiêu chí RDS Aurora
Engine 6 engine (kể cả Oracle, SQL Server, DB2) Chỉ PostgreSQL / MySQL
Storage EBS, phải chọn size Tự grow, 6 bản sao / 3 AZ
Hiệu năng Chuẩn Cao hơn (~3–5 lần MySQL)
Read Replica Tối đa 5 (MySQL) Tối đa 15, auto-scaling
Failover Vài chục giây – vài phút < 30 giây
Chi phí Rẻ hơn Đắt hơn ~20% nhưng thường hiệu quả hơn/đơn vị hiệu năng
Chọn khi Cần engine cụ thể, tối ưu chi phí Cần hiệu năng, HA cao, ít vận hành

Aurora Database Cloning dùng cơ chế copy-on-write → tạo bản clone gần như tức thì mà không tốn gấp đôi storage. Đề thi hỏi "tạo môi trường test từ production nhanh nhất" → Aurora Cloning, không phải restore snapshot.

5. Amazon ElastiCache — cache in-memory

Khía cạnh Chi tiết
Engine Managed Redis / Memcached (mô hình cung cấp giống RDS nhưng cho cache)
Bản chất In-memory data store, latency sub-millisecond
Provisioning Chọn instance type (vd cache.m6g.large)
Scale & HA Hỗ trợ Clustering (Redis), Multi-AZ, Read Replicas (sharding)
Security IAM, Security Groups, KMS, Redis Auth
Backup Backup / Snapshot / Point-in-time restore
Maintenance Có lịch bảo trì do AWS quản lý
Nhược điểm Phải sửa code ứng dụng mới dùng được

Use case: key/value store, đọc nhiều ghi ít, cache kết quả query DB, lưu session data cho website. Không dùng được SQL.

5.1 Redis vs Memcached

Redis Memcached
Dữ liệu Nhiều kiểu (list, set, sorted set…) Chỉ key/value đơn giản
Persistence Có (AOF/snapshot) Không
Replication / HA Có (Multi-AZ, failover) Không
Multi-threaded Không Có
Dùng khi Cần HA, persistence, cấu trúc dữ liệu phong phú Cần cache thuần, đơn giản, multi-thread

Mẹo nhớ: Redis = Reliable (HA + persistence). Memcached = Multi-threaded nhưng "mất là mất".

6. Amazon DynamoDB — NoSQL serverless

Khía cạnh Chi tiết
Bản chất Công nghệ độc quyền AWS, NoSQL serverless managed, latency millisecond
Capacity Provisioned (có thể bật auto-scaling) hoặc On-demand
Thay thế ElastiCache Dùng được làm key/value store (vd lưu session data kèm TTL)
HA Highly Available, Multi-AZ mặc định; read và write tách rời; có transaction
Cache DAX cluster cho read cache — latency microsecond
Security IAM lo cả security, authentication, authorization
Event Processing DynamoDB Streams → Lambda, hoặc Kinesis Data Streams
Global Table Thiết lập active-active đa region
Backup Tự động tới 35 ngày với PITR (restore ra table mới), hoặc on-demand backup
S3 Export to S3 không tốn RCU (trong cửa sổ PITR); import từ S3 không tốn WCU
Schema Rất tiện để thay đổi schema nhanh

Use case: phát triển ứng dụng serverless (document nhỏ, cỡ hàng trăm KB), distributed serverless cache.

Chi tiết đầy đủ về DynamoDB (DAX, Streams, Global Tables, TTL, PITR) xem §19 Serverless.

6.1 DynamoDB vs ElastiCache cho session store

DynamoDB ElastiCache
Latency Millisecond Sub-millisecond
Vận hành Serverless, không quản lý gì Phải chọn & quản lý instance
Bền vững Lưu trên disk, bền In-memory (Redis có persistence tuỳ chọn)
Tự hết hạn TTL có sẵn TTL của Redis

7. Amazon S3 — key/value store cho object

Khía cạnh Chi tiết
Bản chất Là key/value store cho object
Phù hợp Object lớn; không tối ưu cho rất nhiều object nhỏ
Scale Serverless, scale vô hạn; object tối đa 5 TB; có versioning
Tiers S3 Standard, S3 Infrequent Access, S3 Intelligent-Tiering, S3 Glacier + lifecycle policy
Tính năng Versioning, Encryption, Replication, MFA-Delete, Access Logs…
Security IAM, Bucket Policies, ACL, Access Points, Object Lambda, CORS, Object Lock / Vault Lock
Encryption SSE-S3, SSE-KMS, SSE-C, client-side, TLS in transit, default encryption
Batch S3 Batch Operations, liệt kê file bằng S3 Inventory
Performance Multi-part upload, S3 Transfer Acceleration, S3 Select
Automation S3 Event Notifications → SNS, SQS, Lambda, EventBridge

Use case: static file, key/value store cho file lớn, hosting website tĩnh.

Ghi chú sửa số liệu: object tối đa của S3 là 5 TB (không phải 50 TB). Kèm theo: một lần PUT đơn lẻ tối đa 5 GB → file lớn hơn bắt buộc dùng multi-part upload.

Chi tiết S3 xem §12, §13, §14.

8. Amazon DocumentDB — "Aurora cho MongoDB"

  • Aurora là bản AWS triển khai của PostgreSQL / MySQL → DocumentDB là điều tương tự cho MongoDB (một NoSQL database)
  • MongoDB dùng để lưu, query và index dữ liệu JSON
  • Khái niệm triển khai tương tự Aurora
  • Fully managed, highly available với replication qua 3 AZ
  • Storage tự tăng theo bước 10 GB
  • Tự scale tới workload hàng triệu request/giây

Nhận diện đề thi: thấy chữ "MongoDB" hoặc "MongoDB-compatible" → đáp án là DocumentDB. Đừng chọn DynamoDB (DynamoDB không tương thích MongoDB API).

9. Amazon Neptune — graph database

9.1 Tổng quan

  • Fully managed graph database
  • Dataset dạng graph kinh điển: mạng xã hội
    • User có bạn bè; Post có comment; Comment có like từ user; User share và like post…
  • Highly available qua 3 AZ, tới 15 read replica
  • Xây dựng ứng dụng làm việc với dataset liên kết dày đặc (highly connected) — tối ưu cho các query phức tạp và khó
  • Lưu tới hàng tỷ quan hệ, query graph với latency milliseconds
  • Use case: knowledge graph (Wikipedia), phát hiện gian lận (fraud detection), recommendation engine, mạng xã hội

Vì sao không dùng RDS cho graph? Vì query kiểu "bạn của bạn của bạn" trong SQL cần nhiều tầng JOIN đệ quy → cực chậm khi dữ liệu lớn. Neptune được thiết kế riêng để duyệt quan hệ nên chỉ mất mili giây.

9.2 Neptune Streams

  • Chuỗi có thứ tự, real-time của mọi thay đổi trên dữ liệu graph
  • Thay đổi có sẵn ngay sau khi ghi
  • Không trùng lặp, thứ tự chặt chẽ (no duplicates, strict order)
  • Dữ liệu stream truy cập qua HTTP REST API
  • Use case:
    • Gửi thông báo khi có thay đổi nhất định
    • Đồng bộ dữ liệu graph sang data store khác (vd S3, OpenSearch, ElastiCache)
    • Replicate dữ liệu qua region trong Neptune

So với DynamoDB Streams (24 giờ retention, ordered): Neptune Streams cũng ordered và không duplicate, nhưng truy cập qua REST API thay vì trigger Lambda trực tiếp.

10. Amazon Keyspaces — managed Apache Cassandra

  • Apache Cassandra là NoSQL phân tán mã nguồn mở
  • Keyspaces = dịch vụ database tương thích Cassandra, do AWS quản lý
  • Serverless, scalable, highly available, fully managed
  • Tự động scale table lên/xuống theo traffic của ứng dụng
  • Table được replicate 3 lần qua nhiều AZ
  • Dùng Cassandra Query Language (CQL)
  • Latency single-digit millisecond ở mọi quy mô, hàng nghìn request/giây
  • Capacity: On-demand hoặc Provisioned + auto-scaling
  • Có encryption, backup, PITR tới 35 ngày
  • Use case: lưu thông tin thiết bị IoT, dữ liệu time-series…

Nhận diện đề thi: thấy "Cassandra" hoặc "CQL" → Amazon Keyspaces. (Giống pattern: MongoDB → DocumentDB, Redis → ElastiCache.)

11. Amazon Timestream — time series database

  • Fully managed, nhanh, scalable, serverless time series database
  • Tự động scale up/down để điều chỉnh capacity
  • Lưu và phân tích hàng nghìn tỷ event mỗi ngày
  • Nhanh hơn hàng nghìn lần và rẻ bằng 1/10 so với relational database (cho bài toán time-series)
  • Scheduled queries, multi-measure records, tương thích SQL
  • Phân tầng lưu trữ (storage tiering): dữ liệu gần đây giữ trong memory, dữ liệu lịch sử chuyển sang storage tối ưu chi phí
  • Có sẵn hàm phân tích time-series (giúp nhận diện pattern gần real-time)
  • Encryption cả in transit và at rest
  • Use case: ứng dụng IoT, ứng dụng vận hành (operational), real-time analytics

Nhận diện đề thi: đề nhắc "time series", "IoT sensor data theo thời gian", "metrics theo thời gian" → Timestream. Nếu đề nhắc IoT nhưng nhấn vào key/value tra cứu theo device → nghiêng về DynamoDB hoặc Keyspaces.

12. Amazon QLDB — ledger database

  • QLDB = Quantum Ledger Database — sổ cái do AWS quản lý
  • Ghi lại lịch sử thay đổi đầy đủ, bất biến (immutable) và kiểm chứng được bằng mật mã (cryptographically verifiable)
  • Không thể sửa hay xoá bản ghi đã có — chỉ append thêm
  • Use case: hệ thống tài chính, hồ sơ y tế, chuỗi cung ứng — nơi cần audit trail không thể giả mạo

QLDB vs Amazon Managed Blockchain: QLDB có một cơ quan trung tâm sở hữu sổ cái (centralized); Managed Blockchain dành cho trường hợp nhiều bên không tin nhau cùng ghi vào sổ (decentralized). Đề bài có chữ "nhiều tổ chức/đối tác cùng tham gia, phi tập trung" → Managed Blockchain; "một công ty cần audit log bất biến" → QLDB.

Lưu ý thực tế: AWS đã thông báo ngừng hỗ trợ QLDB (end of support 31/07/2025) và khuyến nghị chuyển sang Aurora PostgreSQL. Kiến thức này vẫn có thể xuất hiện trong đề SAA-C03 bản cũ — nên nhớ khái niệm, nhưng không dùng cho thiết kế mới.

13. Nhóm Analytics — nhận diện nhanh (chi tiết ở bài sau)

Dịch vụ Là gì Nhận diện
Redshift Data warehouse OLAP "Data warehouse", "BI", "phân tích petabyte", "SQL trên dữ liệu lịch sử"
Athena Query SQL trực tiếp trên S3, serverless "Query dữ liệu trong S3 mà không cần load", "serverless, trả theo query"
EMR Cụm Hadoop / Spark managed "Hadoop", "Spark", "big data processing"
OpenSearch Full-text search trên JSON "Tìm kiếm toàn văn", "log analytics", "search bất kỳ trường nào"

Phân biệt cốt lõi OLTP vs OLAP: OLTP (RDS/Aurora/DynamoDB) = nhiều giao dịch nhỏ, nhanh, real-time. OLAP (Redshift) = ít query nhưng quét khối lượng dữ liệu khổng lồ để phân tích. Đề bài có "report", "dashboard BI", "phân tích lịch sử" → OLAP.

14.2 Ba cặp cực dễ nhầm

Cặp Cách phân biệt
DynamoDB vs DocumentDB DynamoDB = NoSQL độc quyền AWS, key/value + document. DocumentDB = tương thích MongoDB API. Đề nhắc "MongoDB" → DocumentDB.
ElastiCache vs DynamoDB (+ DAX) ElastiCache cần sửa code và quản lý node, đổi lại sub-ms. DynamoDB + DAX không sửa code, serverless.
Timestream vs DynamoDB cho IoT Đề nhấn "phân tích theo thời gian, tìm pattern, trillion event/ngày" → Timestream. Đề nhấn "tra cứu theo deviceId, ghi/đọc nhanh" → DynamoDB.

14.3 Số liệu cần thuộc

Dịch vụ Con số
RDS / DynamoDB / Keyspaces PITR tới 35 ngày
Aurora storage 6 bản sao trên 3 AZ
Aurora Global 16 Read Instance/region, replication < 1 giây
Neptune 3 AZ, tới 15 read replica
DocumentDB 3 AZ, storage tăng theo bước 10 GB
Keyspaces Replicate 3 lần qua nhiều AZ
S3 Object tối đa 5 TB; single PUT tối đa 5 GB
DynamoDB Item tối đa 400 KB
ElastiCache Latency sub-millisecond
DynamoDB / Keyspaces Latency single-digit millisecond
DAX Latency microsecond

Điểm hay ra thi

  • Chọn database = đọc ra mô hình dữ liệu trước, rồi mới tới scale/latency/chi phí.
  • RDS cho quan hệ chuẩn; Aurora khi cần hiệu năng/HA cao hơn (6 bản sao / 3 AZ, failover < 30s, tới 15 read replica).
  • RDS Custom = engine Oracle/SQL Server + quyền truy cập OS.
  • Aurora Serverless cho workload thất thường; Aurora Cloning để tạo môi trường test cực nhanh (copy-on-write).
  • ElastiCache sub-ms nhưng phải sửa code; Redis (HA + persistence) vs Memcached (multi-threaded, không persistence).
  • DynamoDB serverless, Multi-AZ mặc định, PITR 35 ngày, export S3 không tốn RCU / import không tốn WCU.
  • S3 object tối đa 5 TB, single PUT 5 GB → file lớn phải multi-part upload.
  • DocumentDB = MongoDB, Keyspaces = Cassandra, Neptune = graph, Timestream = time series, QLDB = ledger bất biến.
  • QLDB (một chủ sở hữu, immutable) ≠ Managed Blockchain (nhiều bên phi tập trung).
  • Neptune Streams: ordered, không duplicate, truy cập qua HTTP REST API.
  • Timestream có storage tiering: memory cho dữ liệu mới, storage rẻ cho dữ liệu cũ.
  • OLTP (RDS/Aurora/DynamoDB) ≠ OLAP (Redshift) — đề nhắc "BI/report/phân tích lịch sử" là OLAP.

Takeaway cá nhân

  • Bài này về bản chất là bảng tra cứu, không phải bài lý thuyết — giá trị nằm ở việc map từ khoá đề bài → dịch vụ, học thuộc §14.1 là ăn điểm.
  • Có một pattern rất rõ: AWS làm bản managed cho từng công nghệ open-source phổ biến — MongoDB → DocumentDB, Cassandra → Keyspaces, Redis → ElastiCache, PostgreSQL/MySQL → Aurora, Elasticsearch → OpenSearch. Nhớ cặp "open-source ↔ dịch vụ AWS" là giải quyết được nửa số câu hỏi.
  • Cạm bẫy hay gặp nhất: chọn DynamoDB cho mọi thứ NoSQL. Đọc kỹ — nếu đề nhắc MongoDB/Cassandra/graph/time-series thì DynamoDB là đáp án sai.
  • Số liệu cần thuộc nằm gọn ở §14.3 — ôn nhanh trước khi thi.
