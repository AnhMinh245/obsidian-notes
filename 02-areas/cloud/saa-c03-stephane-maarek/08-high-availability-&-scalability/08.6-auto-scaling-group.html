8.6 – Auto Scaling Group (ASG)

Cách đọc note này: ASG luôn đi kèm ELB trong kiến trúc thi. Trọng tâm: 3 thông số Min/Desired/Max, 5 loại Scaling Policy (Target Tracking là mặc định), và Cooldown Period.

ASG là gì?

Auto Scaling Group (ASG) là dịch vụ tự động thêm (scale-out) hoặc bớt (scale-in) EC2 instances dựa trên tải ứng dụng thực tế.

ASG đảm bảo số lượng EC2 luôn nằm trong ngưỡng Min – Desired – Max bạn đặt, và:

  • Tự đăng ký/deregister instance với Load Balancer.
  • Tự tạo lại instance khi instance cũ unhealthy hoặc bị terminate.
  • ASG miễn phí — bạn chỉ trả tiền EC2 được tạo ra.

Ba thông số quan trọng nhất

Tham số Ý nghĩa
Minimum Capacity Số instance tối thiểu phải chạy (luôn đảm bảo)
Desired Capacity Số instance ASG muốn duy trì — ASG tự scale để đạt số này
Maximum Capacity Số instance tối đa được phép tạo

Ví dụ: Min = 1, Desired = 2, Max = 4

  • Bình thường → 2 EC2 chạy.
  • Traffic tăng → có thể scale đến 4.
  • Luôn có ít nhất 1 instance.

Launch Template — bản thiết kế EC2

ASG cần biết cách tạo EC2 mới → dùng Launch Template (Launch Configuration đã deprecated).

Launch Template chứa:

Thành phần Mô tả
AMI Base image cho EC2
Instance Type t3.micro, m5.large…
EBS Volumes Root volume, data volume
EC2 User Data Script chạy lần đầu
Security Groups Firewall rules
SSH Key Pair Để kết nối SSH
IAM Role Quyền cho EC2 truy cập AWS services
Network + Subnets VPC, subnet cho mỗi AZ
Load Balancer / Target Group Tự đăng ký khi launch

ASG kết hợp với Load Balancer

Khi ASG gắn với ALB/NLB:

  • Mọi instance mới tự động đăng ký vào target group.
  • LB dùng health check để kiểm tra.
  • Instance unhealthy → ASG tự terminate và tạo mới.
  • Scale-in → LB + ASG phối hợp Deregistration Delay để tránh mất request.

CloudWatch Alarms — nền tảng của Dynamic Scaling

ASG scale dựa trên CloudWatch metrics qua alarm:

  1. CloudWatch theo dõi metric (Avg CPU, NetworkIn, request count…).
  2. Metric vượt threshold → Alarm kích hoạt.
  3. Alarm gọi Scaling Policy → scale-out hoặc scale-in.

Metric như Average CPU được tính trên tất cả instance trong ASG, không phải từng instance.

5 Loại Scaling Policies

1. Target Tracking Scaling — phổ biến nhất

Hoạt động như thermostat: bạn chỉ đặt target, ASG tự điều chỉnh để đạt.

Ví dụ: "Duy trì Average CPU = 50%"
→ ASG tự thêm/bớt EC2 để giữ CPU ≈ 50%

Ưu điểm: Đơn giản nhất, thông minh, ít cấu hình. Target Tracking có built-in cooldown riêng, không dùng default cooldown.

2. Step Scaling

Scale theo nhiều ngưỡng tùy mức độ vi phạm:

CPU > 70% → +1 EC2
CPU > 85% → +3 EC2 (scale mạnh hơn)
CPU < 30% → -1 EC2

Phù hợp ứng dụng có mức tải dao động mạnh, cần kiểm soát chi tiết.

3. Simple Scaling (cũ, ít dùng)

Khi alarm kích hoạt → thêm đúng X instance và chờ cooldown.

CPU > 70% → +2 EC2, chờ 300s

Đơn giản nhưng dễ xung đột với cooldown, không linh hoạt.

4. Scheduled Scaling

Scale theo lịch cố định — khi biết chắc thời điểm cao điểm/thấp điểm.

Tăng min capacity = 10 vào 17:00 thứ 6 hàng tuần
Giảm min capacity = 2 vào 22:00 thứ 6

5. Predictive Scaling

AWS dùng machine learning để phân tích dữ liệu lịch sử và dự đoán tải tương lai → scale trước khi tải tăng.

Dùng cho workload ổn định theo mẫu (web traffic 9h–17h giờ làm việc).

Bảng so sánh 5 Scaling Policies

Loại Cách hoạt động Ưu Nhược Khi dùng
Target Tracking Giữ metric ở target Đơn giản, thông minh Ít tùy biến Mặc định cho hầu hết app
Step Scaling Scale theo nhiều ngưỡng Kiểm soát tốt Cấu hình phức tạp Tải dao động mạnh
Simple Scaling 1 alarm → 1 action Đơn giản Dễ xung đột cooldown Legacy, ít dùng
Scheduled Scaling Scale theo lịch Tối ưu giờ cao điểm Không phản ứng realtime Biết trước pattern
Predictive Scaling Dự đoán trước bằng ML Proactive, zero wait Cần dữ liệu lịch sử Pattern ổn định

Các Metrics tốt để Scaling

Metric Ý nghĩa Use case
CPUUtilization CPU trung bình toàn ASG App compute-heavy
RequestCountPerTarget Request trung bình/EC2 Web app dùng ALB
Average NetworkIn/Out Băng thông trung bình App network-heavy
Custom Metrics Tự push vào CloudWatch Queue depth (SQS), job count

Cooldown Period

Cooldown là khoảng thời gian ASG đợi sau khi scale trước khi thực hiện scaling tiếp theo — để metrics ổn định, tránh scale liên tục.

Thông tin Giá trị
Default cooldown 300 giây (5 phút)
Target Tracking Có built-in cooldown riêng — bỏ qua default cooldown
Step/Simple Scaling Dùng default cooldown

Tip: Dùng AMI đã pre-configured để EC2 boot nhanh → giảm cooldown.

Health Checks trong ASG

ASG có 2 loại health check:

  • EC2 Status Check — kiểm tra tình trạng EC2 (hardware/software).
  • ELB Health Check — kiểm tra theo định nghĩa health check của Target Group.

Nếu instance unhealthy → ASG terminate và tạo instance mới để giữ Desired capacity.

Bảng từ khoá đề thi

Từ khoá trong đề Chọn
"Chỉ đặt 1 target (vd CPU 50%), ASG tự lo phần còn lại" Target Tracking Scaling
"Scale mạnh/nhẹ tuỳ mức độ vi phạm ngưỡng" Step Scaling
"Biết trước thời điểm cao điểm (17h thứ 6)" Scheduled Scaling
"Dùng ML để dự đoán tải và scale trước" Predictive Scaling
"Instance unhealthy" ASG tự terminate & replace, không cần thao tác thủ công
"Launch Configuration vs Launch Template" Launch Template — Launch Configuration đã deprecated

Điểm hay ra thi

  • Target Tracking dễ nhất và phổ biến nhất — bỏ qua default cooldown.
  • Step Scaling kiểm soát tốt hơn Simple Scaling vì có nhiều ngưỡng.
  • Cooldown mặc định = 300 giây — Target Tracking không dùng cooldown mặc định.
  • ASG tự terminate và replace instance unhealthy — bạn không cần làm thủ công.
  • ASG miễn phí — chỉ tính tiền EC2 instances.
  • Predictive Scaling dùng ML để scale trước — keyword đề thi về proactive scaling.

Takeaway cá nhân

  • ASG + ALB là combo cốt lõi của kiến trúc web scalable + HA trên AWS.
  • Target Tracking là policy mặc định tốt nhất cho hầu hết trường hợp.
  • Nhớ cooldown: Target Tracking có riêng, Simple/Step dùng default 300s.
