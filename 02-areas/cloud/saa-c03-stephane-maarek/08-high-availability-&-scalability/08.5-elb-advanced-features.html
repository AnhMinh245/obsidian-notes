8.5 – ELB Advanced Features

Cách đọc note này: 4 tính năng độc lập nhau (Sticky Sessions, Cross-Zone, SNI, Connection Draining) — đề thi thường hỏi riêng lẻ từng cái kèm bẫy tên gọi (vd Connection Draining vs Deregistration Delay). Học theo bảng, không cần nhớ theo thứ tự trình bày.

1. Sticky Sessions (Session Affinity)

Sticky Sessions là gì?

Sticky Sessions là cơ chế gắn một client vào một backend instance cố định phía sau load balancer.

Cùng một client → luôn được forward đến cùng một EC2 instance trong suốt thời gian session còn hiệu lực.

Tại sao cần?

Một số ứng dụng cũ lưu session trong bộ nhớ local của từng instance (không phải distributed cache). Nếu load balancer chuyển request sang instance khác → user mất session, bị logout, mất giỏ hàng.

Sticky Sessions ngăn điều đó xảy ra.

Thực hành tốt hơn: Lưu session vào ElastiCache Redis hoặc DynamoDB để ứng dụng stateless hoàn toàn → không cần Sticky Sessions.

Hỗ trợ theo loại LB

Load Balancer Hỗ trợ?
ALB ✔ Có
CLB ✔ Có
NLB ✔ Có (chỉ TCP Stickiness)
GWLB ❌ Không

Nhược điểm

  • Mất cân bằng tải — một số instance phục vụ nhiều client hơn.
  • Không nên dùng nếu ứng dụng đã có: distributed session, session replication, DynamoDB/ElastiCache session store.

Các loại Cookie trong Sticky Sessions

Nhóm 1 — Application-based Cookies (do application tạo):

Cookie Tạo bởi Tên cookie Ghi chú
Custom Cookie Backend application Tùy chọn (không dùng AWSALB, AWSALBAPP, AWSALBTG) Có thể chứa attribute tùy chỉnh
Application Cookie Load Balancer (theo logic app) AWSALBAPP LB tạo nhưng theo lifecycle của app

Nhóm 2 — Duration-based Cookies (LB tự tạo, có thời gian hết hạn):

LB Tên cookie
ALB AWSALB
CLB AWSELB

Trong thi hay hỏi nhất: Duration-based cookie do LB tạo (AWSALB / AWSELB).

2. Cross-Zone Load Balancing

Là gì?

Cross-Zone LB cho phép mỗi LB node phân phối traffic đồng đều đến tất cả backend instances trong mọi AZ, không chỉ trong AZ của nó.

Ảnh gốc: có Cross-Zone (trái) mỗi instance chỉ nhận 6.25 request bất kể ở AZ nào; không có Cross-Zone (phải) AZ ít instance hơn (2 inst) phải gánh 25 request/instance — gấp 4 lần AZ kia (6.25/instance).

Mặc định và chi phí theo loại LB

Load Balancer Mặc định Bật/Tắt? Chi phí Inter-AZ
ALB ✔ Enabled Có thể tắt Miễn phí
NLB ❌ Disabled Có thể bật Tính phí
GWLB ❌ Disabled Có thể bật Tính phí
CLB ❌ Disabled Có thể bật Miễn phí

Điểm thi: ALB mặc định bật Cross-Zone và miễn phí. NLB/GWLB mặc định tắt và tính phí khi bật.

3. SSL Certificates & SNI

SSL/TLS là gì trong context của LB?

SSL/TLS mã hóa traffic giữa client và load balancer (in-transit encryption).

  • SSL = Secure Sockets Layer (cũ).
  • TLS = Transport Layer Security (mới, an toàn hơn).
  • Mọi người vẫn hay nói "SSL" nhưng thực chất là TLS.

Quản lý SSL Certificates

  • LB dùng X.509 certificate (SSL/TLS server certificate).
  • Quản lý tại ACM (AWS Certificate Manager) — tự động renew.
  • Hoặc upload certificate riêng lên LB.

HTTPS Listener yêu cầu

  • Phải có default certificate.
  • Có thể gắn thêm certificate để hỗ trợ multi-domain.
  • Hỗ trợ nhiều phiên bản TLS qua Security Policy.

Server Name Indication (SNI)

Vấn đề: 1 server cũ chỉ phục vụ được 1 certificate.

SNI giải quyết: cho phép 1 LB phục vụ nhiều domain với nhiều certificate — client gửi hostname ngay trong TLS handshake, LB chọn đúng certificate.

SNI hỗ trợ theo LB

LB Hỗ trợ SNI?
ALB (v2) ✔ Có
NLB (v2) ✔ Có
CloudFront ✔ Có
CLB (v1) ❌ Không — chỉ 1 cert/listener

Điểm thi: NLB cũng hỗ trợ SNI — thường bị bỏ sót! CLB không hỗ trợ SNI.

4. Connection Draining / Deregistration Delay

Là gì?

Khi một EC2 instance deregister hoặc unhealthy, ta không muốn cắt ngang các request đang xử lý dở (in-flight requests).

Connection Draining đảm bảo:

Instance được rút khỏi LB một cách an toàn — cho phép xử lý xong request hiện tại, nhưng không nhận request mới.

Hai tên gọi, cùng một tính năng

Load Balancer Tên tính năng
CLB Connection Draining
ALB + NLB Deregistration Delay

Bài thi cố đánh lừa bằng cách dùng cả hai tên — phải biết đây là cùng một cơ chế.

Cơ chế hoạt động

Thời gian chờ (Delay Time)

Cấu hình Giá trị
Default 300 giây (5 phút)
Tối thiểu 1 giây
Tối đa 3600 giây
Tắt Set = 0

Hướng dẫn sử dụng:

  • Set thấp (10–60s): request ngắn hạn như REST API (50–200ms).
  • Set cao (600–3600s): long-running jobs hoặc upload lớn.

Khi nào cần dùng?

  • Deploy version mới → remove instance cũ từ LB.
  • Scale-in Auto Scaling Group.
  • Instance unhealthy nhưng đang còn request đang xử lý.
  • Tắt/terminate EC2 để bảo trì.

Bảng từ khoá đề thi

Từ khoá trong đề Chọn
"App cũ lưu session local, mất giỏ hàng khi đổi server" Sticky Sessions
"Cookie do LB tự tạo, có hạn dùng" AWSALB (ALB) / AWSELB (CLB) — Duration-based cookie
"AZ ít instance bị quá tải trong khi AZ khác rảnh" Bật Cross-Zone Load Balancing
"NLB/GWLB bật Cross-Zone có mất phí không?" Có tính phí (khác ALB — miễn phí)
"1 LB phục vụ nhiều domain HTTPS, nhiều cert" SNI (ALB, NLB, CloudFront — không phải CLB)
"Instance sắp bị remove, đừng cắt ngang request đang chạy" Connection Draining / Deregistration Delay (default 300s)

Xem thêm domain-based: 2.1 – ELB.

Điểm hay ra thi (tổng hợp section này)

  • Sticky Sessions gây mất cân bằng tải — chỉ dùng cho app cũ chưa migrate sang distributed session.
  • AWSALB = ALB duration cookie; AWSELB = CLB duration cookie.
  • Cross-Zone LB: ALB bật mặc định và miễn phí; NLB/GWLB tắt mặc định và tính phí.
  • Connection Draining = Deregistration Delay — hai tên một tính năng.
  • CLB không hỗ trợ SNI → chỉ 1 cert/listener → lỗi thời.
  • Default Deregistration Delay = 300 giây.

Takeaway cá nhân

  • Nhớ bảng Cross-Zone theo LB type (default + chi phí) vì hay ra thi phân biệt.
  • SNI là tính năng giúp 1 ALB phục vụ nhiều domain HTTPS — thay vì cần nhiều LB.
  • Connection Draining giúp deploy zero-downtime bằng cách graceful remove instance.
