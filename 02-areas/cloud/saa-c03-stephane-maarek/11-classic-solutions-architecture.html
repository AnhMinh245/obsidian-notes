11. Classic Solutions Architecture

Cách đọc note này: Đây KHÔNG phải bài học dịch vụ mới — đây là bài ráp lại mọi thứ đã học (EC2, ELB, ASG, Route 53, RDS, ElastiCache, EBS, EFS) thành 3 case study kinh điển, mỗi case study đi từ một kiến trúc đơn giản rồi tiến hoá dần khi gặp vấn đề thực tế (downtime, mất session, cần scale read, cần backup nhanh). Đọc theo đúng thứ tự tiến hoá — đừng nhảy cóc — vì mỗi bước chỉ có ý nghĩa khi hiểu bước trước đó đang thiếu gì. Case study 3 (WordPress) dẫn tới AWS Elastic Beanstalk, phần quan trọng nhất của cả bài.

1. Case study 1 — WhatIsTheTime.com (Stateless, không cần database)

Bài toán: app trả lời "mấy giờ rồi?" — không cần lưu gì, chấp nhận downtime lúc đầu, mục tiêu cuối là scale full và zero-downtime.

Bước Kiến trúc Vấn đề gặp phải Cách giải quyết ở bước sau
1 1 EC2 public, gắn Elastic IP Muốn nâng cấp instance type (VD m5.large) → phải Stop/Start → downtime Chấp nhận ở bước này, xử lý ở bước 3
2 Scale dọc (vertical) — đổi instance type lớn hơn Vẫn 1 điểm chết duy nhất (single point of failure), vẫn downtime khi đổi size Chuyển sang scale ngang
3 Nhiều EC2 public, mỗi cái Route 53 A Record TTL 1h trỏ thẳng vào từng IP TTL 1 giờ → client cache IP cũ; instance chết → Route 53 vẫn trả IP chết trong tối đa 1 giờ Bỏ trỏ thẳng IP, dùng Load Balancer
4 Route 53 Alias Record → ELB + Health Check → EC2 private (Security Group giới hạn chỉ nhận traffic từ ELB) Vẫn phải tự tay thêm/bớt EC2 instance theo tải Auto Scaling Group
5 Auto Scaling Group đứng sau ELB, EC2 private trong ASG Vẫn chỉ 1 Availability Zone → cả AZ chết là sập app Multi-AZ
6 ASG trải 1 → 3 Availability Zone, ELB multi-AZ Đạt mục tiêu: scale ngang + dọc, zero-downtime, chịu được mất 1 AZ — kiến trúc hoàn chỉnh cho app stateless

Kiến trúc cuối case study 1: Route 53 Alias Record → ELB (Health Check + Multi-AZ) → Auto Scaling Group trải đều 3 Availability Zone.

7 khái niệm được ôn lại qua case study này (đã học ở các bài trước, xem lại nếu quên): Public vs Private IP, Elastic IP vs Route 53 vs Load Balancer, Route 53 TTL/A Record/Alias Record, EC2 thủ công vs Auto Scaling Group, Multi-AZ để chịu disaster, ELB Health Check, Security Group rules, Reserved Capacity để tiết kiệm chi phí khi biết trước minimum capacity.

2. Case study 2 — MyClothes.com (Stateful, có shopping cart)

Bài toán: web bán hàng, có shopping cart, hàng trăm user đồng thời, cần giữ session + lưu thông tin user (địa chỉ…) trong database — khác hẳn case study 1 vì giờ có state.

2.1 Vấn đề cốt lõi của stateful app trên kiến trúc scale-ngang

Khi có nhiều EC2 đứng sau ELB, request của cùng 1 user có thể rơi vào EC2 khác nhau ở mỗi lần gọi → shopping cart "biến mất" nếu state lưu trong RAM của từng instance.

2.2 Ba cách xử lý state — tiến hoá dần

Giải pháp Cách làm Nhược điểm
ELB Sticky Session (Session Affinity) ELB luôn định tuyến user về đúng 1 EC2 đã phục vụ họ trước đó Mất cân bằng tải nếu 1 EC2 bị "dính" quá nhiều user
Client-side: Web Cookies Server gửi toàn bộ nội dung cart vào cookie, lưu ở trình duyệt user HTTP request nặng hơn (cookie đi kèm mọi request); rủi ro bảo mật (cookie có thể bị sửa); phải validate; giới hạn < 4KB
Server-side: ElastiCache (khuyến nghị) Server chỉ gửi session_id nhỏ gọn vào cookie; nội dung session thật lưu ở ElastiCache (thay thế: DynamoDB) Cần thêm 1 tầng cache, nhưng đây là cách chuẩn — request nhẹ, không lộ dữ liệu

2.3 Thêm database cho dữ liệu lâu dài (user info)

  • Dữ liệu user (địa chỉ, tên…) → lưu Amazon RDS, Multi-AZ để chịu disaster.
  • ElastiCache đảm nhiệm 2 việc: (a) lưu session, (b) cache kết quả truy vấn từ RDS để giảm tải đọc.

2.4 Scale reads — 2 chiến lược

Chiến lược Cách hoạt động
Cache-first (Lazy Loading qua ElastiCache) App hỏi cache trước → cache hit trả ngay; cache miss → đọc RDS rồi ghi lại vào cache
RDS Read Replica Ghi (write) luôn vào RDS Master; đọc (read) rải ra các Read Replica — RDS tự động replicate Master → Replica

2.5 Kiến trúc hoàn chỉnh + Security Groups tham chiếu lẫn nhau

Kiến trúc cuối case study 2: ELB → ASG (Multi-AZ) ↔ ElastiCache (Multi-AZ, session + cache) ↔ RDS (Multi-AZ). Route 53 vẫn ở đầu vào như case study 1.

Nguyên tắc bảo mật xuyên suốt (rất hay bị hỏi trong đề thi):

  • Security Group của ELB: mở HTTP/HTTPS cho 0.0.0.0/0.
  • Security Group của EC2: chỉ nhận traffic từ Security Group của ELB (không mở public trực tiếp).
  • Security Group của ElastiCache: chỉ nhận traffic từ Security Group của EC2.
  • Security Group của RDS: chỉ nhận traffic từ Security Group của EC2.

Đây chính là kỹ thuật "Security Group referencing Security Group" — mỗi tầng chỉ tin tưởng đúng tầng ngay phía trước nó, không có tầng nào mở public ngoại trừ ELB.

3. Case study 3 — MyWordPress.com (3-tier, dẫn tới Elastic Beanstalk)

Bài toán: WordPress site cần hiển thị đúng hình ảnh upload + lưu blog/user data vào MySQL — kiến trúc gần giống case study 2 nhưng dùng Aurora thay RDS thường và cần giải quyết thêm bài toán lưu file ảnh dùng chung giữa nhiều EC2.

3.1 Database layer — Aurora thay vì RDS

Dùng Aurora MySQL Multi-AZ + Read Replicas thay vì RDS MySQL thường — lý do: Aurora tự động Multi-AZ, replicate nhanh hơn, tối đa nhiều Read Replica hơn RDS (đã học chi tiết ở §09.2 Amazon Aurora).

3.2 Bài toán lưu ảnh: EBS → vấn đề → EFS

Giải pháp Vấn đề
Mỗi EC2 có EBS Volume riêng để lưu ảnh upload EBS chỉ gắn được vào 1 AZ — user upload ảnh vào EC2 ở AZ1, request sau rơi vào EC2 ở AZ2 → không thấy ảnh vừa upload (dữ liệu không đồng bộ giữa các EBS Volume)
Amazon EFS (file system dùng chung, mount qua ENI trên mỗi AZ) Toàn bộ EC2 ở mọi AZ đọc/ghi vào cùng một EFS → ảnh upload ở đâu cũng thấy ngay ở nơi khác — đúng bản chất "network file system" đã học ở [[07 - EC2 Instance Storage

Nguyên tắc chọn nhanh: EBS = ổ đĩa riêng của 1 instance (single-instance application). EFS = ổ đĩa dùng chung nhiều instance/nhiều AZ (distributed application). Ảnh upload cần "ai cũng thấy" → chọn EFS.

4. Instantiating Applications quickly — khởi tạo hạ tầng nhanh

Vấn đề chung của cả 3 case study: launch 1 stack đầy đủ (EC2 + EBS + RDS) từ đầu tốn thời gian (cài app, nạp dữ liệu, cấu hình). 3 kỹ thuật tăng tốc:

Resource Kỹ thuật
EC2 Golden AMI (build sẵn AMI có app + OS dependencies) hoặc User Data (bootstrap script chạy lúc launch) hoặc kết hợp cả 2 (chính là cách Elastic Beanstalk vận hành)
RDS Restore từ snapshot có sẵn schema + data
EBS Restore từ snapshot đã format sẵn + có data

Ghép 3 kỹ thuật này vào đúng mô hình 3 case study ở trên → ra được kiến trúc web app 3-tier điển hình:

3 tầng mạng rõ rệt: Public Subnet (ELB) → Private Subnet (ASG chạy app) → Data Subnet (ElastiCache + RDS). Đây là kiến trúc "mặc định" cho hầu hết web app trên AWS — worth nhớ nằm lòng vì đề thi hay vẽ lại đúng sơ đồ này.

5. AWS Elastic Beanstalk — tự động hoá toàn bộ kiến trúc trên

5.1 Vấn đề của developer

Muốn deploy 1 web app 3-tier như trên, developer phải tự quản lý: EC2, ASG, ELB, RDS, scaling, health monitoring... — trong khi thứ họ thực sự muốn chỉ là code chạy được.

5.2 Elastic Beanstalk là gì?

  • Managed service, developer-centric: bạn chỉ lo code, Beanstalk tự lo capacity provisioning, load balancing, scaling, health monitoring, instance configuration.
  • Dùng lại đúng các thành phần đã học: EC2, ASG, ELB, RDS…
  • Vẫn giữ toàn quyền cấu hình nếu cần can thiệp sâu.
  • Beanstalk miễn phí — chỉ trả tiền cho tài nguyên bên dưới (EC2, RDS…) như bình thường.

5.3 3 khái niệm cốt lõi

Khái niệm Ý nghĩa
Application Tập hợp các component: environments, versions, configurations
Application Version Một phiên bản (iteration) cụ thể của code
Environment Tập tài nguyên AWS chạy 1 application version tại 1 thời điểm; có 2 loại tier: Web Server Tier và Worker Environment Tier; có thể tạo nhiều environment (dev/test/prod)

Vòng đời: Create Application → Upload Version → Launch Environment → Manage/deploy new version (lặp lại khi có version mới).

Nền tảng hỗ trợ: Go, Java SE, Java + Tomcat, .NET Core (Linux) / .NET (Windows), Node.js, PHP, Python, Ruby, Docker (Single container / Multi-container / Preconfigured), Packer Builder.

5.4 Web Server Tier vs Worker Tier

  • Web Server Tier: ELB → Auto Scaling Group → EC2 chạy web server, phục vụ trực tiếp HTTP request từ user (domain dạng myapp.<region>.elasticbeanstalk.com).
  • Worker Tier: EC2 (Worker) poll message từ SQS Queue — dùng cho tác vụ nền/nặng. Scale theo số lượng message trong SQS. Web Tier có thể đẩy message vào SQS để Worker Tier xử lý bất đồng bộ — đây chính là pattern decoupling đã học ở §17.

5.5 Deployment mode

Mode Phù hợp
Single Instance (Elastic IP, không ELB) Development/test
High Availability (ALB + Auto Scaling Group + RDS Multi-AZ Master/Standby) Production

Bảng từ khoá đề thi

Từ khoá trong đề Chọn
"App không cần database, cần TTL nhỏ để đổi IP nhanh nhưng có delay" Route 53 A Record + TTL — hiểu rõ đánh đổi TTL thấp (đổi nhanh, nhiều query hơn) vs TTL cao (ít query, đổi chậm)
"EC2 chết, muốn Route 53 tự động không trả về IP chết" Alias Record trỏ vào ELB (có Health Check), không trỏ thẳng IP
"Shopping cart bị mất khi user chuyển sang request khác" ELB Sticky Session hoặc chuyển session ra ElastiCache/DynamoDB
"Không muốn cookie chứa dữ liệu nhạy cảm, cookie phải nhỏ" Server-side session ở ElastiCache, cookie chỉ chứa session_id
"Nhiều EC2 cần đọc/ghi chung 1 file, ở nhiều AZ" EFS, không phải EBS
"1 EC2, 1 file hệ thống, hiệu năng cao, không chia sẻ" EBS
"Muốn launch EC2/RDS/EBS đã có sẵn data/app ngay lập tức" Golden AMI (EC2) / Restore Snapshot (RDS, EBS)
"Chỉ muốn lo code, không muốn tự quản lý ASG/ELB/RDS" AWS Elastic Beanstalk
"Cần xử lý tác vụ nền nặng, tách khỏi web tier, scale theo hàng đợi" Elastic Beanstalk Worker Tier + SQS
"Mỗi tầng chỉ nên tin tưởng đúng tầng liền trước, không mở public tràn lan" Security Group tham chiếu Security Group (SG-to-SG reference)

Điểm hay ra thi

  • Cả 3 case study đi theo đúng 1 mạch: đơn giản → phát hiện vấn đề → thêm 1 thành phần AWS để giải quyết — đề thi thường mô tả một "vấn đề" và hỏi thành phần nào giải quyết đúng.
  • EBS vs EFS cho lưu trữ file dùng chung nhiều AZ là bẫy hay gặp nhất của case study 3.
  • Security Group tham chiếu Security Group (thay vì mở CIDR) là pattern bảo mật chuẩn cho kiến trúc 3-tier — ELB public, mọi tầng sau chỉ nhận từ SG của tầng liền trước.
  • Elastic Beanstalk không phải dịch vụ mới — nó là lớp tự động hoá phía trên EC2/ASG/ELB/RDS đã học, bản thân Beanstalk miễn phí.
  • Worker Tier dùng SQS, scale theo số message trong queue — khác cơ chế với Web Tier (scale theo CPU/traffic qua ELB).

Takeaway cá nhân

  • Bài này là lúc "ráp lại" toàn bộ kiến thức rời rạc từ EC2 đến RDS thành 1 bức tranh — nên đọc lại sau khi đã học xong Route 53, RDS, ElastiCache để thấy rõ mạch logic.
  • Kiến trúc 3-tier (Public/Private/Data Subnet) ở §4 là khuôn mẫu nên nhớ nằm lòng — phần lớn câu hỏi thiết kế kiến trúc trong đề thi đều biến tấu từ khuôn này.
  • Elastic Beanstalk dễ bị đánh giá thấp vì "chỉ là tự động hoá" — nhưng đề thi hay hỏi phân biệt Beanstalk với CloudFormation (declarative IaC) hay OpsWorks, cần phân biệt rõ tầng trừu tượng của từng dịch vụ.
