Data Ingestion & Transformation: Kinesis, Glue, Athena

Đối với workloads xử lý dữ liệu lớn (Big Data) và phân tích luồng dữ liệu (Streaming Data), kiến trúc High-Performing yêu cầu khả năng đẩy dữ liệu (ingest), chuyển đổi định dạng (transform), và phân tích trực tiếp (query) tốc độ cao mà không làm nghẽn cổ chai ứng dụng cốt lõi. 2. Dòng họ Amazon Kinesis (Streaming Data)

Kinesis được dùng để thu thập và xử lý các luồng dữ liệu thời gian thực có khối lượng khổng lồ. Việc phân biệt chính xác 3 dịch vụ Kinesis là kỹ năng bắt buộc để thi đậu.

2.1. So sánh Chuyên sâu Kinesis Data Streams (KDS) và Kinesis Data Firehose (KDF)

Đây là 2 service dễ gây nhầm lẫn nhất trong bài thi SAA-C03.

Tiêu chí Kinesis Data Streams (KDS) Kinesis Data Firehose (KDF) Kinesis Data Analytics (KDA)
Mục đích chính Hấp thụ dữ liệu theo thời gian thực (Real-time). Tự viết code Consumer xử lý logic. Đẩy thẳng dữ liệu (Delivery) vào kho đích (S3, Redshift) mà không cần code Consumer. Phân tích luồng dữ liệu KDS bằng SQL hoặc Apache Flink theo thời gian thực.
Độ trễ (Latency) Rất thấp (~200ms). Độ trễ do buffer (tối thiểu 60 giây hoặc 1MB buffer). Thời gian thực (tùy thuộc độ trễ của SQL engine).
Cấu trúc quản lý Dựa vào Shards (phân mảnh). Phải Provision shard thủ công hoặc dùng On-Demand. Hoàn toàn Serverless, tự động auto-scale, KHÔNG có shards. Hoàn toàn Serverless.
Lưu trữ dữ liệu Dữ liệu tồn tại trong stream từ 1 ngày đến tối đa 365 ngày. KHÔNG LƯU DỮ LIỆU. Nhận vào là đẩy đi ngay. Không lưu trữ, chỉ đọc và tính toán.
Khả năng đọc lại Hỗ trợ Multiple Consumers đọc cùng 1 data. Có Replay data (đọc lại quá khứ). Không thể đọc lại (No data replay). Dữ liệu trôi đi là mất khỏi ống. Không áp dụng.
Đích đến (Destinations) Bất cứ thứ gì bạn tự code để lấy (KCL, Lambda, EC2). CHỈ HỖ TRỢ đích cứng: S3, Redshift, OpenSearch, HTTP, Splunk, Datadog. Ghi kết quả ngược lại KDS hoặc đẩy vào Firehose.

2.2. Kinesis Data Streams: Limits, Under the Hood & Troubleshooting

  • Limits & Quotas (Bắt buộc phải nhớ):

    • 1 Shard hỗ trợ Ghi (Write): 1 MB/s hoặc 1000 PUT records/giây.
    • 1 Shard hỗ trợ Đọc (Read): 2 MB/s. Mặc định băng thông Đọc này bị chia sẻ (Shared throughput) giữa tất cả các Consumers đang đọc cái stream đó. Kích thước tối đa 1 record là 1 MB.

  • Enhanced Fan-Out (EFO):

    • Vấn đề: Nếu bạn có 5 Lambda functions (Consumers) cùng đọc 1 shard KDS, băng thông 2MB/s sẽ bị chia 5, mỗi thằng chỉ được 400KB/s → Nghẽn cổ chai khủng khiếp.
    • Giải pháp: Bật EFO. Tính năng này cấp cho mỗi Consumer một ống băng thông 2MB/s ĐỘC LẬP không dùng chung. Đi kèm với cơ chế HTTP/2 push data tới Consumer siêu nhanh (trễ < 70ms). Trả thêm tiền khá chat.

  • Troubleshooting: ProvisionedThroughputExceededException:

    • Dấu hiệu: Ứng dụng Producer (người gửi) bị lỗi và không gửi data vào stream được.
    • Nguyên nhân 1: Tổng tải ghi lớn hơn tổng số shard (VD: Ghi 5MB/s nhưng chỉ cấp 3 Shards → max 3MB/s).
    • Nguyên nhân 2: Hot Shard (Phân vùng nóng). Dữ liệu ghi vào KDS dựa trên Partition Key. Nếu bạn chọn Partition Key tồi (ví dụ log từ Mỹ và VN nhưng Mỹ chiếm 95% traffic), thuật toán băm (Hash function) sẽ ném 95% data vào cùng một shard duy nhất, làm nó quá tải 1MB/s trong khi các shard khác rảnh rỗi.
    • Giải pháp:
      1. Tăng số shard (Resharding / Split shard).
      2. Đổi Partition Key phân tán ngẫu nhiên hơn (vd: dùng UUID hoặc kết hợp UserId + Timestamp).
      3. Chuyển stream sang chế độ On-Demand Mode (KDS tự động scale số shard cho bạn mà không cần lo nghĩ, nhưng đắt tiền hơn).
Cảnh báo Kinesis vs SQS

Nếu bài thi hỏi về việc decouple hệ thống với yêu cầu thực thi đúng 1 lần (Exactly-once) và xử lý từng tin nhắn độc lập rồi xoá, hãy dùng SQS. Kinesis chuyên dùng khi cần Nhiều ứng dụng đọc cùng 1 tập dữ liệu đồng thời (Multiple consumers), và cần Replay (phát lại) tin nhắn trong quá khứ. Kinesis không xoá data khi có người đọc xong, nó giữ data đến hết Data Retention Period.

2.3. CLI & JSON Snippet (Kinesis)

Snippet: Gửi một bản ghi JSON vào Kinesis Stream bằng CLI:

# Gửi 1 bản ghi vào KDS
aws kinesis put-record \
    --stream-name SensorDataStream \
    --partition-key "sensor-id-12" \
    --data '{"temperature": 25.4, "humidity": 60}'

# Lệnh để Split Shard (cách khắc phục Hot Shard thủ công)
# Yêu cầu truyền vào ShardToSplit và giá trị băm mới để cắt đôi Shard.
aws kinesis split-shard \
    --stream-name SensorDataStream \
    --shard-to-split shardId-000000000000 \
    --new-starting-hash-key 170141183460469231731687303715884105728

3. Chuyển đổi và Xử lý Dữ liệu: AWS Glue & EMR

3.1. AWS Glue (Deep Dive)

Keo dán (Glue) kết nối hệ sinh thái Data. Nó là nền tảng ETL (Extract, Transform, Load) Serverless dựa trên môi trường Apache Spark.

  • Glue Data Catalog: Metastore trung tâm, lưu trữ thông tin về cấu trúc (schema) của dữ liệu rải rác trên S3, RDS, DynamoDB. Nó đóng vai trò như một quyển danh bạ khổng lồ.
  • Glue Crawlers: Robot đi thu thập thông tin tự động. Nó quét dữ liệu thô trên S3, tự động phân tích định dạng (ví dụ nó phát hiện file CSV có 3 cột: ID kiểu INT, Name kiểu STRING), sau đó nhét thông tin (Table schema) này vào Catalog.
  • Glue ETL Jobs: Dùng Python hoặc Scala để viết logic transform data. Chạy trên hạ tầng Serverless Spark do AWS cấp phát.
    • Tính năng Job Bookmarks: Giúp ETL Job ghi nhớ nó đã xử lý tới dòng data/file nào trong đợt chạy trước, để đợt chạy sau CHỈ xử lý các file mới thêm vào, tiết kiệm chi phí và thời gian.
  • Glue DataBrew: Visual tool với giao diện kéo thả để dọn dẹp dữ liệu (cleaning data, lọc giá trị null, chuẩn hóa ngày tháng) dành cho Data Analysts mà KHÔNG CẦN VIẾT CODE.
Mẹo thi Transformation cốt lõi

Rất nhiều câu hỏi SAA-C03 liên quan đến tối ưu hoá chi phí và tốc độ truy vấn data lake. Bạn phải dùng Glue để chuyển đổi định dạng dữ liệu (Transform) từ text-based (CSV/JSON) sang định dạng cột (Columnar format) như Parquet hoặc ORC, đồng thời áp dụng thuật toán nén (Snappy). Định dạng cột giúp engine đọc từ trên xuống dọc theo cột, bỏ qua các cột không cần thiết, giúp tiết kiệm tới 90% chi phí scan S3.

3.2. So sánh AWS Glue ETL với Amazon EMR

  • AWS Glue:
    • Hoàn toàn Serverless, tự động scale. Tính tiền theo DPU (Data Processing Unit) theo giây.
    • Không cần quản lý hạ tầng cụm máy chủ. Tốt cho các task ETL rời rạc chạy ban đêm, data pipeline hiện đại.
  • Amazon EMR (Elastic MapReduce):
    • Triển khai thành cụm (Cluster) Hadoop/Spark trên tập hợp các máy EC2 (Master node, Core nodes, Task nodes).
    • Phù hợp cho team rành DevOps, đã có sẵn mã nguồn Spark/Hadoop on-premise, hoặc cần cụm máy chủ chạy 24/7 liên tục xử lý data siêu khủng. Hỗ trợ Spot Instances để giảm 90% phí compute.

4. Phân tích Serverless: Athena & QuickSight

4.1. Amazon Athena & Tối ưu Hiệu năng (Deep Dive)

Athena là engine truy vấn SQL tương tác (Interactive Query Service), dựa trên Presto. Cho phép bạn chạy câu lệnh SQL tiêu chuẩn để phân tích dữ liệu trực tiếp trên S3 mà không cần Load vào Database nào (Schema-on-read).

  • Cách tính phí: Không tính phí máy chủ, chỉ tính phí dựa trên lượng dữ liệu bạn QUÉT (Scanned data). VD: $5 / TB quét.
  • Tối ưu Hiệu năng và Chi phí (Bí kíp bắt buộc thi):
    1. Dùng Columnar Format: Như đã nói ở trên, dùng Glue chuyển CSV → Parquet/ORC. Nếu query SELECT Name FROM Users, Athena dạng cột sẽ chỉ đọc file lưu cột Name, bỏ qua cột Age, Address... giảm data scan khổng lồ.
    2. Dùng Partitioning (Phân vùng lưu trữ): Lưu file vào S3 theo cấu trúc thư mục dạng s3://my-lake/logs/year=2023/month=10/day=15/. Truy vấn SELECT * FROM logs WHERE year=2023 AND month=10 sẽ chỉ đạo Athena quét duy nhất thư mục đó, phớt lờ toàn bộ các năm khác.
  • Troubleshooting: Zero records returned (Câu hỏi kinh điển):
    • Tình huống: Bạn đã setup S3, tạo bảng qua Athena, data trên S3 đang nằm trong các thư mục partition như year=2023/.... Nhưng khi chạy query SELECT, Athena báo thành công nhưng trả về 0 dòng.
    • Giải pháp: Do metadata Catalog chưa biết về sự tồn tại của các thư mục mới này. Bạn phải chạy lệnh SQL đặc biệt MSCK REPAIR TABLE table_name để Athena cập nhật các phân vùng mới trên S3 vào Catalog. (Hoặc thiết lập Glue Crawler chạy định kỳ tự động).
  • Athena Federated Query: Gọi query SQL xuyên qua RDS, DynamoDB, Redshift thông qua các Lambda connectors mở rộng. Giới hạn Timeout tối đa của query trong Athena là 30 phút.

4.2. Amazon QuickSight & Lake Formation

  • QuickSight: Công cụ vẽ BI Dashboards (Bảng điều khiển thông minh) Serverless. Engine bộ nhớ siêu mạnh SPICE (Super-fast, Parallel, In-memory Calculation Engine) giúp render biểu đồ cực nhanh, hỗ trợ chục ngàn user đồng thời. Tích hợp Machine Learning để tự động phát hiện dị thường (Anomaly detection).
  • AWS Lake Formation: Công cụ thiết lập Data Lake bảo mật trong vài ngày thay vì vài tháng code thủ công IAM. Tính năng ăn tiền: Fine-grained access control ở cấp độ Cột (Column-level) và Hàng (Row-level) (Ví dụ: user HR chỉ xem được cột Tên, không xem được cột Lương; hoặc chỉ xem được Hàng của nhân viên chi nhánh HN).

5. Dịch chuyển dữ liệu lớn: DataSync & Snow Family

Nếu cần đưa chục TB, PB dữ liệu từ On-premises vào kiến trúc Cloud AWS:

  1. AWS DataSync:
    • Phần mềm (Agent) cài ở on-premise. Đồng bộ qua mạng (Internet/Direct Connect).
    • Hỗ trợ NFS, SMB, HDFS. Đích tới S3, EFS, FSx.
    • Tối ưu hóa giao thức mạng để chạy cực nhanh, tự checksum integrity đảm bảo không lệch bit data. Phù hợp cho Active data migration (dữ liệu đang dùng hàng ngày).
  2. AWS Snow Family (Offline migration / Edge Compute):
    • Thay vì đẩy qua mạng chật hẹp, AWS gửi thiết bị vật lý tới công ty bạn, bạn chép data vào, rồi gửi xe tải chở về Data Center của AWS để họ cắm cáp đổ vào S3.
    • Snowcone: Nhỏ như cuốn sách (8-14TB). Dùng cho môi trường khắc nghiệt (sa mạc, nhà máy), gom data IoT. Pin dùng được ngoài trời.
    • Snowball Edge Storage Optimized: Nặng 22kg (80TB). Hình dạng như cái vali thép.
    • Snowball Edge Compute Optimized: Có chip máy tính mạnh (EC2/Lambda trực tiếp trên vali) để chạy Machine Learning sơ bộ hoặc filter log trước khi chuyển về trung tâm.
    • Snowmobile: (100 PB). Xe tải đầu kéo chở nguyên 1 Container 45 feet chứa hệ thống lưu trữ Exabyte.
Quy tắc vận chuyển (Nguyên tắc chọn đáp án)
  • Dưới 10TB / Mạng internet cực mạnh → Dùng DataSync hoặc S3 Multipart Upload.
  • Hàng chục/trăm TB / Mạng yếu hoặc cấm kết nối mạng ngoài → Dùng Snowball Edge. Dù mất 1 tuần vận chuyển vẫn nhanh hơn chờ 2 tháng up qua mạng 10Mbps.
  • Hàng chục Petabytes → Triệu hồi xe tải Snowmobile.

6. Case Studies Thực Tế (Kiến trúc phức tạp)

Case Study 1: Hệ thống Phát Hiện Gian Lận (Fraud Detection) Thời Gian Thực Của Ngân Hàng

Bài toán: Một ngân hàng cần phát hiện giao dịch thẻ tín dụng bất thường (stolen card) trong thời gian dưới 3 giây từ lúc máy quẹt thẻ (POS) gửi tín hiệu. Đồng thời, họ phải lưu trữ vĩnh viễn toàn bộ lịch sử giao dịch gốc không thay đổi để kiểm toán (audit) bằng SQL và vẽ biểu đồ báo cáo hàng ngày.

Giải pháp Kiến trúc High-Performing:

  1. Hàng ngàn máy POS gửi luồng giao dịch liên tục định dạng JSON vào Amazon Kinesis Data Streams (KDS).
  2. Một AWS Lambda function đóng vai trò là Consumer, đọc KDS liên tục. Nó chạy thuật toán Rule-based, query đối chiếu vị trí khách hàng siêu nhanh (microseconds) thông qua DynamoDB + DAX.
  3. Nếu phát hiện gian lận (VD: quẹt ở VN rồi 5 phút sau quẹt ở Mỹ), Lambda bắn tin nhắn vào SNS để nhắn tin SMS khóa thẻ lập tức.
  4. Để lưu trữ Audit Log, thiết lập một Kinesis Data Firehose đọc data trực tiếp từ cùng KDS gốc đó (hoặc từ chính POS). Firehose được cấu hình Buffer 1MB/60s, cứ mỗi phút nó đóng gói data thành file và đẩy thẳng vào kho lưu lạnh Amazon S3.
  5. Đội ngũ Data Analyst sử dụng Amazon Athena để query S3 Data Lake, phân vùng theo year/month/day, xuất kết quả ra Amazon QuickSight vẽ dashboard cuối ngày.

Case Study 2: Chuyển Đổi Định Dạng Log Hệ Thống IoT Tự Động

Bài toán: Hàng triệu cảm biến nhiệt độ nhà kính gửi dữ liệu thô (Raw log CSV) liên tục. Yêu cầu hệ thống tự động làm sạch data (xóa các dòng nhiệt độ = NULL) và lưu dưới dạng tối ưu (Parquet) để phân tích lâu dài với chi phí query cực rẻ.

Giải pháp Kiến trúc High-Performing:

  1. Cảm biến gọi API gửi CSV vào Kinesis Firehose.
  2. Kinesis Firehose có tính năng Data Transformation, nó được cấu hình gọi một Lambda function (đóng vai trò Transform). Khi có data chạy trong ống Firehose, Lambda lập tức bắt lấy, xóa dòng NULL, rồi trả lại ống.
  3. Đồng thời, Firehose được kích hoạt tính năng Format Conversion tích hợp sẵn (dùng Glue Catalog schema), tự động đổi luồng CSV sạch thành định dạng Parquet rồi mới ghi vào Amazon S3. Không cần bật EMR hay Glue ETL rườm rà.

7. Checklist Kế hoạch Ôn tập Data Ingestion

  • Phân biệt rõ rệt Kinesis Data Streams (Real-time, code consumer, Shards, Replay) vs Kinesis Data Firehose (Near-realtime, no code, auto-scale, no replay).
  • Tính toán giới hạn băng thông Shard của Kinesis (1MB/s In, 2MB/s Out).
  • Nắm vững cách giải quyết lỗi Hot Shard (Split shard, đổi Partition Key) và lỗi chia sẻ băng thông đọc (Bật EFO - Enhanced Fan-out).
  • Nắm khái niệm Glue Catalog (metastore) và Glue Crawlers (robot tìm schema).
  • Hiểu rõ vì sao phải đổi CSV sang Parquet/ORC (Định dạng cột) để Athena quét nhanh và rẻ.
  • Hiểu cơ chế S3 Partitioning (phân vùng theo date/category) để Athena giảm Scanned Data.
  • Thuộc câu lệnh MSCK REPAIR TABLE dùng khi Athena query trả về 0 dòng trên data có phân vùng mới.
  • So sánh AWS DataSync (chuyển qua mạng online, nhanh, tự checksum) và Snow Family (chuyển offline qua xe tải vật lý khi mạng yếu/data siêu lớn).
  • Phân biệt Snowball Edge Storage (80TB) và Compute (chạy EC2/Lambda nội bộ).
