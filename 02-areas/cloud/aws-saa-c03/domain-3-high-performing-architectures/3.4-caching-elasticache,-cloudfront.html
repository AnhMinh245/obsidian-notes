Caching Solutions: ElastiCache & CloudFront

Để tạo nên một kiến trúc High-Performing tuyệt đối trên quy mô toàn cầu, bạn không thể cứ bắt ứng dụng gọi vào cơ sở dữ liệu vật lý hoặc tải tài nguyên tĩnh từ một máy chủ cách xa nửa vòng trái đất. Dữ liệu cần được đưa tới càng gần người dùng (Edge) hoặc được lưu vào bộ nhớ RAM (In-memory) thay vì liên tục đọc từ đĩa cứng.

Hai trụ cột không thể thiếu của Caching trong AWS là Amazon CloudFront (cache tĩnh/động tại Edge) và Amazon ElastiCache (cache dữ liệu ứng dụng bên trong VPC).

1. Amazon CloudFront (Content Delivery Network - CDN)

CloudFront tăng tốc phân phối dữ liệu tĩnh và động (.html, .css, js, ảnh, video, APIs) bằng mạng lưới hơn 400+ Edge Locations trên toàn thế giới nối với nhau bằng đường truyền xương sống (AWS backbone network) độc quyền siêu tốc.

1.1. Kiến trúc phân phối (CloudFront Distribution Flow)

1.2. Origins, Bảo mật S3 (OAC) & Giới hạn (Limits)

  • Origins hợp lệ: Bạn có thể cắm CloudFront vào S3 bucket, Custom Origin (ALB, EC2, máy chủ on-premises HTTP bất kỳ), MediaStore, hoặc API Gateway.
  • Limits & Quotas:
    • Mặc định 100 Distributions mỗi tài khoản.
    • Tối đa 250 Cache Behaviors mỗi Distribution.
    • Hỗ trợ băng thông lên tới hàng chục Gbps mỗi Distribution (có thể yêu cầu tăng).
  • Bảo mật S3 (OAC - Origin Access Control): Trọng tâm bài thi SAA-C03. Khi dùng S3 làm Origin, để cấm người dùng truy cập trực tiếp vào link S3 public (vượt mặt CloudFront), bạn phải block public access toàn bộ S3. Sau đó, thiết lập OAC trên CloudFront. Cuối cùng, gắn một Resource-based Policy vào S3 bucket cho phép Service Principal của CloudFront OAC được đọc data. (OAC là bản nâng cấp bảo mật cao hơn OAI cũ, hỗ trợ cả S3 KMS mã hóa).

1.3. Cấu hình Cache Behaviors & Tối ưu TTL

  • Path Patterns: Dùng để định tuyến request. Ví dụ: *.jpg trỏ về S3 Origin (lưu ảnh tĩnh), trong khi /* trỏ về ALB (ứng dụng web động xử lý logic).
  • TTL (Time To Live): Kiểm soát thời gian file nằm trên edge. Có Min TTL, Max TTL và Default TTL. Tối ưu nhất là để Origin server quy định thông qua HTTP Headers (Cache-Control max-age hoặc Expires).
  • Cache Invalidation (Xoá Cache thủ công): Nếu file lỗi đã bị cache trên toàn cầu, bạn có thể ép CloudFront xóa cache trước khi hết TTL bằng cách tạo Invalidation path (VD: /images/logo.png hoặc /*). Việc này tính phí sau 1000 path đầu tiên mỗi tháng và mất vài phút để lan truyền toàn cầu. Tốt nhất là dùng cơ chế đánh version file (vd: logo_v2.png) thay vì xoá cache.

1.4. Troubleshooting CloudFront Errors

  • Lỗi 502 Bad Gateway: Lỗi CỰC KỲ phổ biến khi dùng Custom Origin (ALB/EC2) kết nối qua HTTPS. Xảy ra khi chứng chỉ SSL ở Origin không hợp lệ (hết hạn, self-signed), hoặc tên miền trên chứng chỉ Origin không khớp với Host header mà CloudFront gửi tới. → Fix: Đảm bảo Origin cài SSL hợp lệ cấp bởi Public CA (VD: dùng AWS ACM cấp chứng chỉ gắn lên ALB).
  • Lỗi 504 Gateway Timeout: CloudFront chờ Origin trả lời quá lâu (vượt ngưỡng timeout mặc định 30s). → Fix: Tăng origin response timeout trong cài đặt CloudFront hoặc nâng cấp cấu hình EC2/ALB phía sau để xử lý nhanh hơn.
  • Lỗi 403 Access Denied (S3 Origin): Xảy ra khi bạn chưa config S3 Bucket Policy đúng cách cho OAC, hoặc user gọi một file không tồn tại nhưng bucket lại không có quyền s3:ListBucket (Lúc này S3 giấu lỗi 404 và trả ra 403 để bảo mật).

1.5. Edge Compute: So sánh Lambda@Edge vs CloudFront Functions

Bạn có thể đưa code chạy trực tiếp tại các Edge của CloudFront thay vì phải chạy ở region gốc.

Tiêu chí CloudFront Functions Lambda@Edge
Ngôn ngữ Chỉ JavaScript Node.js, Python
Vị trí chạy Hơn 400+ Edge Locations (Sát user nhất) Regional Edge Caches (Xa user hơn một chút)
Trigger points Chỉ chặn ở Viewer Request / Viewer Response Viewer & Origin Request/Response
Tốc độ thực thi Siêu nhanh < 1 ms Lên tới 5s (Viewer), 30s (Origin)
Network Access Không có (Không gọi được API bên ngoài) Có (Gọi được database DynamoDB, external APIs)
Use case Rewrite URL, sửa đổi HTTP Headers siêu tốc, kiểm tra cú pháp token JWT tĩnh, A/B testing nhỏ. Custom logic phức tạp, gọi DB kiểm tra quyền truy cập, render trang web động ở rìa.

2. AWS Global Accelerator (Mở rộng Networking Toàn Cầu)

Đây là anh em họ của CloudFront nhưng hoạt động ở layer khác. Hãy chú ý các điểm khác biệt trí mạng:

Tiêu chí Amazon CloudFront AWS Global Accelerator
Bản chất CDN (Content Delivery Network). Tối ưu hóa Network Routing qua BGP.
Giao thức hỗ trợ HTTP, HTTPS. Cấp độ Layer 7. TCP, UDP. Cấp độ Layer 4 (và L7).
Đầu ra IP IP thay đổi liên tục, phụ thuộc vào Edge user truy cập. Cấp đúng 2 địa chỉ IP tĩnh (Anycast IP) trên toàn cầu.
Caching (Lưu trữ đệm) CÓ Caching nội dung ở Edge. KHÔNG Caching. Chỉ làm đường ống siêu tốc gửi thẳng traffic về Endpoint gốc nhanh nhất.
Use Case kỳ thi Phân phối web app tĩnh, video streaming, API caching. App game (dùng UDP traffic), IoT, Whitelisting IP cho B2B (vì cung cấp 2 IP tĩnh vĩnh viễn), chống thảm họa cực nhanh (Failover < 1 phút).

3. Amazon ElastiCache (In-Memory Database Caching)

Nếu CloudFront cache file tĩnh ở rìa, thì ElastiCache là dịch vụ In-Memory Cache (RAM) được quản lý nằm sâu bên trong VPC của bạn. Nhiệm vụ của nó là gánh các truy vấn nặng, lặp đi lặp lại từ cơ sở dữ liệu (RDS/Aurora), giảm độ trễ (latency) từ hàng mili-giây (của ổ cứng) xuống micro-giây (của RAM).

3.1. So sánh Chuyên sâu: Redis và Memcached (Kiến thức lõi)

Bạn phải phân biệt rạch ròi 2 engine này trong đề thi.

Tiêu chí Amazon ElastiCache for Redis Amazon ElastiCache for Memcached
Cấu trúc dữ liệu Phức tạp: Strings, Lists, Sets, Sorted Sets, Hashes, Bitmaps. Đơn giản cơ bản: Cấu trúc Object, Strings thuẩn tuý.
Kiến trúc luồng Đơn luồng (Single-threaded). Đa luồng (Multi-threaded), tận dụng sức mạnh nhiều core CPU của máy chủ.
Tính khả dụng (HA) Hỗ trợ Multi-AZ, tự động failover sang standby node nếu primary sập. KHÔNG có Multi-AZ. Nút (node) nào chết là mất dữ liệu ở nút đó, app phải tự load lại từ DB.
Khả năng mở rộng (Scale) Có Read Replicas (chia sẻ đọc), hỗ trợ Cluster mode phân mảnh (Sharding). Mở rộng ngang bằng cách thêm nodes độc lập (Auto Discovery).
Sao lưu (Persistence) Có thể Backup/Restore tự động (Cơ chế AOF/Snapshots RDB). Cache thuần túy bay hơi trên RAM. KHÔNG hỗ trợ backup.
Mẹo thi ElastiCache

99% các câu hỏi về ElastiCache yêu cầu "High Availability" (Multi-AZ), "Data Persistence" (sao lưu), hoặc "Gaming Leaderboards" (bảng xếp hạng game bằng Sorted Sets) đều dẫn tới đáp án Redis. Memcached chỉ đúng khi đề thi đặc biệt nhấn mạnh "Simple caching object model", "multi-threaded without need for HA".

3.2. Chiến lược Caching (Caching Strategies)

Làm sao để code của ứng dụng đồng bộ dữ liệu vào Cache?

  1. Lazy Loading (Read-Aside) - Tải chậm:

    • Cách hoạt động: Ứng dụng hỏi Cache. Hit → trả về. Miss → đọc Database (chậm) → Lấy kết quả đó Ghi vào Cache → trả về client.
    • Ưu điểm: Tiết kiệm RAM vô cùng, chỉ cache những gì user thực sự hỏi. Khởi động node mới rất nhanh.
    • Nhược điểm: Xảy ra độ trễ nặng (Penalty lag) ở lần gọi đầu tiên (Cache miss). Có nguy cơ cao dính Stale data (dữ liệu cũ trong cache khác với DB thật). Phải bắt buộc cấu hình TTL để huỷ data cũ.

  2. Write-Through - Ghi xuyên qua:

    • Cách hoạt động: Ứng dụng mỗi khi Ghi/Sửa/Xoá dữ liệu trên Database, nó bắt buộc phải GHI LUÔN dữ liệu mới đó vào Cache.
    • Ưu điểm: Cache luôn tươi mới 100% (No stale data). Các thao tác đọc sau đó cực kì mượt mà.
    • Nhược điểm: Tốn thời gian write (Write Penalty). Cực kỳ tốn RAM vì ứng dụng sẽ cache cả những dữ liệu lưu trữ không bao giờ có ai thèm đọc tới.

3.3. Limits & Troubleshooting ElastiCache (OOM Errors)

  • Limits: ElastiCache Redis Cluster hỗ trợ tối đa 500 nodes (ví dụ 90 shards và 5 replicas mỗi shard). Cung cấp hàng trăm TB in-memory data, xử lý hàng triệu request mỗi giây.
  • OOM (Out Of Memory) Errors: Khi Redis nhét đầy RAM, nó không nổ ngay mà kích hoạt cơ chế Eviction Policies (chính sách dọn rác). Mặc định là volatile-lru (xoá các key ít dùng nhất nhưng ĐÃ cấu hình TTL).
    • Sự cố: Nếu bạn dùng Lazy Loading nhưng quên không set TTL cho các key, RAM sẽ đầy 100%, lúc này chính sách volatile-lru không tìm được key nào hợp lệ để xoá → Redis từ chối mọi lệnh Write mới kèm thông báo lỗi OOM.
    • Khắc phục: Sửa lại code set thêm TTL, hoặc đổi eviction policy sang allkeys-lru (ép xoá bất kì key cũ nào dù không có TTL), hoặc nâng cấp instance class (Scale up RAM).
  • Bảo mật: Redis hỗ trợ In-transit encryption, At-rest encryption (KMS) và tính năng Redis AUTH (Yêu cầu ứng dụng gửi kèm password/token để thực thi truy vấn).

4. CLI & JSON Policy Snippets

Snippet: S3 Bucket Policy cho phép CloudFront OAC đọc data (Cực kỳ quan trọng) Mã JSON này giúp khóa chặt S3, chỉ cho phép đúng Distribution cụ thể truy cập, cấm mọi IP ngoài:

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowCloudFrontServicePrincipal",
            "Effect": "Allow",
            "Principal": {
                "Service": "cloudfront.amazonaws.com"
            },
            "Action": "s3:GetObject",
            "Resource": "arn:aws:s3:::my-static-secure-bucket/*",
            "Condition": {
                "StringEquals": {
                    "AWS:SourceArn": "arn:aws:cloudfront::123456789012:distribution/EDFDVBD632BHDS5"
                }
            }
        }
    ]
}

Snippet: Xóa cache thủ công (Invalidation) bằng AWS CLI

# Xóa hình ảnh logo.png và mọi file trong thư mục css
aws cloudfront create-invalidation \
    --distribution-id EDFDVBD632BHDS5 \
    --paths "/images/logo.png" "/css/*"

5. Case Studies Thực Tế (Kiến trúc Caching Tối Cao)

Case Study 1: Nền tảng Video Streaming Bảo Mật Cao Toàn Cầu

Bài toán: Một Startup bán khoá học trực tuyến bằng Video (như Udemy). Yêu cầu: Video phải load nhanh không giật lag ở hơn 50 quốc gia, và TỐI QUAN TRỌNG: Người dùng mua khoá học xong không được copy link video (URL) gửi cho bạn bè xem chùa.

Giải pháp Kiến trúc High-Performing:

  1. Video (.mp4 / .ts) gốc lưu trong Amazon S3. Đóng public access 100%.
  2. Dùng CloudFront làm CDN toàn cầu phân phối luồng video. Cấu hình OAC bảo mật S3.
  3. Sử dụng công nghệ CloudFront Signed Cookies hoặc Signed URLs.
  4. Khi user đăng nhập thành công vào EC2 Auth Server, ứng dụng kiểm tra hóa đơn (Database). Nếu hợp lệ, Auth Server gọi IAM sinh ra một Signed Cookie (có mã xác thực và thời hạn TTL 24 tiếng) gửi về trình duyệt của user.
  5. Trình duyệt tự động đính kèm Cookie này khi gọi tải video từ CloudFront. CloudFront edge xác thực chữ ký (Signature) thành công mới cho xem. Gửi link ra ngoài sẽ bị từ chối 403 Access Denied.

Case Study 2: Hệ Thống Giao Dịch Sàn Thương Mại Điện Tử Dịp Black Friday

Bài toán: Sàn TMĐT chuẩn bị đối mặt với lượng traffic x100 lần bình thường. Các câu truy vấn SELECT product_details FROM catalog WHERE id='x' làm cạn kiệt CPU của cụm MySQL RDS.

Giải pháp Kiến trúc High-Performing:

  1. Triển khai một cụm ElastiCache for Redis Cluster (Multi-AZ) đứng ngay phía trước cơ sở dữ liệu Amazon RDS.
  2. Sửa code ứng dụng áp dụng chiến lược Lazy Loading kết hợp TTL 5 phút. Hàng triệu request truy vấn thông tin sản phẩm "iPhone 15" sẽ đập vào Redis và trả về trong 1 micro-giây. Cơ sở dữ liệu RDS chỉ phải nhận 1 request duy nhất (Cache miss ban đầu), tải CPU của DB tụt từ 99% xuống 5%.
  3. Để chặn DDOS và traffic ảo (bot), triển khai AWS WAF đính kèm lên CloudFront ở vòng ngoài cùng.

6. Checklist Kế hoạch Ôn tập Caching

  • Hiểu luồng hoạt động CloudFront: Edge Location → Regional Edge Cache → Origin.
  • So sánh thuần thục CloudFront Functions (JS, <1ms, Edge) và Lambda@Edge (Node/Python, <5s, REC).
  • Phân biệt CloudFront (Layer 7 HTTP, Caching, thay đổi IP) vs Global Accelerator (Layer 4 TCP/UDP, 2 Anycast tĩnh IP, Không Caching).
  • Thuộc lòng cấu hình OAC chặn public S3, chỉ cho CloudFront truy cập.
  • Biết khi nào dùng CloudFront Signed URLs (truy cập 1 file duy nhất, vd: PDF report) vs Signed Cookies (truy cập hàng ngàn file, vd: HLS Video streaming segments).
  • So sánh tuyệt đối Redis (Multi-AZ, sao lưu, Sorted Sets) và Memcached (Đa luồng, Object đơn giản, bay hơi).
  • Nắm rõ ưu/nhược điểm 2 chiến lược Cache: Lazy Loading vs Write-Through.
  • Hiểu lỗi OOM trên Redis và biết cơ chế Eviction Policy xử lý ra sao khi đầy RAM.
