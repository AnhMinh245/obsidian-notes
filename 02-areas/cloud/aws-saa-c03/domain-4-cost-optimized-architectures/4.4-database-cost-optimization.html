Database Cost Optimization

Task 4.3: Design Cost-Optimized Database Solutions

📊 Tiến độ học tập: Database Cost Optimization

Status: Đã hoàn thành chuyên sâu Tầm quan trọng: Cao (Cơ sở dữ liệu thường là phần mềm đắt đỏ nhất và khó co giãn nhất trong hệ thống).

Tương tự Compute, Database (Cơ sở dữ liệu) là một thành phần có thể tiêu tốn cực lớn. Việc tối ưu Database không chỉ ở tầng hạ tầng (infrastructure sizing) mà còn ở kiến trúc phần mềm, chiến lược lưu trữ bộ nhớ đệm (caching), và đặc tính chi trả bản quyền.

1. Lý Thuyết Chuyên Sâu: Amazon RDS & Tối Ưu Chi Phí

Amazon Relational Database Service (RDS) tính phí dựa trên 5 yếu tố chính:

  1. Instance hours (Thời gian chạy): Loại máy ảo đằng sau database (Ví dụ: db.m5.large).
  2. Storage (Dung lượng lưu trữ): Phí cấp phát SSD (gp2/gp3) hoặc Provisioned IOPS (io1/io2). Giới hạn của Provisioned IOPS là RẤT ĐẮT.
  3. I/O requests: Áp dụng cho một số loại storage cũ.
  4. Automated Backup & Snapshots: RDS tặng không gian backup bằng 100% dung lượng database của bạn. Phần dung lượng vượt qua sẽ tính phí S3-like rate.
  5. Data transfer out: Băng thông truyền ra Internet.

Các chiến lược "Gọt giũa" hóa đơn RDS:

  • Stop/Start Environments: Môi trường Dev/Test không cần chạy 24/7. Nếu bạn dùng tính năng Stop DB Instance, bạn sẽ tiết kiệm được phí Compute (chỉ còn đóng phí Storage). Tuy nhiên, RDS chỉ cho phép Stop tối đa 7 ngày, sau đó nó tự Start lại để cài đặt OS patches.
  • Reserved DB Instances: Giống hệt EC2 RI, mua cam kết 1 hoặc 3 năm giảm tới 69% chi phí cho Production workloads chạy 24/7. (Không có Savings Plans cho RDS).
  • Hạ chuẩn bản quyền (Licensing): Oracle và Microsoft SQL Server Enterprise Edition tốn phí License Include cực lớn. Nên dùng BYOL (Bring Your Own License) nếu đã có sẵn, hoặc dời sang PostgreSQL/MySQL/MariaDB hoàn toàn miễn phí bản quyền.
  • Tránh dùng Multi-AZ bừa bãi: Multi-AZ nhân đôi toàn bộ chi phí (Compute + Storage) vì nó phải chạy ngầm một database phụ (Standby replica) ở AZ khác để đồng bộ dữ liệu. TUYỆT ĐỐI không bật Multi-AZ cho Dev/Test trừ khi để test High Availability.

2. Amazon Aurora Serverless v2 (Kẻ hủy diệt On-Demand)

Với RDS truyền thống (Provisioned), bạn phải dự báo (guess) mức tải cao nhất. Giả sử bạn dự báo sai và cấp phát db.r5.8xlarge, nhưng 90% thời gian tải rất thấp → Lãng phí kinh hoàng.

  • Aurora Serverless v2 sinh ra để giải bài toán này. Nó tự động theo dõi CPU/RAM và mở rộng/thu hẹp (scale up/down) trong tích tắc (vài phần nghìn giây).
  • Tính phí dựa trên Aurora Capacity Units (ACU) (1 ACU ~ 2GB RAM + vCPU tương ứng).
  • Có thể scale down xuống mức rất nhỏ (0.5 ACU) để tiết kiệm trong giờ rảnh rỗi và bung lên hàng trăm ACU khi có Flash Sale.
Mẹo làm bài thi

Nếu câu hỏi miêu tả workload: "unpredictable", "infrequent workloads", "variable traffic", "spiky usage" (lúc rất cao lúc rảnh rỗi) và hỏi "most cost-effective database" → Đáp án auto là Aurora Serverless.

3. Amazon DynamoDB: Limits & Capacity Modes

DynamoDB là NoSQL Database Serverless hàng đầu của AWS. Cách bạn thiết kế bảng (table design) quyết định hóa đơn cuối tháng.

Under the Hood: Cách tính phí RCU và WCU

  • 1 WCU (Write Capacity Unit): Được ghi 1 Item kích thước tối đa 1KB mỗi giây. (Nếu file 2KB, mất 2 WCU).
  • 1 RCU (Read Capacity Unit): Được đọc 1 Item tối đa 4KB mỗi giây với mức đọc nhất quán cao (Strongly Consistent Read).
  • Mẹo tối ưu (Exam trap): Nếu bạn chọn Eventual Consistent Read (chấp nhận dữ liệu có thể bị trễ 1-2 giây), bạn chỉ tốn 0.5 RCU. Nghĩa là bạn tiết kiệm được 50% tiền Read.
Chế độ (Capacity Mode) Cách thức thanh toán Use Case Lý Tưởng
Provisioned Capacity Mua trước số lượng RCU/WCU kết hợp Auto Scaling. (Rẻ nhất). Ứng dụng production đã có traffic dự đoán được, tải đều.
On-Demand Capacity Tính theo số lượng Request thực tế. KHÔNG tốn phí cố định hourly. (Đắt hơn trên từng request). Ứng dụng mới (Start-up chưa rõ traffic), tải nhảy vọt không lường trước.

4. Chiến Lược Caching Để Giảm Chi Phí Database

Cách tốt nhất để tiết kiệm tiền Read vào Database là ... Đừng đọc Database.

Ưu điểm chi phí của Caching:

  • RDS đắt đỏ khi phải liên tục query các bảng tính toán nặng (joins). Thay vì "Scale-Up" RDS lên những cỗ máy khổng lồ (Vertical Scaling) giá hàng ngàn đô, ta mua một cụm RDS nhỏ, và thêm Amazon ElastiCache (Redis/Memcached) hoặc DynamoDB DAX ở đằng trước.
  • Cache cluster nhỏ thường rẻ hơn rất nhiều, phản hồi với độ trễ micro-second, gánh 90% lượng Read → giảm hóa đơn tổng thể.

5. Amazon Redshift (Data Warehouse) Tối Ưu Chi Phí

  • Redshift Pause/Resume: Redshift cluster siêu tốn tiền (chuyên dùng phân tích Big Data). Nếu Data Team của bạn chỉ chạy Report vào giờ hành chính, hãy dùng API để Pause cluster vào ban đêm và cuối tuần. Khi Pause, bạn chỉ đóng phí Storage, phí Compute bằng 0.
  • Redshift Spectrum: Tính năng cho phép Redshift quét (query) trực tiếp dữ liệu đang nằm trên Amazon S3 (định dạng Parquet, ORC, CSV) mà không cần phải load toàn bộ dữ liệu đó vào local storage của Redshift. S3 rẻ hơn hàng chục lần so với ổ đĩa đính kèm của Redshift. Bạn chỉ bị tính phí trên số Byte được quét qua (Query cost).

6. Limits, Quotas & Constraints Quan Trọng

  • DynamoDB Item Limit: Tối đa 400 KB cho mỗi Item. Nếu bạn cố lưu một file ảnh hoặc JSON quá to (VD 300KB), một lệnh Write sẽ cắn 300 WCU của bạn! Hãy lưu file vào S3, và chỉ lưu S3 URL vào DynamoDB (chỉ tốn <1KB = 1 WCU).
  • ElastiCache Redis vs Memcached: Redis hỗ trợ Multi-AZ, backup, persistence. Memcached chỉ là cache thuần túy in-memory, rẻ hơn nhưng dữ liệu bốc hơi khi máy khởi động lại. Cân nhắc kỹ Use-case trước khi chọn (Nếu cần rẻ tuyệt đối và đơn giản: Memcached).
  • Amazon Aurora Storage Limit: Tự động auto-scale dung lượng từ 10GB lên tới 128 TB. Không cần phải provision ổ đĩa thủ công nữa.

7. Case Study: Hệ Thống Lưu Trữ Audit Log Rẻ Hóa Nhờ TTL

Bối cảnh: Một hệ thống E-commerce phải lưu lại toàn bộ lượt click của người dùng trong ngày (Audit logs). Logs sinh ra hàng triệu dòng. Yêu cầu: Cần truy xuất cực nhanh (milliseconds) các log trong 30 ngày qua bằng DynamoDB. Sau 30 ngày, log phải được giữ lại 7 năm cho mục đích Compliance, nhưng hiếm khi xem lại. Việc để 7 năm log trên DynamoDB sẽ tốn cả gia tài.

Giải pháp (Cost-Optimized Architecture):

  1. Ghi log vào DynamoDB.
  2. Thiết lập tính năng Time-To-Live (TTL) của DynamoDB. TTL tự động xóa các Item lớn hơn 30 ngày. Quá trình xóa này HOÀN TOÀN MIỄN PHÍ (không cắn WCU của hệ thống).
  3. Kích hoạt DynamoDB Streams. Bắt lấy sự kiện Item bị xóa bởi TTL.
  4. Kích hoạt một AWS Lambda đọc Stream và đẩy dòng log đã bị xóa sang Amazon Kinesis Data Firehose.
  5. Kinesis Firehose gom các dòng log lại thành file to và lưu thẳng vào Amazon S3 Glacier Deep Archive (Lưu trữ rác lạnh giá cực rẻ - ~$0.00099/GB).

8. Di Cư Database Rẻ Hơn (DMS & SCT)

Bạn muốn thoát khỏi hợp đồng bảo trì triệu đô của cơ sở dữ liệu thương mại (Commercial DB).

  • AWS Schema Conversion Tool (SCT): Chạy công cụ này để nó tự động dịch (convert) toàn bộ cấu trúc bảng (Schema), Stored Procedures, Triggers từ Oracle/SQL Server sang mã nguồn mở (MySQL/PostgreSQL) hoặc Aurora.
  • AWS Database Migration Service (DMS): Đóng vai trò con thoi, di chuyển liên tục dữ liệu từ DB cũ sang DB mới mà gần như không có downtime (zero downtime migration) thông qua kỹ thuật Change Data Capture (CDC).

9. Troubleshooting & Các Lỗi Ngốn Tiền Phổ Biến

Vấn đề (Issue) Nguyên nhân (Root Cause) Khắc phục (Resolution)
Phí Backup RDS tăng sốc Tự tạo quá nhiều Manual Snapshots nhưng không bao giờ xóa. AWS chỉ free phần Automated Backup bằng với dung lượng DB hiện tại. Quản lý vòng đời Snapshot. Dùng AWS Backup để tự động xóa snapshot cũ.
Hóa đơn DynamoDB RCU cao chót vót Ứng dụng code dở, thực hiện hàm Scan (quét toàn bộ bảng) thay vì hàm Query (tìm theo khóa Partition Key). Hàm Scan tính RCU trên mọi Item bị quét qua dù kết quả trả về chỉ là 1. Code lại ứng dụng, TUYỆT ĐỐI không dùng Scan trên bảng Production. Bổ sung Global Secondary Index (GSI) để phục vụ Query.
Dự án chết yểu nhưng RDS vẫn tính tiền Dev tắt DB instance để tiết kiệm tiền nhưng quên mất. RDS tự động Start lại sau 7 ngày và nằm im tính phí theo giờ nhiều tháng liền. Nếu dự án đã kết thúc, tạo 1 Final Snapshot rồi Delete (Xóa hoàn toàn) DB instance.

10. CLI & JSON Policy Snippets

Lệnh CLI Tạm Dừng RDS (Stop DB Instance) để gỡ gạc tiền bạc:

# Tạm dừng DB Instance trong môi trường Dev
aws rds stop-db-instance \
    --db-instance-identifier my-dev-database
    
# Cảnh báo: Lệnh này hiệu lực tối đa 7 ngày!

Terraform (HCL) Cấu hình DynamoDB On-Demand + TTL:

resource "aws_dynamodb_table" "cost_optimized_table" {
  name         = "AuditLogs"
  billing_mode = "PAY_PER_REQUEST" # Chế độ On-Demand linh hoạt (Không cần set RCU/WCU)
  hash_key     = "LogId"

  attribute {
    name = "LogId"
    type = "S"
  }
  
  # TTL (Time To Live) giúp tự xóa dữ liệu cũ miễn phí 100%
  ttl {
    attribute_name = "ExpirationTime"
    enabled        = true
  }
}

11. Cảnh Báo & Mẹo Thi (Exam Tips)

Mẹo từ khóa cho bài thi SAA-C03
  • "Unpredictable workload, intermittent spikes, cost-effective database" → Aurora Serverless.
  • "Save costs on Read queries for relational DB" → Thêm Read Replica hoặc thêm ElastiCache.
  • "Reduce costs of scanning DynamoDB" → Đổi sang Eventual Consistency hoặc thêm DAX (DynamoDB Accelerator).
  • "Offload expensive Oracle licenses" → Dùng AWS SCT + DMS để migrate sang Aurora PostgreSQL.
  • "Keep DynamoDB table small and cost-effective for historical data" → Dùng TTL.
Exam Trap: Redshift Spectrum vs EMR

Nếu đề bài hỏi query data trực tiếp trên S3 rẻ nhất bằng SQL truyền thống, chọn Amazon Athena hoặc Redshift Spectrum. Đừng chọn Amazon EMR vì EMR đòi hỏi provision nguyên một cụm Hadoop EC2 tính phí hourly cực kỳ đắt, không phù hợp cho truy vấn Ad-hoc đơn giản.

12. Checklist Ôn Tập Cuối Cùng

  • DynamoDB: Biết tính số RCU khi xài Eventual Consistent (0.5) so với Strongly Consistent (1.0).
  • DynamoDB: Tại sao không được lưu file 5MB vào bảng? Giải pháp là gì (Lưu S3, giữ link).
  • RDS: Tại sao không bật Multi-AZ cho Dev? Stop RDS được tối đa mấy ngày? (7).
  • Phân biệt rõ Aurora Provisioned (Giá cố định theo instance) và Aurora Serverless (Giá linh động theo ACU).
  • Cách dùng TTL kết hợp Kinesis Firehose + Glacier để làm bài toán Archive tự động.
