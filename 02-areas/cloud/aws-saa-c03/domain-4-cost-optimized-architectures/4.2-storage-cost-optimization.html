Storage Cost Optimization

Task 4.1: Design Cost-Optimized Storage Solutions

Tối ưu hóa chi phí lưu trữ (Storage Cost Optimization) là một phần cực kỳ quan trọng trong đề thi AWS SAA-C03. Dữ liệu ngày càng lớn và nếu không chọn đúng Storage Tier, không dọn dẹp tài nguyên thừa, hoặc cấu hình vòng đời (Lifecycle) sai, hóa đơn AWS của bạn có thể tăng theo cấp số nhân.

1. Amazon S3 Storage Classes & Tối Ưu Chi Phí

S3 cung cấp nhiều Storage Classes khác nhau, phù hợp cho từng mục đích sử dụng. Giá lưu trữ tỷ lệ thuận với tính khả dụng (Availability) và tốc độ truy xuất (Retrieval time).

Mermaid: Biểu đồ Dòng Chảy S3 Storage Classes

Chi tiết các Storage Classes (Under the Hood):

  1. S3 Standard: Đắt nhất, dùng cho dữ liệu truy cập thường xuyên. Không có phí truy xuất, không có thời gian lưu trữ tối thiểu.
  2. S3 Standard-IA (Infrequently Accessed): Phù hợp cho dữ liệu ít truy cập nhưng cần tốc độ lấy (retrieval) mili-giây.
    • Cảnh báo (Cost penalty): Có phí truy xuất (Retrieval fee) tính theo GB.
    • Constraint: Kích thước object tối thiểu là 128KB (nếu lưu object 1KB sẽ bị tính tiền bằng 128KB). Thời gian lưu trữ tối thiểu 30 ngày.
  3. S3 One Zone-IA: Rẻ hơn S3 Standard-IA khoảng 20%, nhưng dữ liệu chỉ nằm trong MỘT AZ. Rất dễ mất dữ liệu nếu AZ gặp thảm họa.
    • Use case: Chỉ dùng để lưu trữ dữ liệu có thể dễ dàng tái tạo (recreatable data), ví dụ: thumbnails, bản copy phụ.
  4. S3 Glacier Flexible Retrieval: Chuyên cho dữ liệu Archive (lưu trữ lâu dài). Truy xuất mất từ vài phút đến 12 tiếng (Expedited, Standard, Bulk). Lưu tối thiểu 90 ngày.
  5. S3 Glacier Deep Archive: RẺ NHẤT trong tất cả. Thời gian lấy dữ liệu lên tới 12 - 48 tiếng. Lưu tối thiểu 180 ngày. Dùng cho dữ liệu pháp lý (Regulatory/Compliance).
  6. S3 Intelligent-Tiering: Cứu tinh khi bạn KHÔNG BIẾT pattern truy cập dữ liệu.
    • Cơ chế: Tự động di chuyển dữ liệu giữa Frequent, Infrequent, Archive Instant, và (optional) Async Archive tiers dựa trên tần suất truy cập.
    • Cost benefits: Không có retrieval fee (phí lấy dữ liệu), không có minimum storage duration.
    • Overhead: Phải trả một khoản phí theo dõi và tự động hóa (monitoring and automation fee) nhỏ hàng tháng trên mỗi 1000 objects. Chú ý: Objects nhỏ hơn 128KB luôn bị tính phí ở mức Frequent Access và không phát sinh phí monitoring.
Exam Tip - Chọn Storage Class
  • "Lowest cost" + "immediate access/milliseconds" -> S3 Standard-IA.
  • "Lowest cost" + "recreatable data" -> S3 One Zone-IA.
  • "Lowest cost" + "archive" + "retrieve in hours" -> S3 Glacier Flexible Retrieval (chọn Bulk retrieval để rẻ nhất).
  • "Lowest cost" + "regulatory archive" + "retrieve in days" -> S3 Glacier Deep Archive.
  • "Unpredictable/changing access pattern" -> S3 Intelligent-Tiering.

2. Các Công Cụ Tiết Kiệm Chi Phí Của S3

S3 Lifecycle Policies

Cơ chế tự động hóa chuyển đổi tier hoặc xóa data.

  • Transition actions: Chuyển Object sang storage class lạnh hơn.
  • Expiration actions: Tự động xóa (Delete) các object hoặc các version cũ của object khi hết hạn (ví dụ xóa non-current versions sau 90 ngày để tránh trả phí lưu giữ version rác).
Lỗi thiết kế phổ biến: Transition Objects siêu nhỏ

Nếu bạn áp dụng Transition Rule chuyển từ S3 Standard sang S3 Standard-IA cho hàng triệu objects có kích thước ~5KB, bạn sẽ TĂNG hóa đơn của mình thay vì giảm. Nguyên nhân do mức phạt minimum object size 128KB (AWS sẽ charge bạn như thể mỗi file là 128KB) kèm theo phí transition API (chuyển đổi per-object).

S3 Storage Class Analysis (S3 Analytics)

Theo dõi lịch sử truy cập để khuyến nghị thời điểm thích hợp chuyển đổi dữ liệu sang S3 Standard-IA. Lưu ý nó CHỈ đưa ra khuyến nghị cho nhóm Standard -> Standard-IA, KHÔNG khuyến nghị cho việc chuyển sang Glacier.

S3 Requester Pays

Khi tính năng này bật, người tải dữ liệu (Requester) sẽ phải trả các chi phí Network Data Transfer Out và API Requests thay vì chủ của Bucket trả.

  • Use case: Chia sẻ dataset khổng lồ (Genomics, ML datasets) với public hoặc đối tác mà chủ bucket không muốn còng lưng gánh phí tải xuống. Lưu ý: Requester phải được authenticate bằng IAM credential của họ.

3. Tối ưu hóa Amazon EBS (Elastic Block Store)

EBS Volumes gắn trực tiếp vào EC2 instances (như ổ đĩa cứng). Việc chọn sai Volume type gây lãng phí rất lớn.

Volume Type Tên gọi Chi phí Đặc điểm Cost Optimization
gp3 General Purpose SSD Thấp Rẻ hơn 20% so với gp2. Cho phép cấu hình IOPS và Throughput độc lập với dung lượng (Baseline 3,000 IOPS / 125 MiBps). Dùng làm Boot/Data volume mặc định.
gp2 General Purpose SSD Trung bình IOPS tăng tuyến tính theo dung lượng (3 IOPS/GB). Để tăng IOPS phải cấp phát (provision) thêm dung lượng => Lãng phí storage cost để đổi lấy IOPS.
io2 / io1 Provisioned IOPS SSD Rất Cao Đắt nhất. Chỉ dùng khi Mission critical DB cần > 16,000 IOPS, tỷ lệ IOPS/GiB cực cao, hoặc cần độ bền 99.999% (io2).
st1 Throughput Optimized HDD Rẻ Không boot được OS. Phù hợp cho workload có throughput cao, sequential I/O (Big Data, Log processing, Data Warehouse).
sc1 Cold HDD RẤT RẺ Rẻ nhất trong các loại EBS. Dùng cho dữ liệu ít truy cập nhưng bắt buộc cần giao thức Block-level, hoặc Archive.

Under the Hood: EBS Burst Balance (gp2)

Trong gp2, nếu dung lượng volume nhỏ, baseline IOPS sẽ thấp (ví dụ: volume 10GB có baseline 30 IOPS). AWS cấp cho bạn các I/O Credits vào "Burst Bucket". Khi bạn cần read/write nhanh, EBS sẽ tiêu thụ Burst Balance để đạt tới 3000 IOPS. Nếu Burst Balance cạn kiệt, hiệu năng rớt thảm hại về baseline. -> Cách giải quyết tối ưu chi phí: Không nên tăng size volume gp2 chỉ để lấy IOPS (vì tốn tiền lưu trữ). Hãy convert sang gp3 để có sẵn 3000 IOPS baseline mà không cần tăng GB.

Chiến lược nâng cấp (Exam Alert)

Đề thi thường mô tả một hệ thống EC2 bị thắt cổ chai I/O dùng gp2, yêu cầu tăng IOPS nhưng phải giữ chi phí thấp nhất -> Lựa chọn đúng: Migrate từ gp2 sang gp3. Đây là live-migration (không downtime).

Quản lý Vòng đời EBS Snapshots (Data Lifecycle Manager - DLM)

EBS Snapshots lưu trữ dạng Incremental (tăng dần) trên S3. Mặc dù là incremental, chi phí tích tụ rất lớn.

  • Dùng Amazon Data Lifecycle Manager (DLM) để tự động hóa tạo, giữ lại (retain), và xóa snapshot định kỳ, tránh tình trạng snapshot cũ mốc meo ngốn tiền.

4. Tối ưu hóa EFS, FSx và Hybrid Storage

  • Amazon EFS (Elastic File System): Đắt hơn EBS. Có Storage Classes: Standard và EFS Infrequently Accessed (EFS IA) hoặc Archive. EFS IA rẻ hơn đến 92%. Dùng EFS Lifecycle Management để tự động chuyển files không bị truy cập trong X ngày sang EFS IA.
  • Amazon FSx for Windows File Server: Hỗ trợ tính năng Data Deduplication (khử trùng lặp dữ liệu) giúp tiết kiệm đến 50-60% dung lượng thực tế.
  • AWS Storage Gateway:
    • S3 File Gateway: Máy chủ On-prem lưu thẳng file vào S3 qua giao thức SMB/NFS. Local cache giúp tiết kiệm băng thông mạng và giảm độ trễ, trong khi chi phí lưu trữ chính (S3) rất rẻ.
  • AWS DataSync: Chuyên dùng đồng bộ dữ liệu khối lượng khổng lồ. Tối ưu hơn rsync vì nén và quản lý băng thông tốt.

5. Limits, Quotas & Constraints

  • S3 Limits:
    • Max Object Size: 5TB. Single PUT tối đa 5GB. Phải dùng Multipart Upload cho file > 5MB (giúp tăng tốc và cho phép resume, tránh phí network transfer lỗi).
    • Tối đa 100 S3 Buckets mỗi tài khoản (có thể xin tăng).
  • EBS Limits:
    • Kích thước gp2/gp3/io1/io2: Lên đến 16 TiB.
    • io2 Block Express: Lên đến 64 TiB.
  • EFS: Không có giới hạn cứng về dung lượng (elastic theo thực tế).

6. Troubleshooting & Common Errors (Tốn Tiền Oan)

  1. Mồ côi EBS Volumes (Orphaned Volumes)
    • Vấn đề: Khi Terminate EC2, Root Volume mặc định tự xóa (DeleteOnTermination = true). Nhưng các volume phụ (Data volumes) được gắn thêm sẽ bị tách ra (Unattached) ở trạng thái Available và AWS vẫn tiếp tục tính tiền hàng tháng.
    • Khắc phục: Dùng AWS Config, AWS Trusted Advisor, hoặc CloudWatch Events + Lambda để phát hiện/cảnh báo/tự động xóa các volume trạng thái Available đã tồn tại quá lâu mà chưa có snapshot.
  2. Quên dọn dẹp Incomplete Multipart Uploads (S3)
    • Vấn đề: Khi tải lên file 50GB bằng multipart upload nhưng bị đứt mạng giữa chừng, các phần (parts) đã lên S3 bị ẩn đi và bạn vẫn bị tính tiền lưu trữ.
    • Khắc phục: Tạo S3 Lifecycle Rule bắt buộc: Delete expired object delete markers or incomplete multipart uploads (ví dụ sau 7 ngày).
  3. Chi phí API Call KMS trong S3 (SSE-KMS)
    • Vấn đề: Khi nhiều ứng dụng đọc/ghi hàng triệu files vào S3 mã hóa bằng SSE-KMS, chi phí KMS API calls (GenerateDataKey, Decrypt) sẽ bùng nổ.
    • Khắc phục: Kích hoạt S3 Bucket Keys. S3 sẽ tạo một Data Key ở mức độ Bucket và cache lại, giảm lượng gọi API tới KMS tới 99% -> Tiết kiệm mạnh chi phí KMS.

7. CLI & JSON Policy Snippets

Chuyển đổi nóng EBS Volume từ gp2 sang gp3 qua CLI: Giúp tiết kiệm 20% chi phí tức thì. Quá trình này không gây downtime.

aws ec2 modify-volume \
    --volume-id vol-0abcd1234efgh5678 \
    --volume-type gp3

S3 Lifecycle Rule JSON (Dọn rác multipart upload): Nên áp dụng cho mọi bucket để tránh mất tiền oan.

{
    "Rules": [
        {
            "ID": "CleanupIncompleteMultipartUploads",
            "Status": "Enabled",
            "Filter": {},
            "AbortIncompleteMultipartUpload": {
                "DaysAfterInitiation": 7
            }
        }
    ]
}

8. Case Study: Kiến trúc Tối Ưu Lưu Trữ Log Tập Trung

Bối cảnh: Công ty phát sinh hàng TB application logs mỗi ngày trên nhóm EC2 instances. Logs cần được giữ lại 30 ngày để phân tích nóng, và 7 năm để tuân thủ luật kiểm toán.

Giải pháp tối ưu chi phí:

  1. EC2 cài CloudWatch Agent hoặc Kinesis Data Firehose Agent.
  2. Firehose nhóm các dòng log lại (batching/compression) -> Tối ưu lượng API PUT lên S3, giảm thiểu số lượng small files.
  3. Firehose đẩy log vào S3 Standard.
  4. Thiết lập S3 Lifecycle Policy:
    • Chuyển logs sang S3 Glacier Deep Archive sau 30 ngày (vì hiếm khi kiểm toán, nhưng bắt buộc lưu 7 năm).
    • Xóa (Expire) toàn bộ sau 2555 ngày (7 năm).

Checklist: Cost-Optimized Storage

  • Bạn đã hiểu điều kiện tối thiểu 128KB và 30-ngày của S3 Standard-IA chưa?
  • Tính năng S3 Bucket Keys giúp giảm chi phí gì? (SSE-KMS API)
  • Khi nào nên dùng S3 Intelligent-Tiering thay vì Lifecycle cứng ngắc?
  • Phân biệt được mô hình giá của gp2 (IOPS phụ thuộc GB) và gp3 (IOPS độc lập)?
  • Cách xử lý các Orphaned EBS Volumes và Incomplete Multipart Uploads.
  • Lợi ích của Data Deduplication trong FSx for Windows.
