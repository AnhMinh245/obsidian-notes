Domain 2 - Design Resilient Architectures

📊 Progress: Đang học Domain 2 - Design Resilient Architectures. Mục tiêu: Nắm vững toàn bộ kiến trúc chịu lỗi, High Availability, và Scalability.

Domain 2: Design Resilient Architectures (26%)

Domain 2 chiếm 26% trọng số trong kỳ thi AWS SAA-C03. Đây là một trong những domain cốt lõi và quan trọng nhất, tập trung vào khả năng thiết kế hệ thống có tính sẵn sàng cao (High Availability), chịu lỗi tốt (Fault-Tolerant), khả năng co giãn linh hoạt (Scalability) và giải trừ liên kết (Decoupling).

Important

Resilient Architecture (Kiến trúc phục hồi) là khả năng của một hệ thống có thể tự động phục hồi sau khi gặp sự cố, dù đó là lỗi phần cứng cấp độ EC2 instance, phần mềm, hay thảm họa diện rộng ở cấp độ Availability Zone (AZ) hoặc Region. Mục tiêu tối thượng là duy trì Business Continuity (hoạt động kinh doanh liên tục) với RPO và RTO thấp nhất có thể, đáp ứng ngân sách cho phép.

1. Phân Tích Chuyên Sâu: Các Task Statements Chính Thức

Kỳ thi chia Domain này thành 2 Task chính. Việc hiểu rõ từng yêu cầu là bắt buộc.

Task 2.1: Design scalable and loosely coupled architectures

Thiết kế các kiến trúc co giãn và liên kết lỏng lẻo. Ở task này, kiến trúc Monolithic (nguyên khối) bị coi là Anti-pattern. Mọi thành phần phải được bẻ nhỏ và giao tiếp qua các kênh trung gian.

  • API creation/management: Sử dụng Amazon API Gateway làm cửa ngõ duy nhất. API Gateway phải xử lý CORS, throttling, caching, và xác thực qua Cognito trước khi traffic chạm tới backend.
  • Managed services thay vì tự host: Tận dụng AWS Transfer Family (SFTP/FTP), Amazon SQS, AWS Secrets Manager để giảm tải việc vận hành (Operational Overhead).
  • Caching strategies: Sử dụng Amazon ElastiCache (Redis/Memcached) cho session data và database queries; Amazon CloudFront cho static/dynamic web content, giảm độ trễ (latency) và offload traffic cho origin.
  • Microservices design: Phân biệt rõ stateless (không lưu trạng thái ở local EC2) và stateful. Stateless cho phép Auto Scaling hoạt động trơn tru vì request nào cũng có thể được xử lý bởi bất kỳ instance nào.
  • Event-driven architectures: Sử dụng Amazon EventBridge làm xương sống điều phối sự kiện giữa các module; AWS Lambda để trigger các đoạn code nhỏ đáp ứng lại sự kiện (event-based processing).
  • Scaling mechanisms:
    • Horizontal scaling (scale-out): Thêm số lượng EC2 (Dùng Auto Scaling Group).
    • Vertical scaling (scale-up): Tăng kích thước instance (từ t3.micro lên t3.xlarge). AWS ưu tiên Horizontal scaling cho tính HA.
  • Edge accelerators: Sử dụng AWS Global Accelerator để có IP tĩnh (Anycast IP) và định tuyến traffic qua mạng backbone của AWS thay vì public internet, giảm jitter và packet loss.
  • Load balancing: Phân biệt rõ Application Load Balancer (ALB - Layer 7 cho HTTP/HTTPS, path-based routing) và Network Load Balancer (NLB - Layer 4 cho TCP/UDP, độ trễ siêu thấp, IP tĩnh).
  • Queuing/Messaging: Sử dụng mô hình pub/sub với Amazon SNS (Push) và Amazon SQS (Pull) để tạo bộ đệm (buffer) cho các burst traffic.
  • Serverless Compute: Dùng AWS Fargate (cho Containers) và AWS Lambda (cho Functions) để loại bỏ gánh nặng quản lý hệ điều hành.
  • Container orchestration: Quản lý vòng đời Docker containers với Amazon ECS (đơn giản, native AWS) hoặc Amazon EKS (chuẩn Kubernetes, multi-cloud).
  • Workflow orchestration: Dùng AWS Step Functions cho các quy trình dài hạn (Saga pattern) cần quản lý trạng thái, xử lý lỗi (retries/catch), và rollback.

Task 2.2: Design highly available and/or fault-tolerant architectures

Thiết kế kiến trúc có tính sẵn sàng cao và/hoặc chịu lỗi.

  • Global infrastructure: Thiết kế đa vùng (Multi-AZ) để chống lỗi datacenter; đa khu vực (Multi-Region) để chống lỗi thảm họa; định tuyến DNS bằng Amazon Route 53 (Failover, Latency, Geolocation routing).
  • Managed AI/ML services: Biết cách tích hợp nhanh Amazon Comprehend (NLP), Amazon Polly (Text-to-Speech), Amazon Rekognition (Image/Video analysis) vào kiến trúc mà không cần train model.
  • DR strategies: Nắm vững 4 chiến lược Disaster Recovery: Backup/Restore, Pilot Light, Warm Standby, Active-Active. Thuộc nằm lòng các chỉ số RPO (Recovery Point Objective - Giới hạn mất dữ liệu) và RTO (Recovery Time Objective - Giới hạn thời gian chết).
  • Proxy: Tối ưu hóa số lượng kết nối khổng lồ từ Lambda đến RDS bằng Amazon RDS Proxy (Connection pooling).
  • Storage options: Lựa chọn EBS cho block storage (gắn vào 1 EC2), EFS cho file storage (chia sẻ nhiều EC2 qua NFS), S3 cho object storage (Archive, Data Lake).
  • Workload visibility: Giám sát hệ thống microservices phân tán, tìm nút thắt cổ chai (bottleneck) bằng AWS X-Ray (Distributed Tracing).

3. Lý Thuyết Chuyên Sâu: Các Khái Niệm Cốt Lõi

3.1 Scalability (Khả năng co giãn)

Khả năng hệ thống xử lý lượng tải tăng lên bằng cách bổ sung thêm tài nguyên.

  • Vertical Scaling (Scale-up/down): Nâng cấp sức mạnh phần cứng (RAM, CPU, IOPS). Ví dụ: đổi RDS từ db.m5.large lên db.m5.4xlarge.
    • Nhược điểm: Có giới hạn trần (hardware limit), và thường BẮT BUỘC có downtime (phải reboot để nhận hardware mới). Rất hiếm khi dùng cho web servers, thường chỉ dùng cho Monolithic DB.
  • Horizontal Scaling (Scale-out/in): Thêm hoặc bớt số lượng instance (máy chủ).
    • Ưu điểm: Không có điểm mù, scale vô hạn theo lý thuyết. Zero downtime. Đây là xương sống của kiến trúc Cloud-Native. Yêu cầu ứng dụng phải Stateless.

3.2 Elasticity (Khả năng đàn hồi)

Elasticity không chỉ là scale-out khi tải tăng, mà quan trọng hơn là scale-in (thu hẹp) khi tải giảm để tiết kiệm chi phí. Một hệ thống Scalable chưa chắc đã Elastic (nếu scale up mà không bao giờ scale down). Trong AWS, Elasticity thể hiện qua Auto Scaling Group (ASG), DynamoDB Auto Scaling, Aurora Serverless.

3.3 High Availability (Tính sẵn sàng cao - HA)

HA đảm bảo hệ thống luôn hoạt động (Uptime >= 99.99%) bằng cách loại bỏ Single Point of Failure (SPOF).

  • Trong một Region: Deploy qua tối thiểu 2 Availability Zones (Multi-AZ).
  • Khi một thành phần (như 1 EC2, hoặc cả 1 Data Center) chết, traffic lập tức được định tuyến qua thành phần khác còn sống mà user không cảm nhận được.

3.4 Fault Tolerance (Khả năng chịu lỗi)

Mức độ cao hơn HA. Trong HA, khi có sự cố, hệ thống có thể bị gián đoạn vài giây/vài phút (ví dụ RDS Multi-AZ mất 60s để failover). Trong Fault Tolerance, hệ thống không bị gián đoạn dù chỉ 1 mili-giây, với sự suy giảm hiệu năng (degraded performance) được phép xảy ra.

  • Ví dụ: DynamoDB, S3 là các hệ thống Fault Tolerant bẩm sinh.
Exam Tip
  • Nếu câu hỏi yêu cầu "most cost-effective" cho HA -> Chọn Multi-AZ (rẻ hơn Multi-Region).
  • Nếu câu hỏi yêu cầu bảo vệ khỏi thảm họa diện rộng (Earthquake, Region failure) -> BẮT BUỘC chọn Multi-Region với Route 53.
  • "Scale seamless" cho database -> Chọn Aurora Serverless hoặc DynamoDB.

4. Limits, Quotas & Constraints Cốt Lõi (Cần nhớ cho thi)

Khi thiết kế Resilient Architecture, bạn phải biết hệ thống sẽ bị "vấp" ở giới hạn nào. Dưới đây là các giới hạn AWS SAA thường test:

Dịch Vụ Giới Hạn (Limits/Quotas) Rủi ro & Cách khắc phục
VPC Max 5 VPCs mỗi Region (Soft limit). Max 200 Subnets mỗi VPC. Thiết kế CIDR cẩn thận. Dùng AWS Transit Gateway nếu có hàng trăm VPC.
API Gateway 29 giây hard timeout cho integration (ví dụ kết nối Lambda). Lambda chạy lâu hơn 29s sẽ gây lỗi HTTP 504. Dùng kiến trúc Async (SQS) để khắc phục.
Lambda Tối đa 15 phút execution time. 10 GB max RAM/Ephemeral Storage. Code chạy quá 15 phút phải chuyển sang Fargate hoặc Step Functions.
SQS Standard: 120,000 In-flight messages. Payload 256 KB. Gửi file lớn hơn 256KB phải dùng SQS Extended Client (Lưu data ở S3, gửi link qua SQS).
Auto Scaling Step Scaling bị giới hạn bởi cooldown period. Tránh scale out quá chậm. Khắc phục bằng Predictive Scaling hoặc Target Tracking.

5. Troubleshooting & Common Errors Thực Tế

Trong bài thi và thực tế, các hệ thống HA thường gặp các lỗi kinh điển sau:

  1. Lỗi 502 Bad Gateway hoặc 504 Gateway Timeout qua ALB:

    • Nguyên nhân 1: ALB không kết nối được tới Target (EC2) do Security Group của EC2 không mở port từ Security Group của ALB.
    • Nguyên nhân 2 (504): Target đang bận, quá tải, không kịp phản hồi HTTP response cho ALB trước khi quá thời gian Idle Timeout của ALB (mặc định 60 giây).
    • Cách Fix: Tăng ALB Idle Timeout, check SG, hoặc Scale-out ASG mạnh hơn.

  2. Auto Scaling Group "vấp" không chịu Scale-out:

    • Nguyên nhân: Thiếu IP khả dụng trong Subnet (CIDR quá nhỏ, ví dụ /28 chỉ có 11 IP). Hoặc chạm ngưỡng Service Quota của EC2 instance limits (VD: Max 20 vCPU chuẩn On-demand).
    • Cách Fix: Dùng subnets lớn hơn (/24 hoặc /22). Request AWS tăng Service Quotas.

  3. RDS Multi-AZ Failover gây đứt kết nối ứng dụng quá lâu:

    • Nguyên nhân: Khi RDS Primary sập, AWS cập nhật DNS (CNAME) trỏ sang Standby. Nhưng App server của bạn (hoặc connection pool framework như HikariCP) đang cache DNS quá lâu, tiếp tục gửi request vào IP cũ đã chết.
    • Cách Fix: Cấu hình JVM/App TTL của DNS cache xuống giá trị thấp (vd: 30-60 giây). Sử dụng Amazon RDS Proxy để nó đứng giữa quản lý connection, app không cần quan tâm DNS change.

  4. Split-brain trong Multi-Region Active-Active:

    • Nguyên nhân: Hai region cùng nhận traffic ghi (write) cho cùng một object/row DB. Gây conflict data khi sync qua lại.
    • Cách Fix: Dùng DynamoDB Global Tables và thiết kế application xử lý conflict bằng cơ chế "Last Writer Wins", hoặc định tuyến ghi về 1 region duy nhất.

6. Case Studies Kiến Trúc Nâng Cao

Case Study 1: Global E-Commerce Event-Driven System (Khó)

Yêu cầu: Một trang thương mại điện tử lớn (Tiki/Shopee) có sự kiện Flash Sale. Lượng request mua hàng nhảy từ 1k/s lên 100k/s trong vài giây. Yêu cầu: Không được rớt đơn hàng, không được over-sell (bán lố hàng tồn kho), độ trễ API dưới 100ms.

Kiến trúc giải quyết:

Bóc tách giải pháp (Under the Hood):

  1. API Gateway + SQS: Dùng API Gateway tích hợp thẳng với SQS (không cần Lambda trung gian). Điều này giúp hứng 100k requests/s cực nhanh và đẩy vào Queue. Tránh bị 504 Timeout.
  2. SQS FIFO: Cực kỳ quan trọng để đơn hàng vào trước được xử lý trước. Message Group ID dựa trên ID Sản phẩm giúp các luồng mua cho 1 sản phẩm xử lý tuần tự, nhưng các sản phẩm khác nhau xử lý song song.
  3. DynamoDB Conditional Writes: Khi trừ kho, Lambda gọi UpdateItem kèm điều kiện ConditionExpression="Stock > 0". Điều này đảm bảo không bao giờ bị bán lố (over-sell) khi nhiều Lambda chạy song song.
  4. Fanout Pattern (SNS + SQS): Sau khi thanh toán xong, bắn event ra SNS để hệ thống Email và Analytics tự động nhận tin, decouple hoàn toàn khỏi luồng mua hàng.

Case Study 2: Migrate Legacy App lên AWS với HA (Medium)

Yêu cầu: Một ứng dụng Java cũ (Monolith) chạy trên 1 máy ảo on-premise, file upload lưu thẳng ở /var/www/uploads (local disk). Session lưu trên RAM. Yêu cầu: Mang lên AWS, đảm bảo Multi-AZ HA, không phải viết lại code nhiều.

Kiến trúc giải quyết:

Bóc tách giải pháp (Under the Hood):

  1. Stateless EC2: Offload Session từ RAM EC2 ra ElastiCache Redis. Đổi thư mục upload ảnh từ disk nội bộ ra mạng chia sẻ bằng Amazon EFS (gắn mount target vào cả 2 EC2).
  2. Khi EC2 đã stateless -> đưa vào Auto Scaling Group (ASG) trải dài 2 AZ.
  3. Đặt ALB phía trước để load balancing. Bật Sticky Sessions trên ALB nếu app chưa chuyển session ra Redis kịp.
  4. Chuyển database sang RDS Multi-AZ (Synchronous Standby).

7. CLI & JSON Policy Snippets

Để thiết kế chuẩn, bạn phải quen thuộc với IAM Policy kiểm soát Resilient architectures.

JSON: Bắt buộc SQS Queue phải được mã hóa và chỉ SNS mới được bắn message vào (Fanout Pattern Secure):

{
  "Version": "2012-10-17",
  "Id": "SQSDefaultPolicy",
  "Statement": [
    {
      "Sid": "Allow-SNS-SendMessage",
      "Effect": "Allow",
      "Principal": {
        "Service": "sns.amazonaws.com"
      },
      "Action": "sqs:SendMessage",
      "Resource": "arn:aws:sqs:us-east-1:123456789012:MyFanoutQueue",
      "Condition": {
        "ArnEquals": {
          "aws:SourceArn": "arn:aws:sns:us-east-1:123456789012:MyTopic"
        }
      }
    }
  ]
}

CLI: Cập nhật Auto Scaling Group (Force Scale-Out để test HA):

aws autoscaling update-auto-scaling-group \
    --auto-scaling-group-name my-web-asg \
    --min-size 2 \
    --desired-capacity 4 \
    --max-size 10

8. Bảng Tóm Tắt Các Dịch Vụ Cốt Lõi Domain 2

Dịch vụ Layer/Loại Vai trò Resilient / Use Case kinh điển
ALB (App Load Balancer) Layer 7 (HTTP/S) Phân tải theo URL Path/Host. Support WAF. Hỗ trợ target là Lambda, ECS, EC2.
NLB (Network LB) Layer 4 (TCP/UDP) Hiệu năng siêu cao (hàng triệu req/s). Có IP tĩnh ở mỗi AZ. Dùng cho gRPC, game server.
ASG (Auto Scaling Group) Compute Compute Tự động thêm/bớt EC2 dựa trên CPU/Network. Bắt buộc kết hợp với ALB để user nhận diện.
Amazon SQS Decoupling (Pull) Bộ đệm (buffer) cực kỳ bền bỉ. Tránh quá tải backend (Lambda/EC2). Hỗ trợ FIFO chống trùng.
Amazon SNS Decoupling (Push) Phát thanh sự kiện. Kết hợp với SQS để tạo mô hình Fanout. Push noti ra email/SMS.
EventBridge Event Bus Router thông minh (Rule/Pattern) điều phối luồng dữ liệu microservices và AWS Events.
AWS Lambda Serverless Tính năng compute không cần quản lý. Scale out tức thì (Concurrent executions).
Route 53 Global DNS Dẫn đường traffic, health check, failover routing giữa các Region (cốt lõi của DR).
Cảnh báo cho kỳ thi

Đừng bao giờ chọn giải pháp lưu trạng thái (State) ở Local Disk (như EC2 Instance Store) cho hệ thống cần High Availability. Instance Store mất dữ liệu vĩnh viễn nếu máy tắt. Luôn offload state ra S3, DynamoDB, hoặc EFS.

9. Checklist Ôn Tập Domain 2

Hãy sử dụng checklist này để track tiến độ ôn tập các bài học trong Domain 2. Đảm bảo bạn hiểu rõ các khái niệm Under the hood trước khi chuyển sang Domain tiếp theo.

  • Nắm rõ khái niệm SPOF và khác biệt giữa Scale-up vs Scale-out.
  • Hoàn thành đọc 2.3 - High Availability - Multi-AZ, Multi-Region (Route 53 routing policies, Global Accelerator vs CloudFront).
  • Hoàn thành đọc 2.5 - Decoupling - SQS, SNS, EventBridge (Phân biệt rõ SQS FIFO vs Standard, Visibility Timeout, Fanout).
  • Hoàn thành đọc 2.6 - Serverless và Containers (So sánh Lambda Timeout/Limits, Fargate vs EC2 ECS, API Gateway Timeout).
  • Hoàn thành đọc 2.4 - Disaster Recovery Strategies (RTO, RPO, Pilot Light vs Warm Standby).
  • Thực hành Lab: Thiết lập ALB + ASG rải trên 2 AZ với Target Tracking Policy.
  • Thực hành Lab: Tạo hệ thống Fanout dùng SNS bắn message vào 2 SQS queues.
  • Thực hành Lab: Triển khai serverless app với API Gateway gọi Lambda xử lý lưu DynamoDB.
  • Ôn tập: RDS Multi-AZ Replication (Synchronous) khác gì với Read Replica (Asynchronous).
  • Nắm vững cách AWS xử lý failover DNS trong Route 53 (Alias record vs CNAME).
