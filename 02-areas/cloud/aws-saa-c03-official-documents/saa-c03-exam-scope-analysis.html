SAA-C03 - Exam Scope Analysis

SAA-C03 — Phân tích phạm vi kiến thức kỳ thi

Phân tích chi tiết phạm vi kiến thức (exam scope) của kỳ thi AWS SAA-C03 dựa trên Official Exam Guide v1.1. Tài liệu này trả lời câu hỏi: "Kỳ thi hỏi CÁI GÌ, ở mức ĐỘ SÂU nào?"

Quick links: SAA-C03 - Key Exam Focus Points · SAA-C03 - Out of Scope and Common Traps · AWS SAA-C03 - Exam Overview · AWS SAA-C03 - In-Scope Services Reference

1. Bản đồ tổng quan 4 Domains

Đọc biểu đồ

Mỗi domain có số lượng Task Statements khác nhau. Mỗi task statement tương ứng với 1 nhóm kiến thức + kỹ năng mà AWS kiểm tra. Tổng cộng có 13 task statements — đây chính là 13 "bài thi con" bên trong SAA-C03.

2. Domain 1 — Design Secure Architectures (30%)

Domain nặng nhất. 30% trọng số = khoảng 19-20 câu scored. Tập trung vào IAM, VPC security, encryption.

2.1. Task Statement 1.1: Design secure access to AWS resources

Kiến thức yêu cầu (Knowledge of):

  • Quản lý access controls xuyên nhiều accounts (AWS Organizations)
  • Federated access: IAM, IAM Identity Center (SSO)
  • AWS Global Infrastructure (AZs, Regions) — context security
  • Security best practices: least privilege principle
  • Shared Responsibility Model — phân chia trách nhiệm AWS vs Customer

Kỹ năng kiểm tra (Skills in):

  • Apply best practices cho IAM users và root users (MFA, password policy)
  • Design role-based access control (RBAC): STS, role switching, cross-account
  • Design security strategy multi-account: Control Tower, SCPs
  • Xác định khi nào dùng resource policies vs identity policies
  • Khi nào federate directory service (AD) với IAM roles

2.2. Task Statement 1.2: Design secure workloads and applications

Kiến thức yêu cầu:

  • Application configuration và credentials security
  • AWS service endpoints (public vs private)
  • Control ports, protocols, network traffic
  • Secure application access patterns
  • Security services: Cognito, GuardDuty, Macie
  • Threat vectors: DDoS, SQL injection

Kỹ năng kiểm tra:

  • Design VPC architectures: security groups, route tables, NACLs, NAT gateways
  • Network segmentation: public subnets vs private subnets
  • Integrate security services: Shield, WAF, IAM Identity Center, Secrets Manager
  • Secure external connections: VPN, Direct Connect

2.3. Task Statement 1.3: Determine appropriate data security controls

Kiến thức yêu cầu:

  • Data access và governance
  • Data recovery strategies
  • Data retention và classification
  • Encryption và key management

Kỹ năng kiểm tra:

  • Align AWS tech với compliance requirements
  • Encrypt data at rest (KMS) và in transit (ACM, TLS)
  • Implement access policies cho encryption keys
  • Data backups và replications
  • Policies cho data access, lifecycle, protection
  • Rotate encryption keys và renew certificates
Lưu ý quan trọng cho D1

Domain 1 chiếm tỷ trọng lớn nhất (30%) và có 3 task statements — mỗi task đều rộng. Đặc biệt chú ý:

  • IAM policy evaluation logic (explicit deny > explicit allow > implicit deny)
  • Phân biệt Security Groups vs NACLs (stateful vs stateless)
  • Phân biệt KMS CMK types (AWS managed, Customer managed, AWS owned)
  • Shared Responsibility Model luôn là nền tảng cho mọi câu hỏi security

3. Domain 2 — Design Resilient Architectures (26%)

Domain lớn thứ 2. 26% trọng số = khoảng 16-17 câu scored. Tập trung vào HA, DR, loosely coupled, microservices.

3.1. Task Statement 2.1: Design scalable and loosely coupled architectures

Kiến thức yêu cầu:

  • API creation: API Gateway, REST API
  • Managed services: Transfer Family, SQS, Secrets Manager
  • Caching strategies (ElastiCache, CloudFront, DAX)
  • Microservices principles: stateless vs stateful workloads
  • Event-driven architectures (EventBridge, SNS, SQS)
  • Horizontal vs Vertical scaling
  • Edge accelerators, CDN
  • Container migration và orchestration (ECS, EKS)
  • Load balancing, multi-tier architectures
  • Pub/Sub messaging, queuing
  • Serverless: Fargate, Lambda
  • Read replicas, workflow orchestration (Step Functions)

Kỹ năng kiểm tra:

  • Design event-driven, microservice, multi-tier architectures
  • Xác định scaling strategies
  • Xác định AWS services cần thiết cho loose coupling
  • Khi nào dùng containers vs khi nào dùng serverless
  • Recommend compute, storage, networking, database phù hợp

3.2. Task Statement 2.2: Design highly available and/or fault-tolerant architectures

Kiến thức yêu cầu:

  • AWS Global Infrastructure (AZs, Regions, Route 53)
  • Managed services: Comprehend, Polly (context: HA của managed services)
  • Networking basics: route tables
  • DR strategies: Backup/Restore, Pilot Light, Warm Standby, Active-Active, RPO, RTO
  • Distributed design patterns, failover strategies
  • Immutable infrastructure
  • Load balancing (ALB), Proxy concepts (RDS Proxy)
  • Service quotas và throttling
  • Storage options: durability, replication
  • Workload visibility: X-Ray

Kỹ năng kiểm tra:

  • Automation strategies cho infrastructure integrity
  • HA/fault-tolerant across Regions hoặc AZs
  • Metrics cho HA solution
  • Mitigate single points of failure
  • Data durability và availability
  • Chọn DR strategy phù hợp business requirements
  • Improve reliability cho legacy applications
D1 + D2 = 56% đề thi

Hai domain này chiếm hơn nửa bài thi. Nắm vững Security + Resilience = đã nắm được hơn nửa số điểm.

4. Domain 3 — Design High-Performing Architectures (24%)

24% trọng số = khoảng 15-16 câu scored. Tập trung vào chọn đúng service cho đúng use case.

4.1. Task Statement 3.1: High-performing storage solutions

Kiến thức yêu cầu (Knowledge of):

  • Hybrid storage: kết hợp on-premises với AWS storage (Storage Gateway, DataSync)
  • S3: object storage, phân biệt storage classes (Standard, IA, Glacier), lifecycle policies
  • EBS: block storage gắn vào EC2, phân biệt volume types (gp3, io2, st1, sc1)
  • EFS: shared file system cho nhiều EC2 instances (NFS protocol, elastic capacity)
  • FSx: managed file systems chuyên dụng (FSx for Windows = SMB, FSx for Lustre = HPC)
  • Storage access patterns: random vs sequential, read-heavy vs write-heavy → ảnh hưởng chọn loại storage
  • Caching: CloudFront cho static content, ElastiCache/DAX cho database queries

Kỹ năng kiểm tra (Skills in):

  • Chọn storage service phù hợp performance yêu cầu (IOPS, throughput, latency)
  • Thiết kế storage auto scaling (S3 tự động, EBS cần resize, EFS elastic)
  • Xác định khi nào dùng caching layer (CloudFront, ElastiCache, DAX)
  • Thiết kế hybrid storage architecture với Storage Gateway

4.2. Task Statement 3.2: High-performing elastic compute solutions

Kiến thức yêu cầu (Knowledge of):

  • Compute services: EC2 (general purpose, compute, memory, storage optimized), Lambda, Fargate, Batch, EMR
  • Distributed computing: xử lý data lớn trên nhiều nodes (EMR/Hadoop, Spark)
  • Queuing và messaging: SQS (decouple), SNS (fan-out), giúp compute scale independently
  • Auto Scaling: EC2 Auto Scaling Groups (target tracking, step, scheduled), AWS Auto Scaling (multi-resource)
  • Serverless: Lambda (event-driven, 15min max), Fargate (containers không quản lý EC2)
  • Container orchestration: ECS (AWS-native, simpler), EKS (Kubernetes, portable)
  • Instance types: M (general), C (compute), R (memory), I/D (storage), P/G (GPU) — chọn theo workload

Kỹ năng kiểm tra (Skills in):

  • Decouple workloads để scale từng component độc lập
  • Chọn scaling strategy phù hợp (target tracking cho steady, step cho spiky)
  • So sánh compute options: EC2 vs Lambda vs Fargate vs ECS (cost, control, complexity)
  • Xác định resource sizing: EC2 instance type, Lambda memory allocation
  • Khi nào dùng Spot Instances (stateless, fault-tolerant) vs On-Demand vs Reserved

4.3. Task Statement 3.3: High-performing database solutions

Kiến thức yêu cầu (Knowledge of):

  • Database engines: RDS (MySQL, PostgreSQL, MariaDB, Oracle, SQL Server), Aurora (MySQL/PostgreSQL compatible, 5x performance)
  • NoSQL options: DynamoDB (key-value, single-digit ms), DocumentDB (MongoDB), Neptune (graph), Keyspaces (Cassandra)
  • Read replicas: RDS up to 5, Aurora up to 15 — phân tải read queries
  • Caching: ElastiCache Redis (persistence, pub/sub, replication) vs Memcached (multi-thread, simple)
  • DAX: DynamoDB Accelerator — microsecond latency cho DynamoDB reads
  • Database capacity planning: RDS instance sizing, DynamoDB capacity modes (provisioned vs on-demand, RCU/WCU)
  • Data access patterns: read-heavy → read replicas + caching, write-heavy → DynamoDB/Aurora
  • Database Proxy: RDS Proxy quản lý connection pooling, giảm failover time

Kỹ năng kiểm tra (Skills in):

  • Thiết kế multi-AZ + read replica architecture cho high availability + performance
  • Chọn đúng database engine theo use case (relational vs key-value vs document vs graph)
  • Implement caching strategy: query-level (ElastiCache) vs item-level (DAX)
  • Tối ưu database performance: indexing, partitioning, connection management
  • Chọn serverless database khi traffic unpredictable (Aurora Serverless, DynamoDB on-demand)

4.4. Task Statement 3.4: High-performing network architectures

Kiến thức yêu cầu (Knowledge of):

  • Edge services: CloudFront (CDN, caching static+dynamic), Global Accelerator (TCP/UDP acceleration, anycast IP)
  • Phân biệt CloudFront vs Global Accelerator: CloudFront = content caching, GA = non-HTTP/TCP acceleration + static IP
  • Network design: VPC, subnets, route tables, NAT Gateway, Internet Gateway
  • DNS: Route 53 routing policies (simple, weighted, latency, failover, geolocation, geoproximity)
  • Load balancing: ALB (HTTP/HTTPS, path-based), NLB (TCP/UDP, ultra-low latency), GLB (3rd party appliances)
  • VPN và Direct Connect: Site-to-Site VPN (encrypted over internet), Direct Connect (dedicated, consistent latency)
  • Transit Gateway: hub cho kết nối nhiều VPCs + on-premises (thay thế VPC peering phức tạp)

Kỹ năng kiểm tra (Skills in):

  • Thiết kế edge caching strategy: CloudFront origin (S3, ALB, custom), TTL, cache invalidation
  • Chọn Route 53 routing policy phù hợp scenario (latency-based cho global, failover cho DR)
  • So sánh ALB vs NLB: HTTP layer-7 routing vs TCP layer-4 performance
  • Network architecture cho multi-region: Transit Gateway + VPC peering + Route 53
Trọng điểm Domain 3

D3 chiếm 24% đề thi (~16 câu). Câu hỏi thường là "Which service/configuration provides the BEST performance?". Phải nắm rõ: (1) EBS volume types + IOPS limits, (2) Database engine selection matrix, (3) CloudFront vs Global Accelerator, (4) ALB vs NLB use cases.

5. Domain 4 — Design Cost-Optimized Architectures (20%)

20% trọng số = khoảng 13 câu scored. 4 task statements — nhiều nhất trong các domain nhưng trọng số thấp nhất.

5.1. Task Statement 4.1: Cost-optimized storage

Kiến thức yêu cầu (Knowledge of):

  • S3 storage classes: Standard → IA → OneZone-IA → Glacier Instant → Glacier Flexible → Glacier Deep Archive (cost giảm, retrieval time tăng)
  • S3 lifecycle policies: tự động chuyển objects giữa classes theo tuổi (transition rules) hoặc xoá (expiration rules)
  • EBS volume types: gp3 (mặc định, cân bằng), io2 (mission-critical, đắt), st1 (throughput HDD), sc1 (cold HDD, rẻ nhất)
  • Backup strategies: AWS Backup (centralized), EBS Snapshots (incremental), S3 Cross-Region Replication
  • Hybrid storage: Storage Gateway (File/Volume/Tape), DataSync (online data transfer), Transfer Family (SFTP/FTP to S3)
  • S3 Requester Pays: người request trả cost thay vì bucket owner — dùng cho shared datasets
  • S3 Intelligent-Tiering: tự động move objects giữa tiers dựa trên access patterns — phù hợp khi không biết pattern

Kỹ năng kiểm tra (Skills in):

  • Thiết kế S3 lifecycle strategy tối ưu cost (vd: IA sau 30 ngày, Glacier sau 90 ngày, delete sau 365 ngày)
  • Chọn EBS volume type cân bằng performance vs cost
  • Xác định backup/archival strategy phù hợp RTO/RPO yêu cầu
  • So sánh storage options cho large-scale data (S3 vs EFS vs FSx)

5.2. Task Statement 4.2: Cost-optimized compute

Kiến thức yêu cầu (Knowledge of):

  • Purchasing options: On-Demand (linh hoạt, đắt nhất) → Savings Plans (linh hoạt, tiết kiệm ~66%) → Reserved (cam kết instance type, ~72%) → Spot (gián đoạn OK, ~90% off)
  • Savings Plans vs Reserved: Compute SP (flexible across family/region/OS) vs EC2 Instance SP (locked, highest discount) vs Standard RI vs Convertible RI
  • Spot Instances: dùng cho batch processing, CI/CD, stateless workloads — có thể bị reclaim với 2-minute warning
  • Right-sizing: dùng CloudWatch CPU/memory metrics + AWS Compute Optimizer để chọn instance size phù hợp
  • Serverless cost: Lambda pricing = request count + duration × memory — rẻ cho sporadic workloads, đắt cho sustained high-throughput
  • Container cost: Fargate pricing theo vCPU/memory — so sánh với EC2 cho long-running containers
  • Hybrid compute: Outposts (AWS hardware on-prem), Snowball Edge (edge computing + data transfer)

Kỹ năng kiểm tra (Skills in):

  • Chọn pricing model phù hợp workload pattern (steady → RI/SP, variable → On-Demand/Spot mix)
  • Thiết kế scaling strategy tối ưu cost (scale-in nhanh, minimum capacity thấp)
  • So sánh Lambda vs Fargate vs EC2 dựa trên cost cho từng scenario
  • Right-sizing workflow: CloudWatch → Compute Optimizer → resize → monitor

5.3. Task Statement 4.3: Cost-optimized database

Kiến thức yêu cầu (Knowledge of):

  • Database engine cost: Aurora (đắt hơn RDS nhưng performance cao hơn, có thể rẻ hơn tổng thể), DynamoDB on-demand (pay-per-request, tốt cho unpredictable)
  • Aurora Serverless: auto-scale capacity, pay-per-ACU — lý tưởng cho dev/test, infrequent workloads
  • DynamoDB pricing: Provisioned (stable, rẻ hơn nếu biết workload) vs On-demand (variable, đắt hơn per-request nhưng không waste)
  • Caching để giảm DB cost: ElastiCache/DAX giảm read load → giảm cần database capacity → giảm cost
  • Read replicas: offload reads → giảm primary instance size cần thiết
  • Database connections: RDS Proxy giảm connection overhead, cải thiện resource utilization
  • Migration: DMS cho database migration, SCT cho schema conversion — heterogeneous (Oracle → Aurora) vs homogeneous (MySQL → RDS MySQL)

Kỹ năng kiểm tra (Skills in):

  • Chọn database service tối ưu cost-performance ratio (RDS vs Aurora vs DynamoDB)
  • Thiết kế caching strategy giảm database cost
  • Xác định khi nào dùng serverless database (Aurora Serverless, DynamoDB on-demand) vs provisioned
  • Tối ưu DynamoDB cost: chọn partition key tốt, dùng GSI sparse index, TTL xoá data cũ

5.4. Task Statement 4.4: Cost-optimized network architectures

Kiến thức yêu cầu (Knowledge of):

  • Data transfer costs: inbound = FREE, outbound to internet = ,𝑐𝑟𝑜𝑠𝑠−𝐴𝑍=$0.01/𝐺𝐵𝑒𝑎𝑐ℎ𝑤𝑎𝑦,𝑐𝑟𝑜𝑠𝑠−𝑅𝑒𝑔𝑖𝑜𝑛=
  • NAT Gateway cost: $0.045/hour + $0.045/GB processing — có thể rất đắt cho high-traffic. NAT Instance rẻ hơn (EC2) nhưng không HA
  • VPC Endpoints: Gateway Endpoint (S3, DynamoDB) = FREE, Interface Endpoint (PrivateLink) = $/hour + $/GB
  • Direct Connect vs VPN: DC đắt hơn upfront nhưng rẻ per-GB cho high-volume data transfer, VPN qua internet
  • CloudFront cost optimization: caching giảm origin requests → giảm data transfer cost từ origin
  • Transit Gateway: tối ưu routing cho nhiều VPCs thay vì mesh VPC peering (giảm complexity = giảm cost vận hành)
  • S3 Transfer Acceleration: đắt hơn standard upload nhưng nhanh hơn cho large files từ xa

Kỹ năng kiểm tra (Skills in):

  • Thiết kế network tối ưu data transfer cost (keep traffic trong cùng AZ khi có thể)
  • Chọn NAT Gateway vs VPC Gateway Endpoint (S3/DynamoDB traffic → dùng Gateway Endpoint, FREE)
  • So sánh Direct Connect vs VPN dựa trên volume data và budget
  • Dùng CloudFront giảm origin load và data transfer cost
  • Thiết kế multi-VPC architecture tối ưu cost (Transit Gateway vs VPC peering)
Cost Optimization Patterns — Quy tắc vàng
  • Compute: steady workload → Reserved/Savings Plans, variable → mix On-Demand + Spot, sporadic → Lambda
  • Storage: biết access pattern → lifecycle rules, không biết → Intelligent-Tiering
  • Network: S3/DynamoDB → Gateway Endpoint (FREE), tránh NAT Gateway cho traffic nội bộ
  • Database: unpredictable → serverless/on-demand, steady → provisioned + caching layer

Tại sao cross-domain quan trọng?

Khi ôn 1 service (ví dụ S3), hãy ôn theo tất cả góc nhìn: security (encryption), performance (storage classes), cost (lifecycle policies). Đề thi thường kết hợp nhiều domain trong 1 câu hỏi.

8. Mức độ sâu kiến thức theo Domain

Hướng dẫn ôn tập theo Tier

Tier Cần biết gì cụ thể Ví dụ cụ thể
🔴 Tier 1: Biết sâu Limits, pricing details, best practices, troubleshooting, so sánh chi tiết giữa các options, security implications IAM policy evaluation logic (explicit Deny > Allow), EBS IOPS limits (gp3: 16k, io2: 64k), VPC subnet design, DR RTO/RPO cho từng strategy
🟡 Tier 2: Biết khá Core features, khi nào dùng, so sánh cơ bản với alternatives, integration patterns Auto Scaling target tracking vs step, ALB path-based routing, S3 lifecycle transition rules, EC2 pricing models
🟢 Tier 3: Biết mặt Service làm gì, 1-2 main use cases, khi nào đề nhắc đến → chọn service này Athena = SQL trên S3, Glue = ETL serverless, EMR = big data Hadoop/Spark, Macie = PII detection

Chi tiết mức độ "biết sâu" cho Tier 1:

Topic Cần nhớ cụ thể
IAM Policy evaluation (DEN trước SÁNG), SCP scope, Permission Boundaries, Cross-account roles
VPC SG (stateful, allow only) vs NACL (stateless, allow+deny), route tables, NAT vs IGW, VPC Endpoints
S3 7 storage classes + transition rules, encryption (SSE-S3/SSE-KMS/SSE-C), versioning, replication
EC2 Instance families (M/C/R/I/P), pricing (On-Demand/RI/SP/Spot), placement groups, ENI
RDS/Aurora Multi-AZ vs Read Replica, Aurora 5x perf, failover time, storage auto scaling
DynamoDB Partition key design, RCU/WCU calculation, DAX caching, Global Tables, Streams
ELB ALB (L7, HTTP) vs NLB (L4, TCP, static IP) vs GLB (L3, 3rd party), health checks
KMS CMK vs AWS-managed, automatic rotation, envelope encryption, key policies
Chiến lược ôn tập hiệu quả
  1. Tuần 1-2: Focus Tier 1 — học sâu, làm labs, hiểu "tại sao" chứ không chỉ "cái gì"
  2. Tuần 3: Tier 2 — nắm core features + so sánh cơ bản
  3. Tuần 4: Tier 3 — skim qua, nhớ tên + use case chính
  4. 3 ngày cuối: Review decision trees + keyword patterns + làm practice exams
  5. Quy tắc 80/20: Tier 1 chiếm 60-70% câu hỏi → dành 70% thời gian ôn cho nó
