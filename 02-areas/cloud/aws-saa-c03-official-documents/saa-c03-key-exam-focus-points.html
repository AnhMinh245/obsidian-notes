SAA-C03 — Trọng điểm kỳ thi và chiến lược

2. Trọng điểm Domain 1 — Security (30%)

2.1. IAM — Trung tâm của Security

Phải biết sâu:

  • IAM Policy evaluation: Explicit Deny > Explicit Allow > Implicit Deny
  • Policy types: Identity-based, Resource-based, Permissions boundary, SCPs, Session policies
  • Root user: chỉ dùng cho tasks không thể delegate (thay đổi billing, close account)
  • MFA: virtual (app), hardware (U2F key), SMS (không recommended)
  • Cross-account: STS AssumeRole pattern
  • Cognito: User Pools (authn) vs Identity Pools (authz) — bẫy phổ biến

2.2. Encryption — KMS là trung tâm

Loại key Ai tạo Ai quản lý Rotate Use case
AWS owned keys AWS AWS AWS tự rotate Default encryption (DynamoDB, S3)
AWS managed keys AWS AWS Tự động mỗi năm aws/service (aws/s3, aws/ebs)
Customer managed keys Customer Customer Có thể bật auto (mỗi năm) hoặc manual Custom policies, audit, cross-account

Bảng Encryption Scenarios phổ biến trong đề:

Scenario Solution
Encrypt EBS volume Enable EBS encryption (KMS) — bật default encryption ở account level
Encrypt S3 objects SSE-S3 (default), SSE-KMS (audit trail), SSE-C (customer key), client-side
Encrypt data in transit TLS/SSL — ACM cho certificates, enforce HTTPS
Encrypt RDS Enable encryption at creation time (không thể encrypt RDS đã tạo)
Key phải lưu trong hardware riêng, FIPS 140-2 Level 3 CloudHSM (không phải KMS)
Cross-account encrypt Customer managed key + key policy cho target account

2.3. Network Security — VPC Flow

So sánh cốt lõi:

Feature Security Group NACL
Level Instance (ENI) Subnet
State Stateful (return traffic auto) Stateless (phải rule cả 2 chiều)
Rules Allow only Allow AND Deny
Default Deny all inbound, allow all outbound Allow all (default NACL)
Evaluation Tất cả rules cùng lúc Theo thứ tự số rule (lowest first)
Association Nhiều SG per instance 1 NACL per subnet
🧠 Mẹo ghi nhớ — Security
  • IAM Policy evaluation: "DEN trước SÁNG" → Explicit Deny > Explicit Allow > Implicit Deny (Deny luôn thắng)
  • SG vs NACL: "SG = Stateful Guard (chỉ Allow), NACL = Network ACL (Allow + Deny, Stateless)"
  • KMS key types: "AMC" = AWS managed → Customer managed → AWS owned (mức control tăng dần)
  • Cognito: "UP = User login (authn), IP = AWS access (authz)" — User Pools = authentication, Identity Pools = authorization

3.3. SQS vs SNS vs EventBridge — Decoupling Decision

🧠 Mẹo ghi nhớ — Resilient
  • DR strategies: "B-P-W-M" = Backup → Pilot Light → Warm Standby → Multi-site (cost tăng dần, RTO giảm dần)
  • SQS vs SNS: "SQS = hàng đợi (Queue, Pull), SNS = phát thanh (Pub/Sub, Push)"
  • Decoupling pattern: "SNS + SQS = Fan-out pattern" — 1 message gửi vào SNS → N SQS queues nhận

4.3. EBS Volume Types — Cheat Sheet

Type Category Max IOPS Max Throughput Use Case
gp3 SSD General 16,000 1,000 MB/s Default choice cho hầu hết workloads
gp2 SSD General 16,000 250 MB/s Legacy, burst credits
io2 Block Express SSD Provisioned 256,000 4,000 MB/s Critical databases, SAP HANA
io1 SSD Provisioned 64,000 1,000 MB/s Legacy provisioned IOPS
st1 HDD Throughput 500 500 MB/s Big data, log processing
sc1 HDD Cold 250 250 MB/s Infrequent access, cheapest
Mẹo thi: EBS
  • gp3 là default choice trong đề thi (trừ khi cần extreme IOPS)
  • Instance Store cho highest performance nhưng mất dữ liệu khi stop/terminate
  • io2 khi đề nói "mission-critical", "sub-millisecond latency"
  • st1/sc1 KHÔNG thể dùng làm boot volume
🧠 Mẹo ghi nhớ — High Performance
  • Database: "RDS = SQL truyền thống, Aurora = RDS on steroids (5x perf), DynamoDB = NoSQL key-value single-digit ms"
  • EBS types: "gp3 = mặc định, io2 = cao cấp IOPS, st1 = throughput HDD, sc1 = cold HDD rẻ nhất"
  • Caching: "Redis = đa năng (persistence, pub/sub, replication), Memcached = đơn giản (multi-thread, no persistence)"

5. Trọng điểm Domain 4 — Cost Optimization (20%)

5.1. EC2 Pricing Decision Framework

5.2. Data Transfer Cost — Bẫy số 1 trong đề

Transfer Type Cost Ví dụ
Inbound (vào AWS) FREE Upload to S3
Cùng AZ, private IP FREE EC2 to RDS cùng AZ
Cùng AZ, public/EIP ~$0.01/GB EC2 to EC2 qua public IP (tránh!)
Cross-AZ ~$0.01/GB mỗi chiều EC2 AZ-a to RDS AZ-b
Cross-Region ~$0.02/GB S3 CRR, RDS cross-region replica
Internet outbound Tiered ($0.09-$0.05/GB) Serve content to users
NAT Gateway processing $0.045/GB Private subnet → Internet
VPC Endpoint $0.01/GB (hoặc free cho Gateway) S3, DynamoDB = Gateway (free!)
Bẫy phổ biến
  • NAT Gateway đắt hơn bạn nghĩ: $0.045/hour + $0.045/GB processed. Dùng VPC Endpoint (Gateway) cho S3/DynamoDB để tránh NAT charges.
  • Cross-AZ charges: Multi-AZ là best practice cho HA, nhưng đề Cost sẽ hỏi trade-off.
  • S3 Gateway Endpoint: FREE — không tốn data transfer qua NAT.

5.3. S3 Storage Classes — Cost Ladder

🧠 Mẹo ghi nhớ — Cost Optimization
  • EC2 pricing: "O-R-S-S-D" = On-Demand → Reserved → Savings Plans → Spot → Dedicated (từ linh hoạt/đắt → cam kết/rẻ cho steady workload)
  • S3 classes: "S-IT-IA-OZ-GI-GF-GD" = Standard → Intelligent-Tiering → IA → OneZone-IA → Glacier Instant → Glacier Flexible → Glacier Deep (cost giảm, retrieval time tăng)
  • VPC Gateway Endpoint cho S3/DynamoDB = FREE — tránh NAT Gateway ($0.045/GB processing fee)

8. Câu hỏi mẫu theo pattern — Tự test

Pattern 1: "MOST cost-effective"

Một công ty chạy batch processing jobs hàng đêm. Jobs có thể bị interrupt và restart. Phương án nào MOST cost-effective?

  • A. On-Demand Instances
  • B. Reserved Instances (1 year)
  • C. Spot Instances ✅
  • D. Dedicated Hosts

Lý do: "can be interrupted" + "cost-effective" = Spot (tiết kiệm đến 90%).

Pattern 2: "LEAST operational overhead"

Một startup cần deploy REST API. Họ muốn LEAST operational overhead. Solution nào phù hợp?

  • A. EC2 + ALB + Auto Scaling
  • B. API Gateway + Lambda ✅
  • C. ECS + Fargate
  • D. Elastic Beanstalk

Lý do: "least operational overhead" = serverless. API Gateway + Lambda = zero server management.

Pattern 3: "HIGHEST availability"

Một ứng dụng cần HIGHEST availability cho database layer. Solution nào đúng?

  • A. RDS Single-AZ with automated backups
  • B. Aurora Multi-AZ with read replicas across regions ✅
  • C. DynamoDB with on-demand capacity
  • D. RDS Read Replica in same region

Lý do: "highest availability" = Multi-AZ + cross-region. Aurora Global Database = RPO gần 0.

Pattern 4: Security — IAM Policy Conflict

Một nhân viên được gán IAM Policy cho phép full access S3 (s3:*). Tuy nhiên, SCP ở Organization level có explicit Deny trên s3:DeleteObject. Nhân viên này có thể xoá objects trong S3 không?

  • A. Có — IAM policy Allow overrides SCP
  • B. Không — Explicit Deny trong SCP luôn thắng ✅
  • C. Có — nếu bucket policy cũng Allow
  • D. Tuỳ thuộc vào Permission Boundary

Phân tích keyword: "SCP", "explicit Deny", "s3:DeleteObject"

Loại trừ:

  • A sai: SCP không bao giờ bị override bởi IAM policy
  • C sai: Bucket policy Allow không thắng explicit Deny
  • D sai: Permission Boundary cũng không thắng explicit Deny ở SCP

Đáp án + Giải thích: B — Quy tắc "DEN trước SÁNG": Explicit Deny luôn thắng mọi Allow ở mọi level (IAM, SCP, Resource policy). SCP đặt boundary tối đa cho mọi account trong Organization.

Pattern 5: Decoupling — Fan-out

Một ứng dụng e-commerce cần gửi thông báo khi có đơn hàng mới: (1) xử lý payment, (2) gửi email xác nhận, (3) cập nhật inventory. Mỗi task do một Lambda function riêng xử lý. Giải pháp nào decouple tốt nhất?

  • A. Lambda gọi 3 Lambda khác trực tiếp (synchronous invoke)
  • B. Gửi message vào 1 SQS queue, 3 Lambdas poll cùng queue
  • C. SNS topic → 3 SQS queues → 3 Lambdas ✅
  • D. EventBridge rule trigger 3 Lambdas song song

Phân tích keyword: "3 tasks riêng biệt", "decouple", "1 event → N consumers"

Loại trừ:

  • A sai: Tight coupling, Lambda gọi nhau = không decouple
  • B sai: SQS standard queue → mỗi message chỉ 1 consumer nhận (không fan-out)
  • D không sai nhưng: EventBridge phù hợp hơn cho event routing phức tạp, pattern đơn giản này SNS+SQS là classic

Đáp án + Giải thích: C — Fan-out pattern: SNS topic nhận 1 message → push đến 3 SQS queues → mỗi Lambda poll riêng queue của mình. Đảm bảo mỗi consumer nhận tất cả messages + buffering qua SQS.

Pattern 6: Migration — Large Data Transfer

Công ty có 50TB dữ liệu on-premises. Kết nối internet 100 Mbps. Cần migrate lên AWS S3 trong vòng 1 tuần. Phương án nào phù hợp nhất?

  • A. S3 Transfer Acceleration
  • B. AWS DataSync qua internet
  • C. AWS Snowball Edge ✅
  • D. Multipart upload trực tiếp lên S3

Phân tích keyword: "50TB", "100 Mbps", "1 tuần"

Loại trừ:

  • A, B, D đều dùng internet: 50TB ÷ 100 Mbps ≈ 46 ngày — vượt xa deadline 1 tuần
  • Network-based transfer không thể đáp ứng yêu cầu thời gian

Đáp án + Giải thích: C — Snowball Edge chứa được 80TB, ship vật lý đến data center trong 4-6 ngày làm việc. Khi network transfer time vượt 1 tuần → Snow Family là phương án đúng.

Pattern 7: Serverless — API Backend

Một startup cần xây dựng REST API cho mobile app. Traffic biến động mạnh (từ 0 đến hàng nghìn request/giây). Yêu cầu: pay-per-request, không quản lý server, auto-scale. Giải pháp nào phù hợp?

  • A. EC2 Auto Scaling Group + ALB
  • B. ECS Fargate + ALB
  • C. API Gateway + Lambda + DynamoDB ✅
  • D. Elastic Beanstalk + RDS

Phân tích keyword: "pay-per-request", "không quản lý server", "traffic biến động", "auto-scale"

Loại trừ:

  • A sai: EC2 = phải quản lý server (patching, scaling config)
  • B sai: Fargate ít overhead hơn EC2 nhưng vẫn cần manage task definitions, ALB
  • D sai: Beanstalk vẫn chạy trên EC2, RDS có fixed cost

Đáp án + Giải thích: C — Full serverless stack: API Gateway (managed API layer, pay-per-call) + Lambda (compute, pay-per-invocation) + DynamoDB (on-demand mode, pay-per-request). Zero server management, scale tự động từ 0.

Pattern 8: Analytics — Data Lake Query

Data team lưu trữ 10TB logs dạng CSV/Parquet trên S3. Họ cần chạy ad-hoc SQL queries để phân tích mà không muốn load dữ liệu vào database riêng và muốn pay-per-query. Giải pháp nào phù hợp?

  • A. Amazon Redshift
  • B. RDS PostgreSQL
  • C. Amazon Athena ✅
  • D. Amazon EMR

Phân tích keyword: "SQL trên S3", "không load vào database", "pay-per-query", "ad-hoc"

Loại trừ:

  • A sai: Redshift cần provision cluster (có cost cố định), phải load data
  • B sai: RDS là database riêng, phải ETL data vào
  • D sai: EMR cần manage cluster (Hadoop/Spark), operational overhead cao

Đáp án + Giải thích: C — Athena = serverless SQL query engine trực tiếp trên S3. Pay-per-query ($5/TB scanned), không cần provision, hỗ trợ CSV/JSON/Parquet/ORC. Dùng Parquet + partition để giảm cost scan.

Pattern 9: Hybrid — Reliable Connection

Công ty có data center on-premises kết nối với AWS VPC. Ứng dụng mission-critical yêu cầu consistent low-latency và dedicated bandwidth. Họ cũng cần encrypted connection làm backup. Giải pháp nào đúng?

  • A. Site-to-Site VPN qua internet
  • B. AWS Direct Connect + Site-to-Site VPN backup ✅
  • C. AWS Client VPN
  • D. VPC Peering

Phân tích keyword: "mission-critical", "consistent low-latency", "dedicated bandwidth", "encrypted backup"

Loại trừ:

  • A sai: VPN qua internet → latency không consistent, bandwidth shared
  • C sai: Client VPN cho remote users, không phải site-to-site
  • D sai: VPC Peering chỉ giữa 2 VPCs trong AWS, không kết nối on-prem

Đáp án + Giải thích: B — Direct Connect = dedicated physical connection (consistent latency, high bandwidth). VPN backup = encrypted fallback khi DC gặp sự cố. Direct Connect không mã hoá mặc định nên VPN bổ sung encryption layer.

Pattern 10: Encryption — Key Rotation

Compliance yêu cầu: (1) tất cả data at rest phải encrypted, (2) dùng customer-managed encryption keys, (3) keys phải automatic rotation hàng năm, (4) có audit trail cho mọi key usage. Giải pháp nào đáp ứng?

  • A. SSE-S3 (AWS managed key)
  • B. SSE-C (customer-provided key)
  • C. AWS KMS Customer Managed Key (CMK) với automatic rotation ✅
  • D. CloudHSM

Phân tích keyword: "customer-managed", "automatic rotation", "audit trail"

Loại trừ:

  • A sai: SSE-S3 dùng AWS managed key → không phải customer-managed
  • B sai: SSE-C → customer phải tự manage, tự rotate, không có audit trail trong AWS
  • D sai: CloudHSM cho full control nhưng phải tự implement rotation, overhead cao

Đáp án + Giải thích: C — KMS CMK: customer-managed (toàn quyền key policy), enable automatic rotation (rotate mỗi năm, giữ old key versions để decrypt data cũ), CloudTrail tự động log mọi API call đến KMS → đáp ứng cả 4 yêu cầu compliance.
